프론트 엔드를 공부하면서 DOM 트리에 대한 이해는 아주 핵심적이다. 코드가 그려내는 요소들이 사용자의 화면에 보여지기까지 브라우저가 어떻게 구성되는지를 이해하지 못하면 비효율적인 코드를 작성하여 렌더링 효율을 떨어뜨리기 십상이기 때문이다. React에서 Virtual DOM 기반 SPA 렌더링의 동작방식은 어느 정도 이해하고 있지만, 그 이전에 DOM자체와 동작박식에 대한 이해가 부족하다는 것을 최근 느꼈다.

## 1. 브라우저 렌더링

사용자가 웹 사이트에 접속할 때, 브라우저는 해당 사이트 도메인으로부터 **자원을 전달**받는다. 자원은 HTML문서일수도, PDF문서나 이미지일 수도 있다. 이 때 HTML문서라면, 해당 문서를 바탕으로 **화면을 구성**한다. 단순하게 얘기하자면, **브라우저가 HTML문서를 화면에 그려내는 것**이 바로 **브라우저 렌더링**이다.

### 브라우저 렌더링 과정

브라우저 렌더링 과정을 단계별로 설명하자면 다음과 같다.

#### 1. DOM 트리 구축 (DOM Tree Construction)
#### 2. CSSOM 트리 구축 (CSS Object Model)
#### 3. 렌더 트리 구축 (Render Tree)
#### 4. 레이아웃 (Layout/Reflow)
#### 5. 페인팅 (Painting)
#### 6. 합성 (Compositing)

위 내용들을 이제부터 하나씩 알아보겠다.

## 2. 브라우저 렌더링 과정

### 1) DOM 트리 구축
브라우저는 먼저 HTML문서를 파싱하여 DOM 트리를 생성한다. HTML의 각 요소들이 **DOM 노드(문서의 구조를 표현하는 객체)**로 변환되고, 트리 구조를 이루어 문서 전체의 **계층 구조를 표현**한다.

### 2) CSSOM 트리 구축
DOM 트리가 웹 사이트의 **구조**라면, CSSOM 트리는 이름 그대로 스타일이다. HTML에 스타일을 입히는 CSS파일과 인라인 스타일을 파싱하여 CSSOM 트리를 구축하게 된다. DOM과 마찬가지로 각 **CSS규칙들이 CSSOM 노드**로 변환되고, 여기서 CSS 스타일의 우선순위가 계산된다.

### 3) 렌더 트리 구축
DOM 트리와 CSSOM 트리를 결합하여 렌더 트리를 생성한다. 렌더 트리는 곧 렌더링이 이루어질 트리이다. 그래서 렌더 트리에는 화면에 표시될 요소들만 포함된다(`display: none`등의 요소는 제외). 렌더 트리가 구축되면 브라우저는 화면에 표시할 요소들의 **레이아웃에 영향을 주는 속성**(박스 모델, 위치 등)과 **시각적 속성**(색상, 배경, 그림자 등)의 기본적인 스타일 정보들을 가지게 된다.

### 4) 레이아웃
앞서 계산한 스타일 정보를 가지고, 레이아웃 단계에서는 렌더 트리의 각 노드를 기반으로 뷰포트 내에 표시할 각 요소의 정확한 좌표를 결정한다. 이 때 상대적인 단위(%, em, rem 등)를 픽셀 단위로 변환하여 계산한다. 예를 들어, 부모 요소의 너비가 1000px이고 자식 요소가 `width: 50%`를 가지고 있다면, 자식 요소의 너비는 500px로 계산된다.

또한 레이아웃 단계에서는 각 요소의 박스 모델(콘텐츠 영역, 패딩, 테두리, 마진)을 모두 고려하여 요소가 실제로 차지하는 공간을 계산한다. 이 과정에서 요소들 간의 상대적 위치 관계도 결정되며, 이는 요소의 배치 방식(일반 흐름`static`, 플로트 `float`, 절대 위치 `absolute` 등)에 따라 달라진다.

### 5) 페인팅
레이아웃 단계에서 계산된 위치와 크기를 기반으로, 페인팅 단계에서는 실제 픽셀을 화면에 그린다. 이 단계에서는 각 요소의 시각적 속성(색상, 배경, 그림자 등)을 실제로 그리게 된다. 브라우저는 효율적인 렌더링을 위해 여러 레이어로 나누어 그리기도 한다. 예를 들어, `transform`이나 `opacity` 속성이 있는 요소는 별도의 레이어로 분리되어 그려질 수 있다.

### 6) 합성
페인팅 단계에서 생성된 여러 레이어를 하나의 이미지로 합성하는 단계이다. 이 과정에서 GPU를 활용할 수 있는 경우, GPU 가속을 통해 효율적인 렌더링을 수행한다. GPU 가속은 사용자의 하드웨어 환경과 브라우저 설정에 따라 활성화될 수 있으며, GPU를 사용할 수 없는 환경에서는 CPU를 통해 합성이 이루어진다. 

특히 애니메이션이나 스크롤과 같은 동적인 변화가 있을 때, GPU 가속이 활성화된 경우 더 부드러운 화면 전환이 가능하다. 예를 들어, `transform`이나 `opacity` 속성을 사용한 애니메이션은 GPU 가속이 활성화된 환경에서 더 부드럽게 처리된다.


## 3. 브라우저 렌더링 최적화
브라우저 렌더링 과정을 이해하는 것은 단순히 알고 싶어서가 아니다. 이해를 바탕으로 더 효율적인 개발을 하기 위해서다. 기본적인 렌더링 과정을 이해한 상태에서, 우리가 할 수 있는 몇가지 최적화 방법들이 있다.

### 1) 렌더링 성능 최적화

1. **불필요한 리플로우 최소화**

>리플로우(reflow): 렌더 트리의 변화로 레이아웃 단계가 다시 실행되는 것

- 레이아웃에 영향을 주는 속성(`width`, `height`, `position` 등) 변경을 최소화
- 여러 스타일 변경을 한 번에 처리(하나만 바뀌어도 전체가 리플로우 처리됨)
   
2. **효율적인 애니메이션 처리**
- `transform`과 `opacity`를 사용한 애니메이션 선호(리플로우를 발생시키지 않음)
- GPU 가속을 활용할 수 있는 속성 사용
   
3. **레이어 관리**
- 불필요한 레이어 생성 방지
- `will-change` 속성의 신중한 사용(과도한 사용은 메모리 낭비로 인한 성능 저하로 이어짐)

### 2) 첫 화면 렌더링 최적화 (CRP)

렌더링 성능 최적화와 함께 중요한 것이 첫 화면의 로딩 속도다. Critical Rendering Path(CRP)는 브라우저가 첫 화면을 그리기 위한 최적화된 경로를 의미한다. 사용자 경험을 위해 첫 화면을 최대한 빠르게 보여주는 것이 중요하다.

1. **필수 리소스 우선 로딩**
- 중요 CSS를 인라인으로 포함
- 중요 JavaScript는 지연 로딩
- 첫 화면에 필요한 리소스만 우선 로드

2. **리소스 로딩 최적화**
- CSS는 `<head>`에 배치
- JavaScript는 `<body>` 끝에 배치
- `async`/`defer` 속성 활용
- 이미지 지연 로딩

3. **불필요한 리소스 제거**
- 사용하지 않는 CSS/JS 제거
- 이미지 최적화
- 코드 분할(Code Splitting)

이러한 최적화 방법들은 서로 연관되어 있다. 렌더링 성능 최적화는 페이지가 로드된 후의 동작을 개선하고, CRP 최적화는 첫 화면의 로딩 속도를 개선한다. 두 가지 모두 사용자 경험을 향상시키는 중요한 요소다.

---

### 4. 개발 시 고려사항
위 최적화 방법들을 기반으로, 실제 웹 개발 시에는 다음과 같은 점들을 고려해야 한다.

#### **CSS 선택자 최적화**
  - 과도하게 복잡한 선택자 사용 지양
  - 불필요한 선택자 중첩 피하기

#### **리소스 로딩 최적화**
  - CSS 파일의 위치와 로딩 방식 고려
  - 중요 CSS를 인라인으로 포함
  
#### **반응형 디자인 고려**
  - 미디어 쿼리를 통한 효율적인 레이아웃 변경
  - 불필요한 리플로우 방지

사실 직관적으로 이해할 수 있는 기본적인 것들이지만, 브라우저 렌더링 과정을 이해하고 나서 보면 조금 더 깊게 체감되는 주의사항들이다.

## 7. 정리
브라우저 렌더링은 웹 페이지가 화면에 표시되기까지의 핵심적인 과정입니다. **HTML과 CSS를 파싱**하여 **DOM 트리와 CSSOM 트리를 구축**하고, 이를 결합하여 **렌더 트리를 생성**합니다. 이후 **레이아웃, 페인팅, 합성** 단계를 거쳐 최종적으로 화면에 표시됩니다. 이 과정을 이해하면 웹 페이지의 성능을 최적화하는 데 큰 도움이 됩니다. 특히 리플로우를 최소화하고, `transform`과 `opacity`를 활용한 효율적인 애니메이션을 구현할 수 있습니다. 현대적인 프레임워크들이 Virtual DOM을 사용하는 이유도 리플로우 발생 횟수를 줄여서 렌더링 과정을 최적화하기 위함입니다.
