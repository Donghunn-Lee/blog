지난 주 README를 코드와 대조하며 시작한 재정비가 이번으로 끝났다. 첫 글에서 순서를 "수정 먼저, README는 마지막"으로 정했고, 다섯 세션에 걸쳐 툴체인 교체 · 테스트 · CI · 결함 수정 · API 입력 검증을 끝낸 뒤 코드를 닫았었다. 남은 것은 README 재작성과 LICENSE 추가(D1)였다.

계획은 코드를 건드리지 않고 README만 쓰는 것이었다. 실제로는 README를 쓰기 전에 한 번, 쓴 뒤에 한 번 코드를 다시 열었고, 그 위에서 README와 LICENSE를 올려 재정비를 닫았다.

---

## 리뷰어 순서로 다시 훑은 것

지금까지의 대조는 "README가 하는 말이 코드에서 참인가"였다. README를 새로 쓰기 전에, 이번엔 채용 담당자가 볼 법한 순서 그대로 가 봤다. 저장소 첫 화면 → README → 라이브에서 한 판 → 소스. README가 주장하지 않는 자리에서 걸리는 것들이 나왔다.

| 발견 | 판정 |
|---|---|
| README의 블로그 링크 3개가 404 | **채택.** 글 제목을 고치며 주소가 바뀜 → 재작성에서 전부 교체 |
| 랭킹 보드 상위가 test · qqqq 같은 개발용 기록 | **채택.** 이전 전 보드 캡처에서 실제 기록 13건 복원 |
| 랭킹 응답 타입에 `id`가 있지만 SELECT에 없음 → 리스트 key가 전부 undefined | **채택.** SELECT에 `id` 추가 |
| 플레이 시간 `00:40:67` — 콜론 셋이 시:분:초로 읽힘 | **채택.** 초와 1/100초 사이만 점으로 |
| `useGame`에 소비처 없는 감도 state · effect로 파생하던 accuracy | **채택.** 제거 · 계산식 한 줄로 |
| Pointer Lock이 실패해도 게임이 시작됨 | **기각(한계로).** 클릭 제스처에서는 락이 성공하고 자동화 · 거부 환경에서만 재현 · 안내 UI는 설계가 필요 → Backlog(B12) |
| LICENSE 없음 · 저장소 About 비어 있음 | **채택.** D1 범위 · 저장소 설정 |

전부 README가 말하지 않는 자리였다. 대조는 README의 문장을 기준으로 삼기 때문에 문장이 없는 곳 — 죽은 링크, 라이브의 데이터, 타입만 있는 필드 — 은 보지 못한다. 수정은 각각 한두 줄이라 두 커밋으로 묶어 올리고 코드를 다시 닫았다. 닫았다고 쓴 지 하루 만이었다.

## README가 결국 말하는 것 — 설계 결정 넷

첫 글에서 설계 결정을 넷으로 고정했었다. 다섯 세션을 지나며 각 항목의 서술은 처음 README와 달라졌고, 무엇이 어떻게 바뀌었는지가 이 README의 본체다.

| 항목 | 처음 README | 지금 README |
|---|---|---|
| 1. 캔버스 렌더 루프 단일화 | "Canvas에는 오직 하나의 렌더 루프" · "모든 시간 제어를 단일 rAF 루프 기준으로 재설계" | 캔버스에 그리는 rAF는 하나 — 참. 원인은 두 루프가 같은 컨텍스트에 save · restore · translate를 다른 시점에 호출해 상태 스택이 꼬인 것. 결과 화면에서 되살아나던 루프 두 경로를 고친 것도 같은 절에 |
| 2. 스포너 | 단일 시간축의 일부로 서술 | `setInterval` → rAF 누적 시간 + 스톨 클램프, 그것만. 경과시간 틱 · 종료 유예 · 테두리 페이드는 통합하지 않았다고 `<details>`에 명시. 서버의 점수 상한이 이 스폰 간격에서 나온다는 연결 |
| 3. 훅 분리 | "587 → 323 lines" | 587 → 312 → 358, 단계별 커밋 여섯. 참조 안정성이 완료 기준에 없어 TIME이 멈춰 있던 경로를 본문에 |
| 4. 입력과 렌더의 경계 | 상태 동기화를 한 훅이 "중앙 관리" | 델타 큐잉 · 타겟 배열은 클래스 안에만 · state는 `targetCount` 하나 · Pointer Lock raw input · 좌표계 CSS px 통일 |

2번의 "시간축"은 이 시리즈 안에서 정정할 지점이다. #10에서 "두 시간축의 충돌"이라고 썼던 것은 지금 다시 보니 캔버스 컨텍스트를 공유하는 rAF 루프 둘의 문제였고, 그 말이 뒤에 "모든 시간 제어"라는 과장으로 자랐다. 이번 README는 그 단어를 쓰지 않는다.

> "모든 시간을 한 루프로"는 이 프로젝트의 주장이 아닙니다. — README, 설계 결정 2

## 적은 것과 제외한 것

품질 절은 도구가 확인하는 것만 적었다. `strict` · `any` 0 · 테스트 74건 · CI 4단계 · 입력 검증 · 미사용 export 0. "컨벤션을 점검했다" 같은 독자가 검증할 수 없는 문장은 뺐고, 알려진 한계는 Backlog 전부를 두 그룹으로 나눠 그대로 실었다.

가장 오래 고민한 것은 결함을 어디까지 적느냐였다. 기준은 리뷰어가 읽고 배울 메커니즘이 있는가 하나다. TIME이 멈춰 있던 것은 훅이 반환한 객체가 매 리렌더 새 객체라 `setInterval`이 틱 전에 재생성된 것, 즉 참조 안정성 이야기라 설계 결정 3의 본문에 적었다. 대신 기간이나 자책은 쓰지 않았다. 한계 목록도 같은 눈으로 다시 읽어, "왜 안 했지"가 서는 셋은 고치고 "굳이" 싶은 넷은 뺐고, 빠져 있던 큰 것 하나를 넣었다.

| 적음 | 뺌 |
|---|---|
| TIME 고정의 메커니즘 — 참조 안정성 → 틱 재생성 | 멈춰 있던 기간 · 자책 |
| 결과 화면에서 되살아나던 루프 두 경로와 수정 | "컨벤션 점검했음" 같은 검증 불가 문장 |
| 점수 검사 `score ≤ play_time × 10`은 개연성 검사 — `play_time`도 클라이언트 값이라 함께 부풀리면 통과 | 타이머 개수 · REAL 범위 · DPR 0.5px — 설계 선택이거나 너무 미세 |
| 「다시 한다면」 — 참조 안정성을 완료 기준에 · 게임 단계를 상태 하나로 | README 수치 교훈 — 문서 교훈이고 세 번 중복 |
| 알려진 한계 9 — Pointer Lock 실패 안내 · 게임 단계 구조 포함 | 고친 셋 — 경과시간 틱(초가 바뀔 때만 state 갱신, 12초 렌더 142 → 49) · 게임 시작 시 카메라 원점 · 유예 3초와 색상 구간의 결합 |
| 랭킹 복원 — 배경의 "데이터 미이관" 삭제 | 복원 경위 |

## 정리

- **D1 종결** — README 298줄 재작성 · 설계 결정 4 전부 코드 · 글과 대조 · 품질은 도구 수치만 · 알려진 한계 9 · LICENSE(MIT). 첫 글에서 꼽은 빈칸 넷(테스트 · CI · 입력 검증 · LICENSE) 전부 채움
- **리뷰어 순서 점검 — 수정 4 · 한계 1** — `id` 응답 · 시간 표기 · 감도 state · accuracy 파생 수정. Pointer Lock 실패 안내는 Backlog 신설(B12)
- **한계 목록 재검토 — 수정 3 · 추가 1 · 삭제 4** — 경과시간 틱 리렌더(12초 142 → 49) · 게임 시작 시 카메라 원점 · 유예 상수 결합 수정. 점수 검사는 개연성 검사라고 적음
- **랭킹 보드 복원** — 이전 전 캡처의 실제 기록 13건
- **재정비 종료** — 10-16 ~ 10-21 · 세션 6 · 커밋 26

"코드를 닫는다"를 세 번 썼다. 도구 점검 뒤, 리뷰어 순서로 훑은 뒤, 한계 목록을 리뷰어 눈으로 다시 읽은 뒤였고 마지막이 진짜였다. 대조는 README의 문장이 있는 자리만 보고, 리뷰어는 문장이 없는 자리와 한계 목록을 먼저 본다는 걸 이번에 알았다.
