> **요약** · TIME이 0에 멈춘 결함을 고치다가, 타겟 목록을 8ms마다 state로 복사하던 경로까지 지웠다.
> - **멈춘 TIME** — `gameActions`가 리렌더마다 새 객체라 경과 시간 effect가 재실행됐고, 거의 매 프레임 오는 리렌더가 100ms interval을 첫 틱 전에 지웠다. `useMemo`로 참조를 고정해 2 · 4 · 6 · 8 · 10초 시점 TIME이 전부 0 → 정상이 됐다.
> - **8ms 복사 경로** — 스폰 · 히트 · 초기화 · 정리 경로가 이미 state를 갱신하고 있어 8ms 동기화는 중복이었다. 렌더 루프가 `TargetManager`를 직접 읽게 하고 React에는 개수만 남겼다. 12초 리렌더 약 670 → 약 260회(참조 고정 직후에는 1,125회로 오히려 늘었다).
> - **루프 재시작 조건** — 그동안은 리렌더마다 도는 effect가 우연히 루프를 다시 켜 주고 있었다. 재시작 조건을 "결과 화면을 벗어나는 전이"로 잡았다.
> - **테스트 먼저** — 데이터 흐름을 바꾸기 전에 순수 함수 테스트 41건을 추가했고, 작업 내내 한 번도 실패하지 않았다.
> - **남긴 것** — 프레임 타임은 개선되지 않았고, 초당 약 12회 남은 리렌더는 출처를 찾지 못했다. 마우스 점프는 원인만 확정했고 수정은 #24에서 했다.

지난 글에서 툴체인을 옮겼고, 이번이 코드를 고치는 첫 세션이다. 대상은 README를 코드와 대조하다 찾은 두 가지였다. 게임 중 TIME이 0에 멈춰 있는 결함(R1)과, 그 뒤에 있던 타겟 목록을 8ms마다 React state로 밀어 넣는 경로(R2)다. 둘 다 데이터가 흐르는 길을 바꾸는 일이라, 그 앞에 순수 함수 테스트(R6)를 먼저 깔아 "길은 바꿨지만 동작은 그대로"를 증명할 안전망으로 삼기로 했다.

계획은 R6 → R1 → R2 순서였고 셋 다 끝났다. 다만 커밋이 하나 더 붙었다. push한 뒤 변경분을 처음부터 다시 읽다가 결과 화면에서 메뉴로 돌아가는 경로를 빠뜨린 걸 찾아 고쳤다. 전후 측정도 60초로 잡았는데, 조준하지 않고 두면 타겟이 10개 쌓여 12초에 게임이 끝나서 측정 창이 12초가 됐다.

## 테스트를 먼저 추가한 이유

R2는 타겟 목록이 렌더 루프까지 가는 길을 통째로 바꾼다. 플레이로는 히트 판정이 반지름의 1/3 지점에서 3점과 2점을 가르는지, 스폰이 100번 겹치면 포기하는지 같은 경계값을 확인할 수 없다. 그래서 R2가 건드리는 코드 옆의 순수 함수부터 테스트로 고정했다. Vitest는 `vite.config.mts`에 `test` 블록 하나를 넣는 것으로 끝났고, alias를 그대로 쓰니 별도 설정 파일은 두지 않았다. 다만 바깥 세계를 직접 읽는 함수 셋은 테스트 전에 손을 봐야 했다.

| 대상 | 케이스 | 고정한 규칙 |
|---|---|---|
| `TargetManager` | 16 | 히트 점수 3구간(경계 포함) · 겹친 타겟은 최상단 우선 · 겹침 재시도 100회 뒤 `null` · 영역 변경 시 크기 재파생 |
| `decideTargetColor` | 8 | 종료 유예 색상 4단계, 1초 · 2초 경계 |
| `computeSpawnInterval` | 4 | 1,000ms에서 감쇠, 하한 330ms |
| `calculateContainerBounds` | 9 | 16:9 · 16:10 · 그 외 4:3 폴백 |
| `formatPlayTime` | 4 | MM:SS:CC 표시 |

| 함수 | 상태 | 처리 |
|---|---|---|
| 스폰 간격 계산 | 훅 안의 콜백, `Date.now()` 직접 호출 | 훅 밖으로 꺼내 경과 ms를 인자로 |
| 유예 색상 판정 | 유틸, `Date.now()` 직접 호출 | `now` 기본 인자 추가, 호출부 무변경 |
| 스폰 위치 | `Math.random()` 직접 호출 | 생산 코드 무변경, 테스트에서 고정 |

fake timer로 시간을 덮는 방법도 있었지만, 시간을 인자로 받는 함수는 테스트 없이 읽어도 무엇에 의존하는지가 보여서 그쪽을 택했다.

## 게임 중 TIME이 멈춰 있던 이유

경과 시간은 100ms `setInterval`의 틱이 올린다. 그 interval을 만드는 effect는 `useGame`이 돌려주는 액션 묶음 `gameActions`에 의존하는데, 이 객체가 리렌더마다 새로 만들어졌다. 그리고 `GameWorld`는 뒤에서 다룰 8ms 동기화 때문에 거의 매 프레임 리렌더되고 있었다. effect가 interval을 만들고, 100ms가 되기 전에 리렌더가 와서 cleanup이 지우고, 다시 만들고. 틱이 한 번도 돌지 못해 TIME은 0에 있었다.

```
전  리렌더 → gameActions 새 객체 → 경과 시간 effect 재실행
    → setInterval 재생성 → 100ms 안에 또 리렌더 → 틱 0회

후  gameActions는 useMemo → effect 1회 → 틱 10회/초
```

같은 패턴이 하나 더 있었다. 렌더 루프 훅이 돌려주는 객체도 리렌더마다 새 것이어서, 루프를 켜는 effect가 매 리렌더에 stop과 start를 반복하고 start 안의 캔버스 크기 설정이 버퍼를 매번 다시 잡았다. 키 입력 리스너도 같은 이유로 매번 다시 구독됐다. #17에서 fullscreen 훅의 반환 객체에 `useMemo`가 없던 걸 고쳤는데, 그때 같은 모양의 객체가 두 개 더 있었던 것이다. 둘 다 `useMemo`로 감쌌다.

## 종료 뒤 루프를 다시 켜는 곳

루프 객체가 안정되자 가려져 있던 게 하나 드러났다. 게임이 끝나면 카메라를 제자리로 돌리는 애니메이션 뒤에 루프가 멈추는데, 그 루프를 다시 켜는 코드가 없었다. 그동안은 매 리렌더마다 effect가 재실행되며 우연히 켜 주고 있었고, 참조를 고정하면 두 번째 게임의 캔버스가 멈춘 채로 시작한다. 재시작 조건을 effect의 의존성에 넣어야 했다.

| 재시작 조건 후보 | 판정 |
|---|---|
| 게임 시작 전이(`isGameStarted` false → true) | 기각. 결과 화면에서 RESTART를 누르는 경로만 통과. 메뉴로 돌아가는 경로는 `isGameStarted`가 false 그대로라 effect가 돌지 않음 |
| **결과 화면을 벗어나는 전이(`isGameOver` true → false)** | **채택.** RESTART와 메뉴 둘 다 이 전이를 지남. 메뉴에서 게임으로 가는 전이는 루프가 이미 돌고 있어 재시작이 필요 없음 |

처음엔 첫 번째로 커밋했다. push 뒤에 변경분을 다시 읽다가 메뉴 경로가 빠진 걸 찾았고, 라이브에서 증상도 바로 보였다. 게임을 한 판 끝내고 메뉴로 돌아가 해상도를 바꾸면 캔버스가 비워진 채 다시 그려지지 않아 START를 누르기 전까지 배경만 보였다. 접속 직후의 메뉴에서는 루프가 돌고 있어 같은 조작이 플래시 한 번으로 끝나니, 둘을 나란히 두고 보면 원인이 루프 정지라는 게 분명했다. 두 번째 조건으로 고쳐 커밋 하나를 더 올렸다.

## 타겟 목록을 state로 돌리던 경로

앞서 #15에서 React state는 UI용, ref는 루프용으로 두고 둘 사이를 `useGameRuntime`의 effect로 동기화한다고 썼다. 그 구조는 그대로인데, 타겟 목록만은 길이 두 홉 더 길었다. 타겟은 `TargetManager` 인스턴스 안에 산다. 그걸 8ms `setInterval`이 매 틱 새 배열로 복사해 state에 넣고, 그 state가 effect를 거쳐 ref로 가고, 루프는 그 ref를 읽었다. 매 틱 새 배열이니 `GameWorld`는 8ms마다 리렌더됐고, 그 리렌더가 앞 절의 TIME을 멈춘 장본인이기도 하다.

```
전  TargetManager → 8ms setInterval → setTargets(새 배열) → 리렌더
    → effect → targetsRef → 렌더 루프

후  TargetManager ← 렌더 루프가 매 프레임 직접 읽음
    React state는 targetCount 하나, 스폰 · 히트 시점에만 갱신
```

바꾸기 전에 이 state를 누가 읽는지부터 셌다. 둘뿐이었다. 루프용 ref 동기화와, 타겟이 10개 이상 쌓이면 종료 유예를 걸고 아래로 내려가면 푸는 판정이다. 그리고 타겟 배열이 바뀌는 네 경로(스폰 · 히트 · 초기화 · 정리)가 이미 전부 state를 갱신하고 있었다. 8ms 동기화는 처음부터 중복이었던 셈이다. 남는 문제는 종료 유예 판정 하나였다.

| 유예 판정 경로 후보 | 판정 |
|---|---|
| **스폰 · 히트 시점에 개수만 state로 올리고, 판정 effect는 그대로** | **채택.** state 갱신이 초당 3번 안이라 UI 값으로 둬도 되고, 기존 effect를 거의 그대로 씀 |
| 스포너 루프 안에서 임계값을 보고 콜백 | 기각. 유예 해제는 히트 경로에서도 필요해 콜백이 두 군데가 되고, rAF 안에서 state를 닫아 둔 함수를 부르면 오래된 값을 볼 위험이 있음 |
| 렌더 루프가 매니저를 직접 읽기 | 채택. 위와 조합. 유예 판정은 해결해 주지 않으므로 단독으로는 부족 |

매니저가 돌려주는 배열은 복사하지 않고 읽기 전용 타입으로 그대로 넘기게 바꿨다. 프레임마다 200개짜리 배열을 복사하는 비용은 미미하지만, 루프가 매니저를 직접 읽는다고 해 놓고 매 프레임 복사하면 그 문장이 반쯤 거짓이 된다. 변이는 타입이 막는다.

## 세 단계 측정 결과

| 항목 | 수정 전 | R1 뒤 | R2 뒤 |
|---|---|---|---|
| TIME (2 · 4 · 6 · 8 · 10초 시점) | 0 · 0 · 0 · 0 · 0 | 2 · 4 · 6 · 8 · 10 | 2 · 4 · 6 · 8 · 10 |
| `GameWorld` 리렌더 / 12초 | 약 670회 | 1,125회 | 약 260회 |
| 프레임 간격 평균 | 17.2 ~ 18.1ms | 16.7 ~ 16.9ms | 16.8ms |
| 게임 종료 시점 | 12.2초 | 12.2초 | 12.2초 |

측정은 창 모드 1920×1080에서 조준 없이 방치해 게임이 끝나는 12.2초까지, 세 단계 같은 조건으로 돌렸다. 리렌더 행의 중간값이 좀 눈에 띈다. R1만 적용했을 때 670에서 1,125로 늘었는데, 리렌더마다 interval과 리스너를 다시 만들고 루프를 멈췄다 켜던 비용이 사라지자 8ms마다 들어오는 state 갱신이 합쳐지지 않고 더 많이 각자 리렌더로 이어진 것으로 보였다. 비싼 리렌더가 리렌더 횟수를 눌러 주고 있었던 셈이다. 리렌더는 state가 바뀔 때만 일어나는데, 매 틱 새 배열을 넣으니 React 입장에선 초당 125번 바뀌는 state였고, 그 배열을 React 쪽에서 읽는 곳은 개수 비교 하나였다. 참조 안정성은 TIME을 고쳤지만 리렌더는 그 state를 빼낸 R2가 줄였다.

나머지 행은 변화가 없는 쪽이 의미다. 종료 시점이 세 단계 모두 12.2초인 건 종료 유예 판정이 바뀐 경로에서도 그대로 산다는 증거고, 프레임 간격이 내내 16.8ms 근처인 건 리렌더 비용이 프레임에 드러날 만큼은 아니었다는 뜻이라 README에 프레임 타임 개선을 쓸 수는 없다. 이번에 바뀐 건 TIME이 돈다는 것과 리렌더 횟수다. 그리고 R2 뒤의 초당 22회 리렌더 중 TIME 틱 10회를 빼고 남는 몫은 아직 어디서 오는지 모른다.

## 마우스가 튀던 원인

개발 초반부터 발생 빈도는 줄였지만 완전히 해결하진 못한 문제가 하나 있었다. 마우스를 빠르게 움직이면 맵이 한 번에 창 너비의 1/3쯤 튀는 현상이다. 정상 플레이중엔 잘 발생하지 않았고, 고감도에서 플레이 시 종종 발생했지만 해결하지 못해 감수했던 부분이다.

원인은 코드가 아니라 Windows Chrome의 Pointer Lock 동작이었다. 잠금 중 숨겨진 커서가 창 가장자리 15% 안으로 들어오면 Chrome이 커서를 창 중앙으로 되돌리면서 위치를 중앙으로 갱신하는 이벤트를 하나 보내는데, 그 직전에 큐에 있던 실제 이동 이벤트가 뒤에 처리되면 이동량이 "가장자리에서 중앙까지"로 계산된다. 창 너비 1,299px에서 466px 점프가 나오는 이유다.

OS 수준 입력을 주입해 재현해 보니 기본 잠금에서는 왕복 6번 중 3번 튀었고, raw input을 쓰는 `unadjustedMovement` 옵션으로 잠그면 한 번도 튀지 않았다. 고치는 건 다음 세션이다.

## 정리

- **R6 종결** — Vitest 5, 순수 함수 테스트 41건. 히트 판정 · 스폰 간격 · 종료 유예 색상 · 컨테이너 경계 · 시간 표시. CI에 test 단계 추가
- **R1 종결** — `gameActions`와 렌더 루프 반환 객체를 `useMemo`로. TIME 작동. 종료 뒤 루프 재시작 조건은 한 번 고쳐 "결과 화면을 벗어나는 전이"로
- **R2 종결** — 8ms 동기화 · 타겟 state · 루프용 ref 삭제. 루프는 매니저를 직접 읽고 React에는 개수만 남김. `GameWorld` 리렌더 약 670 → 약 260회 / 12초
- **마우스 점프 원인 확정** — Chrome Pointer Lock의 커서 재중앙화. 앱 결함 아님, 수정은 다음 세션
- **README 문장 하나 추가** — "겹치지 않게 스폰"은 코드상 50% 겹침 허용
