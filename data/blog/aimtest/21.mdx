AimTest는 1월에 README를 마무리하고 손을 놓은 프로젝트다. EC2 프리티어가 끝나 Vercel + Neon으로 옮긴 게 계기가 됐고, 이전을 끝내고 나니 나머지도 정비하고 싶어졌다. 첫 작업은 README였다. 다시 읽어 보니 서술이 과했고, 주장마다 붙어 있어야 할 코드 링크가 하나도 없었다. 고치기 전에 README가 하는 말을 코드와 하나씩 대조하기로 했다.

계획은 재구성 방향과 목차를 정하는 것이었다. 결과는 조금 달랐다. 대조에서 코드 결함이 하나 나와서, 순서가 "README 먼저"에서 "수정 먼저, README는 마지막"으로 바뀌었다.

---

## 대조 결과

README의 사실 주장 28개를 코드와 git 히스토리로 확인했다. 게임 규칙, 점수 구간, 렌더 순서, 랭킹 상한 같은 것은 전부 맞았다. 틀리거나 과한 건 셋이었고, 하나가 더 딸려 나왔다.

| README | 코드 | 판정 |
|---|---|---|
| `GameWorld` 587 → 323 lines | 어느 커밋에도 323 없음. 피크 587 → 훅 분리 6단계 뒤 312 → 현재 358 | 수치 오류 |
| 모든 시간 제어를 단일 rAF 누적 시간 구조로 | 누적 시간은 스포너 루프 하나. 렌더 · 스포너 · 테두리 페이드 rAF 3개에 `setInterval` 2개 · `setTimeout` 6곳 공존 | 과장 |
| 상태 동기화는 `useGameRuntime`이 중앙 관리 | `graceStartAt` · `isGameOver`만. 타겟 목록은 `GameWorld`가, 테두리 투명도는 `useBorderFade`가 각자 ref에 씀 | 과장 |
| 렌더 루프에서는 state를 전혀 안 쓴다 | 루프 자체는 맞음. 단 타겟 목록이 state를 거쳐 ref로 복사되는 경로가 있음 | 일치, 그런데 |

323 커밋에는 없는데, 완전히 God Component였던 `GameWorld`를 리팩토링하고 나서 본 라인 수를 내가 기록한 거였다. 이후 주석이나 작은 수정으로 바뀌면서 라인수가 달라진 것이다. 숫자 하나가 틀린 것 자체보다, 리뷰어가 `wc -l` 한 번에 358을 보는 순간 README의 다른 숫자도 같이 의심받는다는 게 문제였다.

여기서 마지막행이 이번 세션의 큰 발견이다.

## 멈춰 있던 TIME

타겟 목록은 `TargetManager` 클래스가 들고 있다. 이걸 화면에 그리는 rAF 루프는 ref를 읽고, ref는 React state에서 복사되며, 그 state는 8ms `setInterval`이 매 틱 새 배열로 갱신한다. 여기까지는 "React 렌더와 rAF를 분리했다"는 README 문장과 어긋나지 않아 보였다. 문제는 그 틱이 일으키는 연쇄였다.

```
8ms 틱 → setTargets(새 배열) → GameWorld 리렌더 (초당 약 120회)
  → useGame이 돌려주는 gameActions가 매 렌더 새 객체
    → 경과 시간 effect의 의존성이 바뀜
      → setInterval(100ms) 해제 → 재생성 → 해제 → …
        → 100ms 콜백이 한 번도 안 불림 → 인게임 TIME 0 고정
```

결과 화면의 플레이 시간은 종료 시점에 따로 계산해서 멀쩡하고, 그래서 눈에 안 띄었을 것이다. 좀 억울한 건 조각 하나하나는 다 그럴듯했다는 점이다. 8ms 동기화도, 객체를 매번 새로 만드는 것도, effect 의존성에 함수 객체를 넣는 것도 각자는 흔한 코드인데, 셋이 겹치니 타이머가 죽었다. 리뷰 없이 혼자 만든 코드에서 딱 나올 법한 종류다. 라이브에서 실제로 0에 멈춰 있는지는 아직 안 봤다 — 코드로는 그렇게 읽히고, 다음 세션 첫 작업이 그 확인이다.

## 고칠 것과 남길 것

전체 리팩토링은 처음부터 선택지에서 뺐다. 지금 메인은 SlateKR이고, AimTest에 쓸 시간은 세션 세 개 안쪽이다. 대신 기준을 하나 두고 걸렀다.

**리뷰어가 ① 라이브를 1분 플레이하거나 ② 클론해서 lint · build를 돌리거나 ③ README 수치를 코드와 대조할 때 걸리는가.** 여기에 ④ 신입 포트폴리오 체크리스트(테스트 · CI · API 입력 검증 · LICENSE)의 빈칸이고 한 시간 안에 채워지는가를 더했다.

| 하는 것 | 남기는 것 → README 「알려진 한계」 |
|---|---|
| CRA → Vite · TypeScript 4.9 → 5 (R9) | 컴포넌트 · 훅 테스트 — Canvas · Pointer Lock 모킹 비용 |
| ESLint 설정 정합 · GitHub Actions CI (R3 · R7) | 랭킹 API rate limit — 서버리스에 저장소가 필요 |
| 순수 함수 테스트, R2 **앞**에 (R6) | 접근성 |
| TIME 결함 — `gameActions` · `loop` 반환 객체 참조 안정화 (R1) | 타이머 전부 단일 루프로 통합 — 문제였던 "한 캔버스에 rAF 두 개"는 이미 고쳤고, 100ms UI 타이머가 `setInterval`인 건 문제가 아님 |
| 타겟 state 경유 제거 — rAF가 `TargetManager`를 직접 읽기 (R2) | 볼륨 · 감도 설정 저장 |
| 미사용 코드 · 잠재 버그 3건 · 랭킹 API 입력 검증 (R4 · R5 · R8) | |
| README 재작성 + LICENSE (D1) | |

**CRA 교체는 처음엔 안 하려 했다.** 한 시간 기준에 안 맞고, 기능을 더 붙일 일이 생기면 그때 하자는 생각이었다. 그런데 ESLint 설정을 CRA 기준으로 고쳐 두면 Vite로 갈 때 다시 고쳐야 하고, 테스트를 CRA에 내장된 Jest로 쓰면 나중에 Vitest 이식이 남는다. 4.5k줄에 CRA 전용 기능을 쓴 데도 없어 반나절 작업이라, 기준의 예외로 두고 첫 세션에 몰았다. 세션은 셋에서 넷이 됐다.

**테스트는 리팩토링 앞에 둔다.** R2는 타겟 데이터의 경로를 바꾸는 작업인데, 바뀌면 안 되는 동작 — 히트 판정 점수 구간, 스폰 간격 감쇠, 유예 색상 단계, 컨테이너 경계 — 은 전부 그 옆의 순수 함수에 있다. 먼저 고정해 두면 R2 뒤에 "경로는 바꿨지만 동작은 그대로"가 테스트 한 줄로 증명된다. 플레이로는 반지름 1/3 지점이 정확히 3점인지 같은 경계를 못 잡는다.

## README는 어떻게 바꾸나

소재와 기준만 간단히 정했고, 리팩토링 후 리드미를 전면 개편할 생각이다.

- **수치는 git이 증명하는 것만** 
- **설계 결정은 넷으로 고정** — 캔버스 렌더 루프 단일화 · 스포너 누적 시간 · 훅 분리 6단계 · 입력과 렌더의 경계. 
- **절마다 코드 링크, 「알려진 한계」 · 「다시 한다면」 신설** — SlateKR README와 같은 틀

프로젝트를 다시 보면서 README에 없던 좋은 점도 몇 개 건졌다. 마우스 이동량을 프레임 경계까지 모아서 한 번에 반영하는 큐잉, 탭이 비활성일 때 한 프레임에 타겟이 쏟아지지 않게 하는 dt 클램프, 창을 드래그하는 동안 DPR 재계산을 80ms로 묶은 것, `any` 0에 `strict`. 적을 자리가 없어서 묻혀 있었다.
