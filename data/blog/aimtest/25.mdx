재정비를 시작하며 README를 코드와 대조할 때, 포트폴리오에서 비어 있으면 바로 보이는 칸을 넷 꼽았었다. 테스트 · CI · API 입력 검증 · LICENSE. 앞의 둘은 두 번째 · 세 번째 세션에서 채웠고, 랭킹 API 입력 검증은 지난 세션에서 시간이 모자라 넘겼다. 이번이 README를 쓰기 전에 코드를 손대는 마지막 세션이라, 검증을 넣고 나서 코드 전체를 한 번 점검하고 닫기로 했다.

계획은 랭킹 API 입력 검증(R8) 다음에 컨벤션 · 미사용 코드 점검(R11)이었고, 둘 다 끝났다. 다만 코드를 닫았다고 한 뒤에 커밋이 둘 더 붙었다. push한 diff를 다시 읽다가 나온 작은 수정들인데, 그 얘기는 끝에 적는다.

---

## 서버가 점수를 어디까지 믿을지

랭킹 API를 처음 만들 때는 닉네임만 넣으면 저장되는 걸로 충분했고, 요청 본문을 그대로 `INSERT`했다. 지금 다시 보니 저장은 되는데 걸러지는 게 없었다. 이름 한 글자도, 소수점 점수도, 음수 플레이 시간도 그대로 들어간다. 검증 라이브러리는 들이지 않기로 했었으니 네 필드를 손으로 검사하는 순수 함수를 컨트롤러 옆에 두고, 하나라도 어긋나면 400으로 돌려보내게 했다.

```
POST /api/rankings
  → validateRanking(req.body)   어긋나면 → 400 { error }
  → INSERT                      통과한 값만
```

| 필드 | 규칙 |
|---|---|
| `user_name` | 문자열, 앞뒤 공백을 지운 뒤 2 ~ 10자(클라이언트 입력란과 같은 기준) |
| `score` | 정수, 0 이상 |
| `play_time` | 유한한 수, 0 이상(초 단위) |
| `accuracy` | 유한한 수, 0 ~ 100 |
| `score`와 `play_time`의 조합 | `score` ≤ `play_time` × 10 |

제한 시간에서 좀 고민이 있었다. 제한 시간 없는 서바이벌이라 점수 상한을 숫자 하나로 둘 수가 없고, 대신 규칙에서 상한이 나온다. 스폰 간격은 1초에서 시작해 초마다 0.982배로 줄다가 330ms에서 멈추고 타겟 하나는 최대 3점이니, 초당 9.1점을 넘길 방법이 없다. 그래서 플레이 시간에 10을 곱한 값을 상한으로 잡았는데, 정상 플레이는 절대 걸리지 않고 시간에 비해 말이 안 되는 점수만 걸린다.

이게 조작을 완벽히 막는 건 아니다. 익명 리더보드라 플레이 시간까지 같이 꾸며 보내면 통과하고, 그건 인증이나 요청 제한의 몫이라 계획에서 범위 밖으로 둔 항목(B3)이다. 검증이 하는 일은 "말이 안 되는 값은 받지 않는다"까지다.

## 순위 조회와 확인 방법

순위 조회 쪽도 같이 봤다. `GET /api/rankings/rank/:score`는 경로의 문자열을 그대로 쿼리에 바인딩하고 있어서 숫자가 아니면 DB 오류로 500이 났는데, 같은 검사 함수를 거쳐 400을 돌려주게 했다. 확인은 잘못된 요청 여섯 종(한 글자 이름 · 소수점 점수 · 시간 대비 과한 점수 · 101% 정확도 · 본문 없는 요청 · 문자열 순위 조회)을 `curl`로 보내 전부 400을 받는 것으로 했고, 정상 저장은 `curl` 대신 직접 플레이했다. 로컬 dev 서버도 라이브 DB를 보기 때문에 테스트 데이터를 남기고 싶지 않았다.

## 코드를 닫기 전에 무엇을 볼지

README의 품질 절에는 `strict`에 `any` 없음, 컨벤션, 테스트, CI 같은 말이 들어갈 텐데, 그 문장들을 코드가 실제로 뒷받침하는지 쓰기 전에 확인하고 싶었다. 처음 생각은 파일을 전부 읽는 점검이었다. 그런데 이 코드는 지난 세션에 미사용 코드를 한 번 정리했고 커밋마다 diff를 다시 읽어 왔으니, 다시 읽어서 새로 나올 게 많지 않아 보였다. 읽는 쪽 사정도 있다. README에 "컨벤션을 점검했다"고 적어도 읽는 사람은 그걸 확인할 수 없고, 확인할 수 있는 건 도구가 낸 숫자뿐이다.

그래서 점검을 "도구가 수치로 답하는 것"과 "이미 알고 있던 잔여"로 좁혔다.

| 후보 | 판정 |
|---|---|
| **미사용 export · 타입 · 의존성 — knip 한 번 실행** | 채택. 설정 없이 돌아가고, 0건이면 README에 숫자로 쓸 수 있음 |
| **미사용 지역 변수 · 인자 — `tsc`에 `--noUnusedLocals --noUnusedParameters`** | 채택. 명령 한 줄, 두 tsconfig 모두 |
| **타입 전용 import 혼용 — ESLint 규칙을 한 번만 켜서 실행** | 채택. 위치 목록이 그대로 수정 목록 |
| **주석 잔여 — 작업 맥락 · 변경 이력 표현 · 영어 · 주석 처리 코드를 grep** | 채택. 파일을 열었을 때 가장 먼저 눈에 걸리는 종류 |
| 파일을 전부 읽으며 컨벤션 · 비효율 리뷰 | 기각. 두 번 훑은 코드라 기대 수확이 낮음 · 비효율 목록은 결국 측정으로 판정해야 해서 지난 세션에 줄인 측정을 다시 부름 · 결과를 README 근거로 쓸 수 없음 |

## 도구가 찾아낸 것

| 항목 | 전 | 후 |
|---|---|---|
| knip — 파일 안에서만 쓰는데 export된 것 | 5건(값 2 · 타입 3) | 0 |
| `tsc` 미사용 인자(api, Express 핸들러의 `req`) | 3 | 0 |
| 타입 전용 import에 `type` 없음 / 인라인 `type`만 있는 import | 4 / 5 | 0 / 0 |
| 주석 — 변경 이력 표현 · `@param` · 영어 구획 배너 | 1 · 7줄 · 2 | 0 |
| `React.FC` · DPR을 직접 읽는 곳 · 이름이 `NaN점`으로 찍히는 테스트 | 1 · 6곳 · 6건 | 0 · 헬퍼 1곳 · 0 |

나온 건 전부 자잘했다. knip이 잡은 다섯은 죽은 코드가 아니라 같은 파일 안에서만 쓰는데 export가 붙어 있던 것이라 키워드만 뗐고, 테스트 이름 건은 좀 민망한 쪽이다. `it.each`의 이름 포맷 `%s → %i점`에서 `%i`가 기대 점수가 아니라 두 번째 인자인 함수를 받고 있어서 여섯 케이스가 전부 `NaN점`으로 찍히고 있었다. 판정은 정상이라 테스트를 넣은 세션부터 그대로였다.

타입 import는 규칙 하나로 끝나지 않았다. `consistent-type-imports`는 `type` 한정자가 아예 없는 import만 잡고 `import { type A, type B }`처럼 전부 인라인인 건 통과시키는데, 그걸 `import type { A, B }`로 모으는 건 `no-import-type-side-effects`라는 별도 규칙이었다. 둘 다 켜 두어 "타입 전용 import는 `import type`"이 이번 한 번의 정리가 아니라 lint로 유지되게 했다.

## push한 뒤에 붙은 둘

세션 마지막에 push한 diff를 처음 보는 눈으로 다시 읽었다. 고쳐야 할 건 없었고 권고가 몇 개 나왔는데, 전부 한 줄 수정이나 이름 바꾸기 수준이라 미루지 않고 바로 처리했다.

| 권고 | 처리 |
|---|---|
| 점수가 DB 컬럼 범위를 넘으면 500 | INTEGER 상한(2,147,483,647) 검사 추가 → 400. 앞의 게임 규칙상 상한과 다른 상한이라는 게 드러나게 주석을 구분 |
| 비례 상한이 클라이언트의 최소 스폰 간격 상수에 기대는데 코드로는 연결이 없음 | 상수 옆에 서버 검증이 이 값에 의존한다는 주석. 상수를 줄이면 정상 점수가 거부되기 때문 |
| react의 타입 import가 정렬 그룹에서 빠져 다른 패키지 뒤로 밀림 | 정렬 규칙이 타입 import의 모듈명 뒤에 `\u0000`을 붙여 매칭 → 그룹에 그 형태를 추가 |
| 같은 파일 안에서 `getDpr`와 `setCanvasSizeDPR`로 약어 표기가 갈림 | `getDPR`로 통일 |

코드를 닫았다고 한 뒤에 커밋이 둘 더 생긴 셈이라, 다음부터는 diff를 다시 읽은 다음에 닫기로 했다.

## 정리

- **R8 종결** — 랭킹 저장 · 순위 조회 입력 검증. 네 필드 수동 검사 · 점수는 플레이 시간 × 10과 DB 컬럼 범위 안 · 실패는 400 · 테스트 33건 추가
- **R11 종결** — 전수 읽기 대신 도구 수치로 점검. 미사용 export 5 · 타입 import 9 · 주석 3 · `React.FC` 1 · DPR 읽기 6곳 · 테스트 이름 포맷 → 전부 0. 동작 변화가 없어 검증은 타입 검사 · lint · 빌드 · 테스트에 DPR 측정(이전과 동일) · 전체 회귀 1회
- **ESLint 규칙 둘 추가** — `consistent-type-imports` · `no-import-type-side-effects`. react 타입 import 정렬 그룹
- **README 수치 확정** — `GameWorld.tsx` 358줄 · 테스트 74건 · 미사용 export 0(api 엔트리 제외)
- **knip 상시화는 backlog** — 설정 없이는 api 엔트리를 못 알아봐 서버 쪽 의존성 셋이 미사용으로 잡힘. 기능을 다시 붙일 때 설정과 함께

검증 규칙을 넣는데 시간이좀 걸렸고, 무엇을 보지 않을지 정하는 데도 좀 들었다. 도구가 낸 결과는 export 키워드 다섯 개와 import 아홉 줄 수준이라 처음부터 다시 읽었어도 결과는 비슷했을 것 같고, 오히려 계획에 적어 둔 잔여 항목 하나가 확인해 보니 없었던 쪽이 교훈이다. 지난 세션 검토에서 나온 "미사용 인자" 권고를 확인 없이 그대로 옮겨 적었던 것인데, 해당 인자는 쓰이고 있었다. 이걸로 코드는 닫는다.
