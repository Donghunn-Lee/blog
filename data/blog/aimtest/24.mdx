> **요약** · 결함 다섯을 고쳤다. 하나같이 몇 줄짜리 수정이었다.
> - **마우스 점프** — 원인은 앱 밖, Windows Chrome의 커서 재중앙화였다. Pointer Lock에 `unadjustedMovement`를 적용(거부 시 폴백)해 300px 이상 스파이크가 왕복당 6.5회 → 0, 최대 이동량 481px → 48px이 됐다.
> - **결과 화면에서 살아나던 루프** — 종료 직후 즉시 정지 경로에서 `start`가 멈춘 루프를 다시 살렸다. 즉시 정지 분기를 없애 항상 복귀를 거치게(원점이면 0ms) 하고, 결과 화면에서는 start도 stop도 하지 않게 했다.
> - **DPR 2에서 두 배가 된 맵** — 맵 크기를 DPR배 buffer 크기로 잡고 있었다. CSS px로 맞춰 7,157 × 4,224 → 3,578 × 2,112(DPR 1과 같음)가 됐다.
> - **맵 로딩 레이스** — 로드 effect가 마운트 직후 재실행되며 완료 타이머가 지워졌다. deps를 `[src]`로 줄이고 ref를 `useLayoutEffect`에서 갱신해, 20회 중 7회꼴이던 멈춤이 40회 중 0회가 됐다.
> - **불필요한 리렌더** — Pointer Lock 해제 콜백을 ref로 옮겨, 12초 플레이 리렌더가 262 → 142회(실제 커밋 133회)가 됐다.

이미 직전 세션에서 언급한 바 있지만, 개발 초기부터 마우스를 빠르게 돌리면 화면이 순간이동하는 증상이 있었다. 리렌더 탓으로 보고 캔버스로 옮겨 줄였지만, 고감도에서는 여전히 발생했다. 정확한 원인을 모르지만, 통상 플레이시 발생 빈도는 낮아 감수하고 있었다.

지난 글에서 그 원인이 앱이 아니라 Chrome의 Pointer Lock 동작이라는 걸 확정했고, 이번에 고쳤다. 같은 세션에 미사용 코드 정리와 README를 대조하며 모아 둔 작은 버그 여덟 개를 함께 처리했다.

계획은 마우스 점프 수정(R10) → 미사용 코드 정리(R4) → 소형 버그(R5) → 랭킹 API 입력 검증(R8)이었고, 작업이 길어져 R8은 이월했다. 소형 버그 수정 중 하나를 고치니 옆에 있던 다른 하나가 드러나는 일이 두 번 있어서, 그 부분만 조금 길게 적는다.

## Chrome이 커서를 가운데로 되돌리는 순간

Pointer Lock은 커서를 숨기고 이동량만 넘겨주는 API다. 커서가 보이지 않을 뿐 OS 입장에선 존재하니, Chrome(Windows)은 숨긴 커서가 창 가장자리 15% 구역에 들어오면 창 중앙으로 되돌려 놓는다. 이 되돌리는 이동과 진짜 마우스 이동의 처리 순서가 꼬이면, 한 이벤트에 "가장자리에서 중앙까지"가 이동량으로 들어온다. 창 너비 1,299px에서 측정한 스파이크가 464 ~ 481px, 즉 너비의 35% 남짓이었고 Chromium 소스의 경계 상수(15%)와 맞아떨어졌다.

| 가설 | 판정 |
|---|---|
| 리렌더 중 이벤트 누적(첫 구현 때의 추정) | 기각. 캔버스로 옮긴 뒤에도 고감도에서 재현 |
| 메인 스레드가 멈춰 입력이 뭉침 | 기각. 스파이크 직전 이벤트와 간격 7.5ms 이하 |
| 렌더 루프를 고친 뒤(R1) 더 잦아짐 | 기각. 왕복당 7.0회 → 6.5회, 게임 간 편차 안 |
| **Chrome의 커서 재중앙화 경합** | **채택.** 크기가 창 너비 × 0.35, 합성 (0,0) 이벤트 동반, 원시 입력 모드에서 0회 |

## 원시 입력으로 바꾸고 감도는 그대로

`requestPointerLock({ unadjustedMovement: true })`로 요청하면 커서 위치 대신 마우스의 원시 이동량을 받는다. 커서가 없으니 되돌릴 것도 없다. 이벤트별 이동량에 상한을 두는 우회도 생각했는데 정상 플릭도 1,200px까지 합쳐져 들어오는 터라 자르면 안 됐다. 옵션을 거부하는 브라우저가 있어서(일부 Firefox · Safari, headless Chromium도) 거부되면 옵션 없이 다시 요청하는 폴백을 뒀다.

| 항목 | 전 | 후 |
|---|---|---|
| 스파이크(한 이벤트 300px 이상) / 왕복 | 6.5회 | 0회 |
| 최대 이동량 | 481px | 48px |
| 합성 (0,0) 이벤트 | 214건 | 0건 |
| 게임 시작 직후 세로 125px 점프 | 6게임 중 3 | 0 |

원시 입력은 Windows 포인터 가속을 거치지 않는다. 가속은 빠르게 움직일수록 더 많이 이동시키는 기능이라, 그게 빠지면 플릭이 전보다 덜 돌아간다. 플레이해 보니 좀 느려진 느낌은 있었지만 수용할 만했고, 기본 감도는 1로 두고 기존 조절 키 `[` `]` 만 남겼다. FPS 플레이어 대부분이 OS 가속을 끄는 것과 같은 이유다. 같은 손 움직임이 항상 같은 양만큼 돌아가야 에임이 몸에 쌓인다.

## 결과 화면에서 다시 켜지던 루프

게임이 끝나면 카메라가 0.8초 동안 원점으로 돌아오고, 그 애니메이션이 끝나면 렌더 루프가 멈춘다. 종료 시점에 effect가 도는 순서는 cleanup `stop` → 복귀 시작 → 루프 시작 `start`인데, `start`는 "이미 돌고 있으면 빠진다"만 알았다. 복귀 애니메이션이 도는 동안은 괜찮지만 카메라가 이미 원점이라 즉시 멈추는 경로에서는 `start`가 루프를 되살린다. 이 경로는 사실상 죽어 있었다. 즉시-멈춤 판정이 (0,0)인데 실제 원점은 (0,90)이라, 안 움직인 게임도 제자리로 0.8초 애니메이션을 돌고 있었다. 판정을 맞추자 숨어 있던 것들이 차례로 나왔다.

| 드러난 것 | 고친 것 |
|---|---|
| 판정을 맞추니 안 움직인 게임의 결과 화면에서 루프가 계속 돎 | 루프 시작 effect가 결과 화면(`isGameOver`)이면 start도 stop도 하지 않음. stop하면 복귀 애니메이션을 끊기 때문 |
| 즉시 멈추면 종료 상태 프레임을 한 장도 안 그려 타겟이 만료 색으로 안 바뀜 | 즉시-멈춤 분기를 없애고 원점이면 길이 0ms 복귀로 통일. 마지막 프레임 한 장을 그리고 멈춤 |
| 복귀 0.8초 안에 메뉴를 누르면 `start`가 남은 애니메이션을 이어받아 메뉴 화면에서 루프가 멈춤 | `start`가 복귀 상태를 비우고 시작 |
| 카메라 ref가 초기값 상수 객체 그 자체라 카메라를 움직이면 상수도 따라 바뀜 | 복사본으로. 원점 판정의 전제 |

```
전   cleanup stop → 복귀(원점이면 즉시 stop) → start: 멈춘 루프를 다시 켬
후   cleanup stop → 복귀(원점이면 0ms) → 마지막 프레임 1장 → stop
                                       → start: 결과 화면이면 아무것도 안 함
```

같은 커밋에 Pointer Lock 훅의 리렌더도 묶었다. 잠금 해제 콜백을 인라인 함수로 넘기고 있어서 effect가 커밋마다 다시 돌고, 같은 값으로 state를 쓰면서 커밋 없는 리렌더가 12초에 128회 쌓이고 있었다. 콜백을 ref에 담아 deps에서 빼니 `GameWorld` 리렌더가 262 → 142회로, 실제 커밋 수(133)에 붙었다. 지난 글에서 설명이 안 되던 초당 11회의 정체가 이것이었다.

## DPR 2에서 맵이 두 배로 그려지던 이유

캔버스는 선명하게 그리려고 buffer를 DPR 배로 잡고 `ctx.scale(dpr)`을 건 뒤 CSS px로 그린다. 카메라 · 클램프 · 타겟 영역은 전부 CSS px 좌표계였는데, 맵 크기를 계산할 때만 buffer 크기(`canvas.width`)를 넣고 있었다. DPR 1에서는 두 값이 같아서 드러나지 않았고, 레티나 환경(DPR 2)에서는 맵과 타겟 영역이 두 배로 그려지고 클램프는 화면 절반만큼 안쪽에서 걸렸다.

| DPR 2 | 전 | 후 |
|---|---|---|
| 맵 크기 | 7,157 × 4,224 | 3,578 × 2,112 (DPR 1과 동일) |
| 카메라 클램프 | ±1,701 · ±1,056 | ±851 · ±528 |
| 타겟 영역 | 1,540 × 512 | 770 × 256 |

맵 크기 계산에 `canvas.width / dpr`을 넣는 것으로 끝나는 수정이었지만, 맵만 고치면 타겟이 맵 대비 두 배가 돼 고치기 전보다 더 어긋난다(전에는 둘 다 두 배라 비율은 맞았다). 타겟 영역을 넘기는 네 곳까지 같은 커밋에 넣었다.

## 맵 로딩이 가끔 멈추던 레이스

인게임 진입 20회 중 7회꼴로 "Loading map…"에서 멈추는 일이 있었다. 이미지 로드 effect의 deps에 캔버스 크기 맞춤 함수가 들어 있었는데, 이 함수가 렌더 중 읽은 캔버스 요소(첫 렌더엔 `null`)에 의존해 마운트 직후 한 번 더 바뀐다. 그 사이에 첫 로드가 끝나 있으면 재실행 cleanup이 완료 타이머를 지우고, 이미 로드됐다는 플래그 때문에 다시 걸지 않아 로딩 화면이 영구히 남았다. 로딩 순서를 잡을 때 만든 구조가 그대로 남아 있던 셈이다.

| 수정 | 결과 |
|---|---|
| 함수를 ref에 담고 deps를 `[src]`로, ref 갱신은 `useEffect` | 멈춤 0/20, 대신 맵 미표시 5/20. 이미지 load가 커밋과 passive effect 사이에 오면 직전 렌더의 함수로 계산을 건너뜀 |
| **ref 갱신을 `useLayoutEffect`로** | **멈춤 0/40 · 미표시 0/40** |

## 자잘한 정리

- **미사용 정리(R4)** — 참조 없는 상수 · 함수 · 타입과 885KB짜리 `grid.jpg` 삭제, og:image를 절대 URL로. 번들은 그대로고 배포 용량만 864KB 줄었다
- **테두리 페이드** — 페이드가 끝난 뒤에도 rAF를 계속 걸고 있어서 진행률 1에서 멈추게
- **플레이 시간 표시** — `(0.29 % 1) * 100`이 28.999…가 되는 부동소수 절삭을 정수 연산으로. 테스트 42건
- **`npm audit` 7건** — 전부 Tailwind 3.4가 끌고 오는 빌드 전용 의존성이고 해법이 v4 업그레이드뿐이라, 이번 재정비 범위에선 두기로 했다

## 정리

- **R10 종결** — Pointer Lock을 원시 입력으로. 스파이크 6.5회/왕복 → 0. 감도는 1 유지, 미지원 브라우저는 폴백
- **R4 종결** — 미사용 코드 · 에셋 · 메타 정리, 배포 −864KB
- **R5 종결** — 소형 버그 8건. 종료 경로를 하나로(원점이면 0ms 복귀) · 결과 화면에선 루프를 켜지 않음 · 좌표계 CSS px 통일 · 맵 로딩 레이스 · 리렌더 262 → 142회
- **R8 이월** — 랭킹 API 입력 검증은 다음 세션

하나같이 몇 줄짜리 수정이었다. 다만 소형 버그 쪽은 고치면 옆에 있던 게 드러나는 식으로 이어졌고, 즉시-멈춤 판정 하나를 맞추려다 종료 경로 전체를 다시 그리게 됐다. 마우스 점프 반을 감수하던 문제였는데, 원인이 앱 밖에 있다는 걸 알고 나니 수정은 한 함수였다.
