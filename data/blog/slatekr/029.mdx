이전 작업에서 인프라를 Vercel + Neon으로 전환하고, stocks·financial_statements·disclosure_summaries 세 테이블까지 이관을 끝냈다.

나머지 테이블 하나, daily_prices 614만 row가 남아있었다. 이어서 Vercel로 배포하는 건 간단했다.

---

## Workbench Export 오류

이미 이관 완료한 3개 테이블은 모두 MySQL Workbench의 Table Data Export Wizard로 CSV를 뽑고, Python 스크립트로 Neon으로 옮겼다.

그런데 `daily_prices`는 그 크기가 약 614만 row에 육박하는 길이라 그런건지, 같은 방식으로 추출을 시도하면 무언가의 오류로 Workbench가 다운되거나 몇 분이 지나도 진행률이 올라가지 않았다.

결국 mysql CLI를 직접 쓰기로 했다. 터미널에서 `mysql` 명령어가 PATH에 안 잡혀 있어서 Workbench 설치 경로의 bin 폴더에서 mysql.exe를 찾아 전체 경로로 실행해야했다.

```
& "C:\Program Files\MySQL\MySQL Server 8.0\bin\mysql.exe" -u root -p -e "SELECT ..." --batch --raw slatekr > daily_prices.csv
```

다행히 이 방법으로는 빠르게 작업이 처리됐다. 금방 파일이 만들어졌고, 크기는 약 600MB. 정상적으로 처리됐다.

---

## Neon Free tier 한계

추출한 파일을 neon으로 옮기기 위해 import를 돌렸는데, 323만 row쯤에서 또 멈췄다.

```
ERROR: could not extend file because project size limit (512 MB) has been exceeded
```

Neon Free tier의 스토리지 한도가 512MB였다. 기존 3개 테이블 데이터가 이미 들어가 있는 상태에서 daily_prices 전체는 안 들어간다.

어차피 Launch 플랜으로의 업그레이드는 예정된 수순이었다. Free tier로 개발하고, 배포 시점에 유료로 전환하는 흐름. 스토리지 \$0.35/GB-month, 컴퓨트 \$0.106/CU-hour 종량제인데, 포트폴리오 프로젝트 트래픽 수준이면 월 \$5 이내로 예상했다. Scale to zero가 5분 후 작동하니까 안 쓸 때는 컴퓨트 비용이 0이다.

업그레이드 후 중간에 끊긴 데이터를 TRUNCATE로 정리하고 다시 돌렸다. `COPY 6139877` — 614만 row 전부 들어갔다.

---

## Vercel 배포

daily_prices가 들어가니까 로컬에서 차트까지 정상 동작하는 걸 확인했다. 이제 배포만 남았다.

Vercel에 GitHub 레포를 연결하고, Root Directory를 `web`으로 설정하고, 환경변수 세 개(DATABASE_URL, DART_API_KEY, GEMINI_API_KEY)를 넣었다. DATABASE_URL은 Neon pooler URL을 사용했다. Direct 연결은 psql 같은 장시간 연결용이고, serverless 환경에서는 pooler 쪽이 맞다.

배포는 별 탈 없이 끝났다. https://slate-kr.vercel.app/ — 검색, 차트, 재무, 공시 전부 동작한다.

---

## 정리

#028에서 EC2를 버리고 Vercel + Neon으로 갈아타기로 결정한 시점부터 계산하면, 드라이버 교체 → 쿼리 전환 → 3개 테이블 이관 → daily_prices 이관 → Vercel 배포까지 두 세션이 걸렸다. 작업 단위 자체는 나쁘지 않지만, 조금 속도를 내야 할 필요가 있어 보인다.

이제 URL이 생겼으니, 다음은 collector를 PostgreSQL로 전환하고 데이터 자동 갱신을 붙이는 작업이다. 현재 collector 스크립트 4개가 전부 pymysql 기준이라 psycopg2로 바꿔야 하고, EC2 대신 GitHub Actions cron으로 돌릴 생각이다.

배포된 서비스가 매일 갱신되는 데이터를 보여주기 시작하면, 그때부터가 진짜 실환경이다.
