세션을 열기 전에 증권사 안내문이 하나 도착해 있었다. 9월 14일부터 한국거래소가 16시부터 20시까지 애프터마켓을 열고 시간외단일가를 없앤다는 내용이다. SlateKR은 15시 30분 이후엔 NXT 대상 종목만 움직인다는 전제로 시세 게이트와 출처 배지를 만들어 왔으니, 이 전제가 사흘 뒤 깨진다. 원래 이날은 KIS 호출 수를 정규장에서 실측하는 항목(X25)과 미니차트 장중 시세 실패 홀(F21)을 보는 날이었다.

계획은 X25 실측을 예정대로 하되 제도 변경 대응을 새 항목(X27)으로 세우고 일정을 다시 짜는 것이었고, 그대로 갔다. 다만 X25의 결론이 "갱신 주기를 조정할 필요가 없다"로 나왔고, 대신 종목 분봉 호출 구조에 문제가 있어 그 자리에서 probe까지 돌려 수정 경로를 정했다(X28). 커밋은 없다. 판정 다섯 건과 신설 세 건이 이번 세션의 산출물이다.

## 제도 변경과 일정

### 바뀌는 것

바뀌는 건 KRX 쪽이다. NXT 대상 종목이 늘어나는 게 아니라, KRX가 NXT처럼 저녁 장을 연다.

| 시간대 | 9/14 전 | 9/14 후 |
|---|---|---|
| 09:00~15:30 | KRX 정규장 + NXT 메인마켓 동시 | 변화 없음 |
| 15:30~16:00 | NXT 대상 종목만 | 변화 없음 |
| 16:00~20:00 | NXT 대상 종목만 실시간. KRX는 10분 단일가 | **전 종목 KRX 접속매매 + NXT 동시** |

### SlateKR에 닿는 전제 네 곳

SlateKR에 닿는 지점은 "15시 30분 이후 움직이는 종목 = NXT 대상"이라는 등식이다. 이 등식 위에 서 있는 곳이 넷이다.

```
지금      15:30 이후 라이브 = NXT 대상 종목            (게이트 축: 종목)
9/14~     16:00 이후 라이브 = 전 종목, KRX + NXT      (게이트 축: 시각)
```

1. **라이브 게이트** — 15시 30분 이후 시세 폴링을 NXT 대상 종목에만 허용. 16시부터는 비NXT 종목도 KRX 채널에서 움직이므로 축이 "NXT 대상 여부"에서 "시각"으로
2. **출처 배지** — 장외 시간 가격에 붙는 NXT 배지. 그 시간대 가격의 출처가 KRX일 수 있으니 문구 재검토
3. **통합 시세 스냅샷** — 20시 10분에 받는 값이 어느 채널의 마감값인지
4. **EOD 가드** — 16시 이후에만 당일 일봉을 적재하고 write-once. 일봉이 애프터마켓 체결로 16시 이후에도 갱신되는 구조면 월요일 첫 run이 불완전한 봉을 영구 적재

KIS 개발자센터 공지도 같은 날 올라와 있었다. 변경 목록은 주문 유형 코드, 잔고 조회 필드, WebSocket 장 구분 코드였고, SlateKR이 쓰는 REST 시세·분봉·일봉 조회에는 예고된 변경이 없었다. 필드는 그대로 두고 값의 의미만 바뀐다는 뜻이라 정적 조사는 우리 쪽 전제 네 곳으로 줄었고, 대신 월요일 저녁 실측에 무게가 실렸다.

| 월요일 16:00~20:10 실측 | 갈리는 것 |
|---|---|
| 비NXT 종목 현재가가 16시 이후 움직이는가 | 라이브 게이트 축 |
| KRX 채널 분봉이 20시까지 나오는가 | 인트라데이 세션 캡션 |
| 일봉 시가·고가·저가·거래량이 16시 이후 갱신되는가 | EOD 가드 시각과 write-once |
| 통합 채널 현재가가 KRX+NXT 합산값인가 | 스냅샷·배지 |
| 지수가 애프터마켓 중 산출되는가 | 지수 세션 판정 조건 |

### 순서

작업은 세 갈래 성격대로 나누고 순서를 결정했다.

| 후보 | 판정 |
|---|---|
| 제도 변경 조사부터 | 기각. 실측은 월요일 16시 전엔 불가능하고, 정규장에 묶인 X25 슬롯만 잃음 |
| 잔여 항목을 2~3일 안에 끝내고 조사 | 기각. README와 세션 판정 조건 정리가 세션 모델 위의 작업이라 재작업 확률이 큼 |
| **오늘 X25, 정적 조사는 병행, 실측은 월요일** | **채택.** 두 작업이 시간을 두고 다투지 않음 |

보험 하나만 지금 걸어뒀다. 9월 14일 하루는 일봉 적재를 자동 트리거 대신 20시 10분 이후 수동으로 돌린다. 비용은 없고, 세 번째 실측 문항이 어느 쪽으로 나와도 데이터가 오염되지 않는다.

## KIS 호출 실측과 판정

### 호출 경로 분류

X25는 원래 가변 갱신 주기를 설계하려고 세운 측정이었다. 사용자가 적을 때는 빠르게, 많아지면 늦추는 구조를 넣으려면 지금 호출이 어디서 얼마나 나가는지부터 알아야 했다. 화면별 KIS 호출 경로를 전부 뜨고 두 부류로 나눴다. 캐시 공유는 route 캐시가 사용자 수를 흡수해 호출 상한이 "캐시 키 수 ÷ TTL"로 고정되는 쪽이고, 사용자 비례는 캐시 없이 요청마다 KIS로 나가는 쪽이다.

| 경로 | route 캐시 | 분류 | 캐시 miss 또는 요청당 호출 |
|---|---|---|---|
| 국내 지수 시세 · 분봉 | 60초 | 캐시 공유 | 4 · 4 |
| 해외 지수 시세 · 분봉 | 60초 · 120초 | 캐시 공유 | 8 · 7 |
| 시장 순위 | 60초 | 캐시 공유 | 키당 1 |
| 종목 헤더 시세 · 관심목록 다건 시세 | 없음 | 사용자 비례 | 1 · 1 (30종목까지 한 호출) |
| 종목 당일 분봉 | 없음 (동시 요청 dedup만) | 사용자 비례 | 3~17 (시간이 갈수록 증가) |

동시 사용자 수를 바꿔가며 정규장 초당 호출을 계산했다. 사용자마다 종목 차트 탭 하나와 관심목록 20종목 하나를 열어둔 가정이다.

| 동시 사용자 | 캐시 공유 | 사용자 비례 | 합계 (초당) | 한도 20 대비 |
|---|---|---|---|---|
| 1 | 0.34 | 0.28 | 0.63 | 3% |
| 10 | 0.34 | 2.83 | 3.17 | 16% |
| 50 | 0.34 | 14.2 | 14.5 | 73% |

### 정규장 실측

스크립트로 배포 route를 폴링해 받았고, 네 건 모두 설계대로였다.

| 확인 항목 | 결과 |
|---|---|
| 지수 분봉 route가 60초 tick당 한 번만 KIS를 호출하는지 | 20분간 41요청 중 호출 시각 변화 19회, 인접 간격 최소 59.9초. 확인 |
| 탭 복귀 때 stale 재조회가 한 번만 나가는지(#152) | 90초 백그라운드 뒤 복귀, 분봉 요청 1건. 확인 |
| 시세 route의 호출 시각이 응답 어디에 있는지 | 최상위엔 없고 지수 셀마다 있음. #144 구현도, #153의 "없다"도 둘 다 맞았음 |
| 미니차트 장중 시세 실패(F21) | 정규장 관측에서 실패 0(중간 집계) |

### 가변 주기를 기각한 이유

여기까지 놓고 보니 가변 주기의 전제가 서지 않았다. "사용자가 늘면 비용이 한도를 압박한다"가 전제인데, 표를 층별로 읽으면 세 가지가 남는다.

1. 지수와 순위는 캐시 공유라 KIS 호출이 사용자 수와 무관하다
2. 사용자에 비례하는 건 종목 route 셋뿐이고, 그중 헤더 시세와 관심목록은 요청당 한 호출이라 규모가 안 된다
3. 초당 20이라는 한도를 실제로 위협하는 건 평균이 아니라 **종목 당일 분봉 route 하나의 모양**이다

이 route는 당일 분봉을 30봉 단위 TR로 잘라 받기 때문에 오후엔 요청 하나가 15~17호출을 한꺼번에 쏘고, 그걸 60초 폴링과 탭 포커스마다 하루치 전부 다시 받는다.

```
요청 1건  = 30봉 TR × anchor 15~17  →  15~17호출 동시 발사
요청 2건이 같은 초  →  30호출 > 한도 20  →  초과분 null (무데이터와 구분 불가)
```

> #140: 병목은 KIS가 아니라 함수 호출 수. route 캐시가 사용자 수를 흡수하니 KIS 한도는 문제가 안 되고 …

이렇게 적었었는데, 엄밀히는 평균으로만 본 말이었다. 캐시가 흡수하는 건 지수 쪽이고, 종목 분봉은 캐시 없이 사용자마다 15호출씩 쏘고 있었다.

### 지연 레버

반대 방향인 "사용자가 적을 때 더 빠르게"도 메커니즘이 아니라 상수 하나로 끝나는 문제였다. 다만 어느 상수인지는 층마다 다르다. 종목 route는 캐시가 없어 폴링 간격을 줄이면 표시 지연이 그대로 줄지만, 지수 route는 캐시가 SWR이라 만료 뒤 첫 요청이 옛 값을 받고 뒤에서 갱신하는 구조다. 폴링 60초와 TTL 60초가 나란한 지금은 혼자 보는 사용자의 매 요청이 그 "첫 요청"이라, TTL만 줄여봐야 지연은 그대로다.

```
폴링 60s · TTL 60s · 사용자 1명
t=0     캐시 생성                       값 A
t=60    요청 → 만료 직후. A 서빙(60초 전)  백그라운드 갱신 → B
t=120   요청 → 만료 직후. B 서빙(60초 전)  백그라운드 갱신 → C
        … 매 요청이 "만료 뒤 첫 요청". TTL을 30s로 내려도 t=60·120에 받는 값은 같다
```

| 지수 시세 레버 | 표시 지연 | 비용 |
|---|---|---|
| 현행 (폴링 60 · TTL 60) | 60~120초 | — |
| TTL만 단축 | 변화 없음 | — |
| 폴링 30초 | 30~90초 | route 요청 2배 |
| stale 재조회 임계를 TTL+15초에서 TTL로 내려 시세 훅에 이식 | 3~63초 | route 요청 2배, KIS 0 |

세 번째 행은 #152에서 분봉 route에 넣은 재조회를 시세에도 얹을지 미뤄둔 질문의 답이기도 하다. 현 임계(TTL+15초)로 그대로 옮기면 서빙되는 값의 나이가 60~70초라 거의 걸리지 않고, 임계를 TTL로 내려야 효과가 난다. 되는 건 확인했지만 채택하지 않았다. #140에서 "실시간"을 라벨에서 내린 이상 route 요청을 두 배로 늘려 지연 절반을 사는 건 포지셔닝과 맞지 않고, 원하면 상수 한 줄이라 언제든 돌아올 수 있다. 결론은 60초 유지, 반응형 backoff 드롭이다. 대신 #140에서 /credits에 한 줄로 고지한 폴링 주기를 지수·종목·장외 세 축으로 나눠 적기로 했다. 종목은 60초 폴링, 지수는 캐시 때문에 최대 2분, 장외는 스냅샷이라는 사실을 사용자가 읽을 수 있게.

## 종목 분봉 호출 구조

### 120봉 TR 실측

수정 방향은 두 갈래였다. 30봉 TR을 두고 폴링마다 최신 창만 받는 incremental 구조로 가거나, 한 호출에 120봉을 돌려주는 일별 분봉 TR로 당일 분봉을 받아 호출 수 자체를 줄이거나. 후자가 되면 클라이언트를 건드리지 않아도 되니 정규장이 끝나기 전에 120봉 TR을 직접 호출해 봤다.

| 확인 | 결과 |
|---|---|
| 120봉 TR로 당일 분봉이 오는가 | KRX·통합 채널 모두 반환, 마지막 봉 지연 0분, 진행 중인 분 포함 |
| 30봉 TR과 값이 같은가 | 완결된 창은 일치. 현재 시각을 덮는 창에서만 종목당 1봉 차이 |
| 그 1봉의 원인 | 30봉 TR이 마지막 체결(10:26)을 현재 분(10:46)으로 옮겨 붙이고 원래 분을 거래량 0으로 돌려줌. HTS 분봉으로 대조하니 120봉 쪽이 실체 |
| "120봉"의 의미 | 체결이 있는 분 120개. 무체결 분 채움 옵션을 켜도 동일 (120행 = 당일 53 + 전일 67, 173분 슬롯) |
| 일부 호출이 실패하면 화면은 | 병합에서 조용히 빠지고 실패 표시 없음. 차트는 빈 구간 없이 축을 당겨 붙임 |

사전에 정한 채택 기준은 "30봉 TR과 값이 같을 것"이었고 문면상으론 어긋났다. 그런데 어긋난 봉의 원인이 30봉 TR 쪽이었다.

```
서린바이오 · 10:26 마지막 체결, 이후 20분 무체결 (호출 시각 10:46)

30봉 TR    10:26 거래량 0   ·   10:46 봉 있음 (10:26의 체결값)   ← 허구 봉
120봉 TR   10:26 체결       ·   10:46 봉 없음
HTS        10:26 체결       ·   10:46 봉 없음
```

저유동 종목에서 마지막 체결을 현재 분으로 끌어올리는 quirk인데, 11시 반까지 8천 주도 안 되는 종목이라 HTS 분봉이 듬성듬성해서 어느 쪽이 실체인지 바로 갈렸다. 기준의 전제였던 "30봉 TR = 정답"이 무너진 것이라 #153 F43 때처럼 전제를 정정하고 갔다. 덤으로, 지금 배포된 차트는 저유동 종목의 현재 분에 있지도 않은 체결 봉을 그리고 있다는 사실도 확정됐다.

| 30봉 TR 유지, 폴링마다 최신 창만 받는 incremental | 기각. 마운트 때 15호출 버스트가 남고 허구 봉도 그대로 |
| 120봉 TR 전환, 체결 분만 그대로 그리기 | 기각. #149·#151의 초기 창과 리셋 설계가 "30봉 = 30분" 전제라 축 압축이 그 설계를 깸 |
| **120봉 TR 전환 + 서버 정규화 단계에서 분 슬롯 채우기** | **채택.** 요청당 호출 15→4(NXT 6), 허구 봉 소멸. 채움 규약은 #120에서 확인한 KIS flat 봉과 동일 |

구현 전에 결정을 네 줄로 고정해 뒀다.

1. **채우는 위치** — route 앞 정규화 단계의 순수 함수. 클라이언트 계약(분 단위 dense 봉)은 그대로
2. **채움 규약** — 시가·고가·저가·종가 모두 직전 종가, 거래량 0. KIS가 30봉 TR에서 돌려주던 flat 봉과 같은 형태
3. **어느 분을 채울지** — 새로 정의하지 않고 지금 30봉 경로가 쓰는 갭 창 제외 판정 조건을 소비. 월요일 이후 X27이 16시부터 20시 슬롯을 손볼 곳이 바로 그 판정 조건이라, 여기서 스케줄을 따로 적으면 소스가 둘이 된다
4. **전일 봉 섞임과 중복** — 120봉이 전날로 넘어가며 오는 건 기존 휴장일 경로의 날짜 필터와 dedup 재사용

### 일부 실패와 빠뜨린 버스트

일부 호출 실패 쪽은 한도 초과 응답을 식별해 그때만 재시도하는 안을 먼저 생각했다. 그러려면 초과 응답의 형상이 필요해 25호출을 1초에 쏘는 probe를 준비해 뒀는데, 120봉 경로에서는 무데이터가 전일 봉으로 오지 null로 오지 않으니 null은 곧 실패였다. 구분할 게 없어졌다. "null인 창은 1초 뒤 한 번 재시도, 그래도 null이면 요청 전체를 실패로 보고 기존 실패 배지 경로를 탄다"로 정하고, 배포 앱키로 한도를 일부러 치는 probe는 소비처가 없어져 취소했다.

정리하다 빠뜨린 버스트가 하나 더 보였다. 캐시 공유 route도 캐시가 만료되면 안에서 호출을 한꺼번에 쏜다. 지수 페이지를 연 사용자 한 명이 route 다섯 개를 같은 순간에 폴링하면 만료도 같은 초에 오고, 그 초에 4+4+8+7+1로 17호출, 해외 분봉 TTL이 겹치는 격 tick엔 24호출이 나갈 수 있다. 사용자 한 명으로 성립하는 시나리오라 X28과는 별건으로 신설했다(F92). 다섯 훅의 폴링 시작 위상이 실제로 같은지는 아직 안 봤으니, 확인되면 해외 훅을 15초 비트는 정도의 소형이고 아니면 조치가 없다.

## 정리

- **X25 종결** — 호출 경로 9종 분류, 정규장 실측 4건 전부 설계대로. 가변 갱신 주기는 전제가 서지 않아 기각, 60초 유지, 반응형 backoff 드롭. 코드 0
- **X28 신설** — 종목 당일 분봉 요청 하나가 15~17호출 동시 발사. 120봉 TR 전환 + 서버 분 슬롯 채움으로 4호출, null 창 1회 재시도 후 실패 표시. 다음 세션 구현
- **X27 신설** — 9/14 KRX 애프터마켓. REST 시세 계약 변경 없음, 우리 쪽 전제 네 곳과 월요일 실측 다섯 문항. 당일 EOD는 수동 실행
- **F92 신설** — 지수 route 다섯 개의 동시 만료 버스트 17~24호출 가능성. 폴링 위상 확인 후 판정
- **30봉 TR의 허구 봉** — 저유동 종목 마지막 체결이 현재 분으로 옮겨져 그려지고 있음. X28 배포로 소멸
- **일정** — X28 → README 초안 → 월요일 저녁 X27 실측 → 조치. README는 장외 시간 문구를 스케줄에 묶지 않고 먼저 쓴다

가변 폴링을 설계하려고 잰 측정이 기능 하나를 안 만드는 결론으로 끝났다. 병목이 주기가 아니라 호출 모양이었고, 모양을 고치면 주기를 만질 이유가 사라진다. 사실 #140에서 폴링 단축안을 접을 때 접속자 수를 빼고 계산했다고 적었는데, 이번엔 평균만 보고 버스트를 뺐다는 걸 정리 단계에서야 알았다.
