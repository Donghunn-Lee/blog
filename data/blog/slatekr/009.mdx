---

## 관심 종목의 저장소

관심종목을 어디에 저장할지가 첫 번째 판단이었다.

서버(DB)에 저장하면 기기 간 동기화가 된다.
하지만 그러려면 인증이 필요하고, 인증이 생기면 회원가입, 로그인, 세션 관리가 따라온다.

SlateKR은 투자 추천도 아니고 개인화 분석도 아니다. 종목 정보를 빠르게 조회하는 서비스다.
여기에 인증을 붙이는 건 지금 단계에서 범위를 너무 넓히는 일이었다. 할 수 있다면 물론 좋겠지만, 이건 어디까지나 프론트엔드 프로젝트니까.

localStorage에 저장하는 게 최선이라고 생각했다.
기기 간 동기화는 포기하지만, 로그인 없이 쓸 수 있고 구현 범위도 명확하다.
관심종목이 사라져도 치명적이지 않다. 북마크에 가까운 기능이니까.

---

## Zustand + persist

클라이언트 상태 관리 라이브러리로는 이미 익숙한 Zustand를 쓰기로 했었다.
persist 미들웨어를 쓰면 store 상태를 localStorage에 자동으로 직렬화해서 저장하고, 새로고침해도 유지된다.

```ts
export const useWatchlistStore = create<WatchlistStore>()(
  persist(
    (set, get) => ({ ... }),
    { name: 'slatekr-watchlist' }
  )
)
```

직접 `localStorage.setItem`을 쓰는 것보다 store와 영속성이 하나로 묶여 있어서 관리가 단순해진다.

---

## addedAt은 store 내부에서

`addToWatchlist`의 파라미터 타입을 `Omit<WatchlistItem, 'addedAt'>`으로 했다.

호출하는 쪽에서 `addedAt`을 직접 넘기면, 컴포넌트마다 `Date.now()`를 각자 찍게 된다.  
저장 시점은 store가 결정해야 일관성이 보장된다. 호출 측은 ticker, name, market만 넘기면 된다.

---

## 한도 초과는 컴포넌트에서 먼저 확인

store의 `addToWatchlist`는 한도(50개) 초과나 중복 ticker가 들어오면 조용히 무시한다.  
그런데 사용자 입장에서는 버튼을 눌렀는데 아무 반응이 없으면 의아하다.

그래서 `WatchlistButton`에서 추가 전에 먼저 확인하고, 한도 초과면 toast를 띄운다.  
store는 방어 역할만 하고, 사용자 피드백은 컴포넌트가 담당한다.

---

## StockHeader에 버튼 달기

`WatchlistButton`은 `use client`다. `StockHeader`는 Server Component다.  
Server Component 안에서 Client Component를 import하는 건 Next.js에서 정상 동작한다. 해당 컴포넌트만 클라이언트 번들로 분리되고, `StockHeader` 자체는 서버에서 렌더된다.

`StockHeader`에 `use client`를 붙이는 대신 이 구조를 유지했다. 서버 컴포넌트의 이점을 버릴 이유가 없었다.

---

## /watchlist 페이지

목록 자체가 클라이언트 상태에 있으니 페이지도 `use client`다.
`[...items].sort()`로 addedAt 내림차순 정렬을 했는데, store의 배열을 직접 정렬하면 상태를 변이시키기 때문에 복사 후 정렬했다.

빈 상태는 리스트 대신 안내 문구만 보인다. 처음 방문하거나 전부 지웠을 때다.

현재는 관심 종목을 페이지로 만들었지만, 추구 사이드바나 별도 패널 느낌으로 하는 방식을 나중에 다시 판단할 생각이다.

## MVP 완성, 핵심 기능 구현 시작

관심종목 기능이 붙으면서 핵심 플로우가 닫혔다.

검색 → 종목 상세 → 관심종목 저장.

다음은 홈 페이지 UI 보완과 기본 SEO다. MVP의 마무리 단계다.
물론 MVP일 뿐, 디자인이나 추가하고 싶은 기능, 구현 목표인 핵심 기능은 시작도 안 했다.

이제부터 본격적인 개발 시작이라고 해도 과언이 아닐 것이다.
