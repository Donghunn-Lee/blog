최근 몇 세션에서 동작하는 줄 알았던 것들이 연달아 나왔다. 종목 페이지의 revalidate 선언은 한 번도 적용된 적이 없었고, 차트 당일 봉은 캐시 키가 어긋나 한 달 가까이 갱신되지 않았다. 코드 읽기(G2)에 들어가기 전에 같은 종류를 한 번 훑어 두기로 한 것이 이번 전수조사(R9)다.

계획은 조사를 돌리고 결과를 분류하는 데까지였다. 실제로는 직전 글에서 확인 전으로 남긴 두 건, 곧 로드 중 편집이 서버의 관심종목 목록을 덮는 문제(F123)와 홈 지수 셀 값이 차트 라벨과 다른 문제(E97)의 재현을 조사에 붙였고, 고칠 것이 전부 작아서 수정까지 같은 세션에 끝냈다. F123만 수정 방식을 정하는 데서 멈췄다.

## 조사 구성

조사는 코드를 고치지 않는 probe 셋으로 나눠 동시에 돌렸고, 판정은 결과를 모아 한 번에 했다. 쿠키 이름 상수가 세 군데에 따로 정의돼 있다는 사실처럼 두 조사에 걸쳐 나오는 항목이 있어서, 따로 판정하면 커밋 묶음을 다시 짜야 하기 때문이다.

```
데드코드       knip 리포트 → 후보마다 참조를 다시 확인
무효 선언      지난 사고 유형 7가지를 체크리스트로, 항목마다 조사 범위도 기록
재현 · 원인    F123 브라우저 재현, E97 원본 값 대조
```

무효 선언 쪽에만 조사 범위를 남긴 건 이 유형이 "없다"는 걸 증명할 수 없기 때문이다. 발견이 0건이어도 어디까지 봤는지가 남아 있어야 다음에 같은 자리를 다시 뒤지지 않는다.

## 도구가 사용 중으로 센 함수

미사용 파일은 0건이었고, 걸린 건 "테스트에서만 import되는 export 48건"이었다. 파일 안에서 쓰이면서 테스트용으로 export만 열어 둔 것인지, 테스트만 붙들고 있는 죽은 함수인지가 리포트로는 구분되지 않아 실서비스 코드에서의 호출을 다시 따라갔다. 네 개가 나왔고 한 번 더 확인하니 다섯 번째가 있었는데, knip은 export 단위로만 보기 때문에 죽은 함수가 죽은 함수를 부르면 사용 중으로 센다.

다섯 개는 전부 미국장 세션 판정 함수였다. 8월 말 해외 지수 분봉을 개편하면서 호출이 끊겼고, 그 뒤로는 테스트 24건만 계속 통과하고 있었던 것이다. 삭제 뒤 테스트는 1,175건에서 1,148건이 됐다.

| 묶음 | 판정 |
|---|---|
| 미국장 세션 판정 함수 5개와 내부 helper · 타입 | **삭제.** 실서비스 코드에서 도달 불가, 테스트만 참조 |
| 미사용 타입 1개 · 타입 재수출 6건 · 판정 함수 재수출 2건 | **삭제.** 소비처가 전부 원본을 직접 import |
| 서버가 채우지만 클라이언트가 읽지 않는 시세 출처 필드 | **삭제.** 배지 판정은 실패 플래그와 세션으로 이미 구현 |
| export만 미사용인 상수 · 타입 50건 | 기각. 파일 안에서 사용 중, 접근 범위 문제 |

## 거짓인 선언만 수정

무효 선언의 판정 기준은 "선언이 거짓인가" 하나로 잡았다. #174의 revalidate는 적용되지 않는 주기를 적어 둔 거짓이었지만, route 11곳의 동적 렌더 강제 선언은 기본값과 같을 뿐 실제 동작과 일치한다. 이런 중복까지 지우면 변경만 늘고 얻는 게 없어서 그대로 뒀다.

| 발견 | 판정 |
|---|---|
| 지수 페이지 접힘 애니메이션이 0.2초 동안 돌지만 높이는 한 번에 바뀜 | **수정.** 아코디언용 키프레임이 읽는 CSS 변수를 Collapsible은 설정하지 않음 → 전용 키프레임으로 교체 |
| route 11곳의 동적 렌더 강제 선언 | 유지. 기본값과 같은 중복이지만 참인 선언 |
| 실패 캐시 무효화가 오래된 값을 한 번 더 서빙한다는 지적(#175) | 기각. 호출부 6곳이 이미 즉시 만료 형태, 설치된 Next.js 소스로 확인(배포 환경의 캐시 구현은 미확인) |
| 실패가 빈 상태로 표시되는 곳 6건 | 신설(F124). 동작 변경이라 이번 범위 밖 |
| 수집 스크립트 4개가 전량 실패에도 정상 종료 | 신설(F125). 실패 신호가 없음 |

넷째 줄은 README 문장과 직접 부딪힌다. 섹션마다 실패와 빈 상태를 구분한다고 적었는데, 종목 상세에서 재무 조회만 실패하면 PER · EPS · BPS가 오류 문구 없이 "—"로 그려진다. 동작을 바꾸는 수정이고 실패를 주입해 확인해야 해서 삭제 위주인 이번 작업과는 분리했다.

## 로드 중 편집 재현

관심종목은 로그인 없이 쿠키로 식별해 서버에 스냅샷을 백업한다(#141). 그때 정한 로드 규칙에 "서버 조회 중에 로컬 편집이 생기면 로컬이 더 새것"이라는 줄이 있었고, 직전 글에서 README만 읽은 쪽이 이 줄의 구멍을 짚었다. localStorage가 비고 쿠키만 남은 상태라면 그 새 로컬은 방금 추가한 한 건뿐이라는 것이다.

```
서버에 3건 저장 → localStorage의 관심종목만 삭제 (쿠키 유지)
→ 새로고침, 서버 조회 응답을 8초 지연 → 응답 전에 1건 추가
→ 응답 도착: 조회 중 편집이 있었으므로 로컬 1건을 PUT
→ 서버 3건 → 1건, 그룹 id까지 교체
```

재현 과정에서 원인이 규칙보다 한 단계 앞에 있다는 것도 확인됐다. 로컬이 비면 스토어는 빈 기본 상태로 시작하는데, 이 상태가 원래 비어 있던 유효한 로컬과 구분되지 않는다. 공교롭게도 #141에서 조회 실패 시 쓰기를 막은 이유가 바로 한 건짜리 스냅샷이 서버 전체를 덮는 경우였는데, 조회가 늦게 성공하는 경우에는 바로 윗줄 규칙이 같은 일을 하고 있었다. Safari는 일주일간 상호작용이 없는 사이트의 localStorage를 지우고 서버가 심은 쿠키는 남기므로(WebKit 정책 기준이고 직접 재 보지는 않았다), 드문 조건이라고 넘길 수도 없었다.

| 후보 | 판정 |
|---|---|
| 서버 스냅샷에 로드 중 편집을 다시 적용 | 기각. 편집 기록이 없음, 그룹 관리 모달은 전체 교체, 빈 로컬의 기본 그룹 id가 서버와 달라 매핑 필요 |
| **로드가 끝날 때까지 편집을 막고, 로드 결과는 항상 서버가 덮음** | **채택.** 분기와 플래그가 사라져 코드가 줄고, 최악의 결과가 목록 유실에서 버튼 잠깐 비활성으로 바뀜. 구현은 다음 세션 |

## 홈 지수 셀과 차트 라벨

![](/static/images/velog/3f168c00-9efd-4fc2-8514-7515b21bf9ca-image.png)


| 지수 | 셀 | 차트 라벨 | 차이 |
|---|---|---|---|
| 코스피 | 6,941.39 | 6941.39 | 없음 |
| 코스닥 | 919.92 | 919.92 | 없음 |
| 코스피200 | 1,095.83 | 1095.81 | 0.02 |
| 코스닥150 | 1,596.48 | 1596.35 | 0.13 |

장중에는 두 값의 폴링 시점이 달라 원인을 가를 수 없어서, 값이 고정되는 장 마감 뒤에 원본 응답을 대조했다. 셀은 지수 현재가였고 라벨은 분봉의 마지막 봉이었다. 15:30 이후 프린트가 한 번 더 들어오는 지수는 그 값이 마지막 봉에 병합돼 일치하지만, 프린트가 없는 코스피200과 코스닥150에는 확정 전 값이 남는다.

두 값을 맞추려면 현재가를 마지막 봉에 병합해야 하는데, 그러면 호출도 캐시도 폴링도 따로인 두 값을 장중 내내 맞추는 분기가 생긴다. 라벨이 보여 주는 값은 바로 위 셀에 이미 있으니 라벨을 숨기는 쪽이 잃는 게 없었다. 콤마와 소수 자릿수는 해외 지수 목록이 쓰던 포맷터를 공용으로 올려 축 눈금까지 통일했고, 지수 페이지에 남은 같은 문제는 따로 다루기로 했다(E98).

## 정리

- **R9 종결** — probe 3개 조사 후 일괄 판정, 수정 커밋 7개. 도달 불가 코드 삭제로 테스트 1,175 → 1,148건
- **E97 종결** — 홈 미니 차트의 마지막 값 라벨 숨김, 지수 표기 포맷터 통일. 지수 페이지는 E98로 분리
- **F123 재현** — 서버 3건이 로컬 1건으로 교체되는 것 확인. 병합 대신 로드 중 편집 차단으로 판정, 구현 전
- **F124 · F125 신설** — 실패가 빈 상태로 표시되는 6곳, 전량 실패에도 정상 종료하는 수집 스크립트 4개
- **부수 수정** — 지수 페이지 접힘 애니메이션, AI 요약의 라벨과 값 사이 간격, README와 CLAUDE.md의 캐시 주기 · CI 서술 정정

기능은 하나도 늘지 않았고 지운 줄이 쓴 줄보다 많은 세션이었다. 조사에서 나온 것 가운데 무게가 있는 쪽은 데드코드가 아니라 동작한다고 적어 둔 것들이었는데, 그건 도구가 아니라 README 문장과 대조해서 나왔다. 엄밀히는 전수조사라기보다 지난 사고 유형을 다시 훑은 것에 가까워서, 겪어 보지 않은 유형은 이번에도 못 잡았을 것 같다.
