이번 작업에선 부실했던 검색 플로우를 보완해 완성했다.

기존 검색창은 자동완성 드롭다운에서 항목을 선택할 때만 동작했다.
자동완성 선택 없이 엔터를 누르면 아무 일도 일어나지 않았고,
검색 결과 페이지 자체가 없었다.

자동완성은 사용자가 뭘 찾는지 이미 아는 경우를 위한 경로고,
불확실한 질의나 URL 공유, 새로고침 같은 상황은 전부 비어 있었다.

이번 작업은 그 빈자리를 채우는 일이었다.

---

## 엔터 동작 분기

엔터 동작을 먼저 정리했다.

자동완성에서 특정 항목이 하이라이트된 상태(화살표로 이동된 상태)에서 엔터를 누르면
기존처럼 해당 종목 상세 페이지로 바로 이동한다.

하이라이트된 항목이 없는 상태에서 엔터를 누르면 `/search?q={query}`로 이동한다.
빈 입력이나 공백만 있으면 아무 동작도 하지 않는다.

```
하이라이트 있음 + Enter  →  /stocks/{ticker}
하이라이트 없음 + Enter  →  /search?q={query}
검색 버튼 클릭            →  /search?q={query}
빈 입력 / 공백            →  무동작
```

드롭다운은 "확신이 있을 때"의 빠른 경로, `/search`는 "일단 찾아보자"의 경로로 역할을 나눴다.

---

## /search 페이지 — 결과가 1개일 때

`/search` 페이지는 Server Component로 만들었다.
API route를 거치지 않고 서버에서 `searchStocks()`를 직접 호출한다.

결과에 따라 4가지로 분기한다.

```
빈 쿼리     →  empty state (검색어 입력 안내)
0개 결과    →  empty state ("XXX에 해당하는 종목이 없습니다")
1개 결과    →  redirect('/stocks/{ticker}')
2개 이상    →  결과 목록 렌더링
```

고민했던 건 결과가 1개일 때다.
목록을 보여주고 클릭을 한 번 더 받을 것인가, 아니면 바로 상세 페이지로 보낼 것인가.

"삼성전자"처럼 정확하게 검색한 경우, 카드 한 장을 보여주고 클릭을 유도하는 건 불필요한 중간 단계다.
그래서 `redirect()`로 바로 상세 페이지로 보냈다.
서버 사이드 redirect라서 유저 입장에선 `/search` URL을 의식할 일조차 없다.

---

## 검색 페이지에 검색창 유지

검색 결과 페이지에서도 검색어를 수정할 수 있어야 한다. 결과를 보고 "아, 이게 아니라 저걸 찾으려던 거였지" 싶을 때 다시 입력할 수 있어야 하니까.

그런데 두 가지 제약이 겹쳤다.

`SearchInput`은 controlled 컴포넌트다.
`value`와 `onChange`를 외부에서 받는 구조로, 내부에 상태를 갖고 있지 않다. 홈에서 이 방식으로 이미 연결돼 있다.

`/search` 페이지는 Server Component다.
`searchStocks()`가 DB에 직접 접근하는 함수라 서버에서 실행해야 하고, `generateMetadata`로 검색어 기반 타이틀을 만들어야 하기 때문이다.
그래서 `useState`를 쓸 수 없다.

선택지는 둘이었다.

하나는 `SearchInput`을 상태 내장형으로 바꾸는 것. 하지만 그러면 홈에서도 구조가 달라지거나, 같은 컴포넌트가 페이지에 따라 다르게 동작하게 된다. 홈에서는 외부 상태로 연결돼 있고 `/search`에서는 내부 상태로 움직이는 식이다. 같은 컴포넌트를 쓰는 의미가 옅어진다.

다른 하나는 `/search` 전용으로 얇은 Client 래퍼를 하나 두는 것. `SearchInput`의 controlled 구조는 그대로 두고, 래퍼가 상태를 소유한다.

후자를 택했다.

```tsx
export const SearchBarWithState = ({ initialQuery = "" }: Props) => {
  const [value, setValue] = useState(initialQuery);
  return <SearchInput value={value} onChange={setValue} />;
};
```

Server Component인 `/search`에서 URL의 `q` 파라미터를 `initialQuery`로 넘기면, 래퍼가 이어받아 상태로 관리한다. `SearchInput`은 원래의 controlled 구조를 유지한다.

파일이 하나 늘어났지만, 이 파일의 역할은 명확하다. 상태가 필요 없는 컨텍스트에 controlled 컴포넌트를 심기 위해서.

## 최근 검색어 저장 시점 — 어디서 기록할 것인가

이번 작업에서 가장 오래 고민한 건 최근 검색어 저장 시점이었다.

검색 플로우가 늘어나면서 종목 상세로 진입하는 경로가 세 가지가 됐다.

1. 자동완성 드롭다운에서 선택
2. 엔터 → `/search` → 결과 1개 → redirect
3. 엔터 → `/search` → 결과 목록 → 카드 클릭

기존 구조에서는 1번에서만 `addRecent`가 호출됐다.
2번과 3번을 새로 추가하려면 각 진입점마다 저장 로직을 흩뿌려야 한다.

그런데 세 경로의 공통점이 있다. **결국 전부 `/stocks/{ticker}`에 도달한다.**

그래서 저장 시점을 종목 상세 페이지 마운트로 통일했다.

```tsx
export const RecentSearchRecorder = ({ ticker, name }: Props) => {
  const add = useRecentSearchesStore((s) => s.add);
  useEffect(() => { add(ticker, name); }, [ticker, name, add]);
  return null;
};
```

렌더링 없는 Client Component다.
상세 페이지(Server Component)에 한 줄 추가하면 모든 진입 경로가 커버된다.
`HomePage`와 `SearchBarWithState`에 있던 `addRecent` 관련 코드는 전부 제거했다.

저장 조건의 의미도 더 명확해졌다.
"검색했을 때 저장"이 아니라 "실제로 종목을 봤을 때 저장"이 됐다.

단순 검색만 하고 상세 페이지 방문 없이 돌아갔다면 최근 검색어에 남지 않는다.

---

## 돌아보면 같은 질문

이번 작업을 마치고 보니, 세 가지 결정이 전부 같은 질문에 대한 답이었다.

- `SearchInput`에서 `onSubmit` prop을 제거하고 내부에서 `router.push` → 동작의 완결성을 컴포넌트 안으로
- `SearchBarWithState`로 클라이언트 상태를 분리 → 상태 소유권의 경계
- `RecentSearchRecorder`로 저장 시점을 통일 → side effect의 단일 지점

전부 "이 책임은 어디에 있어야 하는가"였다.
진입점마다 흩뿌리지 않고, 의미에 맞는 한 곳에 모으는 방향으로 결정했다.
