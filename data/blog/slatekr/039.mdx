#  

이번 작업은 [#038](/blog/slatekr/038/)에서 다단계 폴백을 추가하고 6종목 샘플로 검증한 뒤, affected_tickers.txt에 모인 780종목을 전체 재적재하는 데서 시작했다. 재적재가 끝나면 NULL 비율이 얼마나 떨어지는지 측정하고, 다음 트랙으로 넘어가는 게 원래 계획이었다.

근데 측정 결과를 보다가 다시 멈췄다.

---

## NULL 5.48% — 무시하기엔 어려운 공백

```sql
SELECT COUNT(*) FILTER (WHERE eps IS NULL) AS null_count,
       COUNT(*) AS total
FROM financial_statements
WHERE report_type = 'annual' AND year BETWEEN 2020 AND 2024;
-- 512 / 9344 → 5.48%
```

연간 5.48%, 분기 6.51%. 처음엔 이 정도면 끊어도 되는 수준 같았다. 그런데 NULL 종목 상위 30개를 뽑으니 패턴이 좀 이상했다.

| ticker | null_years |
| ------ | ---------- |
| 000320 | 4 |
| 002360 | 4 |
| 002840 | 4 |
| 003380 | 4 |
| ... | ... |

전부 5년 풀 NULL이었다. 한두 해 변형 표현으로 누락된 게 아니라, 종목 자체가 통째로 안 잡히고 있었다. #038 폴백은 이걸 못 잡고 있다는 뜻이다.

추가 폴백을 또 붙이면 될까. 그 전에 한 번 다른 각도에서 보고 싶어졌다.

---

## 다른 서비스들은 어떻게 하고 있을까

네이버 금융, 컴퍼니가이드 같은 곳들도 결국 DART 데이터를 쓸 텐데, 우리처럼 예외 케이스를 사후 보정으로 잡고 있는 건가. 표준 API가 따로 있는데 내가 안 쓰고 있는 건 아닌가.

DART OpenAPI 가이드를 다시 봤다. 우리가 쓰는 `fnlttSinglAcntAll` 외에 세 가지가 더 있었다.

- `fnlttSinglAcnt` — 단일회사 주요계정 조회
- `fnlttSinglIndx` — 단일회사 주요 재무지표 조회
- `fnlttXbrl` — XBRL 원문 내려받기

이름만 보면 `fnlttSinglIndx`가 답이었다. "주요 재무지표"라니. 회사 무관 동일한 키로 EPS, ROE가 떨어진다면 account_nm 정규화로 고생할 일이 없다.

---

## 4종 API를 차례로 떠보기

`fnlttSinglAcnt`부터 호출했다. 응답은 30개 항목으로 떨어졌지만 `account_id` 필드가 아예 없었다. 자산총계, 매출액, 영업이익 같은 핵심 계정만 추린 축약판으로, `fnlttSinglAcntAll`의 부분집합이었다. 표준화 API가 아니라 핵심 계정 추출용이었다.

`fnlttSinglIndx`는 첫 호출에서 status 100이 떨어졌다. 파라미터 구조가 달랐다. `fs_div` 대신 `idx_cl_code`(지표 분류 코드)를 받고, 수익성/안정성/성장성/활동성 4종으로 나뉘어 있었다.

4종을 다 호출해서 어떤 지표가 제공되는지 봤다.

| 필요 지표 | fnlttSinglIndx 제공 | idx_code |
| --- | --- | --- |
| ROE | O | M211550 |
| 부채비율 | O | M221100 |
| 영업이익률 | X (매출원가율만 있음) | — |
| EPS | X | — |
| BPS | X | — |

ROE와 부채비율은 깨끗하게 표준화돼 있었다. 하지만 정작 우리가 가장 고생한 EPS/BPS는 4종 어디에도 없다. 거기다 이 API는 2023년 3분기 이후 데이터만 제공한다. 5년치 중 1.5년만 커버되는 셈이다.

`fnlttXbrl`은 XBRL 원문 ZIP을 받아서 직접 파싱하는 방식이다. 증권사들이 실제로 쓰는 노선인데, Arelle 같은 XBRL 파서를 붙여야 하고, 표준계정 미사용 회사는 XBRL 원문에서도 똑같이 변형돼 있다. 정규화 책임이 우리에게 오는 건 같다.

---

## 도입 보류 결정

여기서 인식이 한 번 바뀌었다. 어떤 데이터 소스를 써도 100% 정규화는 불가능했다. 증권사들도 결국 자체 매핑 테이블에 수동 검증을 더해서 푸는 거였다. EPS만 보면 원본 API + 폴백이 사실상 정답이었다.

`fnlttSinglIndx`의 ROE/부채비율 활용은 가능성 있는 옵션이지만, EPS 문제를 해결해주는 게 아니고 2023 3Q 이후만 커버한다. 활용 방안으로는 23년 3Q이전 데이터는 현재 적재한 데이터를 유지하되, 해당 분기 이후로는 표준 데이터로 사용할 수 있겠지만 당장으로선 도입할 가치 대비 비용이 크다고 봤다. 데이터 일관성도 흐려진다. 트랙 X에 보조 옵션으로 남겨두고 MVP 이후로 미뤘다.

원위치로 돌아왔지만 의미는 있었다. 이제 "왜 `fnlttSinglAcntAll`만 쓰는가"에 근거 기반으로 답할 수 있게 됐다. 4종 다 검토했고, EPS/BPS는 어차피 원본 API에서 폴백으로 잡아야 한다.

그러면 다시 NULL 종목으로 돌아갈 차례였다. 원본을 한 번 더 보는 게 #038에서 배운 거였으니까.

## raw 응답 재확인

상위 30개 종목 중 6개를 골라서 2024년 사업보고서 응답에 "주당" 키워드 포함 행만 출력했다. quota 12건이면 충분했다.

세 가지 패턴이 나왔다.

```null
004410   account_nm: 보통주 기본주당이익     value: -7.92
008700   account_id: ifrs-full_BasicEarningsLossPerShare   value: 0.09
032820   account_nm: 보통주 기본주당이익     value: -22.79
```

4건이 소수점 값이었다. 적자 종목(004410, 032820)이거나 EPS 절댓값이 작은 종목(008700)이었다. account_id는 표준 IFRS 코드로 잘 떨어졌고, account_nm도 매칭 후보에 있었다.

폴백 로직이 못 잡은 게 아니다. **마지막 변환 단계에서 깨지고 있었다.**

```python
raw = item.get("thstrm_amount", "").replace(",", "").strip()
value = int(raw) if raw else None   # ValueError on "0.09"
```

`int("0.09")`는 ValueError를 던진다. 그 try/except 블록은 값을 None으로 두고 다음 단계로 넘어가게 돼 있는데, 폴백 다른 단계도 다 같은 변환을 쓰니까 결국 NULL로 저장된다. 폴백 로직을 4단계, 5단계로 만들어도 변환이 깨지면 의미가 없었다.

좀 허무했다. 동시에 안도감이 들었다. 표준 API를 못 쓰는 게 진짜 한계는 아니었던 거다. 우리 쪽 처리 한 줄이 문제였고, 그건 고칠 수 있었다.

나머지 2건은 account_nm 변형(`기본및희석주당이익` 등)이었고, 1건은 DART 원본에 EPS 항목 자체가 없었다. 변형 케이스는 `_EPS_NM_TARGETS`에 추가하면 됐다.

## numeric 타입으로 전환

DB 스키마부터 다시 확인했다. `eps integer`, `bps integer`. 처음 설계할 자연스레 정수만 들어올 거라 가정한 거였는데, 적자 종목에서 소수점이 빈번하게 나올 수 있다는 점을 고려하지 못했다.

선택지를 정리했다.

- `integer` 유지 + Python에서 `round()` → 정밀도 손실. 0.09는 0이 된다. 부적합.
- `real`(float4) → 부동소수점 오차 위험. 금융 도메인엔 부적합.
- `numeric(15, 4)` → **소수점 보존, PostgreSQL 표준. 적합.**

`numeric(15, 4)`로 갔다. 정수부 11자리까지 수용하므로 [#032](/blog/slatekr/032/)에서 한 번 터졌던 075580 같은 overflow 케이스(원래 B8 항목)도 같이 해결된다. 마이그레이션 자체는 비파괴적이다. PostgreSQL이 INTEGER → NUMERIC을 암시적 캐스팅으로 처리해서 기존 정수 값이 그대로 변환된다.

```sql
ALTER TABLE financial_statements
  ALTER COLUMN eps TYPE numeric(15, 4),
  ALTER COLUMN bps TYPE numeric(15, 4);
```

ALTER 마이그레이션과 별개로 한 가지 확인할 게 있었다. 
[#036](...)에서 발견했던 직렬화 이슈 — Neon HTTP API는 bigint를 string으로 
반환하고, 그걸 잡으려고 `pool.query` 후처리 레이어를 만들어뒀었다. 
numeric도 같은 부류였다. 공식 CONFIG.md에 numeric 파서 예시가 직접 나와 있다.

```ts
const NUMERIC_OID = 1700;
.filter((f) => f.dataTypeID === INT8_OID || f.dataTypeID === NUMERIC_OID)
```

기존 후처리 필터에 OID 1700을 추가하는 한 줄로 끝났다. 
공통 진입점에 처리 레이어를 만들어둔 게 새 타입 도입 비용을 거의 0으로 만들어줬다.

`account_nm`변형 케이스 2건(`보통주 기본및희석주당손익` 등)은 
`_EPS_NM_TARGETS`에 정규화 결과를 추가하는 것으로 처리했다. 
[#038](...)에서 정의한 정규화 함수가 "및희석"을 제거하기 때문에, 
집합에 들어가는 값은 원본이 아니라 정규화 후 형태다.

## 결과

재재적재 후 NULL 비율 측정.

| 항목 | Before | After |
| --- | --- | --- |
| 연간 EPS NULL | 5.48% (512/9344) | 2.74% (256/9344) |
| 분기 EPS NULL | 6.51% (2243/34456) | 2.55% (878/34456) |

연간은 절반, 분기는 60% 이상 회수됐다. 처음 예상(0.8%)보다는 높게 남았는데, 샘플 7건 분포를 전체에 단순 비례로 적용한 추정이 낙관적이었다. 실제로는 DART 원본 자체에 EPS 항목이 없는 종목이 예상보다 많았다.

8개 검증 종목 중 7개에서 회수가 확인됐다. 소수점 케이스(`-95.4`, `0.09`, `-7.92` 등) 4건, account_nm 변형 케이스 3건 모두 정상 적재. 남은 1개는 003380(하림지주)으로, 2021~2024 사업보고서에 EPS row가 아예 없는 케이스다. 폴백 로직과 무관하다.

남은 NULL 종목 상위에 지주사가 다수 분포한다. 지주사는 자체 사업 매출이 작고 종속회사 배당이 주요 수익원이라 단순 EPS 공시 정책이 회사마다 다를 수 있는데, 이건 별도 트랙으로 분리.

## 정리

- DART API 4종을 검토하고 EPS는 결국 `fnlttSinglAcntAll` + 폴백이 정답이라는 걸 근거 기반으로 정리했다. ROE/부채비율 표준 API 활용은 트랙 X에 보조 옵션으로 보존.
- EPS NULL의 주요 원인은 폴백 매칭 실패가 아니라 `int()` 변환에서 소수점을 거부하는 것이었다. raw 응답을 한 번 더 본 게 발견의 계기.
- `integer` → `numeric(15, 4)` 마이그레이션으로 소수점 보존 + overflow 대응을 같이 해결.
- #036 후처리 레이어에 NUMERIC_OID 한 줄을 추가해 직렬화 처리 확장. 진입점 레이어를 잘 만들어두면 새 타입 추가 비용이 거의 0이 된다.

엄밀히는 표준 API 조사가 시간 낭비였느냐 하면 그건 아니다. 그 조사 없이 폴백 5단계, 6단계로 갔으면 더 큰 미궁에 빠졌을 거다. 한 번 막혀봐야 다른 데를 의심하게 된다. 데이터 누락 디버깅에서 매칭 로직만 들여다보고 있었는데, 정작 더 흔한 원인은 타입 변환 한 줄이었다는 게 이번에 배운 것이다.
