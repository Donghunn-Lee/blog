> **요약** · localStorage에만 있던 관심종목을 로그인 없이 서버에 저장하도록 바꿨다.
> - **식별은 저장 시점에** — 서버가 발급한 UUID를 httpOnly 쿠키에 넣는다. 모든 요청에 미들웨어로 발급하는 안은 SSR이 쿠키를 읽지 않아 기각했고, 첫 저장(PUT)이 성공할 때만 발급한다. 저장한 적 없는 방문자에게는 조회 요청도 없다.
> - **스냅샷 1행** — 그룹 · 멤버십을 정규화하면 route 6개 이상과 트랜잭션(Neon HTTP 드라이버에 없음)이 필요했다. 그 이점을 쓰는 곳이 없어 JSONB 1행으로 저장한다.
> - **스토어가 진실** — 서버 우선 단방향 로드. 조회가 재시도 뒤에도 실패하면 쓰기를 막고 "서버 저장 안 됨" 배지를 띄워, 비어 있는 로컬이 서버 목록을 덮어쓰지 못하게 했다.
> - **비교 규칙 하나** — 확정 스냅샷과 같은 변경은 무시해 되쓰기 루프를 막는다. jsonb는 키 순서를 보존하지 않아 정렬 후 비교한다. curl 7건 · Network 시나리오 8건으로 확인했다.

초기 #009에서 관심종목을 localStorage에 두기로 했던 건 인증을 붙이지 않기 위해서였다. 회원가입·로그인·세션이 따라오는 순간 조회형 서비스의 범위를 넘는다고 봤고, 그 대신 기기 간 동기화와 브라우저 저장소가 지워졌을 때의 복구를 포기했다. #125 트리아지에서 이 둘 중 후자만 되돌리는 안을 X7로 편입했다. 로그인 없이 브라우저를 식별해 서버에 저장하는 것으로, 뒤에 붙을 종목별 메모(X8)의 저장 인프라이기도 하다.

토요일이라 시장 실측이 걸린 작업은 할 수 없었고, 세션 2~3개로 잡아둔 이 아크를 주말에 시작하기로 했다. 계획은 서버 2커밋(스키마·DB 헬퍼 → 쿠키·route) 뒤 클라이언트 2커밋(스토어 동기화 → 마이그레이션·안내)이었고, 네 커밋을 하루에 닫고 prod까지 확인했다.

## 로그인 대신 쿠키 두 개

식별자는 서버가 발급한 UUID를 httpOnly 쿠키에 넣는 것으로 정했다. JS가 읽을 수 없으니 스크립트로 새어 나갈 길이 없고, 1년 만료를 저장할 때마다 갱신하면 브라우저를 껐다 켜도 남는다. Safari가 7일 미방문 사이트의 스크립트 저장소를 정리하는 정책도 서버가 설정한 쿠키는 대상이 아니라, 보존성은 localStorage보다 오히려 낫다.

발급 시점이 첫 결정이었다.

| 후보 | 판정 |
|---|---|
| 미들웨어에서 매 요청 확인·발급 | 기각. 미들웨어 파일이 없고 관심종목 표면이 전부 클라이언트라 SSR이 쿠키를 읽을 일이 없음. 전 요청 함수 호출만 늘어남 |
| **첫 저장(PUT) 성공 시 route가 발급** | **채택.** 구경만 하는 방문자에겐 쿠키도 서버 호출도 없음 |

httpOnly라 클라이언트는 자기가 쿠키를 가졌는지 모른다. 그러면 모든 방문자가 페이지마다 서버 저장분을 조회하게 되는데, 홈 관심종목 프리뷰가 전 방문자 표면이라 그 호출이 그대로 비용이 된다. 값이 없는 마커 쿠키(`slatekr_sync=1`)를 같이 발급해 클라이언트가 이걸 보고 조회 여부를 정하게 했다.

쿠키 동의 배너는 띄우지 않기로 했다. 배너는 추적·광고 쿠키에 동의를 받는 장치이고, 이 쿠키는 사용자가 직접 저장한 데이터를 돌려주는 기능성 쿠키라 국내법에 팝업 의무가 없고 GDPR도 "요청한 서비스에 필수"로 면제한다. 저장하는 순간에만 발급하는 구조가 이 성격을 더 분명하게 만든다. /credits에 익명 쿠키를 쓴다는 것과 쿠키를 지우면 서버 연결이 끊긴다는 두 문장을 고지하는 것으로 갈음했다.

## 저장 단위

서버에 어떤 모양으로 둘지가 이후 커밋 수를 정하는 결정이었다.

| 후보 | 판정 |
|---|---|
| 그룹·멤버십 정규화 테이블 | 기각. route 6개 이상, 스토어 shape 재설계, Neon HTTP 드라이버엔 트랜잭션이 없어 다중 행 쓰기 원자성 보장 불가 |
| **persist가 저장하는 state 객체를 JSONB 한 행으로** | **채택.** 스토어에 이미 전체 치환 액션이 있어 저장 어댑터만 갈아끼우면 됨. ticker로 서버를 역조회할 수요 없음 |

정규화가 제대로 된 설계처럼 보이지만 이 프로젝트에서 그 이점을 쓰는 곳이 없었다. 관심 등록 상위 순위는 KIS TR이 주고, 뒤에 올 메모는 별도 테이블로 얹으면 된다. `anon_watchlists(anon_id, snapshot, version, updated_at)` 한 테이블과 GET/PUT route 둘로 끝났다. 스냅샷 검증은 persist v2 shape를 그대로 옮긴 Zod 스키마 하나를 단일 소스로 두고, 스토어의 타입도 이 스키마에서 추론하도록 바꿔 shape가 어긋나면 테스트가 잡게 했다.

마이그레이션 파일 관례가 없던 저장소라 DDL을 `web/sql/`에 추적용으로 두고 Neon 콘솔에서 수동 적용했다. 전에 토큰 캐시 테이블을 콘솔에서만 만들고 저장소에 남기지 않았던 걸 반복하지 않으려는 것이다.

## 로컬/서버 우선순위 설정

동기화에서 실제로 정해야 하는 건 "로컬과 서버가 다르면 누가 이기는가"다.

```
전:  Zustand store ⇄ localStorage (persist)
후:  Zustand store ⇄ localStorage (첫 페인트 캐시)
                   ← GET  서버 스냅샷 도착 시 로컬을 덮음
                   → PUT  편집 뒤 300ms 병합, 전체 스냅샷
```

스토어가 진실이고 서버는 저장 백엔드다. TanStack Query의 mutation을 도입하지 않은 것도 같은 이유로, 이 프로젝트에서 TanStack은 표시용 서버 상태에만 쓰고 있고 관심종목은 서버 상태라기보다 클라이언트 상태가 서버에 백업되는 것에 가깝다.

로드 규칙은 단방향으로 잘랐다.

| 상황 | 동작 |
|---|---|
| 마커 쿠키 없음 | 조회 생략, 로컬을 기준선으로 |
| 서버 스냅샷 도착 | 로컬 덮어씀 |
| 조회 중 로컬 편집 발생 | 로컬이 더 새것. 서버 값은 기준선으로만 잡고 로컬을 PUT |
| 조회 실패(1회 재시도 후) | 쓰기 차단, 로컬 persist는 그대로 |

마지막 행이 이 규칙의 이유다. localStorage가 비워진 뒤 서버 조회까지 실패한 상태에서 사용자가 종목 하나를 추가하면, 그 한 개짜리 스냅샷이 서버의 전체 목록을 덮어쓴다. 조회가 성공한 적 없으면 쓰지 않는 게 안전하고, 로컬 저장은 지금까지처럼 돌아가니 그 시점의 편집이 사라지지도 않는다. 이 상태는 관심종목 헤더에 "서버 저장 안 됨" 배지로 드러낸다. 차단 중 편집분이 다음 로드에서 서버에 밀리는 건 알고 남긴 트레이드오프다.

## 되쓰기 루프를 막는 비교 하나

서버 값을 스토어에 적용하는 것도, 실패 시 롤백하는 것도 결국 `set`이라 구독자가 다시 PUT을 쏠 수 있다. 플래그로 막는 대신 규칙 하나를 뒀다.

```
구독 → 현재 스냅샷 == 마지막 확정 스냅샷 이면 무시
     → 아니면 300ms 뒤 PUT → 성공: 확정 스냅샷 갱신
                          → 실패(1s 재시도 후): 확정 스냅샷으로 롤백 + toast
```

서버 적용과 롤백은 확정 스냅샷과 같은 값을 쓰니 비교에서 걸러지고, 사용자 편집만 통과한다. 여기서 두 가지가 걸렸다. Postgres jsonb는 객체 키 순서를 보존하지 않아서 서버에서 돌아온 스냅샷을 문자열로 비교하면 같은 값이 다르다고 나온다. 종목 메타의 키를 정렬한 뒤 비교하게 했다. 또 전체 치환 액션이 멤버십에 없는 종목 메타를 GC하므로, 기준선은 서버 raw 값이 아니라 적용 뒤의 스토어 값으로 잡아야 첫 비교부터 어긋나지 않는다. raw로 잡으면 로드 직후 불필요한 PUT이 한 번 나간다.

300ms 안에 탭을 닫으면 편집이 서버에 못 가고 다음 로드에서 구버전 서버가 이긴다. `pagehide`에서 대기 중인 스냅샷을 keepalive fetch로 보내 이 창을 메웠다. 처음엔 debounce 타이머가 살아 있을 때만 보내게 했는데, 앞선 PUT이 진행 중일 때 들어온 편집은 타이머 없이 재검사 예약만 걸린 상태라 이 조건에서 빠졌다. 기준선과 다르면 무조건 보내는 것으로 고쳤다.

## 기존 사용자의 로컬 데이터

이미 관심종목을 쌓아둔 사용자는 마커 쿠키가 없고 로컬만 있다. 이 경우 기준선을 비워두면 방금의 비교 규칙이 "로컬 ≠ 확정"으로 판정해 로드 직후 전체를 한 번 PUT한다. 마이그레이션에 코드가 거의 없는 이유다. 실패해도 로컬은 바뀐 게 없으니 롤백·toast 없이 다음 편집 때 다시 올리고, 로컬이 비어 있으면 아무것도 하지 않아 구경 방문자에겐 여전히 쿠키가 생기지 않는다.

## 검증

route는 curl 7건(쿠키 없는 GET·첫 PUT의 Set-Cookie 2건·재PUT의 version 증가와 만료 갱신·잘못된 본문 400·위조 쿠키 무시)으로, 동기화는 브라우저 Network 탭으로 확인했다.

| 시나리오 | 결과 |
|---|---|
| 쿠키 없이 진입 | GET 0건 |
| 종목 추가 | PUT 1건, 쿠키 2개 생성, DB version 1 |
| 300ms 안에 그룹 생성 + 종목 추가 | PUT 1건으로 병합 |
| 새로고침 | PUT 0건 |
| localStorage 삭제 뒤 새로고침 | 서버 값 복원, PUT 0건 |
| 오프라인에서 종목 추가 | 1s 재시도 뒤 롤백 + toast |
| GET만 차단 뒤 새로고침 | 2s 재시도 뒤 차단, 편집해도 PUT 0건, 배지 노출 |
| 쿠키만 삭제 뒤 새로고침 | 로컬 전체 PUT 1건, 쿠키 재생성 |

prod에서 `Secure`·`HttpOnly` 플래그와 새로고침 시 GET만 나가는 것까지 확인했다. 부수로 stocks 테이블의 ticker가 스키마의 6자리 영숫자 정규식을 전부 통과하는지 조회했는데, 하나라도 어긋나면 그 종목을 담은 사용자는 PUT 400과 롤백을 반복해 영영 저장이 안 된다. 0행이었다.

## 정리

- **X7 종결** — httpOnly UUID 쿠키 + 마커 쿠키, JSONB 스냅샷 한 행, GET/PUT route, 스토어 동기화, 로컬 마이그레이션, /credits 고지. 4커밋
- **식별은 저장 시점에** — 미들웨어 대신 첫 PUT에서 발급, 구경 방문자 무비용, 동의 배너 불요
- **스토어가 진실** — 서버 우선 단방향 로드, 조회 실패 시 쓰기 차단으로 stale 로컬의 덮어쓰기 방지
- **비교 규칙 하나** — 확정 스냅샷 동등 비교로 되쓰기 루프 차단. jsonb 키 순서·GC 뒤 기준선 두 함정
- **F82·F83 backlog** — 차단 중 편집분 미반영, 고아 행 정리

세션 두세 개로 봤던 아크가 하루에 끝난 건 결정이 코드보다 앞에서 다 나왔기 때문인 듯하다. 저장 단위를 스냅샷으로 정한 순간 route가 둘로 줄고, 스토어를 진실로 정한 순간 동기화가 비교 규칙 하나로 줄었다. 정규화 테이블로 갔으면 아마 계획대로 세 세션이 걸렸을 것이다.
