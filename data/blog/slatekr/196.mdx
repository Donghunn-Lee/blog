서류를 내기 전에 남겨 둔 작업은 [지난 글](/blog/slatekr/195/)에서 찾은 첫 방문 옛 값 수정과 README 성능 표 재측정이었다. 시작하기 전에 README의 모바일 성능 점수(홈 70 · 지수 77)가 다시 눈에 걸렸고, 작은 수정으로는 80점이 어렵다며 접었던 판정([#182](/blog/slatekr/182/))을 한 번 더 확인해 보기로 했다.

계획은 옛 값 수정, 재측정, README 순서였다. 실제로는 성능 진단이 맨 앞에 들어갔고, 거기서 첫 방문 안내 카드가 모바일 LCP를 늦추고 있는 것을 찾아 고쳤다. 나머지는 계획대로 마쳤고, 재측정은 휴장일을 피해 하루 미뤘다.

| 첫 페인트 직전의 긴 작업 | 문서의 첫 전체 레이아웃(약 110ms). 첫 페인트 전이라 TBT와 무관 |
| 초기 JS 청크의 내용 | 번들 분석으로 확인. 화면에서 쓰지 않는 zod가 실려 있었음 |

## 수정 전 측정한 원인별 점수

모바일 점수를 가장 많이 깎는 지표는 세 페이지 모두 LCP(화면에서 가장 큰 콘텐츠가 그려지는 시점)였다. Lighthouse는 느린 기기를 시뮬레이션할 때, 관측된 LCP 시각 전에 끝난 요청을 전부 LCP에 필요했던 것으로 계산한다. 그래서 LCP 요소가 늦게 그려질수록 그 전에 받은 JS와 글꼴이 통째로 추정에 들어간다. 의심 가는 요소를 고치기 전에, 그 요소가 없는 상태로 같은 측정을 돌려 몇 점이 걸려 있는지부터 쟀다.

| 변형 | 홈 | 종목 상세 | 지수 |
|---|---|---|---|
| 기준 | 69 | 72 | 67 |
| 안내 카드 없음 | +7 | +4 | 0 |
| 한글 글꼴 없음 | +6 | +10 | +6 |
| 둘 다 없음 | 88 | 84 | 72 |

로컬 Lighthouse 모바일로 기준과 번갈아 5회씩 잰 중앙값이다. 글꼴은 측정 방법을 한 번 바꿨다. 글꼴 파일 요청을 막는 방식으로 재자 브라우저가 남은 한글 글꼴 조각 123개를 전부 요청해 점수가 오히려 내려갔고, CSS에서 한글 글꼴 선언만 지우는 방식으로 다시 쟀다. 측정 방식 자체의 영향은 아무것도 지우지 않고 같은 경로만 거치게 한 대조군으로 확인했는데 1점이었다.

## 늦게 그려지던 가상 시세 안내 카드

모바일 LCP 요소는 세 페이지 모두 첫 방문 안내 카드의 본문이었다. [#191](/blog/slatekr/191/)에서 가격이 가상 데이터임을 알리려고 넣은 카드인데, 닫았는지 여부가 브라우저 저장소에만 있어서 서버 HTML에는 넣지 않고 hydration이 끝난 뒤에 그리고 있었다.

```
서버 HTML        안내 카드 없음
hydration 뒤     저장소를 읽고, 닫은 적이 없으면 카드를 그림
모바일 첫 화면   카드 본문이 가장 큰 텍스트 → LCP = 카드가 그려진 시점
```

성능 측정은 항상 첫 방문 상태로 진행되므로 이 카드가 매번 뜬다. 카드는 이달 초에 생겼으니 10월에 잰 README 수치에는 들어 있지 않던 감점이었다.

## 서버 렌더와 인라인 스크립트

| 후보 | 판정 |
|---|---|
| 카드를 더 작게 하거나 더 늦게 띄우기 | 기각. 측정에서만 빠질 뿐 첫 방문자가 카드를 늦게 보는 것은 그대로 |
| 닫힘 여부를 쿠키로 서버에 전달 | 기각. 루트 layout이 쿠키를 읽으면 홈을 정적으로 캐시할 수 없음 |
| **서버 HTML에 포함하고, 닫은 방문자는 그리기 전에 숨김** | **채택.** React 렌더는 저장소를 읽지 않아 서버와 같은 결과 |

카드를 서버 HTML에 넣고, 이미 닫은 방문자에게는 `<body>` 맨 앞의 인라인 스크립트가 저장소를 읽어 화면을 그리기 전에 숨기게 했다. 다크 모드가 깜빡이지 않게 할 때 쓰는 방식과 같다. 지난 글에서 고친 종목 헤더는 브라우저에만 있는 값을 마운트 뒤에 읽게 했는데, 그 방식은 내용이 한 박자 늦게 나와도 될 때만 맞는다. 안내 카드가 원래 그 방식이었고 그래서 LCP가 밀렸다.

수정 전후 빌드를 번갈아 잰 로컬 측정에서 모바일 점수는 홈 +7 · 종목 상세 +8 · 지수 +3이었고, 수정본은 15회 모두 LCP가 첫 페인트와 같은 프레임이었다. 닫은 방문자 상태로 60번 새로고침해도 카드가 보인 프레임은 없었다. 카드가 문서 맨 끝에 있으면 느린 기기에서 첫 페인트에 못 들어가는 경우가 있어서, 위치는 내비게이션 바로 뒤로 옮겼다.

## 화면에서 쓰지 않던 zod

번들 분석에서 종목 상세의 초기 스크립트에 zod가 통째로 실려 있었다. 브라우저에서 zod로 검증하는 곳은 한 군데도 없고, 원인은 메모 버튼이 가져다 쓰는 글자 수 상수 하나였다.

```
전  메모 버튼 → 메모 스키마 파일(상수 1개를 가져옴) → 같은 파일의 zod 스키마 → zod 전체
후  메모 버튼 → 상수만 있는 파일          스키마 파일은 서버에서만 사용
```

파일에서 값을 하나만 가져와도 그 파일은 맨 위부터 실행되기 때문에, 스키마를 만드는 코드와 zod가 같이 따라오고 있었다. 같은 모양이 더 있는지 찾아보니 관심종목 그룹 이름의 길이 상수가 하나 더 있었고, 둘을 옮기자 클라이언트 번들에서 zod가 완전히 빠졌다. 초기 스크립트는 종목 상세 346 → 283KB, 관심종목 337 → 273KB(gzip)가 됐다.

## 휴장일 수치와 10월 기록

안내 카드를 고치기 전 일요일에 잰 PageSpeed Insights(PSI) 모바일 점수는 홈 85 · 종목 상세 89 · 지수 83으로, 아무것도 고치지 않았는데 README보다 높았다. 가상 시세로 바꾸면서 외부 호출이 빠진 덕인가 싶었지만 홈은 원래 정적 페이지라 그걸로는 설명이 되지 않아서, 10월 측정 기록을 다시 찾아봤다.

| 페이지 | README에 적은 값 | 같은 시기의 다른 측정 | 일요일 |
|---|---|---|---|
| 홈 | 70 · LCP 5.6초 (10/11) | 85 · 3.9초 (10/9, 같은 코드) | 85 · 4.3초 |
| 종목 상세 | 82 · 4.7초 (장중) | LCP 3.8초 (휴장) | 89 · 3.8초 |

홈은 [#180](/blog/slatekr/180/)에서 같은 코드가 이틀 사이에 85와 70으로 나왔던 페이지이고, 종목 상세는 README 값이 장중 측정인데 장이 닫힌 시간에는 10월에도 3.8초였다. 로컬에서 같은 방법으로 잰 FCP 추정(2.72 → 2.71초)과 LCP 전에 받는 JS(302 → 305KB)도 그대로여서, 좋아진 게 아니라 측정 조건이 달랐던 것으로 판단했다. 그래서 재측정은 장중으로 옮기고, 조합마다 시간을 두고 6회를 재서 중앙값과 범위를 같이 적기로 했다.

## 옛 값 재조회 확장

지난 글에서 넘긴 문제다. 서버 캐시는 유효 시간이 지난 뒤 첫 요청에 저장돼 있던 값을 그대로 주는데, 방문이 드문 사이트라 방문할 때마다 그 첫 요청이 된다. [#152](/blog/slatekr/152/)에서 지수 분봉에만 넣었던 대책(오래된 응답이면 3초 뒤 한 번 더 요청)을 지수 숫자 · 해외 지수 · 순위로 넓혔다.

- **재조회 로직을 훅 하나로** — 분봉 훅 2개에 복사돼 있던 것이 5곳에서 쓰이게 돼 먼저 추출
- **값을 만든 시각은 유효 시간이 60초인 구간에만 전달** — 장 마감 뒤에는 1시간 캐시라 50분 된 값도 정상, 이때도 판정하면 폴링마다 요청이 하나씩 늘어남
- **캐시 키에 버전 추가** — 서버 캐시는 배포를 넘어 남아서, 저장되는 값의 모양을 바꾼 route는 옛 항목을 읽지 않게 함

```
80초 비운 뒤 홈을 열었을 때(정규장)
지수 숫자   85.5초 전 값 → 3.8초 뒤 재조회 → 3.4초 전 값
해외 지수   85.6초 전 값 → 3.8초 뒤 재조회 → 3.4초 전 값
순위        83.4초 전 값 → 4.0초 뒤 재조회 → 3.0초 전 값
```

재조회는 응답 하나에 한 번만 나갔고, 바로 새로고침하거나 탭이 숨어 있을 때는 나가지 않았다. 장 마감 뒤에는 지수 응답에 시각이 실리지 않아 재조회도 없는 것을 라이브에서 확인했다.

## 장중 재측정

| 페이지 | 10월 README | 11월 16일 장중 (6회 중앙값 · 범위) |
|---|---|---|
| 홈 | 70 · LCP 5.6초 | 99 [95 ~ 100] · 1.1초 |
| 종목 상세 | 82 · 4.7초 | 100 [97 ~ 100] · 0.9초 |
| 지수 | 77 · 5.4초 | 98 [96 ~ 99] · 1.7초 |

모바일 18회 모두 LCP가 첫 페인트와 같았다. 로컬에서 잰 +7보다 훨씬 크게 오른 건, 로컬은 글꼴이 너무 빨리 도착해 첫 페인트 추정부터 2.7초로 부풀어 있었고 PSI에서는 첫 페인트가 원래 1초대였기 때문으로 보인다. 측정 중에 SEO 점수가 92로 내려가 있는 것도 발견했는데, 안내 카드와 배너의 "자세히" 링크가 문구만으로는 어디로 가는지 알 수 없다는 감사였고 화면에 보이지 않는 문맥을 붙여 100으로 되돌렸다.

README에는 측정값과 로컬 교차 측정값만 적었다. 일요일의 85와 오늘의 99는 휴장과 장중으로 조건이 달라 전후 비교로 쓰지 않았다. 지수 페이지의 98은 안내 카드가 LCP 요소라서 나온 값이고, 카드를 닫은 재방문에서는 분봉 응답을 받은 뒤 그려지는 차트 캡션이 LCP 요소라 더 늦다는 점을 한계에 적었다. 설계 결정에는 hydration 에러와 옛 값 재조회를 한 줄씩 더했고, 코드 링크는 새 태그로 옮겼다.

## 정리

- **접었던 성능 판정 재검토** — #182에서 남긴 항목 4개 종결, 코드 수정 전에 원인별 점수 측정
- **안내 카드 LCP 수정** — 서버 HTML에 포함하고 닫은 방문자는 인라인 스크립트로 그리기 전에 숨김, 로컬 교차 측정 +7 · +8 · +3
- **클라이언트 번들에서 zod 제거** — 스키마 파일 2곳에서 상수 분리, 초기 스크립트 63KB 감소
- **첫 방문 옛 값 수정** — 지수 숫자 · 해외 지수 · 순위에 1회 재조회 적용
- **README 성능 표 재측정** — 장중 6회 중앙값, 모바일 99 · 100 · 98
- **한글 글꼴 backlog** — 로컬에서 빼면 6 ~ 10점이지만 디자인 결정이 필요해 서류 뒤로

한 번 접은 판정이라 다시 재는 게 좀 번거롭게 느껴졌는데, 원인 중 하나는 이달 초에 붙인 안내 카드였다. 서류 전에 코드로 할 일은 이걸로 마친 것 같다. 아마 나머지는 블로그로 남기지 않고 리드미와 문서들을 수정할 생각이다. 이제는 정말 마지막이길 바란다.
