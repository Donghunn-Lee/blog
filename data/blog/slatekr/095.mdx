이번 세션은 전일 해외 트랙 적재를 늦게 돌리는 바람에 오늘 밤 이후까지 적재를 기다리는 동안, 데이터와 무관한 UI 잔여를 배치로 처리하는 세션이었다. 선차트 색(P1-③), 검색 더보기(E23), 슬레이트 설명 문구(E25)에 세션 중 헤더 검색(E31)이 하나 더 붙었다. 넷 중 검색이 제일 굴곡이 있었다 — 더보기를 구현해 화면에 띄웠다가, 그 화면을 보고 페이지네이션과 표로 다시 짰다.

## 선차트에 등락 2색

먼저 착수한 작업은 등락에 따른 선 차트 색상 구분. 다른 서비스에서 선 차트가 이렇게 구현되면 좀 더 보기 좋았던 기억이 있어 도입한 디자인이다.

현재는 지수 당일 선차트가 값과 무관하게 상승색 하나로 그려지고 있었다. 원하는 그림은 전일 종가 위 구간은 상승색, 아래 구간은 하락색으로 나타나는 것.

현재 구현은 LineSeries 고정 단색이었고, 원하는 표현은 lightweight-charts의 BaselineSeries가 그대로 제공했다. baseValue에 전일 종가를 주면 선이 기준선을 넘나들 때 구간별로 색이 갈린다. 렌더러엔 `baseline?: number` prop 하나만 뚫고, 값 갱신은 시리즈 재생성 없이 `applyOptions`로만 반영되게 했다.

적용 범위는 당일 차트로 한정했다. 일봉 이상에서 "전일 종가" 기준선은 수개월 히스토리를 어제 값과 비교하는 그림이 돼서 의미가 없고, 주봉·월봉은 기준 개념 자체가 안 선다.

그렇게 긋고 보니 다른 문제가 남았다. 당일만 2색이 되면 나머지 선차트는 여전히 붉은 단색이라, 선차트 읽는 법이 세 갈래로 갈라진다. 여기는 색을 나누는 대신 톤을 빼는 방식은 선택했다. — baseline이 없는 선차트 전부를 무채색 선 + 하단 그라데이션의 AreaSeries로 교체했다. 종목 당일 선차트도 2색에 편입해서, 최종 문법은 두 개로 정리됐다.

| 선차트 | 표현 |
| --- | --- |
| 당일 (지수·종목) | 전일 종가 기준 위 상승색 / 아래 하락색 |
| 일·주·월 | 무채색 선 + 그라데이션 |

## 검색 결과 더보기에서 페이지네이션으로

검색 결과가 10건에서 잘리는 문제(E23)는 문제 발견 시 "더보기" 방식으로 가면 되겠다고 생각했던 문제다. limit/offset을 뚫고, limit+1 트릭으로 다음 페이지 유무를 판정하고, 버튼을 누르면 클라이언트가 이어 붙이는 구조로 구현까지 마쳤다.

![](/static/images/velog/c8f11944-6f7f-4adf-839a-d2af09e829e3-image.png)


근데 띄워놓고 보니 두 가지가 걸렸다. "20개 종목+" 같은 표기로는 총 몇 건인지 알 수가 없고 — 알려면 더보기를 끝까지 눌러야 한다 — 결과가 한 행짜리 카드라 정보 밀도도 낮았다. 그제서야 그냥 페이지네이션으로 하면 깔끔하다는 생각이 들었다. 이후 생각을 곧바로 행동으로 옮겼다.


| | 더보기 | 페이지네이션 |
| --- | --- | --- |
| 총 건수 | 모름 (hasMore만) | 총 페이지로 노출 |
| 상태 | 클라이언트 append | URL이 소스, SSR |

전환 자체는 가벼웠다. 쿼리에 `COUNT(*) OVER()` 한 줄을 얹으면 같은 조회에서 총 건수가 나오는데, bigint로 돌아오는 값도 기존 DB 래퍼가 이미 number로 변환해주고 있어서 후처리가 없었다. shadcn Pagination도 설치돼 있어 Link만 물리면 됐다.

이 김에 잡은 게 둘 있다. 하나는 정렬 — 기존 쿼리에 ORDER BY가 아예 없어서 DB 반환 순서에 기대고 있었다. cap을 푸는 시점엔 순서가 정의돼 있어야 해서, prefix 매치 우선("삼성" 검색 시 "삼성전자"가 "호텔삼성"보다 앞) + 이름순으로 확정했다. 다른 하나는 단일 결과 redirect다. 검색 결과가 1건이면 상세로 바로 보내는 기존 분기가, 페이지 파라미터가 붙으면 마지막 페이지에 1건 남았을 때도 발동해 갑자기 상세로 튄다. 조사 단계에서 미리 보여서 `1페이지 && 총 1건`으로 좁혀두고 갔다.

## 결과 행을 시세 표로

밀도 문제는 카드를 표로 바꾸면서 같이 풀었다. 이름과 코드만 있던 행에 현재가·등락·거래량을 얹기로 했는데, #080에서 순위 페이지에 쓴 문법이 그대로 맞았다 — 행 전체가 링크여야 하니 `<table>` 대신 grid 템플릿 상수를 헤더·행이 공유하는 구조. 컴포넌트는 순위 쪽이 rank와 카테고리 상태에 결합돼 있어 재사용하지 않고, 문법만 가져와 새로 만들었다.

시세를 어디서 가져올지가 실질적인 결정이었다. 관심종목의 멀티 시세 훅을 붙이면 페이지당 20종목이 KIS 1콜(상한 30)에 들어와 비용은 없다시피 한데, 이 경로는 장중에만 값을 준다. 그대로면 저녁이나 주말엔 가격 칸이 전부 빈 표가 된다 — 포트폴리오가 실제로 열릴 시간대가 그쪽인데.

그래서 서버에서 최신 일봉을 베이스로 깔고, 장중엔 라이브 시세가 그 위를 덮어쓰게 했다. 홈 차트가 EOD 위에 당일 값을 병합하는 것과 같은 문법이다. 일봉 테이블에 등락 컬럼이 없어서 전일 종가는 LAG 윈도우로 같은 쿼리에서 파생했고, 이 조회가 실패해도 검색 자체는 정적 필드로 렌더되게 격리했다.

![스크린샷: 검색 결과 표](/static/images/velog/5d4b13cf-43dd-4a20-8929-1a6d75b8c80f-image.png)


작은 소동이 하나 있었다. 표를 커밋하고 띄웠는데 grid가 안 먹고 셀이 전부 세로로 흘러내렸다. 코드를 대조해도 순위 행과 구조가 같아서 수정할 곳이 없었는데, dev 서버를 재시작하니 그냥 살아났다. Tailwind v4 + Turbopack에서 새 파일에 처음 등장한 arbitrary class가 HMR에 안 잡힌 캐시 문제였다. 멀쩡한 코드를 잠깐 의심했다 — prod 빌드는 전체 스캔이라 무관해서 기록만 남겼다.

## 검색창을 헤더로

세션 중에 추가한 항목이다(E31). 종목 페이지나 순위 페이지에서 다른 종목으로 넘어가려면 매번 홈을 거쳐야 했는데, 검색이 홈에만 있어서다. 헤더에 미니 검색창을 놓기로 했다.

이식 비용은 낮았다. SearchInput이 훅·드롭다운·키보드 탐색을 이미 다 품고 있어서, sm 사이즈와 버튼 생략, placeholder를 optional prop으로 여는 것으로 끝났다. 기본값을 두면 기존 호출부는 안 건드린다 — #059에서 size prop을 처음 열 때 쓴 방식 그대로다. Navbar는 좌우 2분할을 로고/검색/링크 3분할로 바꾸고, 모바일은 일단 숨겼다.

그런데 헤더에 검색이 서고 나니 홈이 다르게 보였다. 히어로의 큰 검색창이 중복이 됐고, 안 그래도 안내 카드 3장이 fold 아래 박혀 안 보이는 게 고민이던 참이었다. 홈 상단을 다시 짜기로 했다 — 히어로 검색·로고를 걷고 헤더 검색으로 일원화, 안내 카드를 압축해 최상단으로. 모바일 검색 노출도 이때 같이 푼다. 이번 세션 스코프는 아니라 다음 작업(E33)으로 걸어뒀다.

이 외에 슬레이트마다 한 줄 설명(E25)도 붙였다. "핵심 지표와 가격 정보를 한눈에" 같은 담백한 톤으로 통일했는데, 밝은 "~해요"체도 후보였지만 지금 UI 어디에도 없는 어투라 이질감이 컸다.

## 정리

- **P1-③** — 당일 선차트를 전일 종가 기준 2색(BaselineSeries)으로, 나머지 선차트는 무채색 area로. 선차트 문법이 두 개로 정리됐다
- **E23** — 더보기를 구현했다가 화면 보고 페이지네이션 + 시세 표로 재설계. EOD 베이스 + 라이브 오버라이드로 폐장 시간대에도 표가 산다
- **E31** — SearchInput variant 확장으로 헤더 미니 검색. 이게 홈 상단 개편(E33) 결정으로 이어졌다
- **E25** — 슬레이트 설명 문구, 담백 톤

더보기는 하루를 못 살고 페이지네이션에 자리를 내줬다. 방식을 확정해뒀다고 화면 확인 전에 닫힌 결정이 아니라는 걸 다시 봤고 — #080에서 행 문법을 커밋한 뒤 갈아엎었던 것과 같은 자리다 — 대신 그때 만든 limit/offset과 정렬은 그대로 페이지네이션의 바닥이 됐다.
