종목 목록은 금융위원회 상장종목정보 API에서 주 1회 받는다. 신규 상장 종목은 이 목록에 들어온 뒤에야 가격이 적재되므로, 상장 뒤 최대 일주일 동안 검색에도 상세에도 없는 종목이 된다. 직전 트리아지(#167)에서 이 지연을 하루로 줄이는 일간 편입을 잔여 항목으로 남겼고(F105), 형태는 20:12 EOD 체인이 아닌 별도 평일 오전 워크플로우로 잡아 두었다.

계획은 그 형태 그대로였다. 오전 워크플로우 신설, corp_codes diff 쓰기와 stocks 배치 쓰기, 실패 시 non-zero exit 세 묶음이다. 결과는 20:12 daily 체인에 종목 목록 적재를 편입한 커밋 하나와, 그 전에 주기와 무관한 결함 둘을 고친 커밋 하나다. 배치 쓰기와 diff는 백로그로 내렸고, 스코프는 세션 안에서 두 번 바뀌었다.

---

## 신규 상장이 서비스에 들어오는 경로

착수 전에 경로부터 다시 그렸다. 가격 적재가 DB에 없는 종목 코드를 만나면 등록하는 구조가 아닌지 확인하고 싶어서였는데, 반대였다. 종목 목록(stocks)이 전체 대상이고 가격은 그 목록을 입력으로 KIS 시세를 30종목씩 묶어 부른다. KIS 쪽에는 열거 기능이 없으니 모르는 종목은 부를 수 없고, 발견은 FSS 목록 한 곳에서만 일어난다.

```
FSS 상장종목 목록(주 1회) → stocks upsert (새 코드 INSERT · 사라진 코드 deactivate)
  → fetch_prices(20:12): stocks 활성 목록을 입력으로 KIS 호출, 첫 행이 없으면 150일 초기 적재(#122)
  → corp_codes 매핑(DART) → 주식수 · 재무 · 배당
```

편입 지연은 목록을 읽는 주기 그 자체다. 상장 당일 편입은 소스를 KIS 종목마스터 파일 같은 것으로 바꿔야 가능한데 미검증이라 범위 밖으로 두고, D+7을 D+1로 줄이는 데 집중했다.

## probe가 고친 진단과 조용히 green이던 run

probe 결과가 트리아지 때 진단을 두 군데 고쳤다. 22~29분 소요의 원인을 "행 단위 DB 왕복 3,994건"으로 적어뒀는데, 3,994건은 corp_codes 단독 규모였고 실제는 stocks upsert 약 2,650건과 합쳐 6.6천 건 왕복(행당 약 210ms)이었다. 방향은 같아 계획은 유지했다.

두 번째가 더 문제였다. 최근 weekly run 6회 중 4회에서 종목 목록 step이 0.1분 만에 success로 끝나 있었다. 실패 경로를 보니 FSS 호출 예외, upsert 예외, 가드 skip, deactivate 예외가 전부 exit 0으로 끝나고 non-zero는 DB 커넥션 실패 하나뿐이었다. 아무것도 안 하고 green이 되는 구조라 게이트가 잡을 수 없었고, upsert가 실패해도 deactivate는 계속 도는 순서 문제도 같이 있었다.

| run | step 시간 | 판정 |
|---|---|---|
| 9/11 · 9/18 | 10.3분 · 9.2분 | 정상 적재 |
| 9/25 · 9/26 | 0.1분 | 기준일이 추석 휴장일. basDt를 "전일"로 잡아 휴장 무시 |
| 8/28 · 9/4 | 0.1분 | 기준일이 거래일인데 0.1분. 원인 미확인 |

basDt를 전일로 잡는 로직이 휴장을 모르니, 연휴 뒤 run은 휴장일 목록을 요청해 0행을 받고 그 주 신규 상장을 통째로 놓친다. 10/9와 12/25가 금요일 휴장이라 다음 두 번은 예정된 누락이었다.

## daily 이전 철회?

probe 위에서 원안대로 결정 4건을 세웠다.

| 결정 | 채택 |
|---|---|
| 오전 job 시각 | 평일 07:00. basDt는 직전 거래일로 |
| 배치 쓰기 | psycopg2 execute_values, 500행씩. 백필 스크립트 선례 재사용 |
| corp_codes diff | 메모리 diff. 변경분만 UPDATE, DDL 추가 없음 |
| exit 범위 | 예외 · MAX_DEACTIVATE 초과 → 1. FSS 0행만 skip |

여기서 방향을 접었다. 별도 워크플로우는 cron-job.org 등록, 게시 시각 실측, 주말·휴장 처리까지 신경 쓸 게 많고, 편입 지연은 포트폴리오 독자에게 보이지 않는다. 대신 주기와 무관한 결함 둘(basDt 휴장 미반영 · exit 0)만 고치고 weekly 트리거를 금요일 17:00에서 일요일로 옮기면 지연은 D+6이 되고 연휴 주 누락은 사라진다. 배치와 diff는 weekly의 330분 timeout 안에서는 필요 없으니 빼기로 했다.

## 재사용하려던 헬퍼가 고칠 대상이었다

basDt는 새 캘린더를 만들지 않고 기존 거래일 헬퍼를 재사용할 계획이었는데, 구현에 들어가 헬퍼부터 확인하니 그 함수 `get_latest_biz_date`가 바로 결함이었다. 요일만 계산해(월요일이면 3일 전, 그 외 1일 전) 휴장 표를 보지 않고, 오늘 날짜를 TZ 없는 now로 구해 runner에서는 UTC 날짜가 들어간다. 일요일 오전 KST run이면 UTC로는 토요일이라 우연히 금요일이 나오는 식이었다.

대안은 verify 스크립트의 `compute_expected`였다. 정적 휴장 표를 보고 기준일 이하 최근 거래일을 주는 함수라, 기준일에 KST 어제를 넘기면 "오늘을 제외한 직전 거래일"이 된다. DB 캘린더를 주입하려면 두 스크립트의 커넥션 여는 순서를 바꿔야 해서 정적 표만 쓰기로 했다. 표에 없는 임시공휴일이면 0행이 나오고, 이제 그건 exit 1로 red가 되니 사람이 본다. 헬퍼 본문만 바꿔 호출처 둘(종목 목록 · 상장일)이 함께 고쳐졌다.

### exit 경로 정리

0행도 exit 1로 넣은 건 계획과 다른데, 일요일 run에 금요일분이 0행이면 이틀 미게시라 정상이 아니기 때문이다.

| 경로 | 종료 |
|---|---|
| FSS 호출 · upsert · deactivate 예외 | 1. upsert 실패 시 deactivate 미진입 |
| MAX_DEACTIVATE 초과 | 1. 경고와 수동 UPDATE 목록 로그는 유지 |
| 수집 0행 / 부분 | 1. 0행은 "미게시 추정" 메시지 |

테스트 3케이스(평일 · 월요일 · 추석 연휴 뒤 일요일)와 함께 커밋 하나로 닫았다.

## 요일 하나 정하려다 찾은 규정

남은 건 weekly를 옮길 요일이었다. FSS가 금요일분을 토요일에 올리는지 몰라 실측 계획을 짰는데, 수요일 정오 · 금요일 run · 일요일 오전 세 번 호출해야 결론이 나는 5일짜리였다. 이건 너무 길었다. exit 1이 들어간 이상 run 자체가 측정이니 실측을 접고, 가정이 가장 적은 화요일 21:00을 골랐다. 월요일은 대체공휴일이 잦아 첫 주부터 걸린다고 봤다.

그런데 "휴장일엔 게시가 안 된다"는 게 내 가정이었고, 자동 배치라면 매일 돌 것 같다는 의심이 들었다. 규정을 찾아보니 공공데이터포털 API 설명에 문장이 있었다.

> 데이터 갱신은 기준일자로부터 영업일 하루 뒤 오후 1시 이후에 업데이트됩니다. 예를 들어, 금요일 데이터는 차주 월요일에 제공됩니다. (월요일이 공휴일인 경우, 다음 영업일에 제공됩니다)

| 후보 | 판정 |
|---|---|
| 일요일 weekly | 기각. 금요일분이 월요일에 나오니 매주 0행 |
| 월요일 weekly | 기각. 대체공휴일 주는 화요일에 나옴 |
| 화요일 weekly | 성립. 지연은 D+7 그대로 |
| 평일 오전 daily(원안) | 기각. 13:00 이후 게시라 오전엔 전일분이 없음 |
| **20:12 daily 체인** | **채택.** 게시 7시간 뒤. 편입 D+1, 워크플로우 신설 · cron 변경 0 |

원안의 오전 워크플로우는 애초에 성립하지 않았고, 20:12 체인은 EOD 지연을 걱정해 트리아지 때 배제했던 안이었다. 이날 새벽 00:46에 전일분을 호출하니 0행이었던 것도 이 규정으로 설명된다. 실측 5일 대신 조사 한 번이었다.

## 20:12 체인 편입

종목 목록 step을 캘린더 적재 다음, 가격 EOD 앞에 넣었다. 앞에 두는 이유는 신규 종목이 그날 EOD 대상에 들어가야 하기 때문이고, `continue-on-error`로 실패가 EOD를 막지 않게 하되 게이트에는 넣어 실패면 red가 된다. weekly에서는 이 step과 FSS 키를 뺐고, corp_codes는 소비처(주식수 · 재무 · 배당)가 weekly라 그대로 두었다.

```
전  weekly(금 17:00): stocks → listed_at → corp_codes → shares → financials → dividends
    daily(20:12):     calendar → prices → indices → overseas → verify
후  weekly(금 17:00): listed_at → corp_codes → shares → financials → dividends
    daily(20:12):     calendar → stocks → prices → indices → overseas → verify
```

빠뜨리면 안 되는 게 하나 있었다. daily는 주말·휴장일에도 트리거되고 EOD 스크립트가 자체 가드로 skip하는데, FSS는 영업일에만 게시하니 종목 목록 step에 같은 가드가 없으면 토·일·휴장 월요일마다 0행 exit 1로 red가 난다. 오늘이 거래일이 아니면 FSS 호출과 DB 연결 전에 skip하는 가드를 두고 한글날 케이스로 테스트했다. 행 단위 쓰기 10분은 그대로라 EOD가 20:22쯤으로 밀리는데, 이건 수용하고 배치 쓰기는 백로그(F112)에 뒀다.

## 정리

- **F105 종결** — 종목 목록 적재를 20:12 daily 체인에 편입. 신규 상장 편입 D+7 → D+1. 별도 워크플로우 · 배치 · diff는 게시 규정으로 불요 판정
- **basDt 휴장 반영** — 요일 계산 헬퍼를 정적 휴장 표 기반으로 교체, 상장일 스크립트 동조. 연휴 주 누락 소멸
- **fetch_stocks exit 1** — 예외 · 가드 전 경로 non-zero, upsert 실패 시 deactivate 차단, 비거래일 가드. 6회 중 4회 silent green 해소
- **F112 backlog** — collector 행 단위 왕복 배치화, KST 상수 8모듈 복제 통합
- **기타** — 기업행위 경고 2건이 전부 kis_adj=1로 20:12 판별 3번째 확인. 프리마켓 등락 리셋 4표면 08:21 실측 정상

커밋은 둘이지만 설계는 세 번 바뀌었다. 첫 번째 전환은 부담을 줄이려는 판단이었고 두 번째는 규정이 만든 것이었는데, 돌아보면 게시 시각을 실측 항목으로 둔 것 자체가 문서를 먼저 안 본 결과였다. 외부 소스는 재기 전에 규정부터 읽는 게 좀 더 싸다.
