#050에서 store를 다대다로 갈아엎고, #051에서 그룹 CRUD와 종목 상세의 다중 그룹 선택까지 붙였다. 이번 #052는 E5의 마지막 칸 — **그룹 관리 모달**이다. 그룹을 한곳에서 만들고 지우고, 종목을 검색해 그룹에 넣는 화면이다.

이번 세션에서 시간을 들인 건 모달을 어떤 **편집 방식**으로 굴릴지였다. 그 결정을 중심으로 적는다.

## 그룹 관리 모달

기능 구현 전, 어떤 요소들을 담을지를 먼저 간단히 계획하고 나서 작업을 개시했다.

관심 종목 그룹은 한 종목이 여러 그룹에 들어갈 수 있고, 그룹은 여러 종목을 가질 수 있다. 아주 일반적인 기능이며, 정리하자면 다음과 같다.

- 그룹 CRUD
- 종목 검색 및 추가/제거
- 그룹 및 종목 순서 변경
- 저장/취소

이 중에서 저장/취소에서 약간 고민을 했다. 내가 사용해본 증권사 hts에선 관심 종목 그룹을 수정하고 나서 저장 버튼이 곧 닫기 버튼이었고, 취소시 confirm 같은 것도 없었다. 특별히 어려운 작업이 아니라 confirm이 비용이라 판단된 것일 수 있지만, 나는 있어도 안정감이 생기고 좋겠다는 생각에 추가했다.

또 저장/취소 방식은 **일괄 Staging**으로 했다. 그룹 모달 내에서 변경한 모든 것들은 전부 staging상태, 저장을 누르면 일괄 처리되고 취소하면 모두 수정 이전의 상태로 돌아간다.

자세한 건 이어서 설명하겠다.

## 즉시 commit vs staging

#051의 별표 Popover는 **즉시 commit**이었다. 체크하면 그 순간 store에 반영. 종목 하나를 빠르게 토글하는 맥락이라 그게 맞았다.

근데 관리 모달은 성격이 다르다. 그룹을 만들고, 이름 바꾸고, 종목 여러 개를 검색해 넣다가 — "아 역시 이 그룹은 그만두자" 하고 닫고 싶을 수 있다. 다건을 손대는 화면이라 **"저장하기 전엔 아무것도 안 바뀐다"** 가 더 안전하게 느껴졌다.

| 진입점               | 편집 방식    | 이유                  |
| ----------------- | -------- | ------------------- |
| 종목 상세 별표 (#051)   | 즉시 commit | 종목 하나 빠른 토글         |
| 그룹 관리 모달 (이번)     | staging  | 다건 편집 → 저장/취소가 의미   |

의도된 비대칭이다. 같은 store를 건드리는데 한쪽은 즉시, 한쪽은 저장 단위로 처리된다.

### staging을 어떻게 구현할까 — 부분 갱신과 일괄 갱신

staging으로 가기로 했으면, 로컬에서 편집한 결과를 store에 **어떻게 반영**할지가 남는다. 처리 방식은 두 가지 후보가 있었다. **부분 갱신(diff)**과 **일괄 갱신(staging)**이다.

처음엔 diff를 생각했다. 로컬과 store를 비교해서 바뀐 부분만 `addMembership`·`createGroup` 같은 기존 action으로 순서대로 호출하는 방식이다. 그런데 이 길을 따라가니 **새 그룹의 ID 문제**가 걸렸다. 로컬에서 만든 그룹은 아직 진짜 ID가 없으니 임시 ID를 붙여야 하고, 저장 시점에 진짜 ID로 바꾸면서 그 그룹에 딸린 membership을 다시 연결해줘야 한다. 임시 ID ↔ 진짜 ID 매핑 레이어가 생기게 된다.

그러다 문득 "그냥 통째로 갈아끼우면 안 되나" 싶었다. 로컬 스냅샷을 그대로 store에 덮어쓰면, 로컬에서 만든 그룹 ID가 그대로 진짜 ID가 된다. 매핑이 통째로 사라진다.

처음엔 통째 교체가 더 무식한 방법이라고 봤는데, 따져보니 반대였다.

- 관심종목 데이터는 작다. 그룹 몇 개, membership 수십 개. diff의 "바뀐 것만 갱신" 이점이 의미가 없다. 그룹이 몇십 개가 되어도 비용 자체는 작은 수준이다.
- diff는 action을 여러 번 순차 호출 → 중간 상태가 생긴다. 통째 교체는 단일 연산이라 중간 상태가 없다.
- 코드도 통째 교체가 짧다.

데이터가 클 때나 diff가 값을 하는 거지, 지금 규모에선 통째 교체가 더 단순하고 안전했다. `replaceAll(snapshot)` 하나를 store에 추가했다. 저장 직전 한 가지만 처리한다 — 어느 membership에도 안 남은 ticker는 `stockMeta`에서 정리(GC). 평소엔 `removeMembership`이 자동으로 하던 일인데, 통째 교체는 그 경로를 안 타니 교체 직전에 한 번 돌려준다.

store를 단일 소스(`memberships`)로 잡아둔 #050 결정이 여기서 또 도움이 됐다. 스냅샷이 평평한 배열과 맵뿐이라 통째로 들고 다니기 가볍다.

## 편집 로직을 store에서 떼어내기

문제가 하나 더 있었다. staging이라 모달은 store action을 직접 못 쓴다. `createGroup`은 store를 바로 건드리니까. 그럼 그룹 생성·삭제·순서 로직을 모달 안에 또 짜야 하나? 그러면 #051에서 만든 store action과 똑같은 로직이 두 벌이 된다.

합리적인 방법은 편집 로직을 "**스냅샷 → 새 스냅샷**" 순수 함수로 빼는 거였다. action을 store에 묶지 않으면 store도 모달도 같은 함수를 쓴다.

```ts
createGroupIn(snapshot, name)          → 새 snapshot
deleteGroupIn(snapshot, id)            → 새 snapshot (GC 포함)
moveGroupIn(snapshot, id, "up"|"down") → 새 snapshot
addMembershipIn(snapshot, item, gid)   → 새 snapshot | null  // 상한 초과면 null
// ...
```

그러고 나면 양쪽이 이렇게 갈린다.

- **store action**: `set(s => createGroupIn(s, name))` — 순수 함수를 감싼 얇은 래퍼. 즉시 commit.
- **모달**: `setLocal(prev => createGroupIn(prev, name))` — 같은 함수를 로컬 state에 적용. staging.

로직은 한 군데에만 있고, "어디에 적용할지"만 다르다. #051 store action을 이 래퍼 형태로 다시 쓰면서 동작은 그대로 뒀다. 별표 Popover와 관심종목 페이지에선 아무런 동작 변화가 없도록.

이 추출을 모달보다 먼저 끊어 커밋했다. 모달이 이 함수들에 의존하니 토대가 먼저 서야 했다.

## 모달 — 2단 레이아웃

![](/static/images/velog/116b867d-7dc2-4e26-8197-63b63e95278a-image.png)

*그룹 관리 모달. 좌측 그룹 리스트 / 우측 선택 그룹의 종목과 검색*

좌측에 그룹 리스트, 우측에 선택한 그룹의 종목. 관심종목 페이지(#050)와 같은 2단 구조라 멘탈 모델이 이어진다.

좌측 그룹 행 우측에 액션을 모았다.

- **순서 이동** — `▲▼`를 한 칸에 세로로 쌓았다. #051에선 `▲`와 `▼`가 각자 한 칸씩 차지했는데, 행마다 너무 넓어져서 한 칸에 위아래로 합쳤다. 맨 위 그룹은 `▲`, 맨 아래는 `▼`가 disabled.
- **이름변경** — `✎`를 누르면 그 행이 인라인 입력으로 바뀐다. #051에서 만든 인라인 입력 UX(mount 시 focus·select, Enter 확정/Esc 취소)를 모달 안으로 옮겼다.
- **삭제** — `🗑`. 여기에 staging다운 분기를 하나 뒀다.

삭제 confirm을 종목 유무로 갈랐다. 빈 그룹은 되돌리기 쉬우니 바로 삭제, **종목이 든 그룹만 AlertDialog로 한 번 확인**한다. staging이라 어차피 저장 전엔 취소로 되돌릴 수 있지만, 종목 여러 개가 딸린 그룹을 무심코 날리는 건 막는 게 맞다고 봤다.

글을 작성하며 종목의 순서 조정 기능이 들어가지 않았다는 걸 파악했다. 다음 작업 때 자잘한 수정사항을 모아서 처리할 생각이다.

## #051 인라인 편집은 들어냈다

#051에서 그룹 이름변경·삭제·순서이동을 **우측 헤더 인라인**으로 막 만들었다. 이번에 모달이 그 기능을 전부 흡수하면서, 그 인라인 UI는 중복이 됐다.

아쉬운 트레이드오프다. 바로 직전 세션 작업을 들어내는 거니까. 그래도 이름변경만 모달로 옮기고 삭제·순서는 헤더에 남기면 일관성이 깨진다 — "이건 모달에서, 저건 헤더에서"가 된다. 그룹 편집을 모달 한곳으로 모으는 쪽이 맞았다. 헤더엔 모달을 여는 "그룹 관리" 버튼 하나만 남겼다.

| #051에서 만든 것      | #052에서 |
| ----------------- | ------- |
| 헤더 `✎ 🗑 ▲▼` 인라인  | 제거      |
| `GroupNameInput`  | 모달로 이동  |
| 좌측 `+ 그룹 추가`      | 모달로 이동  |
| store action 6개   | 유지 (순수 함수 래퍼로 재작성) |

다행히 #051 비용이 작았던 작업이라 손실이 크진 않았다. store action은 살아남아 별표 Popover가 계속 쓰고, 인라인 입력 컴포넌트는 모달 안에서 재활용됐다.

## 모달 안 검색 — 훅만 재사용

종목 추가는 검색이 필요하다. 그런데 검색은 홈과 `/search`에 이미 있다. 문제는 기존 `SearchInput`이 검색 결과를 누르면 **종목 상세로 라우팅**하게 박혀 있다는 거였다. 모달에선 라우팅이 아니라 "이 그룹에 추가"여야 한다.

`SearchInput`에 모드 분기를 넣는 안과, 검색 로직을 훅으로 빼는 안을 놓고 봤다. 모드 분기는 한 컴포넌트에 navigate/select 두 책임을 욱여넣는 거라, 라우팅·검색 버튼·Enter 동작마다 `if (mode)` 가 흩어진다.

훅 추출로 갔다. fetch·debounce·AbortController·로딩/에러 state까지를 `useStockSearch(query)`로 빼고, 기존 `SearchInput`은 그 훅 위에 라우팅 UI를 다시 얹어 동작을 유지했다. 모달은 같은 훅 위에 "그룹 추가" UI를 얹는다. 키보드 탐색은 훅에 안 넣었다 — 결과 리스트에 묶인 UI 상태라, 라우팅이 없는 모달과 있는 `SearchInput`이 서로 다르게 굴러야 했다.

![](/static/images/velog/07a4c6a6-0362-42ba-b51d-e2bc96283fda-image.png)

*검색 미리보기. 이미 그룹에 든 종목은 "등록됨"으로 비활성*

모달 검색 동작은 이렇게 정리했다.

- 입력 → 홈처럼 미리보기 드롭다운이 입력 아래에 뜬다. 드롭다운은 절대 위치라 모달 높이를 밀지 않는다.
- 결과 클릭 → 선택된 그룹에 즉시 추가(로컬 스냅샷). 라우팅 없음.
- 이미 그 그룹에 든 종목은 **클릭 불가 + "등록됨"** 표시. 방금 추가한 종목도 바로 이 상태로 바뀐다.
- 상한(distinct 100개) 초과면 추가가 막히고 토스트로 알린다.

## 모달 높이를 고정한 이유

처음엔 모달이 내용에 맞춰 늘어나게 뒀다. 그런데 종목을 추가할수록 모달 세로가 길어지면서 화면에서 출렁이게 될 터였다. 검색 결과를 펼칠 때도 마찬가지다.

높이를 고정값으로 박았다(세로가 가로보다 약간 긴 비율, 모바일은 화면을 안 넘게 상한). 늘어나는 건 모달이 아니라 **내부 리스트**여야 한다. 헤더와 저장/취소 푸터는 고정하고, 가운데 종목 리스트만 스크롤. flex에서 자식이 안 줄어드는 `min-h-0` 함정을 빼먹지 않게 신경 썼다.

## 닫을 때 — dirty 가드

staging이라 닫기 = 버리기다. 편집하다 실수로 닫으면 작업이 날아간다. 그래서 **저장 안 한 변경이 있을 때만** 닫기 시 한 번 확인하는 AlertDialog를 뒀다. 변경이 없으면 가드 없이 바로 닫힌다.

dirty 판정은 로컬 스냅샷과 열 때 떠둔 원본을 `JSON.stringify`로 비교했다. 스냅샷이 작고 키 순서가 결정적이라 이 정도로 충분했다. 더 정교한 비교를 붙일 수도 있지만 지금 규모엔 과했다.

## 남은 것

E5는 이렇게 얼추 마무리 됐다. 그룹을 만들고, 정리하고, 종목을 검색해 담는 흐름이 다 돈다. 다만 브라우저로 돌려보니 다음 글에서 손볼 게 몇 개 보였다.

- **종목에도 순서** — 앞서 언급한 건이다. 그룹은 `▲▼`로 순서를 바꾸는데, 그룹 안 종목엔 순서 개념이 없다(addedAt 정렬). 종목에도 순서를 주려면 membership에 `order` 필드를 넣어야 하고, persist 마이그레이션이 한 번 더 필요하다.
- **모달 검색 키보드 탐색** — 방향키·Enter로 추가. 훅엔 없으니 모달 드롭다운에 따로 붙인다.
- **검색 대소문자** — 검색에 대소문자가 구별된다는 사실을 테스트 중 파악했다. `lg`로 LG전자가 안 잡힌다. Postgres `LIKE`가 대소문자를 가려서 그렇다. `ILIKE`로 바꾸면 끝나는 작업.

E5가 닫혔으니 이제 정할 때가 됐는데, 자잘한 수정들을 한 세션에 모아 처리하면서 같이 보기로 했다. 디자인도 이 때 같이 한 번 점검해 봐야겠다.
