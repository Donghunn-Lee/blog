홈페이지 재구성을 마치고 또 다시 데이터 안정성 작업으로 돌아왔다.

데이터 문제로 #094에서 발견하고 #095에서 재적재로 덮었다가 #096에서 재발한 지수 EOD silent 미적재(F30) 건이 하나 있었다. 확인된 건 1건이지만 재발 가능 위험으로 확정 짓고 이번 세션을 원인 조사로 잡았는데, 조사에 들어가기도 전에 판정이 뒤집혔다. 실패한 run은 한 번도 없었다 — 세 번의 관찰이 전부 같은 착시였다.

판정이 그렇게 나면서 세션은 원인 조사 대신 일봉 소스 전환과 감시 장치 쪽으로 갔다. 세션에 앞서 훑어둔 workflow 실태 리뷰(continue-on-error 비대칭, weekly 계단식 스킵)도 여기에 입력으로 합류했다.

## 기준일이 밀려 발생한 오해

오늘 26일, 세션을 열고 배포 화면부터 봤다. 서비스의 지수 기준일이 7/24였다. 어제 #096 세션 중엔 분명 7/23에 멈춰 있었고, 그 사이 재적재를 돌린 적이 없다. 저절로 하루가 올라왔다는 건 토요일 cron이 금요일분을 정상으로 넣었다는 뜻이다.

여기서 익숙한 사실 하나가 다시 보였다. 일일 적재는 매일 16시(KST)에 돌고, #065에서 정한 대로 "어제"를 조회한다. KRX Marketplace가 그날 데이터를 다음 날 아침 8시에야 채우기 때문이다. 그러면 16시 이전에 화면을 보면 최신 EOD가 전전일인 게 설계상 정상이다.

이 렌즈로 세 번의 관찰을 다시 놓아봤다.

| | 관찰 시각 | 당시 해석 | 실제 |
|---|---|---|---|
| #094 발견 | 금요일 낮 | 목요일분 미적재 | 목요일분은 금 16시에 들어오는 설계 |
| #095 복구 | 금요일 오후 | 재-run으로 복구 성공 | 그 시각에 돌리면 원래 들어오는 데이터 |
| #096 재발 | 토요일 낮 | 금요일분 또 미적재 | 금요일분은 토 16시에 들어오는 설계 |

셋 다 "16시 이전에 봤다" 하나로 설명된다. 사실 재-run이 먹혔다는 것부터가 신호였는데, 그땐 복구됐다는 결과에 안심해서 거기까지 생각이 닿지 않았다.

확정은 로그로 했다. 최근 14일 daily run 13회 전부 성공, continue-on-error에 가려진 step 실패 0건, DB엔 4지수 모두 7/24 봉이 들어 있었다. 실패는 없었다. F30은 silent 실패가 아니라 **노출 지연** 문제였다 — 공표(익일 8시)와 적재(16시) 사이 8시간 동안, 장중 화면엔 이틀 전 EOD가 걸려 있는 설계.


```
collector-daily 최근 5개 run · step 단위

  run 30151915976 (07-25 08:54) : fetch_prices=success  fetch_index_prices=success  fetch_overseas_indices=success
  run 30081840723 (07-24 09:14) : (동일)
  run 29994738604 (07-23 09:18) : (동일)
  run 29907633478 (07-22 09:21) : (동일)
  run 29817997310 (07-21 09:22) : fetch_prices=success  fetch_index_prices=success  fetch_overseas_indices=<step 없음>     
  - continue-on-error 로 가려진 실패: 0건
```

## 일봉 소스를 KRX Marketplace에서 KIS로

KRX 데이터 갱신이 익일 08시라는 건 #065에서 확인하고 설계에 반영했던 사실이다. 문제는 그 위에 얹힌 조합이었다 — 적재는 16시에 돌고 현재가·당일봉은 KIS로 그리다 보니, 장중 차트에 당일봉은 있는데 **D-1 캔들이 공백**이 된다. DB는 아직 D-2까지고, quote가 채워주는 건 당일뿐이라 그 사이 하루가 빈다.

적재를 안 건드리고 푸는 길도 있긴 했다.

| 안 | 내용 | 걸리는 점 |
|---|---|---|
| cron 아침 이동 | KRX 공표 직후(08시대)로 적재를 당김 | Actions 발화 지연이 실측 +1.7~3.2h라 오전 장중 한동안 D-2가 그대로 노출. 공표 타이밍 결합도 남는다 |
| 화면에서 보완 | 빠진 최신 봉을 quote로 합성 | 주말 구멍만 복원된다 — 평일에 비는 D-1의 시·고·저·거래량은 quote에 없다. 소비처마다 "봉이 빠져 있을 수 있음"을 아는 보정이 늘어난다 |

둘 다 증상은 줄인다. 근데 애초에 16시로 정했던 의도가 "당일 장 마감 후 적재"였고, 그게 KRX 공표 구조 때문에 성립한 적이 없다는 게 이번에 드러난 실체다. 그래서 증상을 다듬는 대신 그 의도를 성립시키는 쪽으로 갔다 — 일일 갱신 소스만 KIS 일봉으로 바꾸면 16시에 당일분이 들어오고, 공표 결합은 사라지며, D-1 공백도 저녁의 quote 의존도 소비처 보정도 생길 이유가 없어진다. 뒤에 붙일 freshness 검증도 "거래일이면 DB에 당일이 있다"는 단순한 불변식을 얻는다.

KIS 일봉은 #065에서 한 번 올렸다 내린 후보인데, 그땐 비교 축에 당일 가용성이 없었다. 히스토리는 그대로다 — 3년 치 KRX 백필 위에 일일 인크리먼트의 소스만 바뀌고, KRX 스크립트는 백필 전용으로 남는다.

## 성공 보고를 검증하는 장치

착시로 판정 났다고 감시 사각이 없던 건 아니다. 리뷰에서 나온 문제들은 실재했다. daily는 세 스텝 중 둘만 continue-on-error라 지수 스텝이 실패해도 워크플로우가 초록일 수 있고, weekly는 반대로 격리가 없어 첫 스텝이 넘어지면 재무제표 갱신까지 한 주 통째로 밀린다.

이를 두 겹으로 막았다.

- **failure gate** — 스텝 전부를 continue-on-error로 격리해 부분 적재는 최대한 진행시키되, 마지막 gate 스텝이 outcome을 모아 하나라도 실패면 워크플로우를 실패로 만든다
- **freshness assert** — run 말미에 "오늘 기준 직전 거래일"을 계산해 daily_prices와 index_daily_prices의 MAX(date)를 대조하고, 미달이면 exit 1

둘은 잡는 실패가 다르다. gate는 스텝이 넘어진 걸 잡고, assert는 **정상 종료했는데 데이터가 없는** 걸 잡는다. F30이 진짜 실패였다면 알려줬을 장치는 후자다.

assert엔 직전 거래일 계산이 필요해서 웹의 휴장일 상수를 파이썬에 복제했다. #065에서 "굳이 파이썬에 한 벌 더 둘 이유가 없다, 빈 응답 하나로 충분하다"고 적었던 결정을 이번에 뒤집은 건데 — 빈 응답을 휴장으로 읽는 그 관용 때문에, 진짜 실패가 와도 똑같이 조용했을 거다. 연 1회 두 벌을 같이 갱신하는 비용을 내고 그 모호함을 없앴다.

cron도 정리했다. 매일 발화하던 걸 요일로 갈랐다.

```yaml
schedule:
  - cron: "0 7 * * 1-5"   # 평일 16시: 전체
  - cron: "0 7 * * 6"     # 토요일: 해외 EOD만 (미국 금요일 마감분)
```

일요일 발화가 사라지고, 토요일마다 2,600여 종목을 헛돌던 13분도 없어졌다.

```
verify_daily_freshness.py pass → force fail → pass

  === [2a] pass 기대 ===
  verify: today(KST)=2026-07-26  expected=2026-07-24
    OK daily_prices.MAX(date) = 2026-07-24  (expected 2026-07-24)
    OK index_daily_prices.MAX(base_date) = 2026-07-24  (expected 2026-07-24)
  verify: PASS
  EXIT=0

  === [2b] 강제 fail (VERIFY_FORCE_EXPECTED=2026-07-27) ===
  verify: VERIFY_FORCE_EXPECTED=2026-07-27 (override)
  verify: today(KST)=2026-07-26  expected=2026-07-27
    !! daily_prices.MAX(date) = 2026-07-24  (expected 2026-07-27)
    !! index_daily_prices.MAX(base_date) = 2026-07-24  (expected 2026-07-27)
  verify: FAIL — daily_prices.MAX(date)=2026-07-24 != expected 2026-07-27   (stderr)
  verify: FAIL — index_daily_prices.MAX(base_date)=2026-07-24 != expected 2026-07-27   (stderr)
  EXIT=1

  === [2c] 원복 후 (다시 pass) ===
  verify: today(KST)=2026-07-26  expected=2026-07-24
    OK daily_prices.MAX(date) = 2026-07-24  ...
  verify: PASS
  EXIT=0

```

## 토큰 취득처 세 곳을 하나로

fetch_index_prices를 새로 쓰며 토큰이 필요해졌는데, 확인해 보니 취득 방식이 이미 세 갈래였다. #063에서 12시간 cron이 발급해 DB에 두는 공유 캐시를 만들었는데, 읽는 쪽이 그 뒤로 제각각이 된 거다. intraday는 DB만 읽고 없으면 조용히 종료, 해외 daily는 캐시를 보지도 않고 매 run 자체 발급.

네 번째 변종을 만드는 대신 헬퍼로 모았다. DB에서 읽고, 유효하면 쓰고, 아니면 발급해서 DB에 되써놓는다. 세 소비자를 전부 이 경로로 옮기면서 intraday의 "토큰 없으면 조용히 종료"도 폴백 발급 후 실패 시 소리 나는 종료로 바뀌었다 — 이번 세션에서 걷어낸 것과 같은 종류의 침묵이라 같이 치웠다.

## 화면별 출처 매핑과 등락률 대조

F31의 남은 절반은 조사였다. 화면 요소마다 어느 소스(DB 테이블인지, KIS의 어느 TR인지)를 어떤 캐시 주기로 읽는지 매핑 표를 만들었다. 이번 전환의 영향 범위가 index_daily_prices를 읽는 함수 둘과 그 아래 화면 몇 개로 깔끔하게 닫히는 것도 이 표로 확인했다.

#095부터 걸려 있던 검색 표 등락률 대조도 닫았다. 검색 표와 종목 상세 헤더는 EOD 폴백 쿼리 형태가 다른데(LAG 윈도우 vs LIMIT 2), 5종목을 DB 원천값과 3자 대조한 결과 완전 일치였다. 다만 장중엔 값이 갈릴 수 있다 — 계산이 아니라 소스 차이다. 검색은 KRX+NXT 통합(UN) 시세를, 상세는 세션별 KRX/NXT 토글을 쓰기 때문에, NXT에서 활발한 종목은 두 화면의 "현재가"가 서로 다른 체결가일 수 있다. 실제로 얼마나 벌어지는지는 장중 실측으로 넘겼다.

매핑하다 부스러기도 하나 잡았다. 코스닥150이 quote 이름 매핑에 빠져 있어 도메인 모델의 name이 "3003" 문자열로 채워지고 있었다. UI가 별도 라벨을 써서 안 보였을 뿐이라, 이름 하나 추가로 닫았다.

## 정리

- **F30 종결** — 세 번의 미적재 관찰이 전부 "16시 적재 전 관찰" 착시로 판정. run 이력 13/13 성공, 가려진 실패 0건
- **일봉 소스 KIS 전환** — 당일 16시 적재로 회귀. parity 119건 일치·단위 계수·TR별 코드 상이 확인, incremental 이식으로 자가 복구 확보
- **감시 이중화** — failure gate + freshness assert, 휴장일 상수 파이썬 미러, cron 요일 분리
- **토큰 헬퍼 단일화** — 취득 3패턴을 DB read + 폴백 발급 하나로
- **F31 조사** — 화면별 출처 매핑 완성, 검색 vs 상세 등락률 완전 일치. 장중 소스 차이 실측은 F32로

코드보다 판정이 일을 한 세션이었다. 같은 증상을 세 번 보고도 원인 조사를 시작하고서야 관찰 시각이라는 변수를 의심했는데, 뒤집힌 판정이 결과적으로 원인 조사보다 나은 결론 — 소스 전환 — 으로 데려갔다. 증상을 고치러 갔다가 설계를 고치고 온 셈이다.
