종목 상세 페이지까지 만들고 나서 한 가지가 계속 마음에 걸렸다. `/stocks/005930` 같은 공개 페이지가 있는데, 브라우저 탭 제목은 그냥 "SlateKR"이고 메타 정보가 아무것도 없는 상태였다.

투자 추천 서비스도 아니고 트래픽이 목표도 아니지만, 공개 URL이 있는 페이지가 검색 엔진에 색인될 수 있는 기본 조건은 갖춰두는 게 맞다고 생각했다. 더군다나 이번 프로젝트는 SEO도 충분히 신경 쓰는 것이 기획 의도부터 있었다.

---

## title template

가장 먼저 한 건 루트 `layout.tsx`에 title template을 추가하는 거였다.

```ts
title: {
  template: "%s | SlateKR",
  default: "SlateKR",
}
```

처음엔 그냥 각 페이지 `generateMetadata`에서 `"삼성전자 (005930) | SlateKR"` 이렇게 직접 붙이면 되지 않나 싶었다. 실제로 기존 코드가 그렇게 돼 있었다.

문제는 루트에 template을 추가하는 순간 이중으로 붙는다. `"삼성전자 (005930) | SlateKR | SlateKR"`. 그래서 자식 페이지는 `%s` 자리에 들어갈 부분만 반환하고, suffix는 루트 한 곳에서만 관리하는 방식으로 바꿨다.

`generateMetadata`가 없는 페이지는 `default` 값이 그대로 쓰인다.

## generateMetadata의 null 처리

종목 상세 페이지 `generateMetadata`를 수정하면서 한 가지 주의해야 했다.

페이지 본문은 종목이 없으면 `notFound()`를 호출하는데, `generateMetadata`는 그 이전에 실행된다. 그래서 null 케이스를 직접 처리해야 한다.

```ts
if (!stock) return { title: "종목을 찾을 수 없습니다" };
```

여기서도 `| SlateKR`은 붙이지 않는다. template이 자동으로 붙여준다.

그리고 `generateMetadata`와 페이지 본문이 같은 요청 안에서 각각 `getStockByTicker`를 호출하면 DB 쿼리가 두 번 나간다. 이미 `React.cache()`로 감싸두었기 때문에 동일 인자 결과는 요청 단위로 메모이제이션된다. App Router에서 Server Component 간 데이터를 공유하는 표준적인 방법이다.

## metadataBase

`metadataBase`는 OG 이미지처럼 상대 경로가 들어가는 메타태그에 절대 URL을 붙여주는 설정이다. 지정하지 않으면 Next.js가 경고를 내며 상대 경로를 그대로 쓴다.

지금 당장 OG 이미지는 없지만, 나중에 추가할 때를 위해 미리 잡아뒀다.

```ts
metadataBase: new URL(process.env.NEXT_PUBLIC_BASE_URL ?? "http://localhost:3000")
```

`NEXT_PUBLIC_` prefix를 붙인 건 클라이언트 번들에서도 참조 가능하도록 맞춰두기 위해서다.

---

## robots.ts

Next.js App Router는 `app/robots.ts`를 특수 파일로 인식해서 `/robots.txt` 요청에 자동으로 응답한다.

robots.txt는 검색 엔진 크롤러에게 "어느 경로까지 접근해도 되는지"를 알려주는 파일이다. 그리고 그 안에 sitemap 위치도 함께 명시한다.

```
Sitemap: https://slatekr.com/sitemap.xml
```

이 URL이 로컬과 프로덕션 환경에서 달라지기 때문에 `/public/robots.txt`로 정적 파일을 두면 하드코딩이 필요하다. `app/robots.ts`로 만들면 `process.env.NEXT_PUBLIC_BASE_URL`을 런타임에 읽어서 환경에 맞는 URL을 자동으로 넣어줄 수 있다. `MetadataRoute.Robots` 타입을 쓰면 반환 형식이 잘못될 가능성을 컴파일 타임에 잡을 수 있다.

## sitemap.ts

sitemap.xml은 크롤러에게 "이 사이트에 이런 페이지들이 있다"를 적극적으로 알려주는 파일이다. 없어도 크롤러가 링크를 타고 페이지를 찾긴 하지만, SlateKR처럼 종목 페이지가 2,600개 넘는 경우엔 sitemap 없이 전부 탐색하길 기대하기 어렵다.

---

`lib/stocks.ts`에 `getAllTickers()`를 따로 만들었다. sitemap 생성에는 ticker 목록만 필요하므로 `SELECT ticker FROM stocks WHERE is_active = 1`만 하는 전용 함수다. `is_active = 1` 필터는 상장 폐지 종목을 sitemap에서 제외하기 위해서다.

구조는 정적 경로와 동적 경로를 분리해서 선언했다.

```ts
const staticRoutes = [
  { url: `${base}/`, changeFrequency: "daily", priority: 1 },
  { url: `${base}/watchlist`, changeFrequency: "weekly", priority: 0.5 },
];

try {
  const tickers = await getAllTickers();
  stockRoutes = tickers.map((ticker) => ({
    url: `${base}/stocks/${ticker}`,
    changeFrequency: "daily" as const,
    priority: 0.8,
  }));
} catch {
  // DB 오류 시 정적 경로만 반환
}
```

DB가 죽어도 `/`와 `/watchlist`는 sitemap에 남아있어야 한다. 에러가 전체 sitemap 생성을 막아서는 안 된다는 판단이었다.

`changeFrequency: "daily"`를 map 안에서 추론하면 TypeScript가 `string`으로 넓혀서 `MetadataRoute.Sitemap`의 리터럴 유니온 타입과 충돌한다. `as const`로 리터럴 타입을 유지했다. 정적 경로 배열은 타입을 명시했기 때문에 같은 문제가 생기지 않는다.

---

그동안 SEO를 자주 다뤄보지 못했는데, 생각보다 설계 판단이 여러 군데에 있었다. title template 중복 문제나 sitemap fallback 구조는 그냥 "돌아가게 만들면" 놓치기 쉬운 부분이다.
