#140 마무리에서 찾은 결함이 E69다. 지수 라벨을 "장중 · HH:MM"으로 정직하게 바꿔놓고 보니, 그 HH:MM이 클라이언트 시계였다. 값은 route 캐시에서 최대 60초 전 것이 나오는데 시각만 현재를 가리키니 신선도를 과장하고 있었다.

원래 계획은 월요일 아침 창에 실측과 E69 구현을 같이 넣는 것이었다. 일요일 밤에 한 세션이 더 생겨서 시장이 열려야 볼 수 있는 실측은 떼어내고 구현만 먼저 했다. 대안으로 잡아뒀던 지수 페이지 진입점(E60)도 같이 처리했는데, 이쪽은 계획서에 적어둔 범위가 이미 반쯤 지나간 것이었다. 커밋 5개, 육안 실측은 다음 세션으로 넘겼다.

## 시각을 어디에 담을 것인가

고칠 방향 자체는 #140에서 이미 정해뒀다. 캐시 단위 함수가 KIS를 실제로 부른 시각을 데이터와 함께 돌려주고, 라벨이 그걸 쓰면 된다. 캐시 히트면 저장돼 있던 시각이 그대로 나가니 "60초 전 값"에는 "60초 전 시각"이 붙는다.

남은 건 그 시각을 어느 층에 얹느냐였다.

| 후보 | 판정 |
| --- | --- |
| 응답 봉투에 집계 필드 하나 | 기각. 캐시 단위 바깥에서 계산되니 히트해도 매번 현재 시각이 됨. 고치려던 문제가 그대로 남음 |
| 현재가 타입에 필드 추가 | 기각. 해외 지수 현재가까지 같은 타입을 쓰는데 해외는 이 문제가 없음 |
| **캐시 단위가 반환하는 셀 객체에** | **채택.** 캡처가 캐시 안에서 일어나 히트 시 원래 값이 보존됨. 화면별 집계는 소비 측 책임으로 남음 |

첫 번째 후보를 굳이 적어두는 건 이게 제일 만들기 쉬운 모양이었기 때문이다. 응답을 조립하면서 `Date.now()`를 한 번 찍어 넣으면 코드는 한 줄이고 타입도 안 건드린다. 그런데 그 한 줄이 실행되는 위치가 캐시 밖이라, 캐시가 히트하든 미스하든 항상 지금 시각이 나온다. 지금 클라이언트 시계로 찍는 것과 결과가 같아서, 고쳐도 아무것도 안 고친 게 된다.

그래서 캡처는 KIS 호출 직후, 캐시 콜백 안에서 한다.

```ts
// 캐시 단위 내부
const live = await fetchIndexQuote(code);
const fetchedAt = Date.now();
return { live, fetchedAt };
```

성공이든 실패든 폴백이든 같은 자리에서 찍는다. 현재가 조회에 성공한 시각만 잡으면 폴백 셀에는 시각이 없어 라벨 분기가 하나 더 생긴다. 여기서 잡는 건 "이 셀을 조립한 시각"이라고 정의하면 분기 없이 하나로 간다.

## 필드를 필수로 두지 못한 이유

셀 타입에 `fetchedAt: number`를 필수로 넣으려다 `number | null`로 물러섰다. 이 셀 타입은 국내 지수 route만 만드는 게 아니었다.

| 셀 생성 경로 | 시각 값 |
| --- | --- |
| 국내 지수 route (캐시 단위) | 항상 있음 |
| 공용 조립 함수 · 개장 전 등락 스왑 분기 | 원래 국내 셀 값을 물려받음 |
| 공용 조립 함수 · 해외 현재가 / 해외 마지막 봉 / 마지막 일봉 | 없음 (이번 대상 아님) |

필수로 두면 아래 세 분기에서 값을 지어내야 하고, 그건 없는 시각을 있는 것처럼 만드는 일이라 이 작업의 취지와 정반대다. 대신 route 안에서 쓰는 좁은 타입은 필수로 유지해, 국내 셀은 항상 값을 갖는다는 것이 route 안에서는 타입으로 보장되고 화면 쪽에서는 없을 수 있다는 것만 알면 되게 했다.

## 홈 헤더는 가장 오래된 값

홈 지수 슬레이트는 라벨이 지수별로 있는 게 아니라 슬레이트 전체에 하나다. 네 지수의 시각이 조금씩 다를 텐데 그중 무엇을 쓸지 골라야 했다.

| 후보 | 판정 |
| --- | --- |
| 네 셀 중 최신값 | 기각. 가장 최근에 갱신된 셀이 나머지 셋의 신선도까지 대변함 |
| **네 셀 중 가장 오래된 값** | **채택.** 라벨이 말하는 신선도가 화면의 어느 셀에도 과장이 아님 |
| 값이 없을 때 대체 시각 | 기각. 모를 때는 시각을 빼고 "장중"만 남김 |

애초에 신선도 과장을 걷어내려고 시작한 작업이라 보수적인 쪽이 맞았다. 지수 상세는 라벨이 선택된 지수에 붙어 있으니 그 지수 것을 그대로 쓴다.

| 남긴 것 | 이유 |
| --- | --- |
| 최솟값 계산은 슬레이트 컴포넌트 안에 인라인 | 다섯 줄, 쓰는 곳 하나, 도메인 의미 없음 |
| 시계 훅 존치 | 정규장 판정과 마감 라벨 기준일 계산에는 여전히 현재 시각이 필요함 |

## 계획서가 반쯤 지나가 있던 항목

E60은 "지수 차트 페이지로 가는 진입점이 홈 슬레이트 경유뿐이다"라고 적어둔 항목이다. 착수 전에 코드를 먼저 훑었다.

| 계획서에 적혀 있던 것 | 실제 |
| --- | --- |
| 하단 탭바에 진입 동선 없음 | #104에서 홈·순위·관심·지수 네 탭으로 이미 만들어져 있었음 |
| 탭 하나 추가 시 폭·높이 상수·레이아웃 오프셋 검토 | 검토할 것 없음 |
| 상단 네비게이션에 진입 동선 없음 | 맞음. 링크 하나 추가, 탭바 순서에 맞춰 관심종목 다음에 "주요 지수" |

계획서 비고를 확인 없이 믿었다면 탭바 다섯 칸 확장을 설계하고 있었을 것이다. #143에서도 같은 일이 있었다. 메모 항목 비고의 "관심종목 스냅샷에 메모 컬럼 추가"는 착수해보니 전제부터 다시 판단할 것이었고, 미결로 적어둔 쿠키 발급 문제는 이미 해결돼 있었다. 두 번 연속이면 습관 쪽 문제다. 계획서 비고는 그걸 적던 시점의 코드 상태이고 세션이 쌓이는 동안 코드는 계속 움직이니, 착수 전 확인을 절차로 박아두는 게 맞겠다.

## 확인한 것과 못 한 것

| 항목 | 결과 |
| --- | --- |
| 현재가 API 연속 2회 호출 | 네 셀 모두 시각 필드 존재, 두 응답 값 완전 동일 |
| 시각 값 | 23:04:35 — 첫 호출 시각과 일치 |
| 응답 봉투 | 키 변화 없음 |
| 마감·개장 전 라벨 | 조립 코드 변경 0줄 |
| 게이트 | 테스트 815건 통과, 빌드 성공 |
| "장중 · HH:MM" 육안 | 미확인 |

일요일 밤이라 정규장 라벨을 볼 수가 없었다. 다음 세션 09시 이후에 홈 헤더가 네 셀 중 가장 오래된 시각을 쓰는지, 캐시가 히트하는 60초 동안 시각이 멈춰 있는지 본다. 시각이 60초마다 계단식으로 움직이면 맞게 붙은 것이고, 초 단위로 흐르면 아직 클라이언트 시계를 보고 있는 것이다.

## 정리

- **E69 구현** — 캐시 단위 안에서 호출 시각을 찍어 셀에 동봉, 홈은 네 셀 중 가장 오래된 값·지수 상세는 선택된 지수 값으로 라벨 교체. 값이 없으면 시각 생략
- **셀 타입은 nullable** — 공용 조립 함수가 해외 경로에서도 셀을 만들어 필수로 둘 수 없었음. route 안쪽만 좁은 타입으로 보장
- **E60은 링크 하나** — 하단 탭바 진입점은 #104부터 있었음. 계획서 비고가 stale이던 두 번째 사례
- **"실시간" 문구 판단은 소멸** — #140에서 이미 전면 치환돼 남은 곳이 없었음
- **육안 실측 이월** — 정규장 라벨은 다음 세션 아침에

한 시간 반짜리 세션에서 실제로 판단한 건 시각 필드를 어느 층에 두느냐 하나였다. 나머지는 그 결정을 따라 내려간 것이거나, 확인해보니 할 일이 없어진 것이다. 계획서 비고를 두 번 연속으로 못 믿은 게 이번 세션에서 제일 남는 부분인 듯싶다.
