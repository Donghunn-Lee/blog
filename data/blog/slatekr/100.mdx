## 밤사이 빈 해외 분봉

미국 세션 11:50 부근의 10분봉이 없었다. run 이력을 보니 30분 스케줄이 00:41 다음 2:41로 두 시간을 건너뛰었다. 해외 분봉 TR은 최근 ~100봉만 주고 과거일 조회가 안 되니(#093), run 사이가 lookback 창(약 1시간 40분)을 넘으면 그 사이 봉은 영구 결손이다. 지나간 건 어쩔 수 없고, 재발을 막아야 했다.

원래 계획한 분 오프셋은 정각 피크를 피할 뿐 트리거가 밀리거나 빠지는 것 자체는 못 막는다. 대안을 놓고 봤다.

| 안 | 내용 | 걸리는 점 |
|---|---|---|
| 간격 단축 | 30분 → 15분. 트리거 몇 개가 빠져도 갭이 lookback 안에 남는다 | 갭 상한은 잡지만 발화 시각은 여전히 GitHub 마음 |
| 외부 스케줄러 | 외부에서 정확한 시각에 dispatch API 호출 | 토큰 발급·외부 서비스 관리 지점 추가 |

간격 단축으로 기울다가 요구를 다시 정리해봤다. 해외 분봉은 갭 상한이면 충분하지만, daily는 다르다 — #097·#098에서 일봉 소스를 KIS로 옮긴 이유가 "당일 16시 적재"였는데, 정작 어제 daily run은 19시 반에 돌았다. 3시간 반 지연. 소스를 바꿔 얻은 약속을 트리거가 도로 깨고 있던 거다. 갭 상한이 아니라 정시가 필요한 소비자가 이미 있었다.

GitHub의 schedule 이벤트는 best-effort 큐라 부하가 몰리면 밀리고, 심하면 빠진다. 반면 workflow_dispatch는 거의 즉시 픽업된다. 그래서 스케줄을 GitHub 밖으로 꺼냈다 — cron-job.org(무료)가 정확한 시각에 dispatch API를 호출하고, 워크플로우는 그 이벤트를 받아서 돈다.

이관하며 손본 곳이 하나 있다. daily 워크플로우는 토요일 여부를 cron 문자열 매칭으로 분기하는데, 외부 트리거에선 `github.event.schedule` 컨텍스트가 비어서 분기가 무력화된다. `mode` input(full / overseas-only)을 추가해 문자열이 아니라 파라미터로 분기하게 바꿨다.

```yaml
if: ${{ github.event.schedule != '0 7 * * 6' && inputs.mode != 'overseas-only' }}
```

schedule 트리거에선 inputs가 빈 값이라 기존 거동이 그대로 보존된다.

이관은 이틀로 갈랐다. yml의 schedule은 오늘 하루 fallback으로 남겨두고, 저녁 관측이 green이면 내일 걷기로 했다. 그 저녁 관측 —

- daily가 **16:00:29**에 발화했다. 어제 3시간 반 밀리던 그 자리다
- quote_snapshots 첫 자동 cron green — 캡처 2,650건, #099 수동 캡처와 정합
- 해외 분봉 run이 22시부터 30분 간격으로 정연하게 돌았다

부수로 관측성도 나아졌다. cron-job.org는 호출이 실패하면 메일을 보낸다. GitHub의 schedule 드랍은 아무 소리도 안 났다.

## B10 — 부풀림의 출처

sweep 본편. "매출 73,373조" 같은 값이 들어 있는 종목들의 판별이다.

[#038](/blog/slatekr/038/)에서 이 문제를 처음 팠을 때 "회사 filing error인 줄 알았다가 collector의 단위 정규화 누락으로 정정했다"고 기록한 바 있다. 이번 probe가 그 정정을 한 번 더 뒤집었다. DB 값과 DART 응답 원본을 대조해보니 collector는 받은 그대로 저장하고 있었고, **부풀린 값은 DART가 보낸 것**이었다. 회사가 XBRL의 unit 태그를 잘못 지정하면(천원 단위 값에 원 단위 태그를 붙이는 식) DART API는 배율 보정 없이 원본을 그대로 전달한다. 정상적으로 태그된 filing은 원 단위로 오기 때문에 "전 종목 환산"이 필요한 게 아니라, 오태그된 소수만 산발적으로 부풀려 오는 구조다. 돌아보면 처음 직감이 더 가까웠던 셈이다.

이 판정이 노선을 정했다. #038에서 미뤄뒀던 본 해결 선택지가 HTML 파싱 / 수동 메타 테이블 / 무시 셋이었는데, 원인이 산발적 원본 오류라면 넷째 답이 있다 — **삽입 게이트로 막고, 걸린 건 수동 정정.**

### 의심 목록 전수 판별

기존 의심 목록(강한 4건·약한 3건)에 더해, 같은 패턴을 DB 전체에서 스캔해 후보를 늘렸다. 절대값 1000조 이상 4건, 연간이 분기 합보다 극단적으로 작은 12건. 전부 DART 재조회로 판별했다.

| 판정 | 건수 | 내용 |
|---|---|---|
| 부풀림 확정 | 11행 | 재무 10행(×10³ 6건 · ×10⁶ 4건) + shares 1건(30.6조 주) |
| 실제 급변 | 11건 | 단위 오류 아님 — 정정하면 안 되는 값 |
| 별도 이슈 | 1종목 | 방향이 반대(축소). 다음 섹션 |

실제 급변 11건이 흥미로웠다. 시그니처(annual ≪ 분기 합)만 보면 부풀림과 똑같은데, 원인은 IFRS의 중단영업 재분류였다 — 연중 사업부를 매각하면 분기보고서엔 매각 전 매출이 통합 계상되고, 연간은 계속영업만 재계상된다. 판별 지표는 annual 응답의 frmtrm(전기 재분류값)과 DB의 전년도 원본 사이 격차다. 재분류면 격차가 크고, 부풀림이면 같은 filing이라 frmtrm도 같은 배율로 부풀어 있다. 시그니처만 믿고 일괄 정정했다면 정상 데이터 11건을 오염시켰을 거다.

확정 11행은 종목별 배율을 명시한 SQL로 정정했다. 검증은 DART 원본 ÷ 배율과의 일치, bps = 자기자본/주식수 관계 재성립, 전후 기간 스케일 연속성 세 축으로 — 전부 통과.

### 게이트 설계

재발 방지는 삽입 전 게이트다. |값| ≥ 2e15면 해당 행을 skip하고 WARNING을 남긴 뒤, run 말미에 exit 1로 워크플로우를 실패시킨다. 임계값 근거는 실측 — DB의 정상 최대값이 신한지주 자산 816조(8.16e14)고, 관측된 최소 부풀림이 5.8e15라 그 사이에 경계를 뒀다. shares도 1e11 상한으로 같은 처리.

frmtrm 배율 비교로 자동 정정(나누기)하는 안도 있었는데 기각했다. 전년도 응답까지 부풀린 케이스, 비교 대상이 없는 신규 상장 첫해 같은 엣지에서 오정정 리스크가 skip보다 나쁘고, 전체 DB에서 11행 나온 빈도면 수동 SQL로 충분하다. 한계도 하나 인지하고 수용했다 — 소형주의 ×10³ 부풀림(~1e14)은 대기업 정상값과 절대값으로 안 갈려서 게이트를 통과한다. 연간은 기존 비율 룰이 사후에 잡고, 분기 단독의 소형 부풀림만 미탐지 창으로 남는다.

## 241560 — 표시통화가 달러로 바뀐 종목

재검증 목록에 방향이 반대인 게 하나 있었다. 두산밥캣은 부풀림이 아니라 축소 — 2023 연간부터 매출이 조 단위에서 억 단위로 내려앉았고, 배율도 10^k로 떨어지지 않았다.

probe로 응답을 떠보니 currency 필드가 **USD**였다. #038에서 "currency는 어떤 종목을 호출해도 KRW 한 값뿐"이라고 적었는데, 그때 표본에 이런 종목이 없었을 뿐이었다. 두산밥캣은 매출 대부분이 미국 자회사에서 나와서, 2023 사업보고서부터 연결재무제표 표시통화를 원화에서 달러로 바꿨다. IFRS가 허용하는 정당한 선택이고, DART는 회사가 낸 그대로 USD 값을 준다. 오류가 아니라 정책이라 앞으로도 계속 이렇게 온다.

화면 피해는 부풀림보다 심했다. 연간 3개년이 억 단위로 표시되고, Q4 역산(연간 − 분기 합)은 달러에서 원화를 빼는 꼴이라 **-7.4조**가 찍히고, PER은 원화 종가를 달러 EPS로 나눠 실제의 1/1300이 된다. 대형주라 노출도 크다.

| 안 | 내용 | 판단 |
|---|---|---|
| 환율 복원 | 사업보고서 주석의 기간별 환율(손익=평균·자산=기말)을 곱해 원화로 | 기각 — DART 원본이 아닌 조립 추정치를 DB에 넣게 된다. USD 종목이 늘면 종목마다 반복 |
| **NULL 격리** | 오염 10행의 수치 컬럼을 비운다 | **채택** — 이 종목 3년 치 재무가 공백이 되는 비용 |
| currency gate | KRW 아닌 응답은 삽입 skip + 실패 표면화 | **채택** — 격리와 병행, 재발 봉인 |

복원이 기술적으로 불가능한 건 아니다. 안 하기로 한 거다. 조회 서비스가 원본에 없는 숫자를 만들어 보여주는 것보다 "데이터 없음"이 정직하고, 왜곡값이 노출 중인 상황에선 빈 값이 명백히 낫다. 제대로 지원하려면 환율 파이프라인과 통화 병기 UI까지 가야 해서 백로그로 뒀다(X22).

격리 전에 NULL이 안전하게 렌더되는지 소비 경로를 전수 확인했다. 파생 계산은 전부 null 가드가 있어 Q4 역산도 null로 전파되고, TTM EPS는 연간 fallback까지 비면 "데이터 없음"으로, 셀은 formatter가 "—"를 낸다. 미대응 경로 0건 확인 후 정정을 실행했다.

## F6 — bigint 경로 점검

#036에서 bigint 직렬화 후처리를 lib/db.ts에 넣고 financials 경로만 검증한 채 남겨뒀던 항목. 이번에 전수로 닫았는데 결과는 허무할 정도로 깨끗했다. `neon()` import가 db.ts 한 곳뿐이라 모든 쿼리가 래퍼를 통과하고, 집계(COUNT→int8)·윈도우(LAG→numeric) 반환값도 같은 OID 범주로 처리된다. 문자열 산술 위험 지점 0건. 타입 표기 하나(`shares: bigint | null` — 런타임은 이미 number)만 맞춰 정정하고 종결했다.

## 정리

- **F37** — cron 트리거를 GitHub schedule에서 cron-job.org dispatch로 이관. daily 16:00 정시 발화·해외 분봉 30분 정연 실측. schedule fallback 제거만 잔여
- **B10·B13** — 부풀림 원인을 collector에서 DART 원본(XBRL unit 오태그)으로 재판정. 의심 23건 전수 판별 → 확정 11행 정정, 실제 급변 11건 보존, 삽입 게이트로 재발 봉인
- **241560** — 표시통화 KRW→USD 전환 종목. 환율 복원 대신 NULL 격리 + currency gate
- **F6** — bigint 산술 경로 전수 안전 확인, 종결

일지가 세 자릿수에 들어섰다. 내용은 기념보다 마감에 가까웠는데 — 트리거는 밖으로 꺼내 정시를 잡았고, 데이터는 "틀린 값을 고치고, 다음 틀린 값은 못 들어오게" 닫았다. 이번 세션으로 데이터 sweep이 사실상 정리되면서 남은 활성 트랙이 UI·리팩토링·제출물로 좁혀졌다. 이제부터는 눈에 보이는 것들의 차례다.
