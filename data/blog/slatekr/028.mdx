사실은 훨씬 일찍 했어야 하는데, 손에 걸리는 게 만하서 미뤄오다가 지난 중간 점검을 계기로 바로 다음 작업에서 배포를 하기로 했다.

그래서 이전 프로젝트에서 했던 것처럼 당연하게 EC2로 배포를 준비하려고 이것 저것 조금 알아보다가, 몇 가지 의문이 생기고 고민 끝에 **Vercel과 Neon DB**로 배포를 진행하기로 결정하게 되었다.

---

## EC2가 정말 적합할까?

원래 계획은 EC2에 Next.js, MySQL, Python collector를 전부 올리는 거였다. 블로그에서도 여러 번 언급했고, collector cron 스크립트도 EC2 기준으로 작성하려 했었다.

근데 막상 배포 시점이 되니 고민이 되었다. EC2로 배포하면, 유감스럽게도 사용자는 거의 없겠지만, 유지만으로도 비용이 꽤 발생한다. 추정하기로는 대략 1만 ~ 3만 정도. 물론 취업과 포트폴리오를 위해 충분히 지불할 수 있는 금액이긴 하나, 과거 실수로 요금 폭탄을 맞을 뻔한 적도 있고 다른 대안이 정말 없는가? 하는 의문이 생겼다.

일단 한 발 물러서 생각해봤다. SlateKR은 프론트엔드 포트폴리오 프로젝트다. EC2에 서버를 직접 올려서 보여줄 수 있는 건 DevOps 역량인데, 이 프로젝트가 증명하려는 게 그건 아니다. Next.js니까 Vercel, serverless DB니까 Neon — **도구를 용도에 맞게 고르는 판단**이 오히려 더 적확할 수 있겠다는 생각에 도달했다.

다른 프로젝트(AimTest)는 곧 프리티어 만료 때문에 Neon 마이그레이션이 예정돼 있었다. 두 프로젝트 인프라를 Vercel + Neon으로 통일하면 관리 포인트도 줄어든다. Vercel Hobby는 무료, Neon Launch 플랜 월 \$5. 합쳐서 월 5달러. 합리적인 비용이다. 단순히 돈이 아까워서가 아니다.

## MySQL에서 PostgreSQL로

DB 엔진을 바꾸는 거니까 작업이 좀 있었다.

#### (1) 드라이버 교체
`mysql2`를 빼고 `@neondatabase/serverless`를 넣었다. Neon의 serverless 드라이버는 HTTP/WebSocket 기반이라 Vercel의 serverless 환경에서 TCP 소켓 문제가 없다.

#### (2) neon 호환 래퍼 구현
db.ts에서 `neon()`을 감싸는 호환 래퍼를 만들었다. 기존 코드가 전부 `const [rows] = await pool.query(...)` 패턴이었는데, 이 인터페이스를 유지하도록 래퍼가 `[rows, null]`을 반환하게 했다. 덕분에 나머지 lib/ 파일들에서는 SQL 문법 차이만 고치면 됐다.

#### (3) 쿼리 수정
쿼리 수정은 기계적인 작업이었다. placeholder `?`가 `$1, $2`로 바뀌고, `ON DUPLICATE KEY UPDATE`가 `ON CONFLICT DO UPDATE SET`으로 바뀌고, `is_active = 1`이 `is_active = true`로 바뀌는 정도. DB를 직접 조회하는 lib/ 파일이 5개였는데, 패턴이 반복적이라 Claude Code에 맡겼다.

#### (4) 스키마 전환
스키마 전환도 큰 건 없었다. `AUTO_INCREMENT`가 `BIGSERIAL`로, `tinyint(1)`이 `BOOLEAN`으로, `enum`이 `TEXT + CHECK`로 바뀌는 정도. 테이블 구조 자체는 그대로 유지했다.

## 데이터 이관

`daily_prices`가 614만 row인데, 이걸 한 번에 옮기긴 크다. 우선 `stocks`, `financial_statements`, `disclosure_summaries` 세 테이블만 옮겼다. MySQL Workbench에서 CSV로 뽑고, Python 스크립트로 Neon에 밀어넣는 방식.

삽질이 두 개 있었다. Workbench가 뽑은 CSV의 구분자가 콤마가 아니라 세미콜론이었고, 인코딩이 UTF-8이 아니라 CP949였다. 둘 다 스크립트에서 옵션 한 줄씩 고치면 되는 거라 금방 해결됐지만, 확인 안 하고 돌렸으면 한참 헤맸을 거다.

`npm run dev`를 돌려봤다. 차트와 가격 관련 데이터는 비어있지만, 종목 검색, 재무 요약, 공시 목록까지 정상 동작했다.

## 남은 작업

daily_prices 614만 row 이관이 남아있다. row 단위 INSERT로는 시간이 오래 걸리니까 bulk import 방식을 써야 한다. 매일 데이터를 수집하는 collector 스크립트들도 아직 MySQL 기준이라 PostgreSQL로 전환해야 하고, 그 다음이 Vercel 배포. 다음 세션에서 마무리할 계획이다.

## 정리

#027에서 "다음은 EC2 배포"라고 썼는데, 한 발 더 생각한 결과 EC2 자체를 버렸다. 초기에 EC2 단일 인스턴스로 계획한 건 MVP 단계에서 가장 단순한 구성이었고, 배포 시점에 비용과 목적을 다시 따져보니 더 맞는 조합이 보인 거다.

설계를 초기에 전부 확정할 순 없다는 사실은 아마 이전 이번 개발기간 중 깨달았던 바가 있는데, 이번데 다시금 실감했다. 하지만 그럼에도 내가 더 꼼꼼하지 못했다는 사실은 아쉬울 따름이다.
