이렇게 금방 다시 돌아올 줄은 몰랐다. 분명 직전 글에서 개발을 일단락하고 제출 전 코드 작업은 없다고 확인한 상태였는데, 서류에 반영할 소재를 검토하면서 README를 한 번 더 검증했다. 채용 실무진이 서류를 보는 순서 그대로 저장소 첫 화면 → README → 라이브 → 코드 → 검증 명령을 훑는 점검이다. 아홉 건이 나왔고, 그중 둘은 README「한눈에 보기」의 "부분 실패 UI" 주장과 직접 어긋났다.

결국 일주일도 안돼서 로드맵을 다시 열어 코드 쪽 다섯 건을 이번 세션에 닫았고, 지수 페이지 레이아웃 이동과 README 보정 · 태그는 다음 세션으로 남겼다.

## 리뷰어 순서로 훑은 결과

지금까지의 자가 검토는 README 문장이 코드에서 참인지를 보는 대조였다(#175 · #183). 이번 점검은 방향이 반대다. 라이브를 Playwright로 끝까지 한 번 돌면서 route 하나를 끊어 보고, 잘못된 URL을 넣어 보고, JS 없이 받은 HTML의 메타 태그를 읽는다. README가 말하지 않는 자리에서 걸리는 것이 나온다.

| 발견 | 판정 |
|---|---|
| 시세 route가 응답 없이 실패하면 헤더 가격 자리가 스켈레톤으로 남고 배지가 없음 | **구현.** 응답 없는 실패를 실패 플래그 응답과 같은 경로로(F134) |
| 분봉 route가 응답 없이 실패하면 "당일 인트라데이 데이터 없음" 문구 — empty와 error 구분이 무너짐 | **구현.** 같은 항목(F134) |
| `?ticker=abc`가 200 빈 응답 | **구현.** 형식 검증만, 형식이 맞는 미존재 종목은 그대로(F136) |
| canonical · og:url · og:image 없음, 종목 외 페이지 og:title이 전부 "SlateKR" | **구현.** root 상속 + 정적 OG 이미지(F135), base URL 코드 fallback 동반(F132) |
| 지수 페이지 모바일 CLS 0.52(3회 중 2회) | **다음 세션.** PSI로 재현 확인 뒤 착수(F137) |
| 차트 · 지수 페이지 HTML 586 · 634KB, 장중 지수 분봉 폴링 분당 104KB | 한계에 적음. 압축 전 수치는 재측정 뒤(backlog) |
| 한 화면에 현재가가 둘 — 헤더의 라이브 값과 52주 레인지의 저장 종가 | **구현.** "종가 기준" 캡션, 소형 정리 묶음(F133)에 |
| velog 링크 15개 중 절반이 504 | 수용. 해외 접속은 전부 200, velog 한국 쪽 간헐 |
| About 오타 · topics · LICENSE 없음 · create-next-app 기본 SVG 잔존 | 설정 · 정리, 같은 묶음(F133) |

기준은 셋이다. README 주장과 어긋나는 것은 고치고, 측정 가능한 한계는 고치거나 조건과 함께 적고, 이미 한계에 적힌 것은 둔다. 이 기준으로 가르니 `use cache` 이행이나 velog 미러처럼 크기만 큰 항목이 빠지고 두 세션 분량이 남았다. 면접에서 곤란한 건 결함이 아니라 "몰랐다"는 답이라는 생각으로, 목표는 결함 0이 아니라 모르는 결함 0이다.

## 응답 없는 실패가 빠져 있던 부분 실패 UI

실시간 시세의 실패 처리는 #076에서 정했다. route가 실패해도 500 대신 200에 `failed: true`를 실어 보내고 컴포넌트가 그 플래그로 분기한다. 500으로 올리면 TanStack Query의 자동 재시도가 방금 지운 캐시를 다시 두드리고, 잠깐의 시세 실패를 HTTP 에러로 올리는 건 층위가 안 맞는다는 이유였다. 그 설계에서 `isError`는 처음부터 고려 대상이 아니었다. 그런데 요청 자체가 막히거나 5xx가 오면 응답이 없으니 플래그도 없다. 헤더의 스켈레톤 게이트는 "세션 정보가 아직 없음"을 보는데 응답이 없으면 그 상태가 영원하고, 분봉은 플래그가 없으니 빈 배열과 같은 분기로 떨어진다.

### 새 상태를 만들지 않는다

| 후보 | 판정 |
|---|---|
| 전송 실패 상태를 하나 더 두고 헤더 · 분봉에 분기 추가 | 기각. 라벨 · 배지 · 통계 행의 순수 함수에 입력 축이 하나 늘고, 상태 넷(loading · empty · error · 부분 실패)이 다섯이 됨 |
| 응답 없는 실패를 실패 플래그 응답과 같은 입력으로 수렴 | **채택.** session은 클라이언트 시계로 대체, live는 null, failed는 true. 순수 함수는 무변경 |

헤더는 스켈레톤 게이트를 통과시켜 서버 렌더 가격과 저장 행 통계를 그대로 두고 "일시 지연" 배지만 얹는다. 분봉은 재시도 UI로 보낸다. 결과로 응답 없는 실패의 라벨에는 시각이 붙지 않는다("정규장"뿐, 플래그 응답은 "정규장 · 19:35:02"). 데이터가 없으니 시각도 없는 게 맞다고 봤다.

### isError가 아닌 이유

처음엔 훅의 `isError`를 실패 축에 합치면 끝이라고 봤다. query-core를 읽어 보니 data가 없는 쿼리는 refetch에 들어갈 때 status가 pending으로 되돌아가 `isError`가 풀린다. 응답이 계속 없는 동안에는 60초 폴링과 포커스 복귀마다 스켈레톤이 깜빡였을 것이다 그래서 상태 대신 시각을 비교했다.

```ts
// 응답 없이 실패한 쿼리는 refetch가 시작되면 pending으로 돌아가 isError가 풀린다.
// "마지막 실패가 마지막 성공보다 늦다"는 refetch 중에도 유지된다.
const transportFailed = queryEnabled && errorUpdatedAt > dataUpdatedAt;
const isFailedQuote = (data?.failed ?? false) || transportFailed;
```

분봉은 `||`로 합치지 않았다. 직전 정상 응답이 있는 폴링 실패까지 재시도 UI로 넘어가 "직전 정상본 유지"가 깨지기 때문이다. 응답이 있으면 응답의 플래그, 없을 때만 `isError`다. 로컬 프로덕션 빌드에서 route를 끊고 · 풀고 · 플래그 응답으로 바꿔 넣는 세 경우를 종목 둘, 탭 셋으로 확인했다.

## route 입력 검증은 형식만

점검은 `?ticker=000000`이 200 빈 응답인 것을 런타임 검증의 공백으로 짚었다. 그런데 000000은 여섯 자리라 형식 검증을 통과하는 값이고, 형식이 맞는 미존재 종목이 "데이터 없음"으로 오는 건 맞는 상태다. 400으로 바꾸려면 route마다 DB 조회가 붙는다. 그래서 요약 route가 쓰던 티커 스키마를 시세 · 분봉 route에 적용해 `abc`와 누락만 400으로 막고, 미존재 종목은 그대로 두었다.

## 메타데이터 상속과 OG 이미지

```
전  metadataBase만 선언 · canonical · og:url · og:image 없음 · 종목 외 페이지 og:title "SlateKR"
후  root: metadataBase + title template + canonical 상속 · og:image 1장(파일 컨벤션)
    openGraph를 재선언하는 세그먼트(종목 layout · 지수 page)만 url · type 재기입
    /stocks/indices?index= 는 title이 다르므로 canonical에 파라미터 포함, /ranking?tab · /search?q 는 기본 경로
    sitemap lastmod(빌드 시각) · twitter summary_large_image
```

걸린 건 Next의 metadata 병합이 키 단위 얕은 병합이라는 점이다. 종목 layout이 `openGraph`를 통째로 다시 선언하고 있어 root의 og:url과 파일 컨벤션 이미지가 그 아래에서 사라졌다. url과 type을 다시 적고 이미지는 부모 결과에서 잇는 걸로 풀었다. sitemap에 탭 URL 셋은 넣지 않았다. 2,650개가 10,600개가 되고 요약 페이지가 대표이며, 탭은 각자 canonical을 가지면 된다.

OG 이미지는 1200×630 뷰포트를 그대로 찍으면 홈의「주요 지수」가 그날 시세와 "정규장 마감 · 10.21 15:30"을 달고 들어온다. 정적 이미지라 다음 날부터 틀린 값이 영구히 남는다. 홈 미리보기가 날짜와 가격을 두지 않는 원칙과 같은 이유로 히어로만 담았다.

## 지수 페이지 CLS와 점수 읽기

점검에서 헤드리스로 잰 지수 페이지 모바일 CLS 0.52는 README 성능 표에 없던 페이지라 PSI로 다시 쟀다.

| 회차 | 성능 | LCP | CLS |
|---|---|---|---|
| 1 | 75 | 5.2s | 0.001 |
| 2 | 58 | 5.0s | 0.439 |
| 3 | 56 | 5.4s | 0.439 |

점수 차는 전부 CLS다. 모바일 점수에서 CLS 비중이 25%라 0.439면 그 몫이 거의 0이 되고, 1회차의 75가 이 페이지 본래 점수로 README의 홈 70 · 종목 상세 76과 같은 급이다. 값이 0.001 아니면 0.439로 양봉인 게 단서다. 높이 불일치면 매번 같은 값이 나와야 하니 타이밍에 걸린 이동이고, 홈에서 겪은 `scrollIntoView`가 페이지를 세로로 밀던 문제(#178)와 같은 종류가 아닐까 싶다. 다음 세션의 첫 probe다(F137).

### 점수가 낮은 이유

이쯤에서 점수가 낮은 게 받는 데이터가 많아서 어쩔 수 없는 것인지 한 번 더 생각했다. 그렇지 않다. 원인은 이미 식별돼 있다 — Lighthouse 시뮬레이션 추정(실제 스로틀에서는 LCP가 FCP와 같은 1.5초, #180), 첫 화면 전 JS, 렌더링 차단 CSS 둘, 한글 웹폰트, 종목 상세의 요청당 외부 API 대기. 데이터 양이 걸리는 건 지수 페이지의 RSC 페이로드 하나뿐이다. "데이터가 많아서"는 면접에서 약한 답이고, 정확한 답은 README 한계 절과 같다.

## 소형 정리

미사용 prop 넷, create-next-app 기본 SVG 다섯, 순위 표에서 시장을 못 찾은 행의 빈칸, 수동 matchMedia를 공용 훅으로 바꾼 것은 한 커밋으로 묶었다. 전체 기간 차트 가격축에 0과 −40,000 눈금이 찍히던 건 주 가격축 하단 25%를 거래량 몫으로 비워 두어 가격 범위가 넓으면 그 여백이 음수 가격대로 매핑되는 것이었고, 0 이하 눈금을 빈 문자열로 가렸다. 거래량을 별도 pane으로 분리하는 근본 해법은 차트 컴포넌트를 분해할 때(F129) 같이 본다.

## 정리

- **F134 구현** — 응답 없는 실패를 실패 플래그 응답과 같은 경로로. 헤더는 SSR 가격 + "일시 지연", 분봉은 재시도 UI, 직전 정상본 유지. 판정은 `isError`가 아니라 `errorUpdatedAt > dataUpdatedAt`
- **F136 구현** — 시세 · 분봉 route에 티커 형식 검증. 형식이 맞는 미존재 종목은 그대로
- **F135 · F132 구현** — canonical · og 상속 · 정적 OG 이미지(히어로만) · sitemap lastmod · base URL fallback
- **F133 종결** — 소형 정리 묶음. 공시 응답 타입 union 하나는 backlog
- **F137 신설** — 지수 페이지 모바일 CLS 0.439, 양봉. 다음 세션
- **리뷰어 순서 점검 — 발견 9** — 구현 5 · 한계 2 · 수용 2. 기준은 README 주장과 어긋나는가
- **회고 글 보류** — 작업 방식 회고는 방식이 멈춘 뒤에. 개발을 더 잇지 않기로 하거나 구직이 끝난 뒤

제출 전 코드 작업이 없다고 두 번 적은 뒤에 두 건이 나왔다. 엄밀히는 README가 거짓이었다기보다 README가 말하지 않은 층(요청이 아예 닿지 않는 경우)에서 깨진 것이지만, 리뷰어는 바로 그 자리를 본다. 같은 눈으로 반복하는 재검토로는 안 나왔을 것이고, 다른 역할의 순서를 한 번 빌리는 게 종결 조건에 들어가야 한다는 걸 이번에 알았다.
