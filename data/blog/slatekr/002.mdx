프로젝트 초기 세팅을 마치고 나서 가장 먼저 부딪힌 문제는 "국내 상장 종목의 가격과 재무 데이터를 어디서 가져올 것인가"였다.

기획 단계에서는 "DART API로 공시 데이터를 가져오고, 주가는 open API를 쓰면 되겠지"라고 생각했다. 하지만 막상 찾아보니 생각보다 간단하지 않았다. 좀 더 꼼꼼히 확인해야 했다.

## DART OpenAPI — 공시 데이터 확보

금융감독원의 DART(전자공시시스템)는 Open API를 제공한다. API 키 발급도 간단하고, 기업 기본정보(`company`), 공시 목록(`list`), 재무제표(`fnlttSinglAcntAll`) 등을 JSON으로 받을 수 있다.

테스트 삼아 삼성전자(005930)의 최근 공시 목록을 조회해봤다.

```bash
GET https://opendart.fss.or.kr/api/list.json?crtfc_key=MY_KEY&corp_code=00126380&bgn_de=20250101&end_de=20251231
```

응답은 깔끔했다. 공시 제목, 접수일자, 보고서 링크 등이 모두 들어있었고, 이걸 기반으로 "최근 공시" 섹션을 만들 수 있겠다는 확신이 들었다.

재무제표도 확인했다. `fnlttSinglAcntAll`로 연결/개별 재무제표를 받을 수 있고, EPS(기본주당이익), 자본총계 같은 값도 포함되어 있었다.

DART는 문제없었다. 문제는 주가 데이터였다.

## 주가 데이터 소스 찾기

국내 상장 종목의 일봉 OHLCV(시가/고가/저가/종가/거래량) 데이터를 제공하는 무료 Open API는 거의 없었다.

### KRX OpenAPI
한국거래소(KRX)도 OpenAPI를 제공하지만, 일별 시장 통계 중심이었다. 개별 종목의 일봉 차트를 그릴 수 있는 형태가 아니었고, 승인 절차도 필요했다. 실시간성도 떨어졌다.

### 유료 API (Twelve Data, Styvio 등)
KRX 데이터를 제공하는 유료 API도 있었지만, 월 \$70~\$99 수준이었다. 포트폴리오 프로젝트에 이 비용을 지불하는 건 부담스러웠다.

### Yahoo Finance API
해외 종목은 괜찮지만, 국내 종목 데이터는 불안정했다. KRX 종목 코드 형식도 다르고, 일부 종목은 아예 조회가 안 됐다.

결국엔 지속성을 위해 "무료로 안정적으로 국내 주식 데이터를 가져올 방법"을 찾아야 했다.

## pykrx — Python 라이브러리로 방향 전환

여러 자료를 찾아보다가 `pykrx`라는 Python 라이브러리를 발견했다.

**pykrx란?**
- KRX와 Naver 금융에서 주식 데이터를 스크래핑하는 오픈소스 라이브러리
- OHLCV, 시가총액, PER/PBR, 배당수익률 등 제공
- 종목 코드 + 날짜 범위로 일봉 데이터 조회 가능
- 무료, `pip install pykrx`로 바로 설치 가능

테스트 삼아 삼성전자 최근 1개월 데이터를 가져와봤다.

```python
from pykrx import stock

df = stock.get_market_ohlcv("20240301", "20240331", "005930")
print(df)
```

결과는 완벽했다. 시가/고가/저가/종가/거래량이 DataFrame으로 깔끔하게 나왔다. 이걸 MySQL에 적재하면 Next.js에서 차트 데이터로 쓸 수 있겠다는 생각이 들었다.

## 문제 발생 — 2월 이후 데이터 공백

이제 됐다 싶었는데, 추가 테스트를 하는 과정에서 큰 문제가 발생했다.

pykrx로 시가총액, PER, PBR을 가져오는 함수도 테스트했다.

```python
from pykrx import stock

# 시가총액
cap = stock.get_market_cap("20240301", "20240331", "005930")

# PER/PBR/배당수익률
fundamental = stock.get_market_fundamental("20240301", "20240331", "005930")
```

그런데 2025년 2월 이후 데이터를 조회하면 **빈 DataFrame**이 반환됐다.

원인을 찾아보니, KRX 내부 데이터 구조가 2월에 변경되면서 pykrx의 일부 스크래핑 로직이 깨진 것으로 보였다. OHLCV는 정상 동작했지만, 시가총액/PER/PBR 같은 파생 지표는 받아올 수 없었다.

"pykrx를 쓸 수 없는 건가?" 싶었지만, 곧 다른 방법을 떠올렸다.

## DART + pykrx 조합 — 재무제표와 주가를 직접 계산

필요한 지표 중 핵심은 PER/PBR 같은 기본 지표였다.
그러나 PER/PBR 계산은 사실 어렵지 않다. 다음과 같이 계산된다.

```
PER = 주가 ÷ EPS
PBR = 주가 ÷ BPS
```

- **EPS(주당순이익)**: DART 재무제표에 "기본주당이익"으로 제공됨
- **BPS(주당순자산)**: 자본총계 ÷ 발행주식수로 계산 가능
- **주가**: pykrx로 최신 종가 조회 가능

결론적으로 pykrx에서 PER/PBR을 직접 받지 못해도,
DART 재무제표와 pykrx 주가를 조합하면 **직접 계산할 수 있다**.

### 왜 이게 합리적인가

1. **재무 지표는 분기/반기 단위로만 바뀐다**  
   EPS, BPS는 실적 발표 시점에만 갱신된다. 매일 바뀌지 않는다.

2. **주가는 매일 바뀐다**  
   하지만 pykrx로 최신 종가를 가져올 수 있다.

3. **조합하면 실시간에 가까운 PER/PBR 계산 가능**  
   DART에서 분기별 EPS/BPS를 캐싱해두고, pykrx 최신 주가만 조합하면 된다.

## 최종 데이터 아키텍처

pykrx로 데이터를 가져오는 건 확정했지만,
"Next.js에서 매번 pykrx를 호출할 순 없다"는 문제가 남았다.
pykrx는 스크래핑 기반이라 응답 속도가 느리고,
매 요청마다 호출하면 KRX/Naver 쪽에 부하를 줄 수 있다.

그래서 **데이터를 미리 받아서 DB에 저장해두고, Next.js는 DB에서 조회만 하는 구조**로 결정했다.

### MySQL을 선택한 이유

- 일봉 데이터는 정형 데이터 (종목코드, 날짜, OHLCV)
- 5년치 전체 데이터도 300~500MB 수준으로 작음
- 날짜 범위 조회, 종목별 필터링 같은 쿼리가 빈번함
- RDB가 적합한 구조

### 배포 구조

AWS EC2 t2.micro 1대에 Next.js + MySQL을 함께 운영하기로 했다.  
RDS를 쓰면 비용이 추가되지만, EC2에 MySQL을 직접 설치하면 프리티어 기간엔 무료고, 이후에도 월 \$13~15 수준이다.

Python cron 스크립트가 매일 오후 4~5시경 pykrx로 당일 데이터를 받아서 MySQL에 적재하고, Next.js는 DB를 조회해서 응답한다.

구체적인 DB 스키마 설계와 적재 스크립트 구현은 다음 단계에서 다룰 예정이다.


### 데이터 아키텍쳐
```
[pykrx]
  ↓ 매일 장 마감 후 cron 실행
  ↓ OHLCV 적재
[MySQL]
  ↑ 종목 기본 정보
  ↑ 일봉 가격 데이터
  ↑ DART 재무제표 캐싱 (분기별)
  ↓ 
[Next.js]
  ↓ lib/ 정규화 레이어
  ↓ DART EPS/BPS + pykrx 최신 주가 → PER/PBR 계산
[UI]
```

### 데이터 소스별 역할

| 데이터 | 소스 | 갱신 주기 | 비고 |
|--------|------|----------|------|
| OHLCV | pykrx | 매일 장 마감 후 | cron 스크립트 |
| EPS/BPS | DART | 분기별 | 재무제표 캐싱 |
| 최신 주가 | pykrx | 필요 시 조회 | revalidate 3600초 |
| PER/PBR | 계산 | 서버에서 조합 | DART + pykrx |
| 공시 목록 | DART | 1시간 | revalidate 3600초 |

## 변화가 느린 데이터 vs 빠르게 바뀌는 데이터

이 과정에서 확인한 건 **"모든 데이터를 실시간으로 가져올 필요는 없다"**는 것이다.

- **느리게 바뀌는 데이터 (EPS/BPS)**: DB에 캐싱하고 분기별 갱신
- **빠르게 바뀌는 데이터 (주가)**: 필요 시 조회, 1시간 revalidate
- **조합 계산 (PER/PBR)**: 서버에서 처리, 클라이언트는 결과만 받음

처음엔 "PER/PBR을 외부 API에서 받아야 한다"고 생각했지만, 실제로는 **재무제표와 주가를 조합하면 충분했다**. 오히려 이 방식이 데이터 출처를 명확히 하고, 갱신 주기도 제어할 수 있어서 더 안정적이었다.

## 아직 해결하지 않은 질문들

현재 확정된 건 데이터 소스와 조합 방향이다.  
하지만 실제 구현 단계에서 결정해야 할 것들이 남아있다:

- **EPS/BPS 캐싱 주기**: 분기별로 DART API를 호출할지, 수동 갱신할지
- **pykrx 호출 방식**: cron으로만 적재할지, 실시간 요청도 허용할지
- **섹션별 fallback**: 차트 데이터가 없을 때, 재무 데이터가 없을 때 어떻게 보여줄지

이 질문들은 **실제 데이터를 저장해 사용자 시나리오를 확인한 뒤** 결정하려 한다.  
지금 단계에서 모든 걸 확정하는 건 오히려 변경 비용만 키울 수 있다고 판단했다.
