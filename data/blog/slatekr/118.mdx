이번엔 계획대로 F49다. #037에서 empty와 error를 갈랐는데, 그 사이 화면이 실시간 폴링·SSR fallback·스켈레톤이 얽힌 구조로 커지면서 이번엔 loading과 empty의 경계가 문제가 됐다. 홈 지수 미니 차트에서 "장중 데이터 없음"이 로딩 완료 직전에 순간 스쳐가는 플래시를 계속 봐왔고, 스켈레톤과 실제 렌더가 어긋나 점프하는 구간도 산발적으로 의심됐다. 이번 세션은 이걸 전수조사로 한 번에 터는 작업이다.

세션 초입 이월 관측 두 건은 빠르게 정리됐다 — 어제 16시 run의 지수 08-21 재적재 verify green, 다우 quote도 이상 없음. 본작업으로 들어갔다.

## 전수조사 — 세 축

조사 축은 세 개로 잡았다.

| 축 | 대상 | 결과 |
|---|---|---|
| A | 'empty' 분기가 로딩 중에 노출될 수 있는 경로 | 17건 중 **발생 확정 1건** |
| B | 스켈레톤 ↔ 실제 렌더 구조 대조 | 14건 중 불일치 판정 5건 |

A축 17건 중 13건은 loading 가드가 이미 완전했다. #037 이후 empty 처리에 isLoading 이중 조건을 습관처럼 넣어온 게 대부분의 화면을 지키고 있었던 셈이다. 뚫린 곳은 정확히 한 곳이었다.

## 플래시의 진짜 위치

처음 지목된 용의자는 IndexSlate였는데, 확인해보니 IndexSlate 자체는 `isLoading || !data` 가드가 완전했다. 진짜 원인은 한 층 아래에 있었다.

홈 지수 슬레이트는 quote와 intraday를 **별개 훅**으로 받는다. 부모 스켈레톤은 quote 기준으로 걷히는데, 자식 IndexMiniChart는 intraday의 bars를 기다린다. quote가 먼저 도착하는 전형적인 순간(수백 ms), 슬레이트는 표시되고 미니 차트 자리만 `bars.length === 0` 분기로 떨어져 "장중 데이터 없음"이 스친다.

수정 위치에 선택지가 있었다.

| 안 | 내용 | 판단 |
|---|---|---|
| 부모 가드 확장 | 스켈레톤 조건을 quote+intraday OR로 | quote가 와도 슬레이트 전체가 스켈레톤에 잡힘 — 표시 지연 부작용 |
| 자식 국소 처리 | 미니 차트에 isLoading을 내려 3단 분기 | 슬레이트는 즉시, 차트 자리만 placeholder |

자식 쪽으로 갔다. 렌더가 loading / empty·failed / 데이터 3단으로 갈린다.

```tsx
if (isLoading && bars.length === 0) return <PulsePlaceholder />;
if (bars.length === 0) return failed ? <FailedText /> : <EmptyText />;
return <Chart bars={bars} />;
```

두 훅의 로딩을 병합하는 공용 훅도 떠올랐지만, 사용처가 한 곳이라 접었다. 세 번째 사용처가 나오기 전엔 추출을 고려하지 않는다.

## 스켈레톤 다섯 건, 실제로는 세 건

B축 불일치 판정 5건을 수정하러 들어갔는데, 파일을 다시 열어보니 두 건(차트 동적 로딩 높이, 관심종목 행 반응형 축)은 **이미 정합**이었다. 조사 단계의 스냅샷이 오래됐거나 인접 파일과 혼동한 것으로 보인다. 재무 스켈레톤도 조사에선 13행이라 했는데 실측은 14행이었다. 조사 보고를 수정 근거로 삼기 전에 원본을 다시 확인하는 절차를 이번에 명시적으로 두었는데, 세 군데서 값을 걸러냈으니 제 몫을 했다.

실수정 3건은 전부 라우트 loading이 실제 페이지 구조를 반영하지 않는 유형이었다.

- **종목 오버뷰** — 스켈레톤이 차트 한 칸만 그림 → 실제 4섹션 그리드로 재작성
- **지수 페이지** — 차트 하나만 그림 → rail + detail pane 이중 그리드와 모바일 order 반전까지 반영
- **재무 탭** — 4행 고정 → compact 6행 / full 14행 분기

스켈레톤을 실제 컴포넌트 안에서 export해 공존시키는 구조 개편안도 있었지만 기각했다. 지금 필요한 건 치수와 구조의 일치이지 구조 개편이 아니고, 이 판단은 세션 내내 스코프를 지키는 기준이 됐다.

C축(해외 지수 라벨이 quote 첫 응답에 한 번 교체되는 건)은 원인 시퀀스만 확정하고 분리했다. SSR은 daily 날짜로, 클라이언트는 quote 체결시각으로 라벨을 계산하는 소스 불일치가 원인인데, "데이터 없음" 오표시가 아니라 정확한 라벨이 더 정확한 라벨로 갱신되는 문제라 심각도가 다르다. 설계 결정(SSR 잠정 라벨 유지 vs quote 스냅샷을 SSR에서 같이 로드해 소스 통일)이 걸려 있어 F57로 등록했다.

## 빈 화면에 이유를 달기

여력이 남아 E54까지 갔다. #117에서 아남전자 228행을 격리한 뒤 재무 화면이 전부 "—"가 됐고, 이게 데이터 누락으로 읽히는 문제다.

판정 방식부터 정했다. "값이 전부 NULL이면 안내" 같은 데이터 형상 추론은 비KRW 격리와 단순 미수집을 구분하지 못해 배제하고, collector의 known 13종 frozenset을 웹 상수로 미러링하는 명시적 목록 판정으로 갔다. DB에 통화 컬럼을 두는 안도 있었지만, X22 방향이 미정인 상태에서 0.5% 문제에 스키마를 늘리는 건 과했다. 13종에 변경 빈도도 낮아 양방향 참조 주석으로 동기화 비용을 흡수했다.

1차 구현은 기존 empty 문구 자리에 한 줄을 넣는 것으로 끝냈는데, 막상 띄워보니 좀 엉성했다. 설명문 한 줄이 섹션을 통째로 대체하니 오히려 임시방편처럼 보이고, 재무 요약 패널은 그리드 높이만큼 공백이 떴다.

구조를 세 줄로 나눴다. 각 줄이 다른 역할을 맡는다.

| 역할 | 내용 |
|---|---|
| 제목 (상태) | 재무 데이터 제공 제한 |
| 본문 (원인) | 원화가 아닌 통화(**USD**)로 공시해 재무 기반 지표를 확인할 수 없어요 |
| 경계 (범위) | 가격·거래량·공시 정보는 정상 제공돼요 |

문구를 다듬으며 두 가지가 정리됐다. "제공하지 않아요"보다 "제한" 쪽 뉘앙스로 가고 싶었는데, 섹션 안에서만 보면 재무는 제한이 아니라 전무라서, 이 표현은 종목 수준 서술 — 즉 경계 줄과 세트일 때만 정확하다. 그리고 통화는 "원화가 아닌 통화"로 뭉개지 않고 티커별 실측값(USD·CNY)을 그대로 박았다. #117에서 전수 실측해둔 값이 그대로 표시층 재료가 됐다.

경계 줄을 넣을지도 실측으로 판정했다. 핵심 지표 밴드 높이가 원본 132px 기준 경계 포함 115px(-17), 생략 94px(-38) — 포함 쪽이 리듬 손실이 적고, "오류가 아니라 정상 상태"라는 정보 가치도 경계 줄이 만든다.

![](/static/images/velog/6aadedc8-c80c-4dd5-8b6e-a66b32ff4421-image.png)


이 작업을 하다 보니 KIS 폴백 생각이 다시 올라왔다. gate에 걸린 종목만 KIS 재무로 채우면 빈 화면 자체가 사라지지 않나. 근데 이건 #117에서 기각한 자동 폴백 그대로다 — 출처 표시 없이 원본과 벤더 가공값이 섞인다. 욕구는 유효하니 X22 착수 시 "명시적 소스 결정 + 화면 출처 표시"를 전제로 한 구현 후보로 승격만 해뒀다. 그 전까지 이 층의 일은 왜 비어 있는지 정직하게 말하는 것까지다.

## 정리

- **F49 종결** — 로딩 플래시 전수 17건 중 실결함 1건(홈 미니 차트) 수정, 스켈레톤 5건 중 실수정 3건 정합, 나머지는 판정 종결. 해외 라벨 교체는 F57로 분리
- **E54 종결** — non-KRW 13종 상수 미러링 + 제목/원인/경계 3단 안내, 티커별 통화 명시
- **커밋 scope 재확립** — 도메인 어휘 복원, web은 횡단 전용으로 강등
- **KIS 재무 조회** — 자동 폴백은 기각 유지, X22 구현 후보로 승격

전수조사가 낸 결론이 "고칠 게 별로 없다"에 가까웠던 세션이다. 17건 중 16건이 이미 방어돼 있었고, 스켈레톤 5건 중 2건은 이미 맞아 있었다. #037에서 세운 상태 구분 원칙이 1년 가까이 화면이 불어나는 동안 대체로 지켜지고 있었다는 확인이기도 해서, 수확이 적은 게 오히려 수확이었다.
