[#024](https://velog.io/@dh82680/SlateKR-024-디자인-트랙-2-페이지에-토큰-적용하기) 마지막에 다음 작업을 분기 데이터 트랙으로 잡아뒀다. 이전 `/styleguide` 인터랙션 데모 작업 후 메모 중 하나가 "재무 요약 expand 표 축 변경 — 행=항목, 열=기간으로 뒤집고 연간/분기 토글 추가"였는데, 이건 분기 데이터가 화면에 들어와야 의미가 사는 작업이었다.

다행히 처음 데이터 적재 시 2021~2025년 5년치 + 분기(Q1~Q3) 데이터를 모두 적재해둬서 꺼내 사용만 하면 되었다. 이번 작업의 핵심은 collector가 아니라 데이터 계층과 슬레이트 자체에 있었다.

---

## 표시 항목 정하기

기존 재무 요약 슬레이트는 최근 3년 연간, 매출/영업이익/당기순이익 3개 항목만 보여주고 있었다. 애초에 MVP 구현 용으로 그렇게 한 거라 지금까진 충분했지만, 역시 이대로는 너무 데이터가 적다. 이번 슬레이트를 시작으로, 다른 것들도 더 채워 나갈 예정이다.

표시 지표를 정하면서 한 가지 기준을 잡았다. **DB에 있는 raw 값과 그것으로 계산 가능한 비율 지표만**. 부채총계, 현금흐름 같은 항목은 DB에 없어서 추가하려면 collector부터 손봐야 했다. 결이 다른 작업이라 별도 트랙으로 미뤘다.

그렇게 12개로 정해졌다.

- raw: 매출, 영업이익, 당기순이익, EPS, BPS, 자산총계, 자본총계
- 파생: 영업이익률, 순이익률, 부채비율, ROE, ROA

확장 패널을 두고 기본 4개만 노출하는 안도 봤다. 다만 12개 정도면 한 화면에 다 띄워도 부담스럽지 않은 수준이라 일단 모두 보이게 했다. 확장 패널은 정보가 더 늘어났을 때 다시 꺼내보기로.

## 정규화 레이어가 책임지게

[#006](https://velog.io/@dh82680/SlateKR-006-Next.js-데이터-계층-설계)에서 lib 계층의 역할을 "DB에서 raw 데이터를 가져오고, UI가 소비하기 좋은 형태로 변환한다"로 잡아뒀었다. 그땐 변환의 내용이 snake_case → camelCase, Date → 문자열 같은 형태 정리 정도였다.

이번엔 책임이 하나 늘었다. 바로 추가할 파생 지표 계산. 영업이익률, 부채비율, ROE 같은 비율을 어디서 만들지 정해야 했다.

lib 안에서 처리하기로 했다. UI 컴포넌트는 도메인 모델만 받는다는 원칙이 있고, 이걸 UI 직전이나 컴포넌트 안으로 흘리면 그 원칙이 흐려진다. 파생 지표 계산 정도는 여기서 하는 편이 적절할 것 같았다.

```ts
export type FinancialPeriod = {
  year: number;
  quarter: number | null;  // null = 연간

  revenue: number | null;
  operatingProfit: number | null;
  netIncome: number | null;
  totalAssets: number | null;
  totalEquity: number | null;
  eps: number | null;
  bps: number | null;

  // 파생 지표 (lib에서 계산)
  operatingMargin: number | null;
  netMargin: number | null;
  debtRatio: number | null;
  roe: number | null;
  roa: number | null;
};

export type StockFinancials = {
  annual: FinancialPeriod[];
  quarterly: FinancialPeriod[];
};
```

기간 별 데이터는 연간과 분기를 한 타입(`FinancialPeriod`)으로 통합하고 `quarter` 필드로 구분했다. 따로 두는 안도 잠깐 봤지만 필드가 거의 같고 UI에서도 같은 행 구조로 표시하니 굳이 나눌 이유가 없었다.

## 데이터-기간 축 변환

#023에서 메모로 남겼던 표 축 변경이 여기서 풀렸다. 기존 슬레이트는 행이 연도, 열이 항목이었다. 항목이 3개일 땐 별 문제가 없었지만 12개로 늘리면 가로로 한참 늘려야 했다.

네이버 증권 재무 표가 행이 지표, 열이 기간 구조로 돼 있다. 기간이 5년이든 8분기든 가로 스크롤로 늘어나는 구조라 항목이 늘어도 화면이 깨지지 않는다. 같은 방향으로 뒤집었다.

연간은 최근 5년, 분기는 최근 4분기 롤링으로 정했다. 분기를 "특정 연도 Q1~Q4"로 묶을지 "최근 4개"로 갈지 잠깐 망설였는데, 분기 탭의 일반적 사용 시나리오가 "최근 흐름 확인"이라 롤링 쪽이 자연스러웠다. 동기 비교(YoY)가 필요하면 어차피 연간 탭으로 보면 된다.

탭 컴포넌트는 shadcn `Tabs`를 그대로 썼다. 키보드 접근성, focus 관리 같은 게 무료로 따라오는데 굳이 직접 만들 이유가 없었다.

## 남은 디테일

새 지표들을 추가하고, 레이아웃을 수정해 큰 줄기는 잡혔지만, 만들고 보니 아직 마무리해야 할 디테일이 남아 있다.

#### (1) 기간 정렬 방향

현재는 좌측에 최신 기간이 오도록 정렬되어 있다.
하지만 시간 흐름을 직관적으로 읽으려면 좌측에서 우측으로 갈수록 최신 기간이 오도록 배치하는 편이 자연스럽다.

```txt
현재:   최신 ← 과거
개선:   과거 → 최신
```

따라서 기간 컬럼 정렬 방향을 반대로 조정할 예정이다.

#### (2) 단위 표기 방식

현재는 각 셀마다 `억원`, `원`, `%` 단위가 함께 표시된다.

```txt
1,234억원
5,670원
12.3%
```

값 자체는 명확하지만, 테이블 전체로 보면 단위가 반복되면서 시각적 노이즈가 커진다.
단위는 컬럼 헤더나 별도 안내 영역으로 분리하고, 셀에는 숫자만 남기는 방향이 더 깔끔해 보인다.

```txt
매출액(억원) | EPS(원) | 영업이익률(%)
1,234       | 5,670   | 12.3
```

#### (3) 음수 색상 처리

현재 음수 값에 별도 색상이 적용되어 있지 않다.

재무 테이블에서는 손실, 감소, 마이너스 지표를 빠르게 인지할 수 있어야 하므로 음수 값은 빨간색으로 처리하는 편이 좋다.
단, 모든 음수를 무조건 부정적으로 해석할 수는 없으므로 색상은 “경고”라기보다 “값의 방향성 표시”에 가깝게 사용하는 것이 적절하다.

#### (4) BPS 누락

BPS는 모든 셀이 비어 있다.

확인해보니 분기 row의 `bps` 컬럼이 `NULL`로 들어가고 있었다.
PBR/BPS도 파생 지표로서 계산하는 것으로 [#006](https://velog.io/@dh82680/SlateKR-008-종목-상세-페이지-구현)시점에 결정했었는데, 언젠가부터 안 보이고 있었다.
이 것까지 다음 디테일 수정 작업에서 고쳐보려고 한다.

## 다음 작업

다음 작업은 다시 디자인 트랙 3으로 돌아간다.

우선 위에서 정리한 디테일을 마무리할 예정이다.

- 기간 정렬 방향 조정
- 단위 표기 방식 개선
- 음수 색상 처리
- BPS 누락 원인 분리

그 다음에는 상세 페이지 전체 구조를 다시 볼 생각이다.

현재 상세 페이지는 차트, 재무, 공시가 세로로 길게 이어지는 구조다. 초기에는 단순하고 구현하기 쉬운 방식이지만, 정보가 늘어날수록 스크롤 부담이 커진다.

그래서 네이버 증권처럼 헤더 아래에 가로 nav를 두고, 각 정보를 탭으로 전환하는 구조를 검토하고 있다.

```txt
[종목 헤더]

[차트] [재무] [공시] [뉴스] ...

선택된 섹션만 표시
```

다만 탭 구조로 바꾸면 SEO 처리 방식도 함께 고민해야 한다.

가능한 선택지는 크게 세 가지다.

#### 선택지 1. 모든 섹션을 한 번에 SSR하고 클라이언트에서 토글하기

모든 데이터를 서버에서 렌더링한 뒤, 화면에서는 탭으로 보여줄 섹션만 전환하는 방식이다.

SEO 관점에서는 가장 단순하지만, 초기 HTML과 데이터 양이 커질 수 있다.

#### 선택지 2. 섹션별 라우트 분리하기

차트, 재무, 공시를 각각 별도 URL로 나누는 방식이다.

```txt
/stocks/005930
/stocks/005930/financials
/stocks/005930/disclosures
```

SEO와 공유 가능성은 좋아지지만, 상세 페이지의 구조가 다소 복잡해진다.

#### 선택지 3. Parallel Routes 검토하기

Next.js App Router의 Parallel Routes를 활용해 상세 페이지 내부 섹션을 더 구조적으로 분리하는 방식이다.

구조적으로는 매력적이지만, 현재 프로젝트 규모에서 과한 선택일 수 있다.

---

결국 핵심은 “사용자 경험을 위해 탭 UI를 도입할 것인가”가 아니라, 탭 UI를 도입했을 때 **URL 구조, SSR 범위, SEO, 데이터 로딩 전략을 어떻게 함께 설계할 것인가**다.

이 결정은 단순한 디자인 수정이 아니라 상세 페이지 구조를 다시 잡는 작업에 가깝다.

그래서 다음 작업에서 우선 놓친 디테일과 버그를 수정하고, 디자인과 렌더링 방시 결정은 그 다음에 진행할 생각이다.
