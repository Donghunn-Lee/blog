이번 세션은 이력서와 포트폴리오를 쓰는 자리로 잡아 두었다. 그런데 직전 세션을 마무리한 뒤 저장소를 복제해 코드까지 읽는 평가를 한 번 돌렸다. 프론트엔드 리드가 서류를 보고 면접 대비 지점을 짚는 역할로, 1단계는 README와 배포본만 보는 콜드 리딩, 2단계는 코드 대조, 3단계는 예상 질문이다. 프로젝트 지침 파일은 일부러 지우고 돌렸다.

판정은 대체로 괜찮았지만 지적이 열 건 넘게 나왔고, 그중 README 주장과 코드가 어긋난다는 세 건은 제출 전에 봐야 했다. 그래서 이력서는 다음 세션으로 미루고 지적을 하나씩 대조했다.

추가로 미뤄 둔 세션 외 확인 작업들도 일괄 착수했는데, daily 검증 단계가 일주일째 red인 원인이 드러나, 세션은 수집기 쪽 처리까지 이어졌다.

## 평가 지적의 사실 대조

지적을 고치기 전에 코드와 README 원문으로 하나씩 확인했다. 기준은 제출 전 규칙 그대로다. 몇 분 안에 보이는가, README 주장과 어긋나는가.

| 지적 | 판정 |
|---|---|
| 페이지 단위 client 컴포넌트가 있다(관심종목 · 순위) | **README 정정.** page 파일은 전부 Server Component이고, 데이터가 브라우저 스토어 · 폴링에 있는 두 화면은 본문이 client 하나. 문장이 그 사실을 말하도록 고침 |
| 검색 드롭다운에 combobox 역할이 없어 스크린리더가 활성 옵션을 모름 | **구현.** README의 "키보드 탐색"은 사실이라 과장이 아니었지만, 파일 하나 열두 줄로 참의 범위를 넓힐 수 있어 문구 후퇴 대신 구현 |
| 차트 축이 같은 분기점 훅을 쓴다는 문장 | **README 정정.** 홈 지수 미니차트만 해당. 종목 차트는 다른 훅으로 높이만 바꿈 |
| 픽스처 196건 | **README 정정.** 타입 선언 줄까지 센 값. 배열 항목은 193, 실제 단언은 191 |
| 지수 캐시 TTL이 래퍼 생성 시점에 고정 | **구현.** 정산 창에 만든 60초 래퍼가 세션이 바뀔 때까지 재사용되던 비용 결함. revalidate 값을 캐시 키에 포함 |
| 동기화 훅 2벌 · route 5개 동형 복사 | 조치 불요. 세 번째 사용처가 생길 때 추상화한다는 지침의 결정. 지침 없이 읽으면 결함으로 보인다는 점은 면접 설명 소재 |
| 모바일 홈의 '맨 위로' 버튼이 '전체 보기'를 가림 | 조치 불요. 스크롤 중 잠깐 겹치는 건 플로팅 버튼의 본질이고, 맨 아래 정지 상태에서는 305px 이상 떨어짐 |

combobox가 이 표에서 유일하게 판정이 바뀐 건이다. 평가는 과장이라 했지만 README 문장을 다시 읽으니 키보드 탐색만 주장하고 있었고, 스크린리더 지원은 별개의 공백이었다. 과장이면 문구를 후퇴시키고 미구현이면 구현하는 게 맞는데, 이번엔 후자가 파일 하나 안에서 끝나는 크기였다. input에 combobox 역할과 열림 상태 · 활성 옵션 id를 붙이고 옵션마다 id를 주는 것으로, 새 상태는 없고 레이아웃도 그대로다.

## README 정정 네 문장과 각주 줄

README 쪽은 문장 네 개를 고친 것이 전부다. 평가가 "27KB로 길고 절마다 링크가 서너 개"라고도 했는데, 훑는 독자에게 README 뒷부분은 읽는 곳이 아니라 건너뛰는 곳이라 요구 조건은 짧은가가 아니라 건너뛰기 쉬운가다. 그 기준으로 다시 보니 거슬리는 건 분량이 아니라 절 끝의 "코드: … · 글: …" 줄이었다. 참고 링크 줄이 본문과 같은 크기라 문단처럼 읽힌다.

```
전  코드: session-cache.ts · index-quotes/route.ts · 글: #075 … · #140 … · #155 … · #174 …   ← 본문 16px 한 줄
후  <sub>코드 · session-cache.ts · index-quotes/route.ts</sub>                              ← 12px
    <sub>글 · #075 … · #140 … · #155 … · #174 …</sub>
```

그 줄 다섯 개를 `<sub>`로 감싸 두 줄로 나눴다. 링크를 절 끝으로 모으거나 앵커를 번호로 줄이는 안도 있었지만, 결정 옆에 붙은 글 링크가 사라지면 어느 결정의 기록이 어느 글인지 매핑이 없어져 기각했다. 사실 이 결론 전에 README를 읽지 않고 쓴 수정안 두 개가 전제부터 틀려 되돌린 일이 있었다. 링크는 이미 절 끝에 모여 있었고 파이프라인 절은 이미 표였다.

## 세션 외 확인 열두 항목

세션 사이에 쌓인 확인 항목이 열두 개였다. 제출 전에 닫을 것과 제출과 무관한 것으로 나눠 읽기 전용으로 한 번에 돌렸다.

| 항목 | 결과 |
|---|---|
| GitHub README 렌더(표 라벨 · 모바일 이미지 · 각주) | 이상 없음 |
| 배포본 라이트 · 다크(마크 · 탭 바 아이콘 · 스타일가이드 색 값 · 파비콘) | 이상 없음, 콘솔 오류 0 |
| 직전 글에서 고친 장중 헤더 값(F131) | 거래량 · 기준일 · 시가총액 모두 오늘 값, NXT 탭 거래량이 KRX 탭보다 작음 |
| 공개 저장소의 KIS 키 이력 | 0줄 |
| probe 산출물 정리 준비 | 보존 파일이 지울 파일을 읽는 교차 의존 발견 |
| 신규 상장 종목 편입 | 편입됨, 상장일 봉 1개 결손(정상 상태) → 보충 |
| 재무 탭 분기 PER | 연간 2025와 분기 Q4 모두 18.15 |
| sitemap · robots | **전부 localhost** |
| 최신 weekly · daily run | weekly는 DART 응답이 zip이 아니어서 red, daily는 일주일째 red |

sitemap은 코드가 아니라 설정이었다. 사이트 주소를 환경 변수에서 읽고 없으면 localhost로 떨어지는 fallback인데 배포 환경에 그 변수가 처음부터 없었다. robots.txt에 `Sitemap: http://localhost:3000/sitemap.xml`이 그대로 박혀 있었으니 README의 SEO 서술(sitemap 2,650개 · generateMetadata)이 동작하지 않던 상태였고, 주소창에 치면 바로 보이는 것이라 제출 전 항목으로 올렸다. 변수를 넣고 재배포해 끝났다. 빌드 시 값이 박히는 변수라 저장만으로는 안 바뀐다. 코드 fallback을 배포 플랫폼이 주는 주소로 보강하는 일은 backlog(F132)에 두었다.

이 확인에서 바뀐 판정이 하나 더 있다.

- **probe 산출물 보존 기준** — 지울 파일을 보존 파일이 읽는 의존이 나와 보존을 늘리려다, 왜 보존하는지를 다시 물음. 전부 gitignore라 포트폴리오에 영향이 없고, 문서화된 절차(README 재촬영 · 성능 재측정 · 아이콘 재생성)가 경로를 부르는 열한 개만 남김

## 일주일째 red였던 daily 검증 단계

daily 적재 뒤에 도는 검증 단계는 확인한 최근 일주일 내내 red였다. 원인은 기업행위 미처리 23건이었다. 기준가가 전일 봉 범위를 벗어나면 기업행위로 잡아 검증 단계를 실패시키는 규칙은 #172에서 만든 것이고, 그때 이벤트가 잦아 거의 매일 실패할 수 있다고 적어 두었으니 red 자체는 예정된 것이었다. 처리 절차는 둘로 갈린다. KIS가 과거 봉을 조정하지 않은 건이면 예외 목록에 상수로 등록하면 되고, 조정한 건이면 수정주가를 다시 적재하고 9월 14일 이후 행을 배율로 rescale해야 한다. 상수 등록이면 금방 끝나는 일이라 분포부터 확인했다.

| 분류 | 건수 | 처리 |
|---|---|---|
| KIS가 조정함(액면병합 9 · 액면분할 1 · 권리락 2 · 감자 1 · 미확인 3) | 16 | 재적재 + rescale 232행 |
| KIS가 조정하지 않음 | 0 | 상수 등록 — 해당 없음 |
| 기업행위 아님, 10월 6일 봉 결손 | 11 | 봉 보충 |

기대와 반대였다. 상수로 끝나는 건이 하나도 없었고, 열한 건은 기업행위가 아니었다. 10월 6일 적재에서 KIS 멀티시세 호출 하나가 연결이 끊겼고, 스크립트는 재시도 없이 그 청크 30종목을 건너뛰었다. 그 30종목은 다음 날 기준가를 '직전 봉'과 비교할 때 비교 대상이 10월 2일 봉이 되어, 범위를 벗어난 11종목이 기업행위로 잡힌 것이다. 나머지 19종목은 그냥 비어 있었다.

```
10/06 20:32  KIS 멀티시세 호출 68/89 연결 끊김(Connection aborted) → 청크 30종목 skip → 이 run은 red
10/07 20:12  행 수 2,621/2,651은 검증 기준 90%를 통과
             30종목의 '직전 봉' = 10/02 봉 → 기준가가 범위 밖인 11종목이 기업행위 의심
10/08 ~ 12   기업행위 16건과 함께 미처리로 누적, 매일 red
```

### 결손이 엿새 동안 안 보인 이유

10월 6일 run은 청크 실패 때문에도 red였고 로그에는 그 청크를 건너뛴 줄이 찍혀 있었다. 그런데 기업행위로 매일 red인 상태라 로그를 열어 보지 않았다. 다음 날부터는 검증 단계가 행 수를 보고도 통과했는데, 기준이 직전 거래일 행 수의 90%라 2,621/2,651은 OK였기 때문이다. 거래정지 종목의 스킵을 흡수하려고 넓게 잡은 값인데 그날 스킵은 0이었다. 게이트가 있어도 기준이 느슨하면 못 잡는 건 weekly가 조용히 green이던 때(#170)와 같은 종류다.

그리고 빠진 봉을 뒤늦게 채우는 자동 경로가 없다.

| 경로 | 판정 |
|---|---|
| daily 적재의 과거 봉 룩백 | 없음. 그날 20시 시세로 그날 봉만 씀 |
| KIS 일봉 API로 과거 봉 | 쓰지 않음. 다음 날 정규장 정의로 정정된 값이 와서 저장 축인 20시 캔들과 다름(#159) |
| pykrx | 수동 백필 전용. 일부 종목에서 대량매매가 빠져 시세와 어긋나므로 자동으로 섞지 않음 |

그래서 처방은 자동 채움이 아니라 둘이었다.

1. **빈틈을 안 만든다** — 연결이 끊긴 종류의 예외에 한해 2초 뒤 한 번 재시도. 타임아웃이나 KIS 오류 응답은 별개의 결함(F63)이라 그대로
2. **생기면 그날 밤 보이게 한다** — 행 수 90% 대신 '행이 없는 활성 종목이 3을 넘으면 FAIL', 빠진 종목 코드를 로그에. 3은 최근 열 거래일 결손 분포(10월 6일을 빼면 최대 1)에 거래정지 몫 2를 더한 값

### 16건 rescale과 결손 보충

처리는 절차대로였다. 결손 30종목은 pykrx로 10월 6일 봉을 보충했고, 거래정지 종목 하나는 pykrx가 고가 · 저가를 0으로 줘서 넣으면 새 오탐이 생기기에 비워 두었다. 16건은 수정주가를 다시 적재한 뒤 재적재 전후 9월 11일 종가의 비로 배율을 정했고, 전건이 기대 배율(2 · 5 · 10 · 0.2 · 0.667 · 0.817 · 11.097) ±0.04% 안이었다. 거래량 나누기는 구간에 실거래가 있는 여섯 블록만 적용했다.

rescale은 블록마다 트랜잭션으로 돌렸다. 사전 조회가 기대값과 같을 때만 UPDATE하고 영향 행 수가 맞으면 COMMIT, 아니면 ROLLBACK이다. 16블록 전부 COMMIT이었고, 다시 돌린 검증 단계는 미처리 0건 · 결손 1건(거래정지, 허용 안)으로 통과했다. 권리락 중 1.5배 무상증자 한 건은 2배 미만이라 주식수 비율 판정에 안 걸리는 종류(#172에서 수용한 한계)여서 권리락일 상수로 따로 등록했다. 상수 등록 0건이라는 결과는 지침의 "감자는 KIS가 조정하지 않는다"는 가정과도 어긋났는데, 감자 1건이 조정된 것으로 계산돼 주석 두 곳을 고쳤다.

## 정리

- **평가 지적 트리아지 종결** — README 정정 3문장 · 구현 2건(검색 combobox · 지수 캐시 키에 revalidate) · 조치 불요 2건. 과장 판정은 README 문장 기준으로 다시 읽음
- **README v10.2** — 사실 정정 4문장과 절 끝 참고 줄 `<sub>` 각주화. 링크 자리 · 문장 · 순서 불변
- **sitemap · robots 복구** — 배포 환경 변수 누락으로 localhost였던 것을 설정으로 해결. 코드 fallback 보강은 backlog(F132)
- **daily 검증 단계 red 해소** — 기업행위 16건 재적재 + rescale 232행, 10월 6일 결손 29종목 보충. 상수 등록은 0건, 1.5배 무상증자 1건은 권리락일 상수
- **재발 방지 구현** — 청크 연결 끊김 1회 재시도, 결손 기준을 90% 바닥에서 '활성 종목 − 행 수 > 3'으로
- **probe 보존 기준 축소** — 문서화된 절차가 부르는 11개만

이력서를 쓰려던 세션이 평가 대조와 수집기 처리로 끝났다. 평가를 마무리 직후에 돌려 범위를 다시 연 것과 세션 외 항목을 열두 개까지 쌓아 둔 것, 둘 다 세션 안에서 처리했으면 이렇게 길어지지 않았을 일이다. 30종목 결손은 매일 뜨던 red에 묻혀 있다가 기업행위 오탐 덕에 드러난 셈이라, 엄밀히는 검증 단계가 잡은 게 아니라 다른 기준이 잘못 울린 거지만 그 red가 고마운 쪽에 가깝다.
