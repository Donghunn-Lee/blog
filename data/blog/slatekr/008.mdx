종목 상세 페이지에서 사용하기 위해 `lib/` 에 함수들을 설계했었다. 이제 실제로 페이지를 구현하며 연결할 차례였다.

---

## 섹션을 어떻게 나눌 것인가

종목 상세 페이지에 들어갈 것들을 먼저 정리했다. 상단 요약 헤더, 차트, 핵심 지표, 재무 요약, 최근 공시. 다섯 섹션이다.

페이지에서 데이터를 한꺼번에 받아서 각 섹션에 props로 내려주는 구조가 가장 먼저 떠올랐다.
그런데 그렇게 하면 가장 느린 섹션이 끝날 때까지 페이지 전체가 기다려야 한다.
DART 공시 API가 느리면 가격 데이터도 같이 묶이는 셈이다.

데이터를 한꺼번에 받는 것이 아니라, 각 섹션을 독립적으로 fetch하고 Suspense로 감싸면 처리가 빠른 것부터 순서대로 보인다. fallback으로 각 섹션의 스켈레톤 UI를 등록해 UX를 보장하도록 했다.

섹션 하나가 실패해도 나머지는 영향을 받지 않는다. 이 구조가 맞다고 봤다.

```
<Suspense fallback={<HeaderSkeleton />}>
  <StockHeader ticker={ticker} />
</Suspense>
<Suspense fallback={<ChartSkeleton />}>
  <StockChartSection ticker={ticker} />
</Suspense>
// ...
```

## 에러 처리

이전에 진행했던 프로젝트들에선, 에러처리는 최소한만 보장했다. UI를 띄우거나 로그를 찍는 식.
하지만 보다 실무적인 개발을 하려면 각종 에러 처리, 특히 데이터와 관련된 에러는 철저하게 핸들링 해야 한다고 생각해서 이번엔 좀 더 신경쓰기로 했다.

Error Boundary를 쓰는 방법도 있었다.
그런데 Error Boundary는 클라이언트 컴포넌트에서만 동작해서 서버 컴포넌트의 에러를 잡지 못한다.

그래서 컴포넌트 내부에 try/catch를 사용해 직관적으로 에러를 처리했다. 오류가 나면 빈 상태 UI를 보여준다는 의도가 코드에서도 바로 읽힌다.

```typescript
try {
  [price, financial] = await Promise.all([
    getLatestPrice(ticker),
    getLatestFinancial(ticker),
  ]);
} catch {
  // DB 오류 시 빈 데이터로 폴백
}
```

섹션마다 이 패턴이 반복된다. 한 섹션의 DB 오류나 API 타임아웃이 옆 섹션까지 전파되선 안 될 일이기 때문이다.

## StockChartSection 래퍼

`StockChart.tsx`는 `use client`가 필요하다.
차트 구현에 사용한 lightweight-charts 라이브러리가 DOM에 직접 붙는 라이브러리라서 브라우저 환경이 필요하기 때문이다. 하지만 데이터는 서버에서 가져와야 한다.

그래서 `StockChartSection.tsx`를 서버 컴포넌트 래퍼로 뒀다.
서버에서 DB 조회 → 직렬화 가능한 props로 변환 → 클라이언트 컴포넌트에 전달.
이렇게 되면 차트 렌더링 로직은 클라이언트에만 있고, 데이터 레이어는 서버에만 있다.

## PER/PBR 계산

DB에 PER/PBR을 저장할 수도 있었다.
근데 DB에 저장된 값은 공시 시점 기준이다. 주가가 매일 바뀌니까 어제 저장한 PER은 오늘 주가와 맞지 않는다.

그래서 현재가와 EPS/BPS를 조합해서 그 시점에 계산한다.
`PER = 현재가 / EPS`, `PBR = 현재가 / BPS`.
EPS가 0 이하면 의미가 없으니 `-`로 표시한다.

데이터 아키텍처 단계에서 내린 결정이었는데, 실제로 구현하면서 그 이유가 더 명확해졌다.

## React.cache()

`generateMetadata`와 페이지 컴포넌트 둘 다 `getStockByTicker`를 호출한다.
같은 요청 안에서 DB를 두 번 조회하는 셈이다.

Next.js의 fetch는 같은 인자로 요청하는 경우 값을 캐싱해주는데,
내 mysql2, DB의 데이터 요청의 경우엔 적용되지 않는다. 그래서 `React.cache()`로 직접 감쌌다.
덕분에 동일 요청 범위 안에서 두 번째 호출은 DB를 다시 건드리지 않는다.

## 공시 섹션

공시 데이터는 DB에 저장하지 않고 DART API를 직접 호출한다.
공시는 실시간성이 중요한데, 하루에도 여러 건이 올라온다.
DB에 저장하면 적재 주기 사이의 공시를 놓칠 수 있어서 캐싱만 하는 방향으로 갔다.
`fetch`에 `next: { revalidate: 3600 }`을 걸어서 1시간 단위로 갱신한다.

외부 API 응답 검증 도구로 Zod를 처음 사용해보았다.
`safeParse`를 쓴 건 검증 실패가 예외가 아니라 빈 배열 반환으로 이어지도록 하기 위해서다.
DART API가 응답 구조를 바꾸거나 타임아웃이 나도 공시 섹션만 비고, 나머지 페이지는 영향을 받지 않는다.
