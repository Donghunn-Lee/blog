직전 글에서 채용 실무진이 볼 법한 순서로 README를 점검해 아홉 건을 찾았고, 그중 코드 쪽 다섯 건을 닫았다. 남은 건 지수 페이지의 모바일 레이아웃 이동, README 보정, 수정본에 대한 2차 점검, 그리고 이력서가 가리킬 커밋을 고정하는 태그였다.

앞의 셋은 계획대로 닫혔고 태그는 달지 않았다. README를 한 번 더 손볼 생각이라 그 뒤로 미뤘다. 대신 2차 점검이 새 문제 1순위로 꼽은 것이 수집 워크플로우의 daily run이 나흘 연속 red인 상태였고, 그동안 수동으로 두기로 했던 기업행위 재적재(F119)를 이 세션에서 반자동으로 구현했다.

## 2차 점검 — 지적 해소

처음 보는 실무진 역할로 같은 순서를 한 번 더 돌리되, 보고는 "지난 지적 → 지금" 표로 시작하고 라이브가 최신 커밋인지부터 확인하게 했다. 판정은 통과라기엔 거창하고, 긍정적이었다.

| 지난 지적 | 지금 |
|---|---|
| 시세 · 분봉 route가 응답 없이 실패하면 스켈레톤 고정 · empty 오표시 | 해결. 요청 차단 · 500 모두 서버 렌더 가격 유지, 분봉은 재시도 UI |
| 잘못된 티커에 200 | 해결. `abc` · 7자리 · 누락은 400, 형식이 맞는 미존재 종목은 그대로 |
| canonical · og · OG 이미지 · sitemap lastmod 없음 | 해결. 전 페이지 canonical, 1200×630 PNG, 2,648건 lastmod |
| 지수 페이지 모바일 CLS 0.44 | 해결. 0.001(아래) |
| About · topics · LICENSE | About 재작성 · topics 10개. LICENSE 추가 |
| README 누락 다섯 | 전부 반영 |

새로 걸린 넷 중 셋은 작았다. 종목 404 페이지의 탭 제목과 본문 제목이 다른 것, 순위 · 공시 표가 클라이언트에서 그려지며 푸터를 미는 데스크톱 CLS, 종목 외 페이지의 description이 전부 루트 공통 문장인 것. 마지막 하나만 바로 고쳤고 둘은 backlog로 보냈다. 넷째가 이 글의 본론이다. 점검은 코드를 열기 전에 저장소 Actions 탭을 먼저 보는데, 거기에 daily run의 빨간 실행이 나흘째 줄지어 있었다.

## 매일 red로 남던 기업행위 검증

### 두고 보기로 했던 상태

기준가가 전일 봉 범위를 벗어나면 기업행위로 잡아 검증 단계를 실패시키는 규칙은 #172에서 만든 것이다. 그때부터 "기업행위가 있는 날은 red가 뜨는 게 정상 운영 상태"라고 두었고, #183에서 16건을 수동으로 처리하며 절차를 세운 뒤 #184에서 한 건을 10분에 끝내면서 수동으로 충분하다고 적었다. 자동화는 주 3회 이상 red가 다시 나오면 생각하기로 한 backlog였다.

그런데 다른 건 전부 초록인데 이것만 매주 빨갛게 찍히는 게 점점 신경이 쓰였다. 10월 19일부터 22일까지 나흘 연속 red였고, 앞의 사흘 일곱 건은 그 사이 수동으로 처리했지만 22일에 또 한 건(5:1 병합)이 걸렸다. 2차 점검이 이걸 1순위로 짚자 계산이 달라졌다. 이벤트는 주 1회꼴이고 서류를 낸 뒤 면접까지 몇 주를 쓴다면, 그 기간 내내 Actions 탭이 빨간 저장소를 보여주는 셈이다. 태그를 하루 늦추는 비용보다 그쪽이 컸다.

### 어디까지 기계화되는가

자동화를 미뤘던 이유는 "prod DB를 스크립트가 고치게 둘 것인가"였지 기술적 난도가 아니었다. 지금까지 처리한 18건의 절차가 전부 같았기 때문이다.

| 단계 | 기계화 |
|---|---|
| 감지(기준가 ∉ 전일 봉 범위) | 검증 단계가 이미 함 |
| KIS 수정주가로 9월 11일 이전 재적재 | 스크립트 있음 |
| 배율 = 재적재 전후 9월 11일 종가의 비, 기대 배율 ±1% 검증 | 수식 |
| 9월 14일 이후 행 rescale SQL 생성 · 블록별 검증 적용 | 세 번 같은 절차로 했으니 스크립트화 가능 |
| DART 공시로 사건 종류 대조 | 사람. 다만 판단 입력이 아니라 확인이었음 |
| 비율이 안 맞는 케이스 판정 | 사람 — 자동화하지 않고 red로 남기면 됨 |

사람이 남는 두 줄이 곧 설계였다. DART 대조는 자동 경로에서 빼고, 조건이 하나라도 어긋나면 적용하지 않고 지금과 같은 수동 상태로 떨어뜨린다. 완전 자동이 아니라 게이트를 통과한 건만 처리하는 반자동이고, 통과 조건을 좁게 잡으면 틀린 적용은 생기지 않는다.

### 게이트

probe로 기존 코드를 읽으니 초안의 전제 둘이 먼저 깨졌다. 검증 단계의 감지 결과가 로그 문자열뿐이라 다음 단계가 읽을 수 없었고, "배율이 기대값 ±1%"라는 검사는 실거래 종목에 맞지 않았다. 저장 종가가 20시 애프터마켓 종가라 전일 종가와 기준가 사이에 기업행위가 없어도 드리프트가 있다. 그래서 감지를 함수로 떼어 두 단계가 공유하게 했고, 비율 검사는 배율이 `기준가 ÷ 전일 고가`와 `기준가 ÷ 전일 저가` 사이에 1틱 여유로 들어오는지로 바꿨다. 거래정지 종목은 고가와 저가가 같아 ±1%와 같은 검사가 된다.

적용 조건은 전부 AND다.

- KIS가 과거 봉을 조정한 건(kis_adj=1)
- 종목당 미처리가 한 줄 — 사건 둘이 겹치면 배율이 곱이라 한 구간으로 표현할 수 없음
- 재적재 전 KIS 1콜로 구한 배율과 재적재 계획에서 나온 배율이 같음
- 위의 사건 비율 검사
- rescale 구간의 종가가 한 축 — 중간에 다른 축으로 채워진 행이 있으면 배율이 두 번 들어감
- 전일 고가 · 저가가 0이 아님, 9월 11일 행이 있음, 사건일이 최근 5거래일 안, 한 run에 5건 이하

게이트가 가르지 못하는 것도 둘 남는다.

- **장기 거래정지 뒤 감자 · 유상증자가 겹친 종목** — 수치 게이트 전부 통과. 수동 처리 때도 같은 결과였으므로 수용
- **배율이 1에 가까운 권리락** — "한 축" 검사가 평범한 등락까지 걸어 수동으로 떨어짐. 안전한 쪽의 오탐, 첫 거절 사례 뒤 재검토

### 한 트랜잭션, 처리 기록 테이블, 워크플로우 위치

```
수동 절차  스냅샷 → 재적재 → 배율 → SQL 생성 → 블록별 트랜잭션 적용 → 검증 재실행
자동 경로  감지 → 게이트(전부 쓰기 전) → 재적재 + rescale + 처리 기록 INSERT를 한 트랜잭션 → 검증
           거절 · 실패 → 그 종목만 미적용, run은 red, SQL · 스냅샷을 artifact로
```

배율을 쓰기 없는 재적재 계획에서 먼저 구하니 게이트가 전부 쓰기 전에 끝났고, 재적재와 rescale을 한 트랜잭션에 묶자 "재적재만 되고 rescale은 안 된" 반쪽 상태가 구조적으로 생기지 않게 됐다. 적용은 행 잠금 뒤 계획과 대조하고, 영향 행 수와 사후 1틱 검사가 맞을 때만 COMMIT이다. 강제 적용 플래그는 두지 않았다.

| 후보 | 판정 |
|---|---|
| 검증 실패 뒤에 처리 step을 두고 검증을 한 번 더 | 기각. 실패 사유를 문자열로 파싱해야 하고 집계 게이트가 "복구됨"을 봐주는 로직이 필요 |
| **지수 적재 뒤 · 검증 앞에 처리 step** | **채택.** 감지 함수를 공유하면 검증은 한 번, 거절 건이 있을 때만 red |

rescale SQL을 어떻게 남길지도 갈렸다. 지금까지는 파일을 저장소에 커밋해 DB를 바꾼 근거를 git에 남겼다. run이 직접 커밋하면 secret을 가진 job에 쓰기 권한이 가고 커밋 승인도 건너뛴다. artifact만 두면 90일 뒤 사라지고 수동 커밋을 빠뜨릴 수 있다. 그래서 처리 기록 테이블을 두고 UPDATE와 같은 트랜잭션에 종목 · 사건일 · 배율 · 영향 행 수 · SQL 원문을 기록했다. 파일은 그 기록에서 생성해 커밋하면 되고, 같은 사건을 두 번 적용하지 않는 근거도 이 테이블이 된다. 초기 결정 중 "DB 마이그레이션 자동 실행 도구 없음"에 생긴 첫 예외다.

### 첫 실행

22일에 걸린 종목으로 먼저 로컬에서 돌렸다. dry-run은 구간 24행 · 배율 5.0이었고, 24행 전부 거래정지 구간이라 거래량 블록은 없었다. 실제 실행은 재적재 1,007행과 rescale 24행이 한 트랜잭션으로 COMMIT됐고, 검증 단계는 미처리 0건으로 통과했다. 그날 밤 daily를 다시 돌려 green을 확인했다. 다음 거래일부터는 워크플로우가 직접 처리한다.

## README 정합

### 지수 페이지 CLS

직전 글에서 PSI 3회 중 2회에 0.439가 나와 홈에서 겪은 `scrollIntoView` 문제(#178)와 같은 종류가 아닐까 했다. 아니었다. 칩 스트립에 그 호출이 남아 있긴 했지만 실행 시점에 스트립이 이미 화면 안이라 페이지가 움직이지 않았고, 빈 함수로 바꿔도 값은 그대로였다. 원인은 스켈레톤이 값으로 바뀌는 순간이다. 칩 폭이 96에서 172px로 늘고 가격 행이 7px 올라가는 실제 이동은 작은데, 재사용되는 노드의 display가 block에서 flex로 바뀌면서 이전 위치가 원점으로 잡혀 이동이 크게 집계됐다.

| 조치 | CLS(iPhone 13 · Slow 4G · CPU 4x) |
|---|---|
| 기준 | 0.516 |
| 치수만 값 행과 맞춤 | 0.060 |
| **치수 + display를 값 행과 같게** | **0.001** |

스켈레톤이 값과 같은 자리를 차지하게 하는 것으로 끝냈고, key를 바꿔 노드를 새로 만드는 수법은 불일치를 가릴 뿐이라 쓰지 않았다. 데스크톱 레일의 같은 패턴도 함께 고쳐 0.059가 0.019가 됐다. PSI는 수정 뒤 77 · 82 · 77, CLS 0.001이었다. 엄밀히는 직전 글에서 0.001이 나온 회차를 "본래 점수"로 읽은 게 틀렸던 것 같다. 로컬에서는 매번 0.516이 나왔고, 그 회차는 터치 에뮬레이션이 입력 직후 이동으로 오인해 CLS에서 뺀 것으로 보인다.

태그는 README를 한 번 더 점검한 뒤에 단다. 태그는 커밋 하나를 고정할 뿐 채용 담당자가 보는 README는 main 최신본이라 문구 수정은 그 뒤에도 자유롭지만, 점검 중 코드가 바뀌면 재태그 비용이 생긴다. 미뤄서 잃는 건 없었다.

## 정리

- **F119 구현** — 기업행위 재적재 · rescale을 daily run 안에서 반자동으로. 게이트 전부 통과 시만 한 트랜잭션으로 적용하고 처리 기록 테이블에 남김, 거절은 red와 artifact로 수동 복귀. 첫 건 처리 뒤 daily 초록
- **F137 종결** — 지수 페이지 모바일 CLS 0.516 → 0.001. 원인은 스켈레톤 노드 재사용 시 display 전환, 수정은 스켈레톤을 값과 같은 자리로. 데스크톱 레일 동반
- **README 보정 종결** — 한계 2줄 · 성능 표 지수 행 · 파이프라인 · 로컬 실행 · 수치 줄, description 다섯 페이지, LICENSE, About
- **2차 점검 통과** — 지난 지적 아홉 중 여덟 닫힘, 남은 LICENSE도 직후 추가. 새 발견 중 404 제목 불일치 · 표 푸터 CLS는 backlog
- **태그 이월** — README 점검 뒤에

매일 red가 뜨는 걸 "정상 운영 상태"라고 적어 둔 건 #172 때였고 그 판단은 틀리지 않았다고 생각한다. 다만 그 상태를 두 달 두고 보니 red가 알리는 건 기업행위가 아니라 내가 아직 처리하지 않았다는 사실뿐이었고, 그걸 리뷰어가 코드보다 먼저 보게 된다는 점은 2차 점검 전까지 계산에 없었다.
