README(G1)는 제출물의 본체다. 채용 담당자가 GitHub에서 직접 읽는다는 전제로 써 왔고, 직전 세션에서는 코드와 대조해 틀린 서술을 고쳤다. 다만 그 대조는 쓴 내용이 맞는지를 본 것이어서, 처음 보는 사람이 이 문서에서 무엇을 읽어 가는지는 한 번도 확인한 적이 없었다. 현직자에게 검토를 부탁할 길이 없으니 그 확인은 직접 만들어야 했다.

계획은 README를 처음 읽는 사람 시점으로 검토해 예상 질문을 뽑고, 코드 읽기(G2)를 검색 경로부터 시작하는 것이었다. 코드 읽기는 시작하지 못했다. 검토 결과가 문구 몇 줄로 끝나지 않아 README를 프론트엔드 근거 중심으로 다시 썼고, 그 과정에서 웹 쪽 CI가 없다는 사실과 코드에서 확인할 문제 후보가 따로 나왔다.

## 맥락을 끊은 검토

평소 작업하던 자리에서 README를 검토하면 안 된다고 본 이유는 단순하다. 프로젝트를 아는 쪽은 문서가 설명하지 못한 부분을 알아서 메우기 때문에, 빠진 것이 빠졌다고 보이지 않는다. 그래서 대화 기록도 프로젝트 자료도 닿지 않는 AI 채팅을 따로 열어 README만 붙였고, 스타트업 프론트엔드 리드가 신입 서류를 보는 설정으로 읽게 했다.

```
1패스 (30초)   무엇을 만든 것인지 · 기억에 남는 것 3개 · 계속 읽을지
2패스 (정독)   면접 질문 15개 · 설명 없이는 모를 용어 · 근거가 안 보이는 주장
               과장된 문구 · 있어야 하는데 없는 정보
규칙           칭찬과 수정안 금지, 지적마다 해당 문장 인용
```

첫 결과는 버렸다. 인용된 문장 가운데 직전 세션에 지운 것이 넷이나 섞여 있어서 확인해 보니, 옛 초안 파일을 붙여 넣은 것이었다. 지적마다 문장을 인용하게 한 규칙이 README보다 내 실수를 먼저 잡은 셈이다.

## 지적과 판정

| 지적 묶음 | 판정 |
|---|---|
| **첫 화면**: 기술 스택이 맨 아래 표에만 있음, 주석 처리하다 깨진 링크 줄 노출 | **반영.** 헤더에 스택 배지, 링크 줄 정리 |
| **직무 연결**: 상단 주제가 데이터·캐시 쪽, Suspense · 검색 노출 · 접근성 · 반응형 서술 없음 | **반영(확대).** 코드에서 확인한 프론트엔드 근거를 기존 절에 추가 |
| **근거**: 설계 결정의 링크가 전부 블로그, 코드 링크 0 | **반영.** 결정마다 대표 파일 1~2개 링크 |
| **과장**: "스키마가 강제", "실무에서 더 자주 마주치는" | **반영.** 사실 서술로 낮추거나 삭제 |
| 도메인 용어에 풀이 없음 | 방향 변경. 풀이를 붙이면 시세 서술이 더 길어짐 → 삭제·축약 |
| 문체: 대시 연결, 균일한 단문 | 축소. 반복 구문과 한국어와 겹치는 영어 병기만 수정 |
| 협업 경험 · ERD · 커버리지 수치 없음 | 기각. 1인 프로젝트의 사실이거나 README 범위 밖 |

직무 연결 지적은 반박할 수가 없었다. #156에서 강조 축을 기능에서 설계로 옮겼는데, 그 설계가 캐시와 수집 쪽 말로 쓰여 있어서 프론트엔드 리드에게는 데이터 프로젝트에 화면이 붙은 것으로 읽힐 수 있었다. 종목 상세를 섹션 단위 Suspense로 스트리밍한다는, 이 프로젝트에서 프론트엔드 쪽으로 가장 내세울 만한 구조가 README에는 단어로도 없었다.

용어 풀이는 판정을 한 번 뒤집은 항목이다. 풀이를 붙이면 시세 정의 서술이 그만큼 늘어 위의 지적을 오히려 키우기 때문에, 저장 기준이나 적재 조건 같은 문장은 지우고 풀이는 프론트엔드 쪽 용어에만 남겼다. 순서도 같은 기준으로 바꿨다.

```
전   제목 → 히어로 → 배경 → 화면 → 아키텍처 → 결정 1~4(산문) → … → Tech Stack
후   헤더(스택 배지) → 히어로 → 한눈에 보기 표 → 화면 → 아키텍처
     → 결정 1~4(문제 · 결정 · 코드 링크, 곁가지 서사는 접기) → 품질 → 한계(프론트엔드 먼저)
```

## 코드로 확인되지 않는 문장

다시 쓰기 전에 README에 실을 주장 15항목을 코드에서 먼저 확인했다. 내가 적어 둔 수정 문구도 확인 대상에 넣었는데, 직전 세션에서 그 문구가 일곱 군데 틀렸던 전례가 있어서다. 15항목 가운데 여섯이 정정되고 셋은 확인할 수 없었으며, 수정 문구 쪽도 일곱 군데가 다시 고쳐졌다.

| README 문장 | 확인 결과 |
|---|---|
| "실측에서 15회 중 4회가 HTTP 500" | 확인 불가. 코드와 커밋에 측정 조건 없음 → 수치 삭제 |
| "병목은 KIS가 아니라 함수 호출 수" | 확인 불가 → 삭제 |
| "종목 상세가 4~5개 외부 소스에 의존" | 정정. DB · DART · KIS 셋 |
| "server-wins 단방향 동기화" | 정정. 로드 중에 편집이 있으면 로컬이 이김 → 시점별 네 줄로 |
| "`unstable_cache`는 `null`도 저장하므로 저장 시점에 막을 수 없었고" | 정정. 콜백이 throw하면 저장되지 않음 |
| "커밋 기준: … 전부 green" | 정정. 웹 대상 CI 없음, 로컬 실행뿐 |

"막을 수 없었다"는 초안 때부터 있던 문장이다. Next.js 소스를 열어 보니 콜백이 throw하면 저장 전에 빠져나가므로, 막을 수 없었던 게 아니라 실패를 `null`로 돌려주는 규약을 택한 결과였다. 엄밀히는 틀린 문장이라기보다 내 이해가 거기서 멈춰 있었던 것이고, 그 규약을 왜 유지했는지는 코드 읽기에서 답을 준비해야 할 질문으로 남겼다.

## 웹 CI 추가

README는 커밋마다 타입 검사 · lint · 빌드 · 테스트를 통과시킨다고 적는데, GitHub에서 도는 워크플로우는 수집용 여섯 개뿐이었다. 로컬에서 돌렸는지는 나만 아는 상태였던 것이다.

| 결정 | 판정 |
|---|---|
| 검사 범위 | 타입 검사 · lint · 테스트. 빌드는 DB와 API 키가 필요해 Vercel 배포에 맡김 |
| Node 버전 | 24. 로컬(20)이 아니라 배포 런타임 기준 |
| 커밋 순서 | CI 먼저, README 나중. 문서가 가리키는 대상이 먼저 있어야 함 |

Node 버전을 맞추다 보니 로컬 검사가 그동안 배포와 다른 버전에서 돌고 있었다는 것도 같이 드러났다. 첫 실행은 Node 24에서 57개 파일 1,175건이 통과했다.

## 다시 읽힌 v10

같은 조건으로 v10을 다시 읽혔다. 30초 요약이 "Next.js 16 웹앱"으로 바뀌었고, 표에 적힌 구체적인 주장을 확인하러 본문으로 내려간다고 했다. 앞서 나온 지적은 대부분 사라졌는데, 새로 나온 것들은 문장이 아니라 코드와 화면을 향했다.

| 지적 | 상태 |
|---|---|
| localStorage가 비고 쿠키만 남은 상태에서 서버 목록을 받아 오기 전에 종목을 추가하면, 1개짜리 로컬이 서버 목록을 덮음 | 미재현. 코드의 동기화 순서와는 일치 (F123) |
| 실패 캐시를 무효화하는 호출이 Next.js 16에서는 오래된 값을 한 번 더 서빙할 수 있음 | 미검증 |
| 캡처 속 지수 셀 값과 차트 라벨이 다름 (846.58 / 846.59 등), 콤마 유무도 다름 | 원인 미확인. 0.05까지 벌어진 셀이 있어 반올림이 아니라 시세와 분봉 마지막 봉의 소스 차이로 추정 (E97) |

첫 줄은 좀 뜻밖이었다. 동기화를 "server-wins" 한 단어로 적어 둔 동안에는 나올 수 없던 지적인데, 코드대로 네 줄로 풀어 쓰자 README만 읽은 쪽이 규칙끼리 부딪히는 경우를 찾아냈다. 문구는 소형 수정을 한 번 더 하고(v10.1) 닫았다. 읽는 쪽은 매번 질문 15개를 채우므로 지적이 0이 될 수는 없고, 남은 질문은 고칠 대상이 아니라 답을 준비할 대상이다.

## 코드 읽기 앞에 둔 전수조사

최근 세션에서 되는 줄 알았는데 안 되고 있던 것(동작한 적 없는 revalidate, 멈춰 있던 차트 당일 봉)과 쓰이지 않는 함수가 연달아 나왔다. 코드 읽기에 들어가기 전에 같은 종류를 한 번 훑기로 했다(R9). 컨벤션 점검을 다시 돌리는 건 아니다. #165 이후에 나온 문제는 전부 컨벤션이 아니라 아래 유형이었다.

- **데드코드**: 미사용 파일 · export를 도구 리포트로 확인
- **선언만 있고 효과가 없는 것**: 지난 사고 유형을 체크리스트로 (효과 없는 설정, 어긋난 캐시 키, 실패를 삼키는 catch)
- **일회성 스크립트 정리**: probe 폴더는 git 추적 밖이라 지울 것이 아니라 남길 것을 지정

## 정리

- **G1 v10 반영** — 처음 읽는 사람 시점 검토 2회와 지적 3분류. 헤더 스택 배지 · 한눈에 보기 표 · 결정별 코드 링크, 한계 절은 프론트엔드 5개를 먼저
- **확인 불가 주장 삭제** — 15항목 코드 확인, 정정 6 · 확인 불가 3. "막을 수 없었다"는 Next.js 소스로 반증
- **웹 CI 신설** — 타입 검사 · lint · 테스트, Node는 배포 런타임 24 기준. 첫 실행 1,175건 통과
- **F123 · E97 신설** — 로드 중 편집이 서버 목록을 덮을 가능성, 지수 셀 값과 차트 라벨 불일치. 둘 다 확인 전
- **R9 신설** — 데드코드 · 무효 선언 · probe 폴더 정리. 코드 읽기(G2)는 그 뒤

문서를 다듬는 세션으로 잡았는데 남은 건 CI 하나와 확인할 코드 문제 셋이다. README가 좋아졌다기보다 README가 가리고 있던 것이 줄었다는 쪽이 더 정확한 것 같다. 문장을 코드대로 적을수록 읽는 사람이 구멍을 찾기 쉬워지는데, 그게 문서를 제대로 쓴 값이 아닐까 싶다.
