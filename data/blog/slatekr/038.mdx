## B10 — 1000배 부풀어 있는 매출

#036에서 단위 표기 작업 중 우연히 발견한 게 발단이었다. 일부 종목의 연간 매출이 분기 합 대비 비정상적으로 컸다. 처음엔 회사 측 XBRL filing error일 가능성을 우선 봤다. 중소형 상장사 한 종목(065150 대산F&B)의 2023 연간 매출만 1,000배 부풀어 있고 다른 기간은 멀쩡했기 때문에, 단일 신고의 단위 오기입처럼 보였다.

검증은 DART 공시뷰어로 했다. 사업보고서 연결포괄손익계산서 화면을 열어보니 우측 상단에 `(단위 : 천원)` 표기가 있었다. 공시 자체는 천원 단위로 신고됐고, 우리 DB는 그걸 원 단위로 가정하고 그대로 저장하고 있었다는 뜻이다.

이쯤에서 가설을 갈아엎었다. 회사 filing error가 아니라 collector의 단위 정규화 누락이 맞았다. 코드를 다시 확인해보니 `fetch_financials.py`에 단위 환산 로직 자체가 없었다.

```python
raw = item.get("thstrm_amount", "").replace(",", "").strip()
value = int(raw) if raw else None
```
DART가 주는 문자열에서 쉼표만 떼고 그대로 int로 변환한다. 단위 정보를 받는 흐름이 아예 없는 거다.

그러면 단위 정보는 어디서 받아야 하는지 — API 응답을 직접 떠봤다.

### currency 외에 단위 필드가 없다

`fnlttSinglAcntAll` 응답의 한 row를 보면 필드는 다음과 같다.

```
rcept_no, reprt_code, bsns_year, corp_code, sj_div, sj_nm,
account_id, account_nm, account_detail,
thstrm_nm, thstrm_amount, frmtrm_nm, frmtrm_amount,
bfefrmtrm_nm, bfefrmtrm_amount, ord, currency
```
스케일 정보를 줄 만한 필드는 `currency` 하나인데, 어떤 종목을 호출해도 `"KRW"` 한 값뿐이다. 천원/백만원/원을 구분할 메타데이터가 응답 자체에 없다.

이걸 확인한 시점에서 B10은 즉시 해결할 수 있는 영역이 아니라는 게 분명해졌다. API 응답으로 단위를 판별할 수 없다면 남는 선택지는 (1) DART HTML 보고서를 별도로 파싱해서 "단위: 천원" 텍스트를 수집하거나, (2) 종목별 단위 메타데이터 테이블을 수동으로 유지하거나, (3) 무시하는 것 정도다. 어느 쪽이든 이번 작업에 포함하기엔 복잡해보였다.

### 인지 장치만 먼저 두기

본 해결은 미루더라도, 적어도 의심 케이스를 알아챌 수 있는 정도는 두자고 결정했다. `check_unit_suspects()`라는 후처리 함수를 적재 루프 끝에 붙였다. 같은 종목·같은 연도에서 quarter 1~3 합 대비 quarter 4 annual 비율이 임계값 이상이면 WARNING 로그를 찍는다.

```
[WARN] [UNIT_SUSPECT] ticker=065150 year=2023
       q_sum=96,771,550,036 annual=128,819,482,459,000 ratio=1331.17
```
임계값은 10으로 잡았다. 1000배보다 낮게 잡아 잠재 케이스도 포착되게. 분기 데이터가 3개 미만이면 검증을 스킵해서 false positive를 줄였다.

이건 어디까지나 인지용이다. 적재 자체는 정상 진행시키고, 의심 케이스만 로그에 흔적을 남긴다. 본 해결로 가기 전에 영향 범위를 가늠하는 단계.

## B11 — 일부 종목의 과거 EPS가 NULL

같은 세션에서 따로 가져간 두 번째 이슈. 현대차(005380)의 2021~2023 EPS가 전부 NULL인데 같은 기간 net_income은 정상값이 들어있었다. SK하이닉스 같은 다른 대형주는 같은 기간 EPS가 다 채워져 있어서, "DART 호출 자체는 성공하는데 EPS만 선택적으로 누락된다"는 패턴이 명확했다.

가설은 두 가지였다.

- **A.** 현대차 CFS에는 EPS 항목 자체가 없고 OFS(별도재무제표)에만 있어서, 우리 코드가 CFS 성공 후 OFS를 보지 않아 누락
- **B.** account_id가 표준 IFRS 코드(`ifrs-full_BasicEarningsLossPerShare`)가 아닌 다른 형태라서 매칭이 실패

API 원본을 떠서 확인했다. 결과는 B에 가까웠다 — 정확히는 더 복잡했다.

```
account_id: -표준계정코드 미사용-
account_nm: 보통주 기본주당이익          IS  28521
account_nm: 1우선주 기본주당이익        IS  28207
account_nm: 보통주 희석주당이익         IS  28521
account_nm: 1우선주 희석주당이익        IS  28207
```
현대차는 표준 IFRS 코드를 사용하지 않고, account_nm에 직접 한국어 항목명을 적는 방식으로 공시하고 있었다. 거기다 보통주/우선주, 기본/희석을 분리해서 4개 row로 내놓는다. 우리 매칭 로직은 `ifrs-full_BasicEarningsLossPerShare` 하나만 보고 있었으니 전부 미스.

이 시점까지는 단순했다. account_nm 폴백을 추가하면 될 일이라고 판단했다.

### 첫 폴백 — 작은 효과

정확히 `"보통주 기본주당이익"`만 매칭하는 폴백을 추가하고 영향 종목 780개(eps NULL but net_income 정상)에 대해 재적재를 돌렸다. 결과는 예상보다 적었다.

- 종목 단위로는 780 → 778. 단 2개만 모든 NULL이 해소됐다.
- 분기 단위로는 5,704건 → 5,664건. 40건만 채워졌다.

현대차 2021~2023의 일부 분기는 채워졌지만, 2021 Q3와 2023 Q4는 여전히 NULL이었다. 그리고 영향 종목 780개 중 대부분은 21/21 = 100% NULL인 상태로 남아 있었다.

이 정도 대형 주에서 eps를 공시하지 않을 리가 없었다. 네이버 증권에 EPS가 표시되는 종목들이 다수 포함돼 있고, 현대차 2023도 외부에는 EPS가 공개돼 있다. 우리 폴백이 못 잡고 있을 뿐이다.

> 추정으로 정리하지 말고 원본을 한 번 더 보자고 결정한 게.

### 두 번째 원본 확인 — 3가지 변형 케이스

100% NULL 종목 상위 5개와 현대차 2023을 다시 떠봤다.

```
003550 (LG)         account_nm: 보통주 기본/희석주당순이익
009830 (한화솔루션) account_nm: 보통주 기본 및 희석주당순손익
001210 (금호전기)   account_id: ifrs-full_BasicEarningsLossPerShareFromContinuingOperations
049630 (재현산업)   동일
123570 (이엠넷)     동일
005380 (현대차) 2023  account_nm: 보통주기본주당이익(손실)   ← 공백 없음 + 접미사
```
세 가지 변형 패턴이 같이 끼어 있었다.

- **유형 A**: account_id는 `-표준계정코드 미사용-`인데 account_nm 표현이 다양화돼 있다. 기본주당과 희석주당을 한 줄에 묶어서 공시하는 방식.
- **유형 B**: 표준 IFRS 코드는 쓰지만 통합 코드(`BasicEarningsLossPerShare`) 대신 `FromContinuingOperations`(계속영업) + `FromDiscontinuedOperations`(중단영업)을 분리해서 낸다.
- **유형 C**: 공백 한 칸 차이거나 `(손실)` 접미사가 붙어서 정확 매칭이 어긋난다. 현대차 2023이 여기 해당했다.

첫 폴백이 거의 작동하지 않은 이유가 이걸로 설명됐다. 패턴 하나를 잡았더니 그 뒤에 두 개가 더 있었다.

### 유형 B를 어떻게 처리할까

A와 C는 단순했다. account_nm을 정규화(공백 제거 + 괄호 접미사 제거 + 희석 병기 제거)한 다음, 후보 집합 `{보통주기본주당이익, 보통주기본주당순이익, 보통주기본주당순손익}` 중 하나와 일치하면 매칭. 미세 변형 하나마다 문자열을 추가하는 대신 정규화 함수로 흡수했다.

B는 잠깐 멈춰서 정책을 정해야 했다. 계속영업 EPS만 적재할지, 합산할지.

- **계속영업만 사용**: 단순. 중단영업이 없는 종목엔 정확.
- **계속영업 + 중단영업 합산**: 통합 EPS와 일치. 정확.
- **통합 row 우선, 없으면 합산**: 절충.

현대차 2023 데이터를 보면 계속 47,622 + 중단 -1,919 = 통합 45,703이 맞다. 증권 정보를 제공하는 서비스에서 "중단영업이 있는 종목만 부정확하게 적재"하는 건 받아들이기 어려운 트레이드오프였다. 통합 우선, 없으면 합산으로 정했다.

### 매칭 우선순위

최종 폴백 로직은 다음 순서로 시도한다.

1. `ifrs-full_BasicEarningsLossPerShare` (통합 표준 코드)
2. `ifrs-full_BasicEarningsLossPerShareFromContinuingOperations` + `FromDiscontinuedOperations` 합산
3. account_nm 정규화 후 보통주 기본 EPS 후보 집합 매칭
4. NULL

CFS에서 못 찾으면 OFS도 같은 순서로 시도한다. 이건 [#033](https://velog.io/@dh82680/SlateKR-033-OFS-계정과목-폴백-재적재-검증에서-발견한-누락)에서 정한 정책을 그대로 유지.

## --tickers 옵션과 샘플 검증

전체 재적재는 한 번 돌리는 데 약 8시간이 걸린다. 로직 검증 단계에서 매번 그렇게 돌릴 순 없어서, collector에 `--tickers` CLI 옵션을 추가했다. 한 줄당 ticker가 적힌 텍스트 파일을 받아서 해당 종목만 처리한다. 영향 종목 타게팅 재적재나 샘플 검증용이다.

각 유형 대표 종목 6개로 검증을 돌렸다.

| ticker | 회사 | 유형 | 전 | 후 |
|---|---|---|---|---|
| 003550 | LG | A | 20/20 NULL | 0/20 |
| 009830 | 한화솔루션 | A | 20/20 | 3/20 |
| 001210 | 금호전기 | B | 20/20 | 0/20 |
| 049630 | 재현산업 | B | 20/20 | 0/20 |
| 123570 | 이엠넷 | B | 20/20 | 0/20 |
| 005380 | 현대차 (2023) | C | 2/20 | 0/20 |

한화솔루션 2024 Q1~Q3 3건은 DART 원본 자체에 EPS row가 없어서 폴백 로직과 무관하게 NULL이 유지된다. 그 외 유형별로 의도대로 매칭됐다.

전체 780종목 재적재는 다음 세션에서 백그라운드로 돌리기로 했다. 로직 검증이 끝났으니 단순 적용 작업이고, 세션 한 편을 거기에 쓰는 건 비효율이라고 봤다.

하지만 작업시 또 다른 문제가 발생한다면 새로 게시글을 올릴지도 모른다.

## UNIT_SUSPECT 결과

B10 인지 로그가 작동하는지도 같이 확인했다. 780종목 재적재 중에 발생한 WARNING은 7건이었다.

```
032680 2022  ratio 1,621,173   → 백만원 단위 확실
065150 2023  ratio 1,331       → 천원 단위 확실
311390 2022  ratio 1,312       → 천원 단위 확실
046390 2025  ratio 22.6        → 미약 (false positive 가능)
226330 2024  ratio 15.7        → 미약
226330 2023  ratio 14.1        → 미약
217820 2022  ratio 11.8        → 미약
```
ratio 1,000을 넘는 3건은 단위 오류로 확정. 10~23 사이의 4건은 단위 오류일 수도, 조기 성장이나 M&A 효과일 수도 있다. 이건 별도로 검토할 항목으로 분리했다.

## 정리

- DART API 응답에 단위 메타데이터(원/천원/백만원 구분)가 없다는 게 확인됐다. B10 본 해결은 별도 노선 결정이 필요한 영역으로 분리하고, 인지용 `UNIT_SUSPECT` 로그만 먼저 붙였다.
- EPS 누락 패턴이 단일 원인이 아니라 3유형(account_nm 변형 / 계속·중단영업 분리 / 미세 표기 차이)으로 갈렸다. 다단계 폴백으로 흡수했다.
- 유형 B 정책은 통합 row 우선, 없으면 계속+중단 합산으로 정했다. 증권 정보의 정확성 기준에서 합산이 맞는 접근이라고 봤다.
- 6종목 샘플로 로직 검증을 마쳤다. 전체 780종목 재적재는 다음 세션에서 백그라운드로.

엄밀히는 가설 갈아엎기를 두 번 했다. 처음엔 B10이 회사 filing error라고 봤다가 collector 누락으로 정정했고, B11도 첫 폴백 결과를 보고 "공시 부재 케이스가 다수"라고 정리하려다가 멈췄다. 두 번째 정정이 작업의 결을 바꿨다. 첫 폴백만 보고 마무리했으면 770개가 넘는 종목이 그대로 NULL로 남았을 거다.

데이터 신뢰성 작업은 가설을 일찍 확정하지 않고 원본을 한 번 더 보는 게 비싼 비용이 아니었다. 이번엔 그게 잘 작동했다.
