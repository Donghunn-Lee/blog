직전 세션에서 AI 공시 요약의 기본 모델을 gemini-3.8-flash로 올리고 2.5를 fallback으로 붙였다(#168). 그때 소요 시간도 같이 재서 정상이면 4~11초, 503 재시도와 fallback을 타면 30초대, 요청 예산은 55초라는 분포가 나왔는데, 정작 요청을 누른 사용자가 보는 건 스피너와 "요약 생성 중…" 한 줄이었다. 10초를 기다릴지 1분을 기다릴지 화면이 말해주지 않는다.

이번 세션은 README 마감(G1) 차례였지만, 실측 수치가 살아 있을 때 대기 문구부터 잡기로 하고 이 작업을 신규 항목(E96)으로 앞에 두었다. 계획은 E96 → 거래일 화면 캡처 → README 본문 점검이었고, 결과는 E96 커밋 하나와 README의 리포 첫 반영이다. 아침 실측은 하루가 늦어져 쉽지 않다.

## 진행도가 없는 요청의 대기 문구

요약은 단일 POST 한 번이고 스트리밍이 없어서 진행도라는 신호 자체가 없다. 그래서 선택지는 진행도를 만들어 보이는 쪽과 시간을 말해주는 쪽으로 갈렸다.

| 후보 | 판정 |
|---|---|
| 시간 기반 가짜 진행바 | 기각. 근거 없는 진행도 표시. 예산 끝에서 멈춘 바가 남음 |
| 경과 초 카운터 | 기각. 숫자가 튀는 게 절제된 톤과 어긋나고, 정보는 단계 문구가 이미 담음 |
| 정적 안내 한 줄 | 보류. 15초를 넘긴 사용자에게 아무 변화가 없음 |
| **경과 시간 기준 2단계 문구** | **채택.** 임계 15초와 상한 1분 둘 다 실측·예산에서 나온 숫자 |

```
0~15초   요약 생성 중 (5~15초 소요)
15초~    요약 생성 중 (평소보다 오래 걸리고 있습니다)
고정     서버 상황에 따라 최대 1분까지 소요될 수 있습니다
```

15초는 3.8의 정상 상한(11초)과 2.5의 중앙값(14초) 바로 위라, 이 선을 넘겼다면 503 재시도나 fallback 경로에 들어갔을 확률이 높은 지점이다. "최대 1분"은 55초 예산에 route의 실행 상한 60초를 얹은 값인데, 예산이 요약 호출부터 세기 시작해 앞단의 원문 다운로드는 밖에 있으므로 실제 상한은 60초이고 그 뒤는 504로 끊긴다. 3단계는 두지 않았다. 예산이 55초인 이상 1분 이후에 대해 말할 것이 없다.

## 타이머의 기준 시점

처음엔 타이머를 로딩 마크업 안에 두려 했다. probe를 돌려보니 그러면 안 되는 이유가 나왔는데, "닫기"를 눌러도 진행 중인 요청은 끊기지 않고, 행을 접으면 로딩 마크업만 사라지며, 다시 펼치면 새 요청 없이 진행 중인 요청의 결과를 쓴다. 마크업 안의 타이머는 접었다 펼칠 때마다 0초부터 다시 세는 셈이라, 요청이 시작될 때 타이머를 걸고 요청이 끝날 때(성공·실패·취소 모두) 정리하는 쪽으로 옮겼다. 재시도는 새 요청이니 다시 0초다. setTimeout 하나와 boolean 하나면 되는 구조라 별도 훅이나 순수 함수로 뽑지 않았고 테스트도 두지 않았다. 임계 하나짜리 분기에 테스트 가치는 없다.

문구 구조는 한 번 바꿨다. 첫 구현은 상태 줄을 고정하고 보조 줄을 교체하는 형태였는데, 두 문구의 글자 수가 달라 390px에서 한쪽만 2줄이 되고 스피너가 8px 움직였다. 최소 높이를 잡아 막았지만, 상태 줄의 괄호만 바꾸고 보조 줄을 고정하는 구조로 가니 그 보정 자체가 필요 없어졌고 안내한 범위의 상한(15초)이 전환 임계와 같아져 문구가 바뀌는 순간에 설명이 붙었다.

| | 상태 줄 | 보조 줄 | 레이아웃 |
|---|---|---|---|
| 첫 구현 | 고정 | 15초에 교체 | 줄 수 변동 → 최소 높이 보정 |
| **최종** | **괄호만 15초에 교체** | **고정** | **보정 없음** |

## 실측에서 나온 41초

dev에서 브라우저 자동화로 실측했다. 임계를 2초로 낮추고 캐시에 없는 공시 하나를 펼쳐, 요청 한 건으로 두 문구를 다 봤다.

| 항목 | 결과 |
|---|---|
| 펼침 → 요청 | 1건 |
| 0.7초 | 1단계 문구, 두 줄 모두 1줄 |
| 2.03초 | 2단계로 전환, 스피너 중심 이동 0, 박스 높이 110px 유지 |
| 3.5초 접고 3.9초 펼침 | 2단계 문구 유지, 새 요청 0 |
| 재시도 | 타이머 0초부터 |
| 41.6초 | 요약 대신 rate_limit 오류와 재시도 버튼 |

마지막 줄이 계획에 없던 결과다. 두 모델의 일일 한도가 각각 16/20인 상태였고, 기본 모델이 30초를 다 쓴 뒤 fallback에서 429를 받은 것으로 보였다. 다만 요약 코드가 어느 경로로 끝났는지를 로그로 남기지 않아 확정은 못 했고, 이건 요약 잔손질 항목(F110)에 올렸다. 문구가 필요하다는 증거가 첫 실측에서 나온 셈인데, 41초 동안 "최대 1분"이라는 줄이 없었다면 그 화면은 그냥 멈춘 것으로 보였을 것이다.

## README 이미지 슬롯 정리

구현과 병행해 거래일 정규장 화면 다섯 슬롯을 다시 찍었고, 슬롯 둘은 비웠다.

| 슬롯 | 판정 |
|---|---|
| 분봉 전환 전/후 비교 | 삭제. 전환 전 코드가 없어 '전'을 만들 수 없고, '후'만으론 대비가 없음. 본문 수치(15회 중 4회 500 → 4~7회 실패 0)가 그림 역할 |
| fallback 표면 | 삭제. 분봉 재시도 UI는 재현 불가, .DJI 셀의 '종가 기준' 캡션은 상시 재현되나 셀 하나 크롭은 600px 이미지로 빈약 |
| 종목 상세 | 풀페이지 → 헤더·핵심 지표·탭 바 크롭. 풀페이지가 2×2 그리드를 깨 반대편을 확대 이미지로 메웠더니 정보 없는 filler로 읽힘 |

이미지는 없으면 설명이 안 되는 자리에만 두기로 해서 설계 절 넷 중 AI 요약 하나에만 남았다. 수가 줄어도 남은 것들이 전부 제 몫을 하는 쪽이 낫다고 봤다.

## 본문 정정과 링크 대조

본문은 열여덟 곳을 고쳤다. 유형별로 하나씩만 적는다.

| 유형 | 건수 | 예 |
|---|---|---|
| 사실 | 7 | "로그인 없이 기기 간 동기화" → 쿠키는 브라우저 단위라 기기 간이 아님. "서버 저장 · 유실 복구"로 |
| 반영 누락 | 4 | 요약 입력은 클라이언트 `{rcept_no, ticker}`뿐, 제목·회사명은 서버가 조회한다는 경계(#168) |
| 수치·플레이스홀더 | 4 | 테스트 985 → 1,111 |
| 표현 | 3 | 영어 병기는 첫 등장만 |

링크 아홉 편은 상태 코드가 아니라 본문으로 대조했다. velog는 없는 글도 200을 주기 때문이다. 각 글의 정리 절을 README가 인용한 문장과 맞춰보니 아홉 편 모두 맞았고, 불일치는 한 곳이었다. facts 상한을 README는 18로, 링크된 글은 8로 적고 있었는데(#082에서 올렸다), 숫자 대신 "`maxItems` 같은 제약"으로 일반화했다.

## 개발 방식 내용 추가

README에 개발 방식을 적을지는 판단이 갈렸다. 이 프로젝트는 조사와 코드 생성 대부분을 AI 코딩 도구에 위임했고, 직접 타이핑한 코드는 거의 없다. 반년 가까이 혼자 700개가 넘는 커밋을 영문 Conventional Commits로 쌓은 이력은 그 사실을 이미 말하고 있어서, 숨긴 것처럼 보이는 쪽이 손해라고 봤다. 지원 대상이 스타트업·중소기업이라 레버리지 자체는 감점보다 관심 항목에 가깝기도 하다.

문제는 프레이밍이었다. "직접 친 코드가 없다"는 사실이어도 신입에게 향하는 "본인이 짤 수 있나"라는 의심을 정면으로 건드리고, 사실의 단위도 타이핑 비율이 아니라 분업이다. 조사·생성은 위임하고 설계·검증·판단은 위임하지 않았다는 문장으로 잡고, 세션 하나가 도는 루프(로드맵 → 계획 → 조사 → 결정 → 구현 → 리뷰·커밋 → 일지 → 갱신)를 아키텍처 절과 같은 백틱 체인으로 그렸다. Mermaid로 역할별 색을 입힌 안도 만들어봤지만 오히려 읽기 어려워 접었다. 이 절을 쓴 이상 면접에서 코드 한 줄을 짚어 "왜"를 물을 권리를 준 것이라, 코드 설명 리허설을 면접 준비 항목에 올렸다.

그동안 수정만 하고 커밋을 하지 않았던 리드미를, 이번 작업에서 다듬어 커밋했다. 아직 완전히 끝난 것은 아니라 최종 점검은 필요하다.

## 정리

- **E96 구현** — 요약 대기 문구를 경과 시간 2단계로. 임계 15초·상한 1분은 #168 실측과 예산에서, 타이머는 요청 수명 기준, 보조 줄 고정으로 레이아웃 보정 제거
- **G1 리포 반영** — 거래일 캡처 5슬롯, 빈 슬롯 2 삭제, 본문 18곳 정정, 링크 9편 본문 대조, 개발 방식 절 신설. 잔여는 데모 영상과 현직자 검토
- **F110 추가** — 요약 결과 경로 로그 부재, rate_limit 문구의 재시도 버튼, 도달 불가 분기 하나, 화면 이탈 후 재진입 시 중복 호출

구현은 21줄이고 README는 문서 하나라 거창한 세션은 아니다. 그래도 문구의 숫자 둘이 전부 지난 세션 실측에서 나왔고 첫 실측이 그 숫자의 필요성을 41초로 보여줬으니 순서는 맞았던 것 같다. README는 코드가 굳은 뒤에 닫기로 했던 게 #156이었는데, 그 사이 정정이 열여덟 곳 쌓인 걸 보면 문서는 코드보다 좀 늦게 굳는다.
