로드맵에 C3 "기업 개요 패널"이 한참 전부터 이월돼 있었다. 종목 상세에 회사 자체에 대한 정보가 하나도 없다는 게 걸려서 적어둔 항목이다. 이번 세션은 그걸 받아 시작했는데, 작업을 끝내고 보니 "패널"이라는 형태는 사라지고 헤더에 줄 하나가 늘어난 게 전부였다. 그 줄어드는 과정이 이번 글의 내용이다.

---

## 서술형 설명 고려 — 배제

기업 개요라고 하면 보통 "이 회사가 무엇을 하는지" 한두 문단 설명을 떠올린다. 내가 처음 추가 하고 싶었던 것도 그런 거였다. 하지만 구현이 어려울 듯해 계속 미뤄왔던 건데, 역시나 SlateKR에서 그건 만들 수 없다고 판단했다.

그 서술을 채우려면 사업보고서의 "사업의 내용"을 AI로 요약해야 한다. 네이버 증권 등에서 크롤링하는 건 이전 글들에서 여러 번 언급한 바 있다. 게다가 회사의 사실 정보를 모델이 지어내는 순간 데이터 정확성이라는 이 프로젝트의 정체성과 정면으로 부딪힌다. 하나하나 직접 검증하는 것은 너무 고된 작업이다.

그래서 개요 패널은 추가할 문구가 없으니 배제할 수밖에 없었다. 하지만 대안으로 DART 기업개황 API(`company.json`)를 사용하기로 했다. 대표자, 설립일, 본사 주소, 홈페이지, 업종 코드 정도. 문제는 이 필드들이 패널 하나를 채울 만한가였다.

## 가용 데이터 조사

추측으로 패널을 그리기 전에, 지금 가진 데이터가 어디까지인지부터 봐야 했다. 확인용 스크립트를 임시로 만들어 종목 테이블과 `company.json` 실제 응답을 확인했다.

결과가 몇 가지 정리됐다.

- 종목 테이블에 `sector`와 `listed_at` 컬럼이 있긴 한데 **전 행이 NULL**이었다. 적재 경로가 아예 없었던 거다. FSS 종목 목록 API는 시장·코드·종목명만 주고 업종이나 상장일을 안 보낸다.
- `company.json`은 대표자·설립일·본사·홈페이지·업종코드를 준다.
- 업종은 `induty_code`라는 숫자 코드로 온다. 삼성전자가 `264`다.

## 필드 추리기 — 업종만 유지

남은 필드를 두고 "이게 조회형 서비스에 필요한가"를 하나씩 따졌다.

| 필드 | 판단 | 이유 |
| --- | --- | --- |
| 업종 | 유지 | "이 회사가 뭐 하는 데"의 유일한 답. 조회의 핵심 |
| 홈페이지 | 유지 | 비용 0인 외부 링크 하나. 유용하진 않아도 무해 |
| 대표자 | 컷 | 이름만으론 조회 정보가 아니다. 해석은 이 서비스가 안 하는 영역 |
| 설립일 | 컷 | 회사 나이 정도의 trivia. 상장일의 빈자리를 메우지도 못한다 |
| 본사 주소 | 컷 | 전체 주소는 그냥 노이즈 |

업종만 핵심으로 남고 홈페이지가 보조로 붙는 정도였다. 그러자 패널이라는 형태가 어색해졌다. 업종 한 줄과 링크 하나를 독립 패널로 만들고 5색 시맨틱 중 한 색을 배정하는 건, 빈 껍데기에 색을 칠하는 일이다.

> 쓸만한 건 업종 하나밖에 없었다

그래서 업종을 StockHeader의 메타 줄(종목명·시장·코드 옆)로 흡수하고, 홈페이지는 작은 외부 링크 아이콘으로 붙였다. 별도 패널과 색 배정은 폐기했다. 헤더는 원래 무채색 유지 원칙이라 색 고민도 같이 사라졌다. C3는 새 컴포넌트와 새 색을 추가하는 작업에서, 헤더에 필드 하나 더하는 작업으로 줄었다.

## 업종 코드 매핑 — KSIC 소분류 3자리

`induty_code`는 통계청 한국표준산업분류(KSIC) 코드다. 그대로 두면 화면에 "264"가 뜬다. 이름으로 바꾸려면 매핑표가 필요한데, 어느 자릿수로 매핑하느냐가 작은 결정이었다.

처음엔 앞 2자리(중분류)로 자르려 했다. 표가 77개로 작고 모든 코드에 안정적으로 이름이 붙는다. 실제 코드를 몇 개 넣어봤다.

| 코드 | 2자리(중분류) | 3자리(소분류) |
| --- | --- | --- |
| 264 (삼성전자) | 26 → 전자부품, 컴퓨터, 영상, 음향 및 통신장비 제조업 | 264 → 통신 및 방송장비 제조업 |
| 582 (마키나락스) | 58 → 출판업 | 582 → 소프트웨어 개발 및 공급업 |

마키나락스(최근 상장 기업)는 AI 소프트웨어 회사인데 2자리로 자르면 출판업이 됐다. KSIC가 소프트웨어를 출판(58) 아래에 넣어둔 탓이다. 삼성전자도 2자리는 한 줄로 안 끝나는 행정용 명칭이었다. 2자리는 안정적인 대신 라벨이 너무 거칠거나 엉뚱했다.

3자리(소분류)로 내리니 같은 코드가 "통신 및 방송장비 제조업", "소프트웨어 개발 및 공급업"으로 떨어졌다. DART 종목 산업분류가 소분류를 기준으로 한다는 자료도 찾았다. 응답에 간혹 5자리가 섞여 오긴 하는데, 앞 3자리를 자르면 소분류로 떨어진다. 3자리가 맞는 선택이었다.

매핑표는 KSIC **10차** 기준으로 만들었다. 현행은 11차(2024년 7월 시행)지만, DART의 `induty_code`는 회사가 등록한 시점의 코드이고 대부분 10차 시행기(2017~2024)에 등록됐다. 11차 이름으로 덮으면 오히려 실제 값과 어긋날 수 있다. 소분류 이름은 10차와 11차가 거의 같아서 차이도 미미하다. 232개 소분류를 정적 상수로 넣고, 변환은 순수 함수로 뺐다.

```ts
// 5자리 코드도 앞 3자리만 본다. 매칭 안 되면 null — 2자리 폴백은 안 한다.
const getSectorName = (indutyCode: string | null): string | null => {
  if (!indutyCode || indutyCode.length < 3) return null;
  return KSIC_SUBCLASS[indutyCode.slice(0, 3)] ?? null;
};
```

폴백을 일부러 막았다. 3자리로 못 찾았을 때 2자리로 한 번 더 시도하게 두면 다시 출판업 같은 엉뚱한 라벨이 나온다. 못 찾으면 그냥 업종 줄을 안 보여주는 게, 정확성을 정체성으로 둔 서비스엔 맞다. 억지로 채우지 않는다.

## on-demand vs DB 적재

업종·홈페이지를 어떻게 가져올지가 마지막 결정이었다. 두 갈래가 있었다.

하나는 DB에 적재하는 거다. `company.json`을 종목마다 한 번씩 호출해 비어 있는 `sector` 컬럼을 채우고, UI는 DB만 읽는다. 다른 하나는 조회 시점(on-demand)에 가져오는 거다. 사용자가 종목 상세를 열 때 그 순간 `company.json`을 호출하고 결과를 캐시한다.

DB 적재는 수집 파이프라인을 다시 손대야 하는 무거운 일로 묶어서 생각하고 있었다. 따져보니 업종은 거의 안 바뀌는 정적 데이터라, 매일 도는 파이프라인이 아니라 일회성 스크립트 한 번으로 끝나는 일이었다. 이건 내가 잘못 엮어둔 부분이었다.

그래도 이번엔 on-demand로 갔다.

| | on-demand | DB 적재 |
| --- | --- | --- |
| DART 호출 | 조회된 종목만, 종목당 하루 1번(캐시) | 일회성 전체 1번 + 신규분 재실행 |
| 데이터 위치 | Next.js 캐시 | DB 영구 |
| 추가 작업 | 없음 (이미 동작) | 스크립트 + 실행 |
| 런타임 외부 의존 | 있음 | 없음 |

DB 적재가 더 깔끔한 지점은 분명히 있다. 런타임에 DART 의존이 사라지고 비어 있던 컬럼도 채워진다. 다만 그 이점이 포트폴리오 트래픽에서 체감되는 건 아니고, on-demand는 추가 작업이 0이다. `revalidate 86400`이라 종목당 하루 한 번만 호출하니 "매 요청마다 외부 API"도 아니다. DART가 실패하거나 코드가 매핑 안 되면 업종 줄만 빠지고 헤더 나머지는 그대로 뜬다. 섹션 단위로 독립적으로 죽게 만든 기존 fallback 원칙이 여기에도 그대로 적용됐다.

```ts
// 실패는 throw가 아니라 null. 없으면 헤더에서 안 보이면 그만이다.
const getCompanyProfile = async (corpCode: string): Promise<CompanyProfile | null> => { ... }
```

`sector` 컬럼은 비워둔 채로 남겼다. 나중에 트래픽이 늘거나 파이프라인을 손볼 때 `getCompanyProfile` 내부만 DB 읽기로 갈아끼우면 된다. 도메인 모델과 헤더는 그대로다. 지금은 속도를 택했고, 전환 여지는 열어뒀다.

신규 상장 종목은 두 방식 모두 같은 전제를 깐다 — 종목의 corp_code가 먼저 채워져야 한다. 마키나락스(477850)는 지금 corp_code가 비어 있어 업종이 안 뜬다. C3 코드의 문제가 아니라, corp_code 매핑 스크립트가 그 종목 상장 이후로 안 돌았기 때문이다. 이건 파이프라인 쪽에서 풀 일이다.

## 정리

- **개요 패널 → 헤더 한 줄** — 서술형은 정확성 때문에 배제하고, 사실 필드를 추리니 업종만 남아 패널을 접고 헤더로 흡수
- **업종 코드 매핑** — KSIC 소분류(3자리), 10차 기준 232개 정적 상수, 2자리 폴백 없이 못 찾으면 미표시
- **on-demand 조회** — DB 적재 대신 조회 시점 호출 + `revalidate 86400` 캐시, `sector` 컬럼은 전환용으로 비워둠

기능으로 치면 헤더에 줄 하나 추가한 세션이다. 그런데 거기까지 오는 동안 패널을 그릴 뻔하다가 접고, 매핑 자릿수를 바꾸고, 적재 방식을 두고 한참 따졌다. 만들 것을 줄이는 결정이 만드는 것보다 길었던 셈이다. 무엇을 넣을까보다 무엇을 뺄까를 더 오래 본 건 #057 공시·관심종목 작업과도 같은 흐름이었다.

## 다음 작업

화면 자체에 더 손볼 곳은 줄었고, 다음은 홈으로 간다.

- **E2** — 홈 디자인 재구성. 하단 빈 공간과 최근 검색·관심종목의 위계 정리가 핵심이다. 손볼 범위가 "정형화"보다 커서, 실물을 보며 방향부터 잡는 계획 세션을 따로 둘 생각이다
- **D2** — AI 공시 요약 프롬프트·컨텍스트 정비. 카테고리가 달라 독립 세션으로 뺀다

곁다리로, 멈춰뒀던 수집 파이프라인을 다시 켰다. 초기에 비효율적인 스케줄로 한도를 쓸까 봐 꺼뒀던 건데, 다시 보니 public 레포는 표준 러너 사용 시간 제한이 없어 애초에 그 걱정이 필요 없었다. 재가동 후 멈춘 기간만큼 데이터 갭이 제대로 메워지는지, 신규 상장 종목이 잡히는지는 적재가 끝난 뒤 확인할 항목으로 남겨뒀다.
