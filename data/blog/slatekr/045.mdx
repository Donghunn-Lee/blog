#044에서 인라인 확장 작업을 마치고 뒤에 부록으로 Parallel Routes 회고를 붙였다. 비활성 슬롯 상태 보존이 SlateKR의 단일 슬롯 구조엔 적용되지 않는다는 사실을 짚어두고, 결정 자체가 잘못된 건 아니라는 결론이었다.

작업 시작 전, 회고를 다시 읽다 보니 마음에 걸리는 부분이 생겼다. 살아있는 근거들이 라우트 분리에서도 똑같이 따라오는 거라면, 결정이 합리적이었다는 말이 좀 약해지는 거 아닌가. 이번 세션은 그 의문을 끝까지 따라가 본 결과를 정리한다. 개발은 없고 결정과 계획만 다룬다. 그리고 #046에서 폴더 재배치에 들어가려고 한다.

---

## #044 부록을 다시 들여다본 이유

부록에서 그렸던 비교표는 이런 모양이었다.

| 항목 | 라우트 분리 | Parallel Routes (`@tab` 슬롯) |
| --- | --- | --- |
| layout 공유 | 가능 | 가능 |
| sub-route별 SEO | 가능 | 가능 |
| sub-route별 loading/error | 가능 | 가능 |
| 차등 revalidate | 가능 | 가능 |
| prefetch 제어 | 가능 | 가능 |
| 비활성 슬롯 상태 보존 | 불가 | 이론상 가능, SlateKR 단일 슬롯 구조엔 적용 안 됨 |

부록을 쓸 때는 마지막 줄을 빼고도 결정의 본체 근거(#040에서 적었던)가 충분히 살아있다고 봤다. 다시 표를 보니 그 본체 근거들이 모두 `가능 / 가능`에 들어가 있었다. **라우트 분리에서도 똑같이 가능한 것들이 결정의 본체였다는 얘기**다.

그렇다면 SlateKR 구조에서 Parallel Routes를 택해서 얻는 고유한 가치는 표 마지막 줄(보존 효과) 하나였고 그것마저 슬롯 1개 구조에선 동작하지 않는다. 차별점이 사실상 0인 셈이다.

엄밀히는 "결정이 잘못됐다"보다 "당시 근거 검증의 표본이 좁았다"가 더 정확한 표현이긴 하다. 다만 차별점이 0이라는 사실은 결정을 유지할 이유가 됐을 게 무엇인지 다시 묻게 만들었다.

## 도구의 본래 설계와 탭 nav의 개념

여기서 한 발 물러나 Parallel Routes가 본래 무엇을 하려는 도구인지 다시 봤다.

공식 문서가 드는 대표 예시는 대시보드다. analytics 패널과 team 패널이 한 화면에 동시에 떠 있고, 각자 자기 sub-route를 갖는다. analytics가 `/views`로 이동하는 사이 team은 `/settings` 그대로 머무른다. 슬롯 모델은 **여러 패널을 동시에 노출하고 각자 독립적으로 navigate시키기 위한 것**이다.

탭 nav는 정반대다. 한 번에 하나의 탭만 보여주고 나머지는 가린다. #042에서도 짧게 언급했지만 슬롯 4개를 두면 4개가 한 화면에 동시에 렌더되는 게 기본 동작이라, 처음 시도했을 때 4개 페이지가 세로로 쌓이는 결과가 나왔다.

그래서 슬롯을 하나(`@tab`)로 줄이고 그 안에서 sub-route로 갈아끼우는 우회로 갔다. 이렇게 하면 동작은 한다. 그런데 동작 자체는 일반 nested layout(`layout.tsx + children + sub-route page.tsx`)과 같다. **`@tab` 슬롯에 children prop이 다른 이름(tab)으로 들어왔을 뿐, 라우팅 동작은 동일하다.**

그러면 단일 슬롯을 유지하는 추가 비용(`default.tsx` 두 개, 슬롯 폴더 표기, 시그니처에 안 쓰는 children prop 선언)을 정당화하는 게 무엇이었느냐. **보존 효과 하나뿐이었다.** 그 효과가 적용되지 않는 구조라는 게 확인된 이상, 추가 비용을 유지할 근거가 사라진다.

## 폴더 구조 재배치 — overview를 ticker root로

결정은 이렇게 잡았다.

```
Before
[ticker]/
├── layout.tsx
├── page.tsx             ← null
├── default.tsx          ← null
└── @tab/
    ├── default.tsx      ← null
    ├── page.tsx         ← 종합정보
    ├── chart/page.tsx
    ├── financials/page.tsx
    └── disclosures/page.tsx

After
[ticker]/
├── layout.tsx
├── page.tsx             ← 종합정보 (= /stocks/[ticker])
├── chart/page.tsx
├── financials/page.tsx
└── disclosures/page.tsx
```

`@tab` 폴더와 두 개의 `default.tsx`, 빈 `page.tsx`가 사라진다. 슬롯 안에 있던 종합정보 page.tsx는 한 단계 올라와 `/stocks/[ticker]` 자체를 담당한다.

여기서 한 가지 부수 결정이 같이 따라왔다. **ticker root URL이 곧 종합정보**라는 것.

#042 구조에서도 `/stocks/[ticker]` 진입 시 종합정보가 떴다. 다만 그건 `@tab` 슬롯이 자기 루트(`@tab/page.tsx`)를 렌더해서 그렇게 보인 거라, "종합정보가 기본"이라는 의도와 실제 메커니즘 사이에 슬롯 매핑 한 단계가 끼어 있는 모양이었다.

After 구조에선 `/stocks/[ticker]` 자체가 종합정보 페이지다. 의도가 메커니즘과 1:1로 표현되는 셈. 네이버 금융, 다음 금융 모두 종목 root URL이 종합정보를 가리키는 형태라 외부 링크나 검색 진입에도 자연스럽고, canonical URL이 명확해지는 부수 효과도 있다.

탭 nav의 활성 상태 판단은 한 줄 분기가 늘어난다.

```ts
const isActive = (href: string) => {
  // 종합정보는 정확히 일치할 때만
  if (href === `/stocks/${ticker}`) return pathname === href;
  // 나머지는 prefix 매칭
  return pathname.startsWith(href);
};
```

종합정보 href(`/stocks/${ticker}`)는 다른 탭 URL(`/stocks/${ticker}/chart` 등)의 prefix가 돼서 startsWith 매칭에 함께 걸린다. 종합정보만 따로 완전 일치로 분기.

부수적으로 #044에서 다음 세션 과제로 남겨둔 두 항목도 이번에 같이 정리한다.

- **`prefetch={false}` 제거**. 탭 전환 시 클릭 후 fetch 시작이라 스켈레톤이 깜빡인다. nested layout 구조에서 prefetch + streaming의 표준 동작을 살린다
- **탭별 필터 상태 보존은 폐기**. 조회형 서비스에서 탭 이동 시 이전 선택을 복원하는 게 일반적 UX는 아닌 듯하다. 네이버 금융·다음 금융 모두 그렇게 동작하지 않는다. 이걸 위해 Zustand 슬라이스를 따로 두는 건 비용 대비 가치가 약하다고 봤다

## 이번 결정에서 짚어둘 부분

#040에서 Parallel Routes를 결정할 때 사용한 비교표는 라우트 분리 후보를 함께 두긴 했지만, 보존 효과의 적용 조건을 충분히 검증하지 않았다. 슬롯 1개 구조에서도 보존이 동작한다고 가정한 상태에서 비교가 이뤄졌고, 그 가정이 본 적용 후 실측에서 깨졌다.

가정이 깨지자마자 결정을 다시 본 게 아니라, #044 부록까지 와서 "여전히 살아있는 근거" 쪽에 무게를 실어 결정을 유지하려고 했다. 며칠 묵힌 뒤에야 그 살아있는 근거들이 라우트 분리에서도 똑같이 따라온다는 게 보였다. 회고가 한 차례 더 들어가야 했던 사례.

엄밀히는 "근거가 약했다"보다 "근거 검증 단계가 부족했다"가 정확한 표현일 것 같다. 결정 시점엔 보였던 차별점이 본 적용 단계에서 사라질 수 있고, 그 경우 본 적용 직후에 결정을 다시 보는 게 정상 회로라는 것. 객관적으로 내가 너무 얕게 생각하고 결정 한 것이 맞다. 깊게 반성하고, 다음엔 최종 결정 전, 내 생각이 맞는지 좀 더 면밀하게 검토할 필요가 있겠다.

코드 측면에선 그동안의 작업이 무위는 아니다. `React.cache` 도입(`getCorpCode`, `getDisclosures`, `getLatestPrice`), `Promise.allSettled` + 부분 렌더(`StockMetrics`), `next/dynamic`으로 차트 lazy load — 이건 라우팅 구조와 독립적이라 그대로 살아남는다. 폴더 재배치만 진행하면 된다.

## 다음 작업

다음 작업에서 다룰 항목은 아래와 같이 계획했다.

- 폴더 재배치 (`@tab` 폴더 해체 + `default.tsx` 정리)
- layout.tsx의 slot prop(`tab`)을 `children`으로 변경
- `getStockByTicker`의 `React.cache` 래핑 위치를 `lib/stocks.ts`로 이동 (각 page의 `generateMetadata`에서도 호출되므로 lib에서 래핑하는 게 일관성 있음)
- 탭 nav 활성 상태 분기 명시화 + `prefetch={false}` 제거
- 탭별 `generateMetadata` 추가 (탭마다 다른 title/description으로 SEO 강화)
- 검증: hard refresh로 모든 탭 URL 정상 진입 / 탭 전환 시 layout 영역 유지 / canonical URL 형태 확인

3개 커밋 단위로 나눠서 진행한다. 폴더 재배치 → cache 위치 이동 → metadata + prefetch 정리.

코드 변경량으로는 폴더 몇 개 정리지만 라우팅 구조에 대한 판단이 한 번 바뀐 사례라, 의사결정만 따로 세션을 빼서 정리해뒀다.
