#140에서 지수 라벨을 정리하며 개장 전 등락을 전일 일중 값으로 채우기로 했다. 라벨이 "전일 종가"라고 말하니 등락도 전일 것이 짝이라는 판단이었다. 다섯 세션이 지나 그 화면을 처음 실물로 보게 됐는데, 다른 서비스와 비교해보니 짝이 맞는지와 별개로 사용자가 읽는 의미가 어긋나 있었다. 계속 신경 쓴 부분인데 이렇데 여러 차례 수정이 들어가는 게 참 반성하게 되는 부분이다.

계획은 미뤄둔 육안 실측 세 건(E68·F81·E69)을 보고 가격 출처 배지로 넘어가는 것이었다. 실측은 셋 다 통과했지만 E68을 확인하다 위 문제가 나와, 규칙을 다시 세우는 작업(E70)을 신설해 그날 안에 소화했다. 배지는 조사만 하고 넘겼다. 커밋 3개다.

## 개장 전후 실측

08시에 앉아서 순서대로 확인했다.

| 항목 | 확인 내용 | 결과 |
| --- | --- | --- |
| E68 | 홈 4셀·지수 상세 "개장 전" 라벨, 하단 페어 문구 | 통과. 다만 등락 표시에 이의 |
| F81 | 비NXT 종목 첫 1분봉 위치 | 통과 |
| E69 | 헤더 시각이 캐시 시각을 따르는지 | 통과 |

F81은 하마터면 실패로 적을 뻔했다. 첫 봉이 09:01에 찍히길래 09:00이 아니면 안 되는 줄 알고 있었는데, 국내 1분봉은 09:00~09:01 사이 체결이 09:01로 라벨링되니 09:01이 맞다. #140에서 고친 건 봉 라벨이 아니라 조회 창의 시작점이었고, 창이 09:00에서 열려 있고 프리마켓 구간에 봉이 없으면 그걸로 된 것이다. 실측 기준을 적어두면서 대상을 잘못 옮겨 적은 셈이다. E69는 지수 상세에 초가 표시되지 않아 지수별 차이까지는 못 보고 분 단위로만 확인했다.

## 개장 전 등락을 어떻게 볼 것인가

문제가 된 건 E68 화면의 이 부분이다. 08시대 홈 헤더가 "개장 전 · 전일 종가 09.04"인데 코스피 셀은 `+107.73 / +1.64%`를 띄우고 있었다. 9월 4일 세션의 등락이고 라벨도 그렇게 말하고 있으니 규칙대로다.

![](/static/images/velog/98323a9a-27b5-4b13-be18-4c08faa1b652-image.png)


네이버 증권을 같은 시각에 열어보니 코스피가 `0.00%`, 종목도 `0원 (0.00%)`에 기준일이 당일이었다. 8시 전에는 전 거래일 기준으로 보여주다가 8시를 넘기면서 당일로 넘어간 것이다.

| 후보 | 판정 |
| --- | --- |
| 전일 일중 등락 유지 (#140 결정) | 기각. 헤더가 출처를 밝혀도 숫자는 "오늘 오른 것"으로 먼저 읽힘 |
| **개장 전 창에서 0으로 초기화** | **채택.** 기준가가 오늘로 넘어간 상태를 그대로 표시. HTS·포털 관례와도 일치 |

기각한 쪽을 다섯 세션 전에 내가 채택했으니 뒤집는 근거가 뭔지가 중요했다. #140의 논리는 "라벨과 등락의 출처를 맞춘다"였는데, 그건 두 요소의 정합만 본 것이고 숫자가 단독으로 어떻게 읽히는지는 안 본 것이었다. 등락률은 위치와 색으로 먼저 읽히는 값이라 라벨을 읽기 전에 이미 의미가 전달되고, 정합이 맞아도 오독을 만든다면 정합 쪽을 포기하는 게 맞다. 개장 전은 어제 장이 끝난 상태의 연장이 아니라 오늘 장이 시작되기 직전의 상태이고, 기준가가 이미 오늘 것으로 넘어와 아직 체결이 없을 뿐이다.

## 초기화 시각이 두 개였다

바꿀 범위를 보려고 코드를 훑다가, 종목 상세는 이미 등락을 0으로 초기화하고 있고 그 시작이 6시라는 걸 발견했다.

| 화면 | 초기화 시작 | 판정 근거 |
| --- | --- | --- |
| 지수 | 없음 (전일 등락 유지) | — |
| 종목 | 06:00 | 개장 전 상태 전체를 초기화 대상으로 봄 |

같은 서비스 안에서 "개장 전"의 시작이 화면마다 달랐던 셈이다. 06시 초기화는 이전 hts기준이었는데, 웹서비스 용으로 새 기준을 8시로 잡았다. NXT 프리마켓이 8시에 열리고 KRX 기준가도 그때 오늘 것으로 넘어가니 그 앞의 두 시간은 값도 전일 종가, 등락도 전일 것, 라벨도 마감 계열로 두는 게 세 요소가 한 축에 서는 모양이다. 다만 그 창을 코드로 표현하기가 깔끔하지 않았다.

```null
06:00 ~ 08:00   개장 전 상태
08:00 ~ 08:50   프리마켓        ← 여기부터
08:50 ~ 09:00   개장 전 상태    ← 여기까지
09:00 ~         정규장
```

세션 판정 함수가 8시 50분에 다시 개장 전 상태로 돌아가는 구조라, 내가 원하는 창이 두 상태에 걸쳐 있었다. 대신 늦은 개장 전을 가려내는 술어가 이미 있어서, 그걸 재료로 창 술어 하나만 새로 만들면 됐다.

## 값을 지우지 않고 0을 얹기

지수 쪽 등락 교체는 조립 함수의 분기 하나였으니 그걸 걷어내면 원래 값이 돌아오는데, 그 원래 값이 뭔지가 문제였다. 주석 세 곳과 테스트 한 곳이 "개장 전 KIS 응답의 등락은 0"이라고 같은 말을 하는데, 그걸 뒷받침하는 실측 기록이 저장소 어디에도 없었다. 픽스처는 0을 입력으로 가정할 뿐 검증하지 않고 응답 샘플도 남아 있지 않다.

| 후보 | 판정 |
| --- | --- |
| 분기 제거 후 원래 값 노출 | 기각. 주석이 맞으면 0이 나오지만 틀리면 전일 잔여 등락이 그대로 노출됨 |
| **창 안에서 0을 명시 합성** | **채택.** 주석의 진위와 무관하게 결과가 고정됨. 부호까지 함께 지정하면 가격 색도 중립으로 따라옴 |

주석을 믿고 지우는 것과 안 믿고 덮는 것의 비용 차이가 거의 없었다. 분기는 어차피 손대야 하고 제거 대신 값 교체로 바꾸는 것이라 코드량도 비슷하니, 확인되지 않은 주장에 결과를 맡기지 않는 쪽이 낫다. 부호 필드까지 flat으로 명시한 건 가격 텍스트 색이 그 값을 보고 있어서다. 8시 앞 두 시간은 여전히 마감 표면이라 기존 교체 분기를 그대로 뒀다.

## 기준일은 어느 날짜여야 하나

종목 헤더에는 거래량·시가총액과 나란히 기준일이 있다. 장중에 열어보니 09-07인데 기준일만 09-04였다.

기준일은 일봉 테이블 최신 행의 날짜를 그대로 찍는 값이라 오늘 EOD가 들어오는 16시 이후까지는 계속 전일을 가리킨다. 현재가와 차트는 오늘 값을 보여주는데 기준일만 어제인 구간이 장중 내내 있었던 셈이다.

```null
이전   기준일 = 일봉 최신 행 날짜        (적재 시각에 종속)
이후   기준일 = 표시 중인 값의 거래일     (세션 축)
```

이렇게 정리하니 처음에 다루려던 개장 전은 이 규칙의 한 경우가 됐다. 8시에 오늘로 넘어가고, 저녁 8시부터 다음날 8시까지는 그 값의 거래일인 당일을 유지하고, 휴장일에는 직전 거래일이 된다.

## 세션 판정이 만든 우회 한 곳

거래일을 돌려주는 공용 함수를 쓰려고 경계를 확인했더니, 8시에 오늘로 넘어갔다가 8시 50분에 전일로 되돌아가고 9시에 다시 오늘이 되는 모양이었다. 앞서 본 세션 판정의 구멍이 이 함수까지 그대로 이어진 것이다.

| 후보 | 판정 |
| --- | --- |
| 공용 함수 경계 수정 | 기각. 호출하는 route가 여섯 개라 응답 날짜 축이 함께 움직임. 이번 커밋 범위 밖 |
| **소비 측에서 로컬 보정** | **채택.** 같은 보정이 이미 시세 조회 경로에 있어 동형. 함수와 route 무변경 |

같은 보정이 코드베이스에 세 번째로 생기는 건 마음에 안 들지만, 세 곳의 성격이 서버 조회 축과 화면 표시 축으로 갈려 있어 지금 합치면 잘못 묶을 것 같았다. 함수 경계 정리는 별도 항목으로 등록하고 보정 통합 판단을 거기 붙였다.

## 서버가 아직 어제라고 말할 때

창 판정이 클라이언트 시계를 보고 있어서 한 가지 조합이 남았다. 전날 저녁부터 탭을 열어둔 채로 8시 50분을 넘기는 경우다. 개장 전 구간에는 폴링이 돌지 않아 서버 응답의 세션 값이 갱신되지 않으니, 클라이언트는 "개장 전 창"이라 판단해 등락을 0으로 만드는데 라벨은 서버 값을 따라 "장 마감"이 된다.

해결은 창 판정 앞에 서버 세션 조건을 하나 더 두는 것이었다. 서버가 개장 전이라고 말할 때만 창 판정을 얹으면 두 술어의 세션 집합이 겹치지 않게 갈리고, 서버 값이 오래됐으면 기존 마감 표시가 유지되니 안전한 쪽으로 떨어진다. 기준일 쪽은 서버 세션을 아예 읽지 않아 오래된 응답의 영향이 없고 8시 55분에 화면에 있는 가격은 실제로 오늘 기준가라, 이 조건 없이 클라이언트 시계를 그대로 뒀다.

## 확인한 것과 못 한 것

| 항목 | 결과 |
| --- | --- |
| 실측 3건 | 통과 (F81 판정 기준은 정정) |
| 게이트 | 테스트 835건 통과, 빌드 성공 |
| 두 초기화 술어의 배타성 | 96개 조합 전수 확인, 동시 성립 0건 |
| 개장 전 화면 육안 | 미확인 |
| 기준일 컴포넌트 테스트 | 불가 |

구현이 9시 넘어 끝나서 정작 고친 화면을 실물로 못 봤다. 다음 세션에서 개발 서버의 시각을 고정해 세 지점(8시 20분·8시 55분·7시 30분)을 보기로 했다. 이러면 내일 아침을 기다릴 필요 없이 창 안팎과 경계를 한 번에 확인할 수 있다.

기준일 컴포넌트는 렌더 테스트 환경이 없어 조립 자체를 덮지 못했다. 대신 그 코드가 딛고 있는 사실, 그러니까 공용 함수가 8시 55분에 전일을 돌려준다는 걸 순수 함수 테스트로 고정해뒀다. 보정이 필요한 이유가 사라지면 테스트가 먼저 깨진다.

## 정리

- **개장 전 등락 0으로** — #140의 "전일 등락 유지"를 뒤집음. 라벨과의 정합보다 숫자 단독의 오독을 우선으로 판단
- **초기화 창 8시로 통일** — 지수는 없고 종목은 6시였던 두 기준을 하나로. 8시 앞 두 시간은 마감 표면 유지
- **제거 대신 0 합성** — 개장 전 응답이 0이라는 주장이 주석에만 있고 실측이 없어, 결과를 주장에 맡기지 않는 쪽으로
- **기준일을 거래일 축으로** — 적재 시각에 종속되던 값을 표시 중인 값의 거래일로. 개장 전은 이 규칙의 한 경우가 됨
- **stale 세션 방어** — 창 판정 앞에 서버 세션 조건. 오래된 응답에선 기존 마감 표시로 떨어짐

라벨 하나 확인하러 앉았다가 표시 규칙을 다시 세우고 나왔다. 다섯 세션 전 결정을 뒤집은 건데, 그때 판단이 틀렸다기보다 라벨과 등락의 관계만 보고 숫자가 단독으로 어떻게 읽히는지를 안 본 것에 가깝다. 실물 화면을 보기 전까지는 그 차이가 안 보였다.
