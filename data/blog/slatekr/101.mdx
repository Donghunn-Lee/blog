#100에서 외부 cron으로 정시 스케줄 설계를 완료하고, 정상 동작 확인 후 계획대로 schedule 블록 제거로 이번 세션을 열었다. 이어서 F39를 probe부터 구현까지 당일에 닫았고, 다음 순번이던 모바일 반응형(E36)은 실기기 검증까지 붙는 분량이라 단독 세션으로 미뤘다. 빈 자리에는 #091부터 걸려 있던 autoanalyze 원인 조사(F29)를 넣었다. 셋 다 크지 않은 작업인데, 각자 원인이 또렷해진 세션이었다.

## schedule fallback 제거

어제 이관한 cron-job.org 트리거의 첫날 관측이 green이었다 — daily 16:00:29 정시 발화, 해외 분봉 30분 간격 정연. fallback으로 하루 남겨뒀던 GitHub schedule 블록의 역할이 끝나서, 5개 워크플로에서 걷어냈다.

부수 정리가 하나 있었다. daily의 토요일 분기 조건에 남아 있던 `github.event.schedule` 비교는 dispatch 트리거에선 항상 빈 값이라 죽은 절이다. `inputs.mode` 하나로 단순화했다.

```yaml
# before
if: ${{ github.event.schedule != '0 7 * * 6' && inputs.mode != 'overseas-only' }}
# after
if: ${{ inputs.mode != 'overseas-only' }}
```

이제 트리거도 분기도 파라미터 한 축이다. F37 종결.

## rail과 홈만 멈춰 있던 해외 현재가

F39의 증상은 같은 값이 화면마다 다르게 사는 거였다.

| 지점 | 현재가 텍스트 소스 | 라이브 |
| --- | --- | --- |
| 홈 해외 셀 | SSR EOD snapshot | ✗ — 스파크라인만 라이브 |
| 지수 페이지 rail | SSR EOD | ✗ — 폴링 자체 없음 |
| detail pane | 최신 분봉 → live 셀 합성 | ✓ |

처음엔 캐시 stale을 의심했는데 아니었다. SSR 3600초, 분봉 API 장중 120초 — 숫자가 멀쩡했다. 원인은 소비 지점이다. 병합 유틸도 폴링 훅도 #093~#094에서 다 만들어져 있는데, **분봉에서 현재가·등락률을 합성하는 로직이 detail pane에만 인라인으로** 있었다. 홈은 폴링 받은 분봉을 스파크라인 그리는 데만 쓰고, 텍스트는 여전히 EOD를 읽고 있었다.

국내엔 이 문제가 없다. quote API가 live 값을 완성해서 주니까 화면은 받아서 표시만 하면 된다. 해외는 quote 대신 분봉 폴링 아키텍처라(#093), "분봉 → 현재가 합성"이라는 한 단계가 화면마다 필요한데 그 단계가 한 곳에만 존재했던 거다.

수정 순서는 이랬다.

1. detail pane의 합성 로직을 `buildIndexCell` 순수 함수로 추출 + 유닛 7케이스
2. detail pane을 추출 함수로 교체 — **거동 완전 불변이 회귀 기준**
3. rail·홈 해외 셀에 배선, 분봉 없으면 기존 EOD fallback

detail pane 패턴을 두 화면에 복사하면 같은 로직이 세 곳에 늘어난다. 추출을 1단계로 앞세워서 중복이 생길 틈을 없앴다.

걸렸던 게 하나 있었다 — rail에 폴링 훅을 새로 넣으면 호출이 3지수만큼 늘지 않나. 확인하니 endpoint가 SPX·COMP·NDX 배치 응답이고 TanStack Query 키가 고정이라, rail·detail·홈 어디서 훅을 불러도 캐시 엔트리 하나를 공유한다. 네트워크 왕복 증가 0. 폴링도 응답의 marketOpen 게이트로 미국 정규장에만 돈다.

지금은 미국 폐장 시간대라 검증은 반쪽이다. 세 지점의 현재가·등락률이 전부 같은 값으로 일치하는 것까지 확인했고, EOD가 라이브로 올라가는 순간은 오늘 밤 미국 세션에서 본다.

## autoanalyze가 daily_prices만 건너뛴 원인

#091에서 daily_prices의 planner 통계가 10.8만 행 시절에 멈춰 있는 걸 발견하고 수동 ANALYZE로 증상만 걷은 뒤, 원인 조사를 F29로 남겨뒀었다. 그때 가설은 Neon의 scale-to-zero — 컴퓨트가 유휴로 잠들면 autovacuum 트리거가 밀린다는 쪽이었다.

`pg_stat_user_tables` 한 번으로 정리됐다. quote_snapshots·overseas_index_intraday·stocks는 어제까지 autovacuum·autoanalyze가 정상 발화 중이었다. autovacuum은 살아 있다. daily_prices만 `last_autoanalyze`가 공란이었다. 가설이 틀렸다기보다 #091 땐 표본이 daily_prices 하나뿐이라 비교 대상이 없었던 거다.

남은 답은 산수였다.

- autoanalyze 발화 임계 = 50행 + 테이블의 10% = **약 63만 행 변경**
- 일일 적재 = 약 2,700행
- → 발화까지 **약 230일**

`n_mod_since_analyze`가 21,075행 — #091 수동 ANALYZE 이후 8일 × 2,700과 정확히 맞물린다. 작은 테이블들은 하루치 변경으로 10%를 금방 넘어 정상 발화하고, daily_prices는 클수록 임계가 멀어진다. append-only 대형 테이블의 전형이고, Neon과는 무관했다.

재발 방지는 두 안을 놓고 봤다.

| 안 | 내용 | 걸리는 점 |
| --- | --- | --- |
| per-table 설정 | `ALTER TABLE`로 analyze scale factor 하향 | DB 콘솔에만 존재 — 코드만 봐선 알 수 없다 |
| 명시적 ANALYZE | fetch_prices 적재 완료 직후 1회 실행 | collector 코드 몇 줄 |

명시적 쪽으로 갔다. 적재가 성공한 run에서만 통계가 따라 갱신되는 결합이 깔끔하고, verify_daily_freshness처럼 관리 장치가 repo에 보이는 방식과 결이 같다. 디테일 하나 — ANALYZE 실패는 WARNING만 남기고 전파하지 않는다. 통계 갱신이 실패했다고 적재 성공까지 실패로 덮으면 안 되니까. 600만 행 테이블의 ANALYZE는 몇 초 수준이라 비용은 없는 셈이다.

한 줄 드롭도 있었다. E24(순위 거래량 탭 등락률 미표시)는 #096 이후 재현이 안 돼 삭제했다.

## 정리

- **F37 종결** — schedule fallback 5개 제거, 토요일 분기를 mode input 단일 축으로 정리
- **F39** — 분봉→현재가 합성이 detail pane에만 있던 걸 `buildIndexCell`로 추출해 rail·홈에 배선. 폴링 비용 증가 0, 폐장 값 일치 확인, 라이브 승격은 오늘 밤 실측
- **F29 종결** — Neon 가설 기각. autoanalyze 10% 임계 vs 일일 2,700행이라는 산수를 확정하고, 적재 직후 ANALYZE로 봉인
- **E24 삭제** — 재현 불가

셋 다 앞 세션들이 깔아둔 것의 끝단이었다 — cron 이관의 fallback, 해외 분봉 아키텍처의 마지막 소비 지점, #091에서 미룬 원인 조사. 새로 쓴 코드는 순수 함수 하나 정도인데, 걸려 있던 항목이 넷 정리됐다.
