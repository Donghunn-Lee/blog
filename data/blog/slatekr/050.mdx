#049 끝에 관심종목 그룹 기능(E5)을 다음 작업 후보로 적어뒀다. 이번에 그걸 시작했다.

그런데 막상 범위를 잡아보니 한 세션에 안 들어갔다. 그룹을 다루려면 store를 다대다로 갈아엎어야 하고, 그룹 생성·삭제·이름변경 CRUD가 붙고, 종목 상세에서 어느 그룹에 넣을지 고르는 동선이 필요하고, 관리용 검색 모달까지 들어간다. 한 편으로 묶기엔 결정 포인트가 너무 많았다.

그래서 세 세션으로 나눴다.

| 세션 | 범위 |
| --- | --- |
| #050 (이번) | store 다대다 재설계 + 읽기·전환 가능한 페이지 골격 |
| #051 | 그룹 CRUD + 종목 상세의 다중 그룹 선택 UI |
| #052 | 그룹 관리 모달 (종목 검색 + 그룹 일괄 지정) |

의존성 순서가 자연스럽게 경계를 정해줬다. 구조(store)가 먼저 서야 그 위에서 읽기 UI가 돌고, 읽기가 돌아야 CRUD를 붙일 화면이 생기고, 마지막에 검색 모달이 얹힌다. 이번 글은 첫 칸 — 구조와 골격까지다.

## 최근 검색 store 이름 바로잡기

작업을 시작하면서 "관심종목 페이지 첫 탭에 최근 조회를 두고, 홈에 이미 있는 최근 조회 뱃지랑 같은 store를 쓰면 되겠지"라고 생각했다. 그런데 코드를 열어보니 홈에 있던 건 최근 **조회**가 아니라 최근 **검색**(`useRecentSearchesStore`)이었다. 내 착각이었다.

다만 동작을 따라가 보니 이름만 "검색"이지 실제로는 조회에 가까웠다. 기록 시점이 검색창이 아니라 **종목 상세 페이지 마운트**였다. 검색을 거쳐 들어오든 URL을 직접 치고 들어오든, 상세 페이지를 보면 다 기록된다. 처음 의도부터 "본 종목"이었는데 이름만 검색으로 붙어 있던 셈이다.

그래서 이름을 동작에 맞췄다. 로직은 그대로 두고 네이밍과 상수만 손봤다.

- `useRecentSearchesStore` → `useRecentVisitedStore`
- `RecentSearchRecorder` → `RecentVisitedRecorder`
- 저장 cap 10 → 50 (관심종목 페이지 첫 탭에서 더 보여주려고)
- 홈 뱃지는 `slice(0, 10)`로 노출 개수 기존 유지

저장 키가 바뀌면서 기존 localStorage 데이터는 날아가지만, 최근 조회는 휘발성 편의 기능이라 마이그레이션은 안 했다. 가벼운 변경이라 여기까지.

## store를 다대다로

본체는 여기다. 관심종목 store가 지금까지 이런 모양이었다.

```ts
type WatchlistItem = {
  ticker: string;
  name: string;
  market: "KOSPI" | "KOSDAQ";
  addedAt: number;
};
// state: { items: WatchlistItem[] }  — 단순 배열
```

그룹이 붙으면 **한 종목이 여러 그룹에 속하고, 한 그룹이 여러 종목을 담는** 다대다가 된다. 이걸 store에서 어떻게 들고 있을지가 첫 결정이었다. 세 가지가 보였다.

| 안 | 구조 | 문제 |
| --- | --- | --- |
| 양방향 | `groupTickers` + `tickerGroups` 둘 다 보관 | 두 배열을 항상 같이 갱신해야 함 → 동기화 어긋나면 버그 |
| 단일 소스 | `memberships: { groupId, ticker }[]` 하나만 + 조회는 selector로 파생 | 양방향 조회가 매번 O(n) 필터 |
| 그룹 내장 | `groups: { id, name, tickers[] }[]` | 종목 → 그룹 역방향 조회가 매번 전체 순회 |

단일 소스로 갔다. 관심종목은 cap이 50이라 O(n) 필터 비용이 사실상 무의미하고, 매핑을 한 군데서만 들고 있으니 동기화 버그가 원천적으로 안 생긴다. 양방향 조회는 selector로 뽑으면 된다.

state는 이렇게 잡았다.

```ts
type WatchlistGroup = { id: string; name: string; order: number; createdAt: number };
type Membership = { groupId: string; ticker: string; addedAt: number };
type StockMeta = { name: string; market: "KOSPI" | "KOSDAQ" };

type WatchlistState = {
  groups: WatchlistGroup[];
  memberships: Membership[];              // 다대다 단일 소스
  stockMeta: Record<string, StockMeta>;   // ticker → 메타 1벌
  // ...
};
```

종목 메타(`name`/`market`)를 membership에 같이 넣지 않고 `stockMeta` 맵으로 뺀 건, 같은 종목이 여러 그룹에 있을 때 메타가 중복되기 때문이다. ticker당 한 벌만 두고, 종목이 모든 그룹에서 빠지면 그때 메타도 같이 지운다.

양방향 조회는 selector 두 개로 파생시켰다.

```ts
selectTickersByGroup(state, groupId)   // 그룹 → 종목들
selectGroupsByTicker(state, ticker)    // 종목 → 그룹들 (#051에서 사용)
```

actions도 새 구조에 맞췄다. addToWatchlist는 groupId를
받되 안 주면 기본 그룹으로, removeFromWatchlist는 전 그룹에서
제거 + 메타 정리, isInWatchlist는 "어느 그룹에든 있으면 true"로
파생. cap 판정도 예전 items.length에서 distinct ticker 수로
바꿨다 — 같은 종목이 여러 그룹에 걸칠 수 있으니 그래야 50개
상한이 의도대로 동작한다.

### 그룹이 0개일 때

"모든 관심종목은 1개 이상의 그룹에 속한다"를 규칙으로 잡으니, 그룹이 하나도 없는 신규 사용자가 종목을 등록하려는 순간 갈 곳이 없어진다. 세 가지 처리가 가능했다 — 등록 시 그룹 먼저 만들게 강제, 기본 그룹 자동 생성, 아니면 그냥 그룹 0개(미분류) 허용.

미분류 허용은 방금 세운 규칙을 깨고, 강제 UI는 첫 사용 경험이 번거롭다. 기본 그룹 "내 관심 종목"을 처음부터 하나 만들어두는 쪽으로 갔다. 초기 state에도, 마이그레이션에도 이 그룹이 항상 존재하도록 보장했다. 이름은 #051에서 바꿀 수 있게 할 예정이라 무난한 기본값이면 됐다.

설령 기본 그룹을 삭제하고 관심 종목을 등록하려는 경우에도, 그룹을 먼저 생성하도록 안내하면 된다.

## 기존 사용자 데이터 보존 — persist migrate

store 구조를 통째로 바꾸니까 이미 관심종목을 저장해둔 사용자 데이터가 문제였다. 옛 `items[]`를 그대로 두면 새 구조가 못 읽는다.

zustand persist의 `version` + `migrate`로 처리했다.

```
version 0 (구):  { items: WatchlistItem[] }
        ↓ migrate
version 1 (신):  기본 그룹 "내 관심 종목" 생성
                → 각 item을 그 그룹의 membership으로
                → 각 item의 name/market을 stockMeta로
                → items 필드 제거
```

`addedAt`은 기존 값을 그대로 옮겨서 정렬 순서가 유지되게 했다. 최근 조회 store는 날려도 됐지만 관심종목은 사용자가 직접 쌓은 영구 데이터라 보존이 맞다. 같은 "저장 데이터"라도 휘발성이냐 영구냐에 따라 마이그레이션 판단이 갈린 셈이다.

## 별표는 일단 기본 그룹으로

종목 상세의 별표 버튼은 원래 다중 그룹 선택 UI(어느 그룹에 넣을지 체크)를 붙일 자리다. 그런데 그건 #051 범위라, 이번엔 store만 바꾸고 동작은 안 건드리는 선택을 했다.

`addToWatchlist(item, groupId?)`에서 `groupId`를 안 주면 기본 그룹에 들어가게 했다. 기존 별표 동작(누르면 등록, 다시 누르면 해제)이 그대로 유지되고, 다중 그룹 선택은 #051에서 `groupId`를 채워 호출하는 식으로 얹으면 된다. `isInWatchlist`는 "어느 그룹에든 있으면 true"로 파생.

cap 판정도 손봤다. 예전엔 `items.length`였는데 이제 같은 종목이 여러 그룹에 걸칠 수 있으니, distinct ticker 수로 세야 50개 상한이 의도대로 동작한다.

## 페이지 골격

마지막은 관심종목 페이지를 그룹 전환이 되는 구조로 바꾸는 작업. CRUD 버튼은 아직 없고 읽기·전환만이다.

```
좌측 패널 (데스크탑)          우측
─ 최근 조회   ← 첫 탭 고정      선택한 탭의 종목 리스트
─ 내 관심 종목                 (WatchlistRow 그대로 재사용)
─ (그룹들…)
```

좌우 2단으로 잡고, 모바일에선 좌측 패널을 상단 가로 스크롤 탭으로 접었다. 본격적인 반응형 점검은 F1 트랙에서 따로 돌 거라, 여기선 390px에서 안 깨지는 수준까지만.

첫 탭 "최근 조회"는 `useRecentVisitedStore`를 읽고, 그룹과는 무관하게 항상 맨 앞에 고정된다. 휘발성이라 휴지통(수동 삭제)은 안 달았다. 행은 #049에서 만든 `WatchlistRow`를 그대로 썼는데, 최근 조회 행엔 휴지통이 없어야 해서 `onRemove`를 optional로 바꿨다 — 없으면 휴지통을 안 그린다. 별도 행 컴포넌트를 새로 만드는 것보단 이게 깔끔했다.

데이터 fetch는 #049의 `useQueries`(가격 + 공시 카운트) 흐름을 그대로 두되, 선택한 탭의 종목 목록에 대해서만 돌게 `tickersKey`를 탭 기준으로 구성했다.

빈 상태는 일단 두 가지만 — 그룹에 종목 0개, 최근 조회 0개. 그룹 자체가 0개인 경우는 기본 그룹이 항상 있으니 안 생긴다. 그룹 전체 삭제 같은 분기는 CRUD가 붙는 #051에서 같이 다룬다.
