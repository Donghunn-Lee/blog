리드미를 종결하고, 이력서 수정중에 있었다. 그러나 거의 다 썼다고 생각하고 다시 느긋하게 읽어보니, 뭔가 프론트엔드 포트폴리오로는 애매하게 읽히는 데가 있었다. 원인을 문장이 아니라 구조로 판단해 개요부터 다시 썼다. 손대다 보니 회고에 쓸 사례를 맞추느라 종목 상세 모바일 CLS를 고치고, 컴포넌트 테스트도 추가했다. 코드까지 손보게 될 줄 모르고 지난 세션을 번외 세션으로 했는데, 이번 블로그에 그 내용을 추가한다.

## 번외 세션 요약

- **README 구조 재작성** — 개요를 부분 실패 UI · 클라이언트 데이터 흐름 순으로 재배치, 수집 파이프라인 노트는 collector README로 이동
- **차트 컴포넌트 순수 헬퍼 추출** — 시리즈 매핑 · 범례 · 눈금 포맷터 3모듈 분리, 1,221 → 935줄
- **종목 상세 모바일 CLS** — 헤더 · 지표 · 시세 스켈레톤을 실제 행 구조로, 장외 측정 0.09 ~ 0.11 → 0.001
- **회고 절 재작성** — "판단을 되돌린 기준 2개" 구조로

CLS 수법은 #186의 지수 페이지와 같다. 스켈레톤이 값과 같은 display와 치수를 갖게 하는 것인데, 이번에는 높이를 px로 못 박는 대신 실제 패널과 같은 행 구조에 같은 텍스트 토큰을 써서 맞췄다. 글꼴이나 토큰이 바뀌어도 스켈레톤이 따라가고, 브레이크포인트마다 값을 둘 필요가 없다.

## 장중 검증 — 성능 표의 마지막 공백

스켈레톤 수정의 마지막 커밋은 정적 높이 일치만 확인하고 올렸었다. 남은 이동의 출처가 그 스켈레톤 하나로 분해돼 있어서, 검증은 장중 PageSpeed Insights가 겸하기로 했기 때문이다. 장이 열린 오전에 조합당 3회, 회차 간격 60초 이상으로 쟀다.

| 조합 | 성능 | LCP | CLS |
|---|---|---|---|
| 종목 상세 모바일 | 82 (81~83) | 4.7s (4.6~4.9) | 0 (0~0.001) |
| 종목 상세 데스크톱 | 100 (99~100) | 0.7s | 0.001 (0~0.001) |
| 지수 데스크톱 | 98 | 1.1s | 0.031 (3회 동일) |

기준은 "장중 CLS가 0.01 이상 남으면 로컬에서 다시 분해"였는데 전 회차 0.001 이하로 끝났다. 성능 표의 종목 상세 행을 갱신하고(모바일 76 → 82, CLS 0.113 → 0) 지수 데스크톱 행을 추가해, 표가 세 페이지 × 모바일 · 데스크톱 여섯 행으로 완결됐다.

## 컴포넌트 테스트 추가

#087에서 테스트를 순수 함수로 한정할 때부터 컴포넌트 테스트가  공백이고(F101), 외부 평가 두 번이 똑같이 짚었다. 그동안 리뷰어에게 바로 보이지 않는 작업이라 미뤄 오면서 공백 자체는 README에 밝히고 있었지만, 포트폴리오 태그를 앞두고 셈이 바뀌었다. 태그 뒤에 테스트를 넣으면 저 문장과 코드가 어긋나 재태그를 해야 한다. 어차피 할 일이면 태그 전이 싸다.

방식부터 정했다.

| 후보 | 판정 |
|---|---|
| Playwright E2E 스모크 | 기각. live 데이터 의존이라 CI에서 간헐 실패 → README 상단 CI 배지가 빨개짐. CI 밖에 두면 "테스트는 있는데 CI는 안 도는" 어중간한 상태 |
| **jsdom + Testing Library** | **채택.** mock으로 돌아 기존 Vitest · CI에 그대로 편입 |

조건은 기존 node 테스트 1,194개에 영향이 없을 것. 전역 설정은 node 그대로 두고 컴포넌트 테스트 파일 첫 줄에만 jsdom 환경 지시문을 붙였다. 공용 셋업도 setupFiles에 넣으면 node 테스트 전체에 적용되니, matcher 등록과 cleanup을 담은 헬퍼를 컴포넌트 테스트에서만 import하는 쪽으로 풀었다.

#087에 "async Server Component는 렌더를 지원하지 않아 E2E 영역"이라고 적었었는데, 반쯤만 맞는 말이었다. render에 바로 넣을 수는 없지만 컴포넌트를 함수로 await한 뒤 반환된 트리를 render하면 되고, 하위가 전부 동기 컴포넌트인 핵심 지표 섹션에서는 이 방식이 성립했다. 덕분에 부분 실패 배지를 Suspense 없이 단위 테스트로 검증할 수 있었다.

대상은 전수가 아니라 README가 주장하는 상호작용 3건의 증빙으로 한정했다.

- 검색 combobox 키보드 탐색 — 방향키 경계 · Enter 이동 · Escape, 4케이스
- 부분 실패 배지 — 가격 실패 시 PER · PBR · 시가배당률에만 배지, 전부 성공 · 섹션 에러와 구분, 3케이스
- 서버 조회 전 편집 비활성 — 버튼 · 배지 · "조회 실패 시 PUT 0회"까지, 5케이스

5파일 12케이스, 구현 코드 수정 0. README 문장은 "핵심 상호작용은 Testing Library 컴포넌트 테스트로 검증합니다"로 바꿨다.

## 장 전에 연 탭의 분봉 폴링

한계 절에는 "개장 전에 연 탭은 09:00이 지나도 분봉 폴링이 시작되지 않는다"는 줄도 있었다. 아침에는 이 줄만 지우고 코드는 두기로 했다. 같은 계열의 다른 한계들은 적지 않았는데 이것만 적혀 있어 오히려 비일관이었고, README가 자동 재개를 주장한 적도 없어서다.

그런데 고칠 수 있는지 probe를 돌려 보니 결정의 전제가 둘 다 흔들렸다. 문제 범위가 문장보다 넓었고(프리마켓 중에 연 탭도 세션 전환 응답에서 멈춰 전부 걸린다), 수정이 새 설계가 아니었다. 헤더 시세 훅이 같은 문제를 이미 클라이언트 시계로 풀어 두고 있어서, 그 패턴을 옮기면 끝이었다.

```
전: 폴링 여부 = 마지막 응답의 세션 값
    → 폴링이 멈추면 새 응답이 없어 영원히 못 깬다
후: 60초마다 클라이언트 시계로 현재 세션 판정
    → 활성 세션이면 refetch, 09:00 뒤 1분 내 재개
```

옮기면서 챙긴 게 하나 있다. TanStack Query의 refetchInterval은 숨은 탭에서 자동으로 쉬지만 직접 만든 setInterval은 안 쉰다. 틱마다 탭이 보이는 상태인지 확인하는 조건을 같이 넣었고, 검증은 fake timer로 했다 — 08:59 틱에 요청 0회, 09:01 틱에 1회. 장중 실측 없이 닫을 수 있는 수정이라, 아침의 "코드는 안 건드린다"를 저녁에 뒤집고도 부담이 없었다. 엄밀히는 판단이 틀렸다기보다 수정안의 실체를 모르는 채 내린 결정이었던 거지만.

## 마감 작업과 태그

- **pykrx 분리** — 수동 백필 스크립트 하나가 쓰는 pykrx가 공용 requirements에 있어, 수집 워크플로 7개가 실행마다 pandas · numpy · matplotlib까지 설치하고 있었다. 백필 전용 requirements로 분리
- **주석 정리** — 저장소 전체 주석을 훑어 작업 맥락 · 변경 이력이 남은 17파일 정돈
- **최종 리뷰** — 태그 직전, 이번 변경분만 보는 콜드 리뷰 1회. 사실 불일치 · 바로 보이는 결함 0건

그러고 나서 `v1.0-portfolio` 태그를 걸고, README의 코드 링크 16곳을 태그 경로로 고정했다. 이후 코드가 바뀌어도 README가 가리키는 코드는 그대로 남는다. collector README나 LICENSE 같은 문서 링크는 반대로 상대 경로로 뒀는데, 문서는 최신본이 보이는 게 맞아서다.

## 정리

- **F101 종결** — 컴포넌트 테스트 환경 도입(jsdom 파일 단위 격리) + README 주장 3건 증빙 5파일 12케이스, 품질 절 문장 교체
- **F127 장중 검증 종결** — 종목 상세 모바일 CLS 0, 성능 표 6행 완결
- **F114 일부 구현** — 분봉 폴링을 클라이언트 시계 축으로, 장 전 탭 자동 재개
- **G3 종결** — 태그 `v1.0-portfolio` + 코드 링크 고정 + 수치 줄 갱신
- **pykrx 분리** — 수집 워크플로 설치 경량화

미뤄 둔 항목들을 태그 직전에 당긴 세션이었다. 기준은 하나였다 — 태그 뒤로 미루면 비용이 커지는가. 테스트와 폴링 수정이 거기 걸렸고, 차트 컴포넌트 분해처럼 안 걸리는 건 그대로 미루되 한계 절에 한 줄로 복원했다. 적어 둔 한계가 줄어든 만큼 늘어난 줄도 있는 셈인데, 지금은 그 비대칭이 맞다고 생각한다.
