[#017](/blog/slatekr/017/)에서 DART 공시 원문 구조를 까보고 처리 방향을 정했다. 단순 정규식으로 태그만 제거해도 86% 압축이 되고, 정교한 보일러플레이트 룰을 추가해도 +4%밖에 안 된다는 게 핵심 결론이었다. "복잡하게 갈 필요가 없다"는 결정이었다.

이번엔 그 결정을 production 코드로 옮기는 과정을 다룬다. spike 작업 결과를 어떻게 production 코드에 반영할지, 그리고 그 결과가 실제로 spike와 동일하게 동작하는지 확인하는 과정까지가 이번 글의 주제다.

---

## 작업 범위 쪼개기

지난번 정리한 다음 작업 목록을 다시 보면 이렇다.

- DART `document.xml`을 production 코드에서 받아오는 모듈
- 텍스트 추출 함수 (XML 태그 제거 + 공백 정리)
- Gemini API 연동
- DB 캐싱 테이블 설계
- 프롬프트 디자인

다섯 개를 한 번에 하면 한 작업 단위가 너무 커져서 우선 나눴다. 외부 API 의존성이 들어가는 Gemini 연동은 SDK 도입과 무료 티어 제약 확인부터 해야 하는 별개의 작업이고, 프롬프트 디자인은 그 자체로 충분히 디테일이 많은 글감이다.

이번 작업은 **(1) 본문 추출 모듈 + (2) DB 캐싱 레이어**까지로 좁혔다. 본문을 받아오는 코드와, 그 결과(요약본)를 저장하는 코드는 같은 데이터 파이프라인으로 묶인다.

Gemini 연동, 프롬프트, UI 통합은 다음 글들에서 다룰 예정이다.

## 본문 추출 모듈 — 검증 코드를 production으로

spike 단계에서 만든 검증 스크립트(`extract_text.py`)는 4단계 정제 파이프라인을 갖고 있었다.

1. `<LIBRARY>` 블록 제거 (정정신고 메타 + 커버 페이지)
2. `ENG="..."` 영문 병기 속성 제거
3. XML 태그 전체 제거
4. 공백 정리 + 보일러플레이트 줄 단위 필터

이걸 TypeScript로 옮긴다. 옮길 때 한 가지 결정이 필요했다 — XML parser 라이브러리를 도입할까?

처음엔 `fast-xml-parser` 같은 걸 쓰는 게 자연스러워 보였다. XML을 다루는 코드인데 정규식만 쓰는 건 "원시적"이라는 인상이 있다. 그런데 spike 코드를 다시 보니 정제 파이프라인이 전부 정규식과 문자열 처리만으로 끝난다. 트리 순회나 노드 조회가 필요한 단계가 하나도 없다.

> 💡 spike에서 검증된 로직이 라이브러리 없이 동작했는데, 굳이 production에서 라이브러리를 끼울 이유가 없다고 판단했다.

XML 파서를 도입하면 의존성이 하나 늘고, 파서가 받아들이는 XML 형식의 엄격함(예: well-formed 검증)에 production 코드가 종속된다. DART XML이 항상 완벽하게 well-formed라는 보장이 없는 상황에서, 정규식이 오히려 더 견고할 수 있다.

결국 추가 의존성은 **`jszip` 하나만** 도입했다. ZIP 파일을 풀기 위한 라이브러리고, 이건 정규식으로 대체할 수 있는 게 아니라 필요했다.

## 외부 노출은 함수 하나만

모듈 구조를 잡을 때 한 가지 원칙을 세웠다. **호출자는 단순한 인터페이스 하나만 알면 되게 하자.**

내부적으로는 ZIP 다운로드, XML 추출, 태그 제거, 보일러플레이트 필터 등 여러 단계가 있지만, 이걸 외부에 다 노출하면 호출하는 쪽에서 "어떤 순서로 호출해야 하지?"를 매번 신경 써야 한다. 그건 모듈 설계가 책임을 위로 떠넘기는 거다.

```ts
// 외부 노출 — 이것 하나만
export const fetchDisclosureText = async (rceptNo: string): Promise<string>

// 내부 헬퍼 — 모듈 외부에서 안 보임
const fetchDocumentZip = async (rceptNo: string): Promise<ArrayBuffer> => { ... }
const extractXmlFromZip = async (buffer: ArrayBuffer): Promise<string> => { ... }
const cleanXmlToText = (xml: string): string => { ... }
const removeLibraryBlocks = (xml: string): string => { ... }
const removeEngAttributes = (xml: string): string => { ... }
const stripTags = (xml: string): string => { ... }
const cleanWhitespace = (text: string): string => { ... }
const removeBoilerplate = (text: string): string => { ... }
```

호출자는 `fetchDisclosureText(rceptNo)` 하나만 알면 된다. 다음은 정제된 텍스트를 받아서 LLM에 던지면 끝이다. 내부 단계가 어떻게 쪼개져 있는지 신경 쓸 필요가 없다.

내부 함수들은 export하지 않지만 함수 단위로 쪼개둔다. 단계별 디버깅이 가능하고, 각 함수가 순수 함수라 테스트하기도 쉽다.

## ZIP 응답 검증 — DART의 작은 함정

`document.xml` API의 정상 응답은 ZIP 바이너리지만, 에러 시에는 JSON으로 status code를 반환한다. spike 코드에선 이걸 처리하지 않고 그냥 ZIP을 풀려고 시도해서 에러가 났을 거다.

production에서는 ZIP인지 아닌지를 판별해야 한다. 두 가지 방법이 있었다.

- HTTP `Content-Type` 헤더 확인
- ZIP 매직넘버 검증 (첫 4바이트가 `0x50 0x4B 0x03 0x04`인지)

매직넘버 쪽이 견고하다. 헤더는 서버 설정에 따라 부정확하게 나올 수 있는데, 매직넘버는 파일 자체의 시그니처라 우회될 일이 없다.

```ts
const buffer = await res.arrayBuffer();
const bytes = new Uint8Array(buffer, 0, 4);
const isZip = ZIP_MAGIC.every((b, i) => bytes[i] === b);
if (!isZip) {
  throw new Error("DART document.xml: 비ZIP 응답 (status code 응답 가능성)");
}
```

`Uint8Array(buffer, 0, 4)`로 첫 4바이트만 떼서 검사한다. 전체 버퍼를 새로 할당할 필요 없이 view만 만든다.

## 캐싱 레이어 설계

본문 추출이 끝나면 LLM에 던져 요약을 생성하고, 그 결과를 캐시해야 한다. #017에서 정한 대로 `disclosure_summaries` 테이블 하나로 처리한다.

스키마는 단순하다.

```sql
CREATE TABLE disclosure_summaries (
  rcept_no      VARCHAR(14)  NOT NULL,
  summary_text  TEXT         NOT NULL,
  model_name    VARCHAR(50)  NOT NULL,
  created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (rcept_no)
);
```

`rcept_no`(DART 공시 접수번호 14자리)를 PK로 사용한다. 동일 공시는 단일 요약만 저장된다. 사용자별 캐시가 아니라 전역 캐시다 — A 사용자가 요약한 공시를 B 사용자가 다시 클릭하면 LLM 호출 없이 DB에서 바로 반환된다.

`model_name` 컬럼은 어떤 모델로 생성된 요약인지 기록하기 위해 둔다. 나중에 모델을 바꾸거나, 같은 모델이라도 버전이 올라가면 이 정보가 필요할 수 있다.

`updated_at`은 일부러 안 넣었다. 모델이나 프롬프트가 바뀌어서 재생성하는 시나리오는 MVP 다음 단계다. 지금 단계에선 컬럼 늘려서 복잡도 키울 이유가 없다.

> 💡 한 가지 신경 쓴 건 `INSERT ... ON DUPLICATE KEY UPDATE`로 저장 함수를 짠 점이다. 같은 `rcept_no`로 다시 저장하면 갱신된다. 모델이나 프롬프트 변경으로 재생성하는 시나리오를 추가 컬럼 없이 자연스럽게 흡수한다.

## 스키마 마이그레이션 — Python 스크립트

테이블 생성은 앞선 작업에서 두어 번 한 것처럼 ORM이나 별도 도구 없이 일회성 Python 스크립트로 처리했다. 이전에도 같은 방식으로 한 번 써본 적이 있어서 그 패턴을 그대로 따랐다 — mysql.connector로 연결, load_dotenv로 환경변수 로드, IF NOT EXISTS로 멱등성.

아직까진 단순한 작업이었고, 간단한 테이블 변경이었기에 Python으로 일회성 스크립트를 만들어 처리했는데, 마이그레이션이 누적되거나 환경이 늘어나면 도구 도입을 검토할 예정이다.

## 도메인 모델 정규화

DB Row와 도메인 모델을 분리하는 건 SlateKR 처음부터 정한 규칙이다. UI 컴포넌트는 DB 컬럼명(snake_case)을 직접 받지 않고, 정규화된 도메인 모델(camelCase)만 받도록 했다.

```ts
// 외부 노출 — 도메인 모델
export type DisclosureSummary = {
  rceptNo: string;
  summaryText: string;
  modelName: string;
  createdAt: Date;
};

// 모듈 내부 전용 — DB Row
type DisclosureSummaryRow = {
  rcept_no: string;
  summary_text: string;
  model_name: string;
  created_at: Date;
};

const normalizeDisclosureSummary = (row: DisclosureSummaryRow): DisclosureSummary => ({
  rceptNo: row.rcept_no,
  summaryText: row.summary_text,
  modelName: row.model_name,
  createdAt: row.created_at,
});
```

`DisclosureSummaryRow`는 export하지 않는다. lib 내부 전용 타입이다. 외부에선 `DisclosureSummary`만 알면 된다.

## 검증 — production이 spike와 같은 결과를 내는가

코드는 다 짰지만, **TypeScript 컴파일이 통과한다는 건 타입이 맞다는 뜻이지, 로직이 맞다는 뜻은 아니다.** spike 코드(Python)와 production 코드(TypeScript)가 정말로 같은 출력을 내는지는 직접 비교해야 안다.

다행히 spike에서 step4까지 거친 결과 파일이 남아있었다. `extracted_20260428000814__4__보일러플레이트_제거.txt`. 105줄, 1,769자(개행 포함). 이걸 기준값으로 삼고 production 코드의 출력과 비교했다.

검증 방식은 일회성 Node 스크립트다. Vitest 같은 테스트 프레임워크를 도입할까도 생각했는데, "테스트 환경 셋업"이 또 다른 작업이 되는 게 부담이었다. 지금 필요한 건 한 번 비교해보는 거지 정식 테스트 인프라가 아니다.

`web/scripts/verify-disclosure-pipeline.ts`를 만들고 `tsx`로 직접 실행했다. 검증 항목은 4개로 나눴다.

1. **본문 추출 정확도** — 같은 `rcept_no`로 `fetchDisclosureText`를 호출해서 줄 수와 글자 수를 spike 결과와 비교
2. **캐시 미스** — 존재하지 않는 키 조회 시 `null` 반환 확인
3. **저장 동작** — `saveDisclosureSummary` 호출이 에러 없이 끝나는지
4. **캐시 히트** — 저장한 데이터가 정규화를 거쳐 도메인 모델로 정확히 돌아오는지

## 검증 결과

```
=== 검증 1: 본문 추출 ===
줄 수: 105 (spike: 105, ✓ 일치)
글자 수 (개행 포함): 1769 (spike: 1769, ✓ 일치)
첫 줄: "주요사항보고서(감자 결정)" (✓ 일치)
마지막 줄: "기타" (✓ 일치)

=== 검증 2: 캐시 미스 ===
getDisclosureSummary 결과: ✓ null

=== 검증 3: 저장 ===
saveDisclosureSummary 완료 — 에러 없음 ✓

=== 검증 4: 캐시 히트 ===
rceptNo, summaryText, modelName 모두 일치 ✓
createdAt: Fri May 01 2026 ... ✓
```

> 💡 줄 수와 글자 수가 정확히 일치했다.

다행히 오류 없이 검증에 통과했다. Python `splitlines()`와 JS `split(/\r?\n/)`는 미묘하게 다르고, Python `re.search`와 JS `RegExp.test`도 동작이 미묘하게 다르고, trim 적용 시점에 따라서도 1~2자씩 어긋날 수 있다.

한 글자도 안 어긋났다는 건 정제 파이프라인의 4단계가 Python과 TypeScript 양쪽에서 동일하게 동작한다는 강한 증거다. 이후 LLM에 들어갈 입력 텍스트가 spike 단계에서 검증한 형태와 일관된다는 뜻이다.

## 정리

이번 작업의 무게중심은 **"spike 결과를 production 코드로 옮기되, 그 동등성을 객관적으로 확인하자"** 였다.

spike와 production은 환경이 다르다. 언어가 다르고, 라이브러리가 다르고, 실행 컨텍스트가 다르다. 같은 로직을 옮겨도 미묘한 차이로 결과가 어긋날 수 있다. 이걸 "타입이 맞으니 됐다"로 끝내면 나중에 LLM 출력이 이상할 때 원인을 찾기 어려워진다.

> 검증 스크립트는 그렇게 어렵게 만든 게 아니다. spike 결과 파일을 기준값으로 잡고, production 함수 호출 결과의 글자 수를 비교한 정도다. 한 시간도 안 걸렸다.

근데 이걸 안 했으면 다음 단계(Gemini 연동)에서 문제가 생겼을 때 "이게 본문 추출 단계 문제인지, Gemini 호출 문제인지"를 매번 의심해야 했을 거다. 지금은 본문 추출이 spike와 동일하다는 게 확정됐기 때문에, 다음 단계에서 문제가 생기면 그건 다음 단계의 문제다.
