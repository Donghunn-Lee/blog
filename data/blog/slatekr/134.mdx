#133에서 휴장일 TR을 실측해 거래일 캘린더 테이블을 세웠지만, 그건 collector까지였다. 웹은 여전히 #064에서 박아둔 국내 휴장일 상수 하나로 판정하고, 해외 지수의 세션 함수들은 휴장이라는 개념 자체를 모른다. 엿새 뒤 9/7이 미국 Labor Day라, 이대로 두면 그날 미국 3종이 존재하지 않는 세션을 조회하러 간다.

계획은 E47(재무 배당 축)이었는데, collector 쪽 맥락이 살아 있는 김에 F54 웹 축을 먼저 당겼다. 결과는 서버 판정의 테이블 전환과 해외 휴장 분기까지 3커밋이고, 클라이언트 쪽 전환은 다음으로 남겼다.

---

## 휴장 판정 소비처 전수

바꾸기 전에 소비처부터 훑었다. 국내 휴장 판정은 상수 파일 하나를 세션 유틸이 import하고, 그 파생 함수들을 서버와 클라이언트가 나눠 쓰는 구조였다.

| 분류 | 소비처 | 호출 방식 |
|---|---|---|
| 서버 | route 6곳 + lib 2곳 | 요청당 1회 |
| 클라이언트 | 차트·헤더·슬레이트 등 7곳 | 렌더 tick·60초 폴링 게이트에서 동기 호출 |

이 표가 경로 결정을 반쯤 정했다. 서버는 요청 시작에 테이블을 한 번 읽어 넘기면 되는데, 클라이언트 7곳은 동기 술어를 전제로 짜여 있어 비동기 조회를 끼우려면 파생 함수 시그니처부터 다시 설계해야 했다.

---

## 빌드타임 안이 성립하지 않는 이유

| 후보 | 판정 |
|---|---|
| 빌드 시 캘린더를 정적 상수로 재생성 | 기각. 해외 행은 어제·오늘만 매일 적재, 빌드 스냅샷이 배포 이후 날짜를 못 덮음 |
| route + 비동기 훅으로 클라까지 일괄 전환 | 기각. 클라 7곳의 동기 술어 전제와 충돌, 야간에 닫을 볼륨이 아님 |
| **서버만 선택 인자로 전파, 클라는 상수 유지** | **채택.** collector와 같은 시그니처 관례, 미전달 시 기존 동작 그대로 |

빌드타임 안은 처음엔 그럴듯했다. 클라 코드를 한 줄도 안 바꾸고 상수 파일만 재생성하면 되니까. 근데 적재 창과 배포 주기를 겹쳐보면 성립하지 않는다. 해외는 어제와 오늘 두 날짜만 매일 쌓이는데 빌드는 push할 때만 도니, 배포 다음 날부터의 휴장은 스냅샷에 없다. 매일 배포하는 프로젝트가 아니면 무효인 안이었다.

그래서 서버는 파생 함수마다 선택 인자로 캘린더를 받게 하고, 클라이언트는 상수인 채로 남겼다. 남는 갭은 임시공휴일 당일의 클라 라벨과 폴링 게이트 정도인데, 정기 휴장은 상수에 이미 있으니 실제로 어긋나는 날은 연에 한두 건이다.

---

## 캘린더를 어느 캐시에 태울지

서버가 요청마다 DB를 부르게 둘 순 없어서 캐시 층이 필요했다. 기본 선택지는 #102부터 시세 route 전반에 깔린 unstable_cache인데, 이번엔 쓸 수 없었다. 캘린더를 읽는 위치가 바로 그 route들의 캐시 함수 안이다.

| 후보 | 판정 |
|---|---|
| unstable_cache | 기각. route 캐시 안에서의 호출이라 Data Cache 중첩, 인자로 넘기면 캐시 키에 캘린더가 직렬화됨 |
| **모듈 스코프 memo, TTL 3600초** | **채택.** 토큰 캐시의 in-memory 층과 같은 패턴, 인스턴스당 콜드 1쿼리 |

조회가 실패하면 빈 캘린더를 돌려주고 memo에는 남기지 않는다. 판정 함수는 행이 없으면 어차피 폴백으로 떨어지니, 캘린더 층의 실패가 세션 판정을 죽일 일은 없다.

## 휴장일 상수 폴백 강등

#064에서 세 후보 중 상수를 골랐을 때 약점으로 적어둔 게 임시공휴일이었는데, 이제 그 자리를 테이블이 맡는다. 우선순위는 collector와 같다. 행이 있으면 개장 여부를 그대로 믿고, 없으면 폴백이다.

```ts
export const isKrxHoliday = (dateStr: string, calendar?: MarketCalendar): boolean => {
  const isOpen = calendar?.KRX?.[dateStr];
  if (isOpen !== undefined) return !isOpen; // 테이블이 정본, 상수보다 우선
  return KRX_HOLIDAYS_2026.has(dateStr);
};
```

| 시장 | 캘린더 행이 없을 때 |
|---|---|
| KRX | #064 상수 |
| 미국 | NYSE 상수 (기존) |
| 독일 | XETRA 상수 사흘 (신설, collector 값 미러) |
| 일본·홍콩·중국 | 주말만 — 표 자체가 없음 |

이 배치에서 9/7은 이중으로 걸러진다. 그날 아침 적재가 성공하면 테이블 행이 판정하고, 실패하더라도 NYSE 상수가 받친다. 테이블이 폴백 없이 혼자 일하는 첫날은 상수가 아예 없는 일본의 9/21 휴장이다.

## 해외 세션 함수의 휴장 분기

해외 지수 세션 함수 네 개는 주말만 알았다. 미국 휴장일이면 정규장으로 치고 폴링이 돌고, 직전 거래일 계산도 휴장을 건너뛰지 못했다. 수정 규칙은 하나로 뒀다. 휴장일의 반환값은 주말과 완전히 같게. 주말 early return 다음 줄에 같은 값을 돌려주는 휴장 return을 더하는 식이라, 캘린더를 안 넘기면 기존 동작 그대로다.

미국만 NYSE 상수로 직전 거래일을 걷던 전용 분기는 시장 공통 술어로 일반화했다. 기존 테스트에 미국 경로의 등가성을 직접 어설션하는 케이스가 있어 삭제가 안전한지 바로 확인됐고, 국경절 여드레를 걸어 9/30에 닿는지, Labor Day에 마감 경과가 null로 떨어지는지 같은 픽스처 테스트를 새로 뒀다.

---

## 하지 않은 것 둘

route 응답에 직전 거래일 필드를 실었다가 제거했다. 차트의 해외 기준일은 마지막 봉에서 파생하는 게 원칙이라(적재가 늦으면 라벨이 스스로 전일에 머무는) 시계에서 파생한 값으로 대체할 수 없었고, 그러면 소비처가 0인 필드를 "나중에 쓰겠지"로 남기게 되는데 그건 이 프로젝트가 계속 피해온 패턴이다.

테이블의 과거 행 트림도 검토하다 접었다. 직전 두 거래일만 남기면 테이블의 의미가 또렷해지긴 하는데, 오래된 행을 읽는 소비처가 없고 누적이 연 1,800행 수준이라 비용이 사실상 0이다. 오히려 남겨두면 게이트가 red일 때 그날 API가 뭐라고 답했는지 며칠 뒤에도 볼 수 있는 감사 로그가 된다.

## 작업 검증 및 기타 확인사항

로컬 확인은 심심했다. 지금 테이블 값이 상수와 일치하는 구간이라 국내 route 응답이 하나도 안 변하는 게 정답이고, 실제로 하나도 안 변했다. 테스트는 32건이 늘었고, 배포 후 응답 형태도 그대로였다.

진행에서는 한 번 미끄러졌다. 커밋 세 개 분량을 끊지 않고 한 호흡에 구현해버려서, 다 된 트리에서 각 커밋 상태를 스냅샷으로 역산해 게이트를 세 번 돌리고 나눠 담는 걸로 수습했다. 최종 상태가 원본과 해시 단위로 같은 건 확인했지만, 커밋 단위로 갔으면 없었을 한 바퀴다.

곁가지 둘. #133에서 미뤄둔 계측 정정을 서두에 소화했는데, 압축을 받으니 지수 일봉 전량 응답은 283KB(brotli)였고 CDN이 항상 MISS인 원인도 route의 Cache-Control(max-age=0)로 확정됐다. E65의 근거가 여기서 성립한다. 그리고 #133의 새벽 해외 게이트가 이날 아침 첫 실전을 PASS로 통과했다.

## 정리

- **F54 웹 서버 축** — route 6곳·lib 2곳이 테이블 우선·상수 폴백으로 판정. 클라 7곳은 상수 유지로 이월
- **해외 휴장 분기** — 세션 함수 4종이 휴장을 주말과 동일 취급, 미국 전용 분기는 공통 술어로 일반화
- **캐시 층** — unstable_cache 중첩 대신 모듈 memo 3600초
- **하지 않은 것** — 소비처 없는 응답 필드 제거, 과거 행 트림 드롭
- **세션 외 소화** — 계측 정정(283KB·CDN MISS 원인)과 새벽 게이트 첫 실전 PASS

diff보다 어디까지 바꾸지 않을지를 정하는 데 시간이 간 세션이었다. 실전 검증이 달력에 걸려 있는 게 좀 낯선데, 휴장 기능은 휴장일이 와야 일하는 물건이라 어쩔 수 없다.
