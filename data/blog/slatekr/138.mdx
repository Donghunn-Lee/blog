휴장일 판정은 #133에서 거래일 캘린더 테이블을 세우고 #134에서 서버 route가 그 테이블을 먼저 보게 바꿨지만, 브라우저에서 도는 코드는 아직 하드코딩 상수를 보고 있었다. 세션 라벨과 폴링 게이트가 여기 걸려 있어서, 임시공휴일이 생기면 서버는 알고 화면은 모르는 상태가 된다. 서버 축을 닫으면서 이월해 둔 F54의 완결 작업이다.

계획은 캘린더를 root layout에서 한 번 읽어 context로 내려보내고 클라이언트 소비처를 잇는 3커밋이었다. 그대로 됐고, 배선을 확인하려고 페이지 소스를 열었다가 캘린더 날짜가 하루 밀려 있는 걸 발견해 fix 두 건이 더 붙었다.

---

## 경계를 넘길 값의 형태

서버는 캘린더를 KST 오늘 기준 ±45일의 날짜→개장 여부 맵으로 들고 있다. 이걸 그대로 넘길지, 판정 결과 몇 개로 줄여 넘길지가 첫 결정이었다.

| 후보 | 판정 |
|---|---|
| 오늘 거래일 여부·다음 거래일 같은 판정 결과 몇 개 | 기각. 직전 거래일 계산이 날짜를 순회하고, 자정을 넘기며 상주하는 화면(홈·지수·관심종목)이 셋 |
| **날짜→개장 여부 맵을 그대로** | **채택.** 서버 타입이 이미 직렬화 가능한 plain object라 변환 0 |

국내만 잘라 보낼까 잠깐 생각했는데, 세션 유틸의 인자 타입이 캘린더 전체라 자르면 클라이언트에서 다시 조립해야 하고, 해외 행은 어제·오늘 이틀뿐이라 줄어드는 양도 없었다. 통째로 넘기기로 한 이 결정은 뒤에서 한 번 덕을 본다.

전달 수단은 셋 중에서 골랐다.

| 후보 | 판정 |
|---|---|
| Zustand store | 기각. SSR 값을 store에 hydration하는 경로가 새로 생김 |
| TanStack Query | 기각. 요청 1회가 늘고 첫 렌더는 폴백으로 그려짐 |
| **React context** | **채택.** SSR 값을 그대로 읽는 read-only 데이터. provider 밖이면 `undefined`를 돌려줘 기존 상수 폴백으로 떨어지게 |

도메인 context는 이 프로젝트에서 처음이다. 지금까지 `createContext`는 shadcn primitive 안에만 있었다.

## root layout에 DB 조회를 넣을 때

경로는 단순하다.

```
root layout (서버, 요청당 1회 조회)
  → Providers → MarketCalendarProvider
    → 클라이언트 소비처 useMarketCalendar()
      → 세션 유틸에 calendar 인자로 전달 (#134에서 이미 열어둔 자리)
```

리스크는 하나였다. layout에 데이터 조회가 들어가면 Next.js가 전 페이지를 dynamic으로 뒤집을 수 있고, 그러면 ISR 위에 세운 구조가 통째로 무너진다. `cookies()`나 `headers()`를 안 쓰면 layout은 static으로 남고, ISR 3600 페이지는 시간마다 재생성되니 서버 memo와 같은 주기다. 소비처가 없는 static 라우트에는 빌드 시점 값이 박히지만 그 값을 읽는 코드가 없어서 layout에 `revalidate`를 붙이지 않았다. 첫 커밋 게이트에 빌드 전후 라우트 표 비교를 넣었고, 27개 라우트 마커가 하나도 안 바뀌었다.

## 일곱 곳이 아홉 곳

처음 소비처 조사는 컴포넌트만 훑어 7파일이 나왔고 그대로 배선했는데, 커밋 뒤 보고에 목록 밖의 호출 하나가 딸려 왔다. 종목 시세 훅의 모듈 레벨 폴 게이트였다. 컴포넌트 기준이 아니라 캘린더를 받을 수 있는 함수 심볼 기준으로 다시 grep하니 지수 차트의 해외 분기까지 둘이 남아 있었다. 해외 쪽은 캘린더를 통째로 넘긴 덕에 인자 하나 붙이는 걸로 끝났고, 모듈 스코프 술어는 훅 안에서 값을 받아 인자로 넘기는 형태로 순수 함수를 유지했다.

## 하루 밀린 캘린더

배선 확인은 페이지 소스에서 미래 날짜를 검색하는 걸로 했다. 시세 payload엔 미래가 없으니 잡히면 캘린더다.

작업이 크게 복잡하진 않았으니 확인하고 빠르게 넘어가려 했는데, 확인된 값이 이상했다.

| 날짜 | 요일 | dev 페이지 소스 | DB |
|---|---|---|---|
| 09-04 | 금 | false | true |
| 09-05 | 토 | false | false |
| 09-06 | 일 | true | false |

전 구간이 하루 앞으로 밀린 패턴이었다. 첫 키가 collector 첫 실행일보다 하루 앞인 것도 같은 방향이다. 가설은 둘이었고, 확인 순서가 중요했다. 웹 변환 문제면 dev 한정이지만, DB 자체가 밀려 저장됐으면 prod가 7시간 뒤 금요일 개장을 휴장으로 판정한다.

DB는 정상이었다. 그러면 웹 변환이고, 원인은 DATE 컬럼이 드라이버에서 로컬 자정의 JS Date로 도착하는데 키를 만들 때 UTC 기준으로 문자열화한 것이었다. KST에서는 자정이 UTC 전날 15시라 하루가 빠진다. Vercel은 UTC라 로컬과 UTC가 같아 prod는 무영향이었고, #134에 배포된 뒤로 서버 판정이 어긋난 적은 없다. SQL에서 `to_char`로 문자열을 받아 JS Date 경유를 없애는 걸로 고쳤다.

## 같은 원인이 헤더에도

캘린더가 맞게 도착한 걸 확인하고 같은 dev 화면을 보는데, 종목 헤더 KRX 탭이 "전일 종가 · 09.02"였다. 바로 아래 기준일은 09-03이고, 가격과 등락은 09-03 종가로 맞았다. 라벨의 날짜만 하루 빠져 있었다.

여기서 자기 정정을 하나 해야 한다. #124에서 이 날짜를 만드는 헬퍼가 UTC 컴포넌트로 재산출하는 걸 "KST-safe 격리"라고 적었고, date-fns 로컬 format을 쓰는 다른 경로를 F66 구조 리스크로 남겨뒀다. 그때 전제는 드라이버가 UTC 자정으로 파싱한다는 것이었는데, 이번 관측은 로컬 자정이다. 전제가 뒤집히면 판정도 뒤집힌다.

| 경로 | KST dev | Vercel(UTC) |
|---|---|---|
| UTC 컴포넌트 추출 (#124 "격리") | -1일 | 정상 |
| date-fns 로컬 format (F66 "리스크") | 정상 | 정상 |
| `toISOString` (캘린더) | -1일 | 정상 |

안전하다고 적어둔 쪽만 dev에서 어긋나고 있었다. 헬퍼 하나만 바꾸면 되는 줄 알았는데 이 헬퍼가 헤더의 일봉 조회와 요청 단위 캐시를 공유하고 있어서 row 타입을 나눌 수 없었고, 그러면 선택지는 둘이었다.

| 후보 | 판정 |
|---|---|
| 헬퍼의 UTC 컴포넌트를 로컬 컴포넌트로 교체 | 기각. 3줄이지만 드라이버 파싱 방식에 계속 기대는 구조 |
| **일봉 SELECT 3곳을 `to_char` 문자열 수신으로 전환, row 타입 date를 string으로** | **채택.** 지수 일봉·캘린더와 같은 패턴, 다운스트림 스냅샷 타입은 이미 string이라 무변경 |

```
전:  DATE 컬럼 → JS Date(로컬 자정) → 파일마다 다른 문자열화
후:  DATE 컬럼 → to_char 'YYYY-MM-DD' → 문자열 그대로
```

F66은 여기서 닫혔다. 서버 시간대에 따라 결과가 달라지는 경로가 이제 없다.

## 라벨을 맞추다 본 지연 창

헤더 날짜가 09.03으로 돌아오자 다른 게 눈에 들어왔다. 비NXT 종목은 "장 마감 · 15:30"인데 NXT 종목의 KRX 탭은 "전일 종가 · 09.03"이다. 기준일이 바로 아래 있으니 날짜는 중복이고, 라벨을 통일하자는 게 처음 생각이었다.

날짜를 둔 이유는 #124에 적혀 있다. 15:30 마감 뒤 EOD 적재 전까지 KRX 탭은 DB의 전일 행을 보여주고 옆 NXT 탭은 당일 애프터장이라, 그 창에서 "장 마감 · 15:30"은 오늘 종가처럼 읽히는 거짓 라벨이 된다. 라벨 키를 달력 오늘에서 마지막 거래일로 바꾸는 선에서 접으려 했는데, 생각할수록 문제는 라벨이 아니었다. 정상일엔 45분이지만 EOD 적재가 실패한 날엔 저녁 내내 전일 종가가 서빙되고, 그런 날이 실제로 두 번 있었다.

KRX 종가는 15:30에 확정되니 폴링이 아니라 1회 조회면 된다. 적재 지연이 감지된 창에서만 KRX 시장 파라미터로 시세를 한 번 받고, 그 외 시간은 지금처럼 SSR 값을 쓰면 오프아워 콜 절감이라는 #124의 취지는 유지된다. 게이트는 하나, KRX 시장 파라미터 응답이 NXT 종목에서도 애프터장 체결을 섞지 않는지다. 이전에 섞지 않는 걸 확인했던 듯한데, 1콜이면 되니 한 번 더 실측하기로 하고 E67로 등록 후 다음 세션 앞머리에 얹었다.

## 정리

- **F54 종결** — root layout 1회 조회 → context → 클라이언트 9콜. 캘린더 통째 전달, provider 밖은 상수 폴백
- **static 유지 확인** — layout 조회가 라우트 렌더링 모드를 바꾸지 않음을 빌드 전후 라우트 표로 검증
- **하루 밀린 캘린더** — DATE 컬럼의 로컬 자정 파싱 + UTC 문자열화. dev 한정, `to_char`로 수정
- **F66 완결** — #124에서 안전하다고 본 경로가 실제 취약 경로. 일봉 SELECT 3곳 문자열 수신으로 통일
- **E67 신설** — NXT 종목 KRX 탭의 적재 지연 창 전일 값 서빙. 지연 시에만 1회 조회로 대체

배선이 끝난 시점에 한 번 확인한 게 fix 둘과 다음 과제를 끌어냈는데, 운이 좋았다기보다 검증을 건너뛰지 않은 결과에 가깝다. #124에서 "격리"라고 이름 붙인 쪽이 유일하게 틀린 경로였던 건 좀 머쓱하다.
