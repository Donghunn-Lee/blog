관심종목, 시장 순위 페이지까지 만들고 나서, 오래 미뤄둔 ai공시 요약 업그레이드를 진행할 차례다. 먼저 오래 전 [#020](/blog/slatekr/020/)에서 프롬프트를 잡을 때 했던 메모를 보면 이렇게 적혀 있었다.

> **출력 포맷은 자유 산문 2~4문단** — 섹션·불릿 구조는 UI 통합 단계에서 필요해지면 그때 결정

그때 미뤄둔 결정을 이번에 했다. 로드맵에는 "줄글 → 핵심 즉시 파악"이라고만 한 줄 적혀 있었는데, 열어보니 프롬프트부터 DB, 렌더까지 층이 꽤 여러 개였다.

---

## 수치가 문장에 파묻히는 구조

그동안 요청한 ai 요약은 DB에 캐싱된다. 그 DB에 쌓인 요약을 몇 개 꺼내 봤다. 삼성전자 소유상황보고 요약은 이렇게 나와 있었다.

> 2026년 5월 8일부터 2026년 6월 8일까지 한 달간, 이들이 보유한 삼성전자 주식은 보통주 40,179주가 줄고 종류주 7,450주가 늘어 전체적으로 32,729주가 순감했습니다.

틀린 문장은 아니다. 다만 숫자 세 개를 읽어내려면 문장을 끝까지 따라가야 한다. 공시 요약을 여는 사람이 원하는 건 "얼마가 어떻게 됐나"를 훑는 건데, 산문은 그걸 훑게 해주지 않는다.

프롬프트의 `[출력 형식]` 블록이 산문을 명시적으로 강제하고 있었다.

```
[출력 형식]
- 2~4문단의 자연스러운 한국어 산문. 사안이 단순하면 2문단, 복잡하면 4문단.
- 마크다운 문법(*, #, - 등) 사용 금지
- 각 문단은 빈 줄로 구분
```

여기를 뜯어내는 게 이번 작업이다.

## 어떤 축으로 자를 것인가

구조를 만들려면 필드를 정해야 하는데, 공시 유형마다 중요한 항목이 완전히 다르다.

| 유형 | 핵심 항목 |
| --- | --- |
| 소유상황보고 | 보고자 · 보유비율 전후 · 보유목적 |
| 공급계약 | 계약상대 · 금액 · 매출 대비 비율 · 기간 |
| 유상증자 | 발행주식수 · 발행가 · 조달금액 · 자금용도 · 일정 |
| 주주총회 | 개최일 · 안건 |

`amount`, `date`, `counterparty` 같은 고정 축을 잡으면 필드가 계속 불어난다. 그렇다고 유형별로 스키마를 따로 두면 분기가 다섯 개로 늘어난다. 둘 다 별로였다.

라벨을 모델이 정하게 두는 쪽으로 갔다.

```ts
{
  headline: string;                          // "이 공시는 ~을 알립니다" 한 줄
  facts: { label: string; value: string }[]; // 원문 서식 용어를 라벨로
  detail: string;                            // 나머지 맥락
}
```

유형이 몇 개든 필드는 셋이다. 그리고 이 구조에는 부수 효과가 하나 있다. **판단 축이 스키마에 들어갈 자리가 없다.** 필드명이 고정돼 있었다면 `impact`나 `sentiment` 같은 칸이 언제든 끼어들 수 있는데, `{label, value}`는 원문에서 뽑은 항목 이름만 담는다. 이 프로젝트는 투자 판단을 하지 않는 게 원칙이라, 구조 자체가 그걸 막아주는 편이 낫다.

## 마크다운으로 받지 않은 이유

모델에게 마크다운 표를 뱉게 하는 방법도 있었다. `react-markdown`을 하나 얹으면 끝이고, 프롬프트도 짧아진다.

받지 않았다. **표를 뱉게 하면 레이아웃 책임을 모델과 나눠 갖게 된다.** 컬럼 수를 모델이 정하고, 프론트는 그걸 파싱해서 렌더한다. 모델이 어느 날 표를 안 뱉으면 화면이 무너진다.

반면 `{label, value}[]`는 구조 중립적이다. 표로도, 스택으로도, 카드로도 렌더된다. 모델은 자기 출력이 어떻게 그려지는지 모른다.

이 판단이 뒤에서 회수된다.

## 스키마를 넘길 위치

Gemini에 JSON 출력을 강제하려면 스키마를 넘겨야 한다. 그런데 응답을 Zod로 검증하는 것도 해야 한다. 같은 구조를 두 곳에 적으면 언젠가 어긋난다.

먼저 SDK(`@google/genai`)의 `responseSchema` 필드를 썼는데, 여기가 좀 까다로웠다. `Schema.type`이 대문자 enum(`Type.OBJECT`)을 요구한다. 타입이 `Schema | unknown`이라 소문자 문자열(`"object"`)을 넣어도 TS는 통과시키는데, 실제 서버는 거부한다.

SDK 주석을 뒤져보니 이런 게 있었다.

```
Previously we made GenerateContentConfig.responseSchema field to accept unknown.
Since v1.9.0, we switch to use backend JSON schema support.
```

그리고 `responseSchema`의 JSDoc이 직접 안내하고 있었다 — 처리가 잘 안 되면 `responseJsonSchema`를 쓰라고. 표준 JSON Schema를 그대로 받는 별도 필드다.

Zod v4에 `toJSONSchema()`가 들어와 있어서, 이걸로 소스를 하나로 묶었다.

```ts
// shared/types/disclosureSummary.ts — 이 파일 하나가 소스
export const DisclosureSummaryContentSchema = z.object({
  headline: z.string().describe("...45자 이내. 두 문장 이상 쓰지 않습니다."),
  facts: z.array(FactSchema).max(8).describe("...최대 8개. 없으면 빈 배열."),
  detail: z.string().describe("...추가할 내용이 없으면 빈 문자열을 반환합니다."),
});

// Gemini 호출 — 같은 스키마를 JSON Schema로 변환해 넘긴다
config: {
  responseMimeType: "application/json",
  responseJsonSchema: buildResponseJsonSchema(),
}

// 응답 검증 — 같은 스키마로 파싱
const parsed = DisclosureSummaryContentSchema.safeParse(json);
```

`.describe()`가 변환 결과에 `description`으로 실린다. 구조·제약·지시문이 전부 한 파일에 산다.

덤도 하나 붙었다. `maxItems`가 지원 키워드라, `.max(8)`이 **스키마 레벨에서 강제**된다. 이전 방식이었으면 "최대 8개"는 프롬프트에 적은 자연어 부탁이라 모델이 어겨도 막을 수가 없다.

`propertyOrdering`은 zod가 내보내지 않고 `$schema`는 반대로 내보내는데(SDK 지원 목록에 없다) 이건 헬퍼로 재귀 주입·제거했다.

### 프롬프트에는 스키마를 적지 않는다

구글 문서가 스키마를 프롬프트에 중복해서 적지 말라고 못박고 있다. 중복하면 출력 품질이 떨어진다는 거다. 대신 각 필드의 목적은 schema의 `description`으로 정의하라고 안내한다.

그래서 프롬프트에서는 `[출력 형식]` 블록을 통째로 걷어냈고, 구조 지침은 전부 `.describe()`로 옮겼다.

`[지켜야 할 원칙]` 블록은 그대로 뒀다. 평가·전망 금지, 숫자 원문 유지, 부록 배제 — #020에서 두 번 갈아엎어 만든 가드레일이고, 지금 봐도 프로젝트 원칙과 정확히 맞는다. 첫 불릿 하나만 바꿨는데, 그게 헤드라인 형태를 지정하는 문장이라 스키마 쪽으로 이사 갔기 때문이다.

## 실측 두 번

프롬프트는 던져보기 전엔 모른다. #020에서도 같은 걸 했다. 이번엔 임시 route를 하나 파서 프로덕션 코드와 DB를 건드리지 않고 공시 네 건을 돌렸다.

- 유상증자결정
- 단일판매·공급계약체결
- 타법인주식및출자증권취득결정
- 임원 소유상황보고 (원문이 258자밖에 안 되는 빈약한 케이스)

마지막 하나를 일부러 넣었다. 원문에 쓸 내용이 없을 때 모델이 칸을 억지로 채우는지 보려고.

1차 결과에서 여섯 가지가 걸렸다.

| 문제 | 실제 출력 |
| --- | --- |
| 날짜 포맷이 갈림 | `2026-07-10` / `2026년 06월 04일` 혼재 |
| 어미가 흔들림 | "알린다" / "알립니다", "~한다" / "~습니다" |
| 자기 회사명을 facts에 넣음 | `회사명: 삼성전자주식회사` (종목 페이지에서 자명한 정보) |
| headline 길이 무제한 | 47자짜리 |
| detail이 물타기 | 빈약한 원문에서 headline을 그대로 풀어씀 |
| facts 중복 | `계약 시작일` / `계약일자` 값이 같은데 둘 다 |

`.describe()`를 고쳐 2차를 돌렸더니 전부 잡혔다. 특히 빈약 케이스에서 `detail: ""`이 나온 게 중요했는데, `required`를 유지한 채로 빈 문자열이 나온다는 뜻이라 필드를 optional로 내릴 필요가 없어졌다. 파싱 분기가 하나 줄었다.

### facts 상한은 8로 두기로

1차에서 유상증자·공급계약·타법인취득이 **셋 다 정확히 6개**로 상한에 붙어 있었다. 우연이 아니라 잘린 거다. 상한을 8로 올렸다.

그랬더니 이번엔 공급계약이 8개를 다 채웠는데, 그중 둘이 좀 아쉬웠다.

```
계약명          선박용 엔진        ← headline에 이미 있음
계약시작일      2026년 7월 10일
계약(수주)일자  2026년 7월 10일    ← 위와 값이 같음
```

6으로 도로 내릴까 했다. 그런데 DART 공급계약 서식에 저 두 항목이 실제로 따로 있다. 같은 날 체결·시작이라 값이 겹친 것뿐이고, 모델은 원문을 충실히 옮긴 거다. 게다가 타법인취득 쪽 8개는 하나도 버릴 게 없었다.

6으로 내리면 **뭐가 잘릴지를 우리가 정할 수 없다.** 저정보 항목 두 개 지우자고 중요 항목을 잃을 위험을 지는 건 손해라 8을 유지했다.

## 납입일이 왜 안 나오는가

상한을 8로 올렸는데도 유상증자 요약에 **납입일이 없었다.** 유상증자에서 납입일은 빠지면 안 되는 정보다.

모델이 중요도를 잘못 판단한 줄 알고 지시문을 손보려다, 원문부터 찍어봤다. 그랬더니 진짜로 없었다.

```
주요사항보고서(유상증자결정)

1. 신주의 종류와 수      보통주식 560,852
2. 1주당 액면가액        1,000
3. 증자전 발행주식총수   보통주식 15,188,750
4. 자금조달의 목적
   시설자금 (원)          ← 빈 칸
   영업양수자금 (원)      ← 빈 칸
   운영자금 (원)          999,999,116
   채무상환자금 (원)      ← 빈 칸
5. 증자방식              제3자배정증자
```

항목이 5번에서 끊긴다. 발행가액도, 납입일도, 상장예정일도 없다. 그런데 자금조달 목적의 **빈 칸들은 멀쩡히 살아 있다.**

임원 소유상황보고도 마찬가지였다. 원문이 258자인데, 정작 그 공시의 핵심인 소유주식수 변동 내역이 통째로 없었다. 반면 공급계약과 타법인취득은 표 값이 다 나왔다.

`fetchDisclosureText`가 표를 평문으로 바꾸는 과정에서 뭔가를 흘리고 있다. 유실된 둘은 다차원 표를 쓴다는 공통점이 있는데(자금조달 목적은 6칸 분할, 소유상황은 증권종류 × 변동 전/증감/후 매트릭스), 이건 아직 가설이다. DART 원문 뷰어와 대조해봐야 안다.

**요약 품질의 상한이 여기 있다.** 프롬프트를 아무리 다듬어도 원문에 없는 건 못 뽑는다. D2 작업의 결론이 사실 D8이라는 새 항목이었던 셈이다.

## 모바일을 위한 스택 구조

데스크톱에서는 2열 그리드로 잘 나왔다. 폰 폭으로 열어보고 문제를 봤다.

```
처분예정금액    보통주식
                344,532,012,00
                0원
```

`344,532,012,00` / `0원`. 폭이 모자란 것보다 **숫자가 중간에서 쪼개진 게** 더 나빴다. 오독을 부른다.

원인은 2열 구조 자체다. 320px을 label과 value가 나눠 갖는데, label이 최장 12자(`보유처분계획 주총 승인일`)라 140px쯤 먹으면 value에 180px도 안 남는다. `보통주식 344,532,012,000원`이 들어갈 자리가 아니다.

[#080](/blog/slatekr/080/)에서 같은 상황을 만났을 때 쓴 카드는 **단위를 헤더 라벨로 올리는 것**이었다. `4,293만주`를 값 `4,293` + 헤더 `거래량(만)`으로 쪼개서 예산을 만들었다. 근데 여기선 그 카드가 막혀 있다. 숫자를 원문 그대로 옮기는 게 이 기능의 원칙이라 억 단위로 줄일 수가 없다.

남은 선택지를 하나씩 봤다.

| 안 | 문제 |
| --- | --- |
| 폰트 축소 | `text-[10px]`까지 내려가야 하는데, #080에서 한글 렌더가 버티는 하한 아래로 판정한 크기다 |
| label 축약 (10자 → 6자) | label이 반응형이 아니라 **데스크톱까지 같이 깎인다.** 게다가 원문 서식 용어를 그대로 쓴다는 게 지금 label을 믿을 수 있는 근거다 |
| 숫자 축약 | 원문 그대로 원칙 위반 |

세 개 다 대가가 컸다. 그래서 표를 포기했다. 모바일에서는 label과 value를 세로로 쌓았다.

```
처분예정금액
보통주식 344,532,012,000원
```

label과 value가 폭을 나눠 갖지 않으니 경쟁이 사라진다. `break-words`도 걷어내고 `break-keep`으로 바꿔 어절에서만 줄이 바뀌게 했다.

세로가 늘 줄 알았는데 오히려 줄었다. 2열일 때 `처분예정금액`이 세 줄(`보통주식` / `344,532,012,00` / `0원`)을 먹고 있었으니, 스택의 두 줄이 손해가 아니었다.

**여기서 앞의 결정이 회수된다.** 모델 출력이 `{label, value}[]`라서, 표를 스택으로 바꾸는 데 모델 쪽은 한 글자도 안 건드렸다. 마크다운 표를 받았다면 출력에 이미 컬럼 구조가 박혀 있어서 이 전환 자체가 불가능했을 거다.

Gemini는 항목을 뽑고, 배치는 우리가 한다. 경계가 이렇게 나뉘어 있으면 화면 쪽 사정이 바뀌어도 모델을 다시 손볼 일이 없다.

### `display: contents`에는 border를 못 얹는다

스택과 2열을 전환하려고 `sm:contents`를 썼는데, 나중에 행 구분선을 넣으려 하니 안 먹었다. `display: contents`인 요소는 박스를 만들지 않으니 그릴 자리가 없다. Tailwind v4의 subgrid로 바꿔 해결했다.

## 패널 색이 6개월째 틀려 있었다

요약 패널 배경이 라벤더였다. 공시 탭은 sky인데.

[#048](/blog/slatekr/048/)에서 5색 매핑을 재배치할 때 라벤더가 차트로 넘어갔는데, 요약 패널이 따라오지 않았다. 문서 세 곳이 서로 다른 말을 하고 있었다.

- `CLAUDE.md` — 라벤더 = 차트 / AI 요약 (둘 다 병기)
- styleguide — 라벤더 = "AI 요약·분석 섹션" (차트 누락)
- 코드 상수 — 차트 = 라벤더 (확정)

색만 바꾸면 되는 일이었지만, 그 전에 정할 게 있었다. **AI 요약에 색을 다시 배정할 것인가?**

안 하기로 했다. [#044](/blog/slatekr/044/)에서 사이드 드로어를 걷고 공시 행 안에서 펼쳐지는 형태로 바꾼 시점에, 요약은 독립된 패널이기를 그만뒀다. 공시 섹션에 딸린 기능이면 섹션 색을 따르는 게 맞다. 5색은 섹션을 식별하라고 있는 건데, 한 섹션 안에서 색이 두 개 겹치면 그 기능을 잃는다.

sky 3단계가 이미 다 쓰이고 있어서(`bg`=탭·버튼 hover, `border`=펼친 행 배경·구분선, `accent`=버튼 텍스트) 요약 패널은 `bg-sky-bg`로 뒀다. 펼친 행 배경보다 밝아서 그 위에 살짝 떠오르는 모양이 되는데, 눌러서 여는 콘텐츠니 부상하는 편이 의미상 맞았다.

행 구분선은 무채색을 쓸까 하다가 `border-sky-border/30`으로 갔다. 공시 목록이 이미 같은 톤을 구분선으로 쓰고 있어서, 여기만 회색을 끌어들이면 sky 패널 안에서 튄다.

## 정리

- **출력 구조** — 유형별로 필드가 달라서 고정 축을 못 잡았다. `headline` / `facts[]` / `detail` 셋으로 두고 라벨을 모델이 원문 용어에서 뽑게 했다. 판단 축이 스키마에 들어갈 자리가 없다는 게 덤이다.
- **스키마 단일 소스** — `responseSchema` 대신 `responseJsonSchema`로 갈아타고, Zod 스키마 하나를 `toJSONSchema()`로 변환해 Gemini 제약과 응답 검증에 같이 썼다. `maxItems`가 스키마 레벨에서 강제된다.
- **프롬프트** — `[출력 형식]` 블록만 걷어내고 #020의 가드레일은 그대로 뒀다. 구조 지침은 `.describe()`로 이사.
- **캐시** — 구 포맷 24건은 파싱에 실패하면 캐시 미스로 처리해서 자연히 덮어씌워지게 뒀다. 버전 컬럼을 따로 파는 것보다 쌌다.
- **모바일** — 표를 유지하려면 폰트나 라벨을 깎아야 했는데 대가가 커서, 380px에서는 세로 스택으로 갔다. 숫자가 쪼개지던 것도 `break-keep`으로 잡았다.
- **패널 색** — #048에서 놓친 라벤더 잔재를 sky로 정정하고, AI 요약에는 색을 배정하지 않기로 정리했다.

모델과 화면 사이에 선을 어디에 그을지가 이번 작업의 대부분이었다. Gemini는 원문에서 항목을 뽑는 데까지, 그걸 표로 눕힐지 세로로 쌓을지는 우리 쪽. 그렇게 나눠두니 모바일에서 레이아웃을 갈아엎을 때 프롬프트를 다시 볼 일이 없었다.

다만 정작 요약 품질을 막고 있는 게 프롬프트가 아니었다는 걸 이번에 알았다. 원문 추출이 표를 흘리고 있으면 그 뒤는 다 반쪽이다.
