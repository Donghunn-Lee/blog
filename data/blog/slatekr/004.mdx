#003에서 설계는 끝났다. 테이블 세 개, 소스별 역할 분리.
이제 실제로 붙여보는 단계였다.

## 종목 목록부터 확인

적재 스크립트는 종목 목록부터 만드는 게 순서였다. `daily_prices`와 `financial_statements` 모두 `ticker`를 기준으로 조회하는 구조라, `stocks` 테이블이 먼저 채워져 있어야 했다.

pykrx는 OHLCV만 쓰기로 했으니, 종목 목록은 DART의 `corpCode.xml`에서 가져오면 되겠다고 생각했다. 전체 법인 코드를 ZIP으로 제공하는 엔드포인트가 있었고, 구조도 단순했다.

테스트로 확인은 했었지만, 막상 다시 뜯어보니 문제가 있었다. XML에 시장 구분 필드가 없었다. KOSPI인지 KOSDAQ인지 알 수 없으면 필터링이 안 된다. 종목별로 DART `company` API를 개별 호출하면 알 수 있지만, 2600개 종목을 하나씩 찌르는 건 현실적이지 않았다. DART도 이 용도엔 맞지 않았다.

## 금융위원회 FSS API

종목 목록을 받아야 하는데, pykrx는 내부 오류로 OHLCV 이외의 요청에 전부 오류가 발생하는 상황.
공공데이터포털의 `금융위원회 KRX상장종목정보 API`가 딱 맞는 소스였다.

확인 결과, 공공데이터포털의 금융위원회 KRX상장종목정보 API가 딱 맞는 소스였다. 종목코드(`srtnCd`), 종목명(`itmsNm`), 시장구분(`mrktCtg`)을 한 번에 제공했다. 공식 API라 스크래핑처럼 갑자기 깨질 걱정도 없었다.

한 가지 주의할 점이 있었다. `numOfRows` 없이 호출하면 `totalCount`가 약 390만 건으로 나왔다. 이 API는 날짜별로 데이터가 누적되는 구조라 과거 데이터까지 전부 포함된 탓이었다. `basDt`로 특정 날짜를 지정하니 2659개로 줄었다. 매일 실행할 cron 스크립트에서는 전날 날짜를 자동 계산해서 넘기는 방식으로 처리했다.

## stocks 적재

`fetch_stocks.py`의 구조는 단순하다.
FSS API를 페이지 단위로 순회하면서 KOSPI/KOSDAQ 종목만 필터링하고, stocks 테이블에 upsert한다.
종목코드는 API 응답에 A005930 형태로 앞에 A가 붙어있어서 제거 처리가 필요했다. 매일 cron으로 실행하면 신규 상장이나 폐지도 자동으로 반영되는 구조다.

## 최종 데이터 소스 조합

여기까지 정리하고 나니 소스 조합이 확정됐다.

| 데이터 | 소스 |
|---|---|
| 종목 목록 | 금융위원회 FSS API |
| OHLCV | pykrx |
| 재무제표 / 공시 | DART API |

\#002에서 "pykrx는 OHLCV만 쓴다"고 결론 냈을 때 종목 목록은 생각 못 했다. 구현하면서 발견한 거다. 설계 단계에서 다 정해두는 건 어렵다. 실제로 붙여보면서 빠진 게 드러나고, 그걸 채우는 게 자연스러운 흐름이었다.

다음은 `fetch_prices.py`다. pykrx로 OHLCV를 적재하는 스크립트인데, 언제 또 깨질지 모르는 라이브러리를 쓰는 만큼 교체하기 쉬운 구조로 만들 생각이다.
