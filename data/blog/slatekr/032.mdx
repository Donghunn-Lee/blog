# 

#031 끝에서 지배주주 귀속 문제를 확인했다. collector가 수집하는 net_income이 `ifrs-full_ProfitLoss`(비지배 포함 전체), total_equity가 `ifrs-full_Equity`(비지배 포함 전체)로 적재되고 있었다. PER/PBR/ROE/ROA 전부 분모가 틀린 채로 계산되는 상태였다.

수정 방향은 명확했다. 계정과목 두 개를 지배주주 귀속 버전으로 교체하면 된다.

---

## 계정과목 교체

TARGET_ACCOUNTS에서 두 항목을 바꿨다.

- `ifrs-full_ProfitLoss` → `ifrs-full_ProfitLossAttributableToOwnersOfParent`
- `ifrs-full_Equity` → `ifrs-full_EquityAttributableToOwnersOfParent`

DB 컬럼명(`net_income`, `total_equity`)은 그대로고, lib/의 PER/PBR/ROE/ROA 계산도 같은 컬럼을 읽으니까 collector만 고치면 됐다. 웹 쪽 수정은 없다.

다만 한 가지 처리가 더 필요했다. DART 재무제표 응답에는 같은 계정과목이 여러 구분(`sj_div`)으로 나온다. 손익 항목은 IS(포괄손익계산서)와 CIS(손익계산서)가 섞여 있고, 재무상태표 항목은 BS(재무상태표)로 나온다. 문제는 순서가 보장되지 않는다는 점이다. CIS가 먼저 올 수도 있고 IS가 먼저 올 수도 있다.

revenue, operating_profit, net_income은 IS를, total_assets와 total_equity는 BS를 우선 사용해야 한다. `_PREFERRED_SJ_DIV` 딕셔너리로 각 항목의 선호 구분을 정의하고, 파싱 시 첫 번째 값을 일단 넣되 이후 선호 구분 값이 오면 교체하는 방식으로 처리했다. single-pass로 끝나고, DART list를 한 번만 순회한다.

---

## OFS 폴백 추가

원래 계정과목 교체(B1)만 하려고 했다. 근데 교체하면 전체 재적재가 필요하고, 재적재를 두 번 하고 싶지 않았다.

계정과목을 지배주주 귀속으로 바꾸면 CFS(연결재무제표)에서 해당 항목이 없는 종목이 늘어날 수 있다. 기존에는 CFS만 요청했는데, CFS 응답이 없을 때 OFS(개별재무제표)로 재요청하는 폴백이 없었다. OFS 폴백 없이 재적재하면, 기존에 CFS로 잘 들어가던 데이터가 null로 덮어씌워질 위험도 있었다.

수정 자체는 간단했다. `fetch_financial` 함수에서 `for fs_div in ("CFS", "OFS")` 루프를 돌려 CFS 실패 시 OFS를 재요청하고, 파싱은 `_parse_financial_list`로 공통 처리했다. 코드 복잡도가 올라가는 수준이 아니어서 같이 넣었다.

---

## --force와 sleep 최적화

재적재를 위해 `--force` 플래그를 추가했다. `existing_keys`를 빈 set으로 만들어서 모든 period를 다시 돌린다. INSERT는 원래 `ON CONFLICT DO UPDATE`라 upsert로 동작하니까, 기존 데이터 위에 덮어쓰기된다.

실수로 전체 재적재를 트리거하면 중간에 끊어도 처음부터 다시 해야 하니까, `input()` 확인 프롬프트를 넣었다. GitHub Actions에서는 `--force`를 안 쓰니까 CI 호환성 문제는 없다.

sleep도 조정했다. DART rate limit이 분당 1,000건인데, 기존 설정은 여유를 너무 많이 둔 상태였다. 이전 작업에서 한 차례 `fetch_prices`와 `fetch_financials`모두 sleep을 줄였었는데, 더 줄일 수 있는 부분이 있어 추가로 수정했다. 성공 시 0.3초 → 0.15초, OFS 폴백 시 0.3초 → 0.05초로 줄였다. 5년 풀 재적재 예상 시간이 대략 30% 줄어든다.

`--force` 모드에서는 `mark_non_filer`도 스킵하도록 했다. 전체 재적재 중에 한 period에서 응답이 없다고 non_filer로 마킹하면 다음 period에서 그 종목이 빠지게 되니까.

## 검증

`--force --periods 2`로 테스트 적재를 돌렸다. 2025 Q4 성공 2,218/2,223, 2026 Q1 성공 2,154/2,218.

삼성전자(005930) 2025 Q4 기준으로 대조했다.

- net_income: DB 44,260,956,000,000 vs 네이버 증권 지배주주 442,610억 — 일치
- total_equity: DB 424,313,255,000,000 vs 네이버 증권 지배주주 4,243,133억 — 일치

계정과목 교체가 정상 반영된 걸 확인하고, 5년 풀 재적재(`--force`)를 실행했다.

## 441개 종목의 재무 데이터가 없다

재적재를 돌려놓고, 그 시간 동안 다른 작업을 처리해야 했다. 해결해야 하는 이슈 중, 일부 종목에서 재무 데이터가 아예 누락되어있는 이슈를 로드맵 B3에 적어뒀었고, 순서상 해당 이슈를 처리하기로 했다.

먼저 쿼리를 돌려 재무요약표가 비어있는 종목을 필터링했다.

```sql
SELECT s.ticker, s.name
FROM stocks s
LEFT JOIN financial_statements fs USING (ticker)
WHERE fs.ticker IS NULL;
```

441개. 전체 2,664개 중 16.5%다.

시장별로 보면 KOSPI 87개, KOSDAQ 354개. 이름에 '스팩', '리츠', 'ETF', 'ETN'이 포함된 건 85개. 이건 DART에서 재무제표를 제공하지 않는 종목이니 정상이다.

나머지 356개가 문제였다. `is_financial_filer` 값을 보니 353개가 `false`로 마킹되어 있었다. 최초 적재 시 collector가 DART 응답이 없어서 "이 종목은 재무제표를 안 낸다"고 판단한 거다.

근데 목록에 AP위성, HPSP, KCC건설, PI첨단소재 같은 일반 상장기업이 있었다. 이 종목들이 재무제표를 안 낼 리가 없다.

---

## 원인 추적 — HPSP

HPSP(403870)로 직접 확인해봤다. corp_code는 `01288827`로 정상 매핑되어 있었다.

DART API에 CFS(연결재무제표)로 요청하면 "조회된 데이타가 없습니다"가 돌아온다. OFS(개별재무제표)로 바꿔 요청하면 정상적으로 데이터가 온다.

원인이 명확해졌다. HPSP는 개별재무제표만 제출하는 종목인데, OFS 폴백이 없던 시절에 CFS만 요청하고 응답이 없으니까 `is_financial_filer = false`로 마킹한 거다. 그리고 한번 false로 마킹되면 `get_all_corps()` 쿼리의 WHERE 절에서 영구적으로 제외된다. 복구 경로도 코드에 없다.

이번 세션에서 OFS 폴백을 추가했지만, 이미 non_filer로 찍힌 종목은 애초에 순회 대상에 포함되지 않으니 소용이 없었던 거다.

---

## 리셋

```sql
UPDATE stocks SET is_financial_filer = NULL WHERE is_financial_filer = false;
```

353개를 NULL로 리셋했다. `get_all_corps()`가 `is_financial_filer = true OR is_financial_filer IS NULL`로 조회하니까, NULL이면 다시 순회 대상에 포함된다.

리셋 후 `--force`로 재적재를 다시 실행했다. 이번에는 OFS 폴백이 있으니까, CFS 응답이 없는 종목도 OFS로 수집된다. OFS까지 없는 종목만 다음 정규 실행에서 다시 non_filer로 마킹될 거다.

---

## 정리

#031에서 발견한 지배주주 귀속 문제를 수정하고, OFS 폴백을 추가하고, non_filer 영구 skip 문제를 발견해서 리셋했다. 세 가지가 하나의 흐름으로 이어진 셈이다.

사실 non_filer 문제는 OFS 폴백이 없던 시절의 부산물이다. 당시에는 CFS 응답이 없으면 "재무제표를 안 내는 종목"이라고 판단하는 게 합리적이었다. 근데 그 판단이 영구적으로 고착되는 구조였고, 353개 종목이 거기 걸려 있었다.

적재 결과 검증은 재적재가 끝나면 따로 진행할 예정이다.
