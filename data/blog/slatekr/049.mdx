#048에서 종목 상세 페이지의 구조·디자인 큰 묶음이 일단락된 뒤, E트랙으로 넘어왔다. 관심종목 페이지(E3)가 MVP 이후 손 안 댄 상태였다. 종목명·코드·시장 뱃지·휴지통만 있는 단순 리스트라, 페이지 안의 정보 밀도가 메인 진입점인 홈의 관심종목 카드보다도 낮은 역전 상태였다.

peach는 SlateKR 5-color 시스템 중 마지막 미적용 색이고 #048에서 관심종목 도메인 매핑만 계획해 뒀었다. 이번에 페이지 손보며 peach 첫 적용지로 잡았다.

총 여섯 커밋이 들어갔는데, 첫 커밋은 작업할 게 사실 이미 다 되어 있어 패스됐고, 그 와중에 카드로 한 번 갔다가 리스트로 돌아온 결정도 끼어 있었다.

## 신규 공시 배지 추가

관심종목 카드에 "신규 공시 N건" 표시를 넣기로 했다. 7일 이내 절대 시간 기준이다.

batch endpoint를 신설하면서 `/api/prices` 패턴을 따라가게 했다. 호출 형태와 응답 shape를 일관되게 가져가기 위해서다.

가격은 `daily_prices` 테이블이 있지만 공시는 DART API에서 매번 fetch하는 구조다. ticker별로 DART API를 fan-out 호출하고 `Promise.allSettled`로 격리하는 방식으로 진행했다.

응답 shape는 prices의 `[{ ticker, prevClose: number | null }, ...]`을 그대로 미러해서 `[{ ticker, count: number | null }, ...]`로. `count: null`은 단순 0과 구분되는 의미를 갖는다 — API 실패와 "공시 0건"은 다르다.

DART 트래픽을 줄이기 위해 `pageCount: 1`로 totalCount 메타만 사용하고 `revalidate: 3600` 캐시는 유지했다. 관심종목 종목 수가 많아지면 cold cache 시 응답 지연 가능성이 남는다. X6(DART fetch 부담 실측) 트랙으로 남겨뒀다.

## `/api/prices` 응답에 7일 등락 추가

카드에 "7일 등락 %"도 같이 표시하기로 했다. 7일치 데이터를 어디서 가져올지가 결정 포인트였다.

세 가지 선택지가 보였다.

1. 기존 `/api/prices` 응답에 `change7d` 필드 추가
2. 별도 endpoint(`/api/prices/change` 등) 신설
3. 클라이언트에서 N일 전 종가만 받아 계산

3번부터 빼는 게 빨랐다. 기존 1일 등락(`change`/`changePct`)이 이미 서버에서 계산돼 내려오는데 7일만 클라이언트에서 계산하는 건 비대칭이다. 2번도 명분이 약했다. `/api/prices` 호출처를 확인하니까 `WatchlistPreview.tsx` 한 곳뿐이라 사실상 관심종목 전용 endpoint다. 분리할 이유가 없다.

1번으로 가되 옵션 파라미터(`?changeDays=7`)로 받을지 무옵션 상시 포함으로 갈지가 또 갈렸다. 처음엔 `?changeDays=N` 같은 일반화 형태(N일을 동적으로 받음)도 떠올랐다. 그런데 초기 설계 원칙 — "미래 확장만 가정한 추상화 추가 금지" — 이 정확히 이 경우를 막는다. 7일 외에 30일·90일을 쓸 데가 지금은 없는데 일반화 API를 미리 만드는 건 추상화 부담만 늘린다.

상시 포함으로 결정했다. 호출처가 1곳뿐이라 회귀 위험은 거의 0이다.

```ts
type TickerPriceSummary = {
  ticker: string;
  close: number;
  prevClose: number | null;
  change: number | null;
  changePct: number | null;
  change7d: number | null;       // 신규
  change7dPct: number | null;    // 신규
};
```

SQL은 `cutoff = latest_date - 7 calendar days`로 잡고 `WHERE date <= cutoff ORDER BY date DESC LIMIT 1`. 주말·공휴일은 거래일 데이터가 없으니 자동으로 그 전 거래일을 가져온다. 상장 7일 미만 종목은 0행 반환 → null.

## 카드 디자인 철회

여기서 결정이 매끈하지 않은 부분이 끼어들었다.

원래 디자인 방향은 카드였다. 홈의 관심종목 카드 톤을 확장해서 페이지에서는 더 풍부한 카드로 가는 그림. 클로드 코드에 그대로 시키고 결과를 받았다.

![관심 종목 카드 그리드](/static/images/velog/b815117e-6a21-496d-8c01-0c62a8200dad-image.png)

막상 만들고 보니, 일반적인 케이스와 다르게 가져가고 싶어서 카드를 선택했는데 영 별로였다. 정보 밀도가 낮고, 읽기도 불편했다. 종목 10~20개만 돼도 그리드가 너무 길어지고, 정보 밀도와 카드 크기의 트레이드오프가 점점 나빠질 것 같았다.

더욱이 관심 종목 페이지에는 단순 리스트만이 아니라 관심 그룹 기능의 추가가 계획에 있었다. 그것까지 염두했을 때, 여러모로 리스트가 합리적이었다. 카드 디자인의 판단은 내 욕심이었다.

그나마 리스트로 바꾼다 해도 기존 구현과 겹치는 요소가 많아서 최소 수정으로 디자인을 변경할 수 있었다. 데이터 페칭 hook, Link 오버레이, 휴지통 이벤트 처리는 카드든 행이든 동일하게 필요한 부분이라 어렵지 않게 처리했다.

## 관심 종목 리스트 디자인

행 단위로 외곽 박스를 깔면 panel-in-panel과 시각 무거움이 둘 다 살아난다. #048 공시 탭에서 한 번 정착시킨 패턴 — 외곽 한 겹 + 내부 plain 행 + 호버 bleed — 이 그대로 적용 가능했다.

페이지 전체를 `<StockPanel variant="peach">`로 한 겹 감싸고, 내부의 `WatchlistRow`는 외곽 박스 없이 `-mx-6 px-6`로 bleed 효과만. 호버는 `bg-peach-border/40` tint + bleed로 미세하게 변하고, 행 단위 lift는 안 한다. 행이 들썩들썩하면 어색하다.

컨텐츠 max-width는 종목 상세 페이지와 동일하게 `max-w-4xl`로 통일. 페이지 간 스캔 일관성을 위함이고, 너무 넓은 영역에 행 리스트가 깔리면 행 양 끝이 멀어서 빈 공간이 어색했다.

![](/static/images/velog/96872787-7130-4573-90c6-330cc856bc1b-image.png)


행 클릭 동선은 overlay Link 패턴으로 잡았다. `<Link className="absolute inset-0">`을 `li` 내부 마지막에 두면 행 전체 영역이 클릭 영역이 된다. 휴지통은 `relative z-10`으로 Link 위에 띄우고 `e.preventDefault() + e.stopPropagation()`으로 부모 Link 동선을 차단. nested `<a><button></a>`가 무효 HTML이라 이 패턴을 골랐다.

## 부분 실패 처리

마지막 커밋은 로딩 skeleton과 부분 실패 처리. `WatchlistRowSkeleton`을 `WatchlistRow.tsx`에 co-locate(행 구조 변경 시 함께 수정 보장).

| 상태 | 가격 | 등락/7일 | 공시 카운트 |
|---|---|---|---|
| prices 실패 | "—" | 영역 생략 | 정상 |
| 공시 실패 | 정상 | 정상 | 영역 생략 |
| 양측 실패 | 페이지 단위 에러 메시지 |||
| 둘 다 성공 | 정상 | 정상 | 정상 |

응답 shape 자체가 null 처리를 내장하고 있어서 부분 실패는 상당 부분 자동 처리됐다. 행 컴포넌트가 이미 `price=undefined / disclosure=undefined`를 graceful하게 처리하는 구조라, 추가 prop 없이 `pricesMap[ticker]`가 undefined인 케이스를 그대로 흘리면 됐다. "한 섹션 실패가 전체 페이지 실패로 번지면 안 된다"는 CLAUDE.md 원칙이 코드 구조에 그대로 묻어 있는 셈이다.

빈 상태(0건) UI는 손대지 않고 두기로 했다. 다음 세션에서 그룹 기능 도입할 때 "그룹 없음 / 그룹 있는데 종목 0개 / 최근 조회 0개" 등으로 분기가 생기니까, 그때 함께 재설계.

## 정리

이번 세션의 결정 흐름은 두 갈래로 정리된다.

batch API 책임 분리. 호출처가 1곳뿐인 endpoint의 응답을 확장할지, 옵션 파라미터로 분기할지, 별도 endpoint로 분리할지. 일반화 추상화는 미래만 가정한다는 이유로 빠지고, 책임을 분리할 명분이 약한 별도 endpoint도 빠졌다. 응답 확장 + 무옵션 상시 포함으로 가장 단순한 형태가 남았다.

디자인 사전 정비. 카드 그리드로 시작했다가 그룹 기능을 떠올리고 리스트로 돌렸다. 행 구조로 정착시켜두면 그룹 헤더를 행 사이에 자연스럽게 끼울 수 있다.
