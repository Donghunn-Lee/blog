[#042](/blog/slatekr/042/)에서 깔아둔 두 개편안 중 두 번째다. 종합정보 2×2 그리드는 [#043](/blog/slatekr/043/)에서 처리했고, 이번 작업은 계획대로 공시 탭의 인라인 확장을 구현하는 것이다.

단순히 인라인 확장만으로는 공시 탭이 마무리되기엔 부족했다. 탭으로 분리되기 전엔 일단은 임시라 "최근 3개월, 10건 고정"으로 해 뒀는데, 전용 탭이 된 이상 이 어색한 제약도 해소해야 했다. 그래서 이번 세션은 인라인 확장 + 필터 + 검색 + 페이지네이션 + 테이블 레이아웃까지 묶었다.

## 1. 인라인 확장 — 사이드 패널 폐기

기존 UX의 문제는 두 가지였다.

- AI 요약 버튼이 **row hover** 시에만 노출 → 모바일에서 발견 불가능
- AI 요약 클릭 시 **사이드 패널**(`SummarySlate`) 열림 → 현재 공시와 연결이 잘 안 되고, 사이드 패널이 slate와는 느낌이 좀 달라서 일관성이 떨어짐.

추후 따로 해결하려 했던 문제들인데, 인라인 확장 방식이 두 문제를 한 번에 해소할 만큼 적합해 보여서 아예 방식을 바꾸기로 했다. 개편 방향은 [#042](/blog/slatekr/042/)에서 미리 잡아뒀다.

- AI 요약 버튼 상시 노출
- AI 요약 클릭 → row 하단 인라인 확장
- 동시 확장 1개만. 다른 row의 AI 요약 클릭 시 기존 확장 자동 닫힘
- 확장된 row 외 나머지는 `opacity-50`으로 흐려짐
- `SummarySlate` 폐기

API 캐시(`disclosure_summaries` 테이블)는 그대로 둬서 동일 공시 재확장은 즉시 표시된다. 사이드 패널이 사라진 덕에 도메인 컴포넌트도 하나 줄었다.

## 2. 기간 필터·검색·페이지네이션 — 전용 탭다운 기능

원래 3개월·10건 제한은 한 페이지 슬레이트일 때 자연스러웠던 결정이다. 공시 전용 탭이 된 이상 자유롭게 범위 조회할 수 있어야 했다.

### 페이지네이션을 어떻게, 기간을 어떻게

페이지네이션만 붙이면 되는 줄 알고 시작했는데, 기간 컷도 같이 손봐야 한다는 게 금방 드러났다. 페이지네이션 자체는 DART가 `page_no` / `page_count`를 지원해서 어렵지 않은데, 기본 기간이 3개월에 머물러 있으면 페이지네이션이 닿을 범위 자체가 좁아진다.

기간 필터 모델을 잠시 고민했다. 토글을 단일 선택으로 하고 "전체"를 표현하려면 토글 해제를 허용해야 하나 싶었는데, 해제 가능한 토글은 "전체"라는 상태가 암시적이라 모델이 두 가지가 된다. 그래서 **"전체" 버튼을 명시적으로 두는 쪽**으로 정리했다. 6M / 1Y / 3Y / 5Y / 전체 / 직접 선택 여섯 개 중 항상 하나가 선택된 상태. 모델이 한 차원이라 깔끔하다.

### 검색 API의 부재

검색은 서버 측에서 처리될 거라 생각했는데, DART OpenAPI 문서를 보니 제목 검색 파라미터가 없었다. 공시 유형(`pblntf_ty`), 회사, 날짜 범위까지는 서버가 필터링해주지만 자유 텍스트는 클라이언트에서 처리해야 했다.

검색 활성화 시 현재 기간의 모든 페이지를 fetch해서 메모리에서 제목 매칭 필터링하는 방식으로 구현할 수밖에 없었다. DART API 일일 한도가 4만건이라 검색 1회당 추가 호출 수가 늘어도 부담은 작다. React.cache + revalidate 3600 덕에 같은 페이지 재방문은 비용이 없다.

검색과 기간을 어떻게 합칠지도 짧게 고민했다. "검색하면 기간 무시하고 전체 검색"도 직관적이긴 한데, 토글이 검색 중 무력화되는 순간이 생긴다. 두 필터를 **독립 차원으로 합성**(AND 연산)하는 쪽이 모델 단순하고, DART 뷰어 자체가 같은 방식이라 학습 비용도 없다.

### 결정 사항

| 항목 | 결정 |
|---|---|
| 기간 토글 | 6M / 1Y / 3Y / 5Y / 전체 / 직접 선택 |
| 기본 기간 | 1Y |
| 페이지당 건수 | 10 |
| DART API 호출 단위 | 100건/페이지 |
| 사용자 페이지 ↔ DART 페이지 매핑 | `Math.ceil(userPage / 10)` |
| 검색 | 제목(`report_nm`), 클라이언트 측 필터, 300ms debounce |
| 검색 시 데이터 | 현재 기간의 모든 DART 페이지 fetch 후 메모리 필터 |

DART는 100건/페이지로 호출하고, 사용자가 보는 페이지(10건/페이지)는 그 안에서 슬라이싱한다. 1~10페이지는 DART 1페이지 한 번으로 처리되고, 11페이지 진입 시점에 DART 2페이지가 호출되는 식이다.

## 3. 시각 정리 — 슬레이트 한 겹

1차 구현 후 헤더와 푸터를 흰 카드(`bg-elevated`)로 분리했더니 amber 슬레이트 안에 또 다른 패널이 박힌 모양이 됐다. SlateKR 디자인 언어에서 슬레이트는 외곽 한 겹의 독립 단위라, 안에 또 패널을 두면 위계가 꼬인다.

정리 방향:

- 외곽은 `bg-amber-bg` 한 겹만. 헤더·푸터는 같은 배경 위에서 `border`로 구분
- row 기본 `bg-transparent` → 외곽 amber-bg가 그대로 비침
- row hover `bg-amber-border/40`, 확장 row `bg-amber-border`
- 토글 비활성 `bg-transparent`, 활성 `bg-elevated`. 검색 input과 datepicker 트리거는 `bg-elevated/80`으로 amber 위에서 살짝 떠 보이게

row 기본을 투명하게 하니 hover와 확장이 자연스럽게 부각되고, 비활성(`opacity-50`) 상태와도 충돌하지 않았다.

여전히 헤더의 영역 구분이 애매한 듯해서 약간 신경쓰이지만, 나중에 고려해도 될 정도의 사소한 문제라고 판단해서 우선 미뤄두기로 했다.

## 4. 테이블 레이아웃 도입

인라인 확장과 필터를 다 붙이고 보니 row 정보가 정렬되지 않은 인상이 남았다. 유형 배지, 회사명, 보고서명, 제출인, 날짜, 비고 표기가 row마다 폭이 들쭉날쭉했다.

- 컬럼 헤더 추가: `유형 / 대상회사 / 보고서명 / 제출인 / 접수일자 / 비고`
- 헤더와 모든 row를 같은 CSS Grid 정의로 묶음 (`grid-cols-[72px_88px_minmax(0,1fr)_88px_72px_32px_60px]`)
- DART 원문 버튼 제거 — 보고서명 클릭이 같은 링크라 중복. AI 요약만 단독 액션으로 남음
- 푸터에 출처 표기 추가: `출처: DART 전자공시시스템`

DART 원문 버튼을 빼면서 보고서명 컬럼 폭이 살짝 늘었고, row 우측 버튼 클러스터가 단일 액션(AI 요약)으로 정리됐다.

## 5. datepicker 직접 입력

"직접 선택" 모드의 datepicker는 처음엔 트리거 버튼이 캘린더 팝업을 여는 형태였다. 마우스 사용엔 자연스럽지만 키보드로 빠르게 날짜를 입력하려는 사용자에겐 클릭 → 캘린더 탐색 두 단계가 번거롭다.

input + 캘린더 아이콘 듀얼 UX로 재설계했다. 텍스트 입력란이 메인이고 아이콘으로 캘린더도 열 수 있는 구조.

```ts
const formatDateInput = (raw: string): string => {
  const digits = raw.replace(/\D/g, "").slice(0, 8);
  // 4/2/2 자리에 자동으로 - 삽입
  if (digits.length <= 4) return digits;
  if (digits.length <= 6) return `${digits.slice(0, 4)}-${digits.slice(4)}`;
  return `${digits.slice(0, 4)}-${digits.slice(4, 6)}-${digits.slice(6)}`;
};
```

`20260531`을 입력하면 자동으로 `2026-05-31`로 마스킹된다. 부분 입력 동안은 로컬 state로만 유지하고, 완전한 유효 날짜가 됐을 때만 부모에 onSelect를 호출해 URL을 갱신한다. 13월/45일 같은 잘못된 입력은 `parseInputToDate` 단계에서 차단.

모바일에서는 `inputMode="numeric"`으로 숫자 키패드가 자동으로 뜨고, placeholder를 `"0000-00-00"`으로 둬서 형식이 빈 칸일 때도 즉시 보인다.

## 작업 중 발견하고 처리한 것들

- **ALL preset 동작** — `bgn_de`를 생략하면 DART가 "당일 하루"만 반환하는 동작이 있어 0건이 나왔다. 1999-01-01을 시작일로 넣어 전체 범위를 커버하는 쪽으로 픽스
- **필터 전환 시 스켈레톤 깜빡임** — `<Suspense key={...}>`로 searchParams 조합을 묶어뒀더니 필터 바꿀 때마다 강제 remount가 발생했다. Suspense key 제거 + `useTransition`으로 이전 콘텐츠 유지하며 백그라운드 fetch
- **prop sync useEffect lint 이슈** — URL 변경 시 로컬 state를 다시 끌어오는 패턴이 `react-hooks/set-state-in-effect`에 걸렸다. render-time prev 비교 패턴으로 정리

## 부록 — Parallel Routes에 대한 뒤늦은 회고

공시 인라인 확장이 들어오면 차트 탭을 다녀온 뒤에도 펼쳐둔 요약이 그대로 남는 그림을 머릿속에 그리고 있었다. 작업 끝나고 확인해 보니 안 남아 있었다. 필터 상태도 마찬가지로, `?preset=3Y` 상태에서 다른 탭에 다녀오면 1Y로 돌아왔다.

공식 문서를 다시 펴봤다. Parallel Routes의 "비활성 슬롯 상태 보존"이 말하는 동작은 이거였다.

- 슬롯 두 개 이상이 한 화면에 **동시에** 떠 있을 때
- 한 슬롯의 sub-route를 전환해도 **다른 슬롯의 active subpage가 유지**됨

SlateKR의 구조는 슬롯이 `@tab` 하나뿐이고, 탭 전환은 그 슬롯 안의 sub-route 교체다. 한 슬롯 안에서 sub-route를 갈아끼우는 건 일반 navigation이라 mount/unmount가 발생하고, `useState`도 폐기된다. 즉 본래 의미의 "비활성 슬롯 상태 보존"이 적용되는 시나리오가 아니었다.

### 그러면 결정 자체가 틀린 건가

여기서 라우트 분리(예: `/stocks/[ticker]/financials`를 그냥 별도 페이지로 두는 방식)와 다시 비교해 봤다.

| 항목 | 라우트 분리 | Parallel Routes (`@tab` 슬롯) |
|---|---|---|
| layout 공유 | 가능 | 가능 |
| sub-route별 SEO | 가능 | 가능 |
| sub-route별 loading/error | 가능 | 가능 |
| 차등 revalidate | 가능 | 가능 |
| prefetch 제어 | 가능 | 가능 |
| 비활성 슬롯 상태 보존 | 불가 | 이론상 가능, SlateKR 단일 슬롯 구조엔 적용 안 됨 |

실질 차이가 거의 없다. 라우트 분리로도 같은 결과가 나왔을 가능성이 크다.

다만 결정 자체가 잘못이라기엔 애매했다. 공식 문서가 "Tab Groups" 사례를 Parallel Routes 안에서 권장 패턴으로 명시하고 있고(슬롯 안에 layout을 둬서 sub-route 사이를 navigate), SlateKR이 정확히 그 패턴을 따른다. 코드도 잘 동작한다. 향후 슬롯을 추가할 여지도 살아있다.

정리하면 이렇다.

- **잘못 짚은 부분** — [#042](/blog/slatekr/042/)에서 "본 적용 단계에서 결정 근거가 한 층 더 단단해졌다"고 적었던 이유가 비활성 상태 보존이었는데, 그 효과가 SlateKR 구조엔 적용되지 않았다.
- **여전히 살아있는 근거** — layout 고정 영역 유지, 슬롯별 격리 경계, sub-route 단위 차등 revalidate, SEO. 이건 #040에서 적은 본체 근거고 그대로 유효하다.
- **남은 차별성은 작음** — 라우트 분리 대비 고유 가치가 좁아진다. 결정이 합리성을 잃은 건 아니지만, '이 선택이어야만 했다'고 말하긴 어렵다.

### 알게 된 점

- 패턴 이름과 그 패턴의 모든 효과가 자동으로 따라오는 게 아니라는 것. Parallel Routes를 쓴다고 "보존"이 따라오는 게 아니라, 그 효과가 적용되는 구조여야 한다.
- 본 적용 후 실제 동작을 직접 확인하는 단계가 필요했다. 머릿속 그림과 실제 렌더 동작이 어긋나는 구간이 있을 수 있고, 이번이 그 사례였다.

이 회고에서 떠오른 실질 픽스 — `prefetch={false}` 제거로 탭 전환 매끄럽게 / 필터 상태를 따로 보존 — 는 다음 세션에서 다룬다.
