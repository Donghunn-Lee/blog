종결 전에 작은 작업 네 개를 남겨 두었다. 장중 종목 헤더에서 거래량과 시가총액이 가격과 다른 날의 값으로 찍히는 문제(F131), 모바일 성능 점수를 80점 이상으로 올릴 수 있는지 재 보는 probe(F130), 훅 안의 식을 베껴 검증하던 테스트(F128), 실제 값 대신 자리표시를 보여 주던 스타일가이드 색 표(E101)다.

헤더는 기준일 라벨 한 줄로 끝낼 계획이었는데 값을 현재가에 맞추는 쪽으로 바꿨고, 성능 probe는 80점이 보이지 않아 접었다. 나머지 둘은 계획대로 닫았다.

## 가격과 다른 날을 가리키던 헤더

직전 세션에 배포본에서 본 상태를 코드로 따라가 보니 헤더의 세 값이 서로 다른 곳에서 오고 있었고, 거래일 08:00부터 그날 행이 적재되는 20:12까지 약 열두 시간 동안 날짜가 어긋났다.

| 값 | 출처 | 장중에 가리키는 날 |
|---|---|---|
| 현재가 | 시세 폴링 | 오늘 |
| 거래량 · 시가총액 | 서버에서 렌더한 저장 행 | 전 거래일 |
| 기준일 | 클라이언트 시계 | 오늘 |

| 후보 | 판정 |
|---|---|
| 기준일을 저장 행 날짜로 | 기각. 헤더에서 날짜를 보여 주는 곳이 기준일 하나라, 장중 헤더 전체가 전날 값처럼 읽힘 |
| **거래량 · 시가총액을 현재가 소스로** | **채택.** 누적 거래량은 시세 응답에 이미 있고, 시가총액은 현재가 × 상장주식수 |

처음 세운 계획은 앞의 안이었다. 서버 두 파일만 고치면 되는 수정이었지만 현재가 옆 라벨은 세션과 시각만 보여 주기 때문에, 장중에 이 화면을 여는 사람에게는 헤더 전체가 하루 지난 정보로 보인다. 값을 맞추는 쪽은 직전 글에서 서버 렌더를 클라이언트로 옮기는 일이라 스켈레톤과 hydration, 마감 뒤 저장 행과의 수렴까지 검증해야 한다며 미뤄 두었는데, 코드를 열어 보니 걱정이 과했다. 누적 거래량은 이미 클라이언트까지 오고 있었고, KRX 시세와 저장 캔들은 같은 20시 캔들 정의라(#159) 적재 뒤에는 정의상 같은 값이 된다.

## 현재가가 보여 주는 소스를 따르는 통계 행

통계 행이 소스를 따로 고르면 같은 어긋남이 다른 구간에서 다시 생긴다. 그래서 세 값을 현재가가 지금 무엇을 표시하고 있는지에 따라 정하는 순수 함수 하나로 만들었다.

| 현재가 표시 | 거래량 | 시가총액 | 기준일 |
|---|---|---|---|
| 시세(장중 · 애프터마켓) | 응답의 누적 거래량 | 현재가 × 상장주식수 | 오늘 |
| NXT 장외 스냅샷 | 스냅샷의 NXT 거래량 | 스냅샷 가격 × 상장주식수 | 스냅샷 날짜 |
| 저장 행(KRX 장외 · 시세 실패) | 저장 행 거래량 | 저장 행 종가 × 상장주식수 | 저장 행 날짜 |

- **소스 구분은 둘** — 클라이언트에 도착하는 시세와 스냅샷은 응답 모양이 같아 "시세 | 저장 행"만 구분
- **NXT 탭 거래량은 NXT 체결분** — 통합 거래량이 KRX + NXT와 정확히 일치하는 것을 확인. 가격도 NXT 값이라 탭 안에서 일관
- **스냅샷 날짜는 새 필드로** — 기존 응답 날짜는 차트 당일 봉 병합 키라 의미를 바꾸지 않음
- **SSR은 저장 행 값으로 같은 행** — 서버 출력과 모바일 헤더 높이(268px) 그대로, hydration 경고 없음

서버에서 시가총액을 계산하던 코드는 소비처가 없어져 같이 지웠고, 덕분에 종목 layout이 최신 종가 조회에 더 이상 기대지 않게 됐다. 이전에는 그 조회가 실패하면 페이지 전체가 오류 화면이었는데 이제는 핵심 지표 섹션만 실패한다. 장중 화면은 다음 거래일에 확인할 계획이고, README의 모바일 종목 상세 스크린샷은 장 마감 뒤에 다시 찍었다.

## 모바일 성능 80점 역산

README에 적은 PageSpeed Insights(PSI) 모바일 성능은 홈 70점 · 종목 상세 76점이다. 80점이 보이면 고치고 아니면 접는다는 기준을 먼저 정한 뒤, 코드를 고치지 않는 probe로 로컬 Lighthouse를 PSI와 같은 조건으로 돌렸다. 점수는 LCP(가장 큰 콘텐츠가 그려지는 시점) · CLS(레이아웃 이동) 등 다섯 지표의 가중합이라, 후보를 고르기 전에 어느 지표가 얼마나 올라야 하는지부터 역산했다.

```
가중치   FCP 10 · SI 10 · LCP 25 · TBT 30 · CLS 25
홈       80까지 +18.7점 → LCP 하나로 채우려면 3.08초 이하
상세     80까지 +20.3점 → CLS 만점(+10.2)에 LCP 3.3초 이하
```

| 변형 | 홈 | 종목 상세 |
|---|---|---|
| 기준 | 62 | 60 (CLS 0.211) |
| CSS 인라인 | 58 | 54 |
| CSS 인라인 + CLS 패치 | — | 65 (CLS 0) |

후보마다 다시 빌드해 기준과 번갈아 다섯 번씩 잰 중앙값이고, 측정하는 동안 같은 PC에서 빌드나 테스트가 돌지 않게 다른 작업의 순서를 미뤘다. 로컬 점수는 PSI보다 낮게 나왔고 홈은 추정 LCP가 4.9초와 9초 두 모드로 갈렸지만, 번갈아 잰 덕에 같은 모드끼리 비교된 차이만 읽을 수 있었다.

## 80점이 나오지 않은 이유

| 후보 | 판정 |
|---|---|
| CSS 인라인 | 기각. CSS가 `<style>` 1번 + RSC 페이로드 2번, 문서에 세 번 들어가 홈 HTML gzip 12 → 155KB. 두 페이지 −4 · −6점 |
| 종목 상세 CLS 패치 | 보류. 로컬 +10점이지만 로컬 CLS(0.211)가 PSI(0.113)보다 커서 PSI 환산 약 +3점(76 → 79). 데스크톱 높이 · 헤더 분기 대응이 붙음 |
| 첫 화면 아래 코드 지연 로드 | 보류. LCP가 데이터 대기와 CSS에 묶여 있어 TBT 쪽 최대 +4.7점 추정 |

렌더링을 막는 CSS 두 개는 직전 몇 세션 동안 모바일 첫 페인트를 늦추는 원인으로 짚어 둔 것이고, PSI도 1.5초를 줄일 수 있다고 제시하던 항목이다. Next.js의 CSS 인라인 옵션(`inlineCss`)을 켜자 결과는 반대였는데, PSI의 예상 절감은 요청이 사라지는 몫만 세고 문서가 커지는 비용은 세지 않는 듯했다. 옵션도 Next.js 16에서 여전히 실험 단계다. 종목 상세의 LCP는 이번에 원인이 드러났다. 현재가 텍스트는 SSR HTML에 이미 들어 있었고 1.4초의 렌더 지연은 헤더가 서버에서 DB · DART · KIS를 기다리는 시간이어서, 클라이언트에서 그리는 현재가라 느리다고 봤던 해석(#178 · #180)은 틀린 것이었다.

정해 둔 기준대로 접었고 README의 성능 수치와 한계 문장은 그대로 두었다. 남은 수단은 첫 화면 전 JS를 줄이거나 헤더의 서버 대기를 캐시 · 부분 사전 렌더링(PPR)으로 줄이는 구조 작업이라 제출 뒤로 넘겼다. 그 전에 종목 layout이 요청마다 외부 API를 기다리고 첫 화면 컴포넌트와 차트 · 재무가 266KB 청크를 함께 쓰는 지금 구조가 애초에 성능 면에서 비효율적으로 짜인 건 아닌지부터 점검할 생각이다.

## 복제 테스트와 스타일가이드 색 표

나머지 둘은 짧게 끝났다.

- **훅 로직 복제 테스트(F128)** — 테스트 세 곳이 훅 안의 식을 베껴 검증하고 있었음. 순수 함수로 빼 훅 · 컴포넌트 · 테스트가 같은 함수를 import하게 했고, 화면 코드에 2 ~ 3벌씩 있던 중복도 함께 사라짐. 복제본 하나는 휴장일 캘린더 인자가 빠져 이미 원본과 다른 식이었음
- **스타일가이드 색 표(E101)** — 자리표시와 라이트 상수 대신 globals.css의 라이트 · 다크 선언값을 그대로 표시. 브라우저에서 CSS 변수를 읽으면 빌드 단계에서 hex · lab으로 바뀐 값이 나와, 원문 파일을 빌드 시 파싱

복제 테스트 하나는 헤더와 차트의 시세 캐시 키가 같은지 비교하던 것이었다. 키가 갈려 차트 당일 봉이 한 달 멈춰 있던 문제(#174)를 막는 자리인데, 식이 함수 하나로 합쳐지면서 비교할 두 식 자체가 없어졌다. 커밋 전에 다섯 경우의 코드 경로를 대조해 키가 같다는 것을 확인했고, 복제본끼리의 비교는 원래도 실제 코드를 지키지 못했으니 잃은 것은 없다고 봤다.

## 정리

- **F131 종결** — 거래량 · 시가총액 · 기준일을 현재가가 보여 주는 소스로 통일. 기준일 라벨만 고치는 안은 기각. 장중 화면 확인은 다음 거래일
- **F130 종결** — 80점 미달로 접음. CSS 인라인은 순손실, 상세 CLS 패치는 PSI 환산 약 +3점
- **종목 상세 LCP 원인 정정** — 클라이언트 현재가가 아니라 헤더의 서버 대기 1.4초
- **F128 · E101 종결** — 복제 테스트 3곳 순수 함수 추출, 스타일가이드 색 표를 globals.css 원문으로
- **성능 구조 점검 backlog** — 요청당 외부 API 대기와 청크 경계부터

작은 작업 넷으로 잡은 세션이었는데 둘은 계획과 반대로 결론이 났다. 헤더 값 맞추기를 소형이 아니라고 본 것도, CSS 인라인에 1.5초를 기대한 것도 재 보기 전에 정한 크기였다는 점에서 같은 종류의 짐작이었던 것 같다. 엄밀히는 CSS 쪽은 도구가 틀렸다기보다 예상치가 세지 않는 비용이 있었던 거지만.
