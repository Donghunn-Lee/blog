[#018](/blog/slatekr/018/)에서 본문 추출 모듈과 캐시 레이어를 production으로 옮겼다. 그 사이에 들어갈 LLM 호출을 만들 차례다.

이번 작업의 목표는 단순했다. 공시 본문을 받아 요약 텍스트를 반환하는 함수 하나를 만들고, 1회 호출로 연동이 동작하는지 확인하는 것까지. 본 프롬프트 디자인은 일부러 다음 단계로 미뤘다. **이번에는 SDK 연동, 환경변수, 에러 분기 — 이 셋이 따로 잘 돌아간다는 것만 격리해서 확인**하면 됐다.

---

## SDK 선택

SDK가 두 개 있어서 잠깐 확인이 필요했다.

* `@google/generative-ai` — 구 SDK, 2025년 8월 EOL
* `@google/genai` — 신 SDK

신 SDK로 가면 되는 단순한 결정이긴 한데, 한 가지 신경 쓴 부분이 있었다. **인터넷에 떠있는 Gemini 연동 예제의 상당수가 구 SDK 기준이다.** Claude Code 같은 도구에 작업을 넘길 때 학습 데이터 분포상 구 SDK 코드로 끌려갈 가능성이 있어, 작업 지시 프롬프트에 "구 SDK 사용 금지"를 명시적으로 박아뒀다.

---

## 함수 위치 — 도메인 단위로

연동 함수를 어디에 둘지 후보가 두 개였다.

* `lib/gemini.ts` — 범용 Gemini 호출 래퍼
* `lib/disclosure-summary.ts` — 공시 요약 도메인 함수

후자로 갔다. SlateKR에서 LLM이 들어가는 건 공시 요약 하나뿐이고, 다른 곳에서 Gemini를 쓸 일이 없을 가능성이 높다. 미래에 추가로 쓰일지 모른다는 가정만으로 추상화 레이어를 한 겹 더 두는 건 지금은 불필요하다고 판단했다.

직전에 만든 `dart-document.ts`도 같은 결정 패턴이었다. 범용 DART 래퍼가 아니라 도메인 단위로 묶인 모듈. 일관성 있게 가는 게 코드베이스 전체에 좋다.

```
lib/
├── disclosure-summaries.ts  # 복수: DB 캐시 레이어 (#018)
└── disclosure-summary.ts    # 단수: Gemini 호출 (이번 글)
```

같은 도메인이지만 책임이 다르다 — 하나는 DB I/O, 하나는 외부 API 호출. 한 파일로 합치는 것도 가능했지만 분리하는 게 책임 경계가 더 명확하다.

## 에러 분기 — throw 대신 결과 타입

이번 작업에서 가장 신경 쓴 부분이다. 외부 API 호출은 실패 경로가 많다. Gemini 호출에서 떠올릴 수 있는 실패는 다섯 가지였다.

* **Rate limit 초과** (429)
* **타임아웃** (응답이 30초 안에 안 옴)
* **안전 필터 차단** (모델이 응답을 거부)
* **빈 응답** (응답은 왔는데 텍스트가 비어있음)
* **그 외 API 오류**

이걸 try-catch로 던지는 방식과, 결과 타입으로 명시하는 방식 두 가지가 있었다. 후자를 택했다.

```ts
export type SummarizeResult =
  | { ok: true; summary: string; modelName: string }
  | { ok: false; error: SummarizeError };

export type SummarizeError =
  | { kind: "rate_limit" }
  | { kind: "timeout" }
  | { kind: "safety_blocked" }
  | { kind: "empty_response" }
  | { kind: "api_error"; message: string };
```

이렇게 가면 호출자 쪽에서 두 가지 이점이 생긴다.

**처리 누락이 컴파일 단에서 잡힌다.** `result.ok`로 분기하지 않으면 `result.summary`에 접근할 수 없다. throw 방식은 호출자가 catch를 빼먹어도 컴파일이 통과한다.

**실패 종류별로 UI 메시지를 분리할 수 있다.** "지금은 요청이 많아 잠시 후 다시 시도해주세요"(rate_limit)와 "이 공시는 요약이 어렵습니다"(safety_blocked)는 다른 메시지다. throw 방식은 catch 안에서 에러 객체를 다시 분기해야 하는데, 그 분기 로직이 호출자마다 흩어진다. 결과 타입으로 명시하면 분기 자체가 타입 시스템 안에 있다.

다만 한 가지 예외를 뒀다. **API 키 미설정은 throw로 처리한다.** 이건 호출자가 런타임에 핸들링할 영역이 아니라 환경 설정이 잘못된 거다. 결과 타입에 섞으면 의미가 흐려진다.

> ⚠️ throw가 무조건 나쁜 게 아니라, "복구 가능한 실패"는 결과 타입으로, "복구 불가능한 환경 오류"는 throw로 분리하는 게 명확하다.

## SDK 인스턴스 — lazy 생성

GoogleGenAI 인스턴스는 모듈 스코프에서 lazy 생성하도록 했다.

```ts
let _ai: GoogleGenAI | null = null;

const getAI = (): GoogleGenAI => {
  if (_ai) return _ai;
  const apiKey = process.env.GEMINI_API_KEY;
  if (!apiKey) throw new Error("GEMINI_API_KEY is not set");
  _ai = new GoogleGenAI({ apiKey });
  return _ai;
};
```

처음엔 모듈 import 시점에 바로 만드는 게 단순할 거라 생각했는데, 그렇게 하면 환경변수가 없는 상태에서 import만 해도 throw가 발생한다. 테스트 환경이나 다른 코드 경로에서 모듈을 import만 하고 호출은 안 하는 케이스가 깨진다. 첫 호출 시점까지 throw를 미루는 게 안전하다.

## 검증 — 한 번에 하나씩

검증 스크립트도 따로 만들었다(`web/scripts/verify-gemini-call.ts`). `stocks` 테이블에서 종목 하나를 골라 DART API로 최근 공시를 받고, `fetchDisclosureText`로 본문을 추출한 뒤, `summarizeDisclosure`를 호출해 결과를 콘솔에 찍는 흐름이다.

여기서 한 가지 짚어둘 게 있다. **검증 목적은 "SDK 연동 + 환경변수 + 에러 분기 동작"이지 요약 품질이 아니다.** 그래서 임시 프롬프트로 갔다.

```

{text}
```

프롬프트 정교화 전에 SDK 연동 자체가 동작한다는 사실부터 분리해서 확인하고 싶었다. 프롬프트와 연동 코드를 동시에 만들면 문제가 생겼을 때 어느 쪽이 원인인지 분리하기 어렵다. #018에서 본문 추출과 캐시 레이어의 동등성을 따로 검증한 것과 같은 결의 결정이다.

## 정리

이번 단계에서 결정한 것들은 이렇다.

* **SDK는 신 SDK(`@google/genai`)** — 작업 지시에 명시 필요
* **모델은 `gemini-2.5-flash`** — 비용/한도가 아니라 품질 기준
* **함수 위치는 도메인 단위(`disclosure-summary.ts`)** — 범용 래퍼는 미래의 일
* **에러는 결과 타입(discriminated union)** — throw는 환경 설정 오류에만
* **인스턴스는 lazy 생성** — import는 부수 효과 없이 끝나야 한다
* **검증은 SDK 연동만 격리 확인** — 프롬프트 품질은 다음 단계

가장 무게를 실은 부분은 에러 분기 설계였다. 외부 API는 실패 경로가 많고, 그 실패를 호출자에게 어떻게 전달할지가 코드 전체의 견고함을 결정한다. throw로 던져버리면 단순해 보이지만, 호출자 쪽에서 처리 누락이 생기기 쉽고 UI 분기 로직이 흩어진다. 결과 타입으로 명시하면 컴파일러가 호출자를 강제로 분기시킨다.
