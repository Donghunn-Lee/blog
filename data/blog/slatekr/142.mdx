관심종목 서버 저장(#141)을 토요일 오전에 닫고 나니 오후가 남았다. 시장 실측이 걸린 항목은 월요일까지 손댈 수 없고, 다음 큰 아크인 종목별 메모(X8)는 서버·클라이언트 층을 오가는 작업이라 반나절에 억지로 넣을 크기가 아니었다. 그래서 구조 정리 버킷에 하나 남아 있던 서브섹션 error 격리(E57)를 본 작업으로 잡고, 남는 시간에 데이터 안정성 sweep에 쌓아둔 read-only probe 네 건(X16·X24·F40·X14)을 묶어 판정만 내릴 계획이었다.

결과는 계획보다 길어졌다. E57은 실제 갭이 한 곳뿐이라 커밋 하나로 끝났지만, probe 네 건 중 두 건이 바로 고칠 수 있는 결함으로 판명돼 구현까지 이어갔고, 그중 발행주식수 재적재를 세 번 돌리면서 자정을 넘겼다. 커밋은 일곱 개다.

## 가격 통계 섹션만 격리가 빠져 있던 이유

E57은 "재무·공시 프리뷰·가격 통계에 ChartTabsSection의 try-catch 패턴을 확산한다"로 적어뒀던 항목인데, 착수 전 현황 probe를 돌리니 이 비고가 낡아 있었다. 종합정보 탭 다섯 섹션 중 넷은 이미 섹션 내부에서 catch하고 자기 패널 안에 실패 문구를 띄우고 있었고, 남은 건 가격 통계 하나였다.

가격 통계는 조회 함수 안에서 예외를 삼켜 빈 배열로 돌려주고 있었다. 그러면 페이지는 깨지지 않지만 DB 실패가 "가격 데이터 없음"으로 보인다. #037에서 상세 페이지 네 섹션의 catch→빈 폴백을 걷어내며 empty와 error를 구분했는데, 그 패턴이 lib 안에 하나 남아 있던 셈이다.

| 후보 | 판정 |
| --- | --- |
| 섹션 컴포넌트에 try-catch만 얹기 | 기각. lib가 계속 `[]`를 돌려주니 실제 DB 실패는 여전히 empty 경로. 이중 방어처럼 보이지만 바깥 층이 잡을 예외가 없음 |
| **lib의 catch를 제거하고 섹션에서 catch** | **채택.** 다른 조회 함수(재무·일봉)와 같은 throw 계약. 호출처 1곳, `[]` 반환을 단언하는 테스트 없음 |

공용 error 패널 컴포넌트는 만들지 않았다. 다섯 섹션의 실패 문구가 모양은 같지만 제목·래퍼가 미세하게 다르고, 이미 '일시 지연' 배지 통합 검토(R2)가 걸려 있어 거기에 함께 얹는 편이 낫다고 봤다. 검증은 조회 함수 진입점에 `throw`를 박아 가격 통계 패널만 실패 문구가 뜨고 나머지 네 섹션과 route error boundary가 멀쩡한지 확인하는 것으로 끝냈다.

## 발행주식수 누락 205건

205건은 "사업보고서에 주식총수를 안 낸 종목"이려니 하고 정리만 하려던 항목이었다. 그런데 이 205건 중 201건이 재무제표는 들어와 있었다. 재무는 있는데 주식수만 0이면 파서 쪽이 의심스럽고, 세 종목의 DART 주식총수 응답을 직접 받아보니 전부 정상 status에 값이 들어 있었다.

원인은 행 구분 라벨이었다. 파서는 `se == "보통주"` 정확 일치만 인정하는데, DART 서식이 회사마다 이렇게 갈린다.

| 응답 라벨 (원문) | 기존 파서 |
| --- | --- |
| `보통주` | 매치 |
| `보통주식` | 미매치 |
| `보통주\n(의결권 있는 주식)` | 미매치 |
| `의결권 있는 주식` / `의결권있는 주식` | 미매치 |
| `의결권이 있는주식(보통주)` | 미매치 |

여기서 좀 늘어졌다. 공백을 걷어내고 `보통주` 접두어로 바꿔 돌리니 205건이 77건으로 줄었고, 남은 대형주(SK·롯데칠성·KCC)를 다시 받아보니 `의결권 있는` 계열이라 접두어를 하나 더 붙였다. 그래도 삼성전기가 남아서 세 번째로 받아보니 조사 "이"가 끼어 있었다. 재적재 한 번에 20분씩 걸리는 걸 세 번 돌리고 나서야 접두어 목록으로는 끝나지 않는다는 게 분명해졌다.

```python
s = re.sub(r"\s+", "", se)
is_common = s.startswith("보통주") or (
    s.startswith("의결권") and "있는" in s and "없는" not in s
)
```

엄밀히는 세 번째 변형을 보기 전에 규칙형으로 갔어야 했다. 두 번째 변형에서 이미 "라벨은 서식이 아니라 사람이 쓴 문자열"이라는 게 드러났는데, 접두어를 하나 더 추가하는 쪽이 당장 싸 보였다.

| 회차 | 규칙 | shares=0 잔존 |
| --- | --- | --- |
| 착수 전 | `== "보통주"` | 205 |
| 1차 | 공백 제거 + `보통주` 접두어 | 77 |
| 2차 | + `의결권있는` 접두어 | 17 |
| 3차 | 규칙형 | **12** |

잔존 12건은 SPAC 3, 인프라펀드·리츠 3(주식총수 자체를 안 냄), DART 원본이 10⁶배로 잘못 태깅된 1건(상한 게이트가 설계대로 막음), 나머지 소형주 5건이다. 소형주 다섯을 위해 probe를 한 번 더 도는 건 비용 대비 의미가 없어 여기서 닫았다.

대신 서빙 쪽에 가드를 하나 뒀다. 그동안 shares=0인 종목은 헤더에 시가총액이 ₩0으로 찍히고 있었는데, 0을 값이 아니라 결측으로 보고 null로 돌려 표시하지 않게 했다. 잔존 12건과 앞으로 들어올 신규 상장의 미공시 창을 같이 덮는다.

> KRX 기본정보 응답에 상장주식수 필드가 같이 오긴 한다. 이걸로 잔존분을 채우면 12건은 바로 사라지지만, 발행주식수는 DART 원본을 쓰기로 정한 값이고 두 소스를 섞으면 어느 종목이 어느 기준인지 알 수 없게 된다. 쓰지 않았다.

## 한 번도 채워진 적 없던 상장일

X14는 상장일을 확보해 신규 상장 종목의 PER 산식을 활성화하는 항목이었다. #068에서 TTM으로 바꿀 때 상장 14개월 미만이라 분기가 2~3개뿐인 종목은 연환산하는 분기를 같이 넣어뒀는데, 그 판단 입력인 `stocks.listed_at`이 활성 종목 2,650건 전부 NULL이었다. 컬럼도, 읽는 코드도, 툴팁의 "연환산 기준" 문구도 있는데 두 달 넘게 한 번도 타지 않은 경로였다.

KRX 기본정보 API가 상장일을 8자리 날짜로 준다는 건 probe 한 콜로 확인됐다. 결정은 이걸 어떻게 채우느냐였다.

| 후보 | 판정 |
| --- | --- |
| 백필 스크립트 1회 실행 | 기각. 연환산 분기의 대상이 신규 상장인데, 새로 들어오는 종목은 다시 NULL로 남음 |
| **weekly 워크플로우에 편입 + NULL만 채우는 write-once** | **채택.** 종목 목록 갱신 직후 실행. 기존 값은 덮지 않고 재실행해도 UPDATE 0행 |

```
weekly:  fetch_stocks (FSS 종목 목록)
      →  fetch_listed_at (KRX 기본정보 → listed_at IS NULL 인 행만)   ← 신설
      →  update_corp_codes → fetch_shares → fetch_financials → fetch_dividends
```

한 가지 걸린 건 KRX 쪽 사양이었다. 시장 구분을 파라미터로 넘기는 줄 알고 그렇게 짰다가 첫 실행이 KOSPI만 채웠고, 코스닥은 별도 경로로 요청해야 하는 구조였다. 지수 일봉 백필 때 이미 시장별 경로를 썼던 걸 잊고 있었다. 정정 후 2,650건 중 2,646건이 채워졌고, 남은 4건은 KRX 응답 자체에 없는 종목이다.

실제로 연환산 분기가 도는 장면은 이번에 못 봤다. 8월에 상장한 종목 셋이 후보인데 분기 재무가 아직 없어 조건 자체가 성립하지 않는다. 회귀 테스트는 있으니, 첫 분기 재무가 들어오는 시점에 툴팁 문구로 확인하면 된다.

## 정리

- **E57 종결** — 실제 갭은 가격 통계 1곳. lib의 예외 삼킴을 걷어내 empty와 error를 구분. 로드맵 비고가 낡아 있었음
- **F40 종결** — DART 주식총수 라벨 변형 3종 추적, 접두어 열거를 규칙형으로 교체. 205 → 12건. 시총 0 서빙 가드 추가
- **X14 종결** — 상장일 100% NULL 발견, KRX 기본정보로 2,646건 백필 + weekly 편입. 연환산 PER 경로가 처음으로 활성화 가능
- **X16 종결 · X24 backlog** — 관리종목 배지는 기존재. 우선주는 소스 교체와 지표 의미 재정의가 얽혀 포폴 범위 밖

반나절짜리 정리 세션으로 시작해 데이터 결함 두 개를 잡은 하루였다. 둘 다 화면에는 조용히 드러나 있었다. 시가총액 ₩0은 몇 달째 보이고 있었고, 연환산 툴팁 문구는 있는데 그걸 띄울 조건이 한 번도 성립한 적 없었다. "probe 후 조치 불요 판정 가능"으로 잡아둔 sweep 정책이 이 둘을 건진 건 맞지만, 재적재 세 번은 두 번으로 끝낼 수 있었다는 생각이 남는다.
