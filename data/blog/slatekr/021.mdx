## 이슈 1 — 키워드 보강의 범위

### 진단

7일치 100건 중 67% 미분류라는 수치는 [#020](https://velog.io/@dh82680/SlateKR-020-AI-공시-요약-3-프롬프트-디자인과-가드레일-검증) 부산물에서 발견된 거였다. 

### 주가 영향 큰 키워드를 그냥 늘리면 안 된다

쉽게 떠올린 답은 "주가 영향 큰 공시 키워드를 추가하면 된다"였다. 직관적이긴 한데, 한 단계 정리가 필요했다.

"주가 영향력"은 추측 기준이다. 데이터 기준이 아니라 추측으로 키워드를 늘리면 false positive 위험이 생긴다. 예를 들어 "투자판단관련주요경영사항" 같은 모호한 단어가 행정 공시까지 끌어올 수 있다.

그리고 [#012](https://velog.io/@dh82680/SlateKR-012-공시-분류-레이어-공시-태그)에서 분류 레이어를 만들 때도 일반적으로 영향이 꽤 있는 내용에 배지를 달고, 그렇지 않으면 아예 표시하지 않도록 정했었다. 그래서 측정 및 진단 후 분류 범위를 확장하기로 했다.

방향은 "주가 영향 있는 공시를 더 잘 잡자"가 맞고, 수단은 "추측 대신 미분류 데이터를 보고 추가 패턴을 정한다"로 정리됐다.

### 명확 38건과 경계선

진단 스크립트로 기존 기준에서의 미분류 65건 제목을 모두 출력해 분류했다.

- **명확** 38건 — 분류 기준에 명백히 부합하고 키워드 단독으로 신호가 결정되는 케이스 (증권발행실적보고서, 주식병합결정, 단일판매ㆍ공급계약체결, 영업(잠정)실적, 사외이사의선임ㆍ해임 등)
- **경계선** — 주가 영향은 있을 수 있는데 5개 `DisclosureType`에 깔끔히 안 맞거나, 키워드 단독으로 신호 방향이 결정되지 않는 케이스 (불성실공시법인지정예고, 거래정지, 소송 제기 등)
- **제외** — 거래소 행정 공시, IR 행사, 정정 공시 메타 등 의도된 미분류

명확 38건만 추가하기로 결정했다. 경계선 항목은 분류 기준 토론을 동반해야 해서 작업 분량이 예측 어렵고, 38건만으로도 미분류 67% → 24% 수준 개선이 예상됐다. 경계선은 데이터 더 쌓고 별도 사이클에서 보는 게 깔끔할 듯했다.

### 유형 코드 옵션은 보류

진단 전에 한 가지 옵션이 있었다. DART `list.json` 응답에 공시 유형 코드 필드(`pblntf_detail_ty`)가 있는데, 이걸 받으면 제목 매칭보다 정확한 분류가 가능하다.

확인해보니 현재 `dart.ts`의 Zod 스키마가 이 필드를 미수신 상태였다. 도입하려면 Zod 스키마 + 도메인 타입(`DartDisclosure`) + 정규화 + `classifyDisclosure` 시그니처 + 호출처까지 4파일 이상을 동시에 수정해야 했다. 키워드 보강은 한 파일이면 끝난다. 변경 비용 차이가 컸다.

그리고 한 가지 더 짚었다. DART 유형 코드는 행정 분류 기준이고, `classifyDisclosure`는 "주가 영향 가능성"이라는 다른 분류 기준을 갖는다. 1:1 매핑되지 않는다. 유형 코드를 받아도 결국 매핑 테이블이 또 검증 대상으로 들어온다.

키워드 한계가 데이터로 드러나는 시점에 다시 보기로 하고, 이번엔 한 파일로 끝내는 길을 택했다.

### 결과

명확 38건 추가 후 동일 진단 스크립트 재실행:

```
미분류              65 → 24 (65% → 24%)
MAJOR_EVENT          6 → 41
FINANCIAL            0 → 4
SHAREHOLDER_MEETING  1 → 3
OWNERSHIP/AUDIT     변동 없음 (회귀 없음)
```

남은 24건은 거래소 행정 공시, IR 행사, 정정 공시 메타, 그리고 의도적으로 보류한 경계선 항목으로 구성됐다. 이번 작업 범위 안에서는 도달 가능한 지점에 도달한 듯하다.

## 이슈 2 — 비ZIP 응답의 정체

### 비ZIP 응답 유형 분석

[#020](https://velog.io/@dh82680/SlateKR-020-AI-공시-요약-3-프롬프트-디자인과-가드레일-검증)에서 비ZIP 응답이 일부 발생하는 것을 확인했다.

처음에는 100건 수준의 표본으로 확인했기 때문에, 특정 유형에서만 발생한다고 단정하기에는 근거가 약했다. 그래서 이번에는 진단 범위를 넓혀 최근 공시 1000건에 대해 `document.xml` 응답이 ZIP인지, 비ZIP인지 검사했다.

```txt
전체 검사: 1000건

ZIP 응답  : 806건
비ZIP 응답: 194건
```

비ZIP 응답은 모두 같은 패턴이었다.

```xml
Content-Type: application/xml;charset=UTF-8
<?xml version="1.0" encoding="UTF-8" standalone="yes"?>
<result>
  <status>014</status>
  <message>파일이 존재하지 않습니다.</message>
</result>
```

즉, 비ZIP 응답은 "다른 형식의 원문 파일"이 아니라, DART가 해당 접수번호에 대해 원문 파일을 제공하지 못한다는 XML 응답이었다.

비ZIP 194건을 유형별로 나누면 다음과 같았다.

```txt
비ZIP 194건 유형 분류

1. 펀드·ETF 관련 집합투자증권 서류: 약 185건
   - 투자설명서(집합투자증권)
   - 증권발행실적보고서(집합투자증권)
   - 일괄신고서(집합투자증권)
   - 효력발생안내 등

2. 자산유동화 등록 서류: 3건
   - 자산양도등의등록신청서
   - 자산유동화계획의등록신청서 계열

3. 첨부정정 공시: 4건
   - [첨부정정]주요사항보고서(회사합병결정)
   - [첨부정정]주요사항보고서(전환사채권발행결정)
   - [첨부정정]주식병합결정 등

4. 행정성 공시: 1건
   - 정정신고서제출요구
```

기존 100건 표본에서는 `[기재정정]투자설명서(집합투자증권)`이 눈에 띄었다. 하지만 1000건으로 넓혀보니 정확히는 특정 제목 하나가 아니라, **집합투자증권 관련 서류 전반에서 비ZIP 응답이 집중적으로 발생한다**고 보는 편이 맞았다.

그 외에도 자산유동화 등록 서류, 첨부정정 공시, 정정신고서제출요구 같은 예외 유형이 소수 존재했다.

### `status=014`가 뭐였나

비ZIP 응답이 "다른 형식의 파일"이 아니라 "DART가 원본 파일을 제공하지 못한다는 응답"이라는 점이 중요했다.

DART는 공시 메타데이터, 즉 제목·회사명·접수일자 등은 `list.json`으로 제공한다. 하지만 `document.xml`에서 받을 수 있는 원문 ZIP은 모든 공시에 대해 보장되지 않는다.

이번 검사에서 비ZIP 응답 대부분은 집합투자증권 관련 서류에 몰려 있었다. 투자설명서, 일괄신고서, 증권발행실적보고서, 효력발생안내 등이 여기에 속했다. 이들은 SlateKR이 주로 다루는 KOSPI/KOSDAQ 개별 기업 공시와는 성격이 다르고, AI 요약 우선순위도 낮다.

다만 "원문 부재"와 "중요도 낮음"이 항상 같은 말은 아니다. 소수이긴 하지만 첨부정정 공시처럼 개별 기업 이벤트와 연결될 수 있는 유형도 있었다.

따라서 설계상으로는 특정 유형을 단순히 무시하기보다, **원문 파일이 없는 공시는 AI 요약을 수행할 수 없는 데이터 상태로 분리**하는 편이 안전하다고 판단했다.

### 결과 타입으로 통일

이 지점에서 설계 결정에 고민이 있었다. 비ZIP 응답을 어떻게 호출자에게 전달할까?

이전 [#019](https://velog.io/@dh82680/SlateKR-019-AI-공시-요약-2-Gemini-API-연동과-에러-분기-설계)에서 `summarizeDisclosure`가 채택한 패턴이 있었다. discriminated union 결과 타입(`SummarizeResult`)이다.

`fetchDisclosureText`도 같은 패턴으로 가는 게 자연스러웠다.

이유는 두 가지였다.

첫째, **호출 흐름의 일관성**이다. `fetchDisclosureText` → `summarizeDisclosure` 순으로 이어지는데, 앞 단계와 뒷 단계의 실패 전달 방식이 다르면 호출자 분기 패턴이 흔들린다.

둘째, **"파일 부재"는 시스템 오류가 아니라 데이터 상태**다. 네트워크 타임아웃이나 ZIP 추출 실패는 시스템 오류에 가깝지만, "DART에 원본이 없는 공시"는 정상적으로 발생할 수 있는 데이터 상태다.

```ts
export type FetchDisclosureResult =
  | { ok: true; text: string }
  | { ok: false; error: { kind: "file_not_found" } };
```

다른 비ZIP `status` 값은 일단 `throw` 유지로 뒀다. 이번 1000건 검사에서 확인된 비ZIP 응답은 모두 `014`였기 때문이다. 검증된 데이터 상태는 `file_not_found`로 다루고, 아직 확인되지 않은 상태 코드는 시스템 오류로 남겨두는 편이 더 안전하다.

### 사전 차단 필요성 확인

이 작업이 만든 길은 사후 처리다. AI 요약 버튼을 눌렀을 때 원문 부재면 안내 메시지로 처리하는 흐름이다.

사전에 버튼 자체를 안 띄우는 옵션도 있다. 이번 검사 결과만 보면, 집합투자증권 관련 서류는 원문 부재 가능성이 매우 높기 때문에 공시 유형 기반으로 어느 정도 사전 차단할 수 있다.

예를 들면 다음 유형은 AI 요약 버튼을 숨기거나 비활성화하는 후보가 될 수 있다.

- 투자설명서(집합투자증권)
- 증권발행실적보고서(집합투자증권)
- 일괄신고서(집합투자증권)
- 효력발생안내
- 자산양도등의등록신청서
- 자산유동화계획의등록신청서
- `[첨부정정]` 계열

하지만 DART `list.json` 응답에는 원문 보관 여부 필드가 없다. 공시 제목이나 유형 기반 휴리스틱으로 원문 부재 가능성을 줄일 수는 있어도, 호출 전 확정할 수는 없다.

그래서 이번 작업에서는 사후 처리 경로를 확인 가능하게 정리만 했다. `status=014`를 시스템 오류가 아니라 `file_not_found` 결과 타입으로 반환하게 만들고, UI 통합 단계에서 사전 필터링을 추가할지 판단하기로 했다.

## 정리

이번 단계에서 결정한 것들은 이렇다.

- **배지 키워드 분류 보강은 "데이터 확인된 패턴만"** — 추측 기반 키워드 추가 금지. 명확 38건만 추가, 경계선은 보류
- **`pblntf_detail_ty` 활용은 보류** — 1파일 vs 4파일 비용 차이가 크고, 키워드 보강만으로 미분류 65→24%
- **비ZIP 응답은 `status=014` 파일 부재 응답** — 1000건 검사에서 비ZIP 194건 모두 동일 패턴 확인
- **비ZIP은 집합투자증권 관련 서류에 집중** — 194건 중 약 185건이 펀드·ETF 관련 서류
- **예외 유형도 소수 존재** — 자산유동화 등록 서류, 첨부정정 공시, 정정신고서제출요구 등
- **비ZIP 응답은 결과 타입으로** — `summarizeDisclosure`(#019)와 일관. 파일 부재는 시스템 오류가 아닌 데이터 상태
- **사전 차단 별건 이슈** — 유형 기반 휴리스틱은 가능하지만, 사후 처리 경로는 어느 경우든 필요

작업 자체는 작았지만, 두 이슈 모두 처음 가설을 그대로 밀고 가기에는 위험한 지점이 있었다.

키워드 보강은 "주가 영향이 커 보이는 키워드를 추가하면 된다"는 문제처럼 보였지만, 실제 미분류 데이터를 확인해보니 추측 기반 확장은 false positive를 만들 수 있었다.

비ZIP 응답도 처음에는 특정 정정 투자설명서 문제처럼 보였지만, 1000건으로 넓혀보니 집합투자증권 관련 서류 전반에 집중된 패턴이었다. 동시에 소수 예외도 확인되어, 단순 유형 차단만으로 끝내기보다는 `file_not_found`를 별도 데이터 상태로 분리하는 쪽이 안전했다.

가설을 한 번 더 확인하지 않았다면 분류 보강은 노이즈가 늘었을 것이고, 비ZIP 분기는 특정 유형만 막는 어중간한 해결로 끝났을 것이다.

이번 작업에서 챙겨갈 부분은 명확하다. 공시 요약 기능은 "요약에 성공하는 케이스"만이 아니라, "요약할 수 없는 케이스"역시 구조에 함께 넣어야 한다.
