추석 연휴 마지막 날 토요일이라 시세가 필요한 실측은 안 되는 날이었다. README 마감 전에 적어 뒀던 체크 다섯 건, 요약 모델인 Gemini가 몇 달 사이 바뀌었는지와 출처 페이지의 모델 버전 표기, 종목 상세에만 있는 상단 이동 버튼, 홈 지수 슬레이트에서 국내 4셀만 링크가 없는 것, 다우존스 셀의 캡션 때문에 행 높이가 튀는 것, 신규 상장 종목 수집을 주간에서 일간으로 옮길지가 전부 시세와 무관해 이 날에 맞았다.

계획은 Gemini를 먼저 판정하고 무료·한도 조건에 맞는 새 모델이 있으면 교체까지 끝낸 뒤 나머지를 도는 것이었다. 결과는 달랐다. 후보 둘을 실측하고 2.5 유지로 닫았는데, 아무리 봐도 납득이 안되는 결과에 응답 원문과 프롬프트를 다시 꼼꼼히 대조해 보니 3.8을 떨어뜨린 판정 기준에 반론할 근거를 찾았다.

## Gemini 교체 조건과 후보

요약 모델은 2.5 Flash였고 몇 달 전에 고른 값이라 최신 무료 모델을 확인했다. 조건은 "무료이고 RPM·RPD가 현행 이하로 떨어지지 않을 것" 하나였다. 공식 문서가 9월부터 모델별 무료 한도 공개를 중단해서, AI Studio 콘솔에 뜨는 이 프로젝트의 한도가 유일한 근거였다.

| 모델 | RPM | RPD | 판정 |
| --- | --- | --- | --- |
| 2.5 Flash (현행) | 5 | 20 | 기준 |
| 3.8 · 3.7 · 3.6 · 3.5 Flash | 5 | 20 | 조건 통과, 개선 없음 |
| **3.5 Flash-Lite** | 15 | 500 | **1순위.** Google이 2.5 Flash의 후계로 지정. thinking 기본 minimal이라 JSON 추출 용도에 맞음 |

Lite라는 이름이 좀 걸렸지만 세대가 1년 뒤라 벤치마크로는 2.5 Flash 위였고, 써 보면 안다는 판단으로 교체 작업에 들어갔다. 모델명은 lib 안 상수였는데 출처 페이지에도 표기해야 해서 shared 상수 하나로 뽑았다. lib은 SDK와 DB에 의존하는 모듈이라 라벨 하나 때문에 페이지가 그걸 import하면 경계 위반이다.

## 동일 입력 A/B와 thinking

```
캐시된 2.5 요약 3건 vs 새 모델 요약 3건        → 입력이 달라 A/B가 아님
→ 같은 3건(공급계약·최대주주 변동·주총 소집)을 DB 무접촉 스크립트로, 모델 상수만 바꿔 두 번 실행
→ 3.5 Flash-Lite 회귀 → thinking low·medium 재실행    → 복원 안 됨
→ 3.8 Flash(한도 동일·최신) 실측 → 503        → HIGH 재실측 → 503 3/3
→ 2.5를 같은 조건으로 재실측                     → 3/3 성공
```

| 설정 | 지연 ①/②/③ | 사고 토큰 | 내용 | 503 |
| --- | --- | --- | --- | --- |
| 2.5 Flash | 12.9 / 11.1 / 13.5s | 2,028 / 1,790 / 2,293 | 환율·인물별 사유·안건·날짜 형식 전부 유지 | 0/3 |
| 3.5 Flash-Lite minimal | 2.3 / 2.0 / 2.8s | 0 / 0 / 0 | detail 63~122자, 환율·인물별 사유·안건 누락, 날짜 형식 무시 | 0/3 |
| 3.5 Flash-Lite low · medium | 2.0~5.6s | low 0, medium 건별 0~1,471 | low는 minimal과 동일, medium도 ②에서 사고 0 | 0/6 |
| 3.8 Flash 기본 | 3.5 / 실패 / 13.4s | 0 / – / 1,075 | ① 환율 누락·"대규모" 추가, ③은 2.5 이상 | 2/5 (+429 1) |
| 3.8 Flash HIGH | – | – | 미측정 | 3/3 |

3.5 Flash-Lite가 회귀한 이유는 표에 그대로 있다. 2.5는 설정 없이도 건당 2천 토큰 안팎을 생각하고 쓰는데 Lite는 0이었고, low로 올려도 0, medium은 모델이 건마다 정하니 가장 크게 회귀한 최대주주 변동 건에서 0이었다. 프롬프트는 같았으니 생각하고 쓴 것과 안 하고 쓴 것의 차이였고, 한도 25배는 그 경량화의 값이었다.

3.8은 한도가 2.5와 같아 개선은 없지만 최신이고, 2.5의 실제 문제로 보였던 28.5초 지연(timeout 30초 직전)과 Google의 2.5 접근 제한을 풀 수 있어 실측했다. 503이 다섯 번 나와 가용성에서 접었고, 이쯤에서 2.5를 같은 조건(재시도 차단·15초 간격)으로 다시 재니 3건 모두 성공에 최대 13.5초였다. 28.5초는 재시도가 섞인 튄 값이었다. 2.5 유지로 닫고 실측 중 생긴 3.5 캐시 1행만 지웠다.

## 응답 원문 대조와 판정 정정

세션 마무리 하고 블로그 작성 단계에서, 계속 걸리던 찝찝함을 다시 해소해 보기로 했다. 동 시리즈 상위 버전인 3.8flash가 2.5는 만족하는 조건을 만족하지 못한다는 점을 쉽게 납득할 수 없었다.

그래서 각 모델의 응답 원문을 다시 따고, 프롬프트 문제일 가능성도 염두하여 함께 분석했다.

| 항목 | 2.5 Flash | 3.8 Flash |
| --- | --- | --- |
| headline (공급계약) | 계약명 그대로 | "대만 철도 관련 대규모 공급계약" — 계약명 빠짐, "대규모" 추가 |
| facts (공급계약) | 9개 | 10개. 계약상대 영문명, 대금지급 조건(기성청구) 추가 |
| detail (공급계약) | 적용 환율·최근매출액 기준연도 포함 | 환율 빠짐, 단락 구분 |
| facts (주총) | 일시에 "오전 9시" 포함 | 시각 누락, 기존 준비금 총액 추가 |
| detail (주총) | 목적 한 문장 | 목적 + 의결권 행사 방법(서면투표·전자투표 미도입·도착 기한) |

3.8이 못하지 않았다. 독자 효용(지급 조건·의결권 절차)은 3.8, 원문 그대로의 완전성(환율·시각)은 2.5 쪽이었다. 문제는 내가 쓴 5항목 체크리스트였다. 항목을 2.5 출력에서 뽑았으니 2.5가 넣은 걸 빠뜨리면 실패였고 3.8이 더 넣은 건 점수에 없었다. 판정 기준은 현 모델 출력이 아니라 원문에서 뽑아야 한다는 게 이번 교훈이고, "대규모"도 규칙의 글자 위반이지 독자 피해는 아니었다. 가용성 쪽도 엄밀히는 토요일 오후 한 시간의 8콜 표본에 재시도가 1초 뒤 한 번뿐인 구조라 단정할 수준은 아니었다. 2.5 유지는 README 전의 안정 상태라는 근거로만 남긴다.

## 프롬프트 진단

편차의 대부분은 모델보다 프롬프트 공백이었다. #020에서 세운 프롬프트는 2.5의 성향에 암묵적으로 맞춰진 채 그대로였고, 3필드 구조(#081)의 규칙은 JSON 스키마 설명에만 있었다.

| 공백 | 이번에 드러난 증상 | v2 |
| --- | --- | --- |
| 필드 규칙이 스키마 설명에만 | 날짜 형식·facts 반복 금지 무시. detail에 뭘 담을지 모델 성향대로 | headline·facts·detail 역할을 본문에. detail = 표 밖의 산정 근거·조건·절차 |
| 금지어 리스트 | 모델마다 적용이 다르고 "이 공시는 ~알립니다" 반복 | "본문 근거" 원칙으로. 본문 수치 기반 서술 허용, 모델 자신의 크기·전망 판단어 불허, 회사의 목적·평가는 인용형 |
| 분량 기준 없음 | detail 63자에서 312자까지 | 2~6문장 |
| headline 접두 | 매번 12자 낭비 | 접두 금지, 사안 식별 핵심 필수 |
| 풀어쓰기와 원문 유지의 충돌 | 규칙 두 개가 같은 층에서 부딪힘 | facts value는 원문 그대로, 풀어쓰기는 detail에서 |

평가성 표현 금지는 하단 고지가 있으니 완화해도 되지 않느냐는 생각도 있었다. 고지는 법적 포지셔닝이고 이 규칙은 읽기 보조라는 정체성이라 별개로 보지만, 완화할 지점은 있다. 금지어를 세는 대신 근거를 묻는 쪽이다. 프롬프트 v2와 원문 기준 재실측(카테고리별 6~8건, 시간대 2~3창, 재시도 backoff 포함)을 F108로 잡아 다음 세션 1순위에 뒀다. 모델명이 상수 하나라 README 뒤에 바꿔도 출처 페이지가 따라온다.

## 5주 red weekly와 non-KRW 7종목 격리

신규 상장 조사 중 weekly가 8월 말부터 5주 연속 red인 게 보였다. 실패 step은 재무 적재였는데 로그는 Q2 2,614건 전부 적재 완료(성공 0 · 스킵 2,614 · 오류 0)였고, exit 1을 만든 건 #117에서 세운 non-KRW 게이트의 신규 7건이었다.

```
게이트 발화   신규 non-KRW 7건 (900100 USD · 900110/250/260/270/310/340 CNY) — 전원 900xxx 중국계, 오탐 아님
DB 상태      7종목 × 21행 = 147행이 2021 Q1~2026 Q1 외화 원값 그대로 (BPS 0.5~67, EPS 3 미만)
원인         게이트 도입(7/29) 이전 적재분. 기존 키는 skip이라 게이트가 다시 검사하지 않음
```

| 절차 | 내용 |
| --- | --- |
| 통화 대조 | 7종목의 2021·2025 연간 보고서 14건 GET. 전부 CNY/USD, DART 매출액 = DB 원값 |
| 격리 | 행은 두고 수치 7컬럼 NULL(#117 형식). 검증 SELECT 7×21 → UPDATE 147 → 재검증 all_null 21 |
| 등록 | collector known 목록 + web 통화 매핑 상수 각 +7 |
| 검증 | 로컬 1회(게이트skip 0 · known 18 · exit 0) → push → weekly 수동 dispatch green |

격리 SQL은 이번엔 web/sql에 추적 파일로 남겼다. #117 때 콘솔에서 직접 실행하고 파일을 두지 않아서, 이번에 방식을 DB 상태에서 역추적해야 했기 때문이다. 행을 지우지 않는 이유도 그때 확인했는데, 지우면 매주 재조회하고 known 경고가 반복되며 total_equity를 남기면 bps 백필이 값을 다시 채운다. 게이트 자체는 그대로 둔다. red가 유일한 알림 채널이라 경고로 내리면 검토 요청이 아예 안 보인다. 처리 규칙만 세웠다. weekly red는 그 주 안에 본다.

## 정리

- **F104 종결** — 모델명 shared 상수 단일 출처, 출처 페이지에 모델 ID 표기. 모델은 2.5 유지
- **동일 입력 A/B 3모델** — 3.5 Flash-Lite는 프롬프트 보강 없이는 detail 축소, 3.8 Flash는 원문 대조로 품질 2.5 이상·가용성 미확정. 판정 기준은 원문에서 뽑는다
- **F108 신설** — 프롬프트 v2 + 원문 기준 재실측, 다음 세션 1순위
