#120에서 등록한 F64(미백필 신규 종목)와 E55(라우트 fallback 특수 파일)를 이월 계획대로 묶었다. F64 probe에서 같은 패턴의 종목이 하나 더 나와 6종으로 늘었고, E55 probe에서는 내용이 완전히 같은 error boundary 3개가 걸려 같이 처리했다.

---

## fetch_prices는 첫 행이 있어야 돌아간다

F64는 #120 폐지 종목 대조 중에 걸린 문제다. 신규 상장 5종이 daily_prices 0행인데, 리스트에선 live quote로 가격이 멀쩡히 뜨고 상세에 들어가면 "가격 데이터 없음"이 나온다. probe로 원인을 확정했다.

- 티커 선정(`is_active = true`)에는 5종 모두 들어간다
- 루프 안에서 마지막 적재일이 없으면 — "backfill_prices.py로 초기 적재 필요" WARNING을 찍고 skip

즉 fetch_prices는 이미 첫 행이 있는 티커의 증분만 담당하고, 첫 행을 만드는 일은 백필 스크립트에 명시적으로 미뤄져 있었다. #098에서 pykrx를 백필 전용으로 강등할 때 생긴 역할 분담인데, 신규 상장 종목이 이 분담의 틈에 정확히 끼는 거다. stocks에 자동으로 들어와도 누군가 수동으로 백필을 돌리기 전까지 영원히 empty다.

probe에서 동일 조건 전수를 다시 세니 6종이었다. 추가된 282620은 신규 상장이 아니라 거래 재개 — 첫 행이 없다는 점에서는 같은 처지다.

---

## pykrx 확장 대신 KIS 상시 분기

선택지는 둘이었다.

| 안 | 걸리는 점 |
| --- | --- |
| backfill_prices(pykrx) 확장 + 주간 배치 | 신형 티커 수용 미검증 · 신규 상장이 최대 1주 empty 노출 |
| fetch_prices에 초기 적재 분기 상시 편입 | — |

6종 중 둘(0156T0·0218L0)이 6자리 숫자가 아닌 신형 코드다. pykrx는 KRX 스크레이핑 기반이라 이걸 받는지부터 실측해야 하는데, KIS 쪽은 probe에서 이미 답이 나와 있었다.

| 확인 항목 | 결과 |
| --- | --- |
| 신형 티커(T/L 포함) | 6종 전수 HTTP 200 · rt_cd 0 |
| 상장일 이전 구간 요청 | 실데이터 범위만 잘라서 반환 |
| 봉 수 | 전종목 100봉 이하 — 1콜 한도 내 |

두 번째 줄이 결정적이었다. 상장일을 몰라도 넉넉한 lookback을 던지면 KIS가 서버 쪽에서 존재하는 구간만 준다. 상장일 소스를 따로 확보할 필요가 없어진다. warn-skip 블록을 150일 lookback 초기 적재로 교체하고, 이후 호출·파싱·upsert는 기존 증분 경로를 그대로 태웠다. lookback 상수도 새로 만들지 않고 기존 `DAILY_GAP_LIMIT_DAYS`(150)를 재사용했다 — 뿌리 시멘틱이 "1콜 100봉 안전 상한"으로 같다.

상장일 얘기가 나온 김에 — stocks에 listed_at 컬럼이 있는데 전 행 NULL이고 채우는 코드가 없다. KIS 응답의 가장 오래된 봉 날짜로 채우자는 안이 나왔지만 접었다. 282620이 바로 반례다. 그 종목의 oldest는 재개일이지 상장일이 아니고, 프록시 값으로 채우면 맞는 값과 틀린 값이 같은 얼굴로 섞인다. #117에서 본 균일 오염과 같은 유형이라, 정확한 소스(KRX 기본정보 API)가 생길 때까지 비워두는 쪽이 낫다.

## 자동 백필에 상한을 건 이유

초기 적재를 상시 경로로 넣으면서 걸리는 시나리오가 하나 있었다. daily_prices가 어떤 사고로 대량 유실되면 0행 티커가 수천 개가 되는데, 이때 이 경로가 조용히 종목당 150일씩 부분 백필을 해버리면 유실 사실 자체가 가려진다. 구멍 난 데이터가 "최근 150일은 있는" 데이터로 위장되는 거다.

그래서 run 시작 시 0행 티커를 집계해 10건을 넘으면 초기 적재를 전면 skip하고 ERROR만 남기게 했다. 증분 경로는 그대로 돈다. 정상 상황의 신규 상장은 하루 0~3건 수준이라 오탐 여지가 거의 없고, 우회 플래그는 이번에도 안 만들었다.

---

## end 캡은 이식할 필요가 없었다

구현 전에 하드 스톱 조건으로 걸어둔 확인이 하나 있었다. #098의 end 시각 캡 — 장중에 돌려도 당일 잠정 봉이 안 들어가게 하는 장치 — 이 새 경로에도 적용되는가. 답은 코드 위치가 줬다. 캡의 실체가 공통 `parse_bar`의 미래 날짜 drop이라, 같은 파서를 지나는 초기 적재에는 자동으로 걸린다.

검증은 실측 두 번으로 닫았다. 11시대 수동 실행에서 6종의 latest가 전부 08-24(직전 거래일)로 찍혔고, 봉 수도 probe 때 당일 잠정 봉을 포함해 센 값에서 정확히 1씩 빠진 21/20/8/7/5/2였다. 16시 정기 run 뒤에는 6종 모두 08-25 봉이 증분으로 합류했고, 로그에 [initial-load] 태그가 더는 없었다 — 첫 행이 생겼으니 다음부터는 보통 티커다.

## 상폐 정리가 드러낸 404

E55로 넘어간다. #120에서 폐지 32종을 치운 뒤, 열려 있던 폐지 종목 페이지를 다시 여니 404가 떴다. 그런데 화면이 Next 기본 unstyled 그대로다. probe로 현황을 까니 상태가 이랬다.

- 루트: not-found · error · global-error — 전부 없음
- 있는 건 종목 상세 하위의 error·loading뿐

저작 범위를 정하는 데 결정이 하나 필요했다. **종목 상세 스코프 not-found를 둘 것인가.** notFound() 호출이 프로젝트 전체에 딱 2곳인데 둘 다 상세의 layout.tsx 안이고, 세그먼트의 not-found 경계는 자기 layout이 던진 걸 못 잡는다 — 상위로 bubble된다. `stocks/[ticker]/not-found.tsx`를 만들어봤자 어차피 루트가 받는 구조라 루트 하나로 갔다. 문구도 폐지/미존재를 구분하지 않았다. 폐지 종목은 완전 제거한다는 #120 결정과 같은 결이다.

이 404 경로엔 전사가 있다. #037에서 상세 본체의 DB 오류 catch를 notFound()로 흡수하면서 "이 결정은 이후 다시 봐야 할 수 있다"고 적었었다. 40여 세션 만에 그 목적지가 검색 CTA를 단 프로젝트 스타일 404로 바뀌었다 — 잘못 들어온 사용자가 핵심 플로우의 시작점으로 돌아간다.

## error와 global-error — 렌더 환경이 다르다

남은 두 파일은 같은 에러 화면 같지만 렌더 위치가 다르고, 그게 스타일 전략을 갈랐다.

| 파일 | 렌더 위치 | 쓸 수 있는 것 |
| --- | --- | --- |
| error.tsx | root layout 안 | 토큰·SUIT·다크모드·헤더/푸터 전부 |
| global-error.tsx | root layout이 죽었을 때 단독 | 없음 — html·body를 직접 그려야 함 |

error.tsx는 평소 스타일 그대로 재시도(reset) CTA를 달았다. error.message는 화면에 안 낸다 — DB 연결 문자열 같은 게 찍힐 입구다.

global-error는 의존 0으로 갔다. globals.css를 다시 import하면 토큰이 살아나긴 하는데, layout이 죽은 상황의 비상구에 의존을 붙이는 건 목적과 어긋난다. 인라인 스타일에 prefers-color-scheme 몇 줄로 다크 배경만 맞추고, SUIT 없이 시스템 폰트로 나오는 건 감수했다.

---

## 같은 파일 세 벌

probe가 하나 더 짚어줬다. 종목 상세의 chart·disclosures·financials 하위 error.tsx 세 개가 부모 `[ticker]/error.tsx`와 내용이 완전히 같았다(SHA256 일치까지 확인했다). 자식 boundary를 지우면 에러는 부모로 bubble되는데, 같은 카드가 같은 자리에 뜨니 동작이 안 변한다. 세 파일을 삭제하고 tab 3종에 임시 throw를 심어 부모가 받는 걸 눈으로 확인했다.

다만 probe가 같이 드러낸 게 있다. 섹션 단위 격리가 Suspense(로딩) 층에만 있고, error는 여전히 tab pane 통짜 대체다. 서브섹션 안에서 try/catch로 자체 처리하는 건 차트 탭 하나뿐이라, 이 패턴을 다른 섹션으로 넓히는 걸 E57로 등록만 해뒀다. #037에서 시작한 error/empty 구분 라인의 다음 조각인 셈이다.

## 정리

- **F64 종결** — fetch_prices에 0행 티커 초기 적재 경로 편입. KIS의 범위 자동 절단으로 상장일 소스 없이 성립, 6종 백필 + 다음 run 증분 합류까지 실측. 대량 유실 위장 방지로 10건 상한 게이트
- **E55 종결** — 루트 not-found·error·global-error 3종 저작. 세그먼트 not-found는 bubble 구조상 무의미해 기각, global-error는 의존 0
- **중복 정리(편승)** — 동일 내용 tab error boundary 3벌 삭제, 부모 bubble로 동작 무변
- **신설** — E57(서브섹션 error 격리 확산)

리스트와 상세가 다른 말을 하던 상태가 닫혔고, 앞으로의 신규 상장은 당일 16시 run부터 자동으로 들어온다. 404와 에러 화면도 이제 프로젝트 얼굴을 하고 있다. 데이터가 없는 입구와 화면이 깨지는 출구를 같은 세션에 정리한 게 결과적으로 잘 맞물렸다.
