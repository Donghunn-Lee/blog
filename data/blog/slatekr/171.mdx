종목 상세의 시가총액은 종가에 발행주식수를 곱해 계산하고, PBR은 종가를 주당순자산(BPS)으로 나눈 값인데 BPS도 자본을 주식수로 나눠 저장해 둔 값이다. 주식수는 DART 사업보고서에서 주 1회 받아 왔고, 라벨 파서를 고친 #142와 BPS 결손을 복구한 #153을 거친 뒤에도 주식수가 없는 19종목이 남아 항목 하나(F91)로 적어 두었다. 포트폴리오 제출 전 마지막 데이터 항목이라 이번에 닫을 차례였다.

일단 계획대로 되지 않았다. 계획은 F91을 라벨 매핑 몇 줄로 닫고, 미뤄 둔 실물 확인을 정리한 뒤 README를 다시 읽어 보는 가벼운 세션이었다. 결과는 주식수 소스 교체와 BPS 전 행 재계산, 관심종목 저장 결함 수정까지 커밋 일곱이고, README 재검토는 다음으로 넘겼다.

## 계획과 실제

| 계획 | 실제 |
|---|---|
| 주식수 없는 19종목에 라벨 매핑 추가(F91) | 결손은 34종목, 전 종목 주식수 소스를 KRX로 교체 |
| 분봉 route 캐시 편입 검토(R5) | 폴링당 DB 조회 1회로 확인, 백로그 |
| 미뤄 둔 실물 확인 정리 | 정리 완료, 그 과정에서 주식병합 경고 방치 5종목 발견 |
| README 재점검 | 코드와 대조해 불일치 10건 확보, 정정은 다음 세션 |

방향을 바꾼 건 probe 두 건이었다. 금요일 weekly 로그를 기다리는 대신 주식수 없는 종목의 DART 응답과 KRX 값을 직접 받아 보았고(주식수 probe), 병렬로 README가 말하는 기능들의 코드 위치를 따라가며 분봉 route의 폴링 비용을 같이 셌다(코드 probe).

## 주식수 일치율 58%

주식수 probe에서 결손 종목을 KRX 상장주식수와 대조하는 김에 값이 있는 2,610종목도 같이 대조했다. DB 값은 2025년 사업보고서 기준일(12월 31일)에 고정돼 있어서, 올해 있었던 주식병합과 자사주 소각, 증자가 하나도 반영돼 있지 않았다.

| DB ÷ KRX | 종목 수 |
|---|---|
| 일치 | 1,517 (58%) |
| 1% 이내 | 196 |
| 1% ~ 2배 | 599 |
| 2배 이상 · 절반 이하 | 298 |

298종목 중 142종목은 정수배로 주식병합 방향이었고, 4종목은 DART 원본의 단위 오기로 1,000배였다. 화면에는 이렇게 나가고 있었다.

| 종목 | 시가총액 (전 → 후) | PBR (전 → 후) |
|---|---|---|
| 네오팜 (1,000배 오기) | 382조 원 → 3,823억 원 | 1,987.5 → 1.96 |
| 코아시아씨엠 (5:1 병합) | 1,765억 원 → 353억 원 | 3.00 → 0.60 |
| 삼성전자 (자사주 소각) | 1,627.9조 원 → 1,607.7조 원 | 3.84 → 3.79 |

## 소스 교체 판정

| 후보 | 판정 |
|---|---|
| 라벨 매핑 추가 (원래 계획) | 기각. 4종목이 풀리지만 작년 말 값이라 3종목이 4~10배 과대 |
| 반기보고서 fallback | 기각. 24종목이 풀리지만 10종목은 상장 전 주식수 |
| 결손분만 KRX 값으로 채우기 | 기각. 두 소스가 섞이고 나머지 42%는 그대로 |
| **전 종목을 KRX 상장주식수로 교체** | **채택.** 시가총액 정의와 같은 값, 결손 34종목 전부 해소, 하루 호출 2회 |

세 번째 후보는 #142에서 이미 한 번 기각했던 안이다.

> KRX 기본정보 응답에 상장주식수 필드가 같이 오긴 한다. (…) 발행주식수는 DART 원본을 쓰기로 정한 값이고 두 소스를 섞으면 어느 종목이 어느 기준인지 알 수 없게 된다. 쓰지 않았다.

섞지 않는다는 기준은 이번에도 같고, 달라진 건 DART 쪽을 통째로 내렸다는 점이다. 수집은 매일 20:12 체인의 검증 뒤에 두었고, KRX가 값을 다음 영업일에 게시하므로 변경상장 당일 하루는 시가총액이 어긋나는데 이건 수용했다. 값 자체에는 상한을 두지 않았다. 주식병합이면 주식수가 1/10이 되는 게 정상이라 변동폭으로 막으면 오탐이 나기 때문이고, 대신 응답 행 수가 모자라거나 호출이 실패하면 아무것도 쓰지 않고 실패로 끝나게 했다.

## BPS 재계산과 쓰기 전 확인

주식수만 바꾸면 PBR은 그대로 틀린다. BPS가 적재 시점에 한 번 계산해 저장하는 값이고, #153에서 만든 재계산 경로는 BPS가 비어 있는 행만 다뤘기 때문이다. 조회 시점에 계산하도록 옮기는 안도 있었지만 웹 조회 계층과 테스트까지 바뀌어서, 저장은 유지하고 기존 재계산 조건을 "비어 있음"에서 "현재 주식수로 계산한 값과 다름"으로 넓히는 쪽을 택했다.

```
전  주식수(주 1회, DART) ─ BPS는 적재할 때 1회 계산, 이후 빈 행만 보정
후  주식수(매일, KRX) → BPS 전 행 대조 → 다른 행만 갱신    (한 트랜잭션)
```

첫 실행이 바꾸는 양이 커서, 쓰지 않고 변경 예정 내역만 뽑는 dry-run을 먼저 돌려 분포와 표본 세 종목을 본 뒤 실행했다.

| 대상 | 변경 내역 |
|---|---|
| 주식수 1,127종목 | 결손 → 값 34 · 1% 이내 195 · 1~10% 399 · 10%~2배 196 · 2배 이상 303 |
| BPS 40,296행 | 1% 이상 변동 17,116 · 절사·반올림 보정 23,049 · 빈 값 → 값 131 |
| 실행 결과 | dry-run과 일치, 실행 전 전 행 백업, 재실행 시 대상 0행 |

## 탭을 닫을 때 나가던 저장 요청

코드 probe에서 README의 "서버 조회가 실패하면 쓰기를 막는다"는 문장의 위치를 따라가다가, 그 차단을 거치지 않는 경로가 하나 있다는 걸 알게 됐다. #141에서 디바운스 300ms 안에 탭을 닫으면 편집이 사라지는 창을 메우려고 pagehide에 저장 요청을 넣었고, 조건은 "기준선과 다르면 무조건 보낸다"였다. 그런데 조회 중이거나 조회가 실패한 상태에서는 기준선이 비어 있어서 항상 다르다고 판정된다.

```
localStorage가 비워진 브라우저로 접속
  → 서버 조회가 끝나기 전(또는 실패한 뒤) 새로고침
  → pagehide: 기준선 없음 → "다름" → 빈 목록 전송 → 서버 백업이 빈 목록으로 덮임
```

| 후보 | 판정 |
|---|---|
| 기준선이 비어 있으면 보내지 않기 | 기각. 쿠키 없는 첫 업로드도 기준선이 비어 있어 같이 막힘 |
| **동기화 상태로 판정** | **채택.** 조회 중·차단이면 보내지 않음, 확정 상태는 기존 비교 그대로 |

판정은 함수 하나로 빼서 관심종목과 메모(#143) 양쪽에 같이 썼다. 조회 중에 편집하고 곧바로 탭을 닫으면 그 편집은 서버에 가지 않는데, 백업을 지키는 쪽이 우선이라고 보고 남겼다.

| 시나리오 | 수정 전 | 수정 후 |
|---|---|---|
| 조회 실패 상태에서 새로고침 | 서버 [005930] → [] | 요청 0건, 서버 그대로 |
| 조회 중 편집 후 새로고침 | 판정 함수 테스트에서 전송으로 판정 | 요청 0건 |
| 확정 상태에서 종목 추가 직후 새로고침 | 요청 1건 | 요청 1건, 추가분 유지 |

## 로그에만 남아 있던 주식병합 경고

주식수 대조에서 "주식수는 정수배로 줄었는데 가격 히스토리는 옮겨지지 않은" 종목이 몇 개 보였다. #164에서 만든 기업행위 경고의 판정 규칙을 9월 14일 이후 전체에 다시 적용해 보니 미처리가 일곱 종목이었고, 그중 다섯은 9월 23일과 28일 run 로그에 경고가 찍힌 채 그대로 있었다. 경고는 run을 실패시키지 않으니 그날 로그를 열어 보지 않으면 지나간다.

| 항목 | 결과 |
|---|---|
| 9월 11일 이전 재적재 | 7종목 15,629행 |
| 9월 14일 이후 스케일 보정 | 57행, 전부 거래정지 구간 |
| 검증 | 9월 11일 종가가 KIS 수정 종가와 7/7 일치, 병합일 기준가 ÷ 직전 종가 1.0 |

#167의 weekly 5주 방치와 같은 모양이라 좀 민망했다. 미처리 건이 남아 있으면 검증 단계가 실패하도록 바꾸는 일은 다음 세션 항목(F115)으로 잡았다.

## 정리

- **F91 종결** — 주식수 소스를 DART 사업보고서에서 KRX 상장주식수(매일)로 교체. 1,133종목 교정, 결손 34 → 0. 라벨 매핑과 반기 fallback은 값이 낡아 기각
- **BPS 동기화** — 저장은 유지, 현재 주식수로 계산한 값과 다른 행만 갱신. 40,296행 교정, 재실행 시 0행
- **F113 종결** — pagehide 저장 요청을 동기화 상태로 판정. 조회 중·차단 상태에서 서버 백업이 덮이던 경로 차단
- **주식병합 7종목 재적재** — 로그에만 남아 있던 경고 5종목 포함. 지속 감지는 F115로
- **기타** — R5는 backlog(분봉 route 폴링당 DB 조회 1회, 이득이 동시 조회자 수에 비례). 재무 없음 표시는 상장 1년 이내 매주 재확인으로 바꿔 8종목 복귀

소형 항목 하나를 닫으러 들어가서 커밋 일곱이 나왔다. 돌아보면 #142에서 KRX 값을 쓰지 않기로 하던 날 두 소스를 한 번 대조해 봤으면 그때 나왔을 문제다. 엄밀히는 섞지 않겠다는 판단이 틀렸다기보다, 쓰기로 한 쪽이 맞는 값인지를 확인하지 않은 게 빠져 있었던 것 같다.
