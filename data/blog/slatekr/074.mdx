지난 세션에서 차트 툴바를 통합하며, 몇 가지 손질은 다음으로 미뤄뒀다. 이번엔 그 자잘한 것들부터 털 생각이었다. 차트 섹션 윤곽선을 또렷하게 긋고, 툴바 버튼 폭을 고정하는 정도.

그런데 봉 개수 버튼을 다시 보다가 질문 하나가 걸렸다. 휠로 차트를 축소하면 보이는 봉이 늘어나는데, 그 숫자를 봉 개수 입력 칸에 반영할 수 있을까? 별거 아닐 줄 알았는데, 파고들수록 지금 봉 개수를 다루는 방식 자체가 걸림돌이었다. 손질만 하려던 세션이 차트 인터랙션을 다시 짜는 쪽으로 번졌다.

---

## 봉 개수를 자르던 방식

지난 세션의 봉 개수는 이렇게 동작했다. 받아둔 봉 배열에서 뒤쪽 N개만 잘라 차트에 넘긴다.

```ts
const visibleBars = barCount ? bars.slice(-barCount) : bars;
```

이러면 "60봉 보기"는 60개만 차트에 실린다. 문제는 축소다. 휠로 축소해서 봉을 더 보려 해도, 60개 바깥의 봉은 애초에 차트에 없다. 빈 공간만 나오거나, 왼쪽 끝이 고정돼 있으면 아무 일도 안 일어난다. 즉 **자른 개수보다 많이는 못 보여준다.** 확대(보이는 봉 줄이기)는 되는데 축소가 구조적으로 막혀 있었다.

여기에 하나가 더 얽혔다. 지금 차트는 250봉(약 1년)만 받아온다. 곧 몇 년치를 더 넣을 생각이었는데, slice 방식이면 잘라 보여줄 원본이 250봉에 묶여 버린다. 결국 두 문제가 한 뿌리였다 — 봉 개수를 **데이터를 잘라서** 표현하고 있다는 것.

---

## 데이터를 다 싣고 화면만 조절

방향을 바꿨다. 봉을 자르지 않고 전부 차트에 싣고, 봉 개수는 **보이는 화면 범위**로만 조절한다. lightweight-charts에는 논리적 범위를 지정하는 API가 있어서, "마지막 N개가 보이도록" 창을 잡아주면 된다.

```ts
timeScale().setVisibleLogicalRange({ from: len - n, to: len - 1 + margin });
```

이렇게 하니 세 경로가 하나로 정리됐다. 프리셋·직접입력은 이 창을 세팅하고, 휠은 반대로 현재 보이는 범위를 읽어 봉 개수 칸에 되돌린다. 확대든 축소든 데이터가 이미 다 실려 있으니 양쪽 다 자연스럽게 흐른다.

전량을 싣는 게 부담일까 봐 실제 봉 수를 재봤다. 현재 가장 오래된 종목이 3046봉, 12년 남짓이었다. 다 받아도 gzip 수십 KB 수준이고, 페이지는 어차피 한 시간 단위로 캐시된다. 추후 데이터를 더 적재 해봐야 명확해지겠지만, 당장은 무한 스크롤로 과거를 조금씩 불러오는 장치는 과하다고 판단했다. 기본 뷰는 최근 1년으로 두고, 축소하면 12년 전체까지 펼쳐지도록 했다.

여기서 조심할 건 되먹임 고리다. 휠이 범위를 바꾸면 봉 개수가 갱신되고, 그 갱신이 다시 범위를 세팅하면 무한히 돈다. 프로그램이 창을 세팅하는 동안엔 플래그를 세워 휠 콜백이 무시하게 막고, 되돌리는 값은 80ms 디바운스로 눌렀다.

## 오른쪽 여백 조정

범위를 직접 잡기 시작하니, 그동안 어정쩡했던 오른쪽 여백이 도드라졌다. 차트 오른쪽 끝엔 최신 봉이 벽에 붙지 않게 여백을 조금 준다. 그런데 이 여백을 "봉 6개"처럼 개수로 박아두고 있었다.

일봉에선 6봉이 얇은 띠지만, 월봉은 화면에 열두 봉쯤 보이니 6봉이면 **화면의 절반**이 빈다. 개수 고정의 함정이었다. 처음엔 주기별로 다른 개수를 줄까 했는데(일 10·주 2·월 1), 그러면 줌을 할 때 또 어긋난다. 보이는 봉이 줄면 고정 여백이 상대적으로 다시 커지니까.

그래서 개수가 아니라 비율로 갔다. 보이는 봉 수의 4%를 여백으로 준다.

```ts
const margin = visibleCount * 0.04;
```

일봉 250봉이면 10봉, 주봉 52봉이면 2봉, 월봉 12봉이면 반 봉 남짓. 주기가 뭐든 줌이 얼마든 화면 대비 여백 비율은 같다. 개수로 두던 옵션은 걷어내 여백이 이중으로 붙는 걸 막았다.

---

## 미래로 끝없이 밀리는 문제

잠금을 풀고 나니 반대쪽이 열렸다. 차트를 오른쪽으로 계속 끌면 데이터 없는 미래로 한없이 밀려났다. 적당히 막아야 했다.

라이브러리엔 양 끝을 고정하는 옵션(`fixLeftEdge`, `fixRightEdge`)이 있다. 과거쪽은 여백을 둘 이유가 없어 `fixLeftEdge`로 깔끔하게 막힌다. 문제는 오른쪽이었다. 우리는 오른쪽에 4% 여백을 일부러 두는데, `fixRightEdge`가 이 여백과 부딪힐 것 같았다.

짐작 대신 라이브러리 소스를 열어봤다. 압축된 코드였지만 해당 분기는 분명했다 — `fixRightEdge`가 켜지면 오른쪽 여백을 0으로 깎는다. 우리가 준 여백을 그대로 삼키는 거였다. 그래서 오른쪽만 직접 처리했다. 휠·팬으로 범위가 바뀔 때, 오른쪽 끝이 여백 한계를 넘으면 되돌린다. 되돌릴 때 튕기는 느낌이 안 나게 약간의 여유를 두고, 앞서 만든 플래그로 되먹임도 막았다.

## 지수 변경 시 차트가 다시 그려진다

여기까진 종목 차트 얘기고, 같은 구조를 지수 차트에도 맞춰 넣었다. 그러다 지수 페이지에서 코스피↔코스닥을 오갈 때 차트 전체가 껌뻑이며 다시 그려지는 게 눈에 띄었다.

원인은 Suspense 경계에 걸린 `key`였다.

```tsx
<Suspense key={selected} fallback={<ChartSkeleton />}>
```

지수 코드가 바뀔 때마다 `key`가 바뀌니, 서버 컴포넌트가 통째로 다시 실행되고 그때마다 스켈레톤이 깜빡였다. 실시간 데이터는 이미 세 지수를 한꺼번에 구독하고 있었으므로, 일봉만 세 지수를 서버에서 미리 받아 넘기면 전환할 때 새로 부를 게 없었다. `key`를 걷어내고, 지수 선택을 클라이언트 상태로 옮겼다. URL은 히스토리를 오염시키지 않게 `replaceState`로만 맞춰 딥링크와 새로고침은 살렸다.

전환할 때 껌뻑임이 사라지고 툴바도 그대로 유지된다. SEO에 필요한 초기 렌더는 세 지수 모두 서버에서 내려오니 손해가 없다.

### 지수를 바꿔도 차트가 그대로인 문ㅈ

전환을 매끄럽게 만들고 보니 이상한 게 남았다. 지수를 바꾸면 현재가만 코스닥 값으로 바뀌고, 캔들 몸통은 코스피 그대로였다.

차트는 데이터가 살짝만 바뀌면(장중 마지막 봉 갱신 같은) 전체를 다시 그리지 않고 끝봉만 손본다. 그 판정을 "첫 봉의 시각이 같고 길이가 같으면 같은 데이터"로 하고 있었는데, 지수 전환은 데이터셋이 다른데도 우연히 첫 봉 시각과 길이가 겹쳤다. 그 바람에 갱신 경로로 빠져 첫 봉만 빼고 옛 캔들이 남은 거다. 판정에 첫 봉의 시가·고가·저가·종가까지 비교를 더해 막았다. 장중 갱신이나 주기 전환은 이 조건에 안 걸려 원래대로 흐른다.

## 기간 프리셋 제거

마지막으로 봉 개수 프리셋(60·120·250)을 두고 고민이 남아 있었다. 휠과 직접입력으로 조절이 다 되니 프리셋 버튼이 사실 겉돌았다. 게다가 이 숫자들이 바로 옆 `일·주·월`과 한 줄에 붙어 있어서, `일 60` 처럼 "60일봉" 하는 배수봉으로 읽혔다. 실제로 나부터 그렇게 보였다.

설명을 덧붙이기보다 프리셋을 지우는 쪽이 나았다. 숫자 나열이 사라지니 주기 버튼이 배수봉으로 오해될 여지도 같이 없어진다. 봉 개수 조절은 휠과 직접입력으로 남겼다.

![](/static/images/velog/9980d5e1-63a7-4ca0-9b8d-9500adef561d-image.png)

프리셋이 있던 자리를 어떻게 채울지 잠깐 봤는데, 억지로 뭘 넣기보다 비우는 게 나았다. 대신 당일 차트 쪽을 손봤다. 전체 차트가 `일·주·월`이라면, 당일 차트는 그동안 주기 선택이 비활성인 채였다. 여기에 분봉 단위(`1·5·30분`)를 넣어, 당일 안에서 봉을 얼마로 묶어 볼지 고를 수 있게 했다. 이미 받아둔 1분봉을 시간 버킷으로 다시 묶는 거라 추가 호출은 없다.

```ts
resampleIntradayBars(bars, intervalMin);  // 1분봉 → N분봉, 거래량은 버킷 합산
```

이쯤에서 지난 세션에 적어둔 말이 떠올랐다. 주봉·월봉 리샘플러가 판박이라 "세 번째가 나오면 그때 묶겠다"고 미뤄뒀는데, 분봉 리샘플러가 딱 세 번째였다. 막상 나란히 놓고 보니 못 묶겠더라. 셋의 입력 타입이 제각각이고(지수 일봉 스냅샷, 종목 봉, 분봉), 날짜가 문자열인 것과 숫자인 것이 섞이고, 거래량 처리 방식도 달랐다. 억지로 하나로 묶으면 멀쩡히 돌던 두 리샘플러까지 위태로워진다. 세 번째가 나오면 묶겠다던 규칙이 무색하게, 이번엔 안 묶는 게 맞았다. 엄밀히는 "세 번째"라는 개수가 기준이 아니라 시그니처가 얼마나 닮았는지가 기준이었던 거다.

당일·전체 양쪽 다 범례가 빠져 있던 것도 이참에 채웠다.

## 정리

디자인 손질부터 하려다 차트 인터랙션을 다시 짠 세션이었다.

- **봉 개수 재설계** — 데이터를 자르던 방식을 걷고, 전량을 실은 뒤 보이는 화면 범위로 조절. 휠 축소·확대가 양방향으로 맞물림
- **오른쪽 여백** — 봉 개수 고정에서 보이는 봉의 4% 비율로. 주기·줌 무관하게 균일
- **이동 범위** — 과거는 네이티브 옵션, 미래는 라이브러리 소스를 확인하고 직접 되돌리는 방식으로
- **지수 전환** — Suspense `key`가 부르던 재렌더를 걷고, 세 지수 일봉을 서버에서 미리 받아 클라이언트 상태로 전환
- **기간 프리셋 제거** — 휠·입력으로 대체되고 배수봉 오해를 부르던 프리셋을 삭제. 당일 차트엔 분봉 단위와 범례를 추가

봉 개수를 데이터가 아니라 화면으로 다루기 시작하니, 여백·이동·전환까지 줄줄이 정리됐다. 하나를 제대로 고치면 옆의 것들이 같이 풀리는 세션이 가끔 있는데 이번이 그랬다. 라이브러리 동작을 짐작 대신 소스로 확인한 것도, 리샘플러를 규칙에 얽매이지 않고 안 묶기로 한 것도, 결국 같은 태도였다.

## 다음 작업

차트 인터랙션은 이걸로 대체로 정리됐다. 남은 건 당일 차트의 잠금 자체를 풀지 여부와, 미뤄둔 안정성·구조 트랙들이다.

- **H3 — 당일 차트 잠금 해제** — 확대·축소·이동을 당일에도 열지. 다만 당일은 오늘 봉만 있어 자유롭게 줌할 실익이 크지 않아, 필요성부터 다시 볼 생각이다
- **F20 — hydration 불일치** — 종목 헤더 현재가의 서버·클라 렌더 어긋남
- **C·D·E 잔여** — 상세 페이지 디테일과 홈·관심종목 쪽 남은 손질

우선순위는 실익이 분명한 것부터다. H3는 당일 잠금을 풀 이유를 먼저 저울질한 뒤 잡기로 했다.
