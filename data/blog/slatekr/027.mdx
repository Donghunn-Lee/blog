#000부터 #026까지 27편을 썼다. 프로젝트 세팅부터 재무 슬레이트 데이터 구체화까지. 매일 충실히 했다고는 못하겠지만  5주 정도가 지났다. 기능 단위로 쪼개서 한 편씩 기록하다 보니 어느새 꽤 쌓였는데, 정작 전체를 한 발 물러서 본 적은 없었다.

이번 글은 작업 회고가 아니라 **프로젝트 중간점검**이다. 뭐가 됐고, 뭐가 안 됐고, 앞으로 뭘 해야 하는지 정리한다.

---

## 지금까지 뭘 만들었나

5주 동안 만든 것을 크게 나누면 이렇다.

| 트랙 | 주요 작업 | 관련 글 |
|---|---|---|
| **데이터 파이프라인** | pykrx OHLCV + DART 재무/공시 수집, MySQL 적재, collector 4개 스크립트 자동화 | #002~#005, #015~#016 |
| **핵심 플로우** | 검색 자동완성 + /search 라우트, 종목 상세 5섹션 Suspense, 관심종목 Zustand persist | #007~#009, #014 |
| **데이터 계층** | lib/ 정규화 레이어, DB Row → 도메인 모델, 파생 지표 계산 | #006, #025~#026 |
| **AI 공시 요약** | DART 본문 추출 → Gemini 요약 → DB 캐시 → 사이드 패널 UI | #017~#022 |
| **디자인 시스템** | 라이트 모드 전환, 5색 슬레이트 토큰, /styleguide, 인터랙션 | #023~#024 |
| **재무 확장** | 5년 연간 + 분기 12지표, 축 전환, BPS 백필 | #025~#026 |

핵심 플로우인 **검색 → 종목 상세 → 관심종목 저장**은 동작한다. AI 공시 요약도 spike부터 UI 통합까지 한 사이클을 돌았다. collector도 cron만 걸면 매일 돌릴 수 있는 상태다.

## 잘 된 것

### 데이터 흐름이 안정적이다

#006에서 잡은 데이터 흐름 원칙이 지금까지 깨지지 않았다.

```
DB / 외부 API → lib/ (조회 + 정규화) → 도메인 모델 → UI
```

재무 슬레이트를 초기 3개 항목에서 14개 지표로 확장하고, 연간/분기 탭을 추가하고, 파생 지표 계산 책임을 lib에 넣는 과정에서도 이 흐름은 유지됐다. UI 컴포넌트는 여전히 도메인 모델만 받는다. #025에서 `FinancialPeriod` 타입을 전면 재설계했는데, 변경이 lib 경계 안에서 끝났다.

다만 자동화 갱신에 대해선 cron 설계 후 검증이 필요하다.

### 에러 처리 패턴이 일관적이다

AI 공시 요약 트랙에서 만든 패턴이 꽤 잘 작동하고 있다.

- `SummarizeResult` — Gemini 호출 결과 (discriminated union)
- `FetchDisclosureResult` — DART 본문 추출 결과
- API Route — `{ ok: true, summary } | { ok: false, error: { kind } }`
- UI — 상태 머신 5종 (idle / loading / success / blocked / error)

throw 대신 결과 타입으로 실패를 표현하니까, 호출자가 분기를 빼먹으면 컴파일에서 잡힌다. 에러 8종을 사용자 의미 기준 4그룹으로 묶어 UI 메시지를 매핑한 것도 (#022) 나름 깔끔하게 떨어졌다.

### 블로그가 이해 도구로 작동했다

사실 이게 좀 의외였다. 글을 쓰려면 "왜 이렇게 했지?"를 다시 정리해야 하는데, 그 과정에서 Claude Code가 작성한 코드의 구조를 내가 다시 이해하게 되는 경우가 꽤 있었다. AI 보조 개발에서 "내가 짠 코드인데 정확히 모른다"는 상태가 자연스럽게 생겨 걱정이 많았는데, 블로그가 그걸 잡아주는 역할을 한 셈이다.

---

## 안 된 것

### 배포가 아직이다.

이게 제일 크다. 5주 동안 로컬에서만 돌고 있다. collector cron 등록, Next.js 빌드 배포, 환경변수 세팅 — 다 해야 하는데 계속 뒤로 밀렸다. 디자인 트랙이나 재무 확장처럼 눈에 보이는 작업에 자꾸 먼저 손이 갔다.

### 핵심 지표 수치가 틀려 있다

#026에서 발견한 문제인데, EPS/BPS/ROE/ROA가 네이버 증권과 값이 다르다. 현재 연결 전체 기준으로 계산하고 있는데, 업계 관행은 지배주주 귀속 기준이다. 정보 조회 서비스에서 숫자가 틀려 있으면 신뢰도 문제가 된다. collector + DB 스키마 + lib 동시 수정이 필요해서 범위가 작지 않다.

### 관심종목 페이지가 비어 있다

페이지는 만들어뒀는데, Navbar 아이콘 외에 진입 경로가 없고, UI도 거의 기초 상태다. 핵심 플로우의 마지막 단계인데 가장 손을 못 댄 부분이다.

### 디자인이 아직 미완성이다

#23에서 디자인 토큰을 만들고, `/styleguide` 페이지까지 만들어서 체계적인 디자인의 기틀을 마련했지만 역시 디자인은 어렵다. 자꾸 하나씩 눈에 밟혀서 고치려다 보면, 금세 전반적인 디자인 시스템의 개편에 초점이 옮겨간다.

너무 부실하지 않되, 과하게 신경쓰지 않는 적정선을 찾아 디자인하는 것이 중요하다는 것은 잘 알고 있다.

우선은 종목 상세 페이지의 슬레이트 열람 방식은 이미 고려중이라고 언급했는데, 이 부분을 손 보고 나머지는 부분적으로만 손 댈 생각이다.

## 지금 느끼는 것

솔직히 좀 조급하다. 5주가 지났는데 아직 배포도 안 했고, 고쳐야 할 것도 많고, 추가하고 싶은 것도 많다. 근데 더 솔직하게 말하면, 조급함의 원인이 "진도가 느려서"보다는 **"남은 작업이 정리가 안 돼서"**에 가까운 듯하다.

초반에는 없는 것만 만들면 됐다. DB 스키마 → 적재 → 정규화 → 상세 페이지 순서가 자명했다. 근데 어느 정도 형태가 잡히니까 개선·수정·추가가 동시에 보이기 시작했다. 디자인 뜯어고치고 싶고, 공시에 필터링 넣고 싶고, 재무 표시 양식도 다듬고 싶고, 프롬프트도 개선하고 싶은데 — 갑자기 불어난 할 일에 뭐부터 해야 할지 감이 안 잡혔다.

**그것이 이번 "중간 점검" 글을 작성하게 된 이유다.**
잠시 한 발 멈추고, 메모해둔 수정 사항과 남은 작업을 전부 꺼내서 정리했다.

## 실행 순서

전부 동시에 할 수는 없으니 Phase로 나눴다.

**Phase 1 — 올려놓기**
배포가 먼저다. 로컬에서는 없었던 이슈를 미리 확인할 수 있는 시간이 필요하다. EPS/BPS 산식도 배포와 병행한다. 틀린 숫자가 노출되는 건 정보 서비스에서 치명적이니까.

**Phase 2 — 핵심 품질**
반응형, fallback 점검, 미수집 종목 조사. 배포된 상태에서 실기기로 확인한다.

**Phase 3 — 구조 + 디자인**
상세 페이지 구조 재설계가 여기 들어간다. 렌더링/SEO 전략 결정이 필요해서 범위가 크다. AI 요약 패널 디자인, 홈 디자인, 관심종목 페이지도 이 시기에.

**Phase 4 — 마무리**
README, 이력서, 포트폴리오 정리. 배포 URL이 있는 상태에서 써야 의미 있다.

## 정리하면

5주 동안 데이터 파이프라인, 핵심 플로우, AI 요약, 디자인 시스템까지 꽤 많은 걸 쌓았다. 근데 밖에서 보면 아직 로컬에서만 도는 프로젝트다. 기능을 더 추가하는 것보다, 만든 걸 세상에 꺼내놓는 게 지금 단계에서 더 급하다.
