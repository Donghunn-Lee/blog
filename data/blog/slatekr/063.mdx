#062에서 종목 상세 헤더에 실시간 현재가를 붙이고, 남은 건 관심종목·최근조회 리스트도 헤더처럼 살리는 일(E18), 다른 하나는 토큰을 배포 환경에 맞게 옮기는 일(A6)이었다. 이 둘은 따로 떨어진 작업이 아니라 묶여 있었다. 리스트를 실시간으로 돌리면 폴링이 늘어 토큰 발급이 잦아지고, 그러면 #062에서 미뤄둔 토큰 공유 캐시가 그제야 실제로 필요해진다. 그래서 이번 세션은 A6를 먼저 깔고 그 위에 E18을 얹는 순서로 갔다.

---

## 토큰을 Neon 한 행으로 옮기기

토큰을 cron이 발급해 Neon에 두고 앱에서 읽기만 하는 방식으로 직전 작업에서 결정했다. 1분에 한 번이라는 발급 제한과 Vercel 다중 인스턴스 때문에, 발급 책임을 앱에서 떼어 한 곳에 모으는 그림이다. 이번엔 그걸 실제로 구현했다.

구현은 두 갈래다.
- collector에 발급 스크립트를 두고 12시간마다 cron 실행
- 앱의 `getKisToken` 내부를 메모리 캐시에서 Neon 읽기로 변경

앱은 평소엔 DB 한 행을 읽고, 그 행이 비었거나 만료됐을 때만 한 번 직접 발급해 채운다. cron이 한 번 걸러도 이 fallback이 버틴다.

구현하면서 정한 것 중 하나가 만료 시각을 어떻게 저장하느냐였다. 원래 메모리 캐시는 토큰을 받을 때 만료 시각에서 10분을 미리 빼 저장했다. 만료 직전에 아슬아슬하게 쓰다 실패하는 걸 막는 버퍼다. 그런데 이 버퍼를 저장 시점에 적용해 두면, 같은 토큰 행을 읽는 쪽마다 버퍼가 다를 때 값이 어긋난다. collector 쪽은 60초, 앱 쪽은 600초를 쓰고 있었다.

그래서 DB에는 가공 없는 만료 시각을 그대로 넣고, 버퍼는 읽는 쪽에서 각자 적용하기로 했다. 저장값은 순수한 사실 하나로 두고, "얼마나 미리 만료로 칠지"는 쓰는 쪽의 판단으로 넘긴 셈이다.

```ts
// 저장: 버퍼 없는 raw 만료 (epoch ms)
expires_at_ms = Date.now() + expires_in * 1000;

// 읽기: 판정 시점에 600초 버퍼 적용
const valid = Date.now() < row.expires_at_ms - 600_000;
```

`getKisToken`의 반환 타입과 호출부는 건드리지 않았다. 호출하는 쪽은 토큰 문자열 하나만 꺼내 쓰지 내부가 메모리인지 DB인지 모른다. 그래서 안쪽만 갈아끼우는 걸로 끝났고, 현재가를 부르는 코드들은 한 줄도 바뀌지 않았다.

## 등락 표시 공용 컴포넌트로

이건 #061부터 미뤄둔 작업이다. 지수 패널과 종목 헤더가 각자 등락(변화량·변화율·색)을 인라인으로 그리고 있었는데, 표기 방식이 달라서 묶기 애매했다. 헤더는 "원" 단위에 부호를 붙이고, 지수는 단위 없이 ▲▼와 절대값으로 보여준다. 사용처가 둘뿐일 땐 variant를 받는 컴포넌트를 설계하는 비용이 추출 이득보다 커서, 세 번째 사용처가 생기면 그때 빼기로 했었다.

이번 관심종목 리스트가 그 세 번째다. 세 곳의 표기를 늘어놓고 보니, 다른 건 세 축뿐이었다.

| 축 | 헤더 | 지수 | 관심종목 행 |
| --- | --- | --- | --- |
| 부호 | `+`/`-` 텍스트 | ▲▼ 기호 | `+`/`-` 텍스트 |
| 단위 | "원" | 없음 | "원" |
| 크기 | 큼 | 중간 | 작음 |

색 규칙(상승 빨강·하락 파랑·보합 회색), 퍼센트 포맷, 천 단위 콤마는 셋이 완전히 같았다. 그래서 다른 세 축만 prop으로 받는 컴포넌트로 묶었다.

```ts
type PriceChangeProps = {
  change: number;
  changeRate: number;
  sign?: PriceSign;            // 없으면 change 부호로 자동 판정
  symbol?: "sign" | "arrow";   // 기본 sign, 지수만 arrow
  unit?: string;               // "원" 또는 없음
  size?: "lg" | "sm" | "xs";
};
```

순서는 신중하게 갔다. 컴포넌트를 먼저 빼서 헤더와 지수를 거기에 태우고, 화면이 전과 똑같이 보이는지 확인한 다음에야 관심종목에 새로 적용했다. 추출과 신규 적용을 한 커밋에 섞으면, 뭔가 어긋났을 때 추출이 깬 건지 새 적용이 깬 건지 가려내기 어려워진다.

확인하다 회귀를 하나 잡았다. 부호를 "0 이상이면 +"로 통일했더니, 보합(0%) 케이스가 `+0원 (+0.00%)`로 떴다. 장 시작 전이나 NXT 미지원 종목에서 "전일과 같음, 변동 0%"를 표시하는 자린데, 거기 `+`가 붙으니 상승처럼 읽힌다. 색은 회색이라 큰 오해는 아니지만 기호가 모순이라, 보합일 땐 변화량·변화율 양쪽 다 부호를 빼도록 고쳤다.

## 관심종목 실시간 현재가

리스트는 지금까지 저장 시점의 종가(EOD)만 보여주고 있었다. #062에서 헤더는 +2.11%인데 같은 종목이 리스트에선 -12.47%로 떠 있던 게 이것 때문이다. 리스트 값이 관심종목에 담을 당시의 종가에 멈춰 있던 거다.

여기에 실시간을 얹는 방식은 두 갈래였다.

| 방식 | 내용 | 문제 |
| --- | --- | --- |
| 라이브 일원화 | EOD를 걷어내고 실시간만 | 장 마감·NXT 미지원이면 가격이 빈다 |
| EOD 위에 라이브 | 종가를 깔고 장중엔 실시간이 덮음 | 데이터 출처가 둘 |

EOD를 걷어내는 쪽이 코드는 단순하다. 하지만 NXT로 시간외 가격이 도는 종목은 800개 정도뿐이고, 나머지는 장이 닫히면 실시간 값이 비어버린다. 그러면 그 종목들은 장 마감 후에 가격 칸이 빈 채로 남는다.

종목 상세 페이지 헤더에서 이미 "서버에서 종가를 깔고, 장중엔 그 위를 실시간이 덮고, 장이 닫히면 종가로 남는" 모델을 적용했었다. 이는 지수 슬레이트도 마찬가지다. 따라서 리스트도 같은 모델로 맞추는 게 두 화면의 폴백 동작을 일치시키는 길이라, EOD를 폴백으로 남기는 쪽을 골랐다. 행은 실시간 값이 있으면 그걸 쓰고, 없으면 종가로 떨어진다.

```tsx
const displayPrice  = liveQuote?.price  ?? eodPrice;
const displayChange = liveQuote?.change ?? eodChange;
```

데이터 소스가 둘인 건 공짜가 아니지만, "장 마감엔 종가, 장중엔 실시간"은 어느 증권 서비스나 그렇게 도는 표준 동작이라 받아들였다.

#### 관심종목 멀티 조회

호출은 헤더처럼 종목마다 따로 부르면 관심종목이 늘수록 호출이 폭증한다. 그래서 한 번에 최대 30종목을 받는 멀티 조회를 쓴다. 응답이 어느 키로 오는지가 코드에 없어서 — 예전 probe로 한 번 확인은 했었는데 결과를 저장해두지 않았다 — 기존 probe를 다시 돌려 구조만 떴다. `output` 배열 하나에 종목별 행이 담겨 오고, 행마다 종목 코드가 들어 있었다. 입력한 순서대로 온다는 보장은 없고, 있더라도 불안전하니 종목 코드로 행을 찾아 매칭하도록 짰다.

![](/static/images/velog/d788890b-5b4d-401f-9813-f263d3bcedaf-image.png)


폴링 훅은 헤더 훅을 거의 그대로 옮겼다. 둘 다 TanStack Query의 `useQuery`에 `refetchInterval`을 걸어, 장이 열려 있으면 60초마다 다시 받고 닫히면 멈춘다. 한 가지 다른 건 키다한 가지 다른 건 키다. 보고 있는 종목 목록이 키가 되는데, 같은 목록이면 순서가 달라도 같은 키여야 중복 호출이 안 난다. 그래서 종목 코드를 정렬하고 중복을 지운 뒤 합쳐 키로 썼다.

```ts
queryKey: ["multi-quote", [...new Set(tickers)].sort().join(",")];
```

관심종목 탭과 최근조회 탭이 같은 행 컴포넌트를 쓰고 있어서, 행에 실시간을 붙이는 것만으로 두 탭이 같이 살아났다.

## 헤더와 리스트의 데이터 정합

작업을 마치고 화면을 보다 잠깐 헷갈린 게 있다. 헤더(종목 하나를 부르는 단건 호출)와 리스트(여러 종목을 묶어 부르는 멀티 호출)가 같은 종목에서 정확히 같은 값으로 도는가.

기준은 같다. 둘 다 같은 시간대 판정을 쓰고, 같은 60초 간격으로 돌고, 응답을 같은 도메인 모델로 정규화한다. 그래서 같은 종목이면 같은 값이 나온다. 다른 건 갱신되는 순간이다. 헤더 쿼리와 리스트 쿼리는 별개라 타이머가 따로 도니, 두 화면을 같이 띄워두면 호출 시각이 마운트 시점만큼 어긋난다. 헤더가 방금 갱신한 값과 리스트가 1분 전 받은 값이 잠깐 다르게 보일 수 있다는 얘기다. 다음 주기엔 다시 같아진다.

완전히 한 박자로 맞추려면 두 화면이 쿼리 하나를 공유해야 하는데, 헤더는 단건이고 리스트는 멀티라 구조가 달라 합치는 게 과하다. 60초 주기에서 몇십 초 시차는 체감되지도 않아 그냥 뒀다. 값의 기준은 같고 갱신 시각만 독립인 거라, 손댈 문제는 아니라고 봤다.

## 정리

- **토큰 공유 캐시 구현** — #062에서 방향만 잡아둔 걸 실제로 깔았다. collector 발급 스크립트와 12시간 cron, 앱은 Neon 한 행을 읽고 비면 한 번 발급하는 fallback. 만료 시각은 가공 없이 저장하고 버퍼는 읽는 쪽에서 적용하도록 옮겼다
- **등락 표시 공용 컴포넌트** — #061부터 미뤄둔 추출을 세 번째 사용처에서 했다. 부호·단위·크기 세 축만 prop으로 받고 색·포맷은 공유. 추출과 신규 적용을 나눠 회귀를 격리했고, 보합에 `+`가 붙던 문제를 잡았다
- **관심종목 라이브화** — 저장 종가에 멈춰 있던 리스트에 실시간을 얹었다. EOD를 폴백으로 남겨 장 마감·NXT 미지원이어도 칸이 비지 않게 했고, 호출은 30종목 멀티 조회로 묶었다. 관심·최근조회 두 탭이 같은 행을 써서 함께 살아났다

토큰 쪽은 #062에서 그림을 다 그려둬서 옮겨 담는 일에 가까웠다. 무게가 실린 건 리스트였다. 실시간을 어떻게 얹느냐 자체보다, 실시간이 없을 때 뭘 보여줄지를 정하는 쪽이 정작 결정이었다. EOD를 남길지 걷을지가 코드 단순함과 빈 칸 사이의 선택이었고, 결국 헤더와 같은 모델로 맞추는 쪽이 일관됐다.

## 다음 작업

실시간 트랙은 헤더에 이어 리스트까지 닿았다. 남은 건 홈 프리뷰의 라이브화와, 지수 과거 차트를 위한 소스 결정이다.

- **X12** — 지수 과거 OHLCV를 어디서 받을지 정한다. KIS 지수 기간별 차트와 KRX Marketplace 지수 둘을 probe로 찍어 호출량·과거 범위를 비교한다. 지수 차트(E17)의 선행 작업이다
- **E14 / E18 잔여** — 홈의 관심종목 프리뷰는 행 컴포넌트가 아니라 인라인으로 그려져 있어 이번에 라이브화에서 뺐다. 홈 비주얼 정비(E14)와 묶어 같이 손볼지 다음에 정한다
- **F14 / F15** — 세션 경계에서 값이 멈추는 경우와 공휴일 휴장 판정. 실시간 트랙의 잔손질에 해당한다

X12가 자연스러운 다음이다. 지수 차트를 그리려면 과거 시계열부터 어디서 받을지 정해야 하는데, #061에서 후보만 둘로 추려두고 닫지 않은 채 넘어왔다. 이번엔 두 후보를 실제로 찍어보고 닫을 차례다.
