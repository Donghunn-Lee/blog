검색 플로우까지 마무리하면서 다음 갈래로 두 가지가 남아 있었다. AI 공시 요약 같은 차별화 기능으로 넘어갈지, 아니면 운영 측면에서 데이터 갱신 자동화를 먼저 정리할지.

자동화를 먼저 끝내기로 했다. AI 요약은 DART 원문 파싱부터 검증해야 해서 불확실성이 크고, 자동화는 EC2 배포까지 일직선으로 가는 작업이라 한 번에 묶기 좋았다. 자동화가 도는 상태에서 공시 작업을 하는 편이 운영 환경에 더 가깝기도 했다.

이번 작업은 그 자동화의 첫 단계다. EC2 배포는 별도로 미루고, **collector 스크립트들을 매일 돌려도 안전한 형태로** 먼저 정리했다.

결론부터 말하자면, 매우 피곤하고 지겨운 작업이었다.


---

## 매일 돌리려면 뭐가 필요한가

기존 스크립트들은 "한 번 적재"용으로 짜여 있었다. 기본 MVP UI를 구현하기 위해 우선 지속성보다 먼저 데이터 확보를 우선시 했기 때문이다.

데이터를 매일 갱신하려면, 다음 요소들을 확보해야 했다.

- **증분 갱신** — 어제까지 들어온 데이터에 오늘치만 추가
- **멱등성** — 같은 명령을 두 번 돌려도 결과가 같음
- **에러 격리** — 한 종목 실패가 전체 실행을 막지 않음
- **로깅** — cron 환경에서 사후 추적 가능
- **카운트 정확성** — 성공/스킵/실패가 정확히 분류됨

가격 데이터(`fetch_prices.py`)와 재무 데이터(`fetch_financials.py`) 두 스크립트를 각각 위 다섯 가지 기준에 맞췄다.

---

## fetch_prices.py — 단순한 보강

가격 스크립트는 골격이 이미 잘 잡혀 있었다.

`get_last_date(ticker)`로 종목별 마지막 적재일을 가져오고, 거기서부터 어제까지 pykrx로 받아오는 흐름. `daily_prices` 테이블엔 `(ticker, date)` UNIQUE 제약이 있고, INSERT는 ON DUPLICATE KEY UPDATE를 쓰고 있었다. 멱등성은 자연스럽게 보장되는 구조였다.

다만 몇 군데가 어설펐다.

**`end`가 `today`로 잡혀 있어서, 장중에 실행하면 미확정 데이터가 들어갈 수 있었다.**
`today - 1`(어제)로 바꿨다.

**DB 오류는 격리되지 않았다.**
pykrx 호출만 try/except로 감싸 있고, `cursor.executemany()`나 `commit()`은 밖에 노출돼 있어서 한 종목 DB 오류가 전체 루프를 멈추는 구조였다. INSERT 부분도 try/except로 감쌌다.

**카운터에 버그도 있었다.**
`fetch_and_insert()`가 에러 시 0을 반환했는데, 호출 측에선 0을 그냥 skip으로 분류했다. 결과적으로 `error` 카운터는 항상 0이었다. 반환값 규약을 양수=성공, 0=skip, -1=에러로 정리하고 분기를 맞췄다.

**마지막으로 `print()`를 `logging` 모듈로 바꿨다.**
`collector/logs/prices_YYYYMMDD.log`로 파일과 stdout에 동시 출력. 타임스탬프를 포함했다.

검증은 일요일에 돌렸다. 어제(토요일)는 휴장이라 전 종목이 빈 응답으로 skip되는 게 정상 동작이다. DB의 `MAX(date)`가 마지막 거래일인 금요일에 머물러 있는지 확인했다. 의도대로였다.

## fetch_financials.py — 동작은 했지만 5시간

재무 스크립트가 좀 복잡하고, 오래 걸렸다.

현 구조는 DART `fnlttSinglAcntAll` API를 종목별, 분기별로 호출하는 방식이다. 5년치 × 4분기 × 2,660 종목이면 호출량이 훨씬 크다. sleep 0.3초가 누적되면 산술적으로 4시간이 넘어간다.

먼저 핵심은 **이미 적재된 분기를 다시 호출하지 않는 것**이었다.

`run()` 시작 시 `financial_statements` 테이블의 모든 `(ticker, year, quarter, report_type)` 조합을 set으로 한 번 적재해두고, 루프에서 즉시 체크해서 skip한다. 이미 있는 데이터는 DART API를 찌르지 않는다.

```py
existing_keys = get_existing_keys()  # set, run 시작 시 1회

for (year, quarter) in available_reports:
    for ticker in tickers:
        if (ticker, year, quarter, report_type) in existing_keys:
            continue
        data = fetch_financial(...)
        ...
```

여기에 가격 스크립트와 동일한 4가지 보강(에러 격리 / 카운터 / 로깅 / 사용 안 하는 매핑 정리)을 적용했다.

검증을 돌렸다. **107분이 걸렸다.**

증분 skip은 분명 동작하고 있었다. 이미 적재된 37,571건은 DART 호출 없이 즉시 넘어가고 있었다. 그런데 왜 이렇게 오래 걸리는가.

## 47분의 정체 — DART에 영원히 없는 종목들

분포를 다시 봤다.

```
완전 적재 (20개 분기 모두 보유):  1,523개  (57.3%)
부분 적재 (일부 분기 누락):         700개  (26.3%)
미적재 (0건):                       437개  (16.4%)
```

미적재 437개가 문제였다. 이들은 `corp_code`는 있지만 DART에 재무제표를 제출하지 않는 종목이다. 우선주, 일부 ETF 계열, SPAC 같은 케이스. 매 실행마다 DART API를 찔러보지만 항상 None을 받고, 다음 실행에서도 똑같이 None을 받는다.

437개 × 20분기 × 0.3초 = 약 44분이 그대로 낭비되고 있었다.

해결 방향은 두 가지였다.

- 캐시 테이블에 (ticker, year, quarter) 단위로 None 결과를 기록해 두는 방법.
- 다른 하나는 종목 자체에 "재무 공시 대상인지" 플래그를 다는 방법.

후자를 골랐다. 437개는 분기마다 다른 게 아니라 **종목 자체의 속성**이었기 때문이다. 우선주는 작년이든 올해든 우선주고, ETF는 어떤 분기에도 재무제표를 제출하지 않는다. 캐시는 일시적인 결과를 보관하는 자료구조고, 이건 영구적인 분류였다.

`stocks` 테이블에 `is_financial_filer` 컬럼을 추가했다. 마이그레이션 스크립트로 적재 이력 기준으로 초기값을 채웠다. 적재 이력 있으면 1, 없으면 0.

```sql
UPDATE stocks SET is_financial_filer = 1
WHERE EXISTS (SELECT 1 FROM financial_statements WHERE ticker = stocks.ticker);

UPDATE stocks SET is_financial_filer = 0
WHERE corp_code IS NOT NULL
  AND NOT EXISTS (SELECT 1 FROM financial_statements WHERE ticker = stocks.ticker);
```

`get_all_corps()`의 WHERE 절에 `is_financial_filer = 1 OR IS NULL`을 추가했다. 미공시 437개가 호출 대상에서 사라졌다.

신규 IPO 종목 같은 경우는 NULL로 들어와서 일단 호출 대상에 포함되고, 한동안 None만 반환되면 자동으로 0으로 마킹되도록 `mark_non_filer()`를 추가했다.

## 그리고 700개가 사라졌다

수정한 코드를 돌렸다. 4분 54초.

극적이었다. 너무 극적이었다.

확인해보니 `is_financial_filer = 1`이었던 2,223개가 1,523개로 줄어 있었다. 정확히 700개가 0으로 바뀌어 있었다.

부분 적재 종목 수와 완전히 일치했다.

---

## mark_non_filer의 함정

원인은 단순했다.

`mark_non_filer()`는 DART 응답이 None일 때마다 호출되도록 짜여 있었다. 부분 적재 종목들은 어떤 분기는 정상 공시하고 어떤 분기는 공시하지 않는 종목들이다. 호출 루프 중에 미적재 분기에서 None이 한 번이라도 반환되면, 그 ticker가 0으로 덮어씌워졌다.

예를 들어 현대홈쇼핑은 이미 16분기 적재 이력이 있는데, 누락된 4분기 중 하나를 조회하다 None이 오면 `is_financial_filer = 0`으로 마킹되는 식이다. 다음 실행부터는 호출 대상에서 빠진다. 미래에 새 분기를 공시해도 영영 가져오지 못한다.

조건이 잘못돼 있었다. "이 ticker가 None을 받았다"가 아니라 "**이 ticker가 한 번도 정상 공시한 적 없다**"여야 했다.

수정은 단순했다. `existing_keys`에서 ticker만 뽑아낸 `filed_tickers` set을 만들고, 마킹 조건을 강화했다.

```py
filed_tickers = {key[0] for key in existing_keys}  # ticker만

# 호출 루프
if data is None and ticker not in filed_tickers:
    mark_non_filer(ticker)
```

잘못 마킹된 700개는 SQL로 한 번에 복구했다. 적재 이력 있는데 0으로 표시된 행을 1로 되돌렸다.

다시 돌렸다. 47분.

107분에서 60분이 줄었고, 부분 적재 700개는 보존됐다. 47분의 대부분은 부분 적재 종목들의 미적재 분기에서 None을 받는 시간이다. 이건 더 줄이려면 데이터 정합성과 트레이드오프가 따라온다 — 별도재무제표(OFS) 폴백 같은 영역인데, 연결재무제표(CFS)와 의미가 달라 섞이면 비교 일관성이 깨진다. 지금 단계에선 47분으로 충분하다고 봤다. 더 정교한 최적화는 정말 부담이 될 때 다시 보면 된다.

## 돌아보면

이번 작업의 절반은 코드를 고치는 일이었고, 절반은 **데이터를 들여다보는 일**이었다.

107분이라는 숫자만 보고 "캐시 테이블 추가"로 갔으면, 종목 단위 분류로 풀 수 있는 문제를 캐시 자료구조로 풀어버렸을 거다. 부분 적재 700개도 그 캐시에 묻혔을 거고, 신규 분기 공시는 영영 못 가져왔을 거다.

분포 쿼리(완전 적재 / 부분 적재 / 미적재)를 한 번 돌리고서야 437개가 종목 자체의 속성이고 700개는 다른 종류의 문제라는 게 보였다. 그러고도 처음 짠 `mark_non_filer`는 이 두 케이스를 다시 뭉개버렸다. 700개가 정확히 매칭되는 검증 결과를 보고서야 그걸 알았다.

데이터를 신뢰하기 전에 데이터의 모양부터 봐야 한다는, 익숙한 교훈을 한 번 더 거쳤다.

자동화는 이제 코드 측면에선 거의 정리됐다. 남은 건 환경에 올리는 일이다.
