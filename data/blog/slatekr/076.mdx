지난 #075에서 실시간 시세가 실패했을 때 빈 응답이 캐시에 눌러앉는 결함을 잡았다. 그 끝에 다음은 F19 — 실패를 화면에 알리는 작업 — 이라고 했었고, "신호원은 이미 생겼다"고 덧붙였다. 이번에 그걸 이어받았다. 다만 로드맵에 한동안 걸려 있던 항목 하나(F20)를 먼저 털고 넘어갔다.

---

## hydration 불일치, 지금 코드엔 조건이 없다

F20은 종목 헤더 현재가 작업 시 발생했던 문제였다. 당시 캐시 문제가 있어서 간헐적으로 본 것 같은데, 지금은 안 뜬다. [#72](/blog/slatekr/072/)에서 해결하고 나서 지금은 문제가 발생하지 않아서, 지금 코드에 그 어긋날 조건이 남아 있는지부터 봤다.

skeleton을 내는 분기가 뭘 보고 갈리는지 확인했더니, 현재가를 가져오는 client query의 데이터가 아직 없을 때(`undefined`) skeleton을 낸다. 그런데 이 query 결과를 서버에서 클라로 넘겨주는 장치(HydrationBoundary)가 없다. 그러니 서버 렌더도 `undefined`, 클라이언트 첫 렌더도 `undefined` — 둘 다 같은 skeleton을 낸다. 값이 채워지는 건 fetch가 끝난 뒤의 정상 리렌더지, hydration 시점의 트리 재생성이 아니다. 어긋날 조건 자체가 코드에 없는 셈이다.

지금 무해한 게 확인됐으니 손댈 게 없었다. 추측으로 고치는 대신, 조사로 무해함을 확인하고 로드맵에서 항목을 지웠다.

## 실패 신호가 클라이언트까지 도달하지 않는 문제

여기서부터 본 작업이다.

[#075](/blog/slatekr/075/)에서 실패=`null` 신호를 데이터 층에 만들었다. route는 그 신호를 받아 캐시를 지우고(evict), 클라이언트엔 여전히 빈 배열로 응답한다. `null`이 화면까지 새지 않게 계약을 그대로 지킨 거였다. 그 결정은 #075 맥락에선 맞았다 — 실패 신호가 UI로 흘러가면 안 됐으니까.

문제는 이번 작업이 정확히 그 지점에서 막힌다는 거다. 실패를 화면에 알리려면 클라이언트가 "실패라서 빈 것"과 "원래 비어 있는 것"을 갈라야 하는데, route가 둘 다 `bars: []` + 200으로 응답하니 갈라낼 근거가 없다. TanStack Query의 `isError`도 route가 200을 주는 한 안 뜬다. #075에서 계약을 깔끔하게 지킨 게, 이번엔 그대로 걸림돌이 됐다.

정적 데이터 쪽은 예전에 이 구분을 한 번 해둔 적이 있다([#037](/blog/slatekr/037/)). 종목 상세 섹션들이 조회에 실패해도 "데이터 없는 종목"과 같은 화면으로 보이던 걸, catch에서 `hasError`를 세워 error UI로 분기했다. 그땐 실패를 throw로 흘려보내면 섹션이 알아서 잡아줬다. 근데 실시간 쪽은 실패를 일부러 안 흘리도록(200 + 빈 배열 + evict) 설계해둔 참이라, 같은 손을 못 쓴다. 신호를 실어 나를 다른 통로가 필요했다.

## flag 하나 vs 500으로 던지기

선택지는 둘이었다.

| 방식 | 내용 | 비용 |
| --- | --- | --- |
| flag 추가 | 응답 body에 `failed: boolean`을 실어 보냄 | 필드 하나 + 타입 배선 |
| 500 전환 | 실패 시 200 대신 500 응답, `isError`를 태움 | 이미 있는 `isError` 재사용 |

코드만 보면 500이 덜 든다. 이미 있는 `isError`를 그대로 쓰면 되니까. 근데 이건 #075에서 잡은 구조와 정면으로 부딪힌다.

- #075의 evict는 "실패해도 200 + 빈 배열"을 전제로 짜여 있다. 500으로 바꾸면 그 전제부터 흔들린다.
- TanStack Query는 실패를 기본적으로 자동 재시도한다. 500을 주면 방금 evict한 자리를 재시도가 다시 두드린다. 재시도 몰림을 눌러주려던 #075 쪽 판단과도 어긋난다.
- 실시간 시세가 잠깐 안 되는 건 이 서비스에선 예외라기보다 정상 범위 안의 흐름이다. 그걸 HTTP 에러로 올리면 층위가 안 맞는다.

그래서 flag로 갔다. body에 `failed`를 하나 더 실어 route → 훅 → 컴포넌트까지 통과시키고, 컴포넌트가 그 값으로 분기한다. 상태를 enum으로 여러 개 두는 것도 생각했지만, 지금 필요한 건 실패냐 아니냐 둘뿐이라 boolean 하나로 뒀다.

```ts
// 실패: 캐시를 지우고, 빈 배열이되 failed를 표시
revalidateTag(tag, { expire: 0 });
return Response.json({ bars: [], marketOpen, session, date, failed: true });

// 정상 · 정상 empty
return Response.json({ bars, marketOpen, session, date, failed: false });
```

컴포넌트에선 기존에 하나로 뭉쳐 있던 empty 분기를 둘로 갈랐다. `failed`가 켜져 있으면 실패 표시로, 아니면 기존 "데이터 없음"으로. 실패는 항상 빈 배열을 동반하니, 두 분기는 상호 배타로 떨어진다.

## 종목만, 지수는 미룸

신호원은 #075에서 종목·지수 양쪽에 만들어뒀다. 그런데 이번 화면 작업은 종목만 했다. 둘의 빈 화면이 다르게 생겼기 때문이다.

- **종목** intraday가 비면 빈 차트에 "당일 인트라데이 데이터 없음" 문구만 남는다. 실패를 알릴 실익이 크다.
- **지수** intraday가 비면 조용히 일봉으로 대체된다(silent fallback). 실패해도 최소한 일봉은 보이니 아예 빈 화면은 아니다.

지수는 "그래도 뭔가 보이는데 여기 실패 배지를 얹을지, 아니면 fallback을 접고 실패 상태로 전환할지"라는 UX 판단이 먼저 필요하다. 이건 flag를 배선하는 것과 결이 다른 결정이라, 종목부터 끝내고 지수는 F19 잔여로 미뤘다.

## 화면 — 문구와 재시도

표시는 절제된 쪽으로 갔다. 차트가 실패로 비면, empty와 다른 문구를 두고 그 아래 재시도를 붙였다.

- 문구: "실시간 시세를 일시적으로 불러오지 못했어요"
- 다시 시도: 누르면 query를 refetch한다

![](/static/images/velog/b69d7b68-6737-4641-b4d6-676b3cf6135a-image.png)


재시도가 저비용인 건 #075의 evict 덕이다. 실패 응답이 오는 시점에 route가 이미 캐시를 지워놨으니, refetch가 미스를 내고 KIS를 다시 부른다. 복구됐으면 실봉이, 아직이면 다시 `failed`가 온다. 장중이면 폴링이 돌고 있어서, 굳이 안 눌러도 다음 tick에 알아서 풀리기도 한다.

버튼은 공시 섹션의 재시도(테두리 있는 버튼)를 그대로 가져오지 않았다. 공시 재시도는 sky 색이 깔린 패널 안이라 버튼에 색이 붙어도 맞지만, 차트 섹션은 무채색이 기조다. [#037](/blog/slatekr/037/)에서 empty와 error를 색·아이콘 없이 문구로만 가른 것과 같은 결이라, 여기선 흐린 링크 형태로 뒀다. 버튼을 누르면 isFetching동안 아이콘 스핀정도를 추가로 넣었다.

실제 KIS 다운을 재현하긴 어려워서, 검증은 route에서 `failed`를 잠깐 강제로 켜 화면만 확인하고 되돌리는 식으로 했다. 실장애 상황의 실동작은 여전히 코드 경로로만 확인한 셈이다 — 이건 #075에서 남긴 한계와 그대로 겹친다.

## 정리

- **F20(hydration 불일치)** — 조사 결과 지금 코드엔 어긋날 조건이 없어, 고치지 않고 지웠다. skeleton 분기가 client query 데이터의 유무에 걸려 있고 HydrationBoundary가 없어, 서버와 클라 첫 렌더가 같은 결과를 낸다.
- **실패 신호 계약 확장** — route에서 빈 배열로 뭉개지던 실패를, 응답에 `failed` flag를 더해 화면까지 끌어왔다.
- **flag vs 500** — 500 대신 flag를 고른 건 #075의 evict 구조와 재시도 정책에 어긋나지 않게 하기 위해서다.
- **종목 차트 표시** — 실패 문구와 재시도를 붙였다. 지수는 fallback UX 판단이 남아 미뤘다.

#075가 서버 쪽에서 실패한 빈 값을 지웠다면, 이번엔 그 실패를 사용자에게 보이게 만든 세션이다. 두 세션이 "실시간이 잠깐 안 될 때 무슨 일이 일어나야 하는가"를 앞뒤로 채운 셈이다. 신호를 만드는 것과 그 신호가 화면까지 닿는 건 별개였고, 이번 판단의 대부분은 계약을 다시 여는 데 들어갔다.
