#70에서 차트에 intra_day를 업데이트한 뒤로 로컬 서버가 다운되는 문제가 발생했다. 당장 로컬 서버를 확인할 수 없으니 최우선으로 해결해야 할 문제였다. 

그런데 코드를 손대기 전에 먼저 정리할 게 있었다. 이 문제가 배포 환경까지 번지는 건지 개발 서버에만 있는 건지, 그리고 최근에 늘어난 폴링 구조를 아예 바꿔야 하는 건지.

이번 세션은 그 두 질문에 답을 내고, 답이 나온 만큼만 손을 대는 자리였다. 결론부터 적으면 배포는 문제없고 폴링도 그대로 둔다. 대신 확인하는 과정에서 메모리 문제의 성격이 처음 짐작과 좀 달랐다.

---

## 배포 환경 체크

#071에서 크래시 원인 후보로 모듈 스코프 Map이 쌓이는 문제가 있었다. 티커별 캐시 함수가 계속 쌓여서 GC 대상에서 빠지고 있을 가능성이 있었다.

코드를 열어보니 그 Map의 키는 조회된 티커였다. 상장 종목이 2500개 남짓이니 아무리 쌓여도 그 선에서 멈춘다. 값도 작은 함수 하나라 다 합쳐도 큰 메모리가 아니다. 12GB를 이걸로 채우는 건 산술이 안 맞았고, 후보에서 뺐다.

폴링도 같이 봤는데 이미 꽤 조여져 있었다.

- 폴링은 전부 60초 간격이고, 장이 닫히면 멈춘다
- 차트는 헤더가 이미 받는 값을 공유해서 따로 안 부른다
- 관심종목은 티커가 몇 개든 한 번의 배치 호출로 묶인다

WebSocket으로 갈아타는 건 실시간 트랙을 시작할 때(#060) 이미 접었던 선택지고, 지금 구조를 보면 다시 꺼낼 이유가 없었다. 현재가 갱신이 가져다주는 이점이 커서 폴링은 유지하기로 했다.

## index-quotes에만 캐시

배포 쪽에서 실제로 손볼 건 캐시 하나였다. 현재가 API 몇 개에 서버 캐시가 없어서, 접속자가 늘면 KIS 호출이 그만큼 는다. #071에 적어둔 F17이다.

원래는 두 API에 다 붙이려 했는데, 호출 구조를 실제로 세어보니 셋의 효과가 갈렸다.

| API | 캐시 | 이유 |
|---|---|---|
| index-quotes | 붙임 | 모든 유저가 같은 지수 3개를 본다. 유저 수만큼 늘던 호출이 인스턴스당 상수로 |
| stock-quote | 보류 | 티커별이라 같은 종목에 몰릴 때만 효과. 지금 규모엔 미미해서 필요할 때 |
| multi-quote | 제외 | 관심종목 조합이 유저마다 달라 캐시 키가 매번 바뀐다. 붙여도 거의 안 맞는다 |

multi-quote는 좀 함정이었다. 캐시 없는 목록에 들어 있어 당연히 붙일 대상 같았는데, 키가 티커 조합이라 사람마다 관심종목이 다르면 매번 새 키가 된다. 히트가 거의 안 나는데 배치 호출만 티커별로 쪼개지는 꼴이라 오히려 손해다.

그래서 index-quotes 한 곳에만 붙였다. 마침 지수 분봉 쪽에 같은 패턴(`unstable_cache`를 지수별 키로)이 이미 있어 그대로 옮겨왔다.

```ts
const getIndexQuote = (code: string) =>
  unstable_cache(() => fetchIndexQuote(code), ["index-quote", code], {
    revalidate: 60,
  })();
```

지수 코드를 키에 넣는 게 핵심이다. 안 넣으면 세 지수가 같은 캐시 칸을 공유해 전부 같은 값을 반환한다. 실패해서 `null`이 와도 그대로 60초 캐시하는데, 이건 KIS가 흔들릴 때 재시도가 몰리는 걸 막는 쪽이라 의도한 동작이다.

`unstable_cache`는 Next 16에서 legacy 딱지가 붙었지만 아직 동작한다. 후속인 `use cache`로 가려면 플래그를 켜고 구조를 바꿔야 해서 별도 트랙(F7)으로 미뤄뒀다. 게다가 인스턴스 간 캐시 공유는 오히려 `unstable_cache` 쪽이 되니, 지금 목적(KIS 호출 줄이기)엔 이게 맞았다.

## 메모리 실측, 로그와 스냅샷

원인을 짐작만 하고 고치면 #071의 후보 목록처럼 또 추측이 될 것 같았다. 그래서 수치를 먼저 떴다.

개발 서버에 로거를 하나 붙였다. 5초마다 `process.memoryUsage()`를 찍어 heapUsed·rss·external을 로그로 남기게 했다. 그리고 힙 스냅샷을 두 장 떴다. 켜고 30초 뒤 한 장, 힙이 3GB쯤 올랐을 때 한 장.

스냅샷 비교부터 봤는데 두 장 차이가 수백 바이트였다. 3GB가 늘었는데 스냅샷엔 안 잡힌다. 뭔가 어긋난 것 같아 로그 곡선을 봤다.

```
heapUsed=4192 rss=5931 external=4.3
heapUsed=2785 rss=4684 external=3.8   # GC 후
```

heapUsed가 오르다가 GC가 돌면 절반 가까이 빠졌다. 4192에서 2785로, 그 앞에도 3433에서 1672로. 회수되는 메모리라는 뜻이다. 안 풀리고 쌓이는 메모리였으면 GC 뒤에도 안 내려갔을 거다. 스냅샷 두 장이 비슷했던 것도 이래서였다. 스냅샷을 뜨는 순간 GC가 도니, 두 장 다 회수 직후의 바닥이었다.

그럼 늘어난 3GB는 뭐였나. external이 계속 몇 MB로 평평했으니 네트워크 버퍼 같은 건 아니고, **순간적으로 할당됐다 회수되는 임시 객체**였다. 개발 모드에선 캐시가 안 도니까 폴링이 한 바퀴 돌 때마다 route가 통째로 다시 실행된다. 거기서 쏟아지는 **임시 객체의 할당 속도가 GC 회수 속도를 앞지르면, 톱니 모양으로 바닥이 조금씩 올라가다 결국 12GB 한계를 넘어 크래시가 난다**.

HMR도 의심했었는데, 파일을 저장하지 않고 페이지만 이리저리 눌러도 바닥이 올라갔다. 저장할 때 튀는 게 아니라 폴링만으로 오르는 거라 HMR은 주범이 아니었다.

정리하면 이건 새는 메모리(leak)가 아니라 할당 압박이다. 스냅샷으로 범인 객체를 못 찾는 게 당연했다. 사실 스냅샷으로 잡겠다고 시작했는데 답은 로그 곡선에 있었으니, 도구를 처음에 잘못 고른 셈이다.

### 배포 환경에선 문제 없는 이유

이 크래시가 나려면 두 가지가 겹쳐야 한다. 캐시가 안 돌아 매번 route를 다시 실행하는 것과, 한 프로세스를 오래 켜두는 것. 배포 환경은 둘 다 성립하지 않는다. 프로덕션에선 캐시가 실제로 돌아 재실행이 줄고, Vercel의 서버리스 인스턴스는 수명이 짧아 톱니가 12GB까지 쌓일 시간 자체가 없다. 개발 서버 특유의 오버헤드도 없다.

그래서 근본 수정은 하지 않기로 했다. 배포에 나가지 않는 로컬 편의 문제라 들이는 품에 비해 얻는 게 적다. 개발 중엔 힙 상한을 올려두는 선에서 버티고, 확인이 필요하면 프로덕션 빌드로 돌려 곡선이 평평한지 보면 된다.

## 정리

배포가 정상인지 확인하고, 그 김에 메모리 문제의 성격까지 재본 세션이었다.

- **배포 점검** — 크래시는 개발 서버 전용. 폴링은 이미 조여져 있어 그대로 유지
- **index-quotes 캐시** — 전 유저가 공유하는 지수 호출만 상수화. stock-quote는 보류, multi-quote는 키가 안 맞아 제외
- **메모리 실측** — 새는 게 아니라 할당 압박. GC가 회수하는 걸 곡선으로 확인하고, 근본 수정 대신 band-aid로

수치를 떠보길 잘했다. 안 그랬으면 #071에 적어둔 Map을 붙들고 엉뚱한 데를 고쳤을 거다. 스냅샷이 헛다리였던 것도 결국 어떤 도구가 이 문제를 보여주는지 알게 된 셈이라 나쁘진 않았다.
