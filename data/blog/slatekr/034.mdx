#033까지 재무 데이터 정확성 작업이 마무리됐다. 계정과목 교체, OFS 폴백, non_filer 복구까지 끝났고, 이번 작업은 크게 두 갈래다. 하나는 GitHub Actions 스케줄 조정, 다른 하나는 재무 테이블에 비어 있던 PER/PBR을 채우는 것.

그 사이에 몇 가지 확인 작업을 끼웠다.

---

## 단분기 적재 구조 확인

#025에서 발견했던 이슈 — DB의 분기 데이터가 단분기(해당 분기만)인지 누적인지를 먼저 확인했다.

삼성전자 2024년 기준으로 조회하면 Q1 71.9조, Q2 74.1조, Q3 79.1조. 세 개를 합치면 약 225조이고, annual은 300.9조다. 누적이었으면 Q3이 225조여야 하니까 단분기가 맞다.

Q4 단분기 row는 별도로 없고, `report_type = 'annual'`에 `quarter = 4`로 연간 합계가 들어가 있다. Q4 단분기가 필요하면 annual - (Q1+Q2+Q3)으로 계산해야 하는 구조. 의도대로 적재되고 있어서 별다른 수정 없이 패스했다.

## 이미 적재된 12년치 일봉 데이터

과거 PER/PBR을 계산하려면 과거 종가가 필요하다. 그동안 종목 상세 페이지의 차트가 1년치만 제공하도록 해둬서, 언제부턴가 daily_prices에 1년치가 들어 있을 거라고 생각하고 확장 작업을 계획했는데, 실제로 확인해보니 이미 꽤 많은 양의 데이터가 적재되어있었다.

```
daily_prices row 수: 6,177,061
날짜 범위: 2007-06-05 ~ 2026-05-18
종목당 평균 row 수: 2,319 (≈ 9.2년)
```

#029에서 614만 row를 Neon으로 이관했을 때 전체를 옮긴 거였는데, 그게 몇 년치인지는 당시 확인을 안 했다. 1년치라고 생각했던 건 차트 컴포넌트에서 `getDailyPrices(ticker, 365)` — LIMIT 365로 최근 365개만 가져오고 있었기 때문이다. 거래일 기준 365개면 약 1.5년치인데, 헤더에 "최근 1년"이라고 하드코딩되어 있으니 그렇게 인식하고 있었던 듯하다.

연도별 분포를 보면 2007~2013년은 종목 1~2개뿐이고, 2014년부터 1,585개 종목으로 급증한다. 실질적으로 2014년부터 12년치. 재무 데이터가 5년치이니 과거 PER/PBR 계산에 충분하고, 일봉 확장 작업은 필요 없었다.

## 당일 종가 미수집

스케줄 조정을 하려다가, fetch_prices.py 코드를 보는 과정에서 end 날짜 설정이 눈에 들어왔다.

```python
end = (datetime.today() - timedelta(days=1)).strftime("%Y%m%d")
```

cron이 KST 16:00(장 마감 30분 후)에 실행되는데, end가 어제로 고정되어 있었다. 오늘 장이 끝났는데 오늘 종가를 안 가져오는 셈이다. DB의 `max(date)`가 항상 이틀 전인 것과 일치한다. `today()`로 바꿨다.

그리고 pykrx의 내부 이슈로 OHLCV데이터 이외에는 모두 오류가 난다는 것을 개발 초반부터 인지하고 있었는데, 오늘 확인 중에 실시간 종가 데이터는 제공한다는 것을 확인할 수 있었다. 지금 당장은 MVP+지만, 추후 화면에 보여지는 종목에 한해 실시간 종가를 30초 또는 1분 간격으로 갱신하는 것을 추후 고려할 이슈로 로드맵에 매모했다.

## GitHub Actions 프리티어 스케줄

#031에서 `--periods 2`, sleep 축소 등으로 실행 시간을 줄였지만, 프리티어 월 2,000분 문제는 근본적으로 해결되지 않은 상태였다.

최근 workflow 실행 기록을 보면:

- 갱신 데이터 있는 날: prices ~63분 + financials ~52분 = ~115분
- 갱신 데이터 없는 날(비거래일): ~46분
- weekly (stocks + shares): ~80분

거래일 기준으로 daily 115분 × 22일 = 2,530분. 여기에 비거래일과 weekly를 더하면 한참 초과한다.

핵심은 financials가 daily에 있을 이유가 없다는 점이었다. 재무제표는 분기 실적 발표 시점(3, 5, 8, 11월)에만 새 데이터가 생긴다. #031에서 `--periods 2`로 줄인 것도 "최근 2개 period만 순회한다"는 건데, 그 2개 period도 실적 발표 시즌이 아니면 매일 빈 순회를 하는 거다.

financials를 weekly로 옮기고, period도 1로 줄였다. 정정공시가 직전 분기에 대해 나오더라도, weekly 주기면 최대 1주일 지연이고 upsert가 자동으로 덮어쓴다. 2분기 전 정정은 현실적으로 발생 사례를 찾기 어렵다.

변경 후 예상:
- daily (prices만): 63분 × 22일 ≈ 1,386분
- weekly (stocks + shares + financials): (80 + 26)분 × 4회 ≈ 424분
- 합계: ~1,810분 — 여유 있게 2,000분 이내

## 과거 PER/PBR 계산

#025에서 재무 슬레이트의 12개 지표를 정할 때, PER과 PBR은 `per: null, pbr: null`로 비워뒀었다. 종가 데이터와의 매칭이 필요해서 당시엔 넘긴 건데, 일봉이 12년치나 있으니 이제 채울 수 있다.

계산 자체는 단순하다. 각 재무 기간의 마지막 거래일 종가를 daily_prices에서 가져와서 EPS/BPS로 나누면 된다. 연간이면 12월 마지막 거래일 종가, 분기면 해당 분기 말 종가.

lib/financials.ts에 `fetchClosePricesByQuarter` 함수를 추가했다. `DISTINCT ON`으로 종목의 전체 연도-분기별 마지막 종가를 단일 쿼리로 가져온다. 기존 재무제표 쿼리와 `Promise.all`로 병렬 실행하니까 응답 시간 증가는 거의 없다.

normalizer(`rowToFinancialPeriod`)에 close 파라미터를 추가해서, EPS > 0이고 종가가 있으면 PER을, BPS > 0이고 종가가 있으면 PBR을 계산한다. 음수 EPS일 때 PER은 null — 관례상 음수 PER은 표시하지 않는다.

Q4(합성 분기)의 종가는 해당 연도 마지막 거래일 종가를 사용한다. annual 데이터와 같은 시점이다.

## 네이버 증권과의 산식 차이

결과를 확인하면서 네이버 증권 수치와 대조해봤다. 대체로 값이 나오긴 하는데, 일부 종목에서 꽤 차이가 있었다.

예를 들어 현대차 2024년 — 네이버 PER 15.26, 우리 4.45. 같은 종목 같은 연도인데 3배 넘게 차이난다.

원인은 EPS 산출 기준의 차이로 보인다. 우리는 지배주주 귀속 순이익을 발행주식수로 나눈 EPS를 쓰는데, 네이버는 가중평균 주식수를 쓸 수도 있고, 우선주가 있는 종목에서 보통주만 기준으로 계산할 수도 있다. 로드맵에 B6(재무 표시 양식 기준 결정)과 X2(네이버 증권 산식 조사)가 이미 있어서, 전체 지표의 산식을 한 번에 맞추는 작업은 그쪽에서 처리할 예정이다.

지금은 "과거 PER/PBR 계산 로직이 들어갔고, 종가 매칭까지 동작한다"는 데 의미를 두고 넘어갔다.

## 정리

이번 작업은 새로운 기능을 추가했다기보다는, 기존에 미뤄뒀던 것들을 하나씩 정리한 세션이었다. 단분기 구조 확인, 일봉 데이터 현황 파악, 당일 종가 미수집 수정, 프리티어 스케줄 최적화, PER/PBR 빈 칸 채우기.

이런 류의 작업은 하나하나는 작지만, 안 하면 계속 쌓인다. Phase 1(배포 + 인프라)이 끝나고 Phase 2(핵심 품질)로 넘어가는 시점이라, 지금 정리하는 게 맞는 타이밍이었다.

다음은 B6/X2 — 네이버 증권 산식 조사와 재무 표시 양식 기준 결정. PER/PBR뿐 아니라 EPS/BPS/ROE 등 전체 지표를 한 번에 맞추는 작업이 될 것 같다.
