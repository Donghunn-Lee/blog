#103에서 넷으로 가른 모바일 반응형의 2차다. Nav 구조와 검색 UX는 서로 물려 있어 한 세션에서 같이 보기로 했었다 — 메뉴를 어디에 두느냐가 검색창이 설 자리를 좌우해서다. 그래서 이번엔 코드보다 결정이 먼저였다. Nav 방식을 정하고, 그 위에서 검색 진입점을 하나로 모으고, 마지막으로 iOS 입력 확대 문제를 닫았다. 지난 두 세션에 비하면 가벼운 회차다.

---

## 하단 탭바 결정

모바일 상단은 로고 옆에 텍스트 링크 둘(시장 순위·관심종목)과 GitHub 링크가 시각 구분 없이 붙어 있는 상태였다. 실측 때부터 정리 대상이었고, 후보는 셋이었다.

| 방식 | 목적지 접근 | 화면 점유 | GitHub·테마 토글 |
| --- | --- | --- | --- |
| 사이드바 drawer | 2탭 | 열릴 때만 | 수납 가능 |
| 트리거식 하단 시트 | 2탭 | 열릴 때만 | 수납 가능 |
| 상시 하단 탭바 | 1탭 | 상시 ~56px | 수납 불가 |

상단 사이드바보다는 엄지가 닿는 하단 쪽이 끌렸고, 하단 두 안 중에선 탭바로 기울었다. 근거는 목적지 수다. 홈·순위·관심·지수 — 넷. 탭바에 정확히 맞는 수이고, 조회 서비스 특성상 이 네 화면을 오가는 게 사용의 거의 전부라 매 이동이 1탭인 가치가 상시 56px보다 크다고 봤다. 검색을 다섯 번째 탭으로 넣는 안도 잠깐 있었는데, 검색은 어차피 상단에 상시로 세울 계획이라 중복이었다.

탭바가 수납하지 못하는 둘 중 GitHub 링크는 Footer로 내렸고, 테마 토글은 상단에 남겼다. 모바일 상단은 로고·검색·토글 셋으로 정리된다.

노출 기준은 md(768) 미만이다. 화면 폭만 보면 sm(640)이 자연스러운데, Navbar의 기존 반응형 분기가 전부 md 축이라 sm으로 세우면 640~768 구간에 상단 링크와 탭바가 공존하는 이중 nav 층이 생긴다. 활성 판정은 pathname 기준으로 홈만 정확 일치, 나머지는 startsWith. 종목 상세나 /search처럼 탭에 없는 라우트에선 넷 다 비활성으로 둔다 — 억지로 가까운 탭을 켜는 것보다 정직하다.

## viewport meta가 없었다

탭바 하단을 홈 인디케이터에서 띄우려면 safe-area inset이 필요하다. probe에서 걸린 게 여기다 — 프로젝트에 viewport 설정 자체가 없었다. `env(safe-area-inset-*)`는 `viewport-fit=cover`가 선언돼 있어야 값을 주고, 없으면 0이다. #057에서 ScrollToTopButton에 `bottom-[max(1rem, env(safe-area-inset-bottom))]`을 써뒀는데, 엄밀히 말하면 그동안 이 식은 그냥 1rem이었던 거다.

```ts
export const viewport: Viewport = {
  width: "device-width",
  initialScale: 1,
  viewportFit: "cover",
};
```

layout에 viewport export를 신설했고, 탭바의 safe-area 흡수·본문 하단 패딩·버튼 offset이 전부 이 선언 위에서 계산된다.

## 검색 진입점 셋을 하나로

검색창은 세 곳에 있었다. #095에서 만든 데스크톱 미니 검색, #096에서 붙인 모바일 토글, 그리고 /search 결과 페이지 자체의 검색창. 셋 다 같은 SearchInput을 쓰지만 상태는 각자 로컬이라, 검색해서 결과 페이지에 도착하면 방금 친 검색어가 상단 검색창에선 사라져 있는 식이었다.

- **모바일 토글 → 상시 input.** 상단 링크가 탭바로 내려가며 비운 자리를 검색이 채운다. 토글은 탭 한 번의 비용을 감수하고 공간을 아끼는 장치였는데, 상시로 세울 폭이 생긴 이상 유지할 이유가 없다. #096에서 만든 지 열흘 만의 은퇴다.
- **/search 페이지 검색창 제거 — PC 포함.** 상단에 항상 있으니 페이지 안의 검색창은 이중이다. 이 검색창을 감싸던 SearchBarWithState는 #014에서 "Server Component인 /search에 controlled 입력을 심기 위해" 만든 래퍼였는데, 검색창이 Navbar 하나로 수렴하면서 존재 이유가 같이 사라졌다. 이 래퍼만 쓰던 showButton·showPreview prop도 함께 걷었다.
- **잔존 로고.** 검색창을 들어내고 띄워보니 페이지 상단에 SlateKR 로고만 남아 Navbar 로고와 위아래로 겹쳤다. 검색창과 한 세트로 설계된 헤더였던 거라, 컴포넌트째 삭제했다.

상시가 된 검색창에는 돋보기 아이콘 submit 버튼을 input 안쪽에 넣었다. 지금까지는 Enter로만 실행됐는데, 모바일에서 그걸 기대하긴 어렵다.

## 검색어 유지는 URL로

/search의 검색어 소스는 #014부터 URL `?q=`였다. 이번에 정할 건 Navbar 검색창이 그 값을 어떻게 이어받느냐였는데, 전역 store를 세우는 안은 금방 접었다. 검색창이 하나뿐이면 동기화할 지점도 하나다. pathname이 /search일 때만 URL q를 값으로 채택하고, 다른 라우트에선 로컬 상태를 그대로 둔다.

구현에서 하나 걸린 건 useSearchParams다. 클라이언트 컴포넌트가 이 훅을 쓰면 정적 렌더에서 CSR bailout이 일어나 Suspense 경계로 감싸야 한다. Navbar는 전 페이지 layout에 있으니, fallback을 input과 같은 치수로 맞춰 레이아웃 점프만 막았다.

잡고 보니 하나 더 있었다. 검색을 실행해도 input focus가 안 풀린다 — MPA라면 페이지 전환으로 자연히 사라졌을 focus가, 클라이언트 내비게이션에선 Navbar가 언마운트되지 않아 그대로 남는다. 모바일에선 키보드가 계속 떠서 방금 요청한 결과의 절반 가까이를 가린다. 이동 직전 blur 한 줄로 닫았다.

## iOS 입력 자동 확대

#103 실측 목록에 "검색하면 화면이 확대되고 안 풀린다"로 적힌 항목이 있었다. 조사해 보니 "안 풀리는" 게 별개 문제가 아니라 iOS auto-zoom의 원래 동작이다 — 16px 미만 input에 focus가 가면 확대하고, 스스로 복귀하지 않는다. 세어 보니 16px 미만 input이 검색·공시 필터·차트 봉 개수 입력까지 여덟 곳이었고, 이를 막는 maximum-scale 선언은 없었다. 조건이 전부 갖춰져 있던 셈이다.

| 안 | 해결 범위 | 대가 |
| --- | --- | --- |
| viewport에 maximum-scale=1 정적 선언 | 8곳 전부 | Android까지 핀치 줌 차단 |
| input 폰트를 16px 이상으로 | 개별 | 공시 필터 11px 등 밀도 회귀, 6곳 잔존 |
| iOS에서만 런타임 주입 | 8곳 전부 | UA 스니핑, 주입 타이밍 |

갈림길은 iOS의 예외 동작이다. iOS는 접근성 이유로 maximum-scale을 사용자 핀치에 한해 무시한다. 즉 이 선언은 iOS에서 auto-zoom만 막고 핀치 줌은 살려두는데, Android는 스펙대로 핀치까지 막는다. 그래서 선언이 iOS에서만 존재하게 만드는 세 번째 안으로 갔다 — 마운트 시 iOS를 판별해 viewport meta에 maximum-scale=1을 덧붙이는 방식이다.

```ts
const isIos =
  /iPad|iPhone|iPod/.test(navigator.userAgent) ||
  (navigator.platform === "MacIntel" && navigator.maxTouchPoints > 1);
```

뒤쪽 조건은 iPadOS 13+가 데스크톱 UA로 위장하는 경우다. navigator.platform은 deprecated지만 Safari에서 이 판별의 대안이 없어, 사유를 주석으로 남기고 썼다.

검증에선 소동이 좀 있었다. 실기기에서 처음엔 여전히 확대가 됐는데, 다시 해 보니 안 됐다. 고친 게 없는데 증상이 사라지는 건 고쳤는데 안 낫는 것만큼 찜찜해서 짚고 넘어갔다 — 주입이 useEffect라 하이드레이션 뒤에 실행되는데, dev 첫 로드는 컴파일까지 겹쳐 이 창이 꽤 길다. 그 사이에 input을 터치하면 주입 전이라 확대가 난다. 두 관측이 이 타이밍 하나로 설명됐다. 프로덕션은 창이 훨씬 짧아 일단 그대로 두고, 배포 후에도 재현되면 하이드레이션을 기다리지 않는 inline script로 바꾸는 카드를 남겨뒀다.

## 정리

- **Nav** — 상시 하단 탭바(4탭·md 미만·safe-area 흡수), GitHub는 Footer로, viewport export 신설
- **검색** — 진입점 3→1. 모바일 토글 폐기·상시화, /search 검색창과 SearchBarWithState 제거, 아이콘 submit, URL q 동기화, submit 시 blur
- **iOS** — 입력 auto-zoom을 iOS 한정 maximum-scale 주입으로 억제. 콜드 로드 타이밍은 프로덕션 관측으로 이관

#095에서 헤더에 검색을 올리며 "모바일은 일단 숨겼다"고 했던 게 세 세션을 돌아 상시가 됐고, 그 사이를 메우던 토글은 자리를 내줬다. 구조가 정리되는 과정에서 중간 형태가 생겼다 사라지는 건 자연스러운 흐름이라는 생각이다. 결정을 먼저 닫고 들어간 덕에 구현 자체는 이번 시리즈에서 제일 수월했다.
