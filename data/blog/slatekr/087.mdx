프로젝트가 드디어 마무리 단계에 들어서면서, 화면을 훑기 전에 코드·데이터 안정성 쪽을 먼저 정리하기로 했다. [#086](/blog/slatekr/086/)에서 corp_code 적재를 복구하고, 그 흐름으로 이번엔 테스트를 깔았다. 로드맵 **G3** — 원래 마지막 포트폴리오 트랙에 넣어둔 항목인데, 지금 당겨왔다.

당긴 이유는 `classifyDisclosure`다. [#083](/blog/slatekr/083/)에서 이 함수가 제출인·제목 2축에 절차 키워드 열넷까지 얹히면서 제법 복잡해졌다. 앞으로도 관리종목 같은 규칙이 더 붙을 수도 있는데, 규칙 하나 고칠 때마다 기존 분류가 안 깨졌는지 손으로 확인할 수는 없다. 회귀 안전망을 깔 값이 그만큼 올라간 거다.

대상은 순수함수로 한정했다. async Server Component은 Vitest가 렌더를 지원하지 않아 E2E 영역인데, 지금 E2E까지 벌일 단계는 아니다. DB나 네트워크를 타지 않는, 입력과 출력만 있는 함수들만 골랐다.

## Jest가 아니라 Vitest

테스트 러너로 뭘 쓸지가 첫 갈림이었다. 사실상 Jest와 Vitest 둘인데, "Vitest가 빠르다"는 흔한 이유는 이번엔 근거가 안 됐다. 대상이 순수함수 몇십 개라 전건을 돌려도 1초가 안 걸린다. 속도로는 둘이 구분이 안 된다.

실제로 갈린 건 설정 비용이었다. 이 프로젝트 tsconfig는 `moduleResolution: "bundler"`에 `@/*` 경로 alias를 쓴다. 번들러를 전제한 설정이다.

- **Vitest** — Vite 기반이라 플러그인 하나로 tsconfig를 그대로 상속한다. alias도 resolution도 다시 안 적는다.
- **Jest** — `moduleNameMapper`로 `@/*`를 수동으로 다시 매핑하고, `bundler` resolution과 ts-jest 사이의 궁합도 따로 맞춰야 한다. 설정 표면이 확실히 넓다.

```ts
// vite-tsconfig-paths 하나로 @/ alias와 resolution을 tsconfig에서 그대로 물려받는다
plugins: [tsconfigPaths()]
```

Jest에도 우위가 하나 있긴 하다. Next.js에 깊이 물린 걸 테스트할 땐 `next/jest` 공식 프리셋이 편하다. 근데 이번 대상은 Next와 무관한 순수함수라, 그 이점이 발현될 자리가 없다. 그리고 async SC를 테스트 못 하는 건 Jest도 마찬가지다 — 러너 차이가 아니라 React 생태계의 한계라 선택 근거가 못 된다.

정리하면 속도가 아니라 **설정 경제성**이 이 프로젝트에서 유효한 유일한 근거였다. bundler tsconfig와 alias를 재선언 없이 물려받고, Jest의 유일한 우위(`next/jest`)는 순수함수 대상이라 무효화된다. 면접에서 "왜 Vitest냐"를 받으면 "빨라서"가 아니라 이 프레이밍으로 답할 생각이다.

## 테스트 대상

도구보다 중요한 건 무엇을 테스트할지였다. probe로 순수함수를 훑으니 스무 개 넘게 나왔는데, 전부 같은 값은 아니었다.

기준은 하나로 잡았다. **로직이 복잡하고, 틀렸을 때 조용히 번지는 것.** 이 두 조건에 걸리는 함수가 우선이다.

| # | 성격 | 예 | 처리 |
|---|---|---|---|
| 1 | 복잡 + 조용히 번짐 | classifyDisclosure, computeTtmEps, 호가단위, 리샘플 | 테스트 |
| 2 | 단순 + 즉시 표면화 | format 계열, 룩업 | 제외 |

format 함수는 틀려도 화면에서 바로 티가 나고 로직도 단순하다. 여기에 테스트를 붙이면 커버리지 숫자는 오르지만 실익이 없다. 오히려 "커버리지 채우려고 아무 데나 테스트했다"는 신호가 된다. 그래서 2번은 의도적으로 뺐다.

같은 이유로 커버리지 100%도 쫓지 않았다. `computeTtmEps`에서 두 줄이 안 잡혔는데, 둘 다 `if (합 === null) return` 같은 방어 코드다. 앞선 가드가 이미 null을 걸러낸 뒤라 구조적으로 도달할 수 없는 줄이다. 이걸 커버하려면 방어를 지우거나 불가능한 입력을 억지로 만들어야 하는데, 숫자를 위해 그럴 이유가 없다. 실제로 도달 가능한 경로는 전부 100%다.

여기서 테스트가 필요한 이유가 정리됐다. 처음엔 혼자 하는 프로젝트에 테스트가 과한가 싶었는데, 테스트가 지키는 건 작성하는 지금이 아니라 나중이다. 지금 맞는지는 화면 몇 번 보면 안다. 정작 값은 반년 뒤 규칙을 고치다 기존 분류를 깼을 때, 그걸 손이 아니라 `npm test`가 잡아주는 데 있다. 혼자라도 시간이 지나면 과거의 나는 사실상 남이라, 같은 문제가 축소판으로 생긴다.

## classifyDisclosure — 픽스처를 커밋하다

먼저 작업한 건 `classifyDisclosure`다. #083에서 쓴 3개월치 공시 데이터가 픽스처로 바로 쓸 만했다.

문제가 하나 있었다. 그 데이터는 `tmp/` 아래에 있고 gitignore 대상이라, 언젠가 사라진다. 여기에 직접 의존하면 다른 데서 클론했을 때 테스트가 깨진다. 그래서 raw 데이터는 픽스처 케이스를 **고르는 소스로만** 쓰고, 실제 테스트가 참조하는 값은 커밋되는 파일에 박았다.

케이스는 두 종류로 나눴다.

- **라벨 확정 케이스 12건** — 각 분기 경로마다 입력과 기대 출력을 명시했다. 거래소 발신 + 절차 키워드 → `null`, 회사 발신 + 각 카테고리 매칭 등. 특히 `단일판매ㆍ공급계약`(ㆍ 있음, 회사 발신 → MAJOR_EVENT)과 `단일판매공급계약`(ㆍ 없음, 거래소 발신 → null)처럼 한 글자로 갈리는 경계를 고정했다.
- **불변식 표본 176건** — 거래소 발신 공시를 라벨 없이 넣고, 결과가 `MARKET_ACTION` 아니면 `null`만 나오는지, 회사용 카테고리는 절대 안 나오는지 검증했다. 거래소 발신 경로는 구조상 회사 키워드를 안 타니, 이게 깨지면 게이팅이 무너졌다는 뜻이다.

두 번째가 "3개월치 데이터를 활용한다"의 정직한 형태였다. 1,000건에 일일이 정답 라벨을 달 순 없으니, 라벨 대신 **구조 불변식**으로 전건을 회귀 가드에 넣은 거다.

## computeTtmEps — now를 주입하다

두 번째는 `computeTtmEps`다. [#068](/blog/slatekr/068/)에서 PER을 TTM으로 바꾸며 만든, 최근 4분기 EPS를 굴려 합산하는 함수다. 5개 케이스로 갈리고 연환산 계산까지 있어 위의 1번에서 가장 복잡한 축이다.

여기엔 설정만으로 안 끝나는 지점이 있었다. 연환산 케이스가 `Date.now()`를 직접 불러서, **"오늘이 며칠이냐"에 따라 결과가 바뀐다.** 상장 후 14개월이 임계인데, 시간을 고정하지 않으면 지금 통과한 테스트가 나중에 임계를 넘기며 실패한다. 재현이 안 되는 테스트는 없느니만 못하다.

두 갈래 선택지가 있었다.

- **A. 시계를 모킹** — `vi.useFakeTimers`로 `Date.now()`를 고정. 소스는 안 건드린다.
- **B. now를 인자로 주입** — 함수가 시각을 인자로 받게 바꾼다.

B로 갔다. `market.ts`의 세션 판정 함수들이 이미 `now?: Date`를 받는 패턴을 쓰고 있는데, 이 함수만 내부에서 `Date.now()`를 부르던 게 오히려 예외였다. probe로 호출처가 한 곳뿐이고 인자를 안 넘겨도 기본값으로 도는 걸 확인해서, 바꿔도 깨질 데가 없었다.

```ts
// 시그니처 끝에 now 하나 추가, 내부 Date.now()를 now.getTime()으로
computeTtmEps(quarterly, latestAnnual, listedAt = null, now: Date = new Date())
```

diff는 두 줄이었다. 테스트는 이제 `listedAt`과 `now`를 상수로 넣어 14개월 임계 양쪽을 결정론적으로 고정한다. 모킹이 붙는 A보다 픽스처가 깔끔하고, 무엇보다 시각이 명시적 입력이 됐다.

나머지 함수들(호가단위·가격통계·리샘플 3종)은 성격이 단순해서 묶어 처리했다. 호가단위는 구간 경계에서 틀리기 쉬우니 여섯 구간의 경계를 위아래로 다 찍었고, 리샘플은 주·월·분 버킷이 정확히 나뉘는지를 봤다. 전부 소스를 읽어 실제 경계 규칙을 확인하고 거기에 맞춰 기대값을 잡았다.

한 가지 걸린 건, `computeTtmEps` 테스트를 돌리는데 이 함수를 import하는 것만으로 DB 클라이언트 초기화가 딸려온 거다. 같은 파일이 최상단에서 DB 연결을 세우고 있어서, 순수 계산 함수 하나를 테스트하는데 연결 문자열이 없으면 막혔다. 지금은 테스트 환경에 더미 값을 넣어 넘겼는데, 계산 로직과 DB 접근이 한 파일에 얽혀 있다는 신호이기도 하다. 당장 풀 문제는 아니라 남겨뒀다.

## 정리

- **Vitest 선택** — 속도가 아니라 설정 경제성. bundler tsconfig와 `@` alias를 재선언 없이 상속하고, Jest의 `next/jest` 우위는 순수함수 대상이라 무효였다.
- **테스트 대상 선별** — 복잡하고 조용히 번지는 함수만. format·룩업은 제외하고, 도달 불가한 방어 코드까지 커버율을 쫓지 않았다.
- **classifyDisclosure** — `tmp/` 데이터 대신 커밋 픽스처. 라벨 확정 12건 + 라벨 없는 불변식 176건으로 3개월치를 회귀 가드에 넣었다.
- **computeTtmEps** — `Date.now()`를 now 인자로 주입해 결정론적 테스트를 확보. `market.ts`의 기존 주입 패턴과 맞췄다.

순수 코드 작업만 있는 세션이라 화면에 보이는 변화는 없다. 대신 261개의 대조가 깔렸고, 앞으로 분류나 재무 계산을 고칠 때 뭐가 깨지는지 즉시 뜬다. 무엇을 테스트하느냐보다 **무엇을 테스트하지 않을지**를 정하는 데 생각을 더 쓴 세션이었다.

## 다음 작업

테스트 트랙을 닫으면서, 이제 로드맵 자체를 정리할 때가 됐다. 마무리 단계라 쌓인 항목을 걷어내고 Phase를 넘기는 게 먼저다.

- **로드맵 트리아지** — 남은 항목을 "제출까지 필수 / 출시 후 / 삭제"로 가른다. 이미 조사가 끝나 "안 함"으로 결론난 것들(예: dev 서버 OOM)이 아직 잔여로 남아 있어, 이런 걸 걷어내면 활성 항목이 확 준다.
- **UI 마무리** — 미뤄둔 화면 점검. 검색 결과 개수 제한, 순위 슬레이트 몇 군데, 프리장 현재가 확인 등 메모해둔 것부터. 프리장은 장 시작 시각에 맞춰 실측이 필요하다.

그다음은 데이터 안정성 점검과 리팩토링을 각각 몰아서 처리하고, README와 포트폴리오 정리로 넘어간다. 구현은 거의 닫혔고, 남은 건 마무리의 결이다.
