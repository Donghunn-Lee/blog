>Next.js로 몇 번의 프로젝트를 진행한 경험이 있다. 하지만 Next.js의 핵심인 SSR을 제대로 사용하지 않았었다. 이제 개발을 배우고 있는 시기였기도 했고, 프로젝트 자체도 구현 자체에 목적을 뒀기 때문이었다. 하지만 실제로 현업에서 Next.js를 사용하는 서비스는 분명히 SSR 기능이 필요해서 사용할 것이고, 나는 그 기능에 대해 조금 더 제대로 알아야 한다.

---

## 1. SSR이란?

SSR(Server Side Rendering)은 **사용자가 페이지를 요청할 때, 서버에서 미리 HTML을 만들어 보내주는 방식**이다.

CSR에서는 브라우저가 빈 HTML을 받아온 뒤 자바스크립트를 실행해 화면을 그리지만, SSR에서는 사용자가 처음 페이지를 열 때부터 완성된 HTML이 내려간다.

```
CSR: 브라우저 → 빈 HTML + JS 다운로드 → JS 실행 → 화면 완성
SSR: 브라우저 → 서버가 HTML 생성 → 완성된 HTML 수신 → 바로 화면 표시

```

즉, **첫 화면이 언제 그려지는지**에 있어서 큰 차이가 있다.

---

## 2. CSR과의 비교

| 구분 | CSR(Client Side Rendering) | SSR(Server Side Rendering) |
| --- | --- | --- |
| 초기 로딩 속도 | JS 로딩 후 렌더링 → 상대적으로 느림 | 서버에서 완성된 HTML 제공 → 빠름 |
| SEO | 검색 엔진이 JS 실행 못 하면 불리 | HTML이 처음부터 완성 → 유리 |
| 사용자 경험 | 첫 화면까지 기다림 → `로딩 스피너` 자주 보임 | 바로 내용 확인 가능 |
| 서버 부하 | 브라우저가 렌더링 대부분 담당 | 서버에서 렌더링 부담 증가 |
| 동적 상호작용 | 이후 동작은 동일 (Hydration 필요) | 동일 |

---

## 3. SSR의 장점

### 1) 빠른 초기 렌더링

사용자가 처음 접속했을 때 서버가 완성된 HTML을 주기 때문에, **"첫 화면 표시 속도"**가 빠르다. 특히 느린 네트워크 환경에서는 CSR보다 체감 차이가 크다.

### 2) SEO 친화적

검색 엔진 크롤러는 자바스크립트를 완벽히 실행하지 못하는 경우가 많다. CSR 앱은 빈 HTML만 내려가므로 검색 노출에 불리하다. 반면 SSR은 **처음부터 HTML에 콘텐츠가 담겨 있어 SEO에 유리**하다.

### 3) 소셜 미디어 공유 최적화

카카오톡, 트위터, 페이스북 같은 SNS 미리보기 카드(meta tag)는 HTML의 `og:title`, `og:image` 등을 읽는다. SSR 환경에서는 이 값들이 바로 내려가기 때문에 **정상적으로 미리보기가 생성**된다.

---

## 4. SSR의 한계와 주의점

### 1) 서버 부하 증가

모든 요청마다 서버가 HTML을 렌더링해야 하므로, 트래픽이 많은 서비스라면 서버 리소스 소모가 커진다.

### 2) 캐싱 전략 필요

매번 새로 HTML을 만들면 성능이 떨어진다. 그래서 Next.js는 `SSG(Static Site Generation)`이나 `ISR(Incremental Static Regeneration)` 같은 보완 기법도 제공한다.

### 3) Hydration 비용

SSR로 HTML을 내려도, 클라이언트에서 다시 React가 "Hydration"을 거쳐 이벤트를 붙이고 상태를 동기화해야 한다. 따라서 **첫 화면 표시가 빠르더라도, 상호작용이 가능해지는 시점은 CSR과 비슷**할 수 있다.

---

## 5. Next.js에서 SSR 구현하기

Next.js에서는 `getServerSideProps`를 사용하면 SSR을 적용할 수 있다.

```tsx
// pages/index.tsx
export async function getServerSideProps() {
  const res = await fetch("https://api.example.com/posts");
  const posts = await res.json();

  return { props: { posts } };
}

export default function Home({ posts }) {
  return (
    <ul>
      {posts.map((p: any) => (
        <li key={p.id}>{p.title}</li>
      ))}
    </ul>
  );
}

```

- 페이지 요청 시마다 실행된다.
- 서버에서 데이터를 가져오고, 완성된 HTML을 반환한다.
- SEO와 초기 렌더링이 중요한 페이지에 적합하다.

---

## 6. SSR을 언제 써야 할까?

SSR이 무조건 좋은 건 아니다. 상황에 맞게 선택해야 한다.

- **SSR이 적합한 경우**
    - SEO가 중요한 블로그, 뉴스, 쇼핑몰 상품 상세 페이지
    - 소셜 공유 미리보기가 필요한 페이지
    - 사용자별 맞춤 데이터를 즉시 보여줘야 하는 페이지
- **CSR이 적합한 경우**
    - SEO가 필요 없는 내부 대시보드
    - 사용자 상호작용이 많은 SPA
    - 서버 리소스를 아끼고 싶은 경우

---

## 7. 정리

SSR은 **서버에서 HTML을 미리 만들어 내려주는 방식**으로,

CSR 대비 **빠른 초기 렌더링, SEO 최적화, 소셜 미디어 공유 대응**에서 강점을 가진다.

하지만 서버 부하와 Hydration 비용이 있기 때문에,

Next.js 같은 프레임워크는 **SSR + SSG + CSR**을 혼합해 상황별 최적의 전략을 취할 수 있게 한다.

즉, 중요한 건 "SSR이냐 CSR이냐"의 이분법이 아니라, **각 페이지 특성에 맞는 렌더링 전략을 섞어 쓰는 것**이다.
