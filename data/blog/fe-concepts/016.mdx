**핵심 요약**
- REST는 HTTP 통신 방법이 아니라, 자원을 URI로 표현하고 HTTP 메서드로 행위를 정의하는 **아키텍처 설계 원칙**이다.
- URI에는 행위(동사)가 아닌 자원(명사)을 담고, HTTP 메서드가 행위의 의미를 결정한다.
- 서버는 클라이언트의 이전 요청을 기억하지 않는 Stateless 구조여야 한다 — 이게 서버 확장성의 기반이다.

## API 설계에 규칙이 없으면 생기는 일

백엔드 개발자와 처음 협업하다 보면 이런 API 목록을 마주칠 때가 있다.

```
POST /createUser
GET  /getUserById?id=1
POST /deleteUser
GET  /updateUserStatus
```

HTTP를 쓰고 있으니까 동작은 한다. 그런데 API가 50개, 100개가 되면 문제가 드러난다.
새로 합류한 팀원은 목록만 봐서는 뭐가 뭔지 예측할 수 없고,
비슷한 기능을 만들 때마다 네이밍 규칙 논쟁이 반복된다.
`GET /updateUserStatus`처럼 메서드와 URI가 충돌하는 경우엔 브라우저 캐싱이나 프리패칭이 의도치 않게 동작해서 버그가 생기기도 한다.

REST는 이런 상황을 막기 위한 설계 원칙이다.

## REST란 무엇인가

REST는 **Representational State Transfer**의 약자다.
자원(Resource)의 표현(Representation)으로 상태(State)를 전달(Transfer)한다는 의미인데, 2000년 Roy Fielding의 논문에서 제시된 개념이다.

핵심을 한 문장으로 정리하면 이렇다.
**서버의 자원을 URI로 표현하고, 그 자원에 대한 행위를 HTTP 메서드로 정의하는 아키텍처 스타일.**
HTTP 위에서 어떻게 설계할 것인지에 대한 규칙이지, HTTP를 쓴다고 자동으로 REST가 되는 게 아니다.

## REST API를 구성하는 세 가지 원칙

### URI는 자원을 표현한다

URI에는 동사가 아니라 명사가 들어가야 한다.
`/deleteUser`가 아니라 `/users/1`이고,
`/createUser`가 아니라 `/users`다.
행위는 URI가 담당하는 게 아니기 때문이다.

그 행위는 HTTP 메서드가 결정한다.
`DELETE /users/1`이면 1번 유저를 삭제하는 것이고, `GET /users/1`이면 1번 유저를 조회하는 것이다.
URI가 같아도 메서드가 다르면 전혀 다른 동작이다.
이 구조 덕분에 API가 수백 개가 돼도 일관된 예측이 가능해진다.

### HTTP 메서드는 의미 있게 사용한다

메서드별 의미와 **멱등성(Idempotency)** 을 함께 이해해야 한다.

| 메서드 | 의미 | 멱등성 |
|--------|------|:------:|
| GET | 조회 | ✓ |
| POST | 생성 | ✗ |
| PUT | 전체 수정 | ✓ |
| PATCH | 부분 수정 | ✓ |
| DELETE | 삭제 | ✓ |

멱등성이란 **같은 요청을 여러 번 보내도 결과가 동일한 성질**이다.
`DELETE /users/1`을 두 번 보내도 결과는 "1번 유저 없음"으로 같다.
반면 `POST /users`를 두 번 보내면 유저가 두 개 생길 수 있는데, 이건 의도된 동작이다.

이게 실질적으로 중요한 이유는 네트워크 오류 때문이다.
요청이 중간에 끊겼을 때 클라이언트가 재시도를 한다면, 멱등성이 보장된 메서드는 안전하게 재시도할 수 있다.
POST는 그렇지 않기 때문에 재시도 로직을 별도로 처리해야 한다.

PUT과 PATCH의 차이도 짚어둘 필요가 있다.
PUT은 자원 전체를 교체한다. 이름만 바꾸고 싶어서 `{ "name": "Ethan" }`만 보내면 나머지 필드가 null로 덮어써진다.
PATCH는 보낸 필드만 수정한다. 실무에서 PUT을 잘못 쓰다가 데이터가 날아가는 버그가 생기는 경우가 여기서 비롯된다.

### 서버는 이전 요청을 기억하지 않는다 (Stateless)

REST에서 **서버는 클라이언트의 상태를 저장하지 않는다**. 각 요청은 독립적이어야 하고, 필요한 정보(인증 토큰 등)는 매 요청에 포함해야 한다.

이렇게 설계하는 이유는 서버 확장성 때문이다.
서버가 클라이언트 상태를 기억하면, 같은 클라이언트의 요청은 반드시 동일한 서버로 가야 한다(세션 스티키니스).
서버를 10대로 늘려도 특정 서버에만 요청이 몰릴 수 있다.
Stateless이면 어느 서버로 요청이 가도 동작하기 때문에 수평 확장이 자유로워진다.

## 자주 헷갈리는 것들

**`POST /login`은 REST 원칙에 어긋날까?**

엄밀히 따지면 그렇다. "로그인"은 자원이 아니라 행위이기 때문이다.
REST 순수주의 관점에서는 `POST /sessions`(세션이라는 자원을 생성)가 맞다.
그런데 실무에서는 `POST /login`을 그냥 쓰는 경우가 많고, 업계에서도 관례적으로 허용하는 편이다.
완전한 REST 준수보다 가독성과 팀 내 일관성이 더 중요할 때가 있다.

**경로 파라미터와 쿼리 파라미터는 어떻게 구분하는가?**

자원 자체를 특정할 때는 경로에, 필터링·정렬 조건은 쿼리에 넣는다.

```
GET /users/1          → 1번 유저 (자원 식별)
GET /users?role=admin → admin 역할의 유저 목록 (필터링)
```

이 기준을 지키면 URI만 봐도 "특정 자원을 가져오는 건지, 조건에 맞는 목록을 가져오는 건지"를 바로 알 수 있다.

## REST의 한계와 현실

Roy Fielding은 "REST라고 불리는 API 대부분은 진짜 REST가 아니다"라고 말했다.
진짜 REST를 구현하려면 HATEOAS 같은 조건도 충족해야 하는데, 응답에 다음 가능한 행동(링크)을 함께 포함해야 한다는 원칙이다.

```json
{
  "id": 1,
  "name": "Ethan",
  "links": [
    { "rel": "self",   "href": "/users/1", "method": "GET" },
    { "rel": "update", "href": "/users/1", "method": "PATCH" },
    { "rel": "delete", "href": "/users/1", "method": "DELETE" }
  ]
}
```

클라이언트가 API 문서 없이 응답만 보고 다음 행동을 결정할 수 있어야 한다는 아이디어인데, 구현 비용 대비 실익이 크지 않아서 실무에서는 거의 쓰이지 않는다.
프론트엔드는 어차피 API 문서를 보고 개발하고, 응답의 링크를 동적으로 파싱해서 쓰는 경우는 거의 없기 때문이다.

## REST는 스펙이 아니라 방향이다

REST를 처음 배울 때는 "URI에 동사 쓰면 안 된다"는 규칙처럼 받아들이기 쉽다.
그런데 실제로는 완벽하게 따라야 하는 스펙이 아니라, API 설계의 방향을 잡아주는 원칙에 가깝다.

핵심은 세 가지다.

- URI에 자원을 담고,
- 메서드를 의미 있게 쓰고,
- 서버를 Stateless하게 유지하는 것.

`POST /login`처럼 현실적인 타협이 필요한 경우도 있지만, 이 세 가지 방향만 지켜도 API는 훨씬 예측 가능하고 유지보수하기 쉬워진다.

결국 REST가 중요한 이유는 규칙 준수 자체가 아니라, **팀 전체가 같은 언어로 API를 읽고 쓸 수 있게 되는 것**이다.
