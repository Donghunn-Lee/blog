💡 **핵심 요약**

- 프론트엔드 아키텍처는 "정답"이 있는 영역이 아니라 **상태를 어디서 관리할지, 코드를 어떻게 모을지에 대한 일관된 결정**이다. 같은 프로젝트라도 규모와 도메인에 따라 적합한 답이 달라진다.
- 상태는 **서버 상태와 클라이언트 상태가 본질적으로 다른 종류**라는 점이 출발점이다. 캐싱·동기화·stale 처리가 필요한 서버 상태를 클라이언트 상태 도구로 다루면 결국 그것들을 직접 구현하게 된다.
- 폴더 구조는 결국 **"같이 변하는 코드를 가까이 두는가"의 문제**다. Atomic Design, Feature-Sliced Design 같은 보편 패턴은 이 질문에 대한 검증된 답이고, 프로젝트 규모에 맞게 선택하면 된다.

## 작은 프로젝트에선 안 보이던 문제

부트캠프 프로젝트나 다른 소규모 프로젝트를 만들 때는 아키텍처를 깊게 고민할 필요가 없었다. 컴포넌트 몇 개, `useState` 몇 개, API 호출 몇 개로 끝났으니까.

문제는 프로젝트가 일정 규모를 넘어서면서 시작된다.

- 어떤 상태는 `useState`로, 어떤 상태는 Redux에 넣고, 어떤 상태는 React Query로 가져온다
- 비슷해 보이는 컴포넌트가 여러 폴더에 흩어져 있다
- 한 기능을 수정하려면 `components/`, `hooks/`, `utils/`, `api/` 네 군데를 다 열어야 한다
- "이 함수 어디에 두지?"를 매번 고민한다

이런 상태가 되면 코드를 작성하는 시간보다 **"어디에 둘지", "어디서 가져올지"를 고민하는 시간**이 더 많아진다. 새로 합류한 사람은 코드베이스 파악만으로 며칠을 쓴다.

이 글은 그 고민에 대한 출발점을 정리한다. 정답을 주려는 건 아니다 — 정답이 없는 영역이기 때문이다. 다만 **어떤 질문을 던져야 하는지, 어떤 보편 패턴이 있는지**를 알면 자기 프로젝트에 맞는 답을 찾기가 훨씬 쉬워진다.

## 아키텍처는 두 질문에 대한 답이다

프론트엔드 아키텍처를 한 줄로 정의하자면 이렇다.

> **코드를 어떻게 나누고 모을지에 대한 일관된 결정.**

핵심은 **"정답이 있다"가 아니라 "결정 기준이 있다"** 는 점이다. 같은 프로젝트라도 팀의 규모, 도메인 복잡도, 변경 빈도에 따라 적합한 아키텍처가 다르다.

실무에서 아키텍처가 답해야 하는 질문은 본질적으로 두 개다.

1. **상태를 어디서 관리할 것인가** — 서버 데이터, 폼 입력값, 모달 열림 여부, 인증 정보… 다 같은 "상태"지만 성격이 다르다
2. **코드를 어떻게 모을 것인가** — 같은 기능에 속한 코드를 가까이 두는 것과, 같은 종류의 코드를 한곳에 모으는 것은 완전히 다른 접근이다

이 두 질문에 대한 일관된 답이 있어야 코드베이스가 커져도 무너지지 않는다.

## 상태 분류 — 서버 상태 vs 클라이언트 상태

가장 먼저 이해해야 할 분류는 **서버 상태와 클라이언트 상태가 본질적으로 다른 종류**라는 것이다.

[#023 React State와 Props](/blog/fe-concepts/023/)에서 "state는 컴포넌트가 자기 소유로 가진다"는 소유권 개념을 짚었다. 여기서 한 단계 더 들어가면, 상태마다 **누가 진실의 출처(source of truth)인가**가 다르다는 사실이 보인다.

| 항목 | 클라이언트 상태 | 서버 상태 |
|------|----------------|----------|
| 진실의 출처 | 클라이언트 | 서버 |
| 신선도 | 항상 최신 (내가 만든 거니까) | 시간이 지나면 stale |
| 동기화 | 필요 없음 | 다른 클라이언트와 동기화 필요 |
| 비동기성 | 동기 | 비동기 (네트워크) |
| 캐싱 | 의미 없음 | 핵심 |
| 예시 | 모달 열림 여부, 폼 입력값, 테마 | 사용자 목록, 게시글 데이터 |

오랫동안 React 생태계에서는 이 둘을 똑같이 다뤘다. Redux에 API 응답을 넣고, 로컬 UI 상태도 넣고, 폼 입력값도 넣었다. 그게 왜 문제였냐면 — **두 종류의 상태가 가진 특성이 완전히 다르기 때문이다.**

서버 상태를 클라이언트 상태처럼 다루면 어떻게 되는가 하면, **stale 데이터, 중복 요청, 캐시 무효화 로직, 낙관적 업데이트**를 전부 직접 구현하게 된다. Redux로 API 응답을 관리하던 시절에 `actions/reducers/sagas/selectors`가 끝없이 늘어났던 이유가 이것이다. 진짜 비즈니스 로직보다 동기화 보일러플레이트가 더 많았다.

지금은 이 분류가 도구 단위로 분리되어 있다.

```
서버 상태 → React Query (TanStack Query), SWR
  → 캐싱, 자동 재요청, stale 관리, 낙관적 업데이트가 내장됨

클라이언트 상태 → useState, useReducer, Zustand, Jotai
  → 단순한 메모리 상태, 동기화 불필요
```

> 💡 **"서버 상태도 어차피 메모리에 있으니 클라이언트 상태와 같다"는 흔한 오해다.**
> 기술적으로 둘 다 메모리에 있는 데이터이긴 하지만, 결정적인 차이는 **"누가 진실의 출처인가"** 다. 클라이언트 상태는 내가 마지막으로 쓴 값이 정답이지만, 서버 상태는 다른 사용자가 바꿨을 수도 있고, 다른 탭에서 수정했을 수도 있다. 그래서 동기화·재요청·stale 처리가 필요한 것이다.

## 클라이언트 상태도 한 번 더 나뉜다

클라이언트 상태로 분류했다고 해서 다 같은 자리에 두는 건 아니다. 한 번 더 나뉜다.

```
컴포넌트 로컬 상태
  - 한 컴포넌트 안에서만 쓰임
  - 모달의 입력값, 토글 상태
  → useState로 충분

전역 클라이언트 상태
  - 여러 컴포넌트가 공유
  - 테마, 사이드바 열림 여부, 인증 토큰
  → Zustand, Jotai, 또는 Context
```

판단 기준은 단순하다. **"이 상태를 누가 쓰는가"** 를 보면 된다. 한 컴포넌트만 쓰면 로컬, 여러 곳에서 쓰면 끌어올리거나 전역으로 보낸다.

전역 클라이언트 상태에서 Context와 외부 라이브러리(Zustand, Jotai 등) 중 무엇을 쓸지는 [#026 Context API](/blog/fe-concepts/026/)에서 정리한 기준을 그대로 적용하면 된다. **거의 안 바뀌는 값이거나 props drilling 회피가 주 목적이라면 Context, 자주 바뀌고 부분 구독이 필요하면 외부 라이브러리**를 사용한다.

> ⚠️ **"전역 상태가 필요하다 = Redux/Zustand가 필요하다"가 아니다.**
> 서버에서 온 데이터의 전역 공유는 React Query의 캐시가 이미 해주고 있다. 같은 query key로 호출하면 어디서든 같은 데이터를 본다. 순수 전역 클라이언트 상태(테마, 토글)만 따로 관리하면 되는데, 이건 Context로 충분한 경우가 많다. 외부 라이브러리는 전역 상태 자체가 복잡해지고 업데이트 로직이 많아질 때 의미가 있다.

## 폴더 구조 — 무엇을 기준으로 모으는가

상태 다음으로 답해야 할 질문은 폴더 구조다. 결국 **"같이 변하는 코드를 가까이 두는가"** 의 문제다.

가장 흔하게 보는 두 가지 출발점이 있다.

**1. 종류별 분류 (Type-based)**

```
src/
  components/
  hooks/
  api/
  utils/
```

장점은 단순하다. 파일 종류가 명확하고, "버튼 컴포넌트는 `components` 폴더에 있다"는 규칙이 일관된다.

문제는 **같이 변하는 코드가 멀리 있다**는 점이다. "게시글 기능"을 수정하려면 `components/PostList.tsx`, `hooks/usePost.ts`, `api/post.ts`를 다 열어야 한다. 프로젝트가 커지면 `components` 폴더 하나에 수백 개 파일이 들어간다.

**2. 기능별 분류 (Feature-based)**

```
src/
  features/
    auth/
      components/
      hooks/
      api/
    post/
      components/
      hooks/
      api/
  shared/
```

장점은 명확하다. **같이 변하는 코드가 한 폴더에 모여있다.** 게시글 기능을 수정하려면 `features/post/`만 보면 된다. 기능을 삭제할 때도 폴더 하나만 지우면 된다.

여기서의 문제는 "shared"의 경계가 애매해진다는 점이다. 두 기능이 쓰는 컴포넌트는 shared로 가야 하는가, 아니면 어느 한쪽 features에 두는가? 이런 판단이 매번 필요해진다.

이 두 가지가 가장 단순한 출발점이고, 이걸 더 정교하게 다듬은 것이 다음 섹션의 보편 패턴들이다.

## 실무에서 자주 보이는 아키텍처 패턴

폴더 구조를 처음부터 직접 설계할 필요는 없다. 커뮤니티에서 검증된 패턴이 이미 여럿 있다. 자주 거론되는 것들만 정리한다.

### Atomic Design

UI 컴포넌트를 **크기/복잡도 기준**으로 계층화한다. Brad Frost가 제안한 패턴으로, 디자인 시스템을 만드는 팀에서 자주 쓴다.

```
atoms      → Button, Input, Label (가장 작은 단위)
molecules  → SearchBar (atoms 조합)
organisms  → Header, ProductCard (여러 molecules)
templates  → 페이지 레이아웃 (데이터 없는 골격)
pages      → 실제 데이터가 들어간 화면
```

**장점**: 디자인 시스템과 잘 맞는다. 디자이너와 개발자가 같은 언어로 컴포넌트를 이야기할 수 있다.

**한계**: UI 구조만 다룬다. 비즈니스 로직, 상태 관리, API 호출 같은 영역에 대해서는 답하지 않는다. 그래서 보통 **다른 아키텍처와 조합해서** 쓴다.

### Feature-Sliced Design (FSD)

러시아 React 커뮤니티에서 시작되어 영미권에서도 빠르게 확산된 방법론이다. 기능별 분류를 더 엄격한 계층 구조로 정형화한 것이라고 보면 된다.

```
app       → 앱 초기화, 전역 Provider
pages     → 라우트 단위 페이지
widgets   → 여러 features를 조합한 큰 UI 블록
features  → 사용자 액션 단위 (예: auth/login, cart/add-item)
entities  → 비즈니스 객체 (예: user, product)
shared    → 공용 UI, 유틸, API 클라이언트
```

핵심 규칙은 **위 계층은 아래 계층만 import할 수 있다**는 것이다. `features`가 `pages`를 import하면 안 되고, `entities`끼리 직접 참조해도 안 된다. 이 의존성 방향을 ESLint로 강제한다.

**장점**: 의존성 흐름이 명확해서 큰 코드베이스에서도 무너지지 않는다. 각 슬라이스가 명시적인 public API를 갖기 때문에 리팩토링이 안전하다.

**한계**: 학습 비용이 크다. 작은 프로젝트엔 과하다. "이게 feature인가 widget인가"를 매번 고민하게 된다.

### Presentational / Container 패턴

컴포넌트를 **UI 표현(Presentational)** 과 **로직/데이터(Container)** 로 분리한다.

```tsx
// Container: 데이터 가져오기, 상태 관리
function UserCardContainer() {
  const { data } = useQuery({ queryKey: ['user'], queryFn: fetchUser });
  return <UserCard user={data} />;
}

// Presentational: UI만, props로 받음
function UserCard({ user }: { user: User }) {
  return <div className="card">{user.name}</div>;
}
```

원래 Dan Abramov가 제안했던 패턴이지만, 본인이 나중에 "Hooks가 나온 뒤로 이 패턴은 강하게 권장하지 않는다"고 입장을 바꿨다. 지금은 컴포넌트를 무리하게 둘로 쪼개기보다, **커스텀 훅으로 로직을 분리**하는 방식이 더 보편적이다.

```tsx
function UserCard() {
  const { data: user } = useUser();  // 로직은 훅으로
  return <div className="card">{user?.name}</div>;
}
```

다만 "표현과 로직을 분리한다"는 발상 자체는 여전히 유효하고, FSD의 슬라이스 내부 segment 분리(`ui` / `model` / `api`)에도 같은 사고가 녹아있다.

### 그 외 패턴들

- **Monorepo**: 여러 앱과 공용 패키지를 하나의 저장소에서 관리. Turborepo, Nx, pnpm workspaces. 회사가 여러 프로덕트를 운영하면서 디자인 시스템·유틸을 공유할 때. (예: 구글, 메타, 우버)
- **Micro-frontends**: 큰 앱을 독립적으로 배포 가능한 작은 앱으로 쪼개는 방식. Module Federation 같은 도구를 쓴다. 큰 조직에서 팀별 독립 배포가 필요할 때만 의미가 있고, 보통은 오버엔지니어링이다. (예: 쿠팡, 카카오페이)

| 패턴 | 다루는 영역 | 적합한 규모 |
|------|------------|------------|
| Atomic Design | UI 컴포넌트 분류 | 디자인 시스템이 있는 모든 규모 |
| FSD | 전체 코드 조직 | 중대형 |
| Presentational/Container | 컴포넌트 책임 분리 | 모든 규모 (지금은 훅으로 대체) |
| Monorepo | 저장소 단위 | 다중 프로덕트 |
| Micro-frontends | 배포 단위 | 대형 조직 |

> 💡 **실무에서는 보통 여러 패턴을 조합한다.**
> 예를 들면 "FSD로 코드를 나누고, 그 안의 UI는 Atomic Design으로 정리하고, 회사 전체는 Monorepo로 묶는다" 같은 식이다. 한 패턴만 골라야 한다는 발상 자체가 잘못된 출발점이다.

## 의존성 방향 — 폴더 구조보다 더 중요한 것

어떤 패턴을 쓰든, 폴더 구조 자체보다 더 중요한 게 **의존성 방향**이다. 같은 폴더 구조라도 의존성이 엉키면 결국 같은 문제가 생긴다.

원칙은 단순하다.

```
shared  →  features  →  pages  →  app
   ←           ←           ←

위 방향(역방향)은 절대 안 된다.
```

즉, **공용 컴포넌트가 특정 기능을 import하면 안 되고**, **기능끼리 직접 import해도 안 된다**. 만약 두 기능이 같은 코드를 쓴다면, 그 코드는 shared로 올라가야 한다.

이 규칙을 어기면 어떻게 되냐면 — `features/auth`가 `features/post`를 참조하고, `features/post`가 `features/comment`를 참조하고… 결국 한 기능을 빼려고 하면 다른 기능이 안 돌아간다. 순환 의존이 생기면 빌드 에러까지 발생한다.

ESLint 플러그인(`eslint-plugin-boundaries`, `eslint-plugin-import`)으로 강제하는 게 좋다. 사람이 일일이 지키기엔 한계가 있다. FSD가 매력적인 이유 중 하나가, **이 의존성 방향 규칙을 처음부터 명시적으로 강제한다**는 점이다.

> 💡 **폴더 구조는 보이지만, 의존성 방향은 잘 안 보인다.**
> 그래서 더 빨리 무너진다. 처음부터 의존성 흐름을 한 방향으로 잡고, 그걸 도구로 강제하는 게 장기적으로 훨씬 싸게 먹힌다.

## 아키텍처는 진화한다

마지막으로 짚을 점이 하나 있다. **아키텍처는 처음부터 정해놓고 시작하는 게 아니다.** 대규모 프로젝트를 처음 시작할 때부터 최종 결과물까지의 디렉토리 구조를 모두 계획하는 것은 매우 어려운 일이기 때문이다.

처음부터 FSD 같은 엄격한 계층을 도입하면 작은 변경에도 보일러플레이트가 많아진다. 도메인 경계가 모호한 초기 프로젝트에서 무리하게 기능별로 나누면, 모든 게 "shared"로 흘러가거나 분류 자체에 시간을 쓰게 된다.

현실적인 진화 경로는 보통 이런 모양이다.

```
1. 작은 프로젝트
   - 종류별 폴더 구조로 시작
   - useState + Context 정도로 충분

2. 도메인이 명확해질 때 (보통 5~10개 페이지)
   - 비슷한 코드가 여러 폴더에 흩어지는 게 보임
   - 기능별 폴더 구조로 리팩토링
   - 서버 상태는 React Query로 분리

3. 전역 클라이언트 상태가 늘어날 때
   - 인증, UI 모드, 권한 등이 여기저기서 쓰임
   - Zustand / Jotai 같은 외부 도구 도입 검토

4. 팀이 커지고 기능이 더 늘 때
   - 의존성 방향을 ESLint로 강제
   - 필요하면 FSD 같은 엄격한 계층 도입
```

각 단계의 이동은 **"신호"가 보일 때** 한다. 같은 코드를 세 번째 복사하고 있을 때, "이 함수 어디에 두지"를 매일 고민할 때, 한 기능 수정에 다섯 파일을 동시에 열고 있을 때. 이런 신호가 누적되면 그때 구조를 한 단계 끌어올린다.

좋은 아키텍처는 정답을 외운 결과가 아니라, **"무엇을 어디에 두고, 어디까지 영향이 퍼지게 할 것인가"** 를 자기 프로젝트의 맥락에서 매 순간 의식적으로 답하는 과정의 결과다. 같은 React/TypeScript 코드라도, 이 질문에 답하는 방식이 다르면 1년 뒤의 코드베이스는 완전히 다른 모양이 된다.
