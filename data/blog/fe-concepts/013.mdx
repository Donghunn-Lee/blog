> **핵심 요약**
> - Debounce와 Throttle은 둘 다 이벤트 핸들러의 과도한 실행을 제어하지만, 방식이 다르다.
> - Debounce는 연속 호출이 끝난 뒤 마지막 한 번만 실행하고, Throttle은 호출이 계속돼도 일정 간격마다 실행한다.
> - 중간 과정이 의미 없으면 Debounce, 중간에도 주기적으로 실행돼야 하면 Throttle이다.

## 왜 필요한가

검색창에 "react"를 타이핑하면 `r → re → rea → reac → react`, 다섯 번의 input 이벤트가 발생한다. 각 이벤트마다 API 요청이 나간다면, 사용자가 원하는 건 마지막 "react"에 대한 결과인데 중간 요청 네 개는 전부 불필요한 낭비다.

스크롤 이벤트는 더 심하다. 마우스 휠을 한 번 굴리는 동안 수백 개의 이벤트가 발생하는데, 각각에 DOM 조작이나 계산이 붙어있으면 버벅임으로 이어진다.

이 문제의 본질은 **이벤트 발생 빈도와 핸들러 실행 빈도가 1:1로 묶여있다**는 것이다. 이 묶음을 끊어주는 게 `Debounce`와 `Throttle`이다.

---

## Debounce — 끝날 때까지 기다린다

Debounce는 연속 호출이 들어오는 동안 실행을 미루다가, 마지막 호출 이후 일정 시간이 지나면 그때 한 번 실행한다. 핵심 메커니즘은 **타이머 초기화**다. 함수가 호출될 때마다 이전 타이머를 취소하고 새 타이머를 건다. 결국 호출이 멈추고 나서야 실행된다.
```js
function debounce(fn, delay) {
  let timer;
  return function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => {
      fn.apply(this, args);
    }, delay);
  };
}
```

300ms debounce를 건 검색 핸들러는 타이핑이 멈추고 300ms가 지나야 실행된다. 타이핑 중엔 계속 타이머가 리셋되니까, 아무리 빠르게 쳐도 중간 요청은 하나도 나가지 않는다.

여기서 한 가지 짚고 넘어갈 부분이 있다. Debounce에는 **trailing edge(기본값)**와 **leading edge** 두 가지 방식이 있다. Trailing은 지금 설명한 것처럼 호출이 끝난 뒤 실행하고, Leading은 첫 호출에 즉시 실행하고 이후 연속 호출은 무시한다.
```
trailing:  ↓  ↓  ↓  ↓  ↓  [idle]  ✓
leading:   ↓  ↓  ↓  ↓  ↓  [idle]
           ✓  ✗  ✗  ✗  ✗
```

Leading debounce는 첫 입력에 즉시 반응하지만, 연속 입력이 끝나는 시점엔 실행되지 않는다. "타이핑이 끝나면 검색"이 목적이라면 trailing이 맞다.

---

## Throttle — 주기적으로 허용한다

Throttle은 호출이 아무리 많아도 일정 간격마다 한 번씩만 실행을 허용한다. 핵심 메커니즘은 **실행 잠금**이다. 한 번 실행되면 interval 동안 추가 호출을 무시하고, 시간이 지나면 잠금이 풀린다.
```js
function throttle(fn, interval) {
  let lastTime = 0;
  return function (...args) {
    const now = Date.now();
    if (now - lastTime >= interval) {
      lastTime = now;
      fn.apply(this, args);
    }
  };
}
```

스크롤 이벤트에 100ms throttle을 걸면, 스크롤이 계속되는 동안에도 100ms마다 한 번씩 핸들러가 실행된다. Debounce와 달리 **호출이 끝나지 않아도 실행이 된다**는 게 결정적인 차이다.

무한 스크롤을 Debounce로 구현하면 어떻게 될까. 사용자가 천천히 스크롤을 계속 내리는 동안에는 핸들러가 한 번도 실행되지 않는다. 스크롤이 멈춰야 비로소 위치를 감지한다. 이 경우엔 Throttle이 맞다.

## 뭘 언제 쓰는가

판단 기준은 하나다. **중간 과정이 의미 있는가.**

중간 결과가 필요 없고 최종 상태만 중요하다면 Debounce다. 검색 자동완성은 타이핑 중간 결과가 아니라 완성된 키워드에 대한 결과가 필요하다. 리사이즈 이벤트 후 레이아웃 재계산도 창 크기가 확정된 시점만 필요하다.

중간에도 주기적으로 실행돼야 한다면 Throttle이다. 무한 스크롤은 스크롤 중에도 현재 위치를 파악해야 한다. 드래그 중 실시간 좌표 업데이트, 게임의 버튼 연타 방지도 마찬가지다.

| 상황 | 선택 | 이유 |
|------|------|------|
| 검색 자동완성 | Debounce | 타이핑 완료 후 요청 하나만 필요 |
| 무한 스크롤 | Throttle | 스크롤 중에도 위치 감지 필요 |
| 윈도우 리사이즈 | Debounce | 크기 확정 후 재계산 |
| 드래그 좌표 추적 | Throttle | 실시간 위치 업데이트 필요 |
| 버튼 중복 제출 방지 | Throttle | 첫 클릭 즉시 반응, 연타 무시 |

실무에서는 직접 구현하기보다 lodash의 `_.debounce`, `_.throttle`을 많이 쓴다. leading/trailing 옵션도 제공하고, 취소(`cancel`)나 즉시 실행(`flush`) 메서드도 지원한다.

---

## 마치며

Debounce와 Throttle을 처음 봤을 때 "둘 다 딜레이를 주는 거 아닌가"라고 생각했다. 실제로는 딜레이가 아니라 **실행 시점을 제어하는 것**이고, 그 방식이 다르다. Debounce는 호출이 끝나는 시점을 기다리고, Throttle은 호출이 계속돼도 일정 간격을 유지한다.

이걸 이해하고 나면 선택 기준이 명확해진다. 검색창에 Throttle을 쓰거나 무한 스크롤에 Debounce를 쓰면 의도대로 동작하지 않는다. 두 개념의 차이는 "무엇을 최적화하느냐"가 아니라 "어떤 시점의 실행이 의미 있느냐"의 문제다.
