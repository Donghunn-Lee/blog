> 💡 **핵심 요약**
> - **Server Actions는 `'use server'`로 표시한 비동기 함수로, 클라이언트에서 호출하는 것처럼 보이지만 실제로는 서버에서 실행된다.** 호출 코드는 클라이언트에 있지만, 함수 본문은 클라이언트로 가지 않는다.
> - 기존 fetch + API Route 모델에서 **클라이언트와 서버 양쪽에 나눠 짜던 통신 코드**를 한 함수 정의로 압축한 모델이다. 그 위에 mutation 후 데이터 재검증과 progressive enhancement까지 묶여 있다.
> - "함수를 호출한다"는 표면적 모델 뒤에는 **컴파일러가 자동 생성한 RPC**가 숨어 있다. 이 구조를 잡고 가면 보안 모델과 API Route와의 트레이드오프가 같은 원칙의 다른 표현이라는 게 보인다.

---

## 폼 하나를 만들기 위해 짜야 했던 것

게시글 작성 폼을 만든다고 해보자. [#038 App Router](https://velog.io/@dh82680/Next.js-Pages-Router와-App-Router-FE-개념-탐구-038)까지의 모델에서, 우리가 짜야 했던 코드는 두 곳에 나뉘어 있었다.

서버 측에는 API Route 핸들러가 있다.

```ts
// app/api/posts/route.ts
export async function POST(req: Request) {
  const body = await req.json();
  if (!body.title) return Response.json({ error: '제목 필요' }, { status: 400 });
  await db.post.create({ data: body });
  return Response.json({ ok: true });
}
```

클라이언트 측에는 그 핸들러를 호출하는 코드가 있다.

```tsx
'use client';

const [isPending, setIsPending] = useState(false);
const [error, setError] = useState<string | null>(null);

const handleSubmit = async (e: FormEvent) => {
  e.preventDefault();
  setIsPending(true);
  try {
    const res = await fetch('/api/posts', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ title, content }),
    });
    if (!res.ok) throw new Error('실패');
    router.refresh();
  } catch (e) {
    setError(String(e));
  } finally {
    setIsPending(false);
  }
};
```

두 코드는 같은 도메인 모델을 양쪽 시그니처에 맞춰야 한다. 한쪽이 바뀌면 다른 쪽도 같이 고쳐야 한다. 거기에 pending 상태, 에러 상태, mutation 후 재검증 — 매번 똑같은 보일러플레이트를 다시 짠다.

**Server Actions는 이 구조을 다시 그린다.**

## Server Actions가 다시 그린 풍경

같은 게시글 작성 폼을 Server Actions로 짜면 이렇게 된다.

```ts
// app/actions.ts
'use server';

export async function createPost(formData: FormData) {
  const title = formData.get('title') as string;
  if (!title) throw new Error('제목 필요');
  await db.post.create({ data: { title } });
  revalidatePath('/posts');
}
```

```tsx
// app/posts/new/page.tsx — 서버 컴포넌트
import { createPost } from '@/app/actions';

export default function NewPostPage() {
  return (
    <form action={createPost}>
      <input name="title" />
      <button type="submit">작성</button>
    </form>
  );
}
```

두 파일에 나뉘어 있던 코드가 모두 사라졌다. API Route도, fetch도, useState도, try-catch도 없다. 함수 하나를 정의하고, form에 그대로 바인딩했다.

표면적으로는 `createPost`를 클라이언트에서 import해서 쓰는 것처럼 보인다. 그런데 실제로는 그렇지 않다. **`createPost`의 본문 코드는 클라이언트 번들에 들어가지 않는다.** DB 쿼리도, 검증 로직도, `revalidatePath` 호출도 다 서버에만 있다.

---

## "클라이언트 번들에 안 가는 것"이 신기능이 아니다

여기까지 보면 이렇게 정리하기 쉽다.

> "원래 함수 선언은 클라이언트 번들에 들어가는데, Server Actions는 그걸 서버에 두고 ID 참조만 클라이언트에 내려준다."

후반부는 맞는데, 전제가 틀렸다. **API Route 시절에도 `POST` 핸들러는 클라이언트 번들에 들어간 적이 없다.** 서버 코드는 원래 서버에만 있었다. 그건 새로운 게 아니다.

Server Actions가 실제로 해결한 보일러플레이트는 두 가지다.

1. **클라이언트와 서버를 잇는 통신 코드를 양쪽에 따로 짜야 했던 것** — fetch URL, 메서드, 헤더, 직렬화/역직렬화, 응답 파싱
2. **mutation 주변의 상태 관리** — pending, error, 성공 후 `router.refresh()`

Server Actions가 한 일은 함수 하나만 정의하면 **이 사이의 통신 코드를 컴파일러가 대신 짜주는** 것이다. 양쪽에 흩어져 있던 코드가 한 함수 정의로 압축된다.

---

## 동작 원리 — 함수 호출이 아닌 RPC(원격 프로시저 호출)

표면적으로는 `createPost`를 import해서 form에 바인딩하는 것처럼 보이지만, 클라이언트 번들에 `createPost`의 **본문 코드**는 들어가지 않는다. 이게 어떻게 가능할까.

핵심은 컴파일러가 양쪽 코드를 자동 생성한다는 점이다.

### 1단계. 빌드 타임에 함수 식별

Next.js 컴파일러가 `'use server'`로 표시된 함수를 찾는다. 그리고 각 함수에 고유 ID(해시값)를 부여한다.

### 2단계. 서버 측 — 자동 POST endpoint 생성

서버 빌드에는 이 ID들을 처리하는 endpoint가 자동으로 만들어진다. 우리가 직접 `app/api/...`를 만들지 않아도, 컴파일러가 비슷한 역할을 하는 endpoint를 빌드 결과물에 심어둔다.

### 3단계. 클라이언트 측 — 함수 자리에 stub만 들어감

클라이언트 번들에는 `createPost`의 본문 대신 **이런 모양의 stub**이 들어간다고 이해하면 된다.

```ts
// 클라이언트 번들에 들어가는 (대략의) 실제 모습
const createPost = createServerReference('abc123def');
// 호출하면 → POST /_actions
//          → body: { id: 'abc123def', args: [formData] }
//          → 서버 응답을 역직렬화해서 반환
```

함수 본문은 없다. ID와 "이 ID로 서버에 요청을 보내는 코드"만 있다.

### 4단계. 호출 → 직렬화 → 서버에서 실행 → 결과 반환

클라이언트에서 `createPost(formData)`가 실행되면 인자가 직렬화되어 POST로 전송되고, 서버는 ID로 함수를 찾아 실행한 뒤 결과를 역직렬화해서 돌려준다. 우리 눈에는 "그냥 함수 호출"이지만, 그 사이를 컴파일러가 자동 생성한 통신 코드가 메우고 있다.

> 💡 **즉 Server Actions는 새로운 마법이 아니라, "양쪽에 짜야 했던 fetch + API Route 쌍을 컴파일러가 자동 생성해주는" 모델이다.**
> 우리는 함수 하나만 쓰고, 클라이언트-서버 사이의 RPC는 빌드 도구가 채워 넣는다.

## `form action`에 따라오는 이점 — Progressive Enhancement

`<form action={createPost}>`로 직접 바인딩하면 한 가지 이점이 더 따라온다.

- **JS가 활성화된 환경**: client-side fetch로 처리, 페이지 리로드 없음
- **JS가 비활성화된 환경**: 브라우저 기본 form submit으로 POST, 서버 응답으로 페이지 재렌더링

fetch + API Route 모델에서는 `e.preventDefault()`를 부른 뒤 JS로 모든 걸 처리하기 때문에, JS가 꺼지면 폼이 그냥 죽었다. Server Actions는 form의 기본 submit 동작 위에 JS 향상을 얹는 구조라, **둘 다 자연스럽게 동작한다.**

이 동작은 React 19의 확장된 `<form action={...}>`에 의존한다.

## mutation과 재검증을 한 곳에서 책임진다

기존 모델에서 가장 불편했던 것 중 하나는, "mutation이 끝나면 어떤 데이터를 다시 가져와야 하는지"를 클라이언트가 알아야 했다는 점이다. 게시글을 만들었으면 목록을 다시 불러야 하고, 댓글을 달았으면 댓글 리스트를 다시 받아야 한다. 그걸 컴포넌트마다 `router.refresh()`나 `mutate()`로 처리한다.

Server Actions에서는 mutation을 일으킨 함수가 그 책임을 같이 진다.

```ts
'use server';
export async function createPost(formData: FormData) {
  await db.post.create({ /* ... */ });
  revalidatePath('/posts');   // 해당 경로의 캐시를 무효화한다
  // 또는
  revalidateTag('posts');     // 태그 기반 무효화
}
```

`revalidatePath`가 호출되면 그 경로에 매핑된 [#039 RSC](https://velog.io/@dh82680/Next.js-React-Server-Components-FE-개념-탐구-039) 트리가 다음 요청 시 다시 실행된다. 클라이언트는 "뭘 다시 받아야 하는지" 알 필요가 없다.

거기에 React 19의 두 훅이 상태 관리 보일러플레이트를 마저 덜어낸다.

```tsx
'use client';
import { useActionState } from 'react';
import { createPost } from './actions';

const [state, formAction, isPending] = useActionState(createPost, null);
```

- `useActionState`: 액션 결과 상태와 pending 상태를 한 번에 관리
- `useFormStatus`: 폼 내부 자식 컴포넌트에서 부모 폼의 pending 상태 구독 (제출 버튼을 비활성화하거나 스피너를 띄울 때)

`useState` + `try-catch` + `finally` 조합이 이 두 훅으로 압축된다.

## 헷갈리기 쉬운 부분

**"Server Action은 서버 함수니까 자동으로 안전하다."**
가장 위험한 오해다. Server Action은 빌드 시 **자동으로 공개 POST endpoint**가 만들어진다. ID만 알면 누구나 그 endpoint를 호출할 수 있다. 클라이언트 번들을 뜯어보면 ID는 그대로 보인다. 그래서 함수 안에서 인증·권한 검사를 **반드시 직접 해야 한다.**

```ts
'use server';
export async function deletePost(id: string) {
  const session = await auth();
  if (!session) throw new Error('Unauthorized');
  // 여기까지가 끝나야 실제 mutation
  await db.post.delete({ where: { id } });
}
```

**"Server Actions가 API Route를 완전히 대체한다."**
아니다. Server Actions는 **같은 Next.js 앱 안에서 호출되는 mutation**에 최적화된 모델이다. 모바일 앱, 웹훅, 다른 도메인의 클라이언트가 호출하는 공개 API는 여전히 API Route가 적합하다. URL을 안정적으로 유지해야 하는 공개 endpoint를 Server Actions로 만들면, 빌드마다 ID가 바뀌면서 외부 호출이 깨질 수 있다.

**"`'use server'`와 `'use client'`는 대칭이다."**
의미가 다르다. [#039](https://velog.io/@dh82680/Next.js-React-Server-Components-FE-개념-탐구-039)에서 본 `'use client'`는 "이 모듈은 클라이언트에서 실행되는 컴포넌트 경계"를 표시한다. `'use server'`는 "이 함수를 클라이언트에서 호출 가능한 서버 함수로 노출한다"는 의미다. 후자는 컴포넌트가 아니라 **함수**에 대한 표시이고, "서버 컴포넌트를 만든다"는 뜻이 아니다.

## 정리

Server Actions를 외워야 할 새 API로 받아들이면, `revalidatePath`도 `useActionState`도 progressive enhancement도 따로따로의 규칙처럼 보인다. 하지만 한 줄로 압축하면 이렇다.

> **함수 하나만 정의하면, 그 함수가 서버에서 실행되도록 컴파일러가 클라이언트-서버 사이의 통신 코드를 자동 생성한다.**

왜 `form action`에 직접 바인딩할 수 있는지, 왜 같은 함수 안에서 데이터를 무효화하는지, 왜 자동으로 안전하지 않은지 — 다 같은 원칙의 다른 표현이다. **함수처럼 보이지만 실제로는 RPC다.** 우리가 함수 한 줄을 쓰는 동안, 컴파일러는 그 뒤에서 두 파일에 걸쳐 짜야 했을 코드를 묵묵히 채워 넣고 있다.
