**핵심 요약**
- JWT는 인증 상태를 서버가 아닌 클라이언트가 들고 다니는 방식이다.
- Access Token은 짧게, Refresh Token은 길게 — 둘을 나누는 건 보안과 사용성의 균형 때문이다.
- stateless의 장점은 확장성이고, 단점은 즉시 무효화가 어렵다는 것이다. 이 트레이드오프를 이해하는 게 핵심이다.

---

## 왜 인증이 필요한가

HTTP는 **stateless**다. 요청이 끝나면 서버는 상대를 기억하지 않는다.
로그인을 했어도 다음 요청은 처음 만나는 사람처럼 취급된다.
그래서 "나 인증된 사용자야"를 매 요청마다 증명하는 방법이 필요하다.

---

## 세션 기반 인증: 서버가 기억하는 방식

전통적인 해법은 서버가 기억하는 것이다.

```
1. 로그인 성공
2. 서버: 세션 데이터를 메모리/DB에 저장 → 세션 ID 발급
3. 클라이언트: 세션 ID를 쿠키에 보관
4. 이후 요청마다 쿠키의 세션 ID를 전송
5. 서버: 세션 ID로 DB 조회 → 사용자 식별
```

직관적이고 즉시 로그아웃도 쉽다. DB에서 세션을 삭제하면 끝이다.

문제는 서버가 여러 대가 되는 순간 생긴다.
A 서버에서 로그인했는데 다음 요청이 B 서버로 가면, B는 그 세션을 모른다.
Redis 같은 공유 세션 스토리지를 따로 두거나, 같은 사용자를 항상 같은 서버로 보내는 Sticky Session을 써야 한다.
서버가 늘어날수록 인프라가 복잡해진다.

---

## JWT 토큰 기반 인증: 클라이언트가 증거를 들고 다니는 방식

JWT는 발상을 뒤집는다. 서버가 기억하는 대신, **토큰 자체가 증거**가 된다.

JWT는 세 파트로 구성된다.

```
eyJhbGciOiJIUzI1NiJ9.eyJ1c2VySWQiOjF9.abc123
      Header                Payload        Signature
```

- **Header** — 서명 알고리즘 정보 (`HS256` 등)
- **Payload** — 실제 데이터 (userId, 만료 시간 등)
- **Signature** — Header + Payload를 서버 비밀키로 서명한 값

서버는 요청을 받으면 Header + Payload로 Signature를 직접 다시 계산한다.
토큰의 Signature와 같으면 "내가 발급한 게 맞고, 중간에 조작도 없었다"는 뜻이다. DB 조회 없이 검증이 끝난다.

어떤 서버든 같은 비밀키만 있으면 검증할 수 있어서, 스케일 아웃에 자유롭다.

> **주의:** Payload는 암호화가 아니라 Base64URL **인코딩**이다.
누구나 디코딩해서 읽을 수 있다. Signature는 "위조 방지"지 "내용 숨김"이 아니다.
비밀번호나 민감한 정보는 절대 Payload에 넣으면 안 된다.

## Access Token / Refresh Token을 나누는 이유

JWT 하나만 쓰면 치명적인 문제가 있다. 토큰이 탈취되면 만료될 때까지 서버는 막을 방법이 없다.
stateless라 "이 토큰은 무효"라는 상태를 서버가 갖지 않기 때문이다.

그래서 두 종류의 토큰을 함께 쓴다.

| | Access Token | Refresh Token |
|---|---|---|
| 용도 | API 인증 | Access Token 재발급 |
| 만료 시간 | 짧게 (15분 ~ 1시간) | 길게 (7일 ~ 30일) |
| 저장 위치 | 메모리 or localStorage | HttpOnly 쿠키 |

Access Token은 만료 시간을 짧게 가져간다. 탈취당해도 피해 기간이 제한된다.
만료될 때마다 재로그인을 강제하면 UX가 나빠지니, Refresh Token으로 조용히 재발급받는 구조다.

```
1. 로그인 → Access Token + Refresh Token 발급
2. API 요청: Authorization: Bearer <access_token>
3. 401 응답 (Access Token 만료)
4. Refresh Token으로 재발급 요청
5. 새 Access Token 발급 → 원래 요청 재시도
```

프론트엔드에서는 보통 axios interceptor로 3~5번을 자동으로 처리한다.

---

## 어디에 저장할 것인가

저장 위치는 XSS와 CSRF, 두 공격 사이의 선택이다.

**localStorage**에 저장하면 JS로 자유롭게 다룰 수 있어 구현이 단순하다.
하지만 XSS 공격이 성공하면 악성 스크립트가 토큰을 그대로 읽어간다.

**HttpOnly 쿠키**에 저장하면 JS에서 접근 자체가 불가능해 XSS 탈취 경로가 막힌다.
대신 쿠키는 요청 시 자동 전송되는 특성 때문에 CSRF에 취약해진다. 이건 `SameSite` 설정과 CSRF 토큰으로 방어한다.

그래서 많이 쓰는 패턴은 이렇다.

- **Access Token → 메모리 (JS 변수)**
  XSS로도 탈취가 어렵고, 페이지를 닫으면 사라진다.
- **Refresh Token → HttpOnly 쿠키**
  새로고침 시 Refresh Token으로 Access Token을 재발급받아 로그인 상태를 유지한다.

---

## JWT의 한계 — stateless의 이면

JWT를 쓴다는 건 이 트레이드오프를 받아들이는 것이다.

발급된 토큰을 만료 전에 강제로 무효화할 수 없다.
비밀번호가 변경되거나 계정이 탈취된 상황에서 즉각 차단이 필요하다면,
결국 무효화 토큰 블랙리스트를 DB에 따로 관리해야 한다.
그러면 요청마다 DB를 조회하게 되어 세션 방식과 비슷해진다.

| | 세션 기반 | JWT |
|---|---|---|
| 즉시 무효화 | 가능 | 어려움 |
| 스케일 아웃 | 어려움 | 자유로움 |
| 검증 방식 | DB 조회 | 서명 검증 |
| 적합한 환경 | 보안 민감 서비스 | MSA, 다중 서버 환경 |

JWT가 세션보다 항상 낫다는 건 오해다. "완전한 stateless"와 "즉각적인 무효화"는 동시에 달성하기 어렵다.
어떤 걸 우선순위에 두느냐에 따라 선택이 달라진다.
