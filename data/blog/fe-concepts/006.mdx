## 핵심 요약

- JavaScript는 한 번에 하나의 작업만 실행하지만, 이벤트 루프를 통해 비동기 작업을 순서에 맞게 처리할 수 있다.
- 이때 중요한 것은 `call stack`, 브라우저 환경, `task queue`, `microtask queue`가 어떻게 연결되는지 이해하는 것이다.
- 특히 `Promise.then()`이 `setTimeout(..., 0)`보다 먼저 실행되는 이유는, 둘 다 “나중에 실행”되는 것처럼 보여도 들어가는 queue와 우선순위가 다르기 때문이다.

프로젝트 AimTest를 개발할 때, `setTimeout` 을 정말 복잡하게 사용했었다.
그런데 종종 내 의도보다 콜백이 늦게 실행되서 의문을 가졌었다.

`Promise`에서도 이상한 점이 있다.
`setTimeout`도 나중에 실행되고, `Promise.then()`도 나중에 실행된다.

그런데 왜 둘의 실행 순서는 항상 같지 않을까?
예를 들어 아래 코드는 처음 보면 직관과 다르게 느껴질 수 있다.

```js
console.log('start');

setTimeout(() => {
  console.log('timeout');
}, 0);

Promise.resolve().then(() => {
  console.log('promise');
});

console.log('end');
```

많은 사람이 처음에는 `setTimeout(..., 0)`이 있으니 거의 바로 실행될 것 같다고 생각한다.  
하지만 실제 결과는 다음과 같다.

```js
start
end
promise
timeout
```

왜 이런 순서가 나오는가?

이 질문을 제대로 이해하려면 단순히 “비동기라서”라고 넘어가면 안 되고, JavaScript가 코드를 실행하는 방식 자체를 봐야 한다. 그 중심에 있는 개념이 바로 **이벤트 루프(Event Loop)** 다.

## 왜 이벤트 루프를 이해해야 할까

프론트엔드 개발에서는 비동기 코드가 거의 모든 곳에 들어간다.

- 클릭 이벤트 처리
- API 요청과 응답
- `setTimeout`, `setInterval`
- `Promise`, `async/await`
- 렌더링 이후 실행되는 후속 작업

문제는 이 코드들이 섞이기 시작하면 **“왜 이 코드가 먼저 실행됐는지”**, **“왜 이 로그가 예상과 다른 순서로 찍히는지”** 가 한 번에 헷갈리기 시작한다는 점이다.

이벤트 루프를 이해하지 못하면 비동기 코드는 결국 외워서 예측하게 된다.  
반대로 이벤트 루프를 이해하면, 실행 순서를 단순 암기가 아니라 **브라우저에서 JavaScript가 실제로 어떻게 움직이는지를 흐름으로 설명**할 수 있게 된다.

## JavaScript의 비동기 처리

JavaScript는 기본적으로 **한 번에 하나의 작업만 처리하는 싱글 스레드 언어**이다.  
즉, 어떤 순간에도 현재 실행 중인 코드는 하나뿐이다.

여기서 JavaScript가 모든 일을 혼자 처리하는 것이 아니라는 점이 중요하다.

JavaScript 엔진은 동기 코드를 순서대로 실행하는 역할에 집중하고, 시간이 걸리는 작업은 브라우저 같은 런타임 환경이 대신 맡는다. 타이머를 기다리거나, 네트워크 응답을 대기하거나, 사용자 이벤트를 감지하는 일은 JavaScript 엔진이 직접 계속 붙잡고 있는 것이 아니다.

즉, JavaScript가 비동기 작업을 “직접 수행”한다기보다,  
**외부 환경이 처리한 작업의 결과를 나중에 다시 받아 실행하는 구조**라고 보는 편이 더 정확하다.

그리고 이 “나중에 다시 받아 실행하는 흐름”을 조율하는 것이 이벤트 루프다.

## 이벤트 루프의 핵심 구성 요소

이벤트 루프를 이해하려면 몇 가지 요소를 같이 봐야 한다.

### 1. Call Stack

`call stack`은 현재 실행 중인 함수들이 쌓이는 공간이다.

동기 코드는 기본적으로 이 stack에서 실행된다.  
함수가 호출되면 stack에 쌓이고, 실행이 끝나면 stack에서 빠진다.

예를 들어 아래 코드는 아주 단순한 동기 실행 흐름이다.

```js
function first() {
  console.log('first');
}

function second() {
  first();
  console.log('second');
}

second();
```

이 코드는 대략 이런 흐름으로 움직인다.

1. `second()`가 stack에 들어간다.
2. `second()` 안에서 `first()`가 호출되어 stack 위에 쌓인다.
3. `first()` 실행이 끝나면 stack에서 빠진다.
4. 다시 `second()`가 이어서 실행된다.
5. `second()`도 끝나면 stack이 비게 된다.

즉, JavaScript의 기본 실행은 어디까지나 **call stack 중심의 동기 실행**이다.

### 2. 브라우저 환경(Web APIs 등)

하지만 모든 작업을 stack에 바로 쌓아두면 문제가 생긴다.

예를 들어 `setTimeout`이 3초를 기다려야 한다면, 그 3초 동안 stack이 멈춰 있으면 안 된다.  
`fetch` 요청이 끝날 때까지도 마찬가지다. 응답을 기다리는 동안 다른 코드가 전부 멈춰버리면 브라우저는 사실상 unusable한 상태가 된다.

그래서 브라우저는 타이머, 네트워크 요청, DOM 이벤트 감지 같은 작업을 JavaScript 엔진 바깥의 환경에서 처리한다.

대표적으로 이런 것들이 있다.

- `setTimeout`
- `setInterval`
- DOM 이벤트(`click`, `input` 등)
- `fetch`, XHR 같은 네트워크 요청

JavaScript는 이런 작업을 “등록”만 하고, 실제 대기나 감지는 브라우저가 맡는다.

### 3. Queue

비동기 작업이 끝났다고 해서 그 콜백이 바로 실행되는 것은 아니다.

예를 들어 타이머가 끝났거나, `Promise`의 후속 처리 준비가 됐다고 하더라도, JavaScript는 여전히 현재 stack에서 실행 중인 코드가 있을 수 있다.

그래서 준비가 끝난 작업은 queue 쪽으로 이동해 대기시키고,
나중에 call stack이 비었을 때 실행 기회를 얻는다.

이 때 중요한 점은 queue가 하나가 아니라는 것이다.

### 4. Task Queue와 Microtask Queue

이벤트 루프에서 가장 헷갈리는 지점이 바로 여기다.

비동기 작업은 모두 같은 queue로 가는 것이 아니다.

대표적으로 다음처럼 나뉜다.

**Task Queue(또는 Macrotask Queue)에 들어가는 것**
- `setTimeout`
- `setInterval`
- DOM 이벤트 콜백
- 일반적인 타이머/이벤트 기반 콜백

**Microtask Queue에 들어가는 것**
- `Promise.then`
- `Promise.catch`
- `Promise.finally`
- `queueMicrotask`

즉, 둘 다 “나중에 실행”되지만, **대기하는 줄이 다르다**.

그리고 이 차이가 실제 실행 순서를 갈라놓는다.

## 이벤트 루프의 동작 순서

이제 핵심 흐름을 순서대로 정리해보자.

### 1) 먼저 현재 stack의 동기 코드가 실행된다

JavaScript는 현재 실행 중인 코드를 먼저 끝낸다.  
즉, call stack에 남아 있는 작업을 우선 처리한다.

중간에 타이머가 끝났다고 해서 바로 그 콜백이 끼어드는 일은 없다.

### 2) 비동기 작업은 외부 환경에서 처리된다

`setTimeout`, `fetch`, DOM 이벤트 같은 작업은 브라우저 쪽에서 대기하거나 처리된다.

이 작업들이 완료되면 관련 콜백이 실행 가능한 상태가 된다.

### 3) 실행 가능한 콜백은 queue에 들어가 대기한다

다만 바로 stack으로 가는 것은 아니다.  
현재 실행 흐름을 방해하지 않기 위해 queue에서 대기한다.

### 4) Call Stack이 비면 이벤트 루프가 queue를 확인한다

이 시점부터 이벤트 루프가 동작한다.

이벤트 루프는 단순히 “queue에서 하나 꺼낸다”가 아니라,  
**어떤 queue를 먼저 볼지 정해진 규칙**에 따라 움직인다.

### 5) Microtask Queue를 먼저 비운다

이 부분이 가장 중요하다.

이벤트 루프는 call stack이 비었을 때, 먼저 microtask queue를 확인하고 가능한 작업을 전부 처리한다.

즉, microtask는 하나만 처리하는 것이 아니라, **그 시점에 쌓여 있는 것을 우선적으로 다 비운다**고 이해하는 편이 좋다.

### 6) 그다음 Task Queue에서 작업을 가져온다

microtask가 모두 처리된 뒤에야 task queue의 콜백이 실행된다.

그리고 task 하나를 실행한 뒤 다시 microtask를 확인하는 흐름이 반복된다.

정리하면 흐름은 대략 이렇게 이해할 수 있다.

1. call stack 실행
2. stack이 비면 microtask queue 처리
3. 그다음 task queue 처리
4. task 실행 후 다시 microtask 확인
5. 이 과정을 반복

즉, 이벤트 루프의 핵심은 단순히 “나중에 실행”이 아니라,  
**어떤 종류의 나중이냐에 따라 우선순위가 다르다**는 점이다.

## 헷갈리기 쉬운 포인트

이벤트 루프에서 가장 많이 헷갈리는 부분은 두 가지다.

첫째, **setTimeout(..., 0)은 즉시 실행이 아니다**.
지연 시간이 0이어도 바로 실행되는 것이 아니라, 현재 실행 중인 작업이 끝나고 task queue 차례가 왔을 때 실행된다.

둘째, **Promise.then()과 setTimeout은 둘 다 “나중에 실행”되지만 같은 순서로 처리되지 않는다**.
Promise.then()은 microtask queue, setTimeout은 task queue로 가기 때문에 보통 Promise 쪽이 먼저 실행된다.

## 정리

이벤트 루프는 JavaScript가 비동기 작업을  
**어떤 순서로 다시 실행할지 조율하는 흐름**이다.

- 동기 코드는 먼저 **call stack**에서 실행된다.
- 비동기 작업은 브라우저 환경을 거쳐 **queue**에 들어간다.
- 이때 `Promise.then()` 같은 **microtask**가  
  `setTimeout`보다 먼저 처리된다.
- 그래서 같은 “비동기 코드”처럼 보여도  
  실제 실행 순서는 달라질 수 있다.

결국 이벤트 루프를 이해하는 핵심은  
“비동기니까 나중에 실행된다” 정도로 넘기는 게 아니라,

- **어떤 작업이**
- **어디에 들어가고**
- **어떤 순서로 다시 실행되는지**

이 흐름을 보는 데 있는 것 같다.

이 부분이 정리되면,
왜 `Promise`가 `setTimeout`보다 먼저 실행되는지,  
브라우저에서 비동기 코드가 왜 그런 순서로 흘러가는지도 충분히 이해하고
예측가능한 코드를 작성하는데 도움이 될 것이라 생각한다.
