💡 **핵심 요약**

* CSR과 SSR은 "누가 렌더링하느냐"의 차이가 아니라 **"사용자가 처음 받는 HTML이 비어있느냐 채워져 있느냐"** 의 차이다. 그 차이가 FCP, TTI, SEO, 서버 비용으로 줄줄이 이어진다.
* SSR은 FCP를 빠르게 만들지만, **hydration 비용 때문에 TTI는 오히려 늦어질 수 있다.** "SSR이 빠르다"는 절반만 맞는 말이다.
* 그래서 실무의 질문은 "CSR이냐 SSR이냐"가 아니라 **"이 페이지에 어떤 방식이 맞는가"** 다. Next.js는 페이지 단위로 SSG/SSR/CSR/ISR을 섞어 쓰는 걸 가능하게 해준다.

## 빈 HTML이 만드는 문제

React로 만든 SPA는 빠른 반응성을 제공하고 유지보수성과 확장성이 뛰어나다. 하지만 분명 단점도 존재한다.

* 첫 화면이 너무 늦게 뜬다. 모바일이나 느린 네트워크에서는 흰 화면이 한참 보인다.
* 검색 엔진에 노출이 안 된다. 페이지 소스를 보면 `<div id="root"></div>` 외에 아무것도 없다.
* SNS에 링크를 공유했는데 미리보기 썸네일이 안 뜬다.

이 문제들의 공통 원인은 한 가지다.

> 서버가 빈 HTML을 보내고, JavaScript가 실행된 뒤에야 콘텐츠가 채워진다.

이게 CSR(Client-Side Rendering)의 구조적 특성이다.  
SSR(Server-Side Rendering)은 이 문제를 해결하기 위해 새로 등장한 게 아니라, **원래 웹은 SSR이었고 SPA가 등장하면서 CSR이 자리잡은** 것에 가깝다. 처음 React를 배울 때 CSR을 자연스럽게 받아들이지만, 사실 더 오래된 모델은 SSR이다.

[#008 브라우저 렌더링 과정](https://velog.io/@dh82680/브라우저-렌더링-과정-FE-개념-탐구-008)에서 본 대로, 브라우저는 받은 HTML을 파싱해서 DOM을 만들고 렌더링한다. CSR과 SSR의 차이는 결국 **그 HTML 안에 이미 콘텐츠가 들어있는가**에서 시작된다.

## CSR과 SSR의 차이점

두 방식의 흐름을 나란히 놓고 보면 차이가 분명해진다.

**CSR**

```
1. 사용자가 URL 입력
2. 서버 → 빈 HTML + JS 번들 응답
   <div id="root"></div> + bundle.js
3. 브라우저: HTML 파싱 → JS 다운로드 → JS 실행
4. React가 가상 DOM을 만들어 실제 DOM에 마운트
5. 화면에 콘텐츠 표시
6. (필요시) API 요청 → 데이터 도착 → 다시 렌더링
```

3~5단계가 모두 클라이언트에서 일어난다. 즉 사용자의 기기 성능과 네트워크 상태에 따라 첫 화면이 뜨는 시점이 결정된다.

**SSR**

```
1. 사용자가 URL 입력
2. 서버: 페이지에 필요한 데이터 조회
3. 서버: React 컴포넌트를 HTML 문자열로 렌더링 (renderToString)
4. 서버 → 완성된 HTML + JS 번들 응답
5. 브라우저: HTML 즉시 표시 (사용자는 콘텐츠를 본다)
6. 브라우저: JS 다운로드 → JS 실행
7. Hydration: 서버에서 만든 HTML에 이벤트 핸들러를 연결
8. 인터랙션 가능
```

여기서 중요한 건 **5단계와 8단계가 서로 다른 시점**이라는 점이다. 즉, "콘텐츠가 보이는 시점"과 "조작이 가능한 시점"이 분리된다. 이 간격을 만드는 것이 hydration이다.

## Hydration이란?

서버가 만들어 보낸 HTML은 **정적인 마크업**일 뿐이다. 버튼이 그려져 있어도 클릭이 동작하지 않는다.

이유는 단순하다. 서버는 React 컴포넌트를 문자열로 렌더링했을 뿐, 이벤트 핸들러나 useState는 HTML로 표현할 수 없다. `onClick={...}`을 HTML에 직렬화할 방법이 없으니, 클라이언트에서 별도로 연결해야 한다.

그 "연결"을 담당하는 과정이 hydration이다.

```
1. 서버가 만든 HTML이 화면에 그려져 있다
2. JS 번들 도착 → React 실행
3. React가 클라이언트에서 컴포넌트 트리를 다시 한 번 실행
4. 그 결과를 이미 존재하는 DOM과 매칭
5. 매칭된 DOM 노드에 이벤트 핸들러와 상태를 연결
6. 인터랙션 가능
```

> ⚠️ **Hydration이 끝나기 전까지는 클릭이 동작하지 않는다.**  
> 사용자는 화면을 보고 있지만, 버튼을 눌러도 반응이 없는 시간이 존재한다는 뜻이다.

Hydration은 단순히 이벤트를 붙이는 작업이 아니다. React는 클라이언트에서 컴포넌트를 다시 실행하면서 **그 결과가 서버가 만든 DOM과 일치하는지를 검증한다.**

서버 렌더링 결과와 클라이언트 첫 렌더링 결과가 다르면, Next.js를 처음 사용할 때 흔히 발생하는 에러인 **hydration mismatch** 에러가 발생한다.

```
function Greeting() {
  return <div>현재 시각: {Date.now()}</div>;
}
```

이 코드는 mismatch 에러를 일으킨다. 서버가 렌더링한 시점과 클라이언트가 렌더링하는 시점이 다르니, 같은 컴포넌트가 다른 결과를 만들기 때문이다. `Math.random()`, `typeof window !== 'undefined'` 같은 분기, 사용자 로케일 기반 포맷팅에서 같은 문제가 흔히 생긴다.

> 💡 SSR 환경에서 컴포넌트는 **서버와 클라이언트에서 동일한 결과를 내야 한다.**  
> 시점/환경에 따라 달라지는 값을 첫 렌더에 직접 쓰면 안 되고, 필요하다면 `useEffect` 안에서 클라이언트 마운트 후에만 처리해야 한다.

## SSR이 항상 빠른 것은 아니다

CSR과 SSR을 비교할 때 가장 자주 등장하는 두 지표가 있다.

| 지표 | 의미 | CSR | SSR |
| --- | --- | --- | --- |
| **FCP** (First Contentful Paint) | 사용자가 콘텐츠를 처음 보는 시점 | JS 실행 후 → 느림 | HTML 도착 즉시 → 빠름 |
| **TTI** (Time To Interactive) | 사용자가 실제로 조작 가능한 시점 | 첫 콘텐츠 표시와 거의 동시 | HTML 표시 + Hydration 완료 → 늦을 수 있음 |

즉, 두 방식은 **빨리 보여주고 조금 늦게 조작 가능**하거나 **조금 늦게 보여주지만 즉시 조작 가능**하도록 하는 차이가 있다.

다만 여기서 자주 오해하는 지점이 나온다.

> **SSR은 FCP만 확실히 빠르다.**

SSR은 "콘텐츠가 보이는 시점"을 극적으로 앞당긴다. 하지만 "조작이 가능한 시점"은 hydration 비용 때문에 오히려 CSR보다 늦어질 수 있다.  
화면을 빨리 보는 것과 빨리 조작할 수 있는 것은 다른 문제다.

특히 hydration 중에는 메인 스레드가 블로킹된다. 사용자 입장에서는 화면은 떠 있는데 버튼이 안 눌리는 이상한 상태가 된다. 이걸 **"hydration 지연"** 이라고 부른다.

이 문제를 줄이기 위해 React 18에서 **Streaming SSR**과 **Selective Hydration**이 도입됐다 — 페이지 전체를 한 번에 hydrate하는 게 아니라 컴포넌트 단위로 쪼개서, 사용자가 상호작용한 부분부터 우선 hydrate하는 식이다.

> SSR을 도입할 때 "TTI가 어떻게 되는가"를 같이 봐야 한다는 게 이 섹션의 결론이다. FCP만 보면 거의 항상 SSR이 이기지만, 실제 사용자 체감은 TTI에 좌우된다.

## SEO 관점에서의 차이

검색 엔진과 SNS 크롤러는 두 부류로 나뉜다.

**1. HTML만 보는 크롤러** — 대부분의 SNS 미리보기 봇, 일부 검색 엔진

CSR 페이지를 받으면 빈 HTML로 인식한다. 콘텐츠가 없다고 판단하므로 인덱싱도, OG 태그 기반 미리보기도 만들어지지 않는다.

**2. JavaScript를 실행하는 크롤러** — Googlebot 등

CSR 페이지도 인덱싱은 가능하다. 다만 JS 실행이 비동기 큐(rendering queue)로 미뤄지기 때문에 **인덱싱이 늦어지거나 누락될 수 있다.**

| 페이지 성격 | 적합한 방식 | 이유 |
| --- | --- | --- |
| 블로그, 커머스, 마케팅 | SSR / SSG | 검색 노출이 비즈니스에 직결 |
| OG 태그 미리보기가 필요한 페이지 | SSR / SSG | SNS 봇은 JS를 실행하지 않음 |
| 인증된 대시보드, 어드민 | CSR | 검색 노출 자체가 필요 없음 |

> "CSR은 SEO에 안 좋다"는 명제는 절반만 맞다. 정확히는 **"콘텐츠 도달 시점에 영향을 받는다"** 다. 그게 비즈니스에 중요한 페이지라면 SSR이 맞고, 그렇지 않으면 CSR로 충분하다.

## Next.js의 렌더링 방식 선택

실무에서 "전부 CSR"이나 "전부 SSR"을 선택하는 경우는 드물다. 페이지마다 특성이 다르기 때문이다. Next.js는 페이지 단위로 렌더링 방식을 선택할 수 있게 해준다.

| 방식 | 언제 렌더링 | 적합한 페이지 |
| --- | --- | --- |
| **SSG** (Static Site Generation) | 빌드 시점 | 블로그 글, 마케팅 페이지처럼 자주 안 바뀌는 콘텐츠 |
| **SSR** (Server-Side Rendering) | 요청 시점 | 사용자별로 다른 콘텐츠, 실시간 데이터 |
| **CSR** (Client-Side Rendering) | 브라우저에서 | 대시보드, 인증된 사용자 영역 |
| **ISR** (Incremental Static Regeneration) | 빌드 + 일정 주기 재생성 | 자주 바뀌지만 실시간은 아닌 콘텐츠 |

App Router 기준으로 보면 더 명확하다. 기본은 **Server Component**이고, 이건 서버에서 실행되어 HTML로 직렬화된다. 클라이언트 인터랙션이 필요한 부분만 `"use client"`로 표시해 클라이언트 컴포넌트로 분리한다.

```jsx
// app/page.tsx — Server Component (기본)
import { ProductList } from './ProductList'; // Server Component
import { CartButton } from './CartButton';   // Client Component

export default async function Page() {
  const products = await fetchProducts(); // 서버에서 직접 데이터 fetch
  return (
    <>
      <ProductList products={products} />
      <CartButton />
    </>
  );
}
```

```jsx
// app/CartButton.tsx
'use client';

export function CartButton() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(c => c + 1)}>장바구니 {count}</button>;
}
```

여기서 또 짚고 넘어갈 부분 하나.

> ⚠️ **`"use client"`는 "이 컴포넌트는 CSR만 한다"가 아니다.**  
> 클라이언트 컴포넌트도 서버에서 한 번 HTML로 렌더링되고, 클라이언트에서 hydration된다. SSR을 완전히 끄려면 `dynamic` import에 `ssr: false` 옵션을 명시해야 한다.

```jsx
const NoSSRComponent = dynamic(() => import('./Heavy'), { ssr: false });
```

브라우저 전용 API(`window`, `localStorage`, 일부 라이브러리)에 의존하는 컴포넌트는 이 방식이 필요하다.

## 헷갈리기 쉬운 부분

**① "SSR은 항상 CSR보다 빠르다"**

SSR이 빠른 건 FCP다. TTI는 hydration 비용 때문에 오히려 늦어질 수 있다. 사용자가 콘텐츠를 빨리 보는 것과 빨리 조작할 수 있는 것은 다른 문제다.

**② "Next.js를 쓰면 SSR이다"**

Next.js는 SSR을 **지원하는** 프레임워크일 뿐이다. 실제로는 페이지마다 SSG/SSR/CSR/ISR 중에서 선택해서 빌드된다. 정적인 페이지는 대부분 SSG로 빌드되고, SSR은 필요한 페이지에만 적용된다.

**③ "Client Component는 CSR이다"**

App Router의 클라이언트 컴포넌트도 **서버에서 한 번 렌더링된다.** `"use client"`는 "이 컴포넌트는 hydration이 필요하고 클라이언트 인터랙션을 가진다"는 표시이지, "서버에서 렌더링하지 마라"는 뜻이 아니다.

**④ "Hydration은 그냥 이벤트 연결"**

Hydration은 React가 클라이언트에서 컴포넌트 트리를 다시 실행하면서 서버가 만든 DOM과 일치하는지 검증하는 과정이다. 그래서 컴포넌트 안에서 `Date.now()`나 `Math.random()`처럼 매번 다른 값을 쓰면 mismatch 에러가 난다.

## 정리

CSR과 SSR을 "렌더링 주체"로만 구분하면 둘 중 하나를 고르는 문제처럼 느껴진다. 하지만 실제로는 **"사용자가 처음 받는 HTML이 어떤 상태인가"** 의 문제이고, 그 결정이 FCP, TTI, SEO, hydration 복잡도, 서버 비용까지 줄줄이 영향을 준다.

그래서 실무의 질문은 "CSR이냐 SSR이냐"가 아니라 **"이 페이지는 어떤 특성을 가지며, 어떤 방식이 맞는가"** 가 된다.

* SEO가 중요한 페이지 → SSR / SSG
* 사용자별 동적 콘텐츠 → SSR
* 인증된 대시보드 → CSR
* 자주 안 바뀌는 콘텐츠 → SSG

Next.js 같은 프레임워크가 이런 선택을 페이지 단위로 가능하게 해주기 때문에, 이제는 "하나만 골라서 다 처리한다"보다 **"페이지 특성에 맞게 섞는다"** 가 자연스러운 방향이 됐다.
