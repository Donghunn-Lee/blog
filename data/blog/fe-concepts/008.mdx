## 브라우저는 어떻게 화면을 그릴까

프로젝트를 진행하면서, 렌더링 성능 측면에서 여러 어려움을 겪은 적이 있다.
렌더링이 지나치게 자주 업데이트 되어 느려지거나,
요소가 내가 원하는 타이밍에 렌더링 되지 않는 등이다.

개발 학습 초기에는 브라우저 렌더링을 내가 코드를 짜면 브라우저가 알아서 화면을 그려주는 것으로 쉽게 생각했었다.

하지만 실제로는 브라우저가 문서를 읽고, 구조를 만들고, 스타일을 계산하고, 어디에 어떻게 배치할지 정한 뒤에야 화면을 그릴 수 있다.

이 흐름을 알아야 다음 질문들이 자연스럽게 정리된다.

- 왜 CSS 파일도 렌더링에 중요할까
- 왜 `script` 위치가 첫 화면 표시 속도에 영향을 줄까
- 왜 어떤 스타일 변경은 무겁고, 어떤 변경은 상대적으로 가벼울까
- 왜 애니메이션에서는 `top`, `left`보다 `transform`이 자주 언급될까

브라우저 렌더링 과정은 결국  
**작성한 코드가 사용자의 화면이 되기까지의 실제 처리 흐름**을 이해하는,
프론트 엔드 개발자라면 반드시 알아야 할 주제들 중 하나다.

## DOM, CSSOM, Render Tree는 각각 무엇일까

브라우저는 HTML 문자열을 그대로 화면에 뿌리지 않는다.  
먼저 문서를 해석해서 내부적으로 다룰 수 있는 구조로 바꾼다.

### DOM

DOM은 HTML 문서 구조를 객체 형태의 트리로 바꾼 것이다.

예를 들어 아래와 같은 HTML이 있으면:

```html
<body>
  <h1>Hello</h1>
  <p>world</p>
</body>
```

브라우저는 이를 단순 텍스트가 아니라  
`body` 아래에 `h1`, `p`가 있는 트리 구조로 이해한다.

즉 DOM은  
“문서에 어떤 요소가 어떤 구조로 존재하는가”를 나타내는 트리 구조의 객체 모델이다.

### CSSOM

CSSOM은 CSS를 해석해서 만든 스타일 정보 모델이다.

예를 들어 아래 CSS가 있다면:

```css
h1 {
  color: red;
  font-size: 24px;
}
```

브라우저는 이걸 그냥 문자열로 두는 게 아니라,  
어떤 선택자에 어떤 스타일이 적용되는지 계산 가능한 형태로 정리한다.

DOM과 마찬가지로 CSSOM 역시 트리 구조이며,
DOM이 문서의 구조라면, CSSOM은  
“그 구조가 어떻게 보여야 하는가”를 담고 있다.

### Render Tree

Render Tree는 단순히 말하자면 DOM과 CSSOM을 합쳐 놓은 것이지만, 이게 완전히 맞는 말은 아니다.

Render Tree는 DOM과 CSSOM을 합쳐서 만든,  
**실제로 화면에 그릴 대상들만 모아놓은 트리**다.

즉 문서 구조 전체가 아니라, 렌더링에 필요한 요소들만 포함한다.  
예를 들어 `display: none` 요소는 DOM에는 존재하지만
보여지지 않을 요소이기 때문에 Render Tree에는 들어가지 않는다.

이 부분은 나도 처음엔 DOM이 곧 화면 구조라고 생각해서 헷갈렸는데, 실제로는  
DOM은 전체 문서 구조이고, Render Tree는 그중 실제로 그려질 대상이라는 점이 핵심이었다.

## 렌더링은 어떤 순서로 진행될까

브라우저 렌더링은 보통 아래 순서로 이해하면 된다.

### 1. HTML 파싱 → DOM 생성

브라우저가 HTML을 받아오면 먼저 이를 읽으면서 DOM을 만든다.  
이 단계에서는 문서의 구조를 이해하는 것이 핵심이다.

### 2. CSS 파싱 → CSSOM 생성

HTML 안의 `<link>`, `<style>` 등을 만나면 CSS도 함께 해석해서 CSSOM을 만든다.  
브라우저는 구조만 알아서는 화면을 그릴 수 없기 때문에 스타일 정보도 필요하다.

### 3. DOM + CSSOM → Render Tree 생성

구조와 스타일 정보를 모두 갖춘 뒤, 실제 렌더링 대상만 포함한 Render Tree를 만든다.

이 시점에서 브라우저는  
“어떤 요소를 화면에 그려야 하는지”를 파악한 상태가 된다.

### 4. Layout

이제 각 요소를 화면 어디에, 어느 크기로 배치할지 계산한다.  
이 단계에서 요소의 위치, 너비, 높이 같은 박스 정보가 정해진다.

즉 Layout은  
“무엇을 그릴지”가 아니라  
“어디에 얼마나 크게 놓을지”를 계산하는 과정이다.

Layout단계가 페이지 로드 이후 다시 실행될 때는 Reflow라고 부른다.

### 5. Paint

Layout이 끝나면 이제 실제로 픽셀을 그린다.  
글자 색, 배경색, 테두리, 그림자, 이미지 같은 시각적 정보가 여기서 처리된다.

Layout을 배치 계산이라고 보면, Paint는 겉모습을 그리는 단계다.

### 6. Composite

현대 브라우저는 화면을 한 번에 단순히 그리는 게 아니라, 경우에 따라 여러 레이어로 나눠 처리한 뒤 합성한다.  
이 단계가 Composite다.

특히 `transform`, `opacity` 같은 속성은 잘 활용하면 전체 레이아웃을 다시 계산하지 않고도 비교적 효율적으로 화면 업데이트가 가능한 경우가 있다.

정리하면 브라우저 렌더링은 대략 이런 흐름이다.

**HTML 파싱 → DOM 생성 → CSSOM 생성 → Render Tree 생성 → Layout → Paint → Composite**

이 순서를 머릿속에 넣어두면 이후의 성능 최적화 개념들도 연결이 쉬워진다.

## script가 렌더링에 주는 영향

브라우저 렌더링을 공부할 때 자주 나오는 포인트가 `script`다.

이유는 간단하다.  
JavaScript는 DOM을 바꿀 수 있기 때문이다.

예를 들어 HTML을 한창 파싱하고 있는데 중간에 script가 아래처럼 DOM을 수정할 수 있다고 해보자.

```js
document.body.innerHTML = '<h1>changed</h1>';
```

그러면 브라우저 입장에서는  
“일단 이 script를 실행해봐야 지금까지 만든 구조가 유지되는지 아닌지 알 수 있겠네”가 된다.

그래서 기본 `script`는 보통 HTML 파싱을 잠시 멈추게 만든다.  
이 특성 때문에 script 로딩 방식은 첫 화면 표시 속도와 직접 연결된다.

여기서 `defer`와 `async` 차이도 같이 이해하면 좋다.

- `defer`는 다운로드는 병렬로 하되, 실행은 HTML 파싱이 끝난 뒤로 미룬다.
- `async`는 다운로드가 끝나는 즉시 실행되기 때문에, 문서 순서가 보장되지 않고 DOM이 다 만들어지기 전에 실행될 수도 있다.

즉 둘 다 “다운로드를 병렬로 한다”는 공통점이 있지만, 실행 시점이 다르다.

이 차이를 통해 어떤 스크립트는 `defer`가 더 적절하고, 어떤 스크립트는 `async`가 더 맞는지를 판단할 수 있다.

## 브라우저 렌더링의 이해가 실제로 필요한 경우들

브라우저 렌더링 과정은 이론으로만 끝나는 개념은 아니다.  
실제로 UI를 만들다 보면 꽤 자주 체감된다.

### DOM을 반복적으로 직접 수정할 때

리스트를 렌더링하면서 DOM을 루프 안에서 하나씩 계속 붙이면, 브라우저는 그 과정에서 스타일 계산과 배치 계산을 반복하게 될 수 있다.  
그러면 화면 갱신 비용이 커지고 UI가 버벅일 수 있다.

그래서 실무에서는 DOM 업데이트를 묶거나, 상태 기반으로 렌더링을 관리하는 방식이 중요하다.

### script 로딩 때문에 첫 화면이 늦을 때

초기 로딩 구간에 큰 script가 파싱을 막아버리면, 사용자는 “페이지가 느리다”고 체감한다.  
이럴 때 script 위치를 조정하거나 `defer`를 붙이는 것만으로도 첫 화면 경험이 꽤 달라질 수 있다.

### 애니메이션이 버벅일 때

처음에는 단순히 “애니메이션이 많아서 무거운가 보다”라고 생각할 수 있다.  
하지만 실제로는 어떤 속성을 변경하느냐가 더 중요할 때가 많다.

예를 들어 `top`, `left` 같은 속성은 레이아웃 계산과 더 강하게 연결될 수 있지만,  
`transform`은 비교적 뒤쪽 단계에서 처리될 가능성이 커서 부드러운 애니메이션에 유리한 경우가 많다.

이 부분은 다음에 다룰 Reflow, Repaint와도 바로 연결된다.

## 정리

브라우저는 코드를 받자마자 바로 화면을 그리는 게 아니다.  
구조를 만들고, 스타일을 계산하고, 렌더링 대상을 정하고, 배치와 그리기를 거쳐 최종 화면을 만든다.

정리하면 핵심은 이렇다.

- DOM은 문서 구조
- CSSOM은 스타일 정보
- Render Tree는 실제 렌더링 대상
- Layout은 위치와 크기 계산
- Paint는 실제 픽셀 그리기
- JavaScript는 이 흐름을 바꿀 수 있어서 렌더링 성능과 직접 연결된다

브라우저 렌더링 과정을 이해하면  
단순히 “브라우저가 느리다” 수준이 아니라  
어느 단계에서 비용이 커지며 어떻게 최적화 할 수 있는지를 조금 더 구조적으로 볼 수 있게 된다.
