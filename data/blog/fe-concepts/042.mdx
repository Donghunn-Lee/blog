> 💡 **핵심 요약**
>
> - **데이터 페칭 전략은 "데이터를 어디서 가져오고, 어느 레이어에 캐싱하고, 어떻게 무효화하느냐"의 결정 묶음이다.**
> - 서버 페칭(RSC)과 클라이언트 라이브러리(TanStack Query·SWR)는 경쟁 관계가 아니다. 전자는 진입 시점의 데이터를, 후자는 진입 이후 계속 바뀌는 데이터를 맡는다.
> - 페칭 버그의 대부분은 캐시가 한 층이 아니라는 데서 나온다. 게다가 Next.js의 캐싱 기본값은 버전마다 정반대로 바뀌었다. 어느 버전 기준인지 모르고 캐시를 다루면 반드시 헤맨다.

---

## 다양해진 fetching 전략

`useEffect` 안에서 `fetch`를 부르고, 위에 로딩 스피너를 깔고, 에러를 `useState`로 들고 있던 시절이 있다. 데이터를 가져오는 방법은 사실상 하나였다. 컴포넌트가 마운트되면 요청을 보내고, 응답이 오면 그린다. fetch를 어디서 부르든 결과는 같았다.

App Router로 넘어오면서 이 단순함이 깨졌다. [#039 React Server Components](/blog/fe-concepts/039/)에서 본 것처럼 서버 컴포넌트에서 데이터를 직접 `await`할 수 있게 됐고, [#041 Streaming SSR](/blog/fe-concepts/041/)에서 본 것처럼 그 데이터를 기다리는 동안 화면 일부를 먼저 흘려보낼 수도 있게 됐다. 다만 선택지가 늘었다는 건 잘못 선택할 가능성 또한 늘었다는 얘기다.

잘못된 선택은 보통 이렇게 드러난다. 필요 없는 곳에 스피너가 깜빡일 때. 같은 데이터를 컴포넌트 세 곳에서 각자 fetch해서 네트워크 탭에 동일 요청이 세 번 찍힐 때. 그리고 가장 흔한 것 — 분명 DB는 바꿨는데 화면은 옛날 데이터일 때, 혹은 반대로 안 바뀌어도 되는 데이터가 매번 새로 불러와질 때.

이 버그들은 문법 오류가 아니다. **데이터를 어느 위치에서 가져왔고, 어느 레이어에 캐시됐는지**를 헷갈려서 생긴다. 그래서 이 글은 "어떻게 fetch하나"가 아니라 "어디서 가져오고 어느 캐시에 머무나"를 따라간다.

## 데이터를 어디서 가져오는가

페칭 위치는 세 곳이다. 이 세 곳에서의 페칭은 각자 해결하는 문제가 다르다.

**① 서버 페칭 (RSC)** — `async` 서버 컴포넌트에서 직접 가져온다.

````tsx
async function ProductList() {
  const products = await db.product.findMany(); // DB 직접 호출
  return <ul>{products.map(p => <li key={p.id}>{p.name}</li>)}</ul>;
}
````

이 코드는 클라이언트 번들에 들어가지 않고, DB나 내부 API에 직접 접근하며, 결과가 초기 HTML에 포함된다. 거의 안 바뀌고 모두에게 같은 데이터 — 상품 목록, 블로그 글, 카테고리 — 의 기본값이다.

**② 클라이언트 페칭** — 마운트 이후, 사용자 상호작용에 따라 가져온다.

서버가 모르는 정보(방금 누른 필터, 무한 스크롤 위치)에 의존하거나, 진입 후 주기적으로 갱신돼야 하는 데이터에 쓴다. 다만 `useEffect + fetch`를 직접 짜면 로딩·에러·중복 제거·캐시·재요청을 전부 손으로 다시 만들어야 한다. 이게 다음 선택지가 존재하는 이유다.

**③ 라이브러리 (TanStack Query / SWR)** — ②의 반복 노동을 표준화한 레이어.

`useEffect`로 매번 재생성하던 것들 — 로딩·에러 상태, 백그라운드 리페칭, 캐시 무효화, 요청 중복 제거, 낙관적 업데이트 — 을 라이브러리가 처리한다. 클라이언트 페칭을 버리는 게 아니라, 그 위에 캐시와 동기화 계층을 얹는다.

> 💡 RSC가 생기고 나서 클라이언트 라이브러리 사용하지 않게 될 거란 의견도 있었는데, 그렇지 않다. 서버 페칭은 "페이지에 들어선 그 순간의 데이터"에 강하고, 라이브러리는 "들어선 다음 상호작용·실시간·낙관적 업데이트로 계속 바뀌는 데이터"에 강하다. 둘은 같은 화면의 다른 구간을 맡는다.

## TanStack Query와 SWR, 무엇을 써야 할까

둘 다 현역이고 활발히 유지보수된다(2026년 6월 기준 둘 다 최신 릴리스가 나와 있다). "A가 낫다"의 문제가 아니라 무게와 기능 깊이의 트레이드오프다.

| | TanStack Query (v5) | SWR (v2) |
|---|---|---|
| 번들 크기 | 약 13KB gzipped | 약 4KB gzipped |
| 성격 | 기능 풍부, 익힐 개념 많음 | 작고 단순, 빠른 학습 |
| 익혀야 할 것 | queryKey·staleTime·gcTime·mutation lifecycle | 최소 API, 기본값이 대부분 처리 |
| 강점 | 복잡한 mutation·낙관적 업데이트·공식 devtools | Vercel 제작, Next.js 친화 |

SWR은 API 표면이 작아서 빠르게 생산성이 난다. TanStack Query는 익혀야 할 개념이 더 많지만, 복잡한 서버 상태를 다룰 때 더 많은 제어권을 준다. 앱이 단순하면 SWR, 캐시·mutation 시나리오가 복잡하면 TanStack Query 쪽이 자연스럽다.

> ⚠️ **둘 다 server state 도구지 client state 도구가 아니다.**
> 모달 열림 여부, 다크모드 토글 같은 UI 전용 상태는 여기 두지 않는다. 그건 `useState`나 Zustand의 자리다. 이 구분이 무너지면 서버에서 온 데이터와 UI 상태가 한 곳에 뒤섞여 디버깅이 어려워진다.

## 캐시는 한 층이 아니다 — 그리고 버전마다 다르다

여기가 이 토픽의 핵심이자 함정이다. 데이터 페칭 버그의 대부분은 "캐시가 여러 층 있는데 어느 층 얘기인지 모름"에서 나온다. 그리고 **Next.js의 캐싱 기본값은 버전을 건너올 때마다 방향이 뒤집혔다.**

| 버전 | 기본 동작 | 모델 |
|---|---|---|
| Next.js 14 | fetch·GET Route Handler **기본 캐싱** | "전부 캐시, 필요하면 opt-out" |
| Next.js 15 | fetch·GET Route Handler·내비게이션 **기본 비캐싱** | "기본 `no-store`, 필요하면 opt-in" |
| Next.js 16 | 전부 동적, **명시한 것만 캐시** | `use cache` 디렉티브로 opt-in |

검색해서 나온 글이 어느 버전 기준인지 확인하지 않으면, "분명 공식 문서대로 했는데 동작이 다른" 상황을 만나게 될 수 있다. Next.js 14를 15로 올렸더니 모든 페이지가 느려졌다는 사례가 흔한 이유가 이것이다. fetch가 더 이상 자동 캐싱되지 않아 매 요청마다 origin을 때리기 때문이다.

가장 최신인 Next.js 16은 [#017 HTTP 캐싱](/blog/fe-concepts/017/)에서 본 브라우저 ↔ 서버 협상 캐시와는 또 다른 층의 이야기다. 한 번의 요청이 거치는 캐시 레이어를 안쪽부터 늘어놓으면 다음과 같다.

````text
[ 한 번의 요청이 거치는 캐시 레이어 — Next.js 16, cacheComponents 기준 ]

서버
 ├─ Request Memoization   같은 fetch를 단일 렌더 패스 동안 한 번만 실행
 ├─ Data Cache            use cache — 요청 사이를 넘어 지속 / cacheLife로 수명 관리
 └─ PPR static shell      빌드 시 정적 셸 + 동적 부분은 요청 시 스트리밍

클라이언트
 ├─ Router Cache          방문한 라우트 세그먼트
 └─ 라이브러리 캐시        TanStack Query / SWR — 위 레이어들과 완전히 별개
````

- **Request Memoization** 은 같은 URL·옵션의 GET fetch를 한 번의 서버 렌더 동안 자동으로 한 번만 실행한다. 컴포넌트 세 곳에서 같은 fetch를 불러도 요청은 하나다. 단 **요청 하나를 처리하는 동안만** 유효하다.
- **Data Cache** 는 Next.js 16의 `use cache` 디렉티브로 만든다. 컴파일러가 인자와 클로저 값으로 캐시 키를 자동 생성하고, 요청 사이를 넘어 결과가 지속된다.
- **PPR static shell** 은 [#041 Streaming SSR](/blog/fe-concepts/041/)에서 본 구조가 캐싱과 합쳐진 형태다. 캐시된 셸은 즉시, 동적 구간은 Suspense로 스트리밍된다.

맨 아래 라이브러리 캐시가 위 서버 레이어들과 **다른 메모리에 산다**는 게 핵심이다. 이 분리를 놓치면 무효화에서 막힌다.

> ⚠️ Next.js 16이라도 `cacheComponents` 플래그를 켜야 `use cache`·`cacheLife`·PPR 기본 모델이 완전히 적용된다. 켜지 않으면 15 스타일 동작(`revalidate` export 등)이 상당 부분 유지된다. "16인데 왜 use cache가 안 먹지"는 보통 이 플래그 문제다.

## 무효화는 레이어를 알아야 가능하다

캐시를 새로고침하려면 **그게 어느 레이어의 캐시인지**부터 정해야 한다. 같은 "갱신"이라도 서버 캐시와 클라이언트 캐시는 방법이 다르다.

**서버 (Next.js 16)** — 시간 기반은 `cacheLife()`로 수명을 정하고, 온디맨드는 태그로 끊는다.

````tsx
async function getProducts() {
  'use cache';
  cacheTag('products');           // 이 캐시에 태그를 붙인다
  return db.product.findMany();
}

// Server Action에서 mutation 후
'use server';
import { revalidateTag } from 'next/cache';
export async function updateProduct(/* ... */) {
  // ... DB 업데이트
  revalidateTag('products');      // 'products' 태그가 붙은 서버 캐시만 무효화
}
````

[#040 Server Actions](/blog/fe-concepts/040/)에서 다룬 그 흐름 위에 `revalidateTag`가 얹힌다.

**클라이언트** — 라이브러리가 들고 있는 사본은 라이브러리 API로 무효화한다.

- TanStack Query: `queryClient.invalidateQueries({ queryKey: ['products'] })`
- SWR: `mutate('products')`

> ⚠️ **TanStack Query 캐시를 무효화했다고 서버 Data Cache까지 새로고침되는 게 아니다.**
> 두 캐시는 분리된 레이어다. 서버에서 mutation을 했으면 서버 캐시는 `revalidateTag`로, 클라이언트가 들고 있는 사본은 `invalidateQueries`로 — 양쪽 다 건드려야 화면이 일관되게 갱신된다. "새로고침하면 바뀌는데 그 자리에선 안 바뀐다"는 거의 항상 한쪽만 무효화한 경우다.

## 헷갈리기 쉬운 부분

**"서버 컴포넌트가 있으니 데이터 페칭 라이브러리는 필요 없다."**
서버 페칭은 진입 시점에 한 번 가져오는 데이터에 최적이다. 하지만 진입 이후 사용자 상호작용으로 계속 바뀌는 데이터, 실시간 갱신, 낙관적 업데이트, 창 포커스 시 리페치는 여전히 클라이언트 라이브러리의 영역이다. 둘은 대체재가 아니라 분담이다.

**"Next.js 캐싱은 한 번 배워두면 된다."**
14·15·16의 기본값이 정반대다. 14는 기본 캐싱, 15는 기본 비캐싱, 16은 명시적 opt-in. 특히 옛날 글의 `export const revalidate`나 자동 캐싱을 그대로 따라 하면 최신 버전에서 동작이 어긋난다. 코드를 복사하기 전에 그 글의 작성 시점부터 본다.

**"캐시 무효화는 한 군데만 하면 된다."**
서버 Data Cache, 클라이언트 Router Cache, 라이브러리 캐시는 각자 다른 메모리에 산다. 한 레이어만 무효화하고 다른 레이어의 사본이 남으면, 화면은 자리마다 다른 데이터를 보여준다.

## 정리

이 시리즈에서 데이터를 다룰 때마다 질문은 "어떻게 fetch하나"였다. 데이터 페칭 전략은 그 질문을 바꾼다.

> **이 데이터는 어디에서 가져오고, 어느 레이어에 머무르며, 누가 무효화 책임을 지는가.**

서버에서 한 번 가져올 데이터인지 진입 후 계속 갱신될 데이터인지, 거기에 따라 위치가 갈리고, 위치가 갈리면 캐시 레이어가 갈리고, 레이어가 갈리면 무효화 방법이 갈린다. 세 가지는 따로 외우는 규칙이 아니라 하나의 결정에서 줄줄이 따라 나오는 결과다. 그래서 화면이 옛날 데이터를 들고 있을 때 처음 던질 질문은 "왜 안 바뀌지"가 아니라 "이 데이터는 지금 어느 캐시에 살아 있지"가 된다.
