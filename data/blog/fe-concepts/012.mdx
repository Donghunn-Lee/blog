## 핵심 요약

- 브라우저에는 `localStorage`, `sessionStorage`, `cookie`처럼 데이터를 저장하는 여러 방식이 있다.
- 셋 다 비슷해 보여도 유지 범위와 서버와의 관계가 달라서 쓰임새가 다르다.
- 특히 쿠키는 단순 저장소라기보다 요청 흐름, 세션, 인증과 함께 이해해야 한다.

## 브라우저 저장소

처음 개발을 배울 때는 간단한 데이터를 어디엔가 저장해야 하는 순간이 생각보다 빨리 온다.  
다크모드 같은 설정을 기억하게 하고 싶을 때도 있고, 작성 중인 폼 내용을 잠깐 보관하고 싶을 때도 있다.

이럴 때 가장 먼저 접하게 되는 게 보통 `localStorage`다.  
백엔드 없이도 브라우저에서 바로 값을 저장하고 꺼내볼 수 있어서, 처음엔 꽤 편하게 느껴진다.

문제는 여기서부터다.  
브라우저에 저장할 수 있다는 이유만으로 아무 데이터나 익숙한 저장소에 넣어버리면, 나중에 보안이나 동작 방식 때문에 생각보다 골치 아픈 상황이 생길 수 있다.

브라우저 저장소를 볼 때 중요한 건  
단순히 “어디에 저장할 수 있느냐”보다  
**이 값이 얼마나 오래 남아야 하는지, 서버와 함께 다뤄야 하는지, 민감한 데이터인지**를 같이 보는 것이다.

## localStorage와 sessionStorage

브라우저 저장소라고 하면 가장 먼저 `localStorage`와 `sessionStorage`가 떠오른다.  
둘 다 Web Storage API에 속하고, JavaScript로 직접 값을 넣고 꺼낼 수 있다.

겉으로 보면 비슷하지만, 실제로는 유지되는 범위가 꽤 다르다.

### localStorage

`localStorage`는 오래 남는 저장소다.  
만료 시간이 따로 있는 구조가 아니라서, 직접 지우지 않는 한 계속 남아 있는 편이다.

같은 출처(origin) 기준으로 저장되고, 브라우저를 닫았다가 다시 열어도 값이 유지된다.

그래서 이런 값들과 잘 맞는다.

- 다크모드, 언어 같은 사용자 설정
- 다시 방문했을 때도 유지되면 좋은 UI 옵션
- 비교적 오래 남아 있어도 괜찮은 값

```js
localStorage.setItem('theme', 'dark');
const theme = localStorage.getItem('theme');
```

처음엔 그냥 “브라우저 저장소 = localStorage”처럼 느껴질 수도 있는데, 실제로는 오래 남는다는 점 때문에 오히려 조심해서 써야 한다.

---

### sessionStorage

`sessionStorage`는 이름만 보면 막연하게 “세션 동안 유지되는 저장소”처럼 느껴지는데, 실제로는 **현재 탭 기준의 임시 저장소**에 더 가깝다.

새로고침은 버티지만, 탭을 닫으면 사라진다.  
그리고 같은 사이트를 새 탭으로 열면 그 탭은 또 별개의 저장 공간처럼 동작한다.

이 특성 때문에 이런 값들과 잘 맞는다.

- 다단계 폼의 현재 진행 상태
- 현재 탭에서만 잠깐 유지하면 되는 필터 값
- 새로고침 후 복구되면 좋지만 오래 남을 필요는 없는 값

```js
sessionStorage.setItem('signup-step', '2');
sessionStorage.setItem('signup-email', 'test@example.com');
```

짧게 구분하면 이 정도로 정리할 수 있다.

- `localStorage`: 오래 남아도 괜찮은 값
- `sessionStorage`: 현재 탭에서만 잠깐 필요한 값

실무에서도 이 기준이 꽤 유효하다.

## 쿠키

브라우저에 데이터를 저장하는 방식은 Web Storage만 있는 게 아니다.  
`cookie`도 있다.

쿠키 역시 브라우저에 데이터를 저장한다는 점에서는 비슷하다.  
다만 `localStorage`나 `sessionStorage`처럼 프론트엔드에서 직접 꺼내 쓰는 저장소로만 보기에는 성격이 다르다.

가장 큰 차이는 **요청 흐름에 관여할 수 있다는 점**이다.

브라우저는 조건에 맞는 쿠키를 요청에 함께 실어 보낼 수 있고,  
서버는 응답에서 `Set-Cookie` 헤더를 내려 쿠키를 저장하게 만들 수 있다.

그래서 쿠키는 단순 저장소라기보다  
브라우저와 서버 사이에서 상태를 이어주는 역할로 많이 등장한다.

예를 들어 로그인 이후 서버가 세션 ID를 쿠키로 내려주면,  
이후 요청마다 브라우저가 그 값을 함께 보내고, 서버는 그 쿠키를 보고 사용자를 식별할 수 있다.

이쯤 오면 쿠키는 단순히 “브라우저에 저장되는 값”이 아니라  
**세션, 인증, 요청 흐름과 연결되는 값**으로 보는 편이 더 자연스럽다.

### 쿠키에서 같이 봐야 하는 속성들

쿠키는 값만 저장하는 게 아니라 여러 속성과 함께 다뤄진다.

- `Expires` / `Max-Age`: 언제까지 유지할지
- `Path` / `Domain`: 어느 경로, 어느 도메인에 대해 보낼지
- `Secure`: HTTPS에서만 보낼지
- `HttpOnly`: JavaScript에서 접근하지 못하게 할지
- `SameSite`: 다른 사이트 요청에서 쿠키를 어떻게 다룰지

실무에서는 특히 `HttpOnly`, `Secure`, `SameSite`가 중요하다.  
인증 이야기가 나오면 거의 같이 따라온다고 봐도 된다.

### 왜 인증에서 쿠키가 자주 나올까

이유는 결국 보안과 연결된다.

예를 들어 `localStorage`는 쓰기 편하다.  
JavaScript로 바로 읽고 쓸 수 있고 구현도 단순하다.  
하지만 그만큼 스크립트가 접근할 수 있다는 뜻이기도 하다.  
그래서 XSS 취약점이 있으면 토큰 탈취 위험이 생길 수 있다.

반면 `HttpOnly` 쿠키는 JavaScript에서 직접 읽을 수 없다.  
이 차이 때문에 인증 구조를 설계할 때 쿠키가 자주 언급된다.

물론 쿠키라고 해서 무조건 안전한 건 아니다.  
쿠키를 쓰면 CSRF 같은 다른 보안 이슈도 같이 봐야 한다.

결국  
**토큰을 어디에 저장할까**라는 질문은  
단순히 편한 저장소를 고르는 문제가 아니라, 어떤 공격에 어떻게 대응할지를 포함한 설계 문제에 더 가깝다.

## 실제로는 어떻게 구분해서 쓸까

실제로는 아래처럼 나눠 생각하면 크게 어긋나지 않는다.

### `localStorage`가 잘 맞는 경우

- 다크모드, 언어 설정
- 다시 방문해도 유지되면 좋은 UI 옵션
- 민감하지 않고, 오래 남아 있어도 괜찮은 값

**지속성**이 있으면서, **민감하지 않은 정보**가 핵심이다.

### `sessionStorage`가 잘 맞는 경우

- 현재 탭에서만 유지하고 싶은 상태
- 작성 중인 폼의 중간 단계
- 새로고침 복구는 필요하지만, 탭 종료 후까지 남을 필요는 없는 값

핵심은 **탭 단위 임시 상태**다.

### 쿠키가 잘 맞는 경우

- 세션 ID
- 서버와 함께 관리해야 하는 인증 관련 값
- 요청과 함께 상태가 전달되어야 하는 경우

즉, 단순 저장보다 **서버와의 흐름**이 중요한 데이터에서 더 자주 고려된다.

---

그럼 로그인 토큰은 어디에 두는 게 맞을까?

이건 하나로 딱 잘라 말하기보다는, 어떤 인증 구조를 택했는지를 같이 봐야 한다.

보통 많이 나오는 방향은 이렇다.

- access token은 메모리에서 관리
- refresh token은 `HttpOnly` 쿠키에 저장
- 혹은 서버 세션 기반으로 관리

이유는 단순하다.  
구현만 보면 쉬운 선택지가 있어도, 인증은 결국 보안과 트레이드오프를 같이 봐야 하기 때문이다.

## 간단한 예시

### 1) 다크모드 저장

이건 `localStorage`와 잘 맞는다.  
브라우저를 닫았다가 다시 열어도 유지되면 좋기 때문이다.

```js
localStorage.setItem('theme', 'dark');

const theme = localStorage.getItem('theme');
```

---

### 2) 회원가입 단계 저장

회원가입이 3단계라고 해보자.  
새로고침했을 때는 진행 상태가 복구되면 좋지만, 다음날 다시 왔을 때까지 남아 있을 필요는 없을 수 있다.

이럴 때는 `sessionStorage`가 더 자연스럽다.

```js
sessionStorage.setItem('signup-step', '2');
sessionStorage.setItem('signup-email', 'test@example.com');
```

---

### 3) 객체 저장

`localStorage`와 `sessionStorage`는 문자열 기반이라 객체를 그대로 넣을 수는 없다.

```js
const user = { name: 'donghun', role: 'user' };

localStorage.setItem('user', JSON.stringify(user));

const parsedUser = JSON.parse(localStorage.getItem('user') ?? 'null');
```

처음엔 사소해 보이지만, 은근 자주 놓치는 부분이다.  
나중에 값을 꺼냈는데 이상한 문자열이 나오거나 파싱 에러가 나는 이유가 여기서 시작되는 경우가 많다.

---

### 4) 인증과 쿠키

로그인 이후 서버가 세션 쿠키를 내려준다고 하면, 브라우저는 이후 요청에서 해당 쿠키를 자동으로 포함할 수 있다.

이 구조에서는 프론트엔드가 매번 직접 인증 헤더를 붙이는 방식과는 흐름이 달라진다.  
그래서 쿠키를 이해하면 저장소 개념뿐 아니라, 브라우저 요청 흐름과 인증 구조도 같이 보이기 시작한다.

---

## 정리

- 브라우저에는 데이터를 저장하는 여러 방식이 있다.
- `localStorage`는 오래 남는 값에 더 잘 맞는다.
- `sessionStorage`는 현재 탭에서만 필요한 임시 상태에 가깝다.
- 쿠키는 요청 흐름과 연결될 수 있어서 세션, 인증과 자주 묶인다.
- 특히 쿠키는 `HttpOnly`, `Secure`, `SameSite` 같은 속성까지 같이 봐야 한다.
- 저장소 선택은 단순 구현 편의보다 유지 범위, 요청 흐름, 보안을 기준으로 해야 한다.

처음엔 셋 다 비슷해 보이지만, 실제 상황에 대입해 보면 역할이 꽤 분명하게 갈린다.  
결국 중요한 건 “저장할 수 있느냐”보다 **왜 이 저장소를 선택했는지 설명할 수 있느냐**인 것 같다.
