💡 **핵심 요약**
- TypeScript 5.x 시리즈는 "검증과 추론은 다른 일"이라는 인식을 도구로 풀어낸 시기다. `satisfies` (4.9), `const` 타입 매개변수 (5.0), `NoInfer` (5.4)가 이 흐름의 대표 기능이다.
- 실용성은 셋이 다르다. `satisfies`는 일상에서 쓸 일이 많고, 나머지 둘은 주로 라이브러리 작성자가 쓴다.
- 일상에서 직접 쓰지 않더라도, 라이브러리 타입을 읽다 마주쳤을 때 의미를 알아볼 수 있는 정도면 충분하다.

---

## "5.x의 변화"라는 묶음

TypeScript 5.x 시리즈에서 추가된 기능은 꽤 많다. 그중에서도 한 흐름으로 묶이는 게 있다.

- 4.9 `satisfies` 연산자
- 5.0 `const` 타입 매개변수
- 5.4 `NoInfer<T>`

위 세 도구는 모두 새로운 타입을 만드는 도구가 아니라, **추론이 어디까지 일어나야 하는지를 개발자가 명시할 수 있게** 해주는 도구다. 한 줄로 묶으면 **"검증과 추론은 다른 일"** 이라는 인식이 점점 더 정교하게 도구화된 흐름이다.

먼저 말해두자면 이번 개념은 이전 [유틸리티 타입](ttps://velog.io/@dh82680/TypeScript-유틸리티-타입과-조건부-타입-FE-개념-탐구-035) 글에서와 같이 우리가 개발하며 자주 사용하게 될 만한 것들은 아니다. `satisfies`는 종종 접할 수도 있지만, 나머지 둘은 주로 라이브러리 작성자가 쓰는 도구다.

## satisfies — 타입 어노테이션의 부작용을 떼어내는 도구

### 문제 상황

설정값 객체에 타입을 붙이려는 흔한 패턴부터 보자.

```ts
type Config = Record<string, string | number[]>;

const config: Config = {
  timeout: 3000,
  hosts: ["a.com", "b.com"],
};

config.timeout.toFixed(2); // 에러: 'toFixed'가 'string | number[]'에 없음
```

`Config`로 모양은 검증됐다. 그런데 `config.timeout`이 `number`라는 사실이 사라졌다. 타입 어노테이션이 모든 필드를 `string | number[]`로 깎아버렸기 때문이다.

타입 어노테이션은 두 가지 일을 한 번에 한다.

```ts
const x: SomeType = ...;
//      ^^^^^^^^^
//      ① 할당 가능성 검증
//      ② x의 타입을 SomeType으로 고정
```

문제는 ②가 ①의 부수 효과로 따라온다는 것이다. **검증만 하고 싶을 때도 타입이 강제로 넓어진다.**

### satisfies가 하는 일

`satisfies`는 ①만 떼어낸 연산자다. 표현식 뒤에 붙어, 그 표현식이 특정 타입에 할당 가능한지 검사한 뒤, **추론된 좁은 타입은 그대로 유지**한다.

```ts
const config = {
  timeout: 3000,
  hosts: ["a.com", "b.com"],
} satisfies Config;

config.timeout.toFixed(2);     // OK — timeout은 number로 추론됨
config.hosts[0].toUpperCase(); // OK — hosts는 string[]로 추론됨
```

검증은 어노테이션과 똑같이 작동한다. 오타가 있거나 타입이 맞지 않으면 에러가 난다.

```ts
const wrong = {
  timeout: "3000",         // 에러: string은 string | number[]에 할당 불가
  hosts: ["a.com"],
} satisfies Config;
```

### 언제 쓰지?

사용되는 자리는 대체로 정해져 있다.

- **설정 객체**: 위처럼 `Record`나 `union` 타입으로 검증하지만 키별 구체 타입은 살리고 싶을 때
- **as const 대신**: 리터럴 타입을 유지하면서도 모양 검증을 하고 싶을 때
- **객체 리터럴의 오타 방지**: 키 이름의 typo를 컴파일러에게 잡게 하면서도 값 타입은 추론되게

마지막 경우가 4.9 릴리즈 노트의 원래 예시다.

```ts
type Palette = Record<"red" | "green" | "blue", string | [number, number, number]>;

const palette = {
  red: [255, 0, 0],
  green: "#00ff00",
  bleu: [0, 0, 255], // 에러: 'bleu'는 Palette의 키가 아님
} satisfies Palette;
```

타입 어노테이션을 썼다면 같은 에러가 나면서 `palette.red`도 `string | [number, number, number]`로 깎였을 것이다. `satisfies`는 검증은 가져가고 추론은 보존한다.

> ⚠️ **`satisfies`는 `as`(타입 단언)와 다르다.**
> `as`는 검사를 우회해 컴파일러를 속이는 도구다. `satisfies`는 검사를 강화하는 도구다. 방향이 정반대다.

## const 타입 매개변수 — as const를 함수 쪽에서 강제하기

여기서부터는 라이브러리 작성자 영역에 가깝다. 일상 코드에서 직접 쓸 일은 많지 않지만, 어떤 문제를 푸는 도구인지는 알아두면 라이브러리 타입을 읽을 때 도움이 된다.

### 문제 상황

[#034](https://velog.io/@dh82680/TypeScript-제네릭-FE-개념-탐구-034)에서 본 제네릭 함수를 보자.

```ts
function pickOne<T>(items: T[]): T {
  return items[0];
}

const result = pickOne(["red", "green", "blue"]);
// T = string으로 추론됨. result: string
```

호출자가 원한 건 `"red" | "green" | "blue"` 같은 리터럴 유니온일 텐데, TypeScript는 그냥 `string[]`로 추론한다. 리터럴 타입을 살리려면 호출자가 `as const`를 붙여야 한다.

```ts
const result = pickOne(["red", "green", "blue"] as const);
// T = "red" | "green" | "blue". result: "red" | "green" | "blue"
```

라이브러리 함수라면 이 부담을 매번 호출자에게 떠넘기는 셈이다.

### const 타입 매개변수가 하는 일

5.0부터는 타입 매개변수 앞에 `const`를 붙여서, **호출자가 `as const`를 안 써도 좁게 추론되게** 만들 수 있다.

```ts
function pickOne<const T>(items: readonly T[]): T {
  return items[0];
}

const result = pickOne(["red", "green", "blue"]);
// T = "red" | "green" | "blue"
```

> 📚 [TypeScript 5.0 Release Notes — const Type Parameters](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-0.html#const-type-parameters)

### 적용 범위

`const` 타입 매개변수가 영향을 미치는 건 **호출 시점에 직접 작성된 리터럴 표현식**이다. 변수에 담아 넘기면 효과가 사라진다.

```ts
const items = ["red", "green", "blue"]; // 이미 string[]로 추론됨
pickOne(items);                          // T = string
```

이건 명세에 가까운 동작이다. `as const`가 표현식 뒤에 붙는 것처럼, `const` 타입 매개변수도 **호출 인자로 작성된 리터럴**의 컨텍스추얼 타입에만 작동한다.

## NoInfer — 추론에서 특정 자리를 빼는 도구

여기서부터는 더 좁은 자리다. 라이브러리 작성자가 한 인자에서만 타입을 결정하고 싶을 때 쓰는 도구다.

### 문제 상황

제네릭 함수에서 두 매개변수가 같은 타입 매개변수를 공유하는 경우를 보자.

```ts
function createStreetLight<C extends string>(
  colors: C[],
  defaultColor?: C
) { /* ... */ }
```

의도는 명확하다. `defaultColor`는 `colors` 안의 값 중 하나여야 한다. 그런데 호출해보면 의도대로 안 된다.

```ts
createStreetLight(["red", "yellow", "green"], "blue");
// 에러가 안 남
```

이유는 TypeScript의 추론 방식 때문이다. 같은 타입 매개변수가 여러 자리에 등장하면, **모든 자리에서 추론 후보를 모은 다음 합집합**을 만든다.

```
colors에서:        C 후보 → "red" | "yellow" | "green"
defaultColor에서:  C 후보 → "blue"
최종 C:           "red" | "yellow" | "green" | "blue"
```

`defaultColor`가 자기 자신도 `C`의 추론에 기여해버려서 타입을 넓혀버렸다. 결과적으로 `"blue"`가 유니온 안에 들어와 에러가 안 난다.

### NoInfer가 하는 일

5.4부터 추가된 `NoInfer<T>`는 그 자리를 **추론 후보에서 제외**한다.

```ts
function createStreetLight<C extends string>(
  colors: C[],
  defaultColor?: NoInfer<C>
) { /* ... */ }

createStreetLight(["red", "yellow", "green"], "blue");
//                                            ~~~~~~
// 에러: '"blue"'는 '"red" | "yellow" | "green" | undefined'에 할당 불가
```

`colors` 자리에서만 `C`가 결정되고, `defaultColor` 자리에서는 검증만 일어난다. `colors`가 `C`를 정하고 `defaultColor`는 그 `C`에 맞춰지는 **단방향 의존**이 그대로 표현된다.

> ⚠️ **`NoInfer`는 "그 자리의 타입 검사를 끄는 것"이 아니다.**
> 추론에 기여하지 않을 뿐, 할당 가능성 검사는 그대로 작동한다. 그래서 `"blue"`가 유니온에 안 들어맞는다는 에러가 정확히 발생한다.

## 세 도구의 위치

셋을 한 자리에 두고 보면 작동하는 단계가 다르다.

| 도구 | 단계 | 한 줄 |
| --- | --- | --- |
| `satisfies` | 표현식 | 검증만, 추론은 그대로 |
| `const` 타입 매개변수 | 함수 호출 | `as const`를 함수 쪽에서 강제 |
| `NoInfer<T>` | 제네릭 추론 | 이 자리는 추론 후보에서 빼라 |

공통점은 셋 다 **새 타입을 만들거나 표현력을 늘리는 도구가 아니라는 것**이다. 추론이 어디까지 작동하고 어디서 멈춰야 하는지를 개발자가 명시하는 도구다. 타입 시스템이 더 정교해지면서 "검증과 추론은 다른 일"이라는 인식을 표현할 도구들이 하나씩 갖춰진 흐름이다.

## 정리

이번 개념은 [#035](https://velog.io/@dh82680/TypeScript-유틸리티-타입과-조건부-타입-FE-개념-탐구-035)의 `infer`처럼, **만들 줄 알기보다 읽을 줄 아는 것**이 먼저인 개념들이다. `<const T>`나 `NoInfer<C>` 같은 표기가 라이브러리 시그니처에서 보였을 때, "이 자리에서 추론이 이렇게 일어나도록 설계해놨구나"를 읽어낼 수 있다면 충분하다.

5.x 시리즈가 보여주는 방향은 분명하다. 새로운 타입을 더 만들기보다, **이미 있는 추론이 더 정확하게 일어나도록 도구를 깎아나가는** 쪽이다.
