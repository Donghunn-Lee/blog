💡 **핵심 요약**

- 성능 최적화는 기법을 고르는 일이 아니라 **무엇을 측정하고 무엇을 고칠지** 결정하는 일이다. 측정 없이 시작하는 최적화는 거의 항상 빗나간다.
- 성능 문제는 크게 **네트워크(다운로드) / 렌더링(첫 화면) / 런타임(인터랙션)** 세 단계에서 발생한다. 각 단계는 다른 도구로 푼다 — `memo`로 LCP를 좋게 만들 수 없고, Code Splitting으로 인터랙션이 빨라지지 않는다.
- 측정의 기준은 "총 시간"이 아니라 **사용자가 체감하는 단계별 지표(Core Web Vitals)** 다. 같은 3초라도 0초에 빈 화면이다가 3초에 완성되는 것과, 1초에 윤곽이 보이고 3초에 완성되는 것은 완전히 다른 경험이다.

## memo를 둘러도 여전히 느리다?

[#025 React 렌더링 최적화](https://velog.io/@dh82680/React-렌더링-최적화-FE-개념-탐구-025)에서 다룬 적이 있다. `memo`, `useMemo`, `useCallback`을 모든 컴포넌트에 두른다고 빨라지지 않는다. 비교 비용 때문에 오히려 느려질 수도 있고, 측정해보면 애초에 그곳이 병목이 아닌 경우가 대부분이다.

그런데 한 발 더 나아가면 더 큰 문제가 있다. **이 도구들로는 절대 좋아지지 않는 성능 지표가 따로 있다**는 점이다.

- 첫 화면이 늦게 보이는 문제 — `memo`는 손도 못 댄다
- 번들이 너무 커서 다운로드가 오래 걸리는 문제 — `useMemo`로는 해결할 수 없다
- 이미지가 늦게 뜨는 문제 — `useCallback`은 무관하다

성능 최적화를 React 차원에서만 생각하면 이 영역을 통째로 놓친다. 그리고 실제 사용자가 체감하는 성능은 대부분 이쪽에서 결정된다. 사용자는 "리렌더링이 한 번 더 일어나는 것"보다 "첫 화면이 보이기까지 4초가 걸리는 것"을 훨씬 강하게 느낀다.

이 글의 출발점은 이거다. **성능 최적화는 어떤 도구를 쓸지가 아니라, 어디를 측정하고 어디를 고칠지의 문제다.**

---

## 측정이 먼저라는 말의 진짜 의미

과거엔 잘 몰랐지만, 이제는 정말성능 최적화를 다룰 때 거의 모든 글이 "측정이 먼저"라고 말한다. 그런데 이 말이 왜 강조되는지를 짚지 않으면 그냥 격언처럼 흘려보내게 된다.

측정 없이 시작하는 최적화에는 구조적인 문제가 있다.

**첫째, 대부분의 추측은 빗나간다.**  
"리스트가 많아서 느린 것 같다"고 짐작해서 가상화를 도입했는데, 정작 진짜 병목은 페이지 진입 시 받아오는 거대한 JS 번들이었다는 식의 일이 흔하다. 사람의 직관은 "어디가 느린가"에 대해 생각보다 신뢰할 만하지 않다.

**둘째, 최적화는 공짜가 아니다.**  
`memo`는 비교 비용을 더하고, Code Splitting은 추가 네트워크 요청을 만들고, `useMemo`는 메모리를 쓴다. 잘못된 곳에 적용하면 코드 복잡도만 올라가고 성능은 그대로거나 더 나빠진다.

**셋째, 측정해야 효과를 검증할 수 있다.**  
"적용하니 좀 빨라진 것 같다"는 가장 위험한 결론이다. 같은 페이지를 재방문하면 캐시 때문에 빨라진 것일 수도 있고, 네트워크 상태가 좋아진 것일 수도 있다. 수치 없이 "좋아졌다"는 판단은 거의 의미가 없다.

> 💡 **"측정이 먼저"의 진짜 의미는 "수치 기반 의사결정"이다.**  
> 어디가 느린지 측정하지 않은 채로 도구를 적용하는 건, 아픈 데를 정하지 않고 약을 먹는 것과 같다.

## 무엇을 측정할 것인가 — Core Web Vitals

성능을 측정하려면 기준이 있어야 한다. 지금 사실상 표준은 구글이 정의한 **Core Web Vitals**다.

| 지표 | 의미 | 좋은 값 |
|------|------|---------|
| **LCP** (Largest Contentful Paint) | 가장 큰 콘텐츠가 화면에 그려지는 시점 | 2.5초 이하 |
| **INP** (Interaction to Next Paint) | 사용자 입력에 대한 반응 속도 | 200ms 이하 |
| **CLS** (Cumulative Layout Shift) | 레이아웃이 의도치 않게 밀리는 정도 | 0.1 이하 |

Core Web Vitals가 의미 있는 이유는, 단순히 "총 로딩 시간"이 아니라 **사용자가 체감하는 단계별 경험**을 잡기 때문이다.

- **LCP** — "내가 기다리는 그 콘텐츠가 언제 보이지?"
- **INP** — "버튼을 눌렀는데 왜 안 반응하지?"
- **CLS** — "내가 누르려던 버튼이 왜 갑자기 옮겨가지?"

각각이 측정하는 영역이 다르다는 점이 중요하다. **LCP가 나쁜 것과 INP가 나쁜 것은 완전히 다른 문제고, 다른 도구로 푼다.** LCP는 첫 화면을 그리는 데 필요한 리소스의 다운로드/렌더링 비용 문제고, INP는 JS 실행이 메인 스레드를 점유하는 문제다.

> **참고:** 예전에는 INP 자리에 FID(First Input Delay)가 있었다. FID는 첫 입력에 대한 지연만 봤기 때문에 페이지 전체 생애의 반응성을 잡지 못했고, 2024년 3월에 INP로 대체되었다. INP는 페이지가 살아있는 동안의 모든 인터랙션을 본다.

## 성능 문제는 세 단계에서 생긴다

기법을 정리하기 전에, 성능 문제가 어디에서 생기는지를 분류하는 게 먼저다. 이 분류가 곧 "어떤 도구를 쓸지"의 지도가 된다.

```
[1] 네트워크 단계      서버에서 리소스를 받아오는 동안
    ↓                 → 큰 번들, 무거운 이미지, 많은 요청
[2] 렌더링 단계        받은 리소스를 파싱·실행해 첫 화면을 그릴 때까지
    ↓                 → JS 파싱 시간, 렌더링 블로킹, 폰트 로딩
[3] 런타임 단계        첫 화면이 그려진 후 사용자와 상호작용하는 동안
                      → 불필요한 리렌더링, 무거운 연산, 메모리 누수
```

각 단계가 만드는 문제는 다르고, 영향을 주는 지표도 다르다.

| 단계 | 주로 영향 받는 지표 | 대표적인 해결 도구 |
|------|--------------------|--------------------|
| 네트워크 | LCP | Code Splitting, 이미지 최적화, 압축 |
| 렌더링 | LCP, FCP | SSR/SSG, Critical CSS, 폰트 최적화 |
| 런타임 | INP | memo, 가상화, 디바운스/쓰로틀 |

> ⚠️ **단계가 다르면 도구도 다르다.**  
> 네트워크 단계의 문제(큰 번들)를 `memo`로 풀 수 없고, 런타임 단계의 문제(과도한 리렌더링)를 Code Splitting으로 풀 수 없다. 이걸 섞어서 접근하면 시간만 쓰고 지표는 그대로다.

이제 단계별로 짧게 정리한다.

## 네트워크 단계 — 번들과 리소스

가장 흔하고 효과가 큰 영역이다. 사용자에게 코드와 리소스를 전달하는 시간 자체를 줄이는 일이다.

**Code Splitting**

번들을 통째로 다운로드하는 대신, 라우트나 기능 단위로 잘라서 필요할 때 받아오는 방식. 직전 글 [#028 SPA 동작 원리](https://velog.io/@dh82680/SPA-동작-원리-FE-개념-탐구-028)에서 먼저 다룬 그 기법이다.

```jsx
const About = lazy(() => import('./pages/About'));
```

라우트 단위가 가장 무난한 출발점이다. 너무 잘게 쪼개면 청크가 늘어나면서 요청 오버헤드가 누적되고, 화면 곳곳에 로딩 스피너가 뜨면서 UX가 오히려 나빠진다.

**Tree Shaking**

빌드 도구가 정적 분석으로 사용하지 않는 코드를 제거하는 기법. ES Module의 `import`/`export`는 정적이라 어떤 export가 안 쓰이는지 빌드 시점에 알 수 있고, 그래서 제거가 가능하다. CommonJS의 `require`는 동적이라 안 된다. 라이브러리에서 일부 함수만 가져다 쓸 때 `import { debounce } from 'lodash'`와 `import _ from 'lodash'`의 번들 크기가 크게 차이 나는 게 이 때문이다.

**이미지 최적화**

LCP의 가장 큰 변수가 보통 이미지다. 단계적으로 정리하면 이렇다.

1. **포맷** — JPEG/PNG 대신 WebP/AVIF (압축률이 훨씬 좋음)
2. **반응형** — `srcset`으로 디바이스별 적절한 크기 제공 (모바일에 4K 이미지를 내려보내지 않기)
3. **지연 로딩** — `loading="lazy"`로 뷰포트 바깥 이미지는 나중에 로드
4. **사이즈 명시** — `width`/`height` 속성으로 CLS 방지

Next.js의 `next/image`는 이 중 1~4를 한 번에 처리해주는 추상화다.

**압축**

서버에서 gzip/brotli 압축을 켜는 것만으로 텍스트 리소스(JS, CSS, HTML)의 크기가 70~90% 줄어든다. 보통 호스팅 서비스나 CDN에서 기본으로 활성화되어 있지만, 자체 서버라면 직접 켜야 한다.

## 렌더링 단계 — 첫 화면까지의 시간

리소스를 받은 뒤, 그것이 화면에 그려지기까지의 시간이다.

**SSR / SSG**

[#027 CSR과 SSR](https://velog.io/@dh82680/CSR과-SSR-FE-개념-탐구-027)에서 다룬 주제다. CSR은 빈 HTML을 받고 JS를 실행해야 첫 화면이 보이는 반면, SSR은 서버가 이미 콘텐츠가 채워진 HTML을 내려주기 때문에 LCP가 빨라진다. 콘텐츠가 정적이라면 SSG로 빌드 시점에 미리 만들어둘 수도 있다.

**Critical CSS**

브라우저는 CSS 다운로드/파싱이 끝나야 화면을 그릴 수 있다(렌더링 블로킹). 첫 화면에 필요한 최소한의 CSS만 인라인으로 우선 제공하면 첫 페인트가 빨라진다.

**폰트 최적화**

웹폰트가 늦게 로드되면 텍스트가 안 보이거나(FOIT) 기본 폰트로 보였다가 갑자기 바뀐다(FOUT). `font-display: swap`으로 일단 기본 폰트로라도 보여주고, 핵심 폰트는 `<link rel="preload">`로 우선순위를 높인다.

## 런타임 단계 — 인터랙션 이후

첫 화면이 그려진 다음, 사용자가 사이트와 상호작용하는 동안의 성능이다. 주로 INP와 직결된다.

**불필요한 리렌더링 줄이기**

앞서 언급했지만, #25에서 다룬 내용이 바로 이 내용이다. `memo`, `useMemo`, `useCallback`은 전부 이 런타임 영역의 도구다. 다시 강조하자면, 측정 후 병목이 있을 때만 적용하고, 도구보다 **state 위치를 잘 잡는 구조 설계가 먼저**다.

**가상화 (Virtualization)**

긴 리스트(수천~수만 개)를 그릴 때, 화면에 실제로 보이는 항목만 DOM에 만들고 나머지는 스크롤 위치에 따라 동적으로 교체하는 기법이다. DOM 노드 수 자체를 줄이는 거라 리렌더링 최적화 도구로는 해결 못 하는 영역이다. `react-window`, `@tanstack/react-virtual` 같은 라이브러리가 이 일을 한다.

**디바운스 / 쓰로틀**

[#013 Debounce와 Throttle](https://velog.io/@dh82680/Debounce와-Throttle-FE-개념-탐구-013)에서 다룬 그대로다. 검색창 입력처럼 짧은 시간에 수십 번 일어나는 이벤트를 다 처리하면 메인 스레드가 막히고 INP가 나빠진다. 호출 횟수 자체를 줄이는 게 도구다.

**무거운 연산 분리**

수백 ms 이상 걸리는 연산이 메인 스레드에서 돌면 그 시간 동안 사용자 입력이 막힌다. 정말 무거운 작업은 Web Worker로 분리하거나, 한 번에 처리하지 않고 청크로 쪼개서 처리한다(`requestIdleCallback`, React의 `useTransition`).

## Lab 데이터와 Field 데이터

마지막으로 측정에 대한 중요한 구분이 하나 있다.

**Lab 데이터**는 개발자 환경(또는 일정한 조건의 테스트 환경)에서 측정한 데이터다. Lighthouse나 Chrome DevTools의 Performance 패널이 만들어주는 수치가 여기 해당한다. 통제된 환경이라 같은 조건에서 변경 전후를 비교하기 좋다.

**Field 데이터**(RUM, Real User Monitoring)는 실제 사용자가 사이트를 쓰면서 발생하는 데이터를 수집한 것이다. Sentry, Datadog, 구글의 CrUX 데이터 같은 도구가 여기 해당한다.

```
Lab 데이터  → "이 변경이 효과가 있을까?" 검증
Field 데이터 → "실제로 우리 사용자들이 어떤 경험을 하고 있나?" 파악
```

둘 다 봐야 하는 이유는, 개발자 환경과 실제 사용자 환경이 많이 다르기 때문이다. 개발자는 보통 빠른 와이파이에 좋은 노트북을 쓰지만, 실제 사용자 중에는 느린 모바일 네트워크에 저사양 안드로이드를 쓰는 사람이 있다. Lab에서 LCP 1.8초가 나왔다고 안심하면 Field에서는 4초가 나오는 일이 흔하다.

> 💡 처음에는 Lab 데이터부터 시작해도 충분하다. 다만 **"이 사이트가 빠르다"는 결론은 Field 데이터로만 검증할 수 있다**는 사실은 알아두는 게 좋다.

## 헷갈리기 쉬운 부분

**① "성능 최적화 = React 최적화"가 아니다**

React 개발자가 가장 자주 빠지는 함정이다. `memo`, `useMemo`, `useCallback`은 전체 성능 영역에서 보면 **런타임 단계의 일부**일 뿐이다. 사용자가 체감하는 첫인상(LCP)에는 거의 영향이 없다.

**② Code Splitting은 무조건 좋은 게 아니다**

청크가 작아지면 다운로드 시간은 줄지만 네트워크 요청 수는 늘어난다. HTTP/2의 멀티플렉싱이 있어도 요청 자체의 오버헤드는 0이 아니고, 무엇보다 **사용자가 새 페이지로 이동할 때마다 청크를 받아야 해서 매번 짧은 로딩이 생긴다**. 라우트 단위가 무난한 출발점이고, 그 이상으로 잘게 쪼개려면 측정 근거가 있어야 한다.

**③ "성능이 좋다"는 "총 시간이 짧다"가 아니다**

같은 3초가 걸려도 0초에 빈 화면이다가 3초에 완성되는 것과, 1초에 스켈레톤이 보이고 3초에 완성되는 것은 체감이 완전히 다르다. 그래서 단순한 "총 시간"이 아니라 LCP, INP 같은 **단계별 지표**가 의미가 있고, Suspense나 스켈레톤 UI가 실제 시간을 줄이지 않으면서도 체감 성능을 바꾸는 것이다.

**④ Lighthouse 점수 100점이 목표가 아니다**

Lighthouse는 통제된 환경에서 측정한 Lab 데이터다. 점수를 높이는 데 매몰되면 실제 사용자 경험과는 동떨어진 최적화를 하게 된다. **점수는 진단 도구지, 평가 기준이 아니다.**

## 정리

성능 최적화를 한 줄로 압축하면 이렇게 된다.

> **측정 → 병목 식별 → 해당 단계에 맞는 도구 적용 → 재측정.**

기법을 외우는 것보다 중요한 건, 어떤 문제가 어느 단계에 속하는지 분류할 수 있는 시야다. LCP가 나쁘면 네트워크/렌더링 단계를 보고, INP가 나쁘면 런타임 단계를 본다. 도구는 그 분류 위에 따라온다.

`memo`를 모든 컴포넌트에 두르는 것보다 이미지 포맷을 WebP로 바꾸는 게 LCP에 더 큰 영향을 미칠 수 있고, 그 반대도 가능하다. 무엇이 더 중요한지는 측정해야만 알 수 있다.
