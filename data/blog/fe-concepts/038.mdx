💡 **핵심 요약**
- **Pages Router는 페이지 단위로 사고하고, App Router는 컴포넌트 단위로 사고한다.** 데이터 페칭, 레이아웃, 렌더링 모두 그 차이에서 갈린다.
- App Router는 Pages Router의 **페이지에 묶인 데이터 페칭, 어색한 레이아웃 공유, 비대한 클라이언트 번들, 스트리밍의 어려움**, 이 네 가지 단점을 극복하기 위해 만들어졌다.
- 새 프로젝트의 표준은 App Router로 굳어졌지만, 기존 코드베이스에 Pages Router가 여전히 많다. 두 라우터를 함께 이해해야 하는 이유다.

---

## 두 라우터를 같이 봐야 하는 이유

새 Next.js 프로젝트를 만들면 `app/`이 기본이다. 그런데 회사로 들어가면 사정이 다르다. 2022~2023년에 시작된 프로젝트들은 대부분 `pages/` 위에 올라가 있고, 그 위에 신규 기능을 얹거나 부분적으로 마이그레이션하는 상태로 운영된다.

그래서 처음에는 "App Router만 알면 되겠지" 싶다가, 실제 코드를 만나면 `getServerSideProps`와 `async` 컴포넌트가 같은 레포에 공존하는 풍경을 보게 될 수 있다.

두 라우터는 단순히 폴더 이름이 다른 게 아니다.
- 데이터를 어디서 가져오는가
- 레이아웃을 어떻게 공유하는가
- 클라이언트로 무엇을 보내는가

애플리케이션을 구성하는 멘탈 모델 자체가 다르다. App Router의 결정들이 외워야 할 규칙처럼 느껴진다면, 그건 Pages Router 시절의 어려움을 모르기 때문이다. **왜 그렇게 됐는지를 알면, App Router의 모든 선택이 이유를 갖는다.**

---

## Pages Router — 페이지 단위 구조

Pages Router는 `pages/` 폴더의 파일 구조가 그대로 URL이 되는 시스템이다.

```
pages/
  index.tsx           → /
  about.tsx           → /about
  blog/
    index.tsx         → /blog
    [slug].tsx        → /blog/:slug
  _app.tsx            → 모든 페이지를 감싸는 루트
  _document.tsx       → HTML 문서 셸
```

파일 = 라우트 = 페이지 컴포넌트. 직관적이고 단순하다. 데이터는 페이지에서 export하는 특수 함수가 가져온다.

```tsx
// pages/blog/[slug].tsx
export async function getServerSideProps({ params }) {
  const post = await fetchPost(params.slug);
  return { props: { post } };
}

export default function BlogPost({ post }) {
  return <article>{post.title}</article>;
}
```

서버는 요청이 오면 `getServerSideProps`를 실행해 데이터를 만들고, 그 결과를 props로 넘겨서 페이지 컴포넌트를 HTML로 렌더링한 뒤 클라이언트에 보낸다. 클라이언트는 받은 HTML 위에 hydration을 얹어 React 앱으로 살린다.

깔끔한 모델이다. 다만 이 모델은 네 가지 단점을 가지고 있었다.

---

## Pages Router의 네 가지 문제

### 1. 데이터 페칭이 페이지에 묶여 있다

`getServerSideProps`는 **페이지 컴포넌트에서만** export할 수 있다. 데이터를 가져오는 단위가 "페이지"로 고정된다는 뜻이다.

한 페이지에 여러 독립적인 영역이 있다고 해보자. 사용자 정보, 추천 글, 최근 댓글 — 각자 다른 API를 부른다. Pages Router에서는 이 셋을 페이지 최상단의 `getServerSideProps` 하나에서 모두 가져와야 한다.

```tsx
export async function getServerSideProps() {
  // 세 요청이 모두 끝나야 페이지가 렌더링된다
  const [user, posts, comments] = await Promise.all([
    fetchUser(),
    fetchRecommended(),
    fetchComments(),
  ]);
  return { props: { user, posts, comments } };
}
```

가장 느린 요청 하나가 페이지 전체를 막는다. 그리고 데이터 로직이 UI에서 멀리 떨어진 페이지 최상단으로 끌려 올라간다. 컴포넌트를 다른 페이지로 옮기면, 데이터 페칭도 같이 옮겨야 한다. **데이터와 그 데이터를 쓰는 컴포넌트가 분리되어 있는 것이다.**

### 2. 레이아웃이 한 층이다

여러 페이지가 같은 사이드바, 같은 헤더를 공유하는 대시보드를 떠올려보자. Pages Router에는 **중첩 레이아웃이라는 개념이 없다.**

`_app.tsx`가 모든 페이지를 감싸는 단 하나의 루트는 있지만, "이 폴더 아래 페이지들만 공유하는 레이아웃"을 자연스럽게 만들 방법이 없다. 우회책은 페이지마다 `<Layout>`으로 감싸거나, `getLayout` 패턴을 쓰는 것이다.

```tsx
// 흔히 쓰던 우회책
BlogPost.getLayout = (page) => <BlogLayout>{page}</BlogLayout>;
```

작동은 하지만 컨벤션일 뿐, 프레임워크 차원의 1급 기능은 아니다. 더 큰 문제는 **페이지 이동 시 레이아웃이 매번 다시 마운트된다**는 점이다. `/dashboard/overview`에서 `/dashboard/settings`로 이동하면 사이드바도 처음부터 렌더링된다. 펼쳐둔 메뉴, 스크롤 위치 같은 상태가 라우트마다 초기화된다.

### 3. 클라이언트로 보내는 JavaScript가 너무 많다

Pages Router에서는 페이지 컴포넌트와 그 트리 전체가 클라이언트 번들에 실린다. 마크다운 파서, 날짜 포매팅 라이브러리, 차트 라이브러리 — 사용자가 화면에서 상호작용할 일이 없는 코드까지 전부.

`getServerSideProps`가 서버에서 실행되는 건 맞다. 하지만 렌더링 자체는 클라이언트에서 한 번 더 돌아간다(hydration). 그래서 **컴포넌트 코드는 결국 클라이언트로 가야만 한다.**

### 4. 스트리밍과 부분 로딩이 어렵다

페이지 전체가 하나의 단위이기 때문에, "사용자 정보는 빨리 보여주고 추천 글은 천천히 채워 넣는다" 같은 점진적 렌더링이 자연스럽지 않다. 가능은 하지만 클라이언트 사이드에서 `useEffect`와 로딩 스피너를 직접 짜야 한다.

---

> 💡 **이 네 가지 문제의 공통 원인은 하나다.**
> "단위가 너무 크다." Pages Router는 페이지를 최소 단위로 다루는데, 실제 UI는 그보다 더 잘게 쪼개진 단위로 동작한다.

## App Router — 컴포넌트 단위 구조

App Router는 [#021 React의 렌더링](/blog/fe-concepts/021/)에서 본 클라이언트 렌더링 모델 위에, **React Server Components(RSC)** 라는 새 빌딩 블록을 얹은 시스템이다.

```
app/
  page.tsx            → /
  about/
    page.tsx          → /about
  blog/
    page.tsx          → /blog
    [slug]/
      page.tsx        → /blog/:slug
      loading.tsx     → 로딩 UI
      error.tsx       → 에러 UI
  layout.tsx          → 모든 라우트를 감싸는 루트 레이아웃
```

폴더가 라우트가 되고, 폴더 안의 **특수 파일** (`page`, `layout`, `loading`, `error`)이 각각의 역할을 맡는다. 파일 이름이 곧 컨벤션이고, 그 컨벤션이 프레임워크의 기능과 1:1로 매핑된다.

처음에 App Router는 Pages Router의 네 가지 단점을 해소하기 위해 만들어 졌다고 했다. 그렇다면 어떻게 해결한 것일까?

---

### 1. 데이터 페칭이 컴포넌트에 붙는다

서버 컴포넌트는 `async` 함수일 수 있다. 즉 **데이터가 필요한 컴포넌트가 직접 데이터를 가져온다.**

```tsx
async function UserProfile() {
  const user = await fetchUser();
  return <div>{user.name}</div>;
}

async function RecommendedPosts() {
  const posts = await fetchRecommended();
  return <PostList posts={posts} />;
}

export default function Page() {
  return (
    <>
      <UserProfile />
      <RecommendedPosts />
    </>
  );
}
```

데이터 로직과 UI가 같은 자리에 있다. `UserProfile`을 다른 페이지로 옮기면 데이터 페칭도 따라간다. Pages Router에서 `getServerSideProps`가 페이지 최상단으로 끌려 올라가던 것과 반대다.

### 2. 중첩 레이아웃이 1급 시민이다

App Router에선 중첩 레이아웃이 프레임워크 차원에서 정식으로 지원된다. 각 폴더의 `layout.tsx`가 그 폴더 아래의 모든 라우트를 감싸며, **라우트 이동 시 공통 레이아웃은 다시 마운트되지 않는다.**

```
app/
  layout.tsx              → 전체 루트
  dashboard/
    layout.tsx            → 대시보드 사이드바 (이동해도 유지됨)
    overview/page.tsx
    settings/page.tsx
```

`/dashboard/overview` ↔ `/dashboard/settings`로 이동해도 `dashboard/layout.tsx`는 그대로다. 사이드바에 펼쳐둔 메뉴, 스크롤 위치가 보존된다.

### 3. 기본이 서버 컴포넌트다 — 클라이언트 번들이 줄어든다

App Router의 모든 컴포넌트는 **기본값이 서버 컴포넌트**다. 서버 컴포넌트는 서버에서만 실행되고, 결과물만 클라이언트로 간다. **컴포넌트 코드 자체가 클라이언트 번들에 포함되지 않는다.**

상호작용이 필요한 부분에만 `"use client"`를 붙여 클라이언트 컴포넌트로 만든다.

```tsx
"use client";

import { useState } from "react";

export function LikeButton() {
  const [liked, setLiked] = useState(false);
  return <button onClick={() => setLiked(!liked)}>...</button>;
}
```

이 모델은 "기본은 서버, 필요할 때만 클라이언트"라는 방향 전환이다. Pages Router의 "페이지 전체가 클라이언트로 간다"와 정반대다.

> ⚠️ **`"use client"`는 "이 컴포넌트는 CSR만 한다"가 아니다.**
> 클라이언트 컴포넌트도 서버에서 한 번 HTML로 렌더링되고, 클라이언트에서 hydration된다. `"use client"`는 "이 컴포넌트는 클라이언트에서도 실행된다(상호작용 가능하다)"는 뜻이다.

### 4. Suspense 기반 스트리밍이 빌트인이다

폴더에 `loading.tsx`를 만들면 그 라우트 세그먼트가 자동으로 Suspense 경계로 감싸진다. 빠른 부분은 먼저 보내고, 느린 부분은 준비되는 대로 흘려보낸다. 이 동작이 프레임워크 차원에서 기본 제공된다.

## 한눈에 비교

| 항목 | Pages Router | App Router |
| --- | --- | --- |
| 폴더 | `pages/` | `app/` |
| 라우트 단위 | 파일 | 폴더 + 특수 파일 |
| 데이터 페칭 | `getServerSideProps` / `getStaticProps` | 컴포넌트에서 직접 `await` |
| 페칭 단위 | 페이지 | 컴포넌트 |
| 중첩 레이아웃 | 우회 (`getLayout` 패턴) | 1급 (`layout.tsx`) |
| 라우트 이동 시 레이아웃 | 다시 마운트 | 유지 |
| 기본 컴포넌트 | 클라이언트 | 서버 (RSC) |
| 스트리밍 | 직접 구현 | `loading.tsx` + Suspense |
| React 신기능 | 프로젝트 설치 버전 따름 | canary 내장, 신기능 먼저 받음 |

마지막 줄이 특히 결정적이다. 공식 문서에 따르면 App Router는 React canary 릴리스를 내장해 새 React 기능을 먼저 받고, Pages Router는 프로젝트에 설치된 React 버전을 그대로 사용한다. **Server Components, Server Actions 같은 신기능이 App Router에서만 제대로 동작하는 구조적 이유다.**

## 헷갈리기 쉬운 부분

**"App Router를 쓰면 Pages Router를 못 쓴다."**
같은 프로젝트에서 공존할 수 있다. `pages/`와 `app/` 폴더를 함께 두면 Next.js가 알아서 라우팅한다. 같은 경로에서 충돌하면 App Router가 우선이다. 점진적 마이그레이션을 위한 의도된 설계다.

**"App Router가 무조건 더 빠르다."**
상황에 따라 다르다. 클라이언트 번들이 줄어드는 건 사실이지만, RSC payload 직렬화·전송, 서버 부하, 스트리밍 처리 비용이 새로 생긴다. 작은 정적 페이지라면 Pages Router(또는 SSG)가 단순하고 충분히 빠르다. App Router의 이점은 **데이터가 많이 얽힌 동적 페이지, 여러 영역이 독립적으로 로딩되는 페이지**에서 두드러진다.

**"App Router는 SSR이고 Pages Router는 CSR이다."**
둘 다 SSR / SSG / CSR을 지원한다. [#027 CSR과 SSR](/blog/fe-concepts/027/)에서 본 모델은 양쪽 다 가능하다. 차이는 **무엇이 기본값이고 어떻게 표현하는가**다. Pages Router는 페이지 단위로 모드를 고르고, App Router는 컴포넌트·세그먼트 단위로 더 세밀하게 제어한다.

---

## 그래서 둘 중 무엇을 쓸까

> **새 프로젝트 → App Router**
> **기존 Pages Router 프로젝트 → 유지 또는 점진적 마이그레이션**
> **작은 정적 사이트, 단순 마케팅 페이지 → Pages Router도 합리적**

공식 문서는 새 App Router로의 마이그레이션을 권장하지만, "Pages Router는 끝났다"는 입장은 아니다. Pages Router는 여전히 공식적으로 지원되고, 새 릴리스에서도 개선이 이어진다.

다만 방향성은 분명하다. **새 React 기능은 App Router 위에서 먼저 검증되고, 새 Next.js 기능도 App Router에 우선 들어간다.** 시간이 갈수록 두 라우터 사이의 기능 격차는 벌어진다. 새 프로젝트라면 굳이 Pages Router를 고를 이유는 거의 없다.

---

## 정리

App Router는 갑자기 등장한 게 아니다. **Pages Router가 "페이지 단위"라는 한계 안에서 풀지 못한 네 가지 문제** — 페이지에 묶인 데이터 페칭, 어색한 레이아웃 공유, 비대한 클라이언트 번들, 어려운 스트리밍 — 를 풀기 위해, React Server Components라는 새 빌딩 블록 위에 다시 쌓아 올린 시스템이다.

`"use client"` 경계가 왜 필요한지, 폴더마다 `layout.tsx`를 두는 게 왜 자연스러운지, `async` 컴포넌트가 왜 가능한지 — 모든 결정이 "단위를 페이지에서 컴포넌트로 옮긴다"는 한 가지 방향성에서 나온다.

> **Pages Router는 페이지 단위로 사고하고, App Router는 컴포넌트 단위로 사고한다.**

이 한 줄을 잡고 가면, App Router의 어떤 결정도 더 이상 외워야 할 규칙이 아니다.
