💡 **핵심 요약**

* TypeScript의 본질은 **컴파일 시점의 정적 타입 검사**다. 런타임에 검사하는 게 아니라, 코드를 실행하기 전에 타입 오류를 먼저 잡는다.
* 컴파일이 끝나면 **타입 정보는 모두 사라진다.** 결과물은 그냥 JS이고, 그래서 API 응답 같은 외부 데이터는 TS가 보호해 주지 못한다.
* TS의 진짜 가치는 "버그를 막는 것" 자체보다 **개발자가 작성한 코드 안에서의 일관성을 컴파일 시점에 검증**하는 것과, **자동완성·리팩토링 안전성**으로 IDE 경험이 바뀌는 데 있다.

## 어제까지 잘 돌던 함수가 갑자기 터질 때

```javascript
function getUserName(user) {
  return user.name.toUpperCase();
}
```

작성한 이런 함수가 어느 날 갑자기 화면을 멈춰버린다. `Cannot read properties of undefined (reading 'toUpperCase')`. 콘솔에 빨간 글자가 뜨고, 사용자는 흰 화면을 보고 있다.

원인은 단순하다. 어제까지 백엔드가 보내주던 응답에 `name`이 있었는데, 누군가 코드 수정 중 필드 이름을 `userName`으로 바꾼 것이다. 프론트엔드 코드는 그 사실을 모르고 그대로 배포됐다. **에디터는 빨간 줄을 안 그었고, 빌드는 통과했고, 배포도 됐다.** 개발자는 오류를 알 수 없었고, 사용자가 그 화면에 들어왔을 때 비로소 터진다.

리팩토링도 마찬가지다. 함수 인자 하나를 바꾸면, 그 함수를 어디서 어떻게 호출하는지 IDE가 정확히 알지 못한다. `Ctrl+F`로 텍스트 검색을 하고, 한 군데를 빼먹으면 그게 또 런타임 에러가 된다.

TypeScript는 **이런 종류의 사고를 사용자가 발견하기 전 단계로 끌어올리는 도구**다. 처음 봤을 땐 "JS에 타입 어노테이션을 더한 것" 정도로 보이지만, 실제로 다루는 문제는 한 층 더 깊다.

## TypeScript의 본질 — "정적"이라는 단어

TypeScript를 한 줄로 정의하면 이렇다.

> **JavaScript에 정적 타입 시스템을 더한 언어.**

여기서 핵심은 "타입을 적는다"가 아니라 **"정적"** 이라는 단어다.

* **동적 타입 검사** — 코드가 실제로 실행될 때, 그 값이 무엇인지 본다 (JS의 방식)
* **정적 타입 검사** — 코드를 실행하지 않고도, 소스만 분석해서 타입을 안다 (TS의 방식)

JS에서 `Cannot read properties of undefined`가 사용자 환경에서야 터지는 이유는, JS가 **그 코드가 실제로 실행되는 순간에야 `user`가 무엇인지 알 수 있기** 때문이다. TS는 이걸 컴파일 시점으로 끌어올린다. 코드를 실행하기 전에 "이 함수에는 `{ name: string }` 형태가 들어와야 한다"고 선언해두면, 컴파일러가 호출 시점마다 그게 맞는지 검사한다.

```typescript
function getUserName(user: { name: string }) {
  return user.name.toUpperCase();
}

getUserName(null);            // ❌ TS 에러
getUserName({ name: 123 });   // ❌ TS 에러
getUserName({});              // ❌ TS 에러 (name 누락)
```

도입에서 본 세 가지 런타임 에러가 **모두 코드 실행 전에 잡힌다.** 이게 TS가 주는 첫 번째 가치다.

## 컴파일 파이프라인

TS 코드가 실제로 실행되기까지의 흐름을 보면, "정적 검사"가 어디에서 일어나는지가 더 명확해진다.

```
.ts 파일
   ↓
[1] 파싱 (Parser) → AST 생성
   ↓
[2] 바인딩 (Binder) → 심볼 테이블, 스코프 연결
   ↓
[3] 타입 검사 (Type Checker) → 타입 오류 발견 시 에러 출력
   ↓
[4] 변환 (Emitter) → 타입 어노테이션 제거 후 JS로 출력
   ↓
.js 파일 (런타임에 실제로 실행되는 것)
```

여기서 짚어야 할 두 가지가 있다.

**첫째, 타입 검사 단계와 변환 단계가 분리되어 있다.**
TS 컴파일러(`tsc`)는 타입 에러를 발견해도 변환은 그대로 진행한다(`noEmitOnError` 옵션을 켜지 않은 한). 즉 TS는 **개발자에게 경고를 하는 도구**이지, 실행 자체를 막는 도구가 아니다. 이 분리가 다음에 짚을 "타입은 사라진다"의 기술적 근거가 된다.

**둘째, 변환 단계만 따로 떼어내서 빠르게 처리하는 도구들이 있다.**
실무에서 빌드 도구(Next.js, Vite 등)는 보통 esbuild나 swc 같은 도구로 변환만 한다. 이 도구들은 타입 검사를 하지 않고 어노테이션을 그냥 지운다(type stripping). 타입 검사는 별도로 `tsc --noEmit`이나 IDE의 언어 서버가 담당한다. 이 분리가 가능한 이유는 **타입이 런타임 동작에는 아무 영향을 주지 않기 때문**이다.

> 💡 *공식 명칭은 컴파일러이지만, TS와 JS가 같은 추상 수준의 언어라는 점에서 트랜스파일러라고 불리는 경우도 많다. 이 글에서는 공식 명칭을 따라 컴파일러로 쓴다.*

## 타입은 사라진다 — 그래서 무엇이 따라오는가

TS의 가장 자주 오해받는 지점이 여기다. 다음 코드를 컴파일하면

```typescript
function add(a: number, b: number): number {
  return a + b;
}
```

이렇게 된다.

```javascript
function add(a, b) {
  return a + b;
}
```

타입 정보가 그냥 사라진다. 그래서 런타임에는 `add("1", "2")`를 호출해도 막을 방법이 없고, 결과로 `"12"`가 반환된다. TS가 막은 건 **컴파일 시점**이고, 그 시점에 "string은 안 된다"고 경고했을 뿐이다.

이 사실이 만드는 결과는 생각보다 크다.

**1. 외부에서 들어오는 데이터는 TS가 보호하지 못한다.**

```typescript
const response = await fetch('/api/user');
const user: User = await response.json();
//          ^^^^ "이게 User 타입이다"라고 선언했을 뿐, 실제로 그런지는 검사하지 않는다

console.log(user.name.toUpperCase()); // 응답에 name이 없으면 런타임 에러
```

이 코드는 컴파일을 통과한다. 하지만 백엔드 응답이 바뀌어 `name`이 없다면, 도입에서 본 그 에러가 그대로 다시 발생한다. **TS는 자기가 보지 않은 값에 대해서는 아무것도 보장하지 않는다.**

이 영역을 다루기 위해 [Zod](https://zod.dev/), [io-ts](https://gcanti.github.io/io-ts/) 같은 **런타임 검증 라이브러리**가 따로 존재한다. 이 도구들은 응답을 받을 때 실제 값의 형태를 검사하고, 검증을 통과한 경우에만 타입이 부여된 값으로 반환한다.

**2. `as`는 TS에게 거짓말을 하는 행위다.**

```typescript
const data = JSON.parse(response) as User;
```

`as`는 "내가 이 값이 User라고 확신한다"고 컴파일러에게 선언하는 것이다. 컴파일러는 그 말을 믿고 그 뒤로는 `data`를 User로 취급한다. 거짓말이어도 통과한다.

`as`는 마지막 수단이다. 가능하면 타입 가드를 쓰거나 런타임 검증을 거쳐 자연스럽게 좁혀진 타입을 받는 게 안전하다.

> ⚠️ **"TS를 쓰면 모든 버그가 사라진다"는 흔한 오해다.**
> TS가 막아주는 건 **타입과 관련된 버그**뿐이다. 비즈니스 로직 오류, 잘못된 알고리즘, 잘못된 API 호출 순서 같은 건 막지 못한다. 그리고 외부에서 들어오는 데이터는 TS의 시야 밖이다. "TS가 컴파일됐다 = 안전하다"는 결론은 무리다.

## TS를 쓰는 두 가지 진짜 이유

여기까지 정리하면 이런 의문이 생긴다.
"외부 데이터도 못 막고, `as`로 우회 가능하고, 컴파일 후엔 사라진다면 — 왜 쓰는가?"

답은 **TS의 가치가 "버그를 막는 도구" 그 자체보다 한 단계 위에 있다**는 점이다.

### 1. 개발자가 작성한 코드 안의 일관성

TS는 외부 세계의 값은 검증하지 못하지만, **개발자가 작성한 코드들 사이의 일관성**은 강하게 검증한다.

```typescript
type User = {
  id: string;
  name: string;
  email: string;
  phone: string; // 새로 추가
};

// 이 시점에 User를 만드는 모든 코드가 빨간 줄이 그어진다.
const user: User = { id: '1', name: 'A', email: 'a@b.c' };
//          ^^^^ Property 'phone' is missing
```

JS였다면 이 변경은 **조용히 모든 곳을 깨뜨린다.** 새 필드가 필요한데 안 넣어준 코드들은 그냥 `undefined`를 흘리고, 어딘가에서 그게 문제가 된 후에야 발견된다. TS는 이 종류의 변경을 **컴파일 시점에 전수 검사**한다.

이게 [#023 React State와 Props](https://velog.io/@dh82680/React-State%EC%99%80-Props-FE-%EA%B0%9C%EB%85%90-%ED%83%90%EA%B5%AC-023)에서 다룬 "props 계약"과도 연결된다. 컴포넌트가 받는 props의 형태가 타입으로 정의되어 있으면, 부모 컴포넌트가 잘못된 props를 넘길 때 컴파일 시점에 잡힌다. props가 무엇인지 매번 코드를 따라가서 확인할 필요가 없어진다.

### 2. IDE 경험 — 자동완성과 리팩토링

이게 실무에서 체감이 더 큰 가치다.

```typescript
const user: User = ...;
user.    // 여기서 IDE가 id, name, email, phone을 자동완성해준다
```

JS에서는 `user.`을 입력해도 IDE가 무엇을 제안해야 할지 모른다. TS에서는 타입 정보가 있으니 정확히 안다. 이게 누적되면 **모르는 라이브러리도 코드를 작성하면서 익히게 된다.** 함수 시그니처, 반환 타입, 옵셔널 인자가 전부 IDE에서 보인다.

리팩토링은 더 큰 차이를 만든다. `User`의 `name`을 `fullName`으로 바꾼다고 해보자.

* JS: 텍스트 검색으로 `.name`을 찾는다. `userName`도 잡히고, 다른 객체의 `name`도 잡힌다. 일일이 확인해야 한다.
* TS: IDE의 "Rename Symbol"을 쓰면 **그 타입의 `name`만** 정확히 골라서 바꿔준다. 누락이 없다.

이 차이는 프로젝트가 커질수록 기하급수적으로 벌어진다. **TS 덕분에 안 만들어지는 버그의 양이, TS가 직접 막아주는 버그의 양보다 훨씬 크다.** 자동완성으로 오타가 사라지고, 리팩토링에 자신이 생겨 코드를 더 자주 정리하게 된다.

## TS가 막아주지 못하는 것

균형을 위해 TS가 보호하지 못하는 영역도 분명히 짚어둔다.

| 영역 | 누가 보호해야 하는가 |
| --- | --- |
| API 응답 / 외부 입력 | Zod 같은 런타임 검증 |
| 비즈니스 로직 오류 | 테스트 |
| 성능 / 사이드 이펙트 | 리뷰, 측정 |
| 잘못된 `as` 사용 | 코드 리뷰, 린트 규칙 |

이 표를 거꾸로 보면, **TS가 보장해 주는 건 "개발자가 정직하게 타입을 적었을 때, 그 타입들 사이의 일관성"** 뿐이라는 사실이 보인다. 그 위의 모든 안전성은 다른 도구로 쌓아 올려야 한다.

그래서 실무 프로젝트는 보통 이런 조합으로 간다.

```
타입 일관성       → TypeScript
외부 데이터 검증  → Zod
동작 검증        → 단위 테스트, E2E 테스트
런타임 모니터링   → Sentry 등 RUM
```

TS는 이 스택의 **가장 빠르고 값싼 첫 번째 방어선**이다. 다른 방어선들이 못 잡는 것을 잡는 게 아니라, 다른 방어선들에 도달하기 전에 먼저 거를 수 있는 것을 거른다.

---

TypeScript는 모든 버그를 막아주는 안전망이 아니다. **개발자가 작성한 코드 안에서의 일관성**만 책임지고, 그게 끝나면 바로 사라진다. 이 한정된 영역을 정확히 알고 쓰는 것이, "TS가 다 해줄 거야"라는 환상이나 "어차피 사라지는데 의미 없다"는 냉소보다 훨씬 실용적이다.
