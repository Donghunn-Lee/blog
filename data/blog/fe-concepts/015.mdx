## 네트워크 탭을 읽을 수 있는가

API 호출이 실패했을 때 네트워크 탭을 열면 숫자와 텍스트가 가득하다. 200, 401, 404, `Content-Type`, `Authorization`... 자주 보는 것들은 금방 외워진다. 401이면 로그인 페이지로 보내고, 404면 에러 메시지 띄우고. 근데 왜 그렇게 처리해야 하는지 까지는 제대로 이해하지 못하고 있는 경우가 많다. 내가 그랬다.

HTTP 구조를 제대로 이해하고 나서야 이 숫자들이 단순한 코드가 아니라 설계된 의미 체계라는 걸 알게 됐다. 그리고 fetch가 404에서 catch로 안 간다는 것도, 사실 HTTP 입장에서는 당연한 동작이라는 것도.

## HTTP 메시지의 구조

HTTP는 연결을 만드는 게 아니다. 실제 연결은 TCP가 담당하고, HTTP는 그 연결 위에서 주고받는 **메시지의 형식과 의미를 정의한 규약**이다. 이 구분이 중요한 이유는 나중에 버전 이야기를 할 때 다시 나온다.

메시지 구조는 Request든 Response든 동일하다.

```
[시작줄]
[헤더]
[빈 줄]
[바디]
```

Request의 시작줄은 `GET /api/users HTTP/1.1`처럼 **메서드, 경로, 버전**으로 구성된다. Response의 시작줄은 `HTTP/1.1 200 OK`처럼 **버전**, **상태 코드**와 **이유 문구**가 들어간다. 이유 문구(`OK`)는 사람이 읽기 위한 것이고, 실제 처리는 숫자로 한다.

빈 줄이 헤더와 바디를 구분하는 구분자 역할을 한다. 이게 없으면 어디서 바디가 시작하는지 알 수 없다.

## 헤더는 왜 필요한가

헤더는 메시지 자체에 대한 맥락을 전달하는 메타데이터다. 바디 없이 헤더만으로 충분한 요청도 많다.

**`Content-Type`은 바디가 어떤 형식인지 알려준다.**
서버가 바디를 어떻게 파싱할지 결정하는 데 쓰이기 때문에, 이게 없거나 틀리면 서버가 바디를 제대로 읽지 못한다. `application/json`과 `application/x-www-form-urlencoded`는 전혀 다른 방식으로 파싱된다. axios는 JSON을 보낼 때 자동으로 붙여주지만, fetch는 직접 설정해야 한다.

**`Authorization`은 인증 정보를 담는다.**
보통 `Bearer {토큰}` 형태인데, 쿠키 기반 인증과 달리 자동으로 전송되지 않는다. 브라우저가 알아서 보내주는 게 아니라 클라이언트가 직접 헤더에 실어야 한다.

**`Accept`는 클라이언트가 받을 수 있는 응답 형식을 서버에 알리는 헤더다.**
서버는 이걸 보고 응답 형식을 결정한다. 생략하면 서버 기본값으로 내려온다.

## 상태 코드는 의미 체계다

상태 코드는 **5가지 클래스**로 나뉜다. 1xx는 처리 중, 2xx는 성공, 3xx는 리다이렉션, 4xx는 클라이언트 오류, 5xx는 서버 오류다. 이 분류를 알면 처음 보는 상태 코드도 어느 쪽 문제인지 바로 판단할 수 있다.

실무에서 구분이 중요한 것들이 있다.

**401 vs 403:** 401은 "누군지 모른다"는 뜻이고, 403은 "누군지는 알지만 권한이 없다"는 뜻이다. 처리 방식이 달라진다. 401이면 로그인 페이지로 보내면 되지만, 403은 로그인해도 소용없다. 같은 인증 오류처럼 보이지만 의미가 다르다.

**200 vs 201:** 200은 조회나 처리 성공이고, 201은 리소스 생성 성공이다. POST 요청 후 201이 오면 `Location` 헤더에 생성된 리소스 경로가 담겨 있을 수 있다.

**304 Not Modified:** 바디 없이 헤더만 오는 응답이다. 캐시가 아직 유효하다는 신호로, 브라우저가 서버에서 새로 받는 대신 로컬 캐시를 그대로 쓴다. 캐싱 메커니즘의 핵심인데, 이건 이후 다른 개념에서 자세히 다룬다.

한 가지 주의할 점은 실무에서는 **서버가 상태 코드를 항상 정확하게 내려주지 않는다**는 것이다. 오류가 나도 200에 `{ success: false }`를 내려주는 API가 흔하다. 상태 코드와 응답 바디 둘 다 확인하는 방어 로직이 필요한 이유다.

## fetch의 에러 처리

fetch를 사용할 때, 에러 처리 시 주의점이 하나 있다.

```js
try {
  const res = await fetch('/api/user');
  const data = await res.json(); // 404여도 여기까지 온다
} catch (e) {
  console.error(e); // 여기는 실행 안 됨
}
```

fetch는 **네트워크 레벨 오류**(DNS 실패, 연결 자체 불가)에서만 reject한다. 4xx, 5xx는 서버가 정상적으로 응답한 것이기 때문에 HTTP 입장에서는 성공적인 통신이다. 오류 내용을 담은 메시지를 잘 받아온 것.

그래서 직접 확인해야 한다.

```js
const res = await fetch('/api/user');
if (!res.ok) throw new Error(`HTTP ${res.status}`);
```

`res.ok`는 상태 코드가 200~299일 때 true다. axios는 기본적으로 4xx/5xx에서 throw하도록 되어 있어서 이 차이를 착각하기 쉽다. 둘을 혼용하는 프로젝트라면 에러 처리 방식이 일관성 있게 되어 있는지 반드시 확인해야 한다.

## HTTP 버전이 바뀐 이유

**HTTP/1.1**은 하나의 TCP 연결에서 요청을 순차적으로 처리한다. 앞 요청의 응답이 와야 다음 요청을 보낼 수 있어서, 요청이 많아질수록 대기가 쌓인다. 이걸 **Head-of-Line Blocking**이라고 한다. 브라우저가 이를 우회하기 위해 도메인당 TCP 연결을 6개까지 병렬로 열었는데, 연결마다 핸드셰이크 비용이 생긴다.

**HTTP/2**는 하나의 TCP 연결에서 여러 요청을 동시에 처리하는 **멀티플렉싱**을 지원한다. 각 요청을 스트림으로 분리하고, 프레임 단위로 쪼개서 섞어 보낸 뒤 수신 측에서 스트림 ID로 재조립한다. 연결을 여러 개 열 필요가 없고, 요청 순서에 따른 블로킹도 없다. 리소스가 많은 페이지일수록 체감 효과가 크다.

다만 HTTP/2에도 한계가 있다. TCP 패킷 하나가 손실되면 그 연결의 모든 스트림이 대기해야 한다. TCP 자체가 패킷 순서를 보장하는 프로토콜이기 때문이다. **HTTP/3**는 TCP 대신 UDP 기반의 QUIC을 써서 이 문제를 해결한다. 스트림별로 독립적으로 처리하기 때문에 하나가 막혀도 나머지는 진행된다.

## 정리

HTTP를 구조로 이해하면 네트워크 탭이 다르게 읽히기 시작한다.

- 상태 코드는 단순 숫자가 아니라 클래스 체계다. 401과 403이 다르고, 304는 바디 없이 캐시를 재사용하라는 신호다.
- 헤더는 메시지의 맥락이다. `Content-Type`이 없으면 서버가 바디를 파싱하지 못하고, `Authorization`은 브라우저가 알아서 붙여주지 않는다.
- fetch는 4xx/5xx에서 reject하지 않는다. HTTP 입장에서는 서버가 정상적으로 응답한 것이기 때문이다.
- HTTP/2가 애플리케이션 레벨 병목을 해결했지만, TCP 레벨 한계는 남아 있었다. HTTP/3가 전송 계층 자체를 바꾼 이유다.

결국 HTTP는 외워야 할 규칙이 아니라 읽어야 할 언어다. 이 구조가 잡히면 API 오류를 마주쳤을 때 "왜 이 코드가 왔는지"를 추론할 수 있게 된다.
