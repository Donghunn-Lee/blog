💡 **핵심 요약**
- State와 Props는 컴포넌트 사이의 **데이터 소유권**을 나누는 모델이다. State는 자기 소유, Props는 부모로부터 받는 읽기 전용 데이터.
- state setter는 동기적으로 값을 바꾸지 않고, **update queue에 업데이트를 예약**한다. 이 덕분에 batching과 렌더 일관성이 가능해진다.
- 함수 컴포넌트의 한 렌더는 그 시점의 props/state로 찍힌 **스냅샷**이며, 클로저 동작과 useEffect 의존성 배열이 모두 이 모델 위에 서 있다.

---

## 데이터를 어디에 두어야 할까?

React 컴포넌트를 처음 만들 때 가장 먼저 고려하게 되는 부분이라고 생각한다.

**"어떤 데이터를 어디에 두어야 할까?"**

버튼 클릭으로 바뀌는 카운터 값, 폼 입력값, 모달의 열림/닫힘 상태, API에서 받아온 사용자 정보.
이 데이터들을 **누가 소유할지**, **어떻게 다른 컴포넌트로 전달할지**를 결정해야 한다.

잘못 결정하면 흔히 이런 문제가 생긴다.

- 같은 데이터가 여러 컴포넌트에 중복으로 들어가서 동기화가 깨진다
- 자식 컴포넌트가 부모의 데이터를 직접 바꿔버려서 어디서 변경됐는지 추적이 안 된다
- 별로 안 바뀌어야 할 컴포넌트가 자꾸 리렌더링된다

이 문제를 React는 처음부터 두 가지 규칙으로 해결한다.

1. **데이터의 소유권을 명확히 한다** — state는 컴포넌트가 자기 소유로 가진다, props는 외부에서 받는다
2. **데이터는 한 방향으로만 흐른다** — 부모 → 자식. 자식은 부모의 데이터를 직접 수정할 수 없다

State와 Props는 단순히 "변수의 종류 두 가지"가 아니다.
**컴포넌트 사이의 책임과 권한을 나누는 모델**이다.

---

## State와 Props의 핵심 차이

| 구분 | State | Props |
|------|-------|-------|
| **소유권** | 컴포넌트 자기 자신 | 부모 컴포넌트 |
| **변경 권한** | setter로 자기가 변경 | 받는 쪽은 변경 불가 (읽기 전용) |
| **변경 결과** | 리렌더링 발생 | 부모가 새 값 내려주면 자식 리렌더링 |
| **본질** | Fiber 노드에 묶인 메모리 | 컴포넌트 함수의 인자 |

둘 다 "바뀌면 리렌더링이 일어난다"는 점은 같다.
하지만 **누가 바꿀 권한을 갖는가**가 결정적으로 다르다.

## State는 변수가 아니다 — Fiber에 묶인 메모리

먼저 `useState`로 만든 값은 단순한 지역 변수가 아니라는 것을 분명히 해야 한다.

```jsx
function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

함수 컴포넌트는 리렌더링될 때마다 **함수 본문이 처음부터 다시 실행된다**.
만약 `count`가 그냥 지역 변수였다면 매번 0으로 초기화됐을 것이다.

그런데 그렇지 않다. 왜인가?

`useState`는 React가 **컴포넌트 인스턴스마다 따로 관리하는 메모리 공간**에서 값을 꺼내준다.
이 메모리는 Fiber 노드에 hook 연결 리스트 형태로 붙어있다.

```
Fiber 노드
└── memoizedState (hook 연결 리스트)
     └── useState hook
          ├── current value: 0
          └── queue: [...]
```

즉 함수는 매번 새로 실행되지만,
**상태는 Fiber 노드 안에 남아있다.**

이 구조를 이해하면 자연스럽게 따라오는 결론이 있다.

```jsx
function App() {
  return (
    <>
      <Counter />
      <Counter />
    </>
  );
}
```

같은 `Counter` 컴포넌트를 두 번 써도 카운터는 독립적으로 동작한다.
각 Fiber 노드가 자기만의 state 메모리를 갖기 때문이다.

> **핵심**: state는 컴포넌트 정의가 아니라 **컴포넌트 인스턴스**에 묶인다.

## 단방향 데이터 흐름과 콜백 패턴

Props는 별다른 마법이 없다.
부모 컴포넌트가 자식 컴포넌트를 호출할 때 넘기는 **함수 인자**다.

```jsx
function Parent() {
  return <Child name="Ethan" />;
}
```

JSX의 `<Child name="Ethan" />`는 결국 `Child({ name: "Ethan" })` 함수 호출로 변환된다.
이게 props의 본질이다.

그래서 props가 읽기 전용인 건 React의 규칙이라기보다 **함수 호출 모델의 자연스러운 귀결**이다.
함수 인자를 받은 쪽이 인자 자체를 바꿔도 호출자에게 영향이 없는 것과 같은 원리다.

그렇다면 자식이 부모의 state를 바꿔야 할 때는?
입력 폼, 토글 버튼, 삭제 버튼처럼 흔한 상황이다.

이때 데이터가 거꾸로 흐르는 게 아니라,
**"바꾸는 함수"를 props로 내려보내는** 방식으로 해결한다.

```jsx
function Parent() {
  const [count, setCount] = useState(0);
  return <Child onIncrement={() => setCount(count + 1)} />;
}

function Child({ onIncrement }) {
  return <button onClick={onIncrement}>+</button>;
}
```

자식은 함수를 호출할 뿐이다.
실제 state 변경은 부모의 영역에서 일어난다.

데이터 흐름은 여전히 단방향이고,
**자식은 "이벤트를 알리는 역할"만 한다.**

이 패턴을 보면 React의 설계 의도가 보인다.
state의 변경이 항상 **소유한 컴포넌트 안에서만 일어나도록** 강제한 것이다.
그래야 변경 지점이 한 곳에 모이고, 디버깅과 추적이 가능해진다.

## setter는 비동기다 — update queue의 정체

여기서부터가 진짜다.
다음 코드의 결과를 예측해보자.

```jsx
function handleClick() {
  setCount(count + 1);
  setCount(count + 1);
  setCount(count + 1);
}
```

`count`가 0일 때 클릭하면 결과는 **3이 아니라 1**이다.
처음 보면 직관과 어긋나는 동작인데, 이걸 이해하려면 setter가 **즉시 state를 바꾸지 않는다**는 사실부터 시작해야 한다.

setter를 호출하면 React는 즉시 state를 바꾸지 않는다.
대신 **해당 useState hook의 update queue에 업데이트 객체를 push**한다.

```
queue: [
  { action: 1 },  // "state를 1로 교체해줘"
  { action: 1 },
  { action: 1 }
]
```

이벤트 핸들러가 끝나면 React가 queue를 순회하며 최종 state를 계산한다.

```
초기 state: 0
- update1 적용 → state = 1
- update2 적용 → state = 1
- update3 적용 → state = 1

최종: 1
```

세 번의 업데이트가 모두 적용되긴 했다.
**그런데 셋 다 "1로 교체"라는 같은 명령이라 결과가 1로 끝난다.**

왜 이렇게 됐는가?
`count + 1`이라는 계산이 **setter 호출 시점**, 즉 함수 본문이 실행되는 동안에 이루어졌기 때문이다.
이때 `count`는 그 렌더에 캡처된 값(0)이고, 세 번 다 같은 0을 보고 있었다.

이 문제를 해결하려면 **함수형 업데이트**를 쓴다.

```jsx
function handleClick() {
  setCount(prev => prev + 1);
  setCount(prev => prev + 1);
  setCount(prev => prev + 1);
}
```

이번엔 setter에 **함수 자체**를 넘긴다.
함수는 호출되지 않고 그대로 queue에 들어간다.

queue를 처리할 때 React는 reduce 루프를 돌면서, 매 반복마다 **이전 결과를 인자로 다음 함수에 넘긴다**.

```js
let state = 0;
state = fn1(state);  // fn1(0) → 1
state = fn2(state);  // fn2(1) → 2
state = fn3(state);  // fn3(2) → 3
```

각 함수의 매개변수(`prev`)는 **호출되는 그 순간의 누적 state**를 받는다.
결과는 3이다.

> **두 방식의 본질적 차이**
> - 값을 넘기면: **렌더 시점에** 계산이 끝나서 그 결과가 queue에 들어간다
> - 함수를 넘기면: 계산이 **queue 처리 시점까지 미뤄지고**, 그때 React가 최신 state를 인자로 주입한다
>
> 함수형 업데이트의 본질은 "이전 값을 참조하는 능력"이 아니라 **"계산을 미루는 능력"**이다.

판단 기준은 명확하다.
새 값이 **이전 값에 의존**하면 함수형 업데이트, 그렇지 않으면 일반 업데이트로 충분하다.

## 한 렌더는 하나의 스냅샷이다

setter가 비동기로 설계된 이유는 단순한 성능 최적화가 아니다.
**React의 멘탈 모델 자체가 이 비동기성에 의존한다.**

함수 컴포넌트가 한 번 렌더링되는 동안, state는 시작부터 끝까지 **같은 값**이어야 한다.

```jsx
function Component() {
  const [count, setCount] = useState(0);
  
  console.log("위:", count);   // 0
  setCount(count + 1);
  console.log("아래:", count); // 여전히 0
  
  return <div>{count}</div>;   // 여기서도 0
}
```

이 일관성이 깨지면 어떻게 될까?
- 변수의 의미가 흐려진다 (같은 변수가 시점마다 다른 값)
- 클로저로 캡처된 값을 신뢰할 수 없게 된다
- "이 렌더의 결과"가 무엇인지 정의하기 어려워진다

이 모델을 React 팀은 **"state as a snapshot"**이라고 부른다.
한 번의 렌더는 그 시점의 props/state로 찍힌 스냅샷이고, 새 값은 다음 렌더의 새로운 스냅샷에서나 보인다.

이 모델이 가져다주는 것:

**1. Batching이 가능해진다**

한 이벤트 핸들러 안의 setter 호출들을 모아서 한 번의 리렌더링으로 처리할 수 있다.
React 18부터는 비동기 코드(setTimeout, Promise)에서도 자동으로 적용된다.

**2. 클로저로 캡처된 값이 일관되게 동작한다**

```jsx
function handleClick() {
  setTimeout(() => {
    alert(count); // 이 count는 클릭 시점의 렌더에서 캡처된 값
  }, 3000);
}
```

3초 사이에 count가 바뀌어도, 이 콜백이 보는 `count`는 **클릭한 그 렌더의 값**이다.
클로저가 그 렌더의 스냅샷을 캡처했기 때문이다.

**3. useEffect 의존성 배열이 의미를 가진다**

```jsx
useEffect(() => {
  fetchUser(userId);
}, [userId]);
```

React가 "userId가 바뀌었는지" 판단할 수 있는 건 **각 렌더가 자기만의 props/state 스냅샷을 갖기 때문**이다.
이전 스냅샷과 이번 스냅샷을 비교해서 effect를 다시 실행할지 결정한다.

만약 state가 시점마다 변하는 가변 값이었다면, 비교할 "이전 값"이라는 개념 자체가 성립하지 않는다.

> **결론**: setter의 비동기성은 단순 최적화가 아니라, 함수 컴포넌트를 "순수 함수처럼 다룰 수 있게" 만드는 토대다.

## 헷갈리기 쉬운 지점들

**① props를 state로 복사하면 동기화가 깨진다**

```jsx
function Profile({ name }) {
  const [localName, setLocalName] = useState(name); // ⚠️
}
```

`useState`의 인자는 **마운트 시점에만** 의미를 가진다.
이후 리렌더링에서 React는 그 인자를 **무시한다**. 그래야 state가 외부에 의해 매 렌더마다 덮어쓰이지 않는다.

결과적으로 부모가 `name`을 바꿔도 `localName`은 처음 받은 값에 고정된다.
부모의 변경을 반영해야 한다면 props를 직접 쓰거나, 정말 필요한 경우에만 useEffect로 동기화한다.

**② `useState`는 객체를 머지하지 않는다**

클래스 컴포넌트의 `setState`는 객체를 머지했지만, `useState`의 setter는 통째로 교체한다.

```jsx
const [user, setUser] = useState({ name: "Ethan", age: 26 });

setUser({ age: 27 });                       // ❌ name이 사라진다
setUser(prev => ({ ...prev, age: 27 }));    // ✅
```

**③ setter 호출 직후의 state는 여전히 이전 값이다**

```jsx
setCount(count + 1);
console.log(count); // 새 값이 아니라 이전 값
```

setter는 다음 렌더를 예약할 뿐이다.
새 값이 필요하면 다음 렌더를 기다리거나, 함수형 업데이트 안에서 `prev`로 참조한다.

---

이 모델이 React의 여러 기능을 일관되게 묶어준다.

State와 Props의 분리, 단방향 데이터 흐름, 비동기 업데이트, 클로저 기반 동작, useEffect의 의존성 배열 — 이 모든 것이 **"한 렌더 = 한 스냅샷"**이라는 하나의 멘탈 모델 위에 서 있다.

개별 규칙으로 외우는 게 아니라, 이 모델을 중심에 두고 보면 React의 동작이 훨씬 단순하게 정리될 것이다.
