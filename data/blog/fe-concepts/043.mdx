> 💡 **핵심 요약**
>
> - **Signal은 자기 값을 누가 읽는지 추적하는 값 컨테이너다.** 업데이트 단위가 컴포넌트가 아니라 바인딩 하나이고, 이 granularity 차이가 fine-grained reactivity의 전부다.
> - 자동 의존성 추적, 게으른 평가, glitch 없는 전파 — 이 셋이 핵심이다. 의존성 배열을 손으로 적을 필요가 사라지는 이유가 여기 있다.
> - React는 이 모델을 채택하지 않았다. 리렌더 모델은 그대로 두고 React Compiler로 메모이제이션을 자동화했다. 목적지는 같고 층이 다르다.

## memo를 두르다가 드는 질문

[#025 React 렌더링 최적화](/blog/fe-concepts/025/)에서 정리한 순서를 실제로 밟다 보면 이상한 지점에 도달한다.

자식이 매번 리렌더링된다 → `memo`를 건다 → 효과가 없다 → 부모에서 `useCallback`으로 함수 참조를 안정시킨다 → 객체 props도 `useMemo`로 감싼다 → 의존성 배열을 관리하기 시작한다.

값 하나 바꾸겠다고 파일 세 개를 고치고 있다.

이 시점에서 드는 질문은 최적화 기법에 대한 게 아니다. 더 앞쪽이다.

> **왜 값 하나가 바뀌었는데 컴포넌트 함수 전체가 다시 실행돼야 하지?**

[#021 React의 렌더링이란](/blog/fe-concepts/021/)에서 본 대로, React의 리렌더링은 화면을 다시 그리는 게 아니라 컴포넌트 함수를 다시 실행하는 것이다. 업데이트의 단위가 **컴포넌트**라는 뜻이다. `count`가 바뀌면 `count`를 쓰는 `<span>` 하나가 아니라 그 함수 전체가 돈다. 그래서 전파를 끊으려면 도구로 일일이 막아야 한다.

Solid, Preact, Angular, Svelte가 선택한 방향은 이 단위 자체를 바꾼다. 그 도구가 **signal**이고, 그 모델의 이름이 **fine-grained reactivity(세밀한 반응성)**다.

---

## Signal은 값이 아니라 구독이다

signal의 정의는 짧다.

> **Signal은 자기 값을 누가 읽는지 추적하는 값 컨테이너다.**

일반 변수는 값이 바뀌어도 아무도 모른다. 알려주려면 pub/sub을 직접 깔고, 구독하고, 해제까지 관리해야 한다. signal은 그 배선을 값 자체에 내장한다.

[TC39 Signals 제안](https://github.com/tc39/proposal-signals)의 표준 API로 보면 이렇다.

```js
const counter = new Signal.State(0);
const isEven  = new Signal.Computed(() => (counter.get() & 1) === 0);
const parity  = new Signal.Computed(() => isEven.get() ? "even" : "odd");

effect(() => element.innerText = parity.get());

counter.set(1); // parity를 읽는 effect만 다시 실행된다
```

노드는 세 종류다. 값을 담는 **State**, 다른 signal에서 파생되는 **Computed**, 그리고 변화에 반응해 부수 효과를 내는 **Watcher/Effect**. 이들이 서로를 참조하며 방향성 비순환 그래프를 만든다.

React와의 차이를 한 줄로 놓으면 이렇다.

| | 업데이트 단위 | 값이 바뀌면 |
|---|---|---|
| **React 리렌더 모델** | 컴포넌트 | 함수 재실행 → VDOM diff → 바뀐 DOM만 commit |
| **Signal 모델** | 반응성 바인딩 하나 | 그 값을 읽는 계산과 DOM 바인딩만 재실행 |

[#010 DOM과 Virtual DOM](/blog/fe-concepts/010/)에서 Virtual DOM을 "항상 빠른 게 아니라 충분히 빠른 추상화"라고 정리했다. signal 모델은 그 추상화를 아예 건너뛴다. 무엇이 바뀌었는지 **찾을 필요가 없기 때문이다.** 그래프가 이미 알고 있다.

> ⚠️ **Solid에서 컴포넌트 함수는 최초 1번만 실행된다.**
> 그 실행은 화면을 그리는 게 아니라 반응성 그래프를 배선하는 셋업이다. 이후 업데이트는 컴포넌트를 거치지 않고 그래프를 타고 DOM으로 직행한다. 이건 명세가 아니라 Solid의 구현 특성이다.

## 읽는 행위가 곧 구독이다

signal이 개발자 경험에서 만드는 가장 큰 차이는 성능이 아니라 **의존성 배열의 소멸**이다.

`useEffect(fn, [a, b])`에서 의존성은 사람이 손으로 적는다. 하나 빠뜨리면 stale closure 버그, 다 넣으면 불필요한 재실행. 이 배열이 존재하는 이유는 React가 "이 함수가 무엇을 쓰는지" 모르기 때문이다.

signal은 이걸 실행 시점에 알아낸다. 원리는 놀랄 만큼 단순하다.

```
1. 전역에 "지금 실행 중인 계산"을 가리키는 포인터가 하나 있다
2. 계산이 실행되는 동안 signal.get()이 호출된다
3. 그 signal은 "현재 실행 중인 계산"을 자기 구독자로 기록한다
4. 계산도 그 signal을 자기 의존성으로 기록한다
```

즉 **읽는 행위 자체가 구독**이다. 선언할 게 없으니 빠뜨릴 것도 없다.

여기서 한 걸음 더 나간 성질이 있다. 의존성은 **매 실행마다 새로 수집된다.** 조건문 한쪽 가지에서만 읽는 signal이 있고 이번 계산이 반대 가지를 탔다면, 그 signal은 이번 의존성 목록에 없다. 그 값이 바뀌어도 이 계산은 다시 돌지 않는다.

`useMemo`의 의존성 배열은 정적이라 이런 동적 정밀도를 표현할 수 없다.

## 게으름이 만드는 정확성

여기가 signal 설계에서 가장 정교한 부분이고, 성능 이야기가 실제로는 **정확성** 이야기라는 게 드러나는 지점이다.

값이 바뀌면 구독자를 즉시 다 재계산하는 순진한 방식(pure push)에는 구조적 결함이 있다. 다이아몬드 구조를 보자.

```text
        A  (State)
       / \
      B   C  (Computed — 둘 다 A에 의존)
       \ /
        D  (Computed — B와 C에 의존)
```

`A`가 바뀌면 `B` 갱신 → `D` 재계산, 그다음 `C` 갱신 → `D` 또 재계산.

`D`가 두 번 계산되는 것도 문제지만 진짜 문제는 중간 상태다. 첫 번째 `D` 계산 시점에 `B`는 새 값, `C`는 아직 옛 값이다. 일관성이 깨진 값이 화면에 잠깐 노출될 수 있다. 이걸 **glitch**라고 부른다.

signal은 전파를 두 단계로 쪼개서 이걸 구조적으로 막는다.

**① Push — 표시만 한다.**
`A.set()`이 호출되면 그래프를 타고 내려가며 플래그만 세운다. 직접 의존하는 `B`, `C`는 값이 확실히 낡았으니 `dirty`. 간접 의존하는 `D`는 낡았을 **수도** 있으니 `checked`. 이 단계에서 재계산은 일어나지 않는다.

**② Pull — 읽힐 때 계산한다.**
누군가 `D.get()`을 호출하면, 그때 위상 순서를 따라 가장 깊은 dirty 노드부터 거슬러 올라가며 재계산한다. `B`와 `C`가 먼저 확정되고, 그다음 `D`가 **정확히 한 번** 계산된다.

제안 문서는 이 성질을 glitch-free로 명시하고, 구현 조건으로 dirty한 부분 그래프의 위상 정렬을 요구한다. 게으름은 성능 트릭이 아니라 **일관성 보장 장치**다.

`checked`가 별도로 존재하는 이유도 여기 있다. `B`를 재계산했는데 결과가 이전과 같다면 `D`는 다시 계산할 필요가 없다. 변화가 중간에서 멈추는 것이다.

> 💡 **Computed는 아무도 읽지 않으면 계산되지 않는다.**
> 의존성이 바뀌어도 표시만 될 뿐이다. 화면에 없는 값은 비용이 0이다.

## React가 다른 길을 간 이유

signal이 우아하다면 React는 왜 도입하지 않았을까. 이유는 두 갈래이고, 둘 다 React가 이미 한 다른 선택과 얽혀 있다.

**첫째, 중단 가능한 렌더링과 충돌한다.**

[#022 React Fiber 아키텍처](/blog/fe-concepts/022/)의 존재 이유가 렌더링을 쪼개고, 멈추고, 버리고, 다시 시작할 수 있게 만드는 것이었다. transition으로 시작한 렌더가 더 급한 입력에 밀려 통째로 폐기되는 일이 정상 동작이다.

이게 성립하려면 렌더링 도중의 작업이 **아직 아무것도 확정하지 않은 상태**여야 한다. signal 모델은 반대다. 값을 변이시키면 그래프를 타고 DOM까지 즉시 흐른다. 흘러간 것을 되돌리는 건 어렵다. 화면 밖에서 준비했다가 폐기하는 동작과 궁합이 나쁘다.

**둘째, 같은 문제를 컴파일러로 풀기로 했다.**

signal이 해결하는 실질적 고통은 "불필요한 재계산"과 "수동 메모이제이션"이다. React는 모델을 바꾸는 대신 그 고통을 빌드 타임으로 옮겼다. [React Compiler](https://react.dev/blog/2025/10/07/react-compiler-1)가 2025년 10월 1.0 정식 버전으로 나왔다.

```jsx
// 개발자가 쓰는 코드
function ProductList({ category }) {
  const filtered = products.filter(p => p.category === category);
  const handleClick = (id) => select(id);
  return <List items={filtered} onClick={handleClick} />;
}
// 컴파일러가 데이터 흐름을 분석해 메모이제이션을 삽입한다
```

핵심은 이 컴파일러가 signal을 도입하지 **않는다**는 점이다. 리렌더 모델은 그대로다. 컴포넌트는 여전히 통째로 재실행되고, VDOM diff도 그대로 일어난다. 바뀐 건 `useMemo`와 `useCallback`을 사람이 아니라 컴파일러가 넣는다는 것뿐이다.

게다가 컴파일러는 사람이 못 하던 것도 한다. 조건문 내부처럼 Hook 규칙상 `useMemo`를 넣을 수 없던 위치에도 메모이제이션을 배치한다.

> ⚠️ React 팀이 "signal을 검토하고 기각했다"는 공식 선언문이 있는 것은 아니다.
> 위 두 가지는 React가 실제로 내린 선택(Fiber의 중단 가능한 렌더링, Compiler 출시)에서 역으로 읽어낸 설계 논리다. 확정된 사실은 **React가 signal을 채택하지 않았고 컴파일러를 택했다**는 결과 쪽이다.

## 지금 어디까지 왔나

트렌드 토픽이라 현재 상태를 정확히 짚어둔다. 이 영역은 부정확한 정보가 특히 많이 돈다.

**TC39 표준화 — Stage 1.**
2024년 4월 Stage 1 진입 이후 아직 Stage 2로 가지 않았다. 제안 그룹이 의도적으로 보수적인 것도 이유다. Stage 2 제안 전에 "여러 프레임워크에 실제로 이식해서 성능과 정합성을 검증한다"는, TC39 절차에 없는 추가 과제를 스스로 걸어뒀다. 제안 FAQ는 모든 브라우저에서 폴리필 없이 쓰기까지 **최소 2~3년**을 예상한다. 지금 당장 쓸 API가 아니다.

**프레임워크 채택 현황.**

| | 상태 |
|---|---|
| **Solid** | signal이 코어 반응성 모델 |
| **Preact** | `@preact/signals`로 제공 |
| **Angular** | signal API 제공 |
| **Svelte 5** | runes가 내부적으로 signal 구현으로 컴파일된다 |
| **Vue** | 반응성 시스템을 `alien-signals` 기반으로 재작성 — **3.6에 포함, 아직 pre-release** |
| **React** | 채택하지 않음. React Compiler로 대응 |

Vue 항목은 특히 주의해야 한다. `vuejs/core` 릴리스 기준 최신 stable은 3.5.x이고 3.6은 beta/RC 단계다. "Vue가 이미 signals로 전환했다"고 쓴 글이 적지 않은데, 실제로는 아직 정식 배포 전이다.

> 📚 표준 API의 정확한 알고리즘과 상태 전이는 [TC39 Signals 제안 문서](https://github.com/tc39/proposal-signals)에 프로토 명세 수준으로 정리되어 있다.

한 가지 더. 표준 제안은 `effect`를 포함하지 않는다. 이펙트 스케줄링은 렌더링 사이클과 너무 얽혀 있어서, 제안은 `Signal.subtle.Watcher`라는 하위 재료만 표준화하고 나머지는 프레임워크에 맡긴다. **signal 그래프는 표준화 대상이지만 이펙트는 아니다.**

## 헷갈리기 쉬운 부분

**"Signal은 전역 상태 관리 도구다."**
아니다. Redux나 Zustand는 상태를 어디에 둘지를 다루는 컨테이너다. signal은 업데이트가 어떤 단위로 전파되는지를 바꾸는 반응성 원시 도구다. 층이 다르고, 그래서 signal 위에 상태 관리 라이브러리를 얹는 것도 가능하다. Vue의 `reactive()`, Solid의 store가 그런 구조다.

**"React Compiler는 React가 signal을 도입한 것이다."**
아니다. 컴파일러는 리렌더 모델을 유지한 채 메모이제이션 삽입만 자동화한다. 컴포넌트는 여전히 통째로 재실행되고, 세밀한 반응성도 signal 원시 타입도 없다. 해결하려는 고통이 같을 뿐 수단이 다르다.

**"Signal이 React보다 항상 빠르다."**
"항상"이 틀렸다. 컴포넌트 재실행과 diff를 건너뛰니 다수의 업데이트 패턴에서 낭비가 줄어드는 건 맞다. 다만 signal 그래프도 구독 등록·해제라는 자체 오버헤드를 지불하고, React Compiler가 격차를 좁혔으며, 워크로드에 따라 차이가 측정되지 않는 경우도 많다. 정확한 표현은 "빠르다"가 아니라 **"버리는 작업이 적다"**다.

**"Computed는 의존성이 바뀌면 다시 계산된다."**
아니다. 표시만 된다. 실제 재계산은 누군가 값을 읽을 때, 위상 순서를 따라, 최대 한 번 일어난다. 이 게으름이 성능과 glitch 방지를 동시에 만든다.

## 정리

두 모델의 진짜 차이는 벤치마크 숫자가 아니다. **개발자가 어떤 질문을 반복해서 하게 되느냐**다.

React 모델에서는 계속 이 질문을 하게 된다. "이 리렌더링을 어떻게 막지?" `memo`, `useCallback`, state 위치 조정, children 합성 — [#025](/blog/fe-concepts/025/)의 도구들은 전부 이 질문에 대한 답이다.

signal 모델에서는 그 질문이 아예 생기지 않는다. 막을 리렌더링이 처음부터 없기 때문이다. 대신 다른 질문이 생긴다. "이 그래프는 어디까지 연결되어 있고, 이 Watcher는 언제 해제되지?"

React Compiler의 베팅은 세 번째 길이다. 모델을 바꾸지 않고, 질문을 개발자에게서 컴파일러로 옮긴다.

그래서 signal을 이해한다는 건 Solid로 갈아탈 준비를 한다는 뜻이 아니다. 내가 지금 쓰는 프레임워크가 어떤 질문을 나 대신 처리하기로 했고, 어떤 질문을 아직 나에게 남겨뒀는지를 구분할 수 있게 된다는 뜻이다.
