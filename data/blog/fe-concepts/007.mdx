- Promise는 비동기 작업의 상태와 결과를 다루기 위한 JavaScript의 표준 방식이다.

JavaScript의 비동기를 처음 배우게 되면, 코드의 실행 흐름을 예측하는 것이 정말 쉽지 않다.

단순히 코드 흐름을 예측하기 어려운 것도 있지만,

비동기 작업이 많아질수록 **성공과 실패를 나눠 처리해야 하고**, **여러 작업의 순서를 제어해야 하고**, **중간 에러도 한 흐름 안에서 다뤄야** 했다.

`Promise`와 `async/await`은 바로 이 지점에서 필요해진다.

## 왜 Promise와 async/await이 필요할까

프론트엔드에서는 비동기 작업이 너무 흔하다.

- 서버에서 사용자 정보를 가져오는 요청
- 버튼 클릭 후 저장 API 호출
- 업로드 완료를 기다린 뒤 다음 작업 실행
- 여러 데이터를 모두 받은 뒤 화면 렌더링

이런 작업은 바로 결과가 나오지 않는다.  
그래서 “끝나면 무엇을 할지”를 잘 정리해둘 필요가 있다.

문제는 이 흐름을 아무렇게나 다루면 코드가 금방 읽기 어려워진다는 점이다.  
특히 예전 방식처럼 콜백을 계속 중첩하다 보면, 흐름이 깊어지고 에러 처리도 여기저기 흩어지기 쉽다.

Promise는 비동기 작업을 **하나의 일관된 방식으로 표현**할 수 있게 만들었고,  
async/await은 그 Promise를 **조금 더 순서대로 읽히는 코드**로 바꿔줬다.

## Promise는 무엇을 해결하려고 등장했을까

Promise는 간단히 말하면,  
**“아직 끝나지 않았지만 언젠가 결과가 정해질 작업”을 표현하는 객체**다.

여기서 중요한 건 단순히 “나중에 끝난다”가 아니다.  
그 작업이 나중에

- 성공할 수도 있고
- 실패할 수도 있고
- 아직 진행 중일 수도 있다는 점

이 세 가지 상태를 명확하게 다룰 수 있게 해준다는 데 의미가 있다.

Promise의 상태는 3가지다.

- `pending`: 아직 작업이 끝나지 않은 상태
- `fulfilled`: 작업이 성공적으로 끝난 상태
- `rejected`: 작업이 실패한 상태

그리고 한 번 성공하거나 실패가 결정되면, 그 상태는 다시 바뀌지 않는다.

보통 Promise를 그냥 “비동기 함수의 결과물” 정도로 생각하기 쉬운데,  
실제로는 **비동기 흐름을 연결하고, 결과를 다음 단계로 넘기고, 실패를 한 곳에서 처리하기 위한 구조**라고 보는 편이 더 정확하다.

## Promise는 어떻게 동작할까

흐름은 생각보다 단순하다.

### 1. 비동기 작업을 시작한다

예를 들어 `fetch()`로 데이터를 요청한다고 해보자.  
네트워크 요청은 시간이 걸리기 때문에 바로 결과가 나오지 않는다.

### 2. JavaScript는 Promise를 먼저 돌려준다

아직 결과는 없지만,  
“이 작업은 나중에 끝날 거야”라는 약속 형태의 객체를 먼저 받는다.  
그게 Promise다.

### 3. 작업이 끝나면 상태가 정해진다

요청이 성공하면 `fulfilled`,  
실패하면 `rejected`가 된다.

### 4. then / catch / finally로 후속 처리를 연결한다

- `then`: 성공했을 때 실행
- `catch`: 실패했을 때 실행
- `finally`: 성공/실패와 상관없이 마지막에 실행

이 구조 덕분에 비동기 작업을 그냥 던져두는 게 아니라,  
**성공하면 다음엔 뭘 하고, 실패하면 어떻게 처리할지**를 흐름으로 연결할 수 있다.

처음 Promise를 배울 때는 `then`이 조금 낯설다.  
그런데 실제로는 “이 작업이 끝난 다음 이걸 해라”를 연결하는 문법이라고 보면 된다.

## async/await은 Promise와 무엇이 다를까

여기서 많이 헷갈리는 부분이 있다.

async/await은 Promise와 별개의 완전히 새로운 방식이 아니다.  
**Promise를 더 읽기 쉽게 다루는 문법**이다.

`then` 체이닝의 경우, 흐름이 길어지면 순서를 파악하기 어려워진다.

```js
fetch('/api/user')
  .then((res) => res.json())
  .then((data) => {
    console.log(data);
  })
  .catch((error) => {
    console.error(error);
  });
```

이 코드는 문제는 없지만, 단계가 많아질수록 읽는 사람이 흐름을 따라가기가 조금 번거로워질 수 있다.

같은 흐름을 async/await으로 바꾸면 이렇게 된다.

```js
async function getUser() {
  try {
    const res = await fetch('/api/user');
    const data = await res.json();
    console.log(data);
  } catch (error) {
    console.error(error);
  }
}
```

훨씬 순서대로 읽힌다.

- 요청 보내고
- 응답 받고
- JSON 파싱하고
- 결과를 사용하고
- 실패하면 catch로 처리

이렇게 보면 거의 동기 코드처럼 보인다.

하지만 여기서 중요한 건  
**겉으로만 동기식처럼 읽히는 것이지, 실제 실행 모델은 여전히 비동기**라는 점이다.

`await`이 있다고 해서 JavaScript 전체가 멈추는 것은 아니다.  
정확히는 **그 async 함수 내부에서 다음 줄로 넘어가는 시점만 잠시 기다리는 것**에 가깝다.

## 실제 코드에서는 어떻게 보일까

실무에서는 보통 API 요청이나 폼 제출, 초기 데이터 로딩에서 가장 자주 만난다.

예를 들어 페이지에 들어오자마자 사용자 정보와 게시글 목록을 함께 가져와야 한다고 해보자.

```js
async function loadPage() {
  try {
    const [user, posts] = await Promise.all([
      fetchUser(),
      fetchPosts(),
    ]);

    setUser(user);
    setPosts(posts);
  } catch (error) {
    setError(true);
  } finally {
    setLoading(false);
  }
}
```

여기서 볼 수 있는 포인트가 몇 가지 있다.

첫째, 서로 독립적인 요청은 `await`을 순서대로 두 번 쓰기보다 `Promise.all`로 같이 보내는 편이 낫다.  
그래야 불필요하게 시간을 더 쓰지 않는다.

둘째, 성공 흐름과 실패 흐름, 마지막 정리 작업이 비교적 분명하게 나뉜다.  
실무에서는 이런 구조가 꽤 중요하다.  
로딩 상태를 언제 끄는지, 실패했을 때 어떤 UI를 보여줄지 같은 것들이 결국 사용자 경험과 바로 연결되기 때문이다.

셋째, async/await이 편하다고 해서 모든 상황이 단순해지는 건 아니다.  
병렬 처리인지, 순차 처리인지, 실패를 어디서 잡을지 같은 판단은 여전히 개발자가 해야 한다.

그리고 이벤트 루프를 공부한 직후라면 하나 더 연결해서 이해할 수 있다.  
Promise의 후속 처리인 `then`이나 `await` 이후 코드는 보통 microtask로 처리되기 때문에, `setTimeout`보다 먼저 실행되는 경우가 많다.  
그래서 Promise를 이해할 때는 문법만 보는 것보다, **비동기 실행 순서와 함께 보는 편이 훨씬 덜 헷갈린다.**

## 정리

- Promise는 비동기 작업의 상태와 결과를 다루는 표준적인 방법이다.
- 핵심은 성공, 실패, 대기 상태를 명확하게 표현하고 후속 작업을 연결할 수 있다는 점이다.
- async/await은 Promise를 더 읽기 좋은 형태로 사용할 수 있게 해준다.
- 다만 async/await이 Promise를 대체하는 것은 아니고, Promise 위에서 동작하는 문법이다.
- 실무에서는 API 요청, 로딩 처리, 에러 처리, 병렬 요청 제어 같은 상황에서 거의 계속 만나게 된다.

이전 글에서 이벤트 루프를 보면서 “비동기 작업은 결국 나중에 실행된다”는 흐름을 이해했다면,  
이번에는 그 비동기 작업을 **어떻게 더 안전하고 읽기 좋게 다룰 것인가**까지 연결된 셈이다.

Promise와 async/await은 문법 자체보다,  
비동기 흐름을 다루는 사고방식을 익히는 데 더 큰 의미가 있는 개념이라고 느껴진다.
