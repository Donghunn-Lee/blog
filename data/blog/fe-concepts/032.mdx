💡 **핵심 요약**
- TypeScript는 타입의 호환성을 **이름이 아니라 모양(구조)** 으로 판정한다. 같은 모양을 가진 두 타입은 이름이 달라도 서로 호환된다.
- 이 방식은 JS의 덕 타이핑과 결이 같기 때문에 채택됐다. **TS는 JS 위에 얹히는 점진적 타입 시스템**이라, 명목적 방식이었다면 기존 JS 라이브러리와 거의 호환되지 않았을 것이다.
- 같은 모양의 두 타입을 **의도적으로 구분하고 싶다면** branded type 같은 패턴으로 모양 자체를 다르게 만들어야 한다. 구조적 타이핑은 유연하지만, 이 유연함이 기본값이라는 점을 알고 써야 한다.

## 같은 모양인데 이름만 다른 두 타입

아래에 `User`와 `Product`라는 두 타입이 있다.
두 타입의 이름은 다르지만, 구조는 동일하다.

```ts
type User = { id: number; name: string };
type Product = { id: number; name: string };

const user: User = { id: 1, name: "Ethan" };
const product: Product = user; // ✅ 에러 없음
```

타입 이름이 분명히 다른데 할당에 에러가 없다. Java나 C#을 먼저 만진 사람은 여기서 한 번 멈칫할 수도 있다. "이름이 다른데 어떻게 호환되지?"

이게 단순한 예외 동작이 아니라 **TypeScript가 타입을 판정하는 방식의 핵심**이다. 객체 호환, 함수 매개변수 호환, 제네릭 추론, 라이브러리 간 인터페이스 호환 — TS의 거의 모든 동작이 이 위에 서 있다. 토대를 모르고 쓰면 두 가지 상황이 어색해진다. **의도와 다르게 통과되는 할당**이 보이는데 왜 그런지 모르고, 반대로 **의도적으로 분리하고 싶은 두 타입**을 분리하지 못해 답답해진다.

## 구조적 타이핑(Structural Typing)

TypeScript의 타입 시스템을 한 줄로 정의하면 이렇다.

> **타입의 호환성을 이름이 아니라 모양(structure)으로 판정한다.**

대상이 요구하는 멤버를 원본이 모두 가지고 있으면, 두 타입은 호환된다. 이름이 무엇이든, 어디서 선언됐든 상관없다.

반대 개념이 **명목적 타이핑(nominal typing)**이다. Java의 `class A`와 `class B`는 멤버가 똑같아도 이름이 다르면 다른 타입이다. 하지만 TS는 이 방식을 따르지 않는다.

```
[명목적 타이핑]                  [구조적 타이핑]
                                
  type A ─┬─→ "A"                type A = {x: number}
          │   ≠                          ≡       (모양이 같으면)
  type B ─┴─→ "B"                type B = {x: number}
                                
  이름이 다르면 다른 타입         모양이 같으면 같은 타입
```

## 기본 규칙: 필요한 요소가 다 있으면 호환된다

구조적 호환의 규칙은 한 줄로 요약된다.

> **대상이 요구하는 멤버를 원본이 모두 가지고 있으면 호환된다.**

```ts
interface Named {
  name: string;
}

const person = { name: "Ethan", age: 26 };
const named: Named = person; // ✅
```

`Named`는 `name`만 요구한다. `person`은 `name`을 가지고 있다. `age`가 추가로 있어도 상관없다. 호환된다.

여기서 강조할 부분이 있다. **추가 속성이 있어도 통과한다.** 대상이 요구하는 멤버는 "최소 요구사항"이지 "정확한 모양"이 아니다. 이게 구조적 타이핑의 유연함을 만드는 핵심 동작이다.

## 객체 리터럴은 왜 다르게 동작하는가

방금 본 동작을 알고 나면 다음 코드가 이상해 보인다.

```ts
const named: Named = { name: "Ethan", age: 26 };
// ❌ '{ name: string; age: number; }' 형식은 'Named' 형식에 할당할 수 없습니다.
//    개체 리터럴은 알려진 속성만 지정할 수 있으며 'Named' 형식에 'age'이(가) 없습니다.
```

같은 모양을 변수에 담아 할당할 때는 통과했는데, 리터럴을 직접 쓰면 막힌다. 이 차이를 만드는 게 **excess property check(잉여 속성 검사)** 다.

객체 리터럴을 직접 써서 할당하는 경우는 보통 "그 자리에서 그 객체를 만들었다"는 뜻이다. 이때 정의되지 않은 속성이 들어 있으면, 의도된 추가 데이터일 수도 있지만 **오타일 가능성이 더 크다**. 그래서 TS는 객체 리터럴에 한해 더 엄격하게 본다. 변수를 거치면 "이미 만들어진 어딘가의 객체를 받아서 쓰는 것"이라 보고 기본 규칙으로 돌아간다.

```ts
type ButtonProps = { label: string; onClick: () => void };

// ❌ onclick 오타가 컴파일 시점에 잡힌다
const btn: ButtonProps = {
  label: "Submit",
  onclick: () => {},   // 'onClick' 오타
};
```

이 안전장치가 없으면, 모양이 호환된다는 이유로 오타가 그대로 통과해버린다. excess property check가 그 빈틈을 메운다.

> ⚠️ **구조적 타이핑의 기본 규칙은 "추가 속성 허용"이고, excess property check는 객체 리터럴에만 적용되는 추가 안전장치다.**
> "객체 리터럴이 막혔다 = 구조적 타이핑이 엄격하다"가 아니라, "객체 리터럴은 예외적으로 더 엄격하게 본다"가 정확한 이해다.

## 함수와 클래스도 같은 방식으로 본다

객체뿐 아니라 함수와 클래스의 호환성도 같은 원리로 결정된다.

### 함수

함수의 매개변수도 모양으로 비교된다.

```ts
type LogFull = (user: { name: string; age: number }) => void;

const logName: LogFull = (u: { name: string }) => {
  console.log(u.name);
};
// ✅ 더 적게 요구하는 함수는 더 많이 요구하는 자리에 들어갈 수 있다
```

`LogFull`은 호출자에게 `{ name, age }` 둘 다 갖춘 객체를 넘기겠다고 약속한다. 그 자리에 들어갈 함수가 `{ name }` 만 본다면, 어차피 들어오는 객체는 `name`이 있으니까 안전하다. 반대로 함수가 `{ name, age, email }`을 다 요구한다면, `email`이 안 들어와서 깨진다.

배열 메서드 콜백이 이 원리로 동작한다.

```ts
[1, 2, 3].forEach((value) => console.log(value));
// 실제 시그니처: (value, index, array) => void
// 우리는 value만 받아도 통과 — 더 적게 요구하니까
```

### 클래스

이게 Java/C# 출신에게 가장 어색한 부분일 것이다.

```ts
class Dog {
  name: string = "";
  bark() {}
}

class Person {
  name: string = "";
  bark() {}
}

const dog: Dog = new Person(); // ✅
```

상속 관계도 아니고 전혀 다른 클래스인데 호환된다. 모양이 같으니까. **TS의 `class`는 명목적 단위가 아니라 "특정 모양을 만드는 도구"** 다.

이 동작에는 한 가지 의도적인 예외가 있다. `private`이나 `protected` 멤버가 있으면, **그 클래스에서 선언된 것**만 호환된다. 같은 이름의 `private` 필드가 있어도 다른 클래스에서 선언됐으면 호환되지 않는다. 캡슐화를 보장하기 위한 예외고, **구조적 타이핑의 거의 유일한 명목적 동작**이다.

```ts
class A { private x = 0; }
class B { private x = 0; }

const a: A = new B(); // ❌
```

## TS는 왜 구조적 방식을 택했는가

여기서 자연스럽게 의문이 든다. "이렇게 헐거워 보이는 방식을 왜 택했지? 이름으로 구분하는 편이 더 정확하지 않은가?"

답은 **TypeScript가 JavaScript 위에 얹히는 언어**라는 사실에 있다.

JS는 원래부터 **덕 타이핑(duck typing)** 이다. "오리처럼 걷고 오리처럼 운다면 그건 오리다." JS 코드는 객체의 출처를 따지지 않고 "필요한 메서드가 있는가"만 본다.

```js
function quack(animal) {
  animal.quack(); // 어디서 왔든 quack 메서드만 있으면 됨
}
```

이 동작 방식 위에 TS가 명목적 타입 시스템을 올렸다고 가정해보자. 라이브러리 A에서 받은 `User`를 라이브러리 B의 함수에 넘길 수 없게 된다. 라이브러리 B가 자기 안에서 `User`를 선언했기 때문에, 모양이 같아도 "이건 그 User가 아니다"라며 거부할 것이다. 결과적으로 모든 라이브러리 경계에서 변환 코드를 직접 써야 한다.

[#031 TypeScript는 왜 쓰는가](https://velog.io/@dh82680/TypeScript-TypeScript%EB%8A%94-%EC%99%9C-%EC%93%B0%EB%8A%94%EA%B0%80-FE-%EA%B0%9C%EB%85%90-%ED%83%90%EA%B5%AC-031)에서 짚었던 것처럼, **TS는 "JS에 정적 타입 시스템을 더한 언어"** 다. 기존 JS 코드와 라이브러리에 점진적으로 타입을 도입할 수 있어야 한다는 게 설계 출발점이었다. 명목적 방식이었다면 이 점진적 도입 자체가 거의 불가능했을 것이다.

구조적 방식은 단점이 아니라 **JS와 결을 맞추기 위한 선택**이다. 이 사실을 인정하고 들어가야 다음 섹션의 한계와 회피법이 자연스럽게 따라온다.

## 구조적 타이핑이 만드는 한계와 우회법

유연함은 그 자체로 한계도 함께 갖는다. **같은 모양이라는 이유만으로 의도와 다르게 호환되는 케이스**가 생긴다. 가장 흔한 예가 ID 타입이다.

```ts
type UserId = string;
type ProductId = string;

function getUser(id: UserId) { /* ... */ }

const productId: ProductId = "p_123";
getUser(productId); // ✅ 통과 — 둘 다 그냥 string이라서
```

타입 이름은 분리해 뒀지만, 둘 다 `string`이라 모양이 똑같다. TS 입장에선 두 타입을 구분할 근거가 없다. ProductId를 UserId 자리에 그대로 넣어도 막지 못한다.

이런 상황을 막기 위한 패턴이 **branded type**이다. 모양 자체를 인위적으로 다르게 만든다.

```ts
type UserId = string & { readonly __brand: "UserId" };
type ProductId = string & { readonly __brand: "ProductId" };

function getUser(id: UserId) { /* ... */ }

const productId = "p_123" as ProductId;
getUser(productId);
// ❌ 'ProductId' 형식의 인수는 'UserId' 형식의 매개 변수에 할당될 수 없습니다.
```

`__brand`라는 가짜 속성을 교차 타입(`&`)으로 끼워 넣어, 모양에 차이를 만든다. 이제 두 타입은 구조적으로도 다른 타입이다.

여기서 짚고 넘어갈 점은 **`__brand`는 런타임에 존재하지 않는다**는 것이다. 컴파일 시점에 타입 검사용으로만 쓰이고, 컴파일이 끝나면 사라진다. 이게 가능한 이유는 #031에서 짚었듯 **TS의 타입 정보가 컴파일 후 전부 사라지기 때문**이다. 가짜 속성을 끼워 넣어도 런타임 동작에는 영향이 없다.

ID 외에도 단위(`Meters`, `Seconds`), 검증된 입력(`SanitizedHTML`, `ValidatedEmail`) 같이 **"같은 원시 타입이지만 의미가 다른 값"** 을 구분할 때 자주 쓰인다.

> ⚠️ **모든 ID 타입에 brand를 다는 건 과하다.**
> brand는 가독성을 떨어뜨리고, 라이브러리 경계에서 변환을 강제한다. 두 ID가 섞이는 게 실제로 버그를 만들었거나 만들 위험이 큰 영역에만 적용한다. 작은 프로젝트에서 모든 string ID를 brand로 분리하면 비용이 더 크다.

---

구조적 타이핑은 TypeScript의 우연한 특성이 아니라, **JS 위에서 점진적 타입 시스템이 성립하기 위한 필연적 선택**이다.

같은 모양의 다른 타입이 호환된다는 사실에 놀랄 게 아니라, **"이 도구는 모양으로 본다"** 를 기본 멘탈 모델로 가지고 들어가야 한다. 그래야 TS가 왜 그렇게 판정하는지 보인다.

그러고 나면 brand나 private 같은 예외가 자연스럽게 자리를 잡는다. 기본 규칙을 깨뜨리는 장치가 아니라, **기본 규칙 위에 의도적으로 얹은 안전장치**라는 게 따라온다.
