## GC가 있는데 왜 누수가 생기는가

JavaScript는 GC가 알아서 처리해주는 것으로 알고 있었다. 또는 언마운트 될 때 자동으로 다 초기화 된다고 어렴풋이 생각하고 있었다. 그래서 메모리 누수에 대해 C처럼 직접 `free()`를 호출하지 않아도 되는 언어에서 왜 메모리가 새는 건지 바로 와닿지 않았다.

GC는 만능이 아니다. GC가 메모리를 수거하는 기준은 단 하나, **"루트에서 도달할 수 없는 객체"** 다. 뒤집어 말하면, 도달 가능한 객체는 절대 수거하지 않는다. 메모리 누수는 GC가 잘못 동작해서 생기는 게 아니라, 개발자가 의도치 않게 참조를 살려두고 있어서 GC 입장에서는 "아직 쓰이고 있는 것"으로 판단하는 상황에서 생긴다.

## GC는 어떻게 동작하는가 — Mark-and-Sweep

현대 JS 엔진(V8 등)이 사용하는 방식은 **Mark-and-Sweep**이다. 동작은 두 단계로 나뉜다.

첫 번째 Mark 단계에서 GC는 루트(전역 변수, 현재 실행 중인 함수의 지역 변수)에서 출발해 참조를 따라 모든 객체를 탐색하고, 도달한 객체에 "살아있음" 표시를 한다. 두 번째 Sweep 단계에서 표시되지 않은 객체, 즉 루트에서 도달할 수 없는 객체의 메모리를 해제한다.

이전 방식인 **참조 카운팅(Reference Counting)**은 객체를 참조하는 곳의 수를 세고, 카운트가 0이 되면 수거하는 방식이었다. 직관적이지만 치명적인 한계가 있었다.
```js
function problem() {
  const a = {};
  const b = {};
  a.ref = b;
  b.ref = a;
  // 함수가 끝나도 a, b는 서로를 참조하므로 카운트가 0이 되지 않는다
}
```

a와 b가 서로를 참조하는 순환 구조에서는 카운트가 절대 0이 되지 않아 수거가 불가능했다. Mark-and-Sweep은 이 문제를 근본적으로 해결한다. a, b가 서로를 참조하더라도, **루트에서 도달할 수 없으면** 수거 대상이다. 순환 참조 자체가 문제가 아니라, 루트와의 연결이 끊겼느냐가 기준이다.

## 참조가 끊기지 않는 세 가지 패턴

GC 원리를 알고 나면 왜 특정 패턴에서 누수가 생기는지가 명확해진다.

**이벤트 리스너**가 가장 흔한 원인이다. `window`는 전역 객체라 루트에서 항상 도달 가능하다. 여기에 이벤트 리스너를 등록하면, 그 리스너 함수가 `window → listener → 클로저 내 변수` 순서로 체인이 연결된다. 리스너를 제거하지 않는 한 이 체인은 유지되고, 클로저로 묶인 모든 것이 함께 메모리에 남는다.
```js
// 누수 발생
useEffect(() => {
  window.addEventListener('resize', handleResize);
}, []);

// 올바른 방식
useEffect(() => {
  window.addEventListener('resize', handleResize);
  return () => window.removeEventListener('resize', handleResize);
}, []);
```

**타이머**도 같은 이유다. `setInterval`로 등록된 콜백은 타이머 큐를 통해 루트와 연결된 상태를 유지한다. `clearInterval`로 해제하기 전까지는 콜백 내부에서 참조하는 모든 것이 수거되지 않는다. 언마운트된 컴포넌트의 `setState`를 계속 호출하는 상황이 여기서 나온다.

**전역/모듈 스코프에 데이터를 계속 쌓는 패턴**도 주의가 필요하다. 루트에서 항상 참조 가능한 변수에 데이터를 계속 추가하면 GC는 절대 수거할 수 없다. 캐시 용도로 배열이나 객체를 모듈 상단에 선언하고 데이터를 계속 추가하는 경우가 대표적이다. 적절한 만료 전략 없이 무한정 쌓이면 메모리가 계속 증가한다.

## 컴포넌트 언마운트 ≠ 메모리 해제

React를 쓰면서 오해하기 쉬운 지점이 있다. 컴포넌트가 언마운트되면 그 컴포넌트가 만들어놓은 것들이 전부 정리된다고 생각하기 쉽다. 나도 그렇게 생각했었다.

React가 컴포넌트를 언마운트하면 Virtual DOM에서 제거되고 이후 리렌더링도 발생하지 않는다. 하지만 컴포넌트 함수가 실행되는 동안 외부에 남긴 흔적, 즉 `window`에 등록한 이벤트 리스너, 돌아가고 있는 타이머, 외부 라이브러리 구독 같은 **사이드이펙트는 React가 자동으로 정리하지 않는다.** 이것이 `useEffect`가 cleanup 함수를 반환하는 이유다. React는 컴포넌트가 언마운트될 때 그 cleanup을 실행한다.

클로저 자체가 누수라는 오해도 많은데, 클로저가 있다는 것만으로 누수가 생기지는 않는다. 클로저를 담고 있는 함수가 더 이상 참조되지 않으면 GC가 클로저 스코프까지 함께 수거한다. 문제는 클로저를 담은 함수가 `window` 같은 루트 연결 객체에 등록돼서 **불필요하게 오래 살아있는 경우**다.

## 누수를 찾는 방법

실제로 누수가 의심될 때는 두 단계로 접근한다.

**1단계 — 누수 여부 확인**
Chrome DevTools의 Performance Monitor(점 세 개 → More tools → Performance monitor)에서 실시간 JS heap size를 본다. 특정 동작을 반복할 때 heap 그래프가 계속 우상향하고 내려오지 않으면 누수를 의심한다.

**2단계 — 원인 추적**
Memory 탭의 Heap Snapshot을 활용한다. 의심 동작 전후로 스냅샷을 찍고 Comparison 뷰로 비교하면, 동작 후에 새로 생겼지만 정리되지 않은 객체가 무엇인지 파악할 수 있다. 언마운트한 컴포넌트 관련 객체가 잔존하면 누수가 확정된다.

다만 실무에서는 프로파일러보다 **코드 리뷰 단계에서 패턴으로 예방**하는 경우가 더 많다. `addEventListener`가 있으면 `removeEventListener`를, `setInterval`이 있으면 `clearInterval`을, 외부 구독이 있으면 해제 로직을 짝으로 확인하는 식이다. 프로파일러는 누수가 발생한 이후 원인을 추적할 때 쓰고, 예방은 코드 패턴으로 하는 게 현실적이다.

## 마무리

GC를 이해하고 나면 결국 메모리 관리는 "JavaScript가 알아서 해준다"가 아니라 **"GC가 수거할 수 있는 구조를 만드는 것"** 이라는 걸 알게 된다.

`useEffect`의 cleanup, 이벤트 리스너 제거, 타이머 정리 — 이것들이 전부 같은 이유에서 필요하다. 루트에서 참조 체인을 끊어줘야 GC가 일을 할 수 있다.
