**핵심 요약**
* URL 입력부터 화면 렌더링까지는 DNS 조회 → TCP 연결 → HTTP 요청/응답 → 브라우저 렌더링의 단계가 순서대로 연결된 하나의 흐름이다.
* 첫 요청이 느린 이유는 HTTP 요청 전에 이미 여러 번의 네트워크 왕복이 발생하기 때문이다.
* 각 단계가 왜 필요한지를 이해해야, 캐싱·성능 최적화·HTTPS 비용 같은 개념이 자연스럽게 연결된다.

## 주소창에 URL을 입력하면?

"브라우저 주소창에 URL을 치고 엔터를 눌렀을 때 무슨 일이 일어나나요?"

질문을 듣고, 웹 개발자라면 당연히 알아야 하는 질문이라고 생각했다. 그런데 생각나는 답변은 이랬다.
"DNS에 주소를 요청하고, 받아온 주소로 http요청을 보내 html을 받아옵니다."
아예 틀리진 않았을 것이다. 하지만 너무 얕게 알고 있었다.

실제로는 어떤지 자세히 찾아봤고, 대략적으로 다음과 같이 정리할 수 있었다.

```
URL 파싱 및 캐시 확인
       ↓
  DNS 조회 (도메인 → IP)
       ↓
TCP 3-way Handshake
       ↓
TLS Handshake (HTTPS인 경우)
       ↓
  HTTP 요청 / 응답
       ↓
  브라우저 렌더링
```

각 단계는 독립된 개념이 아니라 하나의 흐름으로 이어진다.
순서대로 살펴보자.

---

## Step 1 — 캐시 확인

브라우저는 URL을 파싱한 뒤 곧바로 네트워크 요청을 보내지 않는다.
먼저 캐시를 확인한다.

```
브라우저 캐시 → 있으면 즉시 사용
      ↓ 없으면
OS DNS 캐시 → 있으면 즉시 사용
      ↓ 없으면
라우터 캐시 → 있으면 즉시 사용
      ↓ 없으면
DNS 조회 시작
```

이미 방문한 사이트라면 브라우저 캐시나 OS 캐시에서 IP가 바로 나온다.
이 경우 DNS 조회 전체를 건너뛰기 때문에 체감 속도 차이가 크다.

캐시에는 TTL(Time To Live)이 설정되어 있다.
TTL이 만료되기 전까지는 같은 IP를 그대로 사용하고, 만료되면 다시 DNS 조회를 한다.

---

## Step 2 — DNS 조회

캐시에 없으면 도메인 이름을 IP 주소로 변환해야 한다.
이 과정을 **DNS(Domain Name System) 조회**라고 한다.

```
브라우저
  → Recursive Resolver (ISP 또는 8.8.8.8)
      → Root DNS 서버    (.com 담당 TLD 서버가 어디인지 응답)
      → TLD DNS 서버     (example.com 담당 서버가 어디인지 응답)
      → Authoritative DNS 서버 (example.com의 실제 IP 응답)
  ← IP 주소 반환
```

Root → TLD → Authoritative 순서로 계층을 내려가며 탐색한다.
처음에는 "왜 이렇게 복잡하게 가는가" 싶었는데, 이유가 있다.
전 세계 도메인 레코드가 수십억 개인데 하나의 서버가 전부 관리하는 건 불가능하다.
책임을 계층적으로 분산시켜서 관리한다.

DNS 조회는 네트워크 왕복이 여러 번 발생하기 때문에 느리다.
그래서 결과를 TTL 기반으로 캐싱해서 재사용한다.

> **주의:** DNS 캐시는 브라우저 하나에만 있는 게 아니다.
> 브라우저, OS, 라우터, ISP 레벨로 여러 계층에 존재한다.
> 브라우저 캐시를 지워도 OS 캐시에 남아 있으면 같은 IP로 연결된다.

---

## Step 3 — TCP 연결과 TLS 핸드셰이크

IP를 알았으면 서버와 연결을 맺는다.
TCP는 데이터를 보내기 전에 반드시 연결 수립 과정이 필요하다.
이게 **3-way Handshake**다.

```
클라이언트 →  SYN       → 서버  ("연결할게")
클라이언트 ←  SYN-ACK  ← 서버  ("알겠어, 나도 준비됐어")
클라이언트 →  ACK       → 서버  ("확인")
```

이 3번의 왕복이 끝나야 데이터를 주고받을 수 있다.

**HTTPS라면 TCP 핸드셰이크 이후에 TLS 핸드셰이크가 추가된다.**
TLS 핸드셰이크에서는 어떤 암호화 방식을 쓸지 협상하고, 서버 인증서를 검증하고, 세션 키를 교환한다.
왕복이 1~2번 더 발생한다.

여기서 첫 요청이 느린 이유가 나온다.
HTTP 요청을 보내기도 전에 DNS 조회 + TCP 핸드셰이크 + TLS 핸드셰이크로 이미 네트워크 왕복이 여러 번 쌓인다.

> **참고:** TLS 핸드셰이크 비용은 Session Resumption으로 줄일 수 있다.
> 이미 연결했던 서버라면 세션 정보를 재사용해서 TLS 협상 과정을 단축한다.

---

## Step 4 — HTTP 요청과 응답

연결이 수립되면 브라우저가 HTTP 요청을 보낸다.

```
GET /index.html HTTP/1.1
Host: example.com
Accept: text/html
Cache-Control: no-cache
```

서버는 상태 코드, 헤더, 바디를 포함한 응답을 돌려준다.

```
HTTP/1.1 200 OK
Content-Type: text/html
Cache-Control: max-age=3600

<!DOCTYPE html>...
```

`Cache-Control: max-age=3600`은 이 응답을 3600초 동안 캐시해도 된다는 뜻이다.
다음 방문 때는 Step 1에서 캐시가 히트되어 네트워크 요청 없이 바로 사용할 수 있다.

---

## Step 5 — 브라우저 렌더링

응답받은 HTML을 바탕으로 브라우저가 화면을 그린다.
이 흐름은 [#008 브라우저 렌더링 과정](/blog/fe-concepts/008/)에서 자세히 다뤘으므로 핵심 흐름만 정리한다.

```
HTML 파싱 → DOM 생성
CSS 파싱  → CSSOM 생성
           ↓
      Render Tree 생성
           ↓
     Layout (위치/크기 계산)
           ↓
          Paint
           ↓
        Composite
```

여기서 주의할 점이 있다.
HTML을 다 받아야 렌더링이 시작된다고 생각하기 쉬운데, 브라우저는 HTML을 **스트리밍으로 파싱**한다.
전체를 받기 전에도 위에서부터 DOM을 구성하고, CSS나 JS 같은 리소스를 미리 다운로드하기 시작한다.

그리고 파싱 도중 `<script>` 태그를 만나면 파싱이 멈추고 JS 실행이 끝날 때까지 기다린다.
`defer`나 `async` 속성을 쓰는 이유가 여기에 있다.

## 연결 재사용 — 두 번째 요청은 왜 빠른가

첫 번째 방문이 느린 이유는 DNS 조회부터 TLS 핸드셰이크까지 모든 단계를 처음부터 밟기 때문이다.

두 번째 방문이 빠른 이유는 두 가지다.

**첫째, DNS 캐시.** 이미 IP를 알고 있으니 DNS 조회를 건너뛴다.

**둘째, TCP 연결 재사용.** HTTP/1.1은 기본적으로 **Keep-Alive**가 활성화되어 있어서 한 번 맺은 TCP 연결을 여러 요청에 재사용한다. HTTP/2에서는 **멀티플렉싱**으로 하나의 TCP 연결 위에서 여러 요청을 동시에 처리한다.

이 두 레이어의 캐싱이 실제 체감 성능 차이를 만든다.
"재방문 페이지가 더 빠른 이유"는 단순히 브라우저 캐시만이 아니라, 연결 수립 비용 자체가 줄어들기 때문이다.
