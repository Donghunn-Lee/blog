💡 **핵심 요약**
- Hooks는 함수 컴포넌트가 state, lifecycle, context 같은 React의 기능에 "접속"할 수 있게 해주는 함수다. 클래스 컴포넌트의 wrapper hell, 흩어진 라이프사이클, this 바인딩 문제를 한 번에 해결한다.
- React는 컴포넌트마다 Hook들을 **연결 리스트로 저장**하고, **호출 순서**로 식별한다. 이 구현 방식이 Hook 규칙(최상위에서만 호출)의 직접적인 원인이다.
- Custom Hook은 React가 특별 지원하는 기능이 아니라, "내부에서 다른 Hook을 호출하는 함수"라는 단순한 패턴이다. 이 단순함이 클래스 시대의 로직 재사용 문제를 풀어버렸다.

## Hooks가 등장하기 전, 클래스 컴포넌트의 한계

React 16.8 이전에는 **함수 컴포넌트가 상태도, 라이프사이클도 갖지 못했다.**
상태가 필요하면 무조건 클래스 컴포넌트를 써야 했고, 그 시절 코드를 만지면 곧 세 가지 위험을 만난다.

**첫째, wrapper hell.**

같은 로직을 여러 컴포넌트에서 재사용하려면 HOC(Higher-Order Component)나 Render Props를 썼다.
둘 다 "컴포넌트로 컴포넌트를 감싸는" 방식이라, 몇 개만 합쳐도 트리가 이렇게 된다.

```jsx
<WithRouter>
  <WithTheme>
    <WithUser>
      <WithAnalytics>
        <ActualComponent />
      </WithAnalytics>
    </WithUser>
  </WithTheme>
</WithRouter>
```

DevTools를 켜면 의미 없는 wrapper가 트리를 채우고, props가 어디서 내려오는지 추적도 어렵다.

**둘째, 라이프사이클에 따라 흩어지는 로직.**

논리적으로 하나인 코드가 라이프사이클 메서드 단위로 쪼개진다.

```jsx
componentDidMount() {
  this.subscription = subscribe(...);   // 시작
  document.addEventListener(...);       // 또 다른 시작
}

componentWillUnmount() {
  this.subscription.unsubscribe();      // 시작과 멀리 떨어진 해제
  document.removeEventListener(...);
}
```

"구독 시작 → 구독 해제"라는 한 묶음이 두 메서드로 갈라진다.
컴포넌트가 커질수록 어느 cleanup이 어느 시작과 짝인지 찾기 어려워진다.

**셋째, `this` 바인딩.**

[#004 this 바인딩](/blog/fe-concepts/004/)에서 다뤘듯이, JavaScript의 `this`는 호출 방식으로 결정된다.
클래스 메서드를 이벤트 핸들러로 그냥 넘기면 `this`가 사라지기 때문에, 매번 `bind`를 걸거나 화살표 함수로 정의해야 했다.
보일러플레이트가 늘고, 빠뜨리면 런타임 에러가 났다.

Hooks는 이 세 가지를 한 번에 해결하기 위해 도입됐다.

## Hook이란 무엇인가

> Hook은 **함수 컴포넌트에서 React의 기능에 "접근"할 수 있게 해주는 함수**다.

`use`로 시작하는 함수가 Hook이라는 규약이고, `useState`, `useEffect`, `useContext`, `useRef`, `useMemo`, `useCallback` 등이 React가 제공하는 빌트인 Hook이다.
직접 만든 함수가 내부에서 다른 Hook을 호출하면 그 함수도 Hook이 된다 — 이걸 **Custom Hook**이라고 부른다.

Hooks가 가져온 변화는 두 가지다.

- 함수 컴포넌트가 **클래스의 모든 능력**을 가질 수 있게 됐다
- **상태가 있는 로직**을 컴포넌트 트리를 늘리지 않고 함수처럼 재사용할 수 있게 됐다

여기까지는 표면적인 설명이다. 이제 안으로 들어간다.

## React는 Hook을 호출 순서로 식별한다

함수 컴포넌트는 매 렌더마다 **함수가 처음부터 다시 실행**된다 ([#021](/blog/fe-concepts/021/) 참조).
그런데 `useState(0)`을 호출했을 때, React는 어떻게 이 컴포넌트가 이전 렌더에서 어떤 값을 들고 있었는지 기억할까?

답은 단순하다. **React가 컴포넌트 외부에서 Hook들을 연결 리스트로 들고 있다.**

함수 컴포넌트가 렌더링될 때, React는 그 컴포넌트의 Fiber 노드 안에 Hook 리스트를 매단다.
컴포넌트 안에서 Hook이 호출될 때마다 리스트의 다음 노드로 이동한다.

```jsx
function Profile() {
  const [name, setName] = useState("Ethan");      // 1번 Hook
  const [age, setAge]   = useState(26);           // 2번 Hook
  useEffect(() => { /* ... */ }, [name]);         // 3번 Hook
}
```

첫 렌더에서 React는 이 컴포넌트의 Hook 리스트를 다음과 같이 구성한다.

```
Hook[0] → { state: "Ethan",   next: → }
Hook[1] → { state: 26,        next: → }
Hook[2] → { effect: ...,
            deps: ["Ethan"],  next: null }
```

리렌더링이 일어나면 React는 같은 함수를 다시 실행하면서 Hook 호출을 처음부터 따라간다.
이때 React는 이름이 아니라 **"이번이 몇 번째 Hook 호출인가"** 만 본다.

`useState("Ethan")`이라고 써도 React 입장에선 "이 컴포넌트의 첫 번째 Hook"일 뿐이다.
두 번째 호출이 `useState(26)`이면 "두 번째 자리에는 숫자 state"라고 기억한다.

> **핵심:** React는 Hook을 **이름이 아니라 호출 순서로 식별한다.**

이 한 줄이 다음 섹션의 모든 것을 결정한다.

## Hook 규칙은 왜 존재하는가

React에서 Hook을 사용하기 위해선, 반드시 지켜야 할 규칙이 2가지 있다.

1. **최상위(top level)에서만 호출한다** — 조건문, 반복문, 중첩 함수 안에서 호출 금지
2. **React 함수 안에서만 호출한다** — 함수 컴포넌트 또는 Custom Hook 내부

규칙 2는 직관적이다. Hook은 React가 관리하는 컴포넌트 컨텍스트 위에서 동작하니까.

규칙 1이 왜 필요한지가 진짜 질문이다.

```jsx
function Profile({ user }) {
  if (user) {
    const [name, setName] = useState(user.name);  // ⚠️ 조건부 호출
  }
  const [age, setAge] = useState(0);
  useEffect(() => { /* ... */ });
}
```

첫 렌더에서 `user`가 있으면 Hook 호출 순서는 `[name, age, effect]`.
다음 렌더에서 `user`가 `null`이 되면 호출 순서는 `[age, effect]`로 바뀐다.

React가 "두 번째 자리는 age"라고 기억해뒀는데, 이번 렌더의 두 번째 자리는 effect다.
**자리가 어긋나면서 React는 이전 렌더의 age state를 effect에 매핑하려고 시도한다.**
결과는 예측 불가능한 버그다.

> **Hook 규칙은 자의적인 제약이 아니라, "호출 순서로 Hook을 식별한다"는 구현 방식의 직접적인 결과다.**

ESLint 경고로 끝나는 스타일 가이드가 아니라, **어기면 런타임이 깨지는 정합성 조건**이다.
`eslint-plugin-react-hooks`가 강하게 강제하는 이유가 여기에 있다.

## Custom Hook — 함수가 함수를 부를 뿐

Hook이 단순한 함수이고, 그 안에서 다른 Hook을 호출할 수 있다는 사실에서 Custom Hook이 자연스럽게 정의된다.

```jsx
function useUser(userId) {
  const [user, setUser] = useState(null);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    fetchUser(userId).then(data => {
      setUser(data);
      setLoading(false);
    });
  }, [userId]);

  return { user, loading };
}
```

이걸 컴포넌트에서 `const { user, loading } = useUser(123)`처럼 호출하면, React 입장에서는 그 컴포넌트의 Hook 리스트에 `useState`, `useState`, `useEffect`가 차례로 등록될 뿐이다.

> **Custom Hook은 React가 특별히 지원하는 기능이 아니다. "Hook을 호출하는 함수"라는 단순한 패턴이다.**

`use` 접두사는 ESLint가 Hook 규칙을 적용하기 위한 컨벤션이지, React가 알아보는 키워드가 아니다.
같은 Custom Hook을 두 컴포넌트에서 쓰면 각자의 Hook 리스트에 따로 등록되므로, **state가 공유되지 않는다.** 로직만 공유되고 인스턴스는 분리된다.

이 단순함이 클래스 시대의 wrapper hell을 풀어버렸다.
컴포넌트 트리를 늘리지 않고도 상태 로직만 함수 단위로 분리해서 재사용할 수 있게 됐다.

## Hooks와 클로저, 그리고 stale closure

Hook이 동작하는 토대는 직전 글 [#023 State와 Props](/blog/fe-concepts/023/)에서 다룬 "state as a snapshot" 모델이다.
함수 컴포넌트는 매 렌더마다 새로운 함수 실행 컨텍스트를 만들고, 그 안의 모든 변수는 **그 렌더 시점에 캡처된 클로저** 안에 갇힌다.

이 모델이 만드는 유명한 함정이 **stale closure**다.

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      console.log(count);  // 이 count는 effect가 등록된 렌더의 값
    }, 1000);
    return () => clearInterval(id);
  }, []);  // ⚠️ deps가 빈 배열
}
```

deps가 빈 배열이면 effect는 마운트 시점에 한 번만 등록된다.
그 effect 안의 `count`는 첫 렌더의 클로저에 캡처된 값이라, count가 1, 2, 3으로 바뀌어도 콜백이 보는 값은 영원히 0이다.

이건 React의 버그가 아니라 클로저의 자연스러운 귀결이다.
함수가 정의된 시점의 변수를 기억하는 게 클로저인데, effect 콜백은 첫 렌더 시점에 정의됐으니까.

해결은 두 가지다.
deps 배열에 `count`를 넣어 effect를 다시 등록하거나, `setCount(prev => prev + 1)`처럼 함수형 업데이트로 최신 값에 접근하거나.

> **Hook을 이해한다는 건 React를 이해하는 것보다, 함수와 클로저를 이해하는 것에 가깝다.**

## 정리 — 단순한 함수가 만드는 일관성

Hooks가 React 생태계를 바꾼 이유는 새로운 기능을 얹어서가 아니다.
**기존 JavaScript의 함수와 클로저로 컴포넌트의 상태와 사이드 이펙트를 표현할 수 있게** 만들었기 때문이다.

이 모델이 자연스럽게 풀어주는 것들이 있다.

- **로직 재사용** — Custom Hook이라는 함수 호출만으로 가능. wrapper 트리 불필요
- **흩어진 라이프사이클** — 관련 로직이 effect 단위로 묶임. setup과 cleanup이 같은 함수 안에 있음
- **this 바인딩** — 함수에는 this 문제가 없음

대신 새로운 학습 곡선이 생겼다. 호출 순서, 의존성 배열, stale closure — 이것들은 React를 잘 쓰려고 외우는 규칙이 아니라, **함수 컴포넌트의 동작 모델을 이해하면 자동으로 따라오는 결과**다.

Hook 규칙을 "지켜야 하는 제약"으로 보면 외워야 할 게 늘어난다.
하지만 **"React가 호출 순서로 Hook을 식별하기 때문에 어쩔 수 없는 정합성 조건"** 으로 보면, 규칙은 특별한 것이 아니라 당연하게 된다.
