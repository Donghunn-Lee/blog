💡 **핵심 요약**
- React Fiber는 재조정(reconciliation)을 **재귀 호출이 아닌 연결 리스트 순회**로 바꾼 아키텍처다.
- 이 자료구조 변화가 "렌더링을 중간에 멈췄다 다시 시작할 수 있다"는 성질을 만든다.
- Fiber 자체가 Concurrent Rendering은 아니다. Concurrent가 가능해지는 **토대**를 만든 구조일 뿐이다.

---

## #021에서 미뤄둔 질문

[이전 글](https://velog.io/@dh82680/React의-렌더링이란-FE-개념-탐구-021)에서 React의 렌더링을 **Render Phase**와 **Commit Phase** 두 단계로 나눠서 봤다. 그리고 이렇게 정리했다.

> Render Phase는 **순수 계산**이라 중단하거나 버리거나 다시 실행해도 안전하고, Commit Phase는 실제 DOM을 건드리기 때문에 한 번에 끝내야 한다.

그런데 거기서 미뤄둔 질문이 있다.

**"Render Phase를 어떻게 중간에 멈출 수 있는가?"**

재귀 호출은 한 번 시작하면 스택을 타고 끝까지 내려가야 한다.
"지금 Component B까지 처리했으니까 잠깐 멈추고 나중에 이어서 해줘"
같은 일을 재귀로는 할 수 없다. 그러면 React는 어떻게 중단 가능한 렌더링을 구현한 걸까?

답은 **렌더링을 구현하는 자료구조 자체를 바꾼 것**에 있다. 그게 Fiber다.

---

## Fiber의 등장 — 재귀 기반 렌더링의 한계

Fiber가 나온 배경부터 보자. React 15까지의 재조정은 단순했다. 루트 컴포넌트부터 리프까지 **재귀로 내려가며** Virtual DOM을 비교하고 DOM을 업데이트했다. 이걸 Stack Reconciler라고 부른다. 재귀 호출이 JS 엔진의 Call Stack을 타고 내려가는 구조였기 때문이다.

재귀의 본질적인 한계는 이것이다.

**한 번 시작하면 중간에 멈출 수 없다.**

구체적으로 어떤 일이 벌어지는지 보자.

```
[대형 리스트 렌더링 시작]
    ↓ reconcile(App) 호출 → 자식들 재귀로 탐색
[reconcile이 Call Stack에 계속 쌓이며 메인 스레드 독점]
    ↓
[사용자가 input에 타이핑 → 이벤트가 큐에 대기]
    ↓ Call Stack이 비어야 이벤트 루프가 처리 가능
[reconcile 재귀가 아직 안 끝남 → input 이벤트 처리 못 함]
    ↓
[16.6ms 넘어감 → 프레임 드롭]
    ↓
[reconcile 완료 후에야 타이핑 반영 → 몇백 ms 지연]
```

JavaScript는 싱글 스레드다. 하나의 task가 메인 스레드를 오래 잡고 있으면 그 뒤에 쌓인 모든 것이 밀린다. Stack Reconciler는 이걸 구조적으로 해결할 수 없었다.

**Fiber는 이 문제를 해결하기 위해 React 16에서 도입된 새로운 재조정 엔진이다.**

---

## Fiber의 자료구조 - 연결 리스트

Fiber는 두 개의 얼굴을 가진다.

| 관점 | 정체 |
|------|------|
| **자료구조** | 각 컴포넌트마다 하나씩 대응되는 노드. "이 컴포넌트의 작업"을 나타내는 객체 |
| **알고리즘** | 그 노드들을 **반복(loop)** 으로 순회하면서 재조정하는 방식 |

재귀가 아닌 반복으로 트리를 순회하려면 트리 구조도 그에 맞게 바뀌어야 한다. Fiber 노드는 세 개의 포인터를 가진 연결 리스트 형태다.

```
Fiber 노드
├── child    → 첫 번째 자식
├── sibling  → 다음 형제
└── return   → 부모
```

이 포인터들만으로 트리 전체를 순회할 수 있다.

```
1. child가 있으면 → child로 내려간다
2. child가 없으면 → sibling으로 이동한다
3. sibling도 없으면 → return으로 올라가서 거기서 sibling을 찾는다
```

여기서 핵심이 나온다.

재귀는 Call Stack에 프레임이 쌓이는 구조다. 중단하려면 스택을 통째로 버려야 하고, 재개하려면 그 시점의 모든 호출 프레임을 복원해야 한다. 사실상 불가능하다.

반면 연결 리스트 순회는 **"지금 어느 노드에 있는지" 포인터 하나만 기억하면** 언제든 멈췄다가 그 지점부터 재개할 수 있다.

**자료구조를 바꾼 것 자체가 인터럽트 가능성을 만든 것이다.** #021에서 말한 "Render Phase는 중단 가능하다"는 성질은 이 구조 덕분에 성립한다.

---

## 더블 버퍼링 — 두 개의 트리를 유지하는 이유

Render Phase가 중단되고 재개된다는 건 작업이 진행 중인 상태가 **중간 단계로 존재한다**는 뜻이다. 이 중간 상태가 현재 화면에 영향을 주면 안 된다. 그래서 React는 두 개의 Fiber 트리를 유지한다.

```
current tree        ← 현재 화면에 반영된 상태
workInProgress tree ← 지금 만들고 있는 다음 상태
```

Render Phase에서는 `workInProgress` 트리만 수정한다. `current`는 절대 건드리지 않는다.
Commit Phase에서 작업이 완료되면 **두 포인터를 스왑**한다. 이제 `workInProgress`가 `current`가 된다.

단일 트리를 직접 수정하면서 중간에 인터럽트되면 트리가 일관성 없는 중간 상태로 남는다. 더블 버퍼링은 **"완성될 때까지 따로 만들고, 완성되면 한 번에 교체"** 하는 방식으로 이걸 방지한다.

게임 렌더링이나 OS 화면 버퍼링과 같은 원리다. 사용자가 절반만 그려진 화면을 보지 않게 하는 전형적인 기법을 React가 재조정에 가져왔다.

> **주의:** Concurrent Rendering에서 높은 우선순위 작업이 들어오면 지금까지 만들던 `workInProgress` 트리를 통째로 버리고 처음부터 다시 시작할 수도 있다. `current`는 계속 그대로이기 때문에 화면은 안전하다.

## 작업을 쪼개는 주체 — Scheduler

Fiber가 "중단 가능한 구조"라면, "**언제 중단할지**"는 누군가 판단해야 한다. 이 역할을 하는 게 Scheduler다.

작업 루프는 대략 이렇게 생겼다.

```js
while (nextFiber && !shouldYield()) {
  nextFiber = performUnitOfWork(nextFiber);
}
```

여기서 `shouldYield()`가 핵심이다. "지금 브라우저에 제어권을 돌려줘야 하는가?"를 판단한다. 기준은 주로 **남은 시간**이다. 브라우저가 준 타임 슬라이스(보통 5ms)를 다 쓰면 yield한다.

yield 이후의 흐름:

```
[React가 Fiber 5까지 처리 후 yield]
    ↓
[Fiber 5 위치를 기억]
    ↓
[브라우저가 input 처리, paint 수행]
    ↓
[Scheduler가 다시 React에 제어권 돌려줌]
    ↓
[기억해둔 Fiber 5부터 재개]
```

여기에 **우선순위** 개념이 더해진다.

- 사용자 입력 반응 → 높은 우선순위 (즉시)
- 네트워크 응답 업데이트 → 보통 우선순위
- Transition (페이지 전환 등) → 낮은 우선순위 (다른 작업에 밀릴 수 있음)

React 18의 `startTransition`(업데이트를 낮은 우선순위로 표시), `useDeferredValue`(값 소비를 뒤로 미룸), `Suspense`(데이터 준비 전까지 렌더링을 중단)가 모두 이 우선순위 시스템 위에서 동작한다.

## Fiber는 Concurrent의 "기반"이지, Concurrent 자체가 아니다

이 지점이 제일 많이 오해받는 부분이다.

**React 16에 Fiber가 들어갔지만, 실제 렌더링은 여전히 동기적으로 동작했다.** Fiber는 "쪼갤 수 있는 구조"를 만들어뒀을 뿐이고, 실제로 "쪼개서 처리한다"는 동작은 React 18의 `createRoot`와 Concurrent 기능들이 활성화되면서 본격적으로 쓰였다.

```
React 16 ~ 17
├── Fiber 자료구조 O
├── 실제 중단/재개 X  (레거시 모드)
└── 구조만 준비됨

React 18+
├── Fiber 자료구조 O
├── createRoot로 Concurrent 기능 활성화
└── startTransition, Suspense 등이 실제로 동작
```

Fiber = Concurrent가 아니라, **Fiber는 Concurrent를 가능하게 만든 토대**다. 그리고 #021에서 강조한 "Render Phase는 순수해야 한다"는 규칙이 왜 그렇게까지 강조되는지도 여기서 한 번 더 납득된다. 우선순위에 밀려 `workInProgress`가 통째로 버려지고 다시 시작될 수 있는 환경이기 때문이다.

## 헷갈리기 쉬운 지점들

**1. Fiber는 Virtual DOM이다?**

Virtual DOM은 "실제 DOM의 가상 표현"이라는 **개념**이고, Fiber는 그 개념을 구현하는 **구체적인 자료구조이자 알고리즘**이다. React 15도 Virtual DOM을 썼지만 Fiber는 아니었다. 같은 개념을 구현하는 방식이 바뀐 것이다.

**2. Fiber 도입으로 React가 무조건 빨라졌다?**

절대 작업량(total work)은 Fiber가 더 클 수도 있다. 쪼개는 오버헤드와 스케줄링 비용이 추가됐기 때문이다.
Fiber가 개선한 건 **체감 성능(perceived performance)** 이다. 전체 작업 시간이 줄어든 게 아니라, 그 사이사이 사용자 입력에 반응할 수 있게 된 것이다.

**3. 중단됐다가 재개되는 거면 어쨌든 같은 Render Phase가 여러 번 실행될 수도 있는 것 아닌가?**

맞다. 그리고 더 나아가, 높은 우선순위 작업이 들어오면 지금까지 만든 `workInProgress`를 버리고 처음부터 다시 실행되기도 한다. 이래서 컴포넌트 함수 안에서 네트워크 요청을 하거나 외부 상태를 직접 바꾸면 안 된다. 한 번의 "렌더링"이 실제로 몇 번 실행될지 개발자가 제어할 수 없기 때문이다.

## React Fiber 정리

#021에서 "렌더링은 함수 실행이고, Render Phase는 중단될 수 있다"고 봤다. #022에서 그 중단이 어떻게 가능해지는지를 봤다. 이 둘을 합치면 React의 렌더링 모델이 하나의 그림으로 정리된다.

**렌더링은 "한 번에 완주하는 작업"이 아니라 "쪼갤 수 있는 작업의 스트림"이다.**

이 관점이 자리잡으면 `startTransition`이나 `useDeferredValue` 같은 API가 다르게 보인다. 단순히 "성능 최적화 훅"이 아니라 **"이 업데이트는 낮은 우선순위야, 급한 일 있으면 먼저 처리해"라고 스케줄러에게 알려주는 태그**라는 게 보인다. 작동하는 기반 구조(Fiber 순회 + Scheduler)가 있기 때문에 우선순위라는 개념이 의미를 가진다.

React 19의 React Compiler, Server Components, `use` 훅 같은 것들도 전부 이 Fiber + Scheduler 기반 위에서 설계되고 있다. 여기를 이해해두면 앞으로 나올 API들도 훨씬 빠르게 맥락을 잡을 수 있을 것이다.
