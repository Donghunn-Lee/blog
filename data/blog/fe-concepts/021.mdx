**핵심 요약**
- React의 "렌더링"은 화면을 그리는 것이 아니라 **컴포넌트 함수를 실행해서 UI 설명서(React Element)를 만드는 과정**이다.
- 리렌더링은 함수 재실행이고, DOM 업데이트는 그 결과가 이전과 달라야 일어나는 별개의 단계다.
- 이 구분이 명확해지면 `memo`, `useMemo` 같은 최적화를 언제 써야 하는지 감이 아니라 근거로 판단할 수 있다.

## 리렌더링에 대한 흔한 오해

React로 개발하다 보면 이런 순간들이 쌓인다.

- 버튼 하나 눌렀는데 관련 없어 보이는 컴포넌트까지 다시 실행되는 것 같다
- `console.log`를 찍어보니 내가 예상한 것보다 훨씬 자주 찍힌다
- `memo`를 붙였는데 왜 여전히 리렌더링되는지 모르겠다
- Profiler를 켜 보니 화면에 아무 변화가 없는데도 특정 컴포넌트가 계속 리렌더링되고 있다

이 모든 상황은 결국 하나의 질문으로 수렴한다.

**"React는 언제, 왜, 어떻게 다시 실행되는가?"**

이걸 이해하지 못하면 최적화는 감으로 하게 되고, 성능 문제가 생겼을 때 원인을 짚지 못한다. 반대로 이걸 정확히 이해하면 이후에 만나게 될 Hooks 동작 방식, Context 리렌더링 문제, memo 최적화가 전부 같은 뿌리에서 설명된다.

## 렌더링은 두 단계로 나뉜다

React에서 "렌더링"이라는 말을 들으면 대부분 화면이 다시 그려지는 장면을 떠올린다.
하지만 React 내부에서 렌더링은 **화면을 그리는 것이 아니라, 컴포넌트 함수를 실행해서 React Element라는 UI 설명서를 만드는 과정**이다.

React가 화면을 업데이트하는 과정은 크게 두 단계로 나뉜다.

```
Render Phase (렌더 단계)
  ↓ 컴포넌트 함수 실행 → React Element 생성 → 이전과 비교(Reconciliation)
Commit Phase (커밋 단계)
  ↓ 실제 DOM에 변경사항 반영
```

우리가 흔히 "리렌더링"이라고 부르는 것은 대부분 **Render Phase**를 의미한다. 즉, 컴포넌트 함수가 다시 실행되는 것이다.

**실제 DOM이 바뀌는 것과는 별개다.** 이 지점을 명확히 하고 넘어가는 것이 이 글 전체의 축이다.

---

## 리렌더링은 언제 발생하는가

React는 아무 이유 없이 컴포넌트를 다시 실행하지 않는다. 다음 세 가지 중 하나가 트리거된다.

1. **해당 컴포넌트의 state가 변경될 때** (`useState`의 setter 호출)
2. **부모 컴포넌트가 리렌더링될 때**
3. **구독 중인 Context 값이 바뀔 때**

여기서 짚고 갈 지점이 있다.
"props가 바뀌면 리렌더링된다"는 설명을 자주 보는데, 이건 엄밀히 말하면 틀렸다.

**props가 바뀌는 것은 결과지 원인이 아니다.**
부모가 리렌더링되면서 새 props를 내려주는 것이고, 자식은 부모가 리렌더링되었기 때문에 같이 실행되는 것이다. props가 바뀌지 않아도 부모가 리렌더링되면 자식은 실행된다.

왜 이렇게 동작할까?
React는 props 변경을 감지해서 자식을 실행하는 방식이 아니기 때문이다. 렌더링 모델은 단순하다. **부모 함수가 실행되면 그 안의 JSX가 평가되고, 그 과정에서 자식 컴포넌트 함수도 호출된다.**

```jsx
function Parent() {
  return <Child name="ethan" />; 
  // Parent가 실행될 때마다 <Child />가 평가되고
  // 그 과정에서 Child 함수가 호출됨
}
```

React가 모든 컴포넌트에 대해 props 비교를 기본값으로 하지 않는 이유는 비교 자체도 비용이기 때문이다. 대부분의 컴포넌트는 비교 비용보다 그냥 재실행하는 비용이 더 싸다. 그래서 비교가 필요하면 `React.memo`로 명시적으로 opt-in해야 한다.

## Render Phase — 함수 실행

트리거가 발생하면 React는 해당 컴포넌트와 그 하위 트리의 컴포넌트 함수들을 실행한다.

이 단계에서 벌어지는 일은 다음과 같다.

```
1. 컴포넌트 함수 호출
   → 함수 내부 코드가 처음부터 끝까지 실행됨
   → Hook들이 순서대로 호출됨
   → JSX가 평가되어 React Element 객체가 반환됨

2. 새로 만들어진 Element 트리를 이전 트리와 비교 (Reconciliation)
   → "무엇이 달라졌는가"를 계산

3. 실제 DOM에 반영해야 할 변경사항 목록 생성
```

핵심은 **"함수가 실행된다"**는 사실이다.
매번 실행되기 때문에 함수 안에 있는 변수 선언, 함수 정의, 객체 리터럴이 **전부 새로 만들어진다.** 이것이 `useMemo`, `useCallback`이 존재하는 이유다. 참조를 렌더링 사이에 유지해주는 장치인 것이다.

그리고 Render Phase에는 반드시 지켜야 할 규칙이 하나 있다.

> **주의:** Render Phase는 순수(pure)해야 한다. 같은 입력에 같은 출력을 반환해야 하고, side effect(API 호출, DOM 조작, 전역 상태 수정)를 일으키면 안 된다.

이 규칙이 있는 이유는 React가 이 단계를 **중단하거나 여러 번 실행할 수 있기 때문**이다.

- **Concurrent Mode**에서는 더 급한 업데이트가 들어오면 진행 중이던 렌더링을 버리고 새로 시작한다
- **Strict Mode**는 개발 환경에서 컴포넌트 함수를 의도적으로 두 번 실행해서 부수 효과가 있는지 검출한다

만약 Render Phase에서 결제 API를 호출한다면 어떻게 될까? 렌더링이 중단되고 다시 시작되면 결제가 두 번 일어날 수도 있고, Strict Mode에서는 개발 중에도 이미 두 번 호출되고 있을 것이다. 그래서 side effect는 Commit 이후에 실행되는 `useEffect`로 옮겨야 한다.

## Commit Phase — DOM 반영

Render Phase에서 계산한 변경사항을 실제 DOM에 반영하는 단계다.

```
1. 실제 DOM 업데이트 (추가/수정/삭제)
2. ref 업데이트
3. useLayoutEffect 실행 (동기적)
4. 브라우저가 화면을 그림 (paint)
5. useEffect 실행 (비동기적)
```

여기서 다시 강조할 지점이 있다.
**컴포넌트 함수가 실행되었다고 해서 실제 DOM이 바뀐 것은 아니다.**

Render Phase에서 비교한 결과 "이전과 동일하다"고 판단되면 Commit Phase에서 DOM은 건드리지 않는다. 리렌더링(함수 재실행)과 DOM 업데이트는 별개의 개념이다.

이게 왜 중요할까? React DevTools Profiler에서 컴포넌트가 노란색/파란색으로 표시되는 것은 **함수가 재실행되었다**는 뜻이지, DOM이 바뀌었다는 뜻이 아니다. 이걸 구분하지 못하면 성능 문제를 진단할 때 병목이 Render Phase(함수 실행)에 있는지 Commit Phase(DOM 조작)에 있는지 판단하지 못하고 엉뚱한 곳을 최적화하게 된다.

## 두 단계로 나뉜 이유

처음 이 구조를 보면 "굳이 왜 나눴을까?" 싶다. 한 번에 함수 실행하고 DOM까지 업데이트하면 안 되는 걸까.

답은 **Render Phase를 중단하고, 버리고, 다시 실행할 수 있게 만들기 위해서**다.

Render Phase는 순수한 계산이다. 함수를 실행해서 Element 트리를 만들 뿐, 외부에 어떤 영향도 주지 않는다. 그래서 React는 이 단계를 중단하거나 여러 번 실행해도 안전하다.

반면 Commit Phase는 실제 DOM을 건드린다. 이걸 중간에 중단하면 화면이 반쯤 업데이트된 상태로 깨진다. 그래서 이 단계는 동기적으로, 한 번에, 중단 없이 실행된다.

만약 렌더링과 DOM 업데이트가 하나로 묶여 있었다면 어떻게 됐을까?
중간에 더 급한 업데이트(사용자 입력 같은)가 와도 현재 작업을 끝낼 때까지 사용자는 기다려야 했을 것이다. 두 단계를 나눴기 때문에 **"계산은 쪼개고, 반영은 한 번에"**가 가능하다. 이것이 Concurrent Rendering의 기반이다.

## 실전 이해

두 단계의 구분을 이해하고 나면 몇 가지가 새롭게 보인다.

**첫째, `React.memo`가 왜 자주 효과가 없는지 이해된다.**

memo는 이전 props와 새 props를 얕게 비교해서 같으면 Render Phase를 건너뛰게 해준다. 그런데 이렇게 쓰면 memo는 무력화된다.

```jsx
function Parent() {
  return <MemoChild options={{ size: 'large' }} onClick={() => {}} />;
  // options와 onClick이 매 렌더링마다 새 참조로 만들어짐
  // 얕은 비교는 항상 다르다고 판단 → memo가 의미 없음
}
```

Render Phase에서 함수가 매번 실행되기 때문에 안에 있는 객체 리터럴과 화살표 함수도 매번 새로 만들어진다. 이 사실을 이해하면 `memo`는 반드시 `useMemo`, `useCallback`과 세트로 써야 한다는 것이 자연스럽게 따라온다.

**둘째, "무조건 memo를 붙이자"가 왜 나쁜 전략인지 보인다.**

memo도 비교 비용이 있다. 컴포넌트 내용이 가벼우면 그냥 재실행하는 게 비교보다 싸다. 게다가 대부분의 Render Phase는 빠르고, 진짜 병목은 특정 무거운 컴포넌트에 집중되어 있다. **측정 없이 일괄 최적화하는 건 복잡도만 올리고 실제 개선은 없는 경우가 대부분**이다.

올바른 순서는 이렇다. React DevTools Profiler로 렌더링 시간을 확인한다. 명확히 느린 컴포넌트를 찾는다. 그 컴포넌트와 props를 넘기는 부모를 같이 손본다.

**셋째, `useState`의 setter가 비동기처럼 보이는 이유가 설명된다.**

```jsx
const [count, setCount] = useState(0);

const handleClick = () => {
  setCount(count + 1);
  console.log(count); // 여전히 0
};
```

setter는 현재 실행 중인 함수의 state를 바꾸는 게 아니다. **"다음 렌더링에서 이 값을 쓰겠다"고 예약할 뿐이다.** state는 렌더링 사이클 단위로 관리되기 때문에, 현재 함수 스코프 안의 `count`는 이번 렌더링의 스냅샷이고 그대로 유지된다. 다음 Render Phase가 시작되어야 새 값이 반영된다.

---

렌더링을 "화면이 그려지는 순간"이 아니라 **"함수가 실행되어 UI 설명서를 만드는 단계"**와 **"그 설명서를 DOM에 반영하는 단계"**로 나눠서 바라보면, React의 많은 동작이 다르게 읽힌다.

memo가 왜 효과가 있을 때와 없을 때가 갈리는지, Profiler의 노란색이 무엇을 의미하는지, useEffect가 왜 Commit 이후에만 실행되는지, 모두 이 두 단계의 역할 차이에서 나온다.
