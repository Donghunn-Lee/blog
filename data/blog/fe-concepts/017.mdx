## 배포 후에도 옛날 버전이 보이는 이유

React 앱을 배포하고 나서 버그가 수정됐는지 확인하러 들어갔는데 여전히 이전 화면이 보일 때가 있다. 강력 새로고침(Ctrl+Shift+R)을 하면 반영이 되는데, 일반 사용자는 그 방법을 모른다.

이게 캐싱 때문이다. 브라우저는 한 번 받아온 리소스를 디스크나 메모리에 저장해두고, 같은 URL로 요청이 들어오면 서버에 다시 묻지 않고 저장된 것을 그대로 쓴다. JS 번들 URL이 바뀌지 않았으면, 새 버전을 배포해도 브라우저는 캐시된 옛날 번들을 계속 사용한다.

캐싱 자체가 문제는 아니다. 캐싱이 잘 되면 두 번째 방문부터는 네트워크 요청 없이 리소스를 바로 쓰기 때문에 로딩 속도가 눈에 띄게 빨라진다. 문제는 캐싱과 배포를 어떻게 함께 다루느냐다.

## 캐싱의 동작 원리

서버가 리소스를 응답할 때 `Cache-Control` 헤더를 함께 내려준다.

```
Cache-Control: max-age=31536000
```

브라우저는 이 값을 보고 "이 리소스는 31536000초(1년) 동안은 서버에 다시 물어볼 필요 없다"고 판단한다.
유효기간 내에 같은 URL 요청이 오면 네트워크 요청 자체를 하지 않는다.
DevTools Network 탭에서 `(disk cache)` 또는 `(memory cache)`로 표시되는 게 이 상태다. 응답 코드도 없고, 서버도 모른다.

주요 `Cache-Control` 값을 정리하면 이렇다.

| 값 | 의미 |
|---|---|
| `max-age=N` | N초 동안 캐시 유효 |
| `no-cache` | 저장은 하되, 쓰기 전에 서버에 확인 |
| `no-store` | 저장 자체를 금지 |
| `public` | CDN 같은 중간 프록시도 캐시 가능 |
| `private` | 브라우저만 캐시 가능 |

`public`과 `private`은 CDN(Content Delivery Network)을 쓸 때 중요하다.
`private`으로 설정된 응답은 브라우저 캐시에만 저장되고, CDN 서버는 캐시하지 않는다.
사용자별로 다른 응답(마이페이지 같은)은 반드시 `private`이어야 한다. `public`으로 설정하면 CDN이 응답을 캐시해서 다른 사용자에게도 같은 응답을 내려줄 수 있기 때문이다.

## 유효기간이 지나면 — ETag와 협상 캐시

`max-age`가 지나면 브라우저는 서버에 다시 요청을 보낸다.
이때 "파일이 바뀌지 않았으면 다시 받지 말고 기존 캐시를 써도 되는지" 서버와 협상한다.

서버는 첫 응답에 `ETag` 헤더를 함께 내려준다. ETag는 해당 리소스 내용의 해시값이다.

```
ETag: "abc123"
```

유효기간이 지나면 브라우저는 `If-None-Match` 헤더에 이 값을 담아 재요청한다.

```
If-None-Match: "abc123"
```

서버가 현재 파일의 ETag를 계산해서 같으면 `304 Not Modified`를 반환한다. body 없이 헤더만 오기 때문에 200보다 훨씬 빠르다.
브라우저는 기존 캐시를 그대로 쓴다. 파일이 바뀌었다면 새 파일과 함께 `200 OK`가 온다.

전체 흐름을 정리하면 이렇다.

```
첫 요청
→ 서버: 200 OK + Cache-Control: max-age=3600 + ETag: "abc"

유효기간 내 재요청
→ 브라우저: 저장된 응답 사용 (네트워크 요청 없음)

유효기간 만료 후 재요청
→ 브라우저: If-None-Match: "abc" 헤더와 함께 요청
→ 파일 변경 없음: 304 Not Modified (body 없음)
→ 파일 변경됨: 200 OK + 새 파일 + 새 ETag
```

ETag와 비슷한 역할을 하는 `Last-Modified`도 있다.
파일의 수정 일시를 기준으로 협상하는 방식인데, ETag보다 정확도가 낮다.
파일 내용이 같아도 서버 재배포 등으로 수정 일시가 바뀔 수 있고, 1초 이내에 두 번 수정되면 구분이 안 된다.
때문에 둘 다 지원하는 서버라면 ETag가 우선 사용된다.

## 헷갈리기 쉬운 개념들

**`no-cache`는 캐시를 안 하는 게 아니다**

이름이 직관적이지 않아서 많이 헷갈린다.
`no-cache`는 "저장은 하되, 사용하기 전에 서버에 유효한지 확인해라"는 의미다.
캐시를 아예 사용하지 않으려면 `no-store`를 써야 한다.

**304는 에러가 아니다**

3xx 코드라서 리다이렉트나 오류처럼 보일 수 있는데,
304 Not Modified는 "서버 확인 결과 캐시가 유효하다"는 정상 응답이다.
body가 없어서 200보다 훨씬 빠르다.

**강한 캐시 상태에서는 서버 요청 자체가 없다**

`max-age` 내에서는 네트워크 탭에 요청이 `(disk cache)`로 표시되거나 아예 안 잡힌다.
이 상태에서 서버를 아무리 바꿔도 클라이언트에 반영이 안 된다.
배포 후 변경사항이 안 보인다면 대부분 이 상황이다.

## 캐시 무효화 — 배포와 캐시를 함께 다루는 방법

`max-age`가 긴 캐시는 성능 측면에서 좋지만, 배포할 때 사용자가 최신 파일을 받을 수 없는 문제가 생긴다.
이걸 해결하는 방식이 **캐시 무효화(Cache Busting)** 다.

핵심 아이디어는 단순하다. URL이 바뀌면 브라우저는 새로운 리소스로 인식하고 캐시를 무시한다.
가장 흔한 방법은 파일명에 콘텐츠 해시를 포함하는 것이다.

```
/static/app.abc123.js   ← 파일 내용 기반 해시
```

Vite나 Webpack은 빌드 시 파일명에 콘텐츠 해시를 자동으로 붙여준다(`[contenthash]`).
파일 내용이 바뀌면 해시가 바뀌고, 해시가 바뀌면 URL이 달라져서 새 파일을 받는다. 내용이 바뀌지 않은 파일은 해시가 그대로여서 캐시가 유지된다.

이 전략을 실제로 적용하면 `index.html`과 번들 파일을 다르게 설정하는 패턴이 나온다.

- **JS/CSS 번들**: 해시가 붙어있으니 `max-age=31536000` 같은 긴 캐시를 설정한다. 내용이 바뀌면 어차피 URL이 달라진다.
- **index.html**: `no-cache`로 설정해서 항상 서버에 확인하게 한다. HTML이 최신이어야 그 안에 담긴 번들 URL도 최신을 가리킨다.

HTML을 `no-cache`로 설정하는 게 포인트다.
HTML이 캐시되면 새 번들 URL이 담긴 HTML을 못 받아서, 결국 옛날 번들을 계속 참조하게 된다.

---

## 캐시는 설정의 문제가 아니라 전략의 문제다

개발자에게 있어서 캐시는 `Cache-Controle` 헤더를 서버에서 설정하면 끝나는 것이 아니라, 어떤 리소스에 어떤 전략을 쓸지를 고려해야 한다.

- 캐시를 길게 잡으면 성능은 좋아지지만 배포가 까다로워진다.
- 짧게 잡으면 항상 최신을 보여줄 수 있지만 캐싱 이점이 줄어든다.

이 트레이드오프를 해결하는 게 콘텐츠 해시 기반 캐시 무효화다. 변하지 않는 리소스는 오래, HTML은 항상 최신으로 — 이 조합이 성능과 신선도를 동시에 챙기는 방법이다.
