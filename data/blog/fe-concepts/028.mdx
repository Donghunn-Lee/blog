## SPA - 웹앱을 데스크톱 앱처럼

전통적인 웹사이트(MPA, Multi-Page Application)는 페이지를 이동할 때마다 서버에 새 HTML을 요청하고, 받은 HTML을 처음부터 다시 렌더링한다. 사용자 입장에서는 화면이 한 번 깜빡이고, 헤더나 사이드바처럼 바뀌지 않는 영역도 다시 그려진다.

[#020 브라우저 요청 흐름](/blog/fe-concepts/020/)에서 본 대로, 브라우저는 URL이 바뀌면 그 URL로 서버에 요청을 보내고, 받은 HTML을 파싱해서 다시 렌더링한다. MPA의 페이지 이동이 정확히 이 흐름을 매번 반복하는 구조다.

웹앱이 점점 데스크톱 앱처럼 동작하길 요구받으면서(Gmail, Notion, Trello 같은 것들) 이 방식의 한계가 드러났다. 페이지 전환마다 깜빡임이 생기고, 입력 중이던 폼이나 모달 상태가 날아가고, 매번 HTML 전체를 다시 받기 때문에 네트워크 비용도 컸다.

> **"페이지 이동 없이 화면만 바뀌었으면 좋겠다."**

이 요구가 SPA(Single Page Application)의 출발점이다.

SPA는 **최초에 한 번만 HTML을 받고, 이후의 모든 화면 전환을 JavaScript가 클라이언트에서 처리하는 방식**이다. 페이지가 깜빡이지 않는 이유는 단순하다 — 애초에 새 페이지를 받아온 적이 없으니까.

React, Vue, Angular 같은 프레임워크가 사실상 SPA를 전제로 만들어졌고, 지금 프론트엔드 개발자가 다루는 대부분의 프로젝트가 SPA 기반이다. 그런데 정작 "왜 페이지 이동 없이 URL이 바뀌는가"는 잘 짚지 않고 라우터 라이브러리만 쓰는 경우가 많다. 이 글은 그 안쪽을 본다.

## SPA의 최초 로딩

사용자가 처음 사이트에 접속하면 서버는 거의 비어있는 HTML과 JS 번들을 내려준다.

```html
<!-- 서버가 내려주는 index.html -->
<html>
  <body>
    <div id="root"></div>
    <script src="/bundle.js"></script>
  </body>
</html>
```

`<div id="root">`는 비어있고, `bundle.js`가 다운로드되어 실행되면서 그 안에 React/Vue 등이 컴포넌트를 그려넣는다. 라우터도 이 시점에 함께 초기화된다.

이게 직전 글 [#027 CSR과 SSR](/blog/fe-concepts/027/)에서 다룬 "빈 HTML이 만드는 문제"의 본질이다. SPA는 구조적으로 CSR이고, 첫 화면이 보이려면 JS 번들이 다운로드되고 실행되어야 한다.

> 💡 **SPA = CSR이 아니다, 정확히는 SPA의 기본 동작이 CSR인 것이다.**  
> Next.js의 SSR/SSG도 페이지 전환은 SPA처럼 동작한다. SPA는 "전환 방식"이고 CSR/SSR은 "초기 렌더링 방식"이라 같은 축이 아니다.

## URL이 바뀌는데 서버 요청이 안 간다 — History API

여기가 SPA의 가장 핵심적인 부분이다.

브라우저는 원래 URL이 바뀌면 그 URL로 서버에 요청을 보낸다. 그런데 SPA는 URL이 분명히 `/`에서 `/about`으로 바뀌었는데도 서버에는 아무 요청이 가지 않는다. 이게 어떻게 가능할까?

답은 **History API의 `pushState`**다.

```javascript
// URL을 /about으로 바꾸지만 서버 요청은 발생하지 않는다
history.pushState({}, '', '/about');
```

`pushState`는 브라우저의 히스토리 스택에 항목을 추가하면서 주소창 URL만 갱신한다. **서버 요청 없이 URL만 조작하기 위해 의도적으로 설계된 API**다. HTML5에서 SPA를 위해 표준화된 기능이라고 봐도 된다.

> **참고:** SPA 초창기에는 `pushState`가 없어서 URL의 hash 부분(`#/about`)을 사용했다. hash는 원래 페이지 내 앵커 이동용이라 서버 요청을 일으키지 않는다는 특성을 활용한 것이다. 지금도 일부 라우터에 `HashRouter` 옵션으로 남아 있다.

뒤로가기 버튼을 누를 때는 `popstate` 이벤트가 발생한다. 라우터는 이 이벤트를 듣고 있다가 변경된 URL에 맞는 컴포넌트로 다시 갈아끼운다. `pushState`로 히스토리 스택에 쌓아둔 덕분에 뒤로가기/앞으로가기가 정상 동작한다.

---

## 라우터가 하는 일

`pushState`는 URL만 바꿀 뿐, "이 URL에 어떤 컴포넌트를 그릴지"는 직접 처리해주지 않는다. 그 역할이 라우터(react-router 같은)다.

`<Link to="/about">`을 클릭했을 때 일어나는 일을 단계별로 보면 이렇다.

```
1. 사용자가 <Link to="/about"> 클릭
2. 라우터가 <a> 태그의 기본 동작(서버 요청)을 막음 (e.preventDefault)
3. history.pushState로 URL을 /about으로 변경
4. 라우터가 URL 변경을 감지
5. /about에 매칭되는 <About /> 컴포넌트를 root에 렌더링
6. React가 가상 DOM을 비교해서 변경된 부분만 실제 DOM에 반영
```

서버는 이 과정에서 한 번도 호출되지 않는다. 페이지 전환에 필요한 데이터는 컴포넌트가 마운트된 뒤 클라이언트에서 직접 API로 가져온다. SPA에서 페이지를 옮길 때마다 로딩 스피너를 자주 보게 되는 이유가 이거다 — 서버에서 데이터를 채워서 보내주는 게 아니라, 빈 컴포넌트를 먼저 그리고 클라이언트가 데이터를 가져와서 채우는 구조이기 때문이다.

> 라우터의 본질은 "URL 변경을 감지하고 알맞은 컴포넌트를 렌더링하는 것"이다. SPA의 매직처럼 보이는 동작은 사실 `pushState` + 이벤트 리스너 + 컴포넌트 렌더링의 조합일 뿐이다.

## 첫 로딩이 느린 이유와 Code Splitting

SPA의 가장 큰 약점은 **첫 로딩이 느리다**는 점이다. 첫 화면이 보이려면 JS 번들을 다 받고 실행해야 하기 때문이다. 페이지가 늘어날수록 번들이 커지고, 사용자는 첫 페이지만 보고 떠날 수도 있는데 사용하지도 않을 페이지의 코드까지 받아야 한다.

이 문제를 해결하는 게 **Code Splitting**이다. 번들을 페이지(또는 기능) 단위로 잘라두고, 사용자가 그 페이지로 이동할 때 비로소 해당 청크를 다운로드하는 방식이다.

```javascript
// React에서의 lazy loading
import { lazy, Suspense } from 'react';

const About = lazy(() => import('./pages/About'));

function App() {
  return (
    <Suspense fallback={<Loading />}>
      <Routes>
        <Route path="/about" element={<About />} />
      </Routes>
    </Suspense>
  );
}
```

`import('./pages/About')`이 동적 import다. 빌드 도구(Webpack, Vite 등)는 이걸 감지하고 `About` 컴포넌트를 별도 청크로 분리한다. 사용자가 `/about`으로 이동하는 순간에야 그 청크를 네트워크로 가져온다.

> ⚠️ **Code Splitting을 너무 잘게 쪼개면 오히려 느려진다.**  
> 청크가 작아지는 건 맞지만 네트워크 요청 수가 늘어나고, 화면 곳곳에 로딩 스피너가 뜨면서 UX가 나빠진다. 무겁고(차트 라이브러리, 에디터) 즉시 안 보이는(모달, 특정 탭) 컴포넌트만 잘라내고, 가벼운 건 메인 번들에 두는 게 낫다. 라우트 단위가 무난한 출발점이다.

## 새로고침하면 404가 나는 이유

SPA 라우팅을 설정한 뒤 흔히 만나는 문제가 있다. `/about` 페이지에서 새로고침을 눌렀더니 갑자기 404가 뜬다.

이유는 단순하다. SPA에서 `/about`은 클라이언트 라우터가 만들어낸 가상의 경로다. 실제 서버에는 `/about.html` 같은 파일이 없고, `index.html` 하나만 있다. 평소엔 `<Link>`로 이동하니까 서버 요청이 안 가서 문제가 없는데, 새로고침을 하면 브라우저가 `/about`을 서버에 직접 요청해버린다. 서버는 그런 경로를 모르니까 404를 반환한다.

해결은 서버에서 **모든 경로를 `index.html`로 fallback**시키는 것이다.

```nginx
# Nginx 설정 예시
location / {
  try_files $uri $uri/ /index.html;
}
```

Vercel, Netlify 같은 SPA 호스팅 서비스는 이 설정이 기본으로 들어가 있어서 별도로 신경 쓸 일이 없지만, 자체 서버에 SPA를 배포할 때는 반드시 챙겨야 한다. `index.html`이 로드되면 그 안의 JS가 실행되고, 라우터가 현재 URL인 `/about`을 보고 알맞은 컴포넌트를 렌더링한다.

## 헷갈리기 쉬운 부분

**① "Single Page"의 "페이지"는 사용자가 보는 화면이 아니다**

이름 때문에 사용자가 보는 화면이 하나뿐이라고 오해하기 쉽다. 그게 아니라 **서버가 내려주는 HTML 문서가 하나**라는 뜻이다. 사용자 입장에서는 여러 페이지를 오가는 것처럼 보이지만, 브라우저 입장에서는 처음 받은 HTML 하나에서 JS가 내용물을 계속 갈아끼우는 것뿐이다.

**② "SPA = React/Vue"가 아니다**

SPA는 아키텍처 패턴이고, React/Vue는 그걸 구현하기 위한 도구다. 바닐라 JS로도 History API와 직접 만든 라우터로 SPA를 구현할 수 있다. 반대로 React로 만들었다고 무조건 SPA인 것도 아니다 — Next.js의 SSR/SSG 페이지는 첫 진입 기준으로는 SPA가 아니다.

**③ "SPA는 SEO에 무조건 불리하다"**

과거에는 검색 엔진 크롤러가 JS를 실행하지 않아 SPA의 빈 HTML만 보고 가버리는 문제가 있었다. 지금은 Googlebot 같은 주요 크롤러가 JS를 실행해서 렌더링된 결과를 인덱싱한다. 그래도 한계는 있다 — 인덱싱이 늦어질 수 있고, SNS 미리보기 봇은 여전히 JS를 실행하지 않는다.

**④ "빠른 페이지 전환" ≠ "빠른 로딩"**

SPA는 페이지 간 전환이 빠르다(서버 요청 없으니까). 하지만 첫 로딩은 MPA보다 느리다(JS 번들을 다 받고 실행해야 하니까). "SPA가 빠르다"는 말은 어떤 시점을 보느냐에 따라 답이 달라진다.

---

## 정리

SPA의 동작을 한 문장으로 압축하면 이렇게 된다.

> **`pushState`로 URL만 바꾸고, 라우터가 URL 변경을 감지해 컴포넌트를 갈아끼우는 것.**

SPA가 만든 부드러운 페이지 전환 경험은 React 같은 프레임워크의 마법이 아니라, 브라우저가 제공한 History API와 라우터의 조합이다. 그 위에서 첫 로딩 비용은 Code Splitting으로 분산하고, 새로고침 404 같은 운영상의 함정은 서버 fallback으로 메운다.

다음 글에서는 이 흐름 위에서 한 발 더 나아가, **프론트엔드 성능 최적화**를 본다. Code Splitting을 포함한 여러 기법들이 각각 어떤 문제를 해결하는지 — 그리고 왜 측정이 먼저인지 — 를 정리한다.
